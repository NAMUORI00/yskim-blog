스마트팜 추론 서버에서는 Docker Compose와 로컬 스크립트의 실행 경로를 마련했다. 모델 위치, 문맥 길이, 병렬 처리 설정이 경로마다 달라 같은 요청을 처리할 준비 상태를 어떻게 확인할지 정리했다.


## 구현과 확인 과정


smartfarm-llm-inference 저장소의 실행 설정을 살펴봤다. 이 저장소에는 Docker Compose를 통한 컨테이너 실행과 로컬 셸 스크립트 실행, 두 가지 경로가 있었다. 두 경로는 모델을 찾는 위치뿐 아니라 문맥 길이와 병렬 처리 기본값도 달랐고, 서버 프로세스가 떠 있더라도 모델 로딩이 끝나지 않으면 추론 요청을 처리할 수 없다는 점도 함께 확인했다.


모델 파일과 런타임, 로딩과 실제 추론의 구분은 보충편에서 다뤘고, 여기서는 그 구분을 두 실행 경로에 적용했다. 이 글은 소스를 읽은 범위의 기록이며, 실제 GPU 서버를 기동하거나 처리량을 측정하지는 않았다.


## 컨테이너와 로컬 실행의 기본 설정


[기본 Compose](https://github.com/NAMUORI00/smartfarm-llm-inference/blob/ec2d186934b77e5ec272eabf9a0bae7a71baf4ae/docker-compose.yml)는 llama.cpp의 server-cuda 이미지를 사용하고 있었다.


models 디렉터리를 컨테이너의 /models에 마운트하고 기본 GGUF 경로를 인자로 넘긴다. 컨텍스트 크기 기본값은 16384, 병렬 슬롯은 2로 설정돼 있었고, 호스트 포트 45857이 컨테이너의 8080에 연결돼 있었다.


[로컬 실행 스크립트](https://github.com/NAMUORI00/smartfarm-llm-inference/blob/ec2d186934b77e5ec272eabf9a0bae7a71baf4ae/scripts/llm/run-llama-local.sh)는 컨텍스트 4096과 --parallel 4를 넘기고 있었다.


이 스크립트는 로컬 빌드 경로의 llama-server를 먼저 찾고, 없으면 PATH에서 실행 파일을 탐색한다. 모델 경로를 명시하지 않았을 때는 후보 파일을 순서대로 확인한다. 같은 저장소에 들어 있는 두 방식이지만 기본 설정이 달라, 메모리 사용량과 동시 처리 조건을 비교할 때 동일한 실행 환경으로 전제하기는 어려웠다.


| 항목          | 기본 Compose      | 로컬 스크립트                |
| ----------- | --------------- | ---------------------- |
| 실행 파일       | server-cuda 이미지 | 로컬 빌드 또는 PATH          |
| 기본 ctx-size | 16384           | 4096                   |
| 기본 parallel | 2               | 4                      |
| 모델 위치       | 컨테이너 /models    | 로컬 파일 후보 또는 MODEL_PATH |
| 실행 흔적       | 컨테이너 상태와 로그     | PID 파일과 로그 파일          |


표의 ctx-size는 각 스크립트가 인자로 넘긴 값이다. 요청별 실제 사용 가능 토큰 수는 입력 길이와 실행 조건에 따라 달라진다. llama.cpp 버전과 병렬 설정에 따라 슬롯별 컨텍스트, KV 캐시, 메모리 배치가 달라질 수 있고, 시작 로그와 런타임 문서를 대조해야 실제 할당을 파악할 수 있다. Compose 파일에는 별도의 컨텍스트 관련 환경 변수도 있었는데, 각각의 효과를 확인하지 않은 상태여서 한 숫자로 합쳐 적지 않았다.


## 실행 전 모델 파일 확인


로컬 스크립트는 실행 파일이 실행 가능한지, 모델 파일이 존재하는지를 검사한다. 둘 중 하나라도 없으면 메시지를 남기고 종료된다. 후보를 찾는 로직은 이미 내려받은 GGUF로 바로 실행할 수 있도록 구성돼 있었지만, 모델을 자동으로 다운로드하는 단계는 포함돼 있지 않았다.


![03-04-01.png](/images/notion/tech-03-04/image-1.png)


그림 1. 로컬 실행 스크립트의 파일 확인과 백그라운드 시작 경로. 출처: 모델 서버 시작 스크립트를 바탕으로 직접 구성.


nohup으로 프로세스를 시작한 뒤 PID를 기록하고 경로를 출력하는 부분이 이어졌다. 여기까지는 시작을 요청한 흔적이었다. 모델 포맷이 맞지 않거나 메모리가 부족해 곧바로 종료되는 경우를 걸러 주는 준비 완료 검사는 이 스크립트에 없었다. 파일 존재→프로세스 시작→모델 로딩→실제 요청의 네 단계로 나누어 보니, 시작 메시지 이후의 로딩과 추론 결과는 별도 확인 항목으로 남았다.


사용된 이미지 태그가 커밋이나 다이제스트로 고정돼 있지 않은 점도 확인했다. 저장소 커밋을 고정하더라도 나중에 같은 태그가 가리키는 이미지 내용은 바뀔 수 있다. 실행 결과를 비교할 때 모델 파일 해시와 런타임 버전 또는 이미지 다이제스트를 함께 남겨 두면 재현에 도움이 된다.


## health 검사와 종료 코드 처리


[관리 스크립트](https://github.com/NAMUORI00/smartfarm-llm-inference/blob/ec2d186934b77e5ec272eabf9a0bae7a71baf4ae/scripts/llm/llama-local-manage.sh)의 health 분기를 보면, curl 뒤에 `|| true`가 붙어 있었다.


연결이 실패해도 분기의 종료 코드는 성공처럼 끝날 수 있었다. curl에는 HTTP 오류를 실패로 처리하는 옵션도 없었다. 그래서 이 명령의 반환값 0만으로 서버 준비 상태를 판단하기는 어려웠다.


llama.cpp의 [서버 문서](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)에는 health 엔드포인트와 생성 API가 구분돼 설명돼 있다.


준비 상태를 확인하려면 설치된 버전에 맞는 응답 상태와 본문을 읽고, 작은 생성 요청의 결과까지 확인하는 과정이 따로 필요하다. health 응답이 정상이더라도 원하는 모델과 프롬프트 조합에서 기대한 답변이 생성되는지는 별도 확인 대상이다.


![readable-03-04-02.png](/images/notion/tech-03-04/image-2.png)


그림 2. 시작 이후에 따로 수행할 준비 상태와 생성 확인 절차. 추가 점검을 위해 구성한 흐름이다. 출처: 직접 구성.


Orin용 [Compose 덮어쓰기 파일](https://github.com/NAMUORI00/smartfarm-llm-inference/blob/ec2d186934b77e5ec272eabf9a0bae7a71baf4ae/docker-compose.orin.yml)에는 컨텍스트 기본값이 4096으로 설정돼 있었다.


이 파일이 존재한다는 것과 특정 Orin 장치에서 속도, 품질이 검증됐다는 것은 다른 문제다. 실제로 사용하려면 이미지의 아키텍처 호환 여부, GPU 런타임 설정, 병합된 Compose 결과, 시작 로그를 각각 확인해야 한다.


이 글에서 확인한 것은 모델 서버를 시작하고 관리하는 설정의 구조와 차이점이다. 큐 대기시간, 첫 토큰 지연, 시간 초과 후 서버 측 취소 같은 런타임 정책은 별도 계측이 필요하고, 이 글의 범위에는 포함되지 않았다. 다음 글에서는 벤치마크 코드가 이 시간을 어디서 재는지 살펴볼 예정이다. 클라이언트 측 측정 시간과 서버 측 측정 시간이 다를 때 그 차이를 곧바로 네트워크 지연으로 볼 수 있는지도 확인할 부분이다.


## 작업을 정리하며


모델 서버의 준비 상태는 프로세스 실행과 모델 로딩을 나누어 보아야 한다. 실행 경로별 기본값을 비교한 표가 있으면 환경 차이를 입력 조건과 연결하기 쉽다. 요청 전에 확인할 항목도 이 구분을 중심으로 구성하려 한다.
