Detection_Track에서는 객체 추적 중 ID를 연결하고 복구하는 경로를 다뤘다. 관측이 끊긴 뒤의 대상 연결과 선택적인 VLM 호출이 맞물려 있어 점수, 임계값, 호출 조건을 분리해 정리했다.


## 구현과 확인 과정


Detection_Track과 Detection_Track_paper_draft의 코드와 문서를 읽으며, 객체 추적에서 움직임, 외형 특징, ID 복구가 어떻게 나뉘어 있는지 정리했다. 검출은 프레임에서 박스 위치를 찾는 단계이고, 추적은 프레임 사이에서 같은 대상을 이어 붙이는 단계다. 가려졌다 다시 나타난 경우에는 새 박스가 생겼다는 사실만으로 이전 대상과 연결되지 않으므로, 별도의 ID 복구 절차가 개입한다.


객체 검출과 추적, IoU와 특징 벡터 개념이 배경 지식에 해당한다. 이 글은 사람이 누구인지 실명으로 알아내는 식별은 다루지 않으며, 영상 안에서 일관된 임시 track ID를 유지하는 연관 문제와 그 판단을 검토할 기록을 정리한 것이다.


## 검출과 ID 연결을 나누어 보기


[ByteTrack](https://arxiv.org/abs/2110.06864)은 낮은 점수의 검출도 트랙과 연결해 유효한 객체를 회수하는 접근을 다룬다.


[BoT-SORT](https://arxiv.org/abs/2206.14651)는 움직임과 외형, 카메라 움직임 보정을 함께 사용하는 추적 방식이다. 이 두 접근을 배경에 두면, 검출 임계값을 조정하는 것과 재식별 특징으로 끊긴 트랙을 복구하는 것은 서로 다른 선택지에 해당한다.


Detection_Track의 [실시간 검출과 추적 처리](https://github.com/NAMUORI00/Detection_Track/blob/01d05e773c864348252c31a2607ebbdfdc029a5b/detection_track/tracker/runtime.py)는 YOLO 검출, BoT-SORT 추적에 Re-ID 특징, 메모리 뱅크, ID 복구를 결합한다.


구성에 따라 Re-ID를 끄거나 시각 특징 추출기를 선택할 수 있고, VLM 직접 사용 경로도 별도로 존재한다. VLM 호출 여부는 실행 옵션과 분기 조건에 따라 결정된다.

## 두 프레임을 기다려 보정하는 설정


[시각언어모델 없이 짧은 추적 구간을 보정하는 실험 설정](https://github.com/NAMUORI00/Detection_Track/blob/01d05e773c864348252c31a2607ebbdfdc029a5b/configs/experiments/final/zero_vlm_tracklet_correction.yaml)은 VLM을 끄고, DINOv2 계열 시각 특징과 tracklet 보정을 켠 실험 설정이다.


tracklet_length는 2, output_delay_frames는 1이며, threshold_source에는 임계값을 얻은 원천이 따로 적혀 있다. 학습 데이터나 정답을 이용한 설정 선택 이력을 설명하는 정보다. 실행 중에는 선택된 설정을 사용한다.


코드는 새 트랙이 생기면 비교 후보와 첫 특징을 저장한다. 두 번째 특징이 들어오면 현재 tracklet의 평균 단위 벡터와 후보 특징의 평균 단위 벡터를 비교한다. 가장 높은 점수가 임계값 이상이면 id_remap에 이전 ID를 연결한다. 그 전에 트랙이 사라지거나 특징이 충분히 들어오지 않으면 별도의 건너뜀 이유를 기록한다.


설명용으로 프레임 100에서 새 ID 21이 생기고 101에서도 이어졌다고 하자. 후보 ID 7과의 점수가 0.93, ID 9와의 점수가 0.88이고 임계값이 0.90이면 7을 선택할 수 있다. 임계값의 역할을 설명하기 위해 실제 설정을 단순화했다. 점수가 임계값을 넘더라도 같은 사람이라는 보장은 아니며, 잘못된 연결이 얼마나 발생하는지는 별도 평가 항목으로 남아 있다.

그림 2. 두 프레임 tracklet을 모아 판단하는 설명용 예제. ID와 점수는 흐름 설명을 위해 정한 예시다. 출처: _zero_vlm_register_pending_tracks와 _zero_vlm_update_pending_tracks를 바탕으로 직접 구성.


두 프레임의 정보를 보고 시작 시점부터 출력 ID를 맞추려면 첫 프레임 결과를 바로 확정할 수 없다. 이 때문에 설정의 출력 지연은 처리 시간과는 별도의 값으로 읽힌다.


코드에서 버퍼를 비우는 시점과 remap을 적용하는 시점을 보면, 오프라인에서 완성된 트랙을 수정하는 방식과 실시간에 가까운 출력 제약 사이에 차이가 있다. 1프레임 지연 설정이 있다고 전체 시스템 지연이 1프레임뿐이라고 해석하지는 않는다.


## VLM 판정과 정답 대조


연구 문서는 VLM을 런타임에 계속 넣기보다 오프라인 감사에서 충돌 신호를 얻는 방향을 설명한다. [감사 코드](https://github.com/NAMUORI00/Detection_Track/blob/01d05e773c864348252c31a2607ebbdfdc029a5b/detection_track/research/audit_runtime_vlm_events.py)는 예측 박스를 해당 프레임의 MOT 정답 박스와 IoU로 대응시킨다.


두 트랙이 같은 정답 ID에 연결되는지에 따라 수락, 거부를 평가할 수 있다. 다만 대응이 불분명한 경우, 모델의 일치 여부만으로는 정답이 확정되지 않는다.


여러 특징 표현이나 모델이 같은 결론을 내렸다는 사실도 이 감사와는 다르다. 서로 비슷한 오류를 내면 합의가 높아도 잘못된 ID를 연결할 수 있다. 선택한 teacher 후보, 감사 후 남긴 신호, 그 신호를 경량 모델로 옮겨 성공한 결과는 각각 별개의 단계다.


[별도 원고](https://github.com/NAMUORI00/Detection_Track_paper_draft/blob/efe478caa1b1de50ce770d8e252a9caebb07eb1c/paper.md)도 working teacher source와 최종 selected teacher를 나누고 배포 준비 완료를 주장하지 않는다.


원고의 일부 수치를 범용 성능 개선으로 요약하면 해당 결과가 어느 데이터 분할과 어떤 보정 경로에서 나왔는지가 빠진다. 이 글에서는 원고에 적힌 실험을 새로 재현했다고 보고하지 않는다.


이번에 확인한 보정 코드는 같은 사람을 다시 연결하려는 선택을 기록할 수 있게 돼 있다. 사건의 의도와 행위 의미는 추적 결과에 추가 맥락을 결합해 판단해야 한다. 다음에는 ID가 연결된 출력 스트림을 기준선과 비교하면서, 복구가 늘어난 만큼 잘못된 연결도 늘었는지, 지연과 실패가 어느 구간에 생겼는지를 함께 읽어 보고 싶다.


## 작업을 정리하며


ID 복구를 평가하려면 같은 대상이라는 판정 근거와 복구 후의 추적 결과를 함께 보아야 한다. 임계값을 고른 이력까지 남기면 설정 변경의 영향을 비교하기 쉽다. 사건의 의미 해석은 그 추적 결과에 추가 근거를 결합할 단계로 본다.
