영상에서 움직이는 사람을 계속 따라가려면 위치 찾기와 번호 잇기가 차례로 동작해야 한다. 먼저 사진 한 장에 해당하는 각 프레임에서 사람의 박스 위치를 찾는 **객체 검출**(object detection)을 수행한다. 그다음 프레임 사이에서 같은 대상을 찾아 이어 붙이는 **객체 추적**(object tracking)을 진행한다. 여기서 추적은 인물의 실명을 알아내는 일이 아니라, 한 영상 안에서 같은 대상에게 일관된 임시 번호(`track ID`)를 유지하는 연관 문제다. 대상이 장애물이나 다른 사람 뒤에 가려졌다가 다시 나타나면 새 검출 박스가 생긴다. 이때 박스 위치만으로는 조금 전에 사라진 대상과 바로 이어지지 않아서, 끊어진 번호를 다시 잇는 **ID 복구** 절차가 필요하다.


`Detection_Track`과 `Detection_Track_paper_draft` 저장소의 코드와 문서를 읽으며 실시간 추적 경로의 구성을 확인했다. 움직임 연결과 외형 특징 추출이 어떻게 나뉘는지, 그리고 끊긴 번호를 다시 이을 때 특징 점수와 출력 지연, 정답 대조 감사가 어떤 조건으로 맞물리는지 따라가 보았다.


## 검출과 ID 복구 구조


한 대상에게 같은 번호가 이어진 흐름을 트랙이라고 부르는데, 추적기가 대상을 놓치지 않는 방법은 검출 단계의 접근과 끊긴 트랙을 다시 잇는 접근으로 나뉜다. [ByteTrack](https://arxiv.org/abs/2110.06864)은 검출기가 매긴 확신 점수인 검출 점수가 낮은 박스도 버리지 않고 기존 트랙과 연결해 가려진 객체를 회수한다. [BoT-SORT](https://arxiv.org/abs/2206.14651)는 대상의 움직임 예측과 외형 정보, 카메라 움직임 보정을 함께 사용해 프레임 사이의 연결을 유지한다. 이 두 방식은 프레임마다 연결이 끊기지 않게 버티거나 낮은 점수의 박스를 살리는 검출 및 연관 단계에 가깝다. 반면 대상을 놓쳐 트랙이 완전히 끊긴 뒤에는, 겉모습을 숫자 배열로 바꾼 특징 벡터를 비교해 같은 대상인지 다시 알아보는 **재식별**(Re-ID)이 필요하다. 즉 검출 기준 점수인 임계값을 조정해 박스를 살리는 것과 Re-ID 특징 벡터로 끊긴 트랙을 복구하는 것은 서로 다른 단계의 선택지다.


`Detection_Track`의 [실시간 검출과 추적 처리](https://github.com/NAMUORI00/Detection_Track/blob/01d05e773c864348252c31a2607ebbdfdc029a5b/detection_track/tracker/runtime.py) 코드는 YOLO 검출과 BoT-SORT 추적 위에 Re-ID 특징 추출을 결합한다. 여기에 트랙별 특징 이력 저장소(메모리 뱅크)와 ID 복구 로직을 함께 둔다. 그림 1처럼 각 프레임에서 검출된 박스가 BoT-SORT를 거쳐 임시 ID를 받으면, 코드는 사람 영역의 외형 특징을 추출해 이력을 쌓는다. 새로 나타난 트랙은 이전에 잃어버린 트랙의 이력과 비교해 ID를 그대로 유지하거나 원래 ID로 복구한다. 설정에 따라 Re-ID를 끄거나 시각 특징 추출 모델을 바꿀 수 있으며, 이미지와 글을 함께 다루는 시각언어모델(VLM)을 직접 호출하는 경로도 따로 마련돼 있다. 실행 중에 VLM을 실제로 호출할지는 실행 옵션과 코드의 분기 조건에 따라 결정된다.


![영상 프레임이 YOLO 검출과 BoT-SORT 연관을 거쳐 임시 ID를 받고, 사람 영역 특징 추출로 쌓은 트랙별 특징 이력과 비교해 끊긴 트랙과 재연결할지 판단하는 흐름도](/images/notion/tech-04-05/image-1.png)

## 두 프레임 특징 비교와 ID 복구


VLM을 매번 호출하지 않고 시각 특징만으로 끊긴 ID를 잇는 방식은 [시각언어모델 없이 짧은 추적 구간을 보정하는 실험 설정](https://github.com/NAMUORI00/Detection_Track/blob/01d05e773c864348252c31a2607ebbdfdc029a5b/configs/experiments/final/zero_vlm_tracklet_correction.yaml) 파일에서 구체적으로 확인할 수 있다. 이 설정은 VLM 호출을 끄는 대신 DINOv2 계열 시각 특징 추출기와 짧은 추적 구간(`tracklet`) 보정을 켠다. 여기서 비교할 구간 길이인 `tracklet_length`는 `2`, 출력을 늦추는 프레임 수인 `output_delay_frames`는 `1`로 지정돼 있다. 함께 적힌 `threshold_source` 항목은 기준 임계값을 어디서 얻었는지 남기는 기록이다. 학습 데이터나 정답을 참고해 설정값을 고른 이력을 적어 둔 것이며, 실제 실행 중에는 그렇게 선택된 고정 임계값을 그대로 사용한다.


구체적인 예로 프레임 100에서 새 트랙 `ID 21`이 생기고 다음 프레임 101에서도 이어진 상황을 본다. 런타임 코드는 프레임 100에서 새 트랙이 나타나면 이전 트랙 후보들과 첫 번째 프레임의 특징 벡터를 대기 목록에 저장한다. 이어서 프레임 101에서 두 번째 특징 벡터가 들어오면, 두 프레임 특징을 평균 내 크기를 1로 맞춘 단위 벡터와 후보 트랙들의 평균 단위 벡터를 비교한다. 이때 이전에 끊긴 후보 `ID 7`과의 유사도 점수가 `0.93`, `ID 9`와의 점수가 `0.88`이고 기준 임계값은 `0.90`이라고 가정한다. 그림 2처럼 임계값을 넘은 최상위 후보 `ID 7`이 선택되어, 번호 변환 사전인 `id_remap`에 새 `ID 21`이 이전 `ID 7`로 연결된다. 만약 두 번째 특징이 들어오기 전에 트랙이 사라지거나 특징이 충분히 모이지 않으면 복구를 건너뛰고 그 이유를 따로 기록한다. 물론 유사도 점수가 임계값을 넘었다고 해서 두 트랙이 실제로 같은 사람이라는 보장은 없으므로, 잘못된 연결이 얼마나 생기는지는 별도의 평가 항목으로 확인해야 한다.


![프레임 100과 101에서 모은 ID 21의 특징을 후보 ID 7(0.93), ID 9(0.88)와 비교해 임계값 0.90 이상인 ID 7로 연결하고 기록하는 흐름도](/images/notion/tech-04-05/image-2.png)


그림 2. 두 프레임의 특징을 모아 후보와 비교하고 ID 복구를 결정하는 예제 흐름. 출처: _zero_vlm_register_pending_tracks와 _zero_vlm_update_pending_tracks를 바탕으로 직접 구성.


## 첫 프레임 보정과 출력 지연


앞선 예처럼 두 프레임의 정보를 모은 뒤에야 첫 프레임부터 일관된 ID를 내보낼 수 있다면, 첫 프레임이 들어온 시점에는 결과를 바로 확정할 수 없다. 그림 3처럼 프레임 100에서 등장한 `ID 21`을 프레임 100 출력부터 `ID 7`로 바꾸려면, 프레임 101의 특징이 들어올 때까지 출력을 보류해야 하기 때문이다. 설정에 적힌 `output_delay_frames: 1`은 연산에 걸리는 처리 시간과는 별개로, 판단을 위해 앞 프레임을 1프레임 동안 붙잡아 두는 논리적 출력 지연을 뜻한다.


![프레임 100에서 새 ID 21의 출력을 1프레임 보류했다가 프레임 101에서 판정을 마친 뒤 프레임 100과 101 모두 ID 7로 출력하는 과정](/images/notion/tech-04-05/image-3.png)


그림 3. 두 프레임의 특징으로 첫 프레임 ID까지 보정하기 위해 1프레임 출력 지연이 발생하는 과정.


코드에서 대기 버퍼를 비우는 시점과 `id_remap`을 적용하는 시점을 따라가 보면 실시간 처리의 제약이 드러난다. 영상을 끝까지 다 처리한 뒤 오프라인에서 트랙을 고치는 방식과 달리, 실시간에 가깝게 결과를 내보내려면 대기할 수 있는 프레임 수가 제한되기 때문이다. 또한 설정에 1프레임 지연이라고 적혀 있더라도 이는 버퍼링 단계의 기준일 뿐, 검출과 특징 추출 시간을 포함한 전체 시스템 지연이 1프레임뿐이라는 뜻은 아니다.


## 오프라인 VLM 감사와 정답 대조


시각 특징 점수만으로는 두 트랙이 같은 사람인지 판단하기 모호한 구간도 생긴다. 연구 문서는 이런 구간을 다룰 때 실행 중에 VLM을 계속 호출하기보다, 오프라인 감사(audit)에서 판단이 엇갈리는 충돌 신호를 수집하는 방향을 설명한다. [감사 코드](https://github.com/NAMUORI00/Detection_Track/blob/01d05e773c864348252c31a2607ebbdfdc029a5b/detection_track/research/audit_runtime_vlm_events.py)는 추적기가 예측한 박스를 같은 프레임의 다중 객체 추적(MOT) 정답 박스와 **IoU**(Intersection over Union)로 대응시킨다. 여기서 IoU는 두 박스를 합친 전체 영역 가운데 서로 겹치는 영역의 비율을 뜻한다. 비교 대상인 두 트랙이 같은 정답 ID에 매핑되는지를 보면, ID 복구를 수락하거나 거부한 판단이 맞았는지 평가할 수 있다. 다만 그림 4처럼 예측 박스와 정답 박스의 IoU 대응 자체가 불분명한 경우에는, 모델들의 판단이 일치한다는 사실만으로는 정답 여부를 확정할 수 없다.


![예측 트랙 박스와 MOT 정답 박스를 IoU로 대응시켜 대응이 명확하면 같은 정답 ID 여부로 평가하고, 불분명하면 모델 합의만으로 확정하지 않는 구조도](/images/notion/tech-04-05/image-4.png)


그림 4. 예측 박스를 MOT 정답 박스와 IoU로 대응시켜 ID 연결 여부를 평가하는 오프라인 감사 흐름.


여러 특징 표현이나 모델이 같은 결론을 내렸다는 사실 역시 정답을 대조하는 감사와는 구분해야 한다. 서로 다른 모델이라도 비슷한 상황에서 같은 오류를 내면, 모델 간 합의가 높아도 잘못된 ID를 연결할 수 있기 때문이다. 그래서 비교에 사용한 교사 모델 후보(`working teacher source`)와 감사를 거쳐 걸러낸 신호는 서로 구분해야 한다. 걸러낸 신호를 경량 모델로 옮겨 실제로 효과를 확인한 결과 역시 별개의 단계로 다루어야 한다. [별도 원고](https://github.com/NAMUORI00/Detection_Track_paper_draft/blob/efe478caa1b1de50ce770d8e252a9caebb07eb1c/paper.md)에서도 실험에 쓴 `working teacher source`와 최종 선택된 `selected teacher`를 구분해 적고 있다. 또한 현 단계가 배포 준비까지 마친 상태라고 주장하지 않으며, 일부 수치만 떼어 내 범용 성능 개선으로 요약하면 데이터 분할과 보정 경로의 맥락이 빠지게 된다.


## 결론


`Detection_Track`의 보정 코드는 두 프레임의 외형 특징을 비교해 끊긴 ID를 복구하며, 첫 프레임 번호까지 맞추기 위해 1프레임의 출력 지연을 둔다. 이때 코드는 끊긴 대상을 다시 연결할 때마다 후보 점수와 임계값 출처(`threshold_source`), 건너뜀 이유를 함께 남기도록 짜여 있다. 따라서 ID 복구 성능을 제대로 평가하려면 같은 대상이라고 판정한 근거와 복구 이후의 추적 결과를 정답 데이터와 대조해 함께 살펴야 한다.


이 글에서는 저장소 코드와 원고의 구성을 검토해 추적과 감사 경로를 확인했을 뿐, 원고의 실험을 새로 재현하지는 않았다. 영상 속 사건의 의도나 행위의 의미 역시 추적 결과 위에 추가 맥락을 결합해 판단할 다음 단계의 문제다. 이어지는 작업에서는 ID가 복구된 출력 스트림을 기준선과 대조해, 복구 성공과 함께 잘못된 연결도 늘었는지, 출력 지연과 연결 실패가 어느 구간에서 생기는지 확인할 생각이다.
