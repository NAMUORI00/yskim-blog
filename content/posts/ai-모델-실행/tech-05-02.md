MedEdge의 응답 시간을 정리하며 모델 초기화와 토큰 생성의 측정 구간을 나누었다. Android 코드의 generationMs가 포함하는 작업을 확인하고, 에뮬레이터 기록과 실기기에서 확인할 항목을 구분했다.


## 구현과 확인 과정


앞 글에서 정리한 생성 경로에 이어, MedEdge Android 구현의 시간 측정 구간을 확인해 봤다. generationMs라는 필드가 실제로 어디서부터 어디까지를 재는지, 모델 초기화가 그 안에 포함되는지를 코드에서 따라갔다.


모델 파일과 런타임의 차이, 양자화와 메모리의 관계는 기초편에서 이어 읽을 수 있다. 이 글에서는 generationMs가 담고 있는 구간을 확인하고, 그 값으로 실제 생성 속도를 어디까지 설명할 수 있는지 정리했다.


## APK 구성과 모델 실행 조건


[APK 검사 스크립트](https://github.com/NAMUORI00/ondevice-medical-rag/blob/d5dd214987338e1e57664bb6143ce9d38436c14e/scripts/verify_android_apk.py)는 샘플 QA 파일과 arm64-v8a, x86_64용 런타임 라이브러리를 확인한다.


모델 가중치 확장자와 일부 원본 자료 경로가 APK에 들어가 있는지도 검사한다. 모델은 앱 설치 파일과 별도로 준비하는 구성이어서, APK 검사를 통과했더라도 모델까지 준비된 상태라고 보기는 어렵다.


권한 검사에는 INTERNET 허용 여부를 구분하는 옵션도 있다. 기본 검사는 해당 권한이 있으면 실패한다. 이는 검사한 APK의 구성에 관한 결과다. 다른 빌드 변형이나 외부 구성 요소의 동작까지 한꺼번에 검증한 결과로 넓힐 수는 없다.


이 구분은 실패 원인을 좁히는 데 쓸 수 있다. 앱 설치가 안 되면 패키지와 기기 ABI를 살피고, 모델 파일이 없으면 배치 경로를 확인하고, 파일이 있는데 생성이 실패하면 포맷, 런타임, 가용 메모리 쪽을 살피는 식이다. 모든 경우를 '온디바이스 실행 실패'로 뭉뚱그리면 다음에 어디부터 볼지 알기 어렵다.

## 모델 파일 존재 검사


[LiteRtGemmaEngine.kt](https://github.com/NAMUORI00/ondevice-medical-rag/blob/d5dd214987338e1e57664bb6143ce9d38436c14e/android/MedEdgeRag/app/src/main/java/com/mededge/rag/LiteRtGemmaEngine.kt)의 isReady는 File(resolvedModelPath()).isFile을 반환한다.


이름만 보면 추론 준비가 끝났다는 뜻처럼 읽히지만, 실제로 확인하는 범위는 파일 존재 여부였다. 파일이 손상됐거나 런타임이 지원하지 않는 포맷이어도 이 단계를 통과할 수 있었다.


generate 안으로 들어가야 EngineConfig를 만들고 Backend.CPU()를 선택한다. 이어서 엔진 초기화, 대화 생성, sendMessage, 문자열 변환을 수행한다. 따라서 이 커밋의 Android 실행 경로를 GPU나 NPU 가속 결과로 설명할 근거는 없다.


LiteRT-LM 공식 Kotlin 안내는 여러 실행 백엔드를 다루지만, 이 프로젝트가 실제로 넘긴 옵션은 코드에서 별도로 확인한 것이다. [LiteRT-LM Kotlin 문서](https://github.com/google-ai-edge/LiteRT-LM/blob/main/docs/api/kotlin/getting_started.md)


엔진의 수명도 함께 살펴봤다. Engine(...).use 블록이 generate 안에 있어, 요청마다 엔진을 만들고 초기화한 뒤 닫는 구성이었다. 엔진을 유지하면 반복 초기화 비용을 줄일 여지가 있지만, 메모리 점유와 앱 생명주기, 동시 요청 처리도 함께 고려할 부분으로 남는다.


현재 구성은 호출이 끝나는 지점에서 자원 정리가 드러난다는 점이 명확하다. 어느 쪽이 더 적절한지는 실제 기기에서 반복 요청 조건을 비교해 봐야 판단할 수 있는 부분이다.


## 초기화를 포함한 생성 시간 측정


[MedEdgeRagEngine.kt](https://github.com/NAMUORI00/ondevice-medical-rag/blob/d5dd214987338e1e57664bb6143ce9d38436c14e/android/MedEdgeRag/app/src/main/java/com/mededge/rag/MedEdgeRagEngine.kt)는 generator.generate(prompt) 호출 전후를 재서 generationMs에 넣는다.


그 안에서 엔진 초기화도 수행되므로, 이 값은 토큰 출력 시간만 나타내지 않는다. 종료 시 자원 정리까지 호출 범위에 포함되고, 캐시 효과가 있을 수 있어 매 호출이 완전히 같은 콜드 스타트라고 단정하기도 어렵다.


![05-02-02.png](/images/notion/tech-05-02/image-2.png)


그림 2. generationMs가 둘러싼 실행 구간과 생성 호출을 건너뛰는 경로. 출처: MedEdgeRagEngine.kt와 LiteRtGemmaEngine.kt를 바탕으로 직접 구성. 초기화 외에 생성 단계의 예외도 같은 대체 경로로 처리된다.


설명용으로 요청 세 개를 가정해 보면, 첫 요청은 모델 파일이 없어 생성 호출을 건너뛰었고, 두 번째는 초기화 도중 예외가 났으며, 세 번째는 문자열 응답을 받았다. 첫 요청의 generationMs는 0, 두 번째는 실패하기까지의 시간, 세 번째는 초기화를 포함한 호출 시간이다. 이 셋을 평균 내서 '모델 평균 추론 지연'이라고 부르면 서로 다른 사건이 하나로 섞인다.


| 경로                | usedLocalModel | generationMs 해석        |
| ----------------- | -------------- | ---------------------- |
| 근거 없음 또는 모델 파일 없음 | false          | 생성 호출을 건너뛴 값 0         |
| 생성 호출 중 예외        | false          | 예외가 반환되기까지의 시간         |
| 생성 호출 성공          | true           | 초기화, 응답, 자원 정리를 포함한 시간 |


usedLocalModel은 로컬 모델 사용 여부를 나타내는 값이다. 코드에서는 generated.isSuccess를 사용하는데, 예외 없이 문자열을 받았는지와 그 문장이 검색 근거에 맞는지, 질문에 충분히 답했는지는 별도의 평가 영역이다. generationMs를 출력 토큰 수로 나눠 토큰당 시간을 구하는 계산도, 초기화 비용이 포함되어 있어 해석이 달라진다.


## 기기 평가표에 남겨야 할 조건


저장소 README의 에뮬레이터 설정과 실제 휴대전화 측정은 구분해서 읽어야 한다. 이 기록은 Pixel 7 프로필의 x86_64 에뮬레이터 실행에 해당한다. 물리 Pixel 7의 속도는 별도 측정이 필요하다.


[Android 실행 안내](https://github.com/NAMUORI00/ondevice-medical-rag/blob/d5dd214987338e1e57664bb6143ce9d38436c14e/android/MedEdgeRag/README.md)


후속 측정 항목은 기기 모델, 칩, ABI, OS, 모델 파일 해시, 런타임 버전, CPU 백엔드, 입력 길이와 출력 길이로 정리했다. 같은 행에 조건을 남기고 초기화와 응답 시간을 분리하면 비교 기준을 맞출 수 있겠다. 성공, 대체 응답, 예외 건수도 나누어 보면 앱 응답성과 모델 동작을 함께 살펴볼 수 있다.


반복 호출에 따른 발열이나 메모리 상태 변화까지 통제해야 두 구성을 비교할 근거가 생긴다. 코드를 읽어 측정 구간을 확인했다. 실기기 성능은 후속 측정 항목이다.


다음 글에서는 GPU 연산을 바꾸는 커널 코드와 모델을 불러오는 웹 UI를 살펴본다. 각 도구가 맡은 호출을 따라가며, 추론 과정에 관여하는 위치를 정리한다.
