휴대전화 안에서 직접 인공지능(AI) 언어 모델을 돌리는 **온디바이스**(on-device) 앱은 답변이 나오기까지 걸린 시간을 숫자로 기록한다. 앞 글에서 다룬 의료 질의응답 앱 MedEdge도 로컬 검색과 답변 생성을 마친 뒤 걸린 시간을 `generationMs` 항목에 기록한다. 이름만 보면 답변 조각(토큰)을 만든 시간 같지만, 초시계를 켜고 끄는 코드 위치에 따라 모델을 메모리에 올리는 초기화 시간까지 섞일 수 있다.


모델 파일과 실행 도구(런타임)의 차이, 양자화와 메모리의 관계 같은 기본 개념은 글 끝에 있는 기초편 글에서 먼저 확인할 수 있다. 이 글에서는 Android 설치 파일 검사부터 모델 초기화와 응답 생성까지의 단계를 따라가며 `generationMs`가 실제로 재는 구간을 추적한다. 이어서 이 값으로 생성 속도를 어디까지 설명할 수 있는지 확인하고, 실제 기기에서 성능을 잴 때 분리해야 할 조건을 짚는다.


## APK 구성 검사와 실행 실패 원인 분리


응답 시간을 재려면 먼저 앱 설치 파일과 모델 파일이 기기에 제대로 준비되었는지부터 단계별로 확인해야 한다. 저장소의 [APK 검사 스크립트](https://github.com/NAMUORI00/ondevice-medical-rag/blob/d5dd214987338e1e57664bb6143ce9d38436c14e/scripts/verify_android_apk.py)는 빌드된 설치 파일(**APK**) 안에 샘플 질의응답(QA) 파일이 들어 있는지 먼저 살핀다. 또한 기기 프로세서 규격인 **ABI**(Application Binary Interface)별 네이티브 런타임 라이브러리가 들어 있는지도 확인한다. 이 라이브러리는 `arm64-v8a`나 `x86_64` 같은 프로세서 규격에 맞춰 기기에서 모델을 직접 돌리는 실행 부품이다.


이와 함께 모델 가중치 파일의 확장자나 일부 원본 데이터 경로가 APK에 잘못 들어갔는지도 검사한다. MedEdge는 용량이 큰 모델 파일을 앱 설치 파일에 넣지 않고 기기 저장소 경로에 따로 배치한다. 따라서 APK 구성 검사를 통과했다는 사실만으로는 기기에 모델 파일까지 준비되었다고 볼 수 없다.


권한 검사에는 네트워크 통신 권한인 `INTERNET` 허용 여부를 구분하는 옵션도 있다. 기본 설정에서는 APK에 `INTERNET` 권한이 들어 있으면 검사가 실패한다. 다만 이 검사는 대상 APK의 패키지 구성만 확인할 뿐이므로, 다른 빌드 변형이나 외부 구성 요소의 실행 동작까지 검증했다고 볼 수는 없다.


이처럼 패키지 검사와 실제 실행 조건을 단계별로 나누어 두면 문제가 생겼을 때 원인을 빠르게 좁힐 수 있다. 앱이 설치되지 않으면 패키지와 기기 ABI 호환성을 먼저 살피고, 설치된 앱에서 모델을 찾지 못하면 기기 안의 파일 배치 경로를 확인한다. 모델 파일이 제자리에 있는데도 답변 생성에 실패해 대체 응답으로 넘어간다면 파일 형식(포맷), 런타임 호환성, 남은 메모리를 차례로 점검하면 된다. 이 단계들을 구분하지 않고 모두 '온디바이스 실행 실패'로 묶어 버리면 문제가 생겼을 때 어디부터 확인해야 할지 알기 어렵다.

## 파일 존재 검사와 요청별 엔진 수명


앱이 실행된 뒤 기기 안의 모델 파일을 확인하고 엔진을 호출하는 단계는 [LiteRtGemmaEngine.kt](https://github.com/NAMUORI00/ondevice-medical-rag/blob/d5dd214987338e1e57664bb6143ce9d38436c14e/android/MedEdgeRag/app/src/main/java/com/mededge/rag/LiteRtGemmaEngine.kt)에서 담당한다. 이 클래스의 `isReady` 메서드는 `File(resolvedModelPath()).isFile`의 결과를 그대로 돌려준다. 이름만 보면 모델의 추론 준비가 모두 끝났는지 확인하는 것처럼 읽히지만, 실제로는 지정된 경로에 일반 파일이 있는지만 검사한다. 파일이 손상되었거나 런타임이 지원하지 않는 포맷이더라도 경로에 파일만 있으면 `isReady` 단계를 통과한다.


실제 추론 설정과 엔진 구동은 답변을 만드는 `generate` 메서드 안으로 들어가야 시작된다. 여기서는 `EngineConfig`를 만들며 연산을 맡을 실행 백엔드로 일반 프로세서인 `Backend.CPU()`를 선택한다. 공식 [LiteRT-LM Kotlin 문서](https://github.com/google-ai-edge/LiteRT-LM/blob/main/docs/api/kotlin/getting_started.md)는 여러 실행 백엔드를 안내하지만, 이 프로젝트 코드가 실제로 넘긴 옵션은 CPU 백엔드다. 따라서 이 커밋의 Android 실행 경로를 그래픽 칩(GPU)이나 인공지능 전용 칩(NPU) 가속 결과로 설명할 근거는 없다.


시간 측정과 직결되는 또 다른 특징은 `generate` 메서드 안의 `Engine(...).use` 블록이 결정하는 엔진의 수명이다. 이 블록 안에서 엔진 초기화, 대화 세션 생성, `sendMessage` 호출, 응답 문자열 변환이 차례대로 실행된다. 파일 유무만 살피는 `isReady`와 달리, `generate`는 요청이 들어올 때마다 엔진을 새로 열어 초기화하고 응답 직후 곧바로 닫는다.


![isReady 호출의 파일 존재 확인 범위와 generate 호출 내부 Engine.use 블록의 초기화, 메시지 전송, 엔진 닫기 과정을 비교한 구조도](/images/notion/tech-05-02/image-2.png)


그림 2. LiteRtGemmaEngine.kt에서 파일 존재만 확인하는 isReady와 요청마다 엔진 초기화부터 자원 정리까지 수행하는 generate의 실행 범위 비교.


엔진을 닫지 않고 메모리에 유지하면 요청마다 되풀이되는 초기화 비용을 줄일 여지가 있다. 대신 평상시 메모리 점유가 늘어나고, Android 앱 생명주기에 따른 메모리 해제 시점이나 동시 요청 처리도 함께 고려해야 한다. 반면 지금처럼 `use` 블록으로 감싸면 호출이 끝나는 지점에서 자원이 즉시 정리된다는 점이 코드에서 명확히 드러난다. 두 방식 가운데 어느 쪽이 더 적절한지는 실제 기기에서 반복 요청 조건을 비교해 봐야 판단할 수 있다.


## 초기화를 포함한 생성 시간 측정


앞에서 본 `generate` 메서드를 실제로 호출하고 시간을 재는 곳은 상위 엔진인 [MedEdgeRagEngine.kt](https://github.com/NAMUORI00/ondevice-medical-rag/blob/d5dd214987338e1e57664bb6143ce9d38436c14e/android/MedEdgeRag/app/src/main/java/com/mededge/rag/MedEdgeRagEngine.kt)다. 이 코드는 `generator.generate(prompt)` 호출 직전과 직후의 시각 차이를 계산해 `generationMs` 필드에 넣는다. 문제는 `generator.generate(prompt)` 내부에 앞서 확인한 `Engine(...).use` 블록 전체가 들어 있다는 점이다. 따라서 `generationMs`는 순수 토큰 출력 시간만 나타내지 않으며, 엔진 초기화와 응답 생성, 종료 시 자원 정리 시간까지 모두 포함한다. 그렇다고 매 호출이 아무 준비 없이 처음부터 구동되는 **콜드 스타트**(cold start) 상태와 완전히 같다고 단정하기도 어렵다. 반복 호출 과정에서 운영체제가 최근 읽은 파일을 메모리에 남겨 두는 파일 캐시 효과가 개입할 수 있기 때문이다.


질문이 들어와 로컬 검색을 마친 뒤에는 실행 경로가 어떻게 갈라지느냐에 따라 `generationMs`에 기록되는 숫자의 뜻도 달라진다. 검색 근거가 없거나 기기에 모델 파일이 없으면 생성 호출을 건너뛰어 대체 응답으로 넘어가고, 생성 호출 도중 예외가 발생해도 대체 응답으로 이어진다.


![질문과 로컬 검색 후 모델 파일 존재 여부에 따라 generationMs 측정 구간을 거치거나 건너뛰어 대체 응답으로 이어지는 흐름도](/images/notion/tech-05-02/image-3.png)


그림 3. MedEdgeRagEngine.kt에서 generationMs가 둘러싼 실행 구간과 생성 호출 생략 및 예외 발생 시 대체 응답으로 넘어가는 경로(출처: MedEdgeRagEngine.kt와 LiteRtGemmaEngine.kt를 바탕으로 직접 구성).


예를 들어 세 번의 요청이 차례로 들어왔다고 가정해 보자. 첫 요청은 모델 파일이 없어 생성 호출을 건너뛰었고, 두 번째는 엔진 초기화 도중 예외가 났으며, 세 번째만 정상적으로 문자열 응답을 받았다. 이때 첫 요청의 `generationMs`는 `0`이고, 두 번째는 예외가 나기까지의 시간이며, 세 번째는 초기화와 자원 정리를 포함한 전체 시간이다. 이 세 값을 평균 내서 '모델 평균 추론 지연'이라고 부르면 서로 다른 사건이 하나의 숫자에 섞이게 된다.


| 실행 경로             | `usedLocalModel` | `generationMs` 해석      |
| ----------------- | ---------------- | ---------------------- |
| 근거 없음 또는 모델 파일 없음 | `false`          | 생성 호출을 건너뛴 값 `0`       |
| 생성 호출 중 예외        | `false`          | 예외가 반환되기까지의 시간         |
| 생성 호출 성공          | `true`           | 초기화, 응답, 자원 정리를 포함한 시간 |


표에 함께 정리한 **로컬 모델 사용 여부**(`usedLocalModel`) 값도 해석할 때 주의해야 한다. 코드에서는 호출이 예외 없이 끝났는지를 뜻하는 `generated.isSuccess`를 여기에 그대로 사용한다. 즉 예외 없이 문자열을 돌려받았는지만 나타낼 뿐, 그 문장이 검색 근거에 맞는지나 질문에 충분히 답했는지는 별도의 품질 평가 영역이다. 마찬가지로 `generationMs`를 출력 토큰 수로 나누어 토큰당 생성 시간을 구할 때도 주의가 필요하다. 나누어지는 값(분자)에 엔진 초기화 비용이 포함되어 있으므로 순수 토큰 생성 속도와는 구분해서 읽어야 한다.


## 에뮬레이터 기록과 실기기 측정 항목 구분


코드에서 확인한 측정 구간의 특성은 기존 실험 기록을 읽고 후속 평가를 설계할 때도 그대로 적용된다. 먼저 저장소 [Android 실행 안내](https://github.com/NAMUORI00/ondevice-medical-rag/blob/d5dd214987338e1e57664bb6143ce9d38436c14e/android/MedEdgeRag/README.md)에 적힌 가상 기기 환경인 **에뮬레이터**(emulator) 설정과 실제 휴대전화 측정은 구분해서 읽어야 한다. 현재 기록은 Pixel 7 프로필의 `x86_64` 에뮬레이터 실행에 해당하며, 실제 물리 Pixel 7 기기의 속도는 별도 측정이 필요하다.


실기기 후속 측정을 위한 기록표에는 기기 모델, 칩, ABI, 운영체제(OS), 런타임 버전, CPU 백엔드를 기본 환경 항목으로 정리했다. 여기에 파일 고유값인 모델 파일 해시와 입력 길이, 출력 길이를 같은 행에 적고 초기화 시간과 응답 생성 시간을 분리하면 비교 기준을 맞출 수 있다. 생성 성공, 검색 근거 기반 대체 응답, 예외 발생 건수도 나누어 집계하면 앱 응답성과 모델 동작을 함께 파악할 수 있다. 또한 요청마다 엔진을 여닫는 방식과 메모리에 유지하는 방식을 비교하려면, 반복 호출에 따른 발열이나 메모리 상태 변화까지 통제해야 판단 근거가 생긴다.

## 결론


이처럼 응답 시간 측정값은 변수 이름보다 코드에서 초시계가 켜지고 꺼지는 지점으로 설명하는 편이 정확하다. MedEdge의 Android 코드에서 `isReady`는 파일 유무만 검사하고, `generate`는 요청마다 CPU 백엔드 엔진을 새로 초기화한 뒤 닫는다. 그 결과 `generationMs`에는 답변 생성뿐 아니라 엔진 초기화와 자원 정리 시간까지 함께 포함된다. 함께 기록되는 `usedLocalModel` 또한 답변 품질이 아니라 예외 없이 문자열을 돌려받았는지만 나타낸다.


다만 현재 실행 기록은 `x86_64` 에뮬레이터에서 확인한 결과이므로, 실제 물리 Pixel 7 기기의 속도와 엔진 유지 방식의 차이는 별도 측정이 필요하다. 후속 실기기 성능 측정에서도 이번에 확인한 구간 정의를 유지하며 환경 조건과 분리된 시간 지표를 기록할 계획이다. 다음 글에서는 GPU 연산을 바꾸는 커널 코드와 모델을 불러오는 웹 UI를 따라가며 각 도구가 추론 과정의 어느 위치에 관여하는지 확인한다.
