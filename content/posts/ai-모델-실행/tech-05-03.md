앞 글에서는 모델을 처음 준비하는 초기화 시간과 답변을 만드는 응답 시간을 나누어 확인했다. 모델을 실행할 때 화면이나 설정에서 옵션을 바꾸더라도, 내부 계산이 의도대로 바뀌었는지는 바로 드러나지 않는다. 로그에 찍힌 속도가 어느 구간을 잰 값인지도 코드가 실제로 실행되는 경계를 따라가 봐야 알 수 있다. 이 글에서는 GPU 연산을 다루는 `triton_llama3`와 실행 화면을 묶은 `text-generation-webui` 코드를 읽었다. 두 코드를 따라가며 화면의 설정 선택이 실제 연산과 속도 지표까지 그대로 이어지는지 따져 보았다.


두 저장소는 모두 인공지능 모델을 실행한다는 공통점이 있지만 코드가 관여하는 층위는 서로 다르다. `triton_llama3`는 단어들의 연결 관계를 계산하는 **어텐션**(Attention) 연산을 직접 작성한 GPU 코드로 바꾸는 저장소다. 반면 `text-generation-webui`는 모델을 메모리에 올리는 로더(loader)와 생성 함수를 웹 화면에서 고르게 묶어 둔 도구다. 두 코드는 서로 연결된 배포 구성이 아니라 각각 따로 동작하는 독립된 저장소다. 본문에 인용한 `triton_llama3` 소스 링크는 비공개 저장소여서 접근 권한이 있어야 열람할 수 있다. `text-generation-webui`는 복사해 보관해 둔 포크(fork) 저장소의 구조를 읽은 것이라 원본 기능 전체를 직접 작성한 변경으로 세지 않았다.

## 모델 로딩과 어텐션 커널의 대체 경로


그림 1의 GPU 커널 영역에 해당하는 `triton_llama3`는 모델을 불러오는 단계와 어텐션을 계산하는 단계마다 대체 경로를 두고 있다. 여기서 사용한 Triton은 GPU가 실행할 작은 연산 프로그램인 **커널**(kernel)을 작성하고 변환하는 언어이자 컴파일러다. 2026년 9월 15일에 확인한 [Triton 공식 문서](https://triton-lang.org/main/index.html)에서도 커스텀 신경망 연산을 작성하는 환경으로 이 도구를 소개한다. 추론 요청을 받아 모델을 배치하고 서빙하는 서버 프로그램인 NVIDIA Triton Inference Server와는 이름만 같을 뿐 별개의 도구다.


`triton_llama3`의 [InferencePipeline](https://github.com/NAMUORI00/triton_llama3/blob/858f05e15ca33def2e6ccef1c28320babc826b9a/src/main.py)은 문장을 작은 조각인 토큰(token)으로 나누는 토크나이저와 모델을 준비한 뒤 `generate`를 호출한다. 설정에서 `use_triton`이 켜져 있으면 `Llama3TritonModel`을 불러오고, `ImportError`가 나면 일반 모델 로더로 전환한다. 반면 메모리 부족이나 잘못된 학습 값(가중치) 때문에 생기는 다른 로딩 오류는 바깥 예외 처리에서 기록한 뒤 그대로 다시 발생시킨다. 자동 복구는 `ImportError`만 처리하므로 나머지 오류는 따로 다루어야 한다.


현재 코드를 기준으로 보면 이 방식은 익숙한 모델 호출 형태를 그대로 유지하면서 일부 연산만 바꾸어 시험하려는 의도로 읽힌다. 다만 이는 코드 구조에서 읽은 해석일 뿐이며, 당시의 선택 동기를 기록으로 확인한 내용과는 구분했다.


어텐션을 수행하는 [MultiHeadAttention.forward](https://github.com/NAMUORI00/triton_llama3/blob/858f05e15ca33def2e6ccef1c28320babc826b9a/src/kernels/attention.py)는 호출 시점에 두 가지 조건을 먼저 검사한다. `use_triton` 플래그가 켜져 있는지와 입력 데이터(텐서)가 NVIDIA GPU 환경인 CUDA에 올라와 있는지를 함께 본다. 조건을 만족해 커널을 호출하더라도, 실행 중 예외가 발생하면 PyTorch 기준 연산으로 돌아가 다시 계산한다. 출력에 정의되지 않은 수치 결과인 `NaN`이나 표현 범위를 넘어선 무한값인 `Inf`가 포함되어 있을 때도 마찬가지로 PyTorch 기준 연산을 다시 실행한다.

## 커널 실행 로그와 마스크 전달의 빈틈


그림 2처럼 연산 내부에 대체 경로가 들어 있으면, 초기 로딩 로그만으로는 모든 어텐션 연산이 Triton 커널에서 끝났는지 알 수 없다. 모델을 Triton 경로로 불러왔다는 로그가 남더라도, 실행 중 오류가 나면 PyTorch 기준 연산으로 넘어가 겉으로는 정상 응답을 돌려주기 때문이다.


또한 `NaN`과 `Inf`만 걸러내는 유한값 검사는 수치 상태만 확인할 뿐 정답 일치를 보장하지 않는다. 모든 원소가 유한한 값이지만 계산이 틀린 출력은 이 검사를 그대로 통과할 수 있다. 설정과 실제 결과를 정확히 연결하려면 기준 연산과의 출력 오차를 비교하고, 대체 경로가 실제로 실행된 횟수를 따로 기록해야 한다.


코드를 읽으며 한 가지 더 확인한 빈틈은 계산에서 가릴 위치를 지정하는 `attention_mask` 전달이다. `MultiHeadAttention.forward`는 함수 인자로 `attention_mask`를 받는다. 하지만 확인한 코드에서는 Triton 커널과 PyTorch 기준 함수 양쪽 모두에 이 인자를 빼고 `causal=True`만 넘기고 있었다.


어텐션 연산에서 **인과 마스크**(causal mask)는 현재 위치보다 뒤에 오는 미래 토큰을 미리 보지 못하게 가리는 조건이다. 반면 **패딩 마스크**(padding mask)는 여러 문장의 입력 길이를 맞추려고 채워 넣은 빈자리를 계산에서 제외한다. `causal=True` 설정 하나가 두 역할을 모두 대체한다고 가정할 수는 없다. 커널을 직접 다룰 때는 연산 배치와 메모리 접근을 조정할 여지가 생기지만, 마스크와 캐시, 자료형 조건도 함께 맞아야 한다. 길이가 다른 문장을 한 묶음(배치)으로 처리하거나 이전 계산값을 저장하는 KV 캐시를 붙이면 결과가 달라질 수 있다. 따라서 이 두 조건은 속도 비교에 앞서 먼저 확인해야 할 후속 대조 대상이다.


## 추론 UI의 로더 선택과 생성 경로


모델 안쪽의 커널 연산과 달리 바깥 실행 경로를 다루는 `text-generation-webui`는 어떤 로더와 생성 함수를 거쳐 요청을 처리할지 결정한다. 이 저장소의 [모델 로딩 방식 선택](https://github.com/NAMUORI00/text-generation-webui/blob/65099dc192b3b75327e4e4fe10a5cac0d46a6b10/modules/models.py) 코드는 Transformers, llama.cpp, ExLlamav2 같은 로더 이름을 각각의 로딩 함수에 연결한다. 사용자가 명시한 `loader`가 없으면 실행 옵션과 모델 설정 정보(메타데이터)를 따라 로더를 자동으로 선택한다.


여기서 선택된 로더는 모델 파일을 읽는 방법뿐 아니라 이후 호출할 모델 객체의 종류까지 결정한다. 이어지는 [텍스트 생성 처리](https://github.com/NAMUORI00/text-generation-webui/blob/65099dc192b3b75327e4e4fe10a5cac0d46a6b10/modules/text_generation.py) 모듈은 추가 기능(확장)의 커스텀 생성 함수가 있는지 먼저 확인한다. 확장 함수가 없으면 모델 객체의 종류에 따라 Hugging Face 생성 경로 또는 자체 커스텀 경로로 나뉜다. 커스텀 경로 안에서도 답변을 한 번에 받을지, 생성되는 대로 이어서 받는 스트리밍(streaming)을 쓸지 다시 나뉜다. 이 선택에 따라 호출 함수가 `generate`와 `generate_with_streaming`으로 갈린다.

## 토큰 처리량 계산의 분자 기준


실행 경로가 어디로 이어지는지 확인하는 일에 더해, 마지막에 로그로 남는 성능 지표가 어떤 기준으로 집계되었는지도 코드에서 따져 봐야 했다. `triton_llama3`의 추론 요청과 응답 처리를 보면, 화면에 돌려줄 문자열을 만들 때는 전체 결과에서 입력 길이만큼 토큰을 잘라 낸다. 그런데 로그의 `total_tokens`는 앞부분을 잘라 내기 전인 `outputs`의 전체 길이를 합산하고 있었다. 입력까지 포함하는 출력 형식이라면 표시된 초당 토큰 처리량(`tok/s`)의 분자에 입력 토큰까지 함께 들어간다.


설명용 계산 예로, 입력 토큰 100개와 새 토큰 20개가 반환되고 측정 시간이 2초였다고 가정한다. 전체 길이인 120개를 2초로 나누면 `60 tok/s`가 되지만, 새 토큰 20개만 2초로 나누면 `10 tok/s`가 된다. 같은 측정 시간에도 나눗셈의 분자를 무엇으로 잡느냐에 따라 처리율이 크게 달라진다.


![입력 토큰 100개와 새 토큰 20개를 2초 동안 처리했을 때 전체 길이 기준은 60 tok/s, 새 토큰 기준은 10 tok/s로 계산되는 비교 그림](/images/notion/tech-05-03/image-4.png)


그림 4. 입력 토큰 포함 여부에 따라 초당 토큰 처리량(tok/s) 계산 결과가 달라지는 예.


따라서 GPU 커널의 연산 속도, 새 토큰 생성 속도, 사용자가 화면에서 기다린 전체 시간은 각각 다른 항목으로 나누어 기록해야 비교가 흔들리지 않는다.


## 결론


이 글에서는 `triton_llama3`와 `text-generation-webui` 코드를 읽으며 실행 옵션이 실제 연산과 속도 지표까지 이어지는지 확인했다. 커널의 대체 경로 전환 여부나 마스크 전달 조건, 로더별 옵션 적용 방식, 토큰 처리량의 분자 기준은 설정 화면이나 초기 로그만으로는 드러나지 않는다. 최적화 대상을 먼저 정해야 측정할 지표가 정해지고, 외부 도구를 조합할 때도 각 도구가 바꾸는 층위를 구분해야 어느 변경이 효과를 냈는지 추적할 수 있다.


이번 글은 호출 구조와 집계 방식을 코드에서 읽은 기록이며, GPU 성능을 새로 측정한 결과는 포함하지 않는다. 같은 입력과 가중치, 생성 조건에서의 출력 오차, 대체 경로 실행 여부, 입력 처리와 새 토큰 생성 시간을 분리한 측정값은 후속 대조 항목으로 남겼다. 이어지는 글에서는 가중치를 세 값으로 제한하는 BitNet 구현을 통해, 연산에 쓰는 값의 종류가 줄었을 때 파일 크기와 실행 속도에 어떤 영향이 있는지 확인한다.
