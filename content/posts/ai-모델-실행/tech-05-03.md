모델 실행을 조정할 때 GPU 커널과 사용자용 추론 UI가 맡는 역할을 비교했다. triton_llama3와 text-generation-webui를 각각 검토하며 연산 선택, 모델 로딩, 생성 호출의 경계를 정리했다.


## 구현과 확인 과정


triton_llama3와 text-generation-webui의 코드를 읽으며, 생성 화면의 옵션 설정과 GPU 연산을 바꾸는 작업의 범위를 비교했다. 전자는 모델 내부 커널을, 후자는 모델 로딩과 생성 경로를 다루고 있었다. 앞 글의 시간 측정 문제를 이어, 각 도구가 실행 과정의 어느 부분에 관여하는지 정리했다.


두 저장소는 모델을 실행한다는 접점이 있지만 바꾸려는 층이 달랐다. 전자는 모델 내부 GPU 연산을 다루고, 후자는 모델 로딩과 생성 경로를 사용자가 선택할 수 있게 감싼다. 서로 독립된 두 코드의 역할을 비교했다.


이 글에서는 '화면의 설정이 실제 실행되는 연산까지 설명해 주는가'라는 관점으로 두 저장소를 읽었다. triton_llama3의 소스 링크는 비공개 저장소여서 접근 권한이 있어야 확인할 수 있다.


## Triton 커널의 실행 위치


여기서 Triton은 GPU 커널을 작성하는 언어와 컴파일러다. 커널은 GPU가 수행할 작은 연산 프로그램이다. 요청을 받고 모델을 배치하는 NVIDIA Triton Inference Server와는 이름이 같지만 별개의 도구다.


2026-09-15 확인한 [Triton 공식 문서](https://triton-lang.org/main/index.html)에서도 커스텀 신경망 연산을 작성하는 환경으로 소개하고 있었다.


triton_llama3의 [InferencePipeline](https://github.com/NAMUORI00/triton_llama3/blob/858f05e15ca33def2e6ccef1c28320babc826b9a/src/main.py)은 토크나이저와 모델을 준비한 뒤 generate를 호출한다.


use_triton이 켜져 있으면 Llama3TritonModel을 불러오고, 해당 경로에서 ImportError가 발생하면 일반 모델 로더로 전환한다. 다른 종류의 로딩 오류는 바깥 예외 처리에서 기록한 뒤 다시 발생시킨다. 자동 복구는 ImportError를 처리하며, 메모리 부족과 잘못된 가중치 등은 별도 오류 처리가 필요했다.


이 구성은 익숙한 모델 호출 형태를 유지하면서 일부 연산을 바꾸어 살펴보는 방식으로 읽혔다. 현재 코드에서 읽은 해석이며, 당시의 선택 동기를 기록으로 확인한 내용과는 구분했다. 커널을 직접 다루면 연산 배치와 메모리 접근을 조정할 여지가 생기지만, 마스크, 캐시, 자료형 조건도 함께 맞아야 한다. 속도 비교에 앞서 두 경로의 출력이 같은 의미를 갖는지 확인할 부분이 남았다.

## 설정 옵션과 커널 실행 경로


[MultiHeadAttention.forward](https://github.com/NAMUORI00/triton_llama3/blob/858f05e15ca33def2e6ccef1c28320babc826b9a/src/kernels/attention.py)는 use_triton 플래그와 입력의 CUDA 배치 여부를 함께 검사한다.


커널 호출에서 예외가 발생하거나 출력에 NaN, Inf가 포함되어 있으면 PyTorch 기준 연산으로 다시 수행한다. 모델을 Triton 경로로 불러왔다는 로그만으로는 모든 Attention 연산이 Triton 커널에서 완료되었는지 알 수 없는 구조다.


NaN은 정의되지 않은 수치 결과, Inf는 표현 범위를 넘어선 무한값이다. NaN, Inf를 걸러내더라도 모든 값이 유한하면서 잘못된 출력은 그대로 통과할 수 있다. 설정과 결과를 정확히 연결하려면 기준 연산과의 오차 비교, 대체 경로가 실제로 실행된 횟수의 별도 기록이 함께 있어야 한다.


또 하나 확인한 것은 attention_mask다. 함수 인자로 받지만, 확인한 forward에서는 Triton과 PyTorch 기준 함수 호출 모두에 이 인자를 전달하지 않고 causal=True만 넘기고 있었다.


인과 마스크는 미래 토큰을 가리는 조건이고, 패딩 마스크는 채워 넣은 빈 자리를 가리는 조건이다. causal=True가 두 역할을 모두 대체한다고 가정할 수는 없다. 길이가 다른 문장을 한 배치로 묶었을 때, 그리고 KV 캐시를 붙였을 때 결과가 달라지는지가 후속 대조 대상이다.


## 웹 UI의 모델 로더 선택


text-generation-webui는 포크 저장소다. 여기서는 보관된 코드의 구조를 읽었고, 원본 기능 전체를 직접 작성한 변경으로 세지 않았다.


[모델 로딩 방식 선택](https://github.com/NAMUORI00/text-generation-webui/blob/65099dc192b3b75327e4e4fe10a5cac0d46a6b10/modules/models.py)에서는 Transformers, llama.cpp, ExLlamav2 등 로더 이름을 각각의 로딩 함수에 연결하고 있었다. 명시한 loader가 없으면 실행 옵션과 모델 메타데이터를 따라 자동으로 선택된다.


로더는 파일을 읽는 방법뿐 아니라 이후 호출할 모델 객체의 종류까지 결정한다. 생성 모듈은 확장의 커스텀 생성 함수가 있는지 먼저 확인하고, 없으면 모델 객체의 종류에 따라 Hugging Face 생성 경로 또는 커스텀 경로로 나뉜다. 커스텀 경로 안에서도 스트리밍 여부에 따라 generate와 generate_with_streaming으로 갈린다.

이 구조에서는 UI가 열리는지, 모델을 불러오는지, 요청이 생성 함수까지 도달하는지, 해당 백엔드가 어떤 연산을 실행하는지를 단계별로 나누어 확인할 수 있다. 로더 선택의 폭은 모델 포맷에 맞춰 실행기를 바꿀 여지를 주지만, 같은 화면의 옵션이 모든 로더에서 같은 의미로 적용되는지는 로더별로 따로 확인이 필요한 부분이다.


## 토큰 처리량의 집계 기준


triton_llama3의 추론 요청과 응답 처리를 보면, 화면에 돌려줄 문자열을 만들 때 입력 길이만큼 토큰을 잘라 낸다. 그런데 로그의 total_tokens는 outputs의 전체 길이를 합산하고 있었다. 입력까지 포함하는 출력 형식이라면 표시된 tok/s의 분자에 입력 토큰이 포함된다.


설명용으로, 입력 100개와 새 토큰 20개가 반환되고 측정 시간이 2초였다고 해 보자. 전체 길이를 나누면 60 tok/s, 새 토큰만 나누면 10 tok/s다. 같은 시간에도 분자의 정의에 따라 처리율이 달라지는 계산 예제다. 커널 속도, 새 토큰 생성 속도, 사용자가 기다린 전체 시간은 각각 다른 항목으로 나누어 기록해야 비교가 안정적이다.


후속 대조 항목으로는 같은 입력, 가중치, 생성 조건에서의 출력 오차, 대체 경로 실행 여부, 입력 처리와 새 토큰 생성 시간을 남겼다. 이번 글은 호출 구조를 코드에서 읽은 기록이며, GPU 성능을 새로 측정한 결과는 포함하지 않는다.


다음 글에서는 가중치를 세 값으로 제한하는 BitNet 구현을 살펴본다. 연산에 쓰는 값의 종류가 줄었을 때 파일 크기와 실행 속도에 어떤 영향이 있는지가 이어지는 질문이다.

최적화 대상을 먼저 정해야 측정할 지표도 정해진다. 커널 시간, 새 토큰 생성 속도, 전체 대기 시간을 구분하면 어느 변경이 효과를 냈는지 추적할 수 있다. 외부 도구를 조합할 때도 각 도구가 바꾸는 층을 먼저 표시하려 한다.
