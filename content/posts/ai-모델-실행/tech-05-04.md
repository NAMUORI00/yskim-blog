BitNet 구현을 검토하며 삼진 가중치의 학습 계산과 추론용 변환을 나누어 정리했다. bitnet-llama3의 BitLinear에서 표현값, 실제 저장 형식, 실행 커널이 각각 어떻게 연결되는지를 확인했다.


## 구현과 확인 과정


bitnet-llama3의 BitLinear 코드를 읽으며 삼진 가중치의 학습용 계산과 추론용 변환을 정리했다. 가중치가 −1, 0, +1 세 값만 갖더라도 파일이 곧바로 원소당 1.58비트로 저장되지는 않는다. 값을 표현하는 방식과 실제 메모리에 담는 방식이 다르기 때문이다. 작은 가중치 네 개를 예제로 두고 각 단계의 계산을 따라가 봤다.


수치 정밀도와 양자화의 기본 원리는 기초편에서 다뤘다. 이 글에서는 작은 가중치 네 개를 코드의 계산에 넣어 학습용 표현과 추론용 변환을 각각 따라간다. 연결한 소스는 비공개 저장소여서 접근 권한이 필요하다.


## 삼진 가중치와 비트 수 계산


2024년 [BitNet b1.58 논문](https://arxiv.org/abs/2402.17764)은 가중치를 −1, 0, +1의 삼진 표현으로 다루는 모델을 소개했다. 세 가지 상태의 정보량은 log₂3, 약 1.585비트다.


이 숫자는 표현할 상태 수에서 나온다. 각 원소에 2비트를 배정하는 단순한 방식, 여러 원소를 묶어 저장하는 방식, 스케일 같은 부가 정보를 넣는 방식에 따라 실제 파일 크기는 달라진다.


논문의 성능 결과를 구현 이름만 같은 저장소에 그대로 대입하기는 어렵다. 같은 가중치 표현이라도 학습 조건, 저장 포맷, 연산 커널이 맞아야 품질과 효율 비교의 출발점이 된다. 이번 확인 범위는 저장소의 BitLinear 계산이며, 논문 성능을 재현하는 실험은 포함하지 않았다.


## 가중치 네 개의 양자화 예제


[weight_quant](https://github.com/NAMUORI00/bitnet-llama3/blob/6b95497250050702ed89f6d41da40e0c150d5150/src/llama3/bitlinear.py)는 가중치 절대값의 평균을 구하는 함수다.


그 역수를 곱하고 반올림한 뒤 −1과 1 사이로 제한한다. 마지막에는 다시 스케일로 나누어 원래 수치 범위로 돌아간다.


설명용 가중치를 [−0.8, −0.1, 0.2, 0.9]로 두면 절대값 평균은 0.5, 역수 스케일은 2다. 스케일을 곱한 값은 [−1.6, −0.2, 0.4, 1.8], 반올림과 범위 제한을 거치면 [−1, 0, 0, 1]이 된다.


함수가 반환하는 값은 이를 2로 나눈 [−0.5, 0, 0, 0.5]다. '세 값'이라는 표현 자체는 맞지만, 반환 텐서가 정수 −1, 0, 1 그대로라고 읽으면 마지막 나눗셈이 빠진다.

활성값 쪽은 다른 기준을 쓴다. activation_quant는 마지막 차원에서 최대 절대값을 찾아 127에 맞추고, 반올림과 범위 제한 후 다시 나눈다. 주석에는 absmean이라는 표현이 섞여 있지만 실행되는 식은 maxabs다. 가중치는 절대값 평균, 활성값은 최대 절대값으로, 두 경로의 정규화 방식이 다르다.


## 학습 중 가중치 보간


BitLinear.forward는 입력에 layer_norm을 적용하고 양자화 계산을 임시 float32로 수행한다. 이어 원래 값에 양자화 차이의 일부를 더한다. 가중치 쪽을 간단히 쓰면 다음과 같다.


```python
w_used = w + lambda_ * (quantized_w - w).detach()
```


detach는 괄호 안의 차이를 역전파 경로에서 떼어 놓는다. 코드에서는 순전파에 양자화 영향을 주고, 역전파에서는 원래 가중치로 기울기를 흘리는 STE 구성을 읽을 수 있었다. 반올림 연산의 미분을 그대로 따라가기 어려운 조건에서 쓰는 추정 경로이며, 이 구성만으로 학습 안정성을 판단할 수는 없었다.


lambda_가 1일 때 위 예제의 가중치는 완전히 양자화된 값으로 바뀐다. lambda_=0.5라면 −0.8은 −0.65로, 0.2는 0.1로 바뀌어 중간 단계에는 세 종류보다 많은 값이 남는다. 점진적으로 양자화 영향을 키우는 구조인데, 모든 학습 단계에서 가중치가 이미 삼진이라고 표현하면 이 보간 과정이 빠진다.


현재 스텝은 외부에서 전달받고 스케줄러가 강도를 계산한다. 실제 학습에서는 함수의 존재뿐 아니라 스텝 갱신이 해당 레이어까지 전달되는지, 최종 lambda_ 값이 얼마인지를 함께 확인할 대상이다. 학습을 끝낸 체크포인트를 추론용으로 변환했을 때 출력이 얼마나 달라지는지도 별도 비교 항목이다.


## 추론용 변환과 비트 패킹


같은 파일의 BitLinearInference.from_bit_linear는 가중치를 −1, 0, 1로 제한하고 w_scale을 따로 저장한다. 하지만 round와 clamp는 값의 종류를 바꿀 뿐 텐서 자료형을 작은 비트열로 포장하지 않는다. 변환된 weight에 w_quant를 대입하는 경로에는 비트 패킹이 없다.


![05-04-02.png](/images/notion/tech-05-04/image-2.png)


그림 2. 확인한 추론용 변환과 연산 경로. 출처: BitLinearInference를 바탕으로 직접 구성. 점선은 비트 패킹, 전용 커널을 적용할 때 추가로 필요한 단계다.


forward도 일반 F.linear를 호출한 뒤 스케일을 복원한다. 전용 저비트 커널을 쓰지 않는다는 주석과 실제 호출이 일치했다. 1,000개 가중치를 float16 텐서로 유지하면 데이터 부분은 2,000바이트가 된다.


세 상태의 이상적인 정보량으로 계산한 약 198바이트와는 크기가 달랐다. 스케일, 파일 헤더, 정렬을 포함하지 않은 계산이므로, 실제 체크포인트 크기를 예측한 값과는 구분했다.


## 변환 전후의 비교 조건


[모델 추론 실행](https://github.com/NAMUORI00/bitnet-llama3/blob/6b95497250050702ed89f6d41da40e0c150d5150/src/llama3/run_inference.py)은 모델을 불러온 뒤 convert_to_inference_mode를 호출한다.


변환 함수는 실제 BitLinear 인스턴스를 찾아 바꾸는데, 로그 문구만으로는 몇 개의 레이어가 변환됐는지 알기 어렵다. 변환 대상 목록과 반환 결과, 모델 안의 레이어 자료형을 함께 확인하는 편이 정확하다.


코드를 읽으며 확인한 작은 항목이 하나 있다. 변환 함수는 bias가 있으면 복사하지만, 추론 forward의 F.linear 호출에는 bias를 전달하지 않는다. bias 없는 레이어에서는 이 차이가 드러나지 않는다.


bias가 있는 입력을 일반적으로 지원하는지 판단하려면 변환 전후의 출력 비교가 남아 있다. 이번에는 코드에서 대조할 입력, 형상 조건을 정리했다.


가중치 표현을 제한하는 실험의 출발점으로 이 구현을 쓸 수 있다. 파일 크기, 최고 메모리 사용량, 생성 속도, 답변 품질은 각각 따로 측정할 대상이다. 일반 연산으로 양자화를 흉내 내는 현재 단계와 패킹된 데이터에 전용 커널을 적용하는 단계 사이에는 간격이 있고, 그 간격을 명시하는 편이 현재 구현의 위치를 더 정확하게 나타낸다.


이어지는 모델 학습 글에서는 내부 활성값을 읽는 프로브를 살펴본다. 가중치의 저장 방식을 확인했으니, 다음은 레이어가 만든 표현에서 무엇을 측정할 수 있고 그 결과를 어디까지 해석할 수 있는지를 정리할 차례다.
