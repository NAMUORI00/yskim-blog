크기가 큰 인공지능 모델을 GPU 여러 개로 학습할 때는 학습 데이터를 장치마다 나누어 주거나, 모델의 계산 층인 레이어와 행렬 연산을 쪼개 배치한다. 이때 GPU를 어떤 방식으로 나누어 쓰느냐에 따라, 모델이 학습하며 조정하는 내부 숫자 값인 가중치를 한 번 갱신할 때 실제로 반영되는 데이터 표본 수가 달라진다. GPU 여덟 개를 동시에 써도 업데이트 한 번에 데이터가 몇 개 반영되는지, 나뉜 레이어가 어떤 순서로 계산하는지는 설정과 학습 루프 코드를 함께 봐야 알 수 있다.


이 설정들이 실제 코드에서 어떻게 맞물리는지 직접 확인해 보았다. 2026년 9월 15일에 확인한 Hugging Face의 [원본 Nanotron](https://github.com/huggingface/nanotron)과 이를 포크한 `NAMUORI00/nanotron` 저장소를 읽었다. 세 가지 병렬 방식이 각각 무엇을 나누는지부터 전역 배치 크기 계산, 파이프라인 실행 순서, 학습 재개를 위한 체크포인트 저장 구조까지 차례대로 따라간다.


## 세 가지 병렬 방식과 GPU 배치


여러 GPU에 학습 작업을 나누어 배치할 때 Nanotron은 **데이터 병렬**(DP), **파이프라인 병렬**(PP), **텐서 병렬**(TP) 세 가지 축을 조합한다. 여기서는 전문가 병렬(expert parallelism)이나 문맥 병렬(context parallelism) 같은 추가 축은 제외했다. GPU 여덟 개를 `DP=2`, `PP=2`, `TP=2`로 묶은 단순한 구성을 예로 들어 본다. 이 구성에서는 논리적 모델 복제본 두 개(`DP=2`)가 서로 다른 학습 데이터 묶음을 동시에 받아 처리한다. 이처럼 같은 모델을 복제한 그룹마다 다른 데이터를 나누어 주는 방식이 데이터 병렬이다. 각 복제본에 배정된 GPU 네 개는 새로운 데이터 표본을 더 받는 대신 같은 표본 하나의 모델 계산을 나누어 맡는다. 모델의 앞쪽 레이어와 뒤쪽 레이어를 두 단계(stage, `PP=2`)로 나누어 순서대로 통과시키는 방식이 파이프라인 병렬이다. 그리고 각 단계 안에서 한 레이어의 행렬 연산을 다시 두 조각(`TP=2`)으로 쪼개 여러 GPU가 함께 계산하는 방식이 텐서 병렬이다.


이 여덟 개 GPU의 데이터 흐름을 보면 복제본 A(GPU 0~3)와 복제본 B(GPU 4~7)는 각각 데이터 묶음 A와 B를 입력받는다. 입력 데이터를 앞 레이어부터 차례로 통과시켜 예측값을 구하는 과정을 **순전파**(forward pass)라고 한다. 순전파가 시작되면 복제본 A의 앞 레이어를 맡은 GPU 0, 1이 연산을 마친 뒤 중간 계산 결과인 활성값(activation)을 뒤 레이어인 GPU 2, 3으로 넘긴다. 그다음 정답과의 오차를 거꾸로 전달하며 가중치 수정 값인 기울기(gradient)를 구하는 **역전파**(backward pass)가 진행된다. 역전파가 끝나면 두 복제본에서 같은 위치의 파라미터를 맡은 GPU끼리 기울기를 동기화해 가중치를 똑같이 맞춘다.

그림 1. DP=2, PP=2, TP=2 구성에서 GPU 여덟 개의 논리적 배치와 데이터 흐름. 출처: Nanotron의 병렬 축 구분을 바탕으로 직접 구성. GPU 번호는 논리적 배치를 설명하기 위한 표기다.


실제 학습에서 어느 병렬 축을 늘릴지는 GPU 메모리 용량과 장치 간 통신 여건에 따라 정한다. 모델 자체가 커서 단일 GPU 메모리에 들어가지 않으면 텐서 병렬이나 파이프라인 병렬로 모델을 쪼개야 한다. 반대로 모델이 GPU에 올라가고 한 번에 처리할 데이터 표본 수를 늘리고 싶다면 데이터 병렬을 늘릴 수 있다. 다만 어느 쪽이든 장치 사이에 데이터를 주고받는 통신과 대기 시간이 따라오므로, GPU 수를 늘린 비율만큼 학습 시간이 그대로 줄어든다고 가정할 수는 없다.


## 데이터 병렬 수와 전역 배치 계산


앞선 예처럼 GPU 여덟 개를 모두 쓰더라도 텐서 병렬과 파이프라인 병렬에 배정된 장치는 같은 데이터 표본의 연산을 나누어 맡을 뿐이다. 가중치를 한 번 갱신할 때 처리하는 전체 표본 수를 **전역 배치 크기**(global batch size)라고 한다. 전역 배치 크기는 전체 GPU 수가 아니라 데이터 병렬 그룹 크기를 기준으로 계산한다. Nanotron의 [학습 반복 처리](https://github.com/NAMUORI00/nanotron/blob/9a542e794670a8c0d0232ed34098942aefe0079f/src/nanotron/trainer.py) 코드를 보면 전역 배치 크기는 다음 세 항목의 곱으로 구한다.


```plain text
global_batch_size
  = micro_batch_size
  × batch_accumulation_per_replica
  × 데이터 병렬 그룹 크기
```


한 번의 순전파에 넣는 작은 묶음인 마이크로 배치 크기(`micro_batch_size`)는 2로 둔다. 복제본마다 기울기를 모아 두는 누적 횟수(`batch_accumulation_per_replica`)는 4이고 데이터 병렬 크기(`DP`)는 2라고 하자. 이때 가중치 업데이트 한 번에 해당하는 전역 배치 크기는 `2 × 4 × 2 = 16`이다. 만약 여기에 `TP=2`와 `PP=2`까지 다시 곱해 64로 세면, 똑같은 표본이 나뉜 레이어와 텐서 조각을 지나가는 과정을 새로운 표본으로 중복 집계하게 된다. 표본 하나의 입력 시퀀스 길이(`sequence_length`)를 1,024토큰으로 고정해 처리한다고 하자. 그러면 업데이트 한 번에 다루는 토큰 위치는 `16 × 1,024 = 16,384`개가 된다.


![마이크로 배치 2, 누적 횟수 4, 데이터 병렬 2를 곱해 전역 배치 16 표본과 16,384 토큰을 구하고, TP=2와 PP=2는 모델 분할이므로 표본 수 계산에서 제외함을 보여 주는 도식](/images/notion/tech-06-03/image-2.png)


그림 2. 가중치 업데이트 1회 기준 전역 배치 크기(16)와 처리 토큰 수(16,384) 계산 구조.


다만 빈자리를 채우는 패딩(padding)이나 일부 구간을 오차 계산에서 빼는 손실 마스킹(loss masking)이 쓰일 때가 있다. 여러 문장을 이어 붙이는 패킹(packing) 방식에 따라서도 16,384개와 실제 유효 학습 토큰 수는 달라질 수 있다. Nanotron 저장소의 처리량 계산 코드는 전역 배치 크기와 `sequence_length`를 사용하고 있어, 실행 결과를 읽을 때도 이 정의를 기준으로 삼았다. 또한 GPU 수를 바꾸면서 배치 크기도 함께 바꾸면 실행 속도뿐 아니라 최적화 조건까지 달라진다. 같은 실험을 더 빨리 수행했는지 비교하려면 학습률, 업데이트 횟수, 전체 소비 토큰 수도 맞아야 하므로 실험 설정을 기록할 때는 장치 수와 배치 크기를 별도 항목으로 나누어 본다.


## 파이프라인 스케줄과 실행 순서


전역 배치 하나를 채우기 위해 각 복제본이 마이크로 배치 네 개를 연속으로 처리할 때, 파이프라인으로 나뉜 앞뒤 레이어는 정해진 스케줄에 따라 순전파와 역전파를 실행한다. 병렬 설정을 담당하는 [ParallelismArgs](https://github.com/NAMUORI00/nanotron/blob/9a542e794670a8c0d0232ed34098942aefe0079f/src/nanotron/config/parallelism_config.py)는 파이프라인 엔진(`pp_engine`)과 텐서 병렬 통신 모드(`tp_mode`)를 따로 둔다. 설정에서 `pp_engine`을 생략하면 기본값으로 `AllForwardAllBackward`를 선택한다. `tp_mode`의 기본값은 모든 조각의 연산 결과를 합산해 맞추는 `ALL_REDUCE`다. 프레임워크가 여러 방식을 지원한다는 점과 특정 실행에서 적용되는 기본값은 구분해서 읽어야 한다.


파이프라인 실행 엔진인 [AllForwardAllBackwardPipelineEngine](https://github.com/NAMUORI00/nanotron/blob/9a542e794670a8c0d0232ed34098942aefe0079f/src/nanotron/parallel/pipeline_parallel/engine.py)은 누적할 마이크로 배치의 순전파를 모두 먼저 수행한다. 이때 역전파 계산에 필요한 활성값을 상태에 보관해 두었다가 역전파를 한꺼번에 몰아서 진행한다. 같은 파일에는 `1F1B`(One-Forward-One-Backward) 엔진도 함께 들어 있다. 이 엔진은 초기 준비 구간에서 순전파를 먼저 흘려보낸 뒤, 본 구간에서 순전파와 역전파를 한 번씩 번갈아 배치하고 마지막에 남은 역전파를 마무리한다. 어느 스케줄이든 마이크로 배치 네 개의 처리가 끝나 누적 기울기가 만들어지면, 복제본 간 기울기 동기화와 기울기 상한을 자르는 클리핑(clipping)이 이어진다. 그 뒤 학습 루프는 가중치를 갱신하는 `optimizer.step`과 기울기를 비우는 `zero_grad`를 차례로 호출한다.


![복제본별 마이크로 배치 4개가 AFAB 또는 1F1B 파이프라인 스케줄을 거쳐 누적 기울기를 만들고, 동기화와 클리핑 뒤 옵티마이저 업데이트 1회와 기울기 초기화로 이어지는 순서도](/images/notion/tech-06-03/image-3.png)


그림 3. 마이크로 배치 처리부터 파이프라인 스케줄을 거쳐 한 번의 가중치 업데이트에 이르는 흐름. 출처: 분할한 모델의 실행 연결과 학습 반복 처리를 바탕으로 직접 구성. 세부 통신 겹침과 각 rank의 시간표는 생략했다.


`1F1B` 스케줄에서는 역전파를 일찍 시작하는 만큼, 역전파 차례를 기다리며 메모리에 머무는 활성값을 줄일 여지가 있다. 다만 실제 이점은 파이프라인 단계 수, 마이크로 배치 수, 통신과 계산 시간의 비율에 영향을 받는다. 여기서 확인한 범위는 코드에 작성된 스케줄 구현까지이며, 특정 GPU에서 메모리가 얼마나 절감되는지는 측정하지 않았다. 작은 예제를 실행해 두 엔진의 업데이트 결과를 직접 대조하는 작업은 다음 과제로 남아 있다.


## 체크포인트의 저장 항목과 재개 조건


마이크로 배치 누적과 가중치 업데이트가 반복되는 학습을 중간에 멈췄다가 다시 시작하려면, 그 시점의 상태를 파일로 남겨 두는 **체크포인트**(checkpoint)가 필요하다. 이때 모델 가중치만 남겨서는 업데이트가 어디까지 진행됐는지 알 수 없다. Nanotron의 [학습 상태 저장](https://github.com/NAMUORI00/nanotron/blob/9a542e794670a8c0d0232ed34098942aefe0079f/src/nanotron/serialize/main.py) 코드는 다섯 가지 항목의 저장 경로를 각각 나눈다. 저장 항목에는 설정(config), 분할된 모델 가중치(model), 가중치 갱신 상태를 담은 옵티마이저 상태(optimizer)가 있다. 여기에 학습 속도를 조절하는 학습률 스케줄러(lr scheduler)와 진행 단계를 기록한 학습 메타데이터(metadata)가 더해진다. 저장 옵션에 따라 체크포인트에 포함되는 항목이 달라지므로, 어떤 상태가 기록되어 있는지 먼저 확인해야 학습 재개 조건을 판단할 수 있다.


코드에서 확인한 다섯 가지 저장 항목에 맞춰 학습 재개 실험의 비교 기준도 함께 세워 두었다. 체크포인트를 저장한 뒤 복원해 수행한 첫 업데이트의 오차 값인 손실(loss), 누적 소비 표본 수, 학습률을 중단 없이 그대로 진행한 실행과 대조하는 방법이다.


![체크포인트 저장 항목인 설정, 분할 모델 가중치, 옵티마이저 상태, 학습률 스케줄러, 학습 메타데이터 다섯 가지와 복원 후 첫 업데이트에서 확인할 손실, 소비 표본 수, 학습률 일치 기준을 나타낸 도식](/images/notion/tech-06-03/image-4.png)

## 결론


Nanotron 코드에서 GPU를 나누는 병렬 설정은 전역 배치 크기 계산, 파이프라인 스케줄, 체크포인트 구조에 각각 다르게 연결된다. 텐서 병렬과 파이프라인 병렬은 같은 표본의 연산을 나누어 맡으므로, 전역 배치 크기는 마이크로 배치 크기와 누적 횟수에 데이터 병렬 크기만 곱해 계산한다. 누적할 마이크로 배치는 기본값인 `AllForwardAllBackward`나 순전파와 역전파를 번갈아 실행하는 `1F1B` 스케줄로 처리한다. 학습을 멈췄다가 이어 가려면 분할된 모델 가중치뿐 아니라 옵티마이저 상태, 학습률 스케줄러, 학습 메타데이터가 체크포인트에 함께 있어야 한다.


이번에는 코드에서 스케줄 구현과 체크포인트 저장 경로를 확인했으며, `1F1B` 스케줄의 실제 GPU 메모리 절감량이나 엔진별 업데이트 결과는 아직 측정하지 않았다. 학습 도중에 병렬 배치(`DP`, `TP`, `PP`)를 바꾸어 재개할 때 저장된 분할 정보와 복원 경로가 어떻게 동작하는지도 추가로 확인해야 한다. 다음 강화학습 글에서는 환경에서 모은 경험과 보상을 어떤 단위로 기록하는지 이어서 다룬다.
