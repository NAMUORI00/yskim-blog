글자 명령으로 조작하는 코딩 에이전트 CLI를 여러 개 함께 쓸 때는 작업을 나누어 맡기고 결과를 하나로 모으는 **오케스트레이터**(orchestrator)가 필요하다. 해야 할 일을 저장해 두는 영속 작업 큐(persistent task queue)와 실행 엔진을 새로 만드는 방법도 있지만, 기존 도구 위에 규칙 문서만 얹는 방식도 있다. 사용자의 요청을 받아 도구를 호출하고 결과를 확인하기를 되풀이하는 **실행 루프**가 이미 Claude Code에 들어 있기 때문이다.


`claude-orchestrator` 저장소는 Claude Code의 실행 루프 위에 정책 문서와 명령, 위임 규칙을 얹어 오케스트레이터를 구성한다. 이 글에서는 고정 커밋(`23a74633900fd496add0134456e3fe3abff590ce`)을 기준으로 아키텍처 문서와 설치 스크립트, 정책 파일을 읽었다. 도구를 직접 설치하거나 위임 작업을 실행하지 않고 코드와 문서만으로 설계 범위와 한계를 확인한 기록이다. 본문에 연결한 소스 코드 링크는 비공개 저장소여서 접근 권한이 필요하며, 비동기 작업과 재시도, MCP의 기본 개념은 앞선 글에서 다루었다.


## 작업 위임과 결과 종합 구조


도입부에서 말한 설계 방식이 실제 저장소에서 어떻게 짜여 있는지 [아키텍처 문서](https://github.com/NAMUORI00/claude-orchestrator/blob/23a74633900fd496add0134456e3fe3abff590ce/claude/docs/orchestrator-architecture.md)부터 확인했다. 이 문서에는 Claude Code 안에 이미 도구 호출과 에이전트 실행 루프가 구현돼 있어 새 실행 엔진을 만들지 않았다는 설계 동기가 적혀 있다. 실행 루프 위에 행동 정책과 명령만 얹어 오케스트레이터 역할을 맡긴다는 설명이 문서에 남아 있어 코드만 보고 동기를 추측할 필요는 적었다. 저장소 문서는 이 설계의 근거로 [Anthropic의 에이전트 패턴 설명](https://www.anthropic.com/engineering/building-effective-agents)을 인용한다. 2026-09-15에 다시 확인한 해당 문서에서는 에이전트 작업 흐름을 경로 분기(라우팅), 순차 연결, 병렬화, 작업 분해와 위임, 평가와 수정 반복으로 구분한다. 아키텍처 문서에는 다른 시스템의 실험 수치도 함께 적혀 있었지만, 이는 참고 자료의 수치일 뿐 이 저장소 자체의 비용 절감이나 성능 향상 결과는 아니다.


전체 구조는 작업을 나누고 결과를 모으는 주 실행 에이전트 아래에 다른 도구를 부르는 얇은 **위임 정의**(delegation definition)를 연결한다. 예를 들어 위임 정의 중 하나인 `codex-delegate`는 외부 도구를 실행한 뒤 응답 결과와 코드, 수정 전후의 변경 차이(diff)를 돌려주도록 정해져 있다. 서로 다른 외부 실행기를 일관된 인터페이스로 다루려는 구성으로, 별도의 영속 작업 큐를 두는 아키텍처와는 방향이 다르다.

## 전역 설치 스크립트의 갱신 범위


앞 절에서 본 정책과 위임 파일은 [사용자 환경 설치 스크립트](https://github.com/NAMUORI00/claude-orchestrator/blob/23a74633900fd496add0134456e3fe3abff590ce/install.ps1)를 통해 로컬 컴퓨터에 배치된다. 고정 커밋의 `install.ps1`을 읽어 보면 사용자 설정 디렉터리에 `commands`, `agents`, `docs` 폴더를 복사하고 기본 지침과 설정 파일을 수정한다.


저장소 README에는 설치 스크립트가 '기존 파일을 덮어쓰지 않는다'고 요약돼 있지만, 실제 스크립트 코드를 보면 대상 항목마다 갱신 방식이 다르다. 예를 들어 `commands`와 `agents` 디렉터리 안의 파일은 이름이 같으면 `Copy-Item -Force` 명령으로 덮어쓴다. 반면 기본 작업 지침 파일에서는 지정된 표식(marker) 사이에 있던 이전 오케스트레이터 블록만 지우고 새 정책 블록을 덧붙여 기존 문서 전체를 바꾸지는 않는다. 공통 실행 설정 파일에서는 기본 모델을 `opus`로 지정하고, 도구 실행 허용 규칙을 기존 목록과 병합한다.


![install.ps1 스크립트가 기본 작업 지침은 표식 블록만 교체하고 명령과 에이전트 파일은 덮어쓰며 공통 설정은 모델과 허용 규칙을 병합하는 구조도](/images/notion/tech-07-02/image-2.png)


그림 2. 설치 스크립트([install.ps](http://install.ps/)1)가 대상 항목별로 적용하는 서로 다른 갱신 방식.


이처럼 사용자 설정 디렉터리에 전역으로 설치하면 프로젝트마다 같은 위임 정의를 되풀이해 배치하지 않아도 된다. 대신 프로젝트별로 다르게 두어야 할 설정이 전역 기본값에 가려질 수 있다. 또한 설치 스크립트는 MCP 서버 등록 명령을 호출한 직후 성공 문구를 출력하지만, 이 문구만으로는 MCP 서버를 실제로 호출할 수 있는지 알 수 없다. 파일 배치와 설정 파일 반영, 실행 루프의 도구 발견, 실제 요청과 응답 성공은 각각 따로 확인해야 하는 단계다.


## 마크다운 정책과 시간 제한 제어


설치 스크립트가 배치한 [정책 파일](https://github.com/NAMUORI00/claude-orchestrator/blob/23a74633900fd496add0134456e3fe3abff590ce/claude/CLAUDE.orchestrator.md)에는 위임 작업을 통제하는 세 가지 실행 규칙과 시간 초과 대응 지침이 적혀 있다. 먼저 하위 에이전트가 다시 다른 에이전트에게 작업을 넘기지 못하도록 위임 깊이를 한 단계로 제한한다. 실행 결과는 파일에 기록하고 외부 호출에는 시간 제한을 두며, 호출이 멈추면 종료한 뒤 다시 시도하라는 지침도 함께 둔다.


여기서 주의할 점은 이 정책 파일이 사람이 읽는 문서 형식인 **마크다운**(Markdown)으로 적혀 실행 에이전트에게 전달된다는 사실이다. 문서가 에이전트의 행동 방침을 정할 뿐, 파일 자체가 타이머를 실행하거나 재시도 횟수를 저장하지는 않는다. 실제로 시간 제한이 걸렸는지 확인하려면 에이전트가 만든 호출 명령과 실행 도구의 결과를 직접 읽어야 한다. 문서에 '시간 제한 정책이 있다'는 것과 실제 실행 환경(런타임)에서 '모든 호출에 종료 가능한 시간 제한이 적용되고 있다'는 것은 다른 상태이므로 구분해야 한다.


시간 초과가 발생했을 때 곧바로 재시도하는 규칙도 파일 수정 작업에서는 문제를 일으킬 수 있다. 예를 들어 외부 도구가 파일을 수정하는 도중 응답을 돌려주기 전에 시간 초과가 났다고 해 보자. 응답이 돌아오지 않았다는 사실만으로 파일이 바뀌지 않았다고 단정할 수는 없다. 이 상태에서 바로 재시도하면 같은 변경이 두 번 적용되거나, 아직 실행 중인 첫 번째 작업과 충돌할 수 있다.


이런 중복 적용과 충돌을 막으려면 응답이 끊겼을 때 작업 결과를 미확정 상태로 두어야 한다. 재시도하기 전에 실행 중인 프로그램(프로세스) 상태와 실제 파일 변경 여부를 먼저 확인하고, 작업마다 고유 ID와 시도 번호를 남기는 상태 저장 구조가 뒷받침되어야 안전하다.

## 얇은 위임 래퍼와 결과 종합 검증


정책 파일의 규칙 아래에서 외부 실행기를 실제로 호출하는 역할은 [codex-delegate 정의](https://github.com/NAMUORI00/claude-orchestrator/blob/23a74633900fd496add0134456e3fe3abff590ce/claude/agents/codex-delegate.md)가 맡는다. 이 파일은 하위 도구가 다른 도구에 다시 작업을 위임하지 않고, 외부 도구를 감싸 실행 결과만 돌려주는 얇은 **래퍼**(wrapper) 역할을 하도록 요구한다. 여러 위임 응답을 하나로 모으고 실제 코드 차이를 검토하는 책임은 정책 파일에 정의된 주 실행 에이전트가 진다.


주 실행 에이전트가 다른 모델의 결과를 받아 종합할 때도 짚어 볼 조건이 있다. 서로 다른 모델을 연결하면 문제를 보는 관점이 달라질 여지는 있지만, 두 모델이 같은 소스 코드와 잘못된 전제를 공유하면 비슷하게 틀릴 수도 있다. 예를 들어 두 도구가 모두 '문제없다'고 답한 것과 실제 빌드, 테스트, 사용 흐름이 통과한 것은 별개의 문제다. 결과를 종합할 때 작업에 사용한 파일과 커밋, 코드 차이, 실행한 검사, 남은 실패 항목을 함께 기록하면 텍스트 요약문에만 의존하는 범위를 줄일 수 있다.

## 결론


코드와 문서로 확인한 `claude-orchestrator`는 별도의 실행 엔진을 만드는 대신 기존 도구의 실행 루프를 재사용해 위임 방식을 일정하게 맞춘다. 다만 마크다운 문서에 적힌 규칙만으로는 설치 이후의 실제 도구 동작이나 시간 초과 뒤의 파일 상태까지 보장하기 어렵다.


이번에는 도구를 직접 실행하지 않고 문서와 스크립트만 읽었으므로, 설치 전후의 설정 차이와 실제 도구 호출 기록, 시간 초과 뒤의 중복 적용 여부는 아직 확인하지 못했다. 앞으로 작업 큐와 작업 간 의존성을 더 다루게 되면 정책 파일을 늘리는 방식만으로 충분한지, 명시적인 상태 저장소를 따로 두어야 하는지도 비교해 볼 과제다. 다음 글에서는 Discord 이벤트처럼 외부 입력이 계속 들어오는 환경에서 대화 세션과 도구 실행을 이어 가는 방식을 다룬다.
