작업 위임 구성을 정리하기 위해 claude-orchestrator의 정책, 명령, 위임 정의를 검토했다. Claude Code 실행 루프에 설치되는 규칙을 따라 자료 준비와 위임, 결과 종합, 실패 후 재시도의 책임을 나누었다.


## 구현과 확인 과정


claude-orchestrator의 설치 스크립트와 정책 파일을 읽으며 작업을 나누고 결과를 모으는 구성을 정리했다. Claude Code 위에 얹힌 정책, 명령, 위임 정의가 담당하는 범위와, 실패한 작업을 다시 시작하는 데 필요한 복구 상태를 함께 살펴봤다.


Claude Code의 기존 실행 루프 위에 정책, 명령, 위임 정의를 설치하는 형태였다. 비동기 작업과 재시도, MCP의 기본 개념은 앞선 글에서 이어 읽을 수 있다. 이번 글은 고정 커밋 기준으로 설치 스크립트와 정책 파일을 읽은 기록이며, 도구를 직접 설치하거나 위임 작업을 실행하지는 않았다. 소스 링크에는 비공개 저장소 접근 권한이 필요하다.


## 정책과 명령 중심의 구성


[아키텍처 문서](https://github.com/NAMUORI00/claude-orchestrator/blob/23a74633900fd496add0134456e3fe3abff590ce/claude/docs/orchestrator-architecture.md)에는 Claude Code에 이미 도구 호출과 에이전트 실행 루프가 있으므로 그 위에 정책과 명령을 얹는다는 설계 동기가 적혀 있었다. 설계 설명이 문서에 남아 있어서 코드만으로 동기를 추측할 필요는 적었다.


구조를 보면, 작업을 분해하고 결과를 종합하는 주체를 하나로 두고 다른 CLI를 호출하는 얇은 위임 정의를 연결하고 있었다. codex-delegate는 실행 결과와 코드, 차이를 반환하도록 정의돼 있었고, 서로 다른 실행기를 비슷한 위임 인터페이스로 다루려는 의도가 드러났다. 별도의 영속 작업 큐를 도입하는 구성과는 다른 방향이었다.


2026-09-15에 다시 확인한 [Anthropic의 에이전트 패턴 설명](https://www.anthropic.com/engineering/building-effective-agents)에서는 라우팅, 순차 연결, 병렬화, 작업 분해, 위임, 평가, 수정 반복을 구분하고 있었다.


저장소는 이 패턴들을 설계 근거로 인용하고 있었다. 다른 시스템의 실험 수치가 함께 언급돼 있었지만, 그 수치를 이 저장소 자체의 비용 절감이나 성능 향상으로 읽지는 않았다.

## 설치 파일과 설정 항목


[사용자 환경 설치 스크립트](https://github.com/NAMUORI00/claude-orchestrator/blob/23a74633900fd496add0134456e3fe3abff590ce/install.ps1)는 사용자 설정 디렉터리에 commands, agents, docs를 복사하는 구조였다.


정책 반영 방식을 보면, 기존 기본 작업 지침에서 표식 사이의 이전 블록을 제거한 뒤 새 블록을 덧붙이고 있었다. 기존 문서 전체를 새 정책으로 교체하지는 않지만, 같은 이름의 명령, 에이전트 파일은 Copy-Item -Force로 갱신된다.


공통 실행 설정에서는 모델 값을 opus로 설정하고 허용 규칙을 기존 목록과 합치고 있었다. 전역 설치 방식이라 프로젝트마다 같은 정의를 반복 배치하지 않아도 되지만, 프로젝트별 차이가 전역 기본값에 가려질 수 있는 범위가 생긴다. README에는 '기존 파일을 덮어쓰지 않는다'고 요약돼 있었는데, 실제로는 항목별로 갱신 범위가 달라서 나누어 읽는 편이 정확했다.


설치 스크립트에는 MCP 등록 호출 뒤 성공 문구를 출력하는 경로도 있었다. 다만 출력 문구만으로는 등록 후 서버 호출까지 성공했는지 알 수 없고, 파일 배치, 설정 반영, 도구 발견, 실제 요청 성공은 각각 별도의 확인 단계다. 고정 커밋의 스크립트 내용을 기준으로 확인했다.


## 재위임과 시간 제한 정책


[정책 파일](https://github.com/NAMUORI00/claude-orchestrator/blob/23a74633900fd496add0134456e3fe3abff590ce/claude/CLAUDE.orchestrator.md)에는 위임 깊이를 한 단계로 제한하고, 결과를 파일에 기록하며, 호출에 시간 제한을 두는 규칙이 적혀 있었다. 호출이 멈추면 종료하고 다시 시도한다는 규칙도 있었다.


이 규칙은 실행 에이전트의 행동 방침을 정의하지만, 파일 자체가 타이머를 실행하거나 재시도 횟수를 저장하지는 않는다. 실제로 제한이 걸렸는지는 생성된 호출과 실행 도구의 결과를 읽어야 확인할 수 있다. '시간 제한 정책이 있다'는 것과 '모든 호출에 종료 가능한 시간 제한이 적용되고 있다'는 것은 다른 상태이므로 구분해서 기록했다.


예를 들어 파일 수정 작업이 응답을 반환하기 전에 시간 초과가 났다고 하면, 응답이 없다는 사실만으로 파일이 바뀌지 않았다고 판단할 수는 없다. 바로 재시도하면 같은 변경이 두 번 적용되거나, 첫 작업이 계속 실행 중인 상태에서 충돌할 수 있다. 재시도 전에 프로세스 상태와 실제 변경 여부를 확인하는 단계가 빠져 있으면 이런 중복, 충돌이 발생할 수 있는 구간이 남는다.

## 실행 요약과 변경 내용 검토


[codex-delegate 정의](https://github.com/NAMUORI00/claude-orchestrator/blob/23a74633900fd496add0134456e3fe3abff590ce/claude/agents/codex-delegate.md)는 다른 도구에 다시 위임하지 않고 결과를 돌려주는 얇은 래퍼 역할을 요구하고 있었다. 주 실행 에이전트가 응답들을 종합하고 실제 차이를 검토하도록 하는 규칙은 정책 파일 쪽에 적혀 있었다.


서로 다른 모델을 쓰면 관점이 달라질 여지는 있지만, 같은 소스와 잘못된 전제를 공유하면 비슷하게 틀릴 수도 있다. 두 도구가 모두 '문제없다'고 답한 것과 빌드, 테스트, 사용 흐름이 실제로 통과한 것은 별개다. 종합 단계에서 사용한 파일, 커밋, 실행한 검사, 남은 실패를 함께 기록하면, 요약문에만 의존하는 범위를 줄일 수 있다.


전체적으로 이 저장소는 기존 도구의 실행 루프를 재사용하면서 위임 방식을 일정하게 만드는 구성이었다. 후속으로는 설치 전후 차이와 실제 도구 호출 기록을 함께 확인하고, 시간 초과 뒤 중복 적용이 일어나는지 살펴볼 부분이 남아 있다.


작업 큐와 의존성을 더 다루게 되면, 정책 파일을 늘리는 것만으로 충분한지 명시적인 상태 저장이 필요한지 비교해 볼 수 있다. 다음 글에서는 Discord 이벤트처럼 입력이 계속 들어오는 환경에서 세션과 도구 실행을 이어 가는 방식을 살펴본다.


## 작업을 정리하며


위임에서는 작업을 나누는 기준과 결과를 다시 확인하는 경로가 함께 필요하다. 응답이 끊겼을 때도 완료 여부를 판단할 수 있도록 작업 ID와 상태를 남기는 설계가 중요하다. 설치 성공 문구와 실제 도구 호출 성공도 별도 단계로 확인하려 한다.
