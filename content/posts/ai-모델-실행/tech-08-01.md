display-share에서는 캡처한 화면을 분석하고 결과를 다시 화면에 표시하는 경로를 구성했다. 캡처 해상도, 모델 입력 크기, UI 좌표가 달라지는 지점이 있어 크기 변환과 결과 전달을 함께 다뤘다.


## 구현과 확인 과정


display-share의 화면 캡처와 좌표 변환 과정을 코드 기준으로 따라가 봤다. 이 앱은 캡처한 화면을 분석하고 결과를 다시 화면에 표시하는데, 그 사이에서 이미지 크기와 좌표가 바뀌는 지점이 여러 곳 있다.


NAMUORI00/display-share의 b4460b7 커밋을 기준으로 캡처 → 분석 → 화면 표시 경로를 추적했다. 프레임, 해상도, 좌표의 기초 개념을 실제 Rust 구조체와 함수에 연결하는 내용이며, 특정 PC에서 측정한 처리 속도나 검출 성능을 다루지는 않는다.


## 프레임을 받는 경로와 분석하는 경로


[WindowsCaptureBackend](https://github.com/NAMUORI00/display-share/blob/b4460b7b3360fa93ccbd8f98f42cf1c44b37b618/capture-first/crates/capture-windows/src/lib.rs)는 DXGI Desktop Duplication으로 시작한다.


타입에 Windows Graphics Capture 이름이 있지만, 이 모듈에는 해당 실행 경로가 연결되어 있지 않았다. 지원하는 백엔드와 이름만 정의된 백엔드가 섞여 있는 상태였다.


[Microsoft 문서](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/desktop-dup-api)에 따르면 Desktop Duplication은 데스크톱 이미지를 DXGI 표면으로 전달한다.


이미지 형식은 BGRA8이며, 화면 회전과 포인터 처리는 별도로 다뤄야 하는 영역이다. API가 이 기능을 제공한다는 것과 앱이 모든 화면 조건을 처리한다는 것은 다른 이야기다.


앱은 캡처 스레드에서 CPU 버퍼를 준비하고, 분석 작업자에게는 CPU 데이터만 전달한다. D3D11 자원을 분석 스레드에서 다시 읽지 않으려는 구조로 보였다. GpuVisionPipeline이라는 모듈 이름이 붙어 있지만 현재 코드에는 CPU 변환이 들어 있어서, 모듈 이름만으로 전체 분석이 GPU에서 완료된다고 볼 수는 없었다.


## 기본 캡처 영역과 실제 분석 범위


[pipeline](https://github.com/NAMUORI00/display-share/blob/b4460b7b3360fa93ccbd8f98f42cf1c44b37b618/capture-first/crates/pipeline/src/lib.rs)에는 기본 중앙 ROI 320×320과 동기 process 경로가 있다. 그러나 앱의 VisionWorker는 process_analysis_roi를 호출한다.


그 입력을 만드는 [화면 캡처와 축소 처리](https://github.com/NAMUORI00/display-share/blob/b4460b7b3360fa93ccbd8f98f42cf1c44b37b618/capture-first/crates/capture-windows/src/dxgi.rs)는 capture_roi를 화면 전체로 두고, 긴 변이 최대 640인 분석 이미지를 만든다.


중앙만 보는 구조와 화면 전체의 물체를 표시하는 구조는 입력 범위가 다르다. 기본 상수와 실제 앱의 호출 경로를 나란히 확인한 이유다. roi_buffer에는 전체 화면을 축소한 버퍼가 담겼다.


![08-01-01.png](/images/notion/tech-08-01/image-1.png)


그림 1. 현재 앱이 사용하는 캡처와 분석 경로. 출처: 화면 캡처, 축소 처리, 백그라운드 영상 분석, pipeline의 호출 관계를 바탕으로 직접 구성. 분석과 미리보기가 함께 필요할 때 같은 전체 화면 읽기를 공유한다.


미리보기의 최소 생성 간격은 50ms, 분석은 66ms로 분리되어 있다. 코드에 설정된 간격 조건이다. 실제 처리율은 캡처, 분석, 표시 시간을 포함해 측정해야 한다. 분석이 느려지더라도 화면 표시가 같은 속도로 묶이지 않도록 분리한 구조였다. 다만 서로 다른 시점의 이미지와 결과가 함께 표시될 가능성은 별도로 확인이 필요한 부분이다.


## 네 좌표계를 작은 숫자로 따라가기


설명을 위해 원본 화면을 1920×1080으로 놓으면, 분석 버퍼는 640×360이 된다. 모델 입력이 640×640이면 전처리에서 세로 방향이 다시 늘어난다.


[cpu_preprocess_nchw](https://github.com/NAMUORI00/display-share/blob/b4460b7b3360fa93ccbd8f98f42cf1c44b37b618/capture-first/crates/vision-gpu/src/lib.rs)는 지정 크기로 직접 resize하며, 여백을 넣는 letterbox 처리는 하지 않는다.


모델 입력의 점 (320, 320)은 화면 전체 ROI에서 다음처럼 돌아간다.


```plain text
원본 x = ROI 시작 x + 모델 x × ROI 폭 / 모델 폭
원본 y = ROI 시작 y + 모델 y × ROI 높이 / 모델 높이

x = 0 + 320 × 1920 / 640 = 960
y = 0 + 320 × 1080 / 640 = 540
```


예제의 점은 원본 화면의 중심으로 돌아왔다. [UI의 박스 표시 코드](https://github.com/NAMUORI00/display-share/blob/b4460b7b3360fa93ccbd8f98f42cf1c44b37b618/capture-first/crates/ui/src/lib.rs)는 이 계산 뒤 미리보기 축소 비율과 실제 표시 사각형의 크기를 적용한다. 모델 좌표에 미리보기 배율만 곱하면 중간 변환이 빠진다.


![readable-08-01-02.png](/images/notion/tech-08-01/image-2.png)


그림 2. 화면 전체를 정사각형 모델 입력으로 변환했을 때의 좌표 복원 예제. 출처: UI 변환식을 바탕으로 직접 계산. 실제 검출 결과가 아닌 설명용 점이다.


HSV 결과는 경로가 다르다. 검출 함수가 분석 버퍼의 박스를 이미 원본 화면 크기로 확대해서 반환하기 때문에, UI 쪽에서 모델 입력 역변환을 다시 수행하지 않는다. 겉으로는 비슷한 사각형이지만 어느 좌표계에서 반환된 값인지가 다르므로, 자료형 옆에 좌표계를 표기해 두면 혼동을 줄일 수 있는 지점이다.


## 좌표와 프레임 시점의 일치


분석 입력 AnalysisFrame에는 frame_number가 있지만 [WorkerEvent::Frame](https://github.com/NAMUORI00/display-share/blob/b4460b7b3360fa93ccbd8f98f42cf1c44b37b618/capture-first/apps/smartscreencapture/src/vision_worker.rs)에는 그 번호가 전달되지 않는다. UI가 받은 검출 결과와 현재 미리보기가 같은 캡처에서 나온 것인지 이 이벤트만으로 대조하기 어렵다.


큐는 용량이 제한되어 있고, try_send는 가득 찬 큐에 대해 새 작업을 보내지 못한다. 큐가 가득 차면 새 항목을 버리므로, 화면에 남는 결과의 최신성은 큐 상태와 처리 속도에 따라 달라진다.


움직이는 대상의 경우 좌표 변환의 정확성뿐 아니라 결과가 얼마나 오래된 것인지도 영향을 준다. 후속 검증에서 확인할 부분은 프레임 번호를 출력 이벤트까지 연결하는 것, 그리고 캡처 시각과 표시 시각의 차이를 측정하는 것이다.


이번에 읽은 경로는 CPU 읽기와 resize를 포함한다. supports_zero_copy가 true인 캡처 백엔드에서 출발하더라도, 분석 과정 전체를 복사 없는 처리로 볼 근거는 코드에서 확인되지 않았다. 다음 글에서는 이 분석 버퍼에서 HSV와 YOLO가 각각 무엇을 찾는지, 그리고 두 결과를 같은 '검출 성공'으로 묶기 어려운 이유를 정리한다.


## 작업을 정리하며


화면 분석의 결과는 좌표와 시각을 함께 가져야 쓸모가 있다. 박스가 정확해도 오래된 프레임의 결과라면 현재 화면과 어긋날 수 있다. 다음에는 프레임 번호와 캡처, 표시 시각을 끝까지 연결해 위치 오차와 처리 지연을 나누어 확인하려 한다.
