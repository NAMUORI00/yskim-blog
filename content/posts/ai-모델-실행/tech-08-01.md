화면에서 특정 물체나 색상을 찾아 그 자리에 상자를 그리려면 모니터 화면을 캡처해 분석해야 한다. 그런 다음 찾아낸 위치를 앱의 사용자 인터페이스(UI) 화면 위에 다시 맞춰 그린다. 문제는 캡처한 원본 화면, 분석용 이미지를 임시로 담는 **버퍼**(buffer), 모델 입력 이미지, 앱 창의 미리보기 크기가 모두 다르다는 점이다. 단계마다 달라진 가로세로 해상도와 비율을 거꾸로 계산하지 않으면 검출 상자가 엉뚱한 위치에 그려진다.


이 글에서는 `NAMUORI00/display-share` 저장소의 `b4460b7` 커밋을 기준으로 화면 캡처와 영상 분석, UI 표시 과정을 코드로 따라간다. 연속된 화면의 한 장면인 **프레임**(frame)과 해상도, 위치 기준인 **좌표계**가 실제 Rust 구조체와 함수에 어떻게 구현되어 있는지 확인한다. 특정 PC 환경에서의 처리 속도나 검출 성능 측정은 다루지 않는다.


## 화면 캡처와 CPU 버퍼 변환


화면 캡처부터 UI 표시까지의 흐름은 운영체제에서 모니터 화면 프레임을 받아 오는 일로 시작한다. `display-share`의 윈도우 화면 캡처 모듈인 [WindowsCaptureBackend](https://github.com/NAMUORI00/display-share/blob/b4460b7b3360fa93ccbd8f98f42cf1c44b37b618/capture-first/crates/capture-windows/src/lib.rs)는 윈도우의 화면 복제 기능(API)인 DXGI Desktop Duplication으로 동작을 시작한다. 코드의 타입 정의에는 Windows Graphics Capture라는 이름도 들어 있지만, 이 모듈에 실제 실행 경로가 연결되어 있지는 않았다. 실제로 동작하는 캡처 백엔드와 이름만 정의된 백엔드가 코드에 섞여 있는 상태다.


[Microsoft 문서](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/desktop-dup-api)를 보면 Desktop Duplication API는 데스크톱 화면 이미지를 그래픽 카드(GPU) 메모리의 DXGI 표면(surface)으로 전달한다. 이 이미지는 픽셀 하나마다 파랑, 초록, 빨강, 투명도를 8비트씩 담는 BGRA8 형식을 쓰며, 화면 회전이나 마우스 포인터 합성은 별도로 처리해야 한다. 운영체제 API가 화면 복제 기능을 제공하는 것과 앱이 모든 화면 조건을 직접 처리하는 것은 별개의 문제다.


캡처한 프레임을 분석 단계로 넘길 때, 앱은 화면을 찍는 작업 흐름인 캡처 **스레드**(thread)에서 미리 CPU 메모리 버퍼를 준비한다. 그리고 뒤에서 분석을 맡는 백그라운드 작업자(worker)에게는 CPU 데이터만 전달한다. 그래픽 자원인 D3D11 텍스처를 분석 스레드에서 다시 읽지 않도록 두 작업을 분리한 것으로 보였다. 코드에는 `GpuVisionPipeline` 모듈이 있고, 메모리 복사를 생략한다는 뜻의 `supports_zero_copy` 속성도 `true`로 설정되어 있다. 그러나 실제 실행 경로에는 CPU 메모리로 데이터를 읽고 크기를 조절(resize)하는 과정이 들어 있다. 모듈이나 속성 이름만 보고 분석 과정 전체가 메모리 복사 없이 GPU 안에서만 끝난다고 볼 수는 없었다.


## 기본 캡처 영역과 실제 분석 범위


CPU 메모리 버퍼로 옮긴 화면 데이터에서 실제로 어느 범위까지 분석에 쓰이는지는 함수 호출 경로를 따라가야 알 수 있다. 이미지에서 분석할 부분만 잘라낸 영역을 **관심 영역**(ROI, Region of Interest)이라고 한다. 분석 과정을 정의한 [pipeline](https://github.com/NAMUORI00/display-share/blob/b4460b7b3360fa93ccbd8f98f42cf1c44b37b618/capture-first/crates/pipeline/src/lib.rs) 모듈만 보면 화면 중앙의 320×320 영역만 잘라내는 기본 관심 영역 상수와 동기식 `process` 함수가 먼저 눈에 띈다. 하지만 실제 앱의 백그라운드 분석 스레드인 `VisionWorker`는 이 기본 경로 대신 `process_analysis_roi` 함수를 호출한다.


`process_analysis_roi`에 넣을 입력을 준비하는 [화면 캡처와 축소 처리](https://github.com/NAMUORI00/display-share/blob/b4460b7b3360fa93ccbd8f98f42cf1c44b37b618/capture-first/crates/capture-windows/src/dxgi.rs) 코드를 따라가 보면, 캡처 영역인 `capture_roi`를 모니터 화면 전체로 잡는다. 그리고 전체 화면의 가로세로 비율을 유지한 채 긴 변의 길이가 최대 640픽셀이 되도록 줄여 분석 버퍼(`roi_buffer`)에 담는다. 화면 중앙의 일부만 검사하는 경우와 모니터 전체에서 물체를 찾는 경우는 입력 범위가 전혀 다르다. 그래서 모듈에 적힌 기본 상수만 보지 않고 실제 호출 경로를 끝까지 따라가 확인했다.


캡처 스레드가 D3D11 텍스처를 CPU 메모리로 읽어 들이면, 이 데이터는 화면 표시용 미리보기 경로와 백그라운드 분석 경로로 나뉜다. 미리보기와 분석이 동시에 필요할 때는 전체 화면을 한 번 읽은 결과를 공유해 두 버퍼를 만든다.


![모니터 전체 화면이 DXGI 프레임과 CPU 버퍼 읽기를 거쳐 미리보기 버퍼 경로와 분석 버퍼 경로로 나뉜 뒤 UI 화면 표시로 합쳐지는 흐름도](/images/notion/tech-08-01/image-1.png)


그림 1. 화면 캡처, 축소 처리, 백그라운드 영상 분석, pipeline의 호출 관계를 바탕으로 구성한 캡처와 분석 흐름도다.


이때 코드에 설정된 최소 생성 간격은 미리보기가 50ms, 분석 입력이 66ms로 서로 다르다. 이 숫자는 코드에 지정된 최소 간격 조건일 뿐이며, 실제 초당 처리율은 캡처와 분석, 화면 표시 시간을 모두 합쳐 측정해야 알 수 있다. 분석 작업이 길어지더라도 화면 미리보기까지 함께 느려지지 않도록 두 주기를 나눈 것이다. 다만 주기가 나뉘어 있는 만큼, 화면에 그려진 미리보기 이미지와 그 위에 겹쳐진 검출 상자가 서로 다른 시점의 프레임에서 나왔을 가능성은 따로 따져 봐야 한다.


## 네 좌표계와 검출 경로별 좌표 변환


전체 화면을 축소한 분석 버퍼는 검출 단계와 UI 표시를 거치며 크기가 다시 바뀌므로 단계마다 좌표를 알맞게 변환해야 한다. 프레임이 캡처되어 화면에 다시 그려지기까지는 원본 화면, 축소된 분석 버퍼, 정사각형 모델 입력, UI 미리보기 표시 영역이라는 네 가지 좌표계를 거친다.


원본 모니터 화면 해상도가 1920×1080인 경우를 예로 들면, 긴 변을 640으로 맞춘 분석 버퍼(`roi_buffer`)의 크기는 640×360이 된다. 이어서 객체 검출 모델에 넣기 위해 이미지를 640×640 정사각형으로 바꾸면 가로 길이는 그대로지만 세로 방향은 360에서 640으로 늘어난다. 모델 입력을 준비하는 전처리 함수 [cpu_preprocess_nchw](https://github.com/NAMUORI00/display-share/blob/b4460b7b3360fa93ccbd8f98f42cf1c44b37b618/capture-first/crates/vision-gpu/src/lib.rs)는 원본 비율을 유지하려고 위아래에 여백을 채우는 **레터박스**(letterbox) 방식을 쓰지 않는다. 대신 이미지를 목표 크기로 바로 늘려(resize) 색상 채널별 값을 묶는 채널 우선 배열(NCHW)로 변환한다.


이 때문에 640×640 모델 입력 이미지에서 찾은 좌표를 원본 화면 좌표로 되돌릴 때는 가로와 세로에 서로 다른 배율을 곱해야 한다. 화면 전체를 ROI로 잡았을 때, 모델 입력의 중심점인 `(320, 320)`은 다음 계산을 거쳐 원본 화면 좌표로 복원된다.


```plain text
원본 x = ROI 시작 x + 모델 x × ROI 폭 / 모델 폭
원본 y = ROI 시작 y + 모델 y × ROI 높이 / 모델 높이

x = 0 + 320 × 1920 / 640 = 960
y = 0 + 320 × 1080 / 640 = 540
```


가로에 3(`1920 / 640`), 세로에 1.6875(`1080 / 640`)를 곱하면 원본 1920×1080 화면의 정중앙인 `(960, 540)`으로 돌아온다. [UI의 박스 표시 코드](https://github.com/NAMUORI00/display-share/blob/b4460b7b3360fa93ccbd8f98f42cf1c44b37b618/capture-first/crates/ui/src/lib.rs)는 이렇게 복원한 원본 화면 좌표에 다시 미리보기 축소 비율과 실제 표시 사각형의 크기를 적용해 최종 상자를 그린다. 만약 중간 복원 과정을 건너뛰고 정사각형 모델 좌표에 곧바로 미리보기 배율만 곱하면, 전처리에서 세로로 늘어났던 비율이 보정되지 않아 상자 위치가 어긋난다.


![모델 입력 640×640의 점 (320, 320)이 가로 3배, 세로 1.6875배 역변환을 거쳐 원본 화면 1920×1080의 점 (960, 540)과 UI 표시 영역 중심으로 변환되는 다이어그램](/images/notion/tech-08-01/image-2.png)


그림 2. UI 변환식을 바탕으로 설명용 모델 입력 좌표인 (320, 320)이 원본 화면과 미리보기 중심 좌표로 복원되는 과정을 계산한 예제다.


반면 색상 영역을 찾는 HSV 검출 결과는 좌표 변환 경로가 다르다. HSV 검출 함수는 640×360 분석 버퍼에서 찾은 상자 좌표를 함수 내부에서 이미 1920×1080 원본 화면 크기로 확대해 반환한다. 그래서 UI 코드에서는 모델 출력에 적용했던 역변환 식을 거치지 않고, 원본 화면 기준으로 바로 미리보기 배율만 적용한다.


![분석 버퍼 640×360에서 나뉜 모델 검출 경로(640×640 기준 반환 후 UI에서 원본 복원과 배율 적용)와 HSV 검출 경로(함수 내부에서 1920×1080으로 확대 후 UI에서 미리보기 배율만 적용)의 비교도](/images/notion/tech-08-01/image-3.png)


그림 3. 분석 버퍼에서 출발한 모델 검출 결과와 HSV 검출 결과가 서로 다른 좌표계를 거쳐 UI에 표시되는 흐름 비교도다.


모델 검출 상자와 HSV 검출 상자는 코드에서 겉보기엔 비슷한 사각형 데이터로 다뤄지지만, 함수를 빠져나올 때 기준이 되는 좌표계가 서로 다르다. 구조체나 변수 이름 옆에 어느 좌표계 기준의 값인지 밝혀 두지 않으면 변환을 중복 적용하거나 빼먹기 쉽다.


## 프레임 번호 전달과 표시 시점 대조


좌표 변환식이 정확하더라도 화면 속 물체가 움직이고 있다면, UI에 그려진 검출 상자가 현재 미리보기 화면과 같은 시점의 프레임에서 나왔는지 확인해야 한다. 코드를 확인해 보니 캡처 스레드가 분석 작업자에게 넘기는 입력 구조체인 `AnalysisFrame`에는 프레임 번호(`frame_number`)가 들어 있다. 그러나 분석이 끝난 뒤 UI 쪽으로 결과를 돌려주는 [WorkerEvent::Frame](https://github.com/NAMUORI00/display-share/blob/b4460b7b3360fa93ccbd8f98f42cf1c44b37b618/capture-first/apps/smartscreencapture/src/vision_worker.rs) 이벤트에는 이 프레임 번호가 전달되지 않는다. 이 때문에 UI가 받은 검출 결과와 현재 화면에 띄운 미리보기 이미지가 같은 캡처 프레임에서 나온 것인지 이벤트 정보만으로는 대조하기 어렵다.


![화면 캡처에서 50ms 간격의 미리보기 이미지와 66ms 간격의 AnalysisFrame이 나뉘고, VisionWorker를 거친 WorkerEvent::Frame에서 프레임 번호가 빠져 UI 화면 합성 시 시점을 대조할 수 없는 구조도](/images/notion/tech-08-01/image-4.png)


그림 4. 캡처 스레드가 생성한 프레임 번호가 작업 큐와 VisionWorker를 거치며 출력 이벤트에서 빠지는 실제 구현 구조다.


게다가 캡처 스레드가 분석 작업을 순서대로 넣어 두는 대기열인 **큐**(queue)는 용량이 제한되어 있다. 캡처 스레드는 큐에 빈자리가 없을 때 기다리지 않고 넘어가는 비차단 전송 함수(`try_send`)로 프레임을 넣는다. 분석 속도가 캡처 속도를 따라가지 못해 큐가 가득 차면 `try_send`는 새 프레임을 큐에 넣지 않고 버린다. 결국 화면에 남아 있는 검출 결과가 얼마나 최신 프레임의 것인지는 당시의 큐 상태와 분석 처리 속도에 따라 달라진다.


움직이는 대상을 추적할 때는 좌표 계산의 정확성만큼이나 결과가 얼마나 오래된 프레임의 것인지도 화면 표시 위치에 영향을 준다. 상자 좌표를 아무리 정확히 변환해도 이전 프레임의 결과라면 현재 화면의 물체 위치와 어긋날 수밖에 없다. 프레임 번호를 출력 이벤트까지 연결하고 캡처 시각과 표시 시각의 차이를 재야, 화면의 어긋남이 계산 오차 때문인지 처리 지연 때문인지 구분할 수 있다.


## 결론


지금까지 `display-share`의 코드에서 화면 캡처 데이터가 분석 버퍼와 모델 입력을 거쳐 UI 미리보기 좌표로 변환되는 과정을 확인했다. 캡처 스레드는 모니터 전체 화면을 CPU 버퍼로 읽은 뒤 50ms 간격의 미리보기 경로와 66ms 간격의 640×360 분석 버퍼 경로로 나눈다. UI에 상자를 그릴 때 모델 검출 결과는 640×640 입력 좌표를 원본 화면 크기로 역산한 뒤 미리보기 배율을 곱한다. 반면 HSV 검출 결과는 함수 안에서 이미 원본 크기로 확대한 좌표에 미리보기 배율만 적용한다.


실제 PC 환경에서의 초당 처리율이나 지연 시간은 아직 측정하지 않았다. 또한 `AnalysisFrame`의 프레임 번호가 `WorkerEvent::Frame`까지 이어지지 않아, 미리보기와 검출 상자의 시점을 대조하는 일은 과제로 남았다. 다음 글에서는 640×360 분석 버퍼에서 HSV 색상 마스크와 YOLO 모델이 각각 무엇을 검출하며, 두 결과를 왜 같은 기준의 '검출 성공'으로 묶기 어려운지 다룬다.
