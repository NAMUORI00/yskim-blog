`display-share`의 분석 화면에는 색상 조건으로 픽셀을 찾는 HSV 경로와 객체 검출 모델로 물체를 찾는 YOLO 경로가 함께 들어 있다. 화면의 같은 물체 둘레에 네모 박스가 그려지더라도, 빨간 픽셀을 묶어 만든 박스와 모델이 물체 종류를 분류해 만든 박스는 판단 근거가 다르다.


앞 글에서는 화면을 캡처해 모델 입력 좌표로 바꾸는 과정을 먼저 확인했다. 이번에는 `NAMUORI00/display-share` 저장소(`b4460b7` 커밋)의 코드를 따라가며 두 경로가 박스를 만드는 조건을 점검했다. RGB와 HSV 색공간, 임계값, 마스크, 객체 검출의 기초 개념은 앞선 글에서 정리했으므로, 이 글에서는 `display-share` 내부 구현과 입출력 조건에 집중한다.


## 색 조건 경로와 모델 검출 경로


두 경로가 같은 화면에서 어떻게 다른 기준으로 박스를 만드는지 먼저 전체 흐름을 비교한다. HSV 경로는 픽셀의 색상(Hue), 채도(Saturation), 밝기(Value)가 지정한 범위 안에 들어오는지 검사한다. 빨간 표식처럼 찾고 싶은 색 조건을 사람이 직접 정해, 조건을 통과한 픽셀만 남긴 **마스크**(mask)를 만든다. 검출 결과가 나왔을 때 왜 그 영역이 잡혔는지 원인을 추적하기 쉽다. 다만 비슷한 색을 띤 배경이나 다른 물체도 같은 범위를 그대로 통과하며, 색 조건만으로는 물체의 종류를 구분하지 못한다.


반대로 YOLO 경로는 입력 이미지를 모델 계산용 다차원 숫자 배열인 텐서(tensor)로 바꾼다. 그다음 미리 학습된 가중치를 거쳐 물체의 종류를 뜻하는 클래스 이름과 점수를 출력한다. 사람이 색 규칙을 직접 짜는 대신 모델 구조와 학습 데이터, 출력 텐서 형식에 의존한다. `display-share`가 한 화면에 두 경로를 나란히 둔 것은, 색 조건을 직접 조절하는 검출과 학습된 범주를 찾는 검출을 같은 장면에서 비교하려는 구성으로 읽혔다.

이 가운데 HSV 경로의 기본 흐름은 [OpenCV 설명](https://docs.opencv.org/4.x/df/d9d/tutorial_py_colorspaces.html)에 나오는 색공간 변환 뒤 범위 마스크 생성 예제와 같다. `display-share`는 이 과정을 Rust 코드로 직접 구현하고 있었다. 같은 개념을 따른다는 것과 OpenCV 함수의 세부 동작을 그대로 재현했다는 것은 별개이므로, 실제 코드가 색상 범위와 마스크를 어떻게 처리하는지 단계별로 확인했다.


## 순환 색상 범위와 마스크 팽창


앞 절에서 본 두 경로 가운데 먼저 HSV 경로가 픽셀의 색 범위를 검사하고 마스크를 넓히는 과정을 코드로 따라간다. Rust 코드 묶음인 `vision-gpu` 크레이트의 [색상 범위 검사](https://github.com/NAMUORI00/display-share/blob/b4460b7b3360fa93ccbd8f98f42cf1c44b37b618/capture-first/crates/vision-gpu/src/hsv_detect.rs) 코드를 보면, 색상각(H)을 절반 범위로 바꾸고 채도(S)와 밝기(V)를 0~255 값으로 변환한다. 색상각은 원형으로 이어져 있어서 빨간색 주변을 고르려면 0 근처의 작은 값과 최댓값 근처의 큰 값을 함께 묶어야 할 때가 있다. 이 때문에 원의 양 끝을 아우르도록 하한이 상한보다 큰 값이 들어오면 조건문이 달라진다. 예를 들어 색상 하한이 170이고 상한이 10이면, 코드는 픽셀의 색상각이 `H ≥ 170` 또는 `H ≤ 10`인지 검사한다. 채도와 밝기가 지정한 범위 안에 있을 때, `H=175, S=220, V=200`인 픽셀은 마스크를 통과하지만 `H=90`인 픽셀은 통과하지 못한다.


색상 범위를 통과해 초기 마스크를 만든 뒤에는 설정한 커널(주변 픽셀을 살피는 작은 격자)로 두 번 **팽창**(dilation)한다. 팽창은 조건을 통과한 픽셀 둘레를 넓혀서 끊어진 이웃 영역을 잇고 작은 빈틈을 메워 준다. 하지만 서로 떨어진 두 물체가 하나로 합쳐지거나 결과 박스가 실제 물체보다 커지는 부작용도 생긴다. 코드는 원래 색 조건을 통과한 마스크와 팽창을 거친 마스크를 따로 보관하고 있어서, 팽창 단계가 검출 영역에 준 변화를 비교할 수 있게 되어 있다.

## 픽셀 수와 검출 영역 수의 집계


원래 마스크와 팽창 뒤 마스크를 따로 다루기 때문에, 결과를 모으는 집계 구조체에서도 두 단계의 숫자가 서로 다른 필드에 담긴다. `HsvMaskStats`의 `hit_count`는 원래 마스크에서 0이 아닌 픽셀의 개수다. 반면 `objects`는 팽창 뒤 찾은 물체 테두리(윤곽) 후보 가운데 최소 면적 조건을 통과한 영역의 목록이다. 필드 이름만 보고 `hit_count`를 검출된 물체 수로 읽으면, 한 물체를 이루는 픽셀 수를 물체 개수로 잘못 해석하게 된다.


상위 `pipeline`의 `hsv_hit_count` 함수에서는 이 두 값이 하나의 반환값으로 합쳐진다. `objects`에 검출된 영역이 있으면 그 목록의 길이를 반환하고, `objects`가 비어 있지만 `hit_count`가 양수이면 픽셀 수를 대신 반환한다. 함수 이름은 하나인데 조건에 따라 반환값의 단위가 영역 개수와 픽셀 수로 달라진다. 평가나 로그 기록에 이 값을 그대로 쓰면 마스크 픽셀 수와 검출 영역 수가 한 항목에 섞여 해석하기 어려워지므로, 두 값은 별도 항목으로 나누어 기록하는 편이 명확하다.

검출 영역을 추릴 때 윤곽 면적을 계산하는 코드에는 추가로 확인할 부분도 남았다. 코드는 경계 후보 픽셀을 데이터를 쌓아 두는 스택에 모은 뒤, 그 순서대로 다각형 면적 공식을 적용한다. 따라서 복잡한 모양에서도 스택에 쌓인 순서가 올바른 외곽선 둘레 순서가 되는지 대조해 볼 필요가 있다. 단순한 색 블록 테스트로 동작을 확인하는 것과, 임의의 복잡한 모양에서 OpenCV와 같은 면적을 반환하는지는 별개의 문제로 구분해 두었다.


## 검출 모델의 출력 형식과 후처리 조건


픽셀 조건을 단계별로 집계하는 HSV 경로와 달리, YOLO 경로는 모델이 내놓은 숫자 배열을 해석해 박스와 점수로 바꾸는 과정을 거친다. YOLO 경로를 담당하는 [inference-dml](https://github.com/NAMUORI00/display-share/blob/b4460b7b3360fa93ccbd8f98f42cf1c44b37b618/capture-first/crates/inference-dml/src/lib.rs) 크레이트에는 모델 출력을 좌표와 점수로 읽어 내는 **파서**(parser)가 들어 있다. 이 파서는 모델이 내놓는 결과 한 줄(레코드)의 길이에 따라 값을 다르게 읽는다. 레코드 길이가 6이면 각 값을 `x1`, `y1`, `x2`, `y2`, 점수, 클래스 ID 순서로 해석한다. 레코드가 6보다 길면 앞의 네 값을 중심 좌표와 폭, 높이로 읽고 바로 다음 값을 물체 존재 점수인 `objectness`로 둔다. 그 뒤 나머지 클래스 점수 가운데 최댓값을 골라 `objectness`와 곱해서 최종 점수를 구한다.


여기서 주의할 점은 ONNX 모델 파일을 메모리에 불러오고 실행 세션을 여는 데 성공했더라도 출력 해석까지 맞는다는 보장은 없다는 것이다. 모델 구조나 내보내기(export) 설정에 따라 별도의 `objectness` 항목이 없을 수도 있고, 이미 최종 검출 형태로 바뀐 텐서를 출력하거나 좌표 단위가 다를 수도 있다. 파일 이름에 YOLO가 들어 있다는 이유만으로 같은 파서를 쓰면 엉뚱한 위치를 좌표나 점수로 읽게 된다. 따라서 모델의 실제 출력 텐서 형식과 export 옵션을 파서 코드와 대조해야 한다.


후처리 단계인 `limit_results` 함수도 모델의 출력 형식과 맞물려 있다. 이 저장소의 `limit_results`는 검출 후보를 점수순으로 정렬해 상위 개수만 남긴다. 두 박스가 겹치는 비율(IoU)을 기준으로 중복 박스를 지우는 **비최대 억제**(NMS)는 따로 수행하지 않는다. 참고로 [현재 YOLO26 공식 문서](https://docs.ultralytics.com/models/yolo26/)는 NMS가 필요 없는 종단 간(end-to-end) 검출 방식을 소개하고 있다. 모델이 추론 결과에서 이미 중복을 제거해 내보내는 방식이라면 정렬과 개수 제한만으로 충분하지만, 그렇지 않은 모델이라면 한 물체에 여러 박스가 겹쳐 남게 된다. 결국 후처리 코드가 적절한지는 사용한 YOLO 모델의 최종 출력 조건에 맞춰 확인해야 한다.

## 경로별 오검출 원인과 해석 한계


이처럼 두 경로는 박스를 만드는 방식이 다르므로, 한 화면에서 결과를 비교할 때는 검출이 빗나간 이유도 경로별로 나누어 봐야 한다. 예를 들어 색상 마스크가 물체뿐 아니라 배경까지 함께 잡는다면 HSV 범위, 조명 변화, 팽창 커널 크기, 최소 면적 조건을 점검해야 한다. 반대로 YOLO 모델이 물체를 다른 클래스로 잘못 분류한다면 학습 데이터의 범주, 입력 변환, 출력 텐서 파서를 살펴봐야 한다. 화면에 비슷하게 잘못된 박스가 생겼더라도 고쳐야 할 지점은 경로마다 서로 다르다. 화면 UI에 표시되는 모델 점수 또한 별도의 확률 보정과 평가를 거쳤는지 확인하기 전에는 실제 그 물체일 확률로 곧바로 해석하기 어렵다.


## 결론


지금까지 `display-share`의 코드를 따라가며 HSV 색상 마스크와 YOLO 객체 검출 경로가 각기 다른 입출력 조건을 거쳐 박스를 만든다는 점을 확인했다. HSV 경로는 순환 색상 범위 검사와 두 번의 팽창을 거치는데, 집계 함수인 `hsv_hit_count`에서 영역 개수와 픽셀 수가 한 반환값에 섞인다. YOLO 경로는 레코드 길이에 따라 달라지는 출력 파서와 NMS 없이 상위 개수만 남기는 `limit_results` 함수를 모델의 실제 출력 형식과 대조해야 한다. 같은 이름의 모델이나 설정을 가져오더라도 텐서 형상, 좌표 기준, 임계값과 집계 단위의 의미를 코드와 대조해야 한다. 작은 테스트 입력과 예상 출력을 함께 남겨 두면 모델을 교체할 때 점검할 범위가 분명해진다.


반면 스택 순서로 계산한 윤곽 면적이 복잡한 모양에서도 OpenCV와 일치하는지, 화면의 모델 점수가 확률 보정을 거쳤는지는 아직 확인하지 않았다. 다음 단계로는 장면 변화와 설정 변경의 영향이 섞이지 않도록 동일한 입력 프레임을 고정해 두고 두 경로의 원래 출력과 후처리 출력을 비교할 계획이다. 이어지는 글에서는 화면의 색상 도구 슬라이더 범위가 마스크 조건과 저장 설정 파일로 어떻게 연결되는지 다룬다.
