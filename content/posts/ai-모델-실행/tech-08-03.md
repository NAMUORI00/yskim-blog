색을 색상(H), 채도(S), 명도(V) 세 숫자로 나타내는 방식을 **HSV**라고 부른다. 화면에서 특정 색을 찾는 프로그램은 이 숫자의 범위를 정해 조건에 맞는 픽셀만 골라낸 흑백 이미지인 **마스크**를 만든다. 그런데 두 프로그램에서 HSV 슬라이더를 똑같은 숫자로 맞춰도, 실제로 만들어지는 마스크나 물체를 표시하는 검출 상자가 서로 달라질 때가 있다.


프로그램마다 화면을 잘라내는 영역과 색상 성분의 순서, 입력값을 고치는 규칙, 마스크를 다듬는 단계가 다르기 때문이다. 이 글에서는 앞서 다룬 원리를 이어받아 공개 Rust 저장소인 `HsvColorPicker`와 비공개 Python 저장소인 `mss_color_project_`의 코드를 비교한다. 화면 입력부터 설정 저장까지 이어지는 경로를 따라가며 두 도구의 검출 결과가 달라지는 이유를 확인했다.


## 캡처 영역과 색상 채널 순서


검출 결과가 달라지는 첫 번째 이유는 두 도구가 화면을 잘라내는 영역과 픽셀의 색 성분을 저장하는 채널 순서가 다르기 때문이다. [HsvColorPicker의 화면 캡처 처리](https://github.com/NAMUORI00/HsvColorPicker/blob/700b7fca32f5176c8dfd2db22eaeb44fe7135224/src/capture.rs)는 선택한 모니터 이미지를 가져와 중앙에서 최대 320×320 정사각형 영역만 RGB 순서로 복사한다. 모니터 해상도가 320×320보다 작으면 가져올 수 있는 크기로 줄여서 읽는다. 이 때문에 프로그램 창에 보이는 모니터 전체 이미지와 실제 색상 검출에 쓰이는 중앙 영역은 크기가 다르다.


반면 [mss_color_project_의 Capture](https://github.com/NAMUORI00/mss_color_project_/blob/2a540ad0b42deddaae394f42a5ae3acd82447e52/modules/capture.py)는 화면 크기를 기준으로 기본 중앙 위치를 먼저 계산한다. 그다음 지정한 폭과 높이만큼의 영역을 화면 캡처 라이브러리인 MSS로 읽어 들인다. 이때 MSS가 메모리 버퍼에 담아 돌려주는 데이터는 파랑, 초록, 빨강, 투명도 순서인 **BGRA** 배열이다. RGB 순서를 기대하는 함수에 이 데이터를 그대로 넘기면 빨강과 파랑 채널이 뒤바뀐다. 따라서 뒤따르는 이미지 처리 함수가 색상 채널을 어떤 순서로 읽는지 함께 확인해야 했다.


![Rust 도구는 선택 모니터 중앙 최대 320x320 영역을 RGB로 복사하고, Python 도구는 지정한 폭과 높이를 BGRA 버퍼로 읽는 차이를 비교한 다이어그램](/images/notion/tech-08-03/image-1.png)


그림 1. HsvColorPicker와 mss_color_project_의 화면 캡처 영역 및 색상 채널 순서 비교.


화면을 입력받는 방식에서는 정지된 이미지를 다시 처리하는 경로가 있는지도 다르다. 실시간으로 움직이는 화면을 보면서 슬라이더를 조절하면 화면 자체의 변화와 설정을 바꾼 효과가 섞여서 보인다. `HsvColorPicker`에는 멈춰 있는 정지 이미지를 다시 처리하는 경로가 따로 있다. 같은 이미지를 고정해 두면 설정을 바꿨을 때의 영향만 화면 변화와 분리해서 확인할 수 있다. 조명이나 배율, 해상도 조건을 설정과 함께 기록해 두는 이유도 같은 입력 조건에서 검출 결과를 비교하기 위해서다.


## 색 범위 검사와 화면 입력 보정


화면을 캡처해 HSV 색 공간으로 바꾼 뒤에는 사용자가 입력한 최솟값(하한)과 최댓값(상한)으로 픽셀을 거른다. 이때 빨강처럼 색상 값 0의 양끝에 걸친 색을 찾으려면 범위를 170~10처럼 하한이 상한보다 크게 넣어야 한다. [Rust의 마스크 함수](https://github.com/NAMUORI00/HsvColorPicker/blob/700b7fca32f5176c8dfd2db22eaeb44fe7135224/src/detection/mask.rs)는 이처럼 색상 하한이 상한보다 큰 경우를 원의 경계를 가로지르는 **원형 범위**로 처리해 양끝 영역을 한 번에 포함한다.


그런데 설정값을 검증하는 [색상 범위 설정 검사](https://github.com/NAMUORI00/HsvColorPicker/blob/700b7fca32f5176c8dfd2db22eaeb44fe7135224/src/settings.rs)의 `clamp_min_max` 함수는 하한이 상한보다 크면 하한을 상한 값으로 덮어쓴다. 문제는 [앱의 설정 적용 함수](https://github.com/NAMUORI00/HsvColorPicker/blob/700b7fca32f5176c8dfd2db22eaeb44fe7135224/src/app.rs)가 검출기를 실행하기 전에 이 보정 함수를 먼저 호출한다는 점이다. 검출 함수 안에는 원형 범위를 처리하는 코드가 있지만, 일반 화면(UI) 입력 경로에서는 `clamp_min_max`가 먼저 실행된다. 이 때문에 170~10 같은 원형 범위가 검출 함수까지 그대로 전달되는지는 추가로 확인해야 했다.


![메모리의 HSV 설정이 명시적 저장을 통해 hsv_settings.json으로 저장되는 경로와 하한과 상한 보정을 거쳐 픽셀별 범위 검사로 전달되는 경로를 나타낸 흐름도](/images/notion/tech-08-03/image-2.png)


그림 2. 화면 입력 적용 처리와 색상 범위 설정 검사를 바탕으로 직접 구성한 HsvColorPicker의 입력, 보정, 저장 경로.


메모리에 올라간 HSV 설정은 프로그램을 실행한 폴더의 JSON 파일(`hsv_settings.json`)에서 읽고 쓴다. 파일을 읽지 못하거나 JSON 해석에 실패하면 프로그램은 미리 정해 둔 기본값으로 돌아간다. 이 기본값이 꽤 넓은 색상 범위를 포함하고 있어서, 설정 복원에 실패해도 화면에는 프로그램이 정상으로 열린 것처럼 보일 수 있다. 파일 복원이 실제로 성공했는지와 어떤 경로로 설정이 적용되었는지는 실행 단계에서 직접 확인할 과제로 남았다.


## 입력 배율과 마스크 후처리 비교


색상 범위를 검사해 조건에 맞는 픽셀만 남긴 이진 마스크를 만든 뒤에도 두 도구는 서로 다른 후처리 과정을 거친다. Rust 도구의 [Detector](https://github.com/NAMUORI00/HsvColorPicker/blob/700b7fca32f5176c8dfd2db22eaeb44fe7135224/src/detection/mod.rs)는 RGB 이미지를 HSV로 바꿔 마스크를 만들고, 3×3 커널로 영역을 넓히는 **팽창**(dilation) 연산을 두 번 수행한다. 그다음 넓어진 영역에서 윤곽선을 찾고 면적 조건을 검사해 검출 대상을 추린다. 여기서 `Detector`가 돌려주는 `mask`는 이미 두 번의 팽창을 거친 결과다. 따라서 원래 색상 범위에 들어간 픽셀만 따로 확인하려면 반환된 마스크를 팽창 전 마스크와 구분해서 다뤄야 한다.


반면 Python 도구가 호출하는 [process_frame](https://github.com/NAMUORI00/mss_color_project_/blob/2a540ad0b42deddaae394f42a5ae3acd82447e52/modules/image_processor.py)은 현재 설정된 배율에 따라 이미지를 먼저 축소한 뒤 HSV 마스크를 만들고 팽창을 다섯 번 적용한다. 이어서 서로 맞닿은 픽셀 덩어리를 하나로 묶는 **연결 성분**을 구하고, 픽셀 수와 가로세로 비율(종횡비)로 후보를 거른다. 검출된 후보가 있는지에 따라 다음 화면(프레임)을 처리할 축소 배율도 실행 중에 바꾼다.


![Rust Detector의 3x3 팽창 2회 및 윤곽선 검사 경로와 Python process_frame의 배율 축소, 팽창 5회, 연결 성분 검사 및 배율 조정 경로를 나란히 비교한 흐름도](/images/notion/tech-08-03/image-3.png)


그림 3. Rust Detector와 Python process_frame의 입력 축소 및 마스크 후처리 단계 비교.


예를 들어 원본 화면에서 10×10 픽셀 크기인 표식을 가로세로 절반 배율로 줄이면 약 5×5 픽셀 영역이 된다. 여기에 축소할 때 주변 픽셀 값을 섞는 경계 보간(interpolation)과 다섯 번의 팽창 연산이 더해지면 픽셀 수가 크게 달라진다. 이처럼 축소 배율과 팽창 횟수가 다르기 때문에 두 도구에 똑같은 H, S, V 숫자를 넣어도 최종 검출 상자는 달라진다. 한 도구에서 쓰던 최소 면적 수치를 다른 도구에 숫자만 그대로 복사해서는 같은 기준으로 동작하지 않는 이유다.


## 색상 설정의 JSON 구조와 복원 확인


검출 과정에 쓰인 색상 범위와 조건을 파일로 저장하고 다시 불러오는 설정 구조도 함께 비교했다. `mss_color_project_`의 [Python 뷰어](https://github.com/NAMUORI00/mss_color_project_/blob/2a540ad0b42deddaae394f42a5ae3acd82447e52/modules/custom_image_processor_viewer.py)에는 일반 설정 저장과 자주 쓰는 설정 묶음인 프리셋 저장이 별도 기능으로 나뉘어 있다. 일반 설정은 JSON 파일의 가장 바깥에 `lower_color`, `upper_color` 같은 이름을 바로 둔다. 반면 프리셋은 `hsv.lower`, `hsv.upper`처럼 상하위 단계를 묶어 저장하며, 파일을 읽는 로더와 적용 함수도 일반 설정과 다르다.


![현재 처리기 설정이 일반 설정(lower_color, upper_color)과 프리셋(hsv.lower, hsv.upper) 두 경로로 나뉘어 저장 및 로드된 뒤 같은 고정 이미지로 복원 결과를 확인하는 흐름도](/images/notion/tech-08-03/image-4.png)


그림 4. save_settings, save_preset, load_settings, _apply_settings를 바탕으로 직접 구성한 Python 도구의 두 저장 형식과 복원 확인 흐름.


설정이 두 형식으로 나뉘어 있을 때는 저장 완료 메시지만 보고 복원이 제대로 되었는지 판단하기 어렵다. 파일을 다시 불러온 뒤 이미지 처리기에 들어간 범위와 화면 입력 칸의 숫자, 같은 고정 이미지로 만든 마스크가 일치하는지 대조해야 한다. 두 형식을 하나로 합친다면 HSV 값 외에 파일 형식 버전, 캡처 영역, 입력 배율, 후처리 조건을 함께 적어 두어야 결과를 비교하기 수월하다.


## 결론


두 저장소의 코드를 따라가며 색상 검출 결과가 HSV 수치와 캡처 영역, 채널 순서, 입력 배율, 팽창 횟수에 따라 달라진다는 점을 확인했다. 도구 사이에 설정값을 옮기거나 JSON 파일을 공유할 때도 색 공간과 해상도, 각 필드의 후처리 조건이 맞아야 같은 검출 결과를 얻는다.


다만 화면 입력 보정 뒤에도 원형 범위가 그대로 전달되는지와 설정 파일 복원 여부는 실제 실행 단계에서 추가로 확인해야 한다. 다음에는 대표 정지 이미지와 설정 파일을 한 쌍으로 묶어 보관하면서 입력 조건이 바뀔 때의 영향을 비교해 보려 한다. 이어지는 글에서는 `ObjectDetectionLab`의 작은 실습으로 검출 결과 목록이 평가 지표와 어떻게 연결되는지 다룬다.
