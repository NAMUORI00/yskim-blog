색상 도구에서는 입력 영상의 색상 범위를 조절하고 설정을 저장하는 과정을 다뤘다. 입력 배율과 색 공간, 설정 파일의 필드가 처리 결과에 영향을 주므로 Python과 다른 도구의 설정을 그 기준으로 비교했다.


## 구현과 확인 과정


HsvColorPicker와 mss_color_project_ 두 프로그램에서 색상 조건이 적용되는 경로를 나란히 읽어 봤다. HSV 슬라이더를 같은 숫자로 맞춰도 잘라내는 영역, 색 채널 순서, 후처리 단계가 다르면 마스크 결과가 달라질 수 있어서, 각 경로를 따로 추적할 이유가 있었다.


HSV, 마스크, 팽창의 기본 원리는 앞선 개념 글에서 이어받는다. 여기서는 공개 Rust 저장소와 비공개 Python 저장소를 각각 하나의 구현으로 다뤘다. Python 프로그램의 색상 설정과 영상 처리 경로를 소스에서 추적했다.


## 캡처 영역과 입력 형식


[HsvColorPicker의 화면 캡처 처리](https://github.com/NAMUORI00/HsvColorPicker/blob/700b7fca32f5176c8dfd2db22eaeb44fe7135224/src/capture.rs)는 선택한 모니터의 이미지를 가져온 뒤 중앙의 최대 320×320 정사각형을 RGB로 복사한다. 모니터 해상도가 그보다 작으면 가능한 크기로 줄인다. 화면에 표시되는 전체 모니터 이미지와 실제 검출에 쓰이는 중앙 영역은 크기가 다르다.


[mss_color_project_의 Capture](https://github.com/NAMUORI00/mss_color_project_/blob/2a540ad0b42deddaae394f42a5ae3acd82447e52/modules/capture.py)는 화면 크기로 기본 중앙 위치를 계산하고 지정한 폭과 높이의 영역을 MSS로 읽는다.


MSS의 반환 버퍼는 BGRA 순서다. RGB를 기대하는 함수에 그대로 넣으면 빨강과 파랑 채널이 뒤바뀔 수 있으므로, 이미지 처리 함수가 채널을 어떤 순서로 읽는지도 함께 확인했다.


Rust 도구에는 정지 화면을 다시 처리하는 경로도 있었다. 움직이는 화면을 보며 슬라이더를 바꾸면 장면 변화와 설정 효과가 섞이는데, 같은 이미지를 고정해 두면 설정 변경의 영향만 분리해서 볼 수 있다. 조명, 배율, 해상도 조건을 기록해 두는 이유도 같은 입력 조건에서 결과를 비교하기 위해서다.


## 색 범위 검사와 UI 입력 규칙


[Rust의 마스크 함수](https://github.com/NAMUORI00/HsvColorPicker/blob/700b7fca32f5176c8dfd2db22eaeb44fe7135224/src/detection/mask.rs)는 색상 하한이 상한보다 큰 경우를 원을 가로지르는 범위로 처리한다. 예를 들어 170~10이면 빨강 근처 양쪽 끝을 포함할 수 있다.


그런데 [색상 범위 설정 검사](https://github.com/NAMUORI00/HsvColorPicker/blob/700b7fca32f5176c8dfd2db22eaeb44fe7135224/src/settings.rs)의 clamp_min_max는 하한이 상한보다 크면 하한을 상한으로 바꾼다.


[앱의 설정 적용 함수](https://github.com/NAMUORI00/HsvColorPicker/blob/700b7fca32f5176c8dfd2db22eaeb44fe7135224/src/app.rs)는 이 보정을 먼저 호출한다. 검출 함수 자체에는 원형 범위 처리가 있지만, 일반 UI 적용 경로에서는 clamp_min_max가 먼저 실행되므로 원형 범위가 그대로 검출 함수까지 전달되는지는 확인이 더 필요했다.

그림 1. HsvColorPicker의 입력, 적용, 저장 경로. 출처: 화면 입력 적용 처리와 색상 범위 설정 검사를 바탕으로 직접 구성. 범위 검사 함수와 UI 보정은 서로 다른 단계다.


색상 설정은 프로그램을 실행한 폴더의 파일에서 읽는다. 읽기나 JSON 해석이 실패하면 기본값으로 돌아간다. 기본값이 넓은 색 범위를 포함하므로, 설정 복원에 실패해도 프로그램이 정상적으로 열린 것처럼 보일 수 있다. 복원 성공 여부와 실제 사용 경로는 실행에서 확인할 부분으로 남았다.


## 색상 검사 이후의 후처리


Rust의 [Detector](https://github.com/NAMUORI00/HsvColorPicker/blob/700b7fca32f5176c8dfd2db22eaeb44fe7135224/src/detection/mod.rs)는 RGB → HSV → 마스크 → 3×3 팽창 두 번 → 윤곽과 면적 조건 순서다.


반환되는 mask는 이미 팽창을 거친 결과다. 원래 색 범위에 들어간 픽셀만 보려면 이 반환값은 팽창 전 마스크와 구분해서 다뤄야 한다.


Python 뷰어가 호출하는 [process_frame](https://github.com/NAMUORI00/mss_color_project_/blob/2a540ad0b42deddaae394f42a5ae3acd82447e52/modules/image_processor.py)은 현재 배율에 따라 이미지를 줄인 뒤 HSV 마스크를 만들고 팽창을 다섯 번 적용한다. 이어 연결 성분을 구하고 픽셀 수와 종횡비로 후보를 거른다. 후보 유무에 따라 다음 처리의 배율도 조정한다.


이런 차이 때문에 두 프로그램에서 같은 H, S, V 숫자를 입력해도 출력 박스가 달라질 수 있다. 예를 들어 원본에서 10×10인 표식이 가로와 세로 절반으로 줄면 대략 5×5 영역이 되고, 여기에 경계 보간과 팽창의 영향이 더해진다. 최소 면적 수치만 복사해서는 같은 기준이라고 보기 어렵다. 입력 배율이 결과에 미치는 영향을 설명하기 위한 크기 계산 예제다.


## 색상 설정의 JSON 구조


[Python 뷰어](https://github.com/NAMUORI00/mss_color_project_/blob/2a540ad0b42deddaae394f42a5ae3acd82447e52/modules/custom_image_processor_viewer.py)에는 일반 설정 저장과 프리셋 저장이 별도로 존재한다.


일반 설정은 lower_color, upper_color 같은 최상위 키를 쓰고, 프리셋은 hsv.lower, hsv.upper처럼 묶어 저장한다. 두 로더도 다른 함수를 사용한다.

그림 2. Python 도구의 두 저장 형식과 복원 검토 지점. 출처: save_settings, save_preset, load_settings, _apply_settings를 바탕으로 직접 구성. JSON 파일을 주고받을 때는 필드 구조와 값의 의미도 맞춰야 한다.


복원이 제대로 되었는지 확인하려면 저장 메시지만으로는 부족하다. 같은 파일을 다시 읽은 뒤 처리기의 실제 범위, 화면 입력 값, 고정 이미지의 마스크를 서로 대조하는 과정이 남아 있다. 형식을 통합한다면 버전, 캡처 영역, 배율, 후처리 조건을 함께 기록해 두면 이후 비교가 수월해진다.


두 저장소를 읽으며 색상 범위와 함께 캡처 영역, 채널 순서, 후처리가 결과에 관여하는 과정을 정리했다. 다음 글에서는 ObjectDetectionLab의 작은 실습을 통해 검출 목록과 평가 지표의 연결을 살펴본다.


## 작업을 정리하며


색상 값은 숫자만 옮기기보다 색 공간과 범위를 함께 옮겨야 한다. 설정 파일을 공유할 때도 해상도와 필드 의미가 맞아야 같은 효과를 기대할 수 있다. 다음에는 대표 이미지와 설정을 함께 보관해 입력 조건이 바뀐 영향을 비교하려 한다.
