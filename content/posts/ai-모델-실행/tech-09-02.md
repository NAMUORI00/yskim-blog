이 글은 앞선 글들에서 다룬 학습, 추론, 스펙트로그램, 파일 처리 흐름에 이어지는 내용이다. 이미 만들어진 모델 가중치로 음원을 분리하는 웹 화면을 띄우는 일과 가중치를 직접 학습하는 일은 준비할 데이터와 실행 환경부터 다르다. 학습 코드가 요구하는 입력 데이터 구조와 Docker 컨테이너에서 연결해야 하는 파일 경로를 구분해 보기 위해 두 저장소를 나란히 확인했다.


학습과 추론 코드는 `NAMUORI00/Music-Source-Separation-Training` 저장소의 `c941d0a` 커밋을 기준으로 확인했다. 컨테이너 실행 환경은 설정 파일을 묶은 `NAMUORI00/MsstDocker` 저장소의 `70733f0` 커밋과 비교했다. 앞선 학습 저장소는 ZFTurbo의 공개 프로젝트를 복제한 포크(fork)이므로, 아래 내용은 직접 새로 작성한 코드가 아니라 기존 구현을 분석한 기록이다.


## 혼합음과 개별 음원의 학습 구성


먼저 학습 저장소에서 모델에 넣을 입력 음원과 정답 음원을 어떻게 짝지어 준비하는지 본다. 완성된 모델로 음원을 분리하는 추론 단계에서는 보컬과 반주가 섞인 곡 하나만 입력하면 되지만, 가중치를 맞추는 학습 단계에서는 분리 결과를 정답과 비교해야 한다. 예를 들어 어느 한 시점의 보컬 진폭 값이 `0.2`이고 반주 값이 `0.3`이라면 두 소리를 더한 혼합음 값은 `0.5`가 된다. 모델에는 `0.5`에 해당하는 혼합 신호를 넣고, 모델이 예측한 보컬 값을 정답인 `0.2`와 비교해 오차를 줄인다. 실제 오디오 입력은 시간에 따라 이어지는 긴 파형이므로 시점 하나의 숫자만으로 두 소리를 구별할 수는 없다. 다만 이 예에서 보듯 모델을 학습하려면 입력할 혼합음과 정답이 될 개별 음원이 항상 한 쌍으로 준비되어야 한다.


이 데이터 쌍은 [학습용 혼합음 구성](https://github.com/NAMUORI00/Music-Source-Separation-Training/blob/c941d0a7f260d9860a5af0e8e40f0b208d458036/dataset.py)의 `__getitem__` 메서드가 만든다. 이 메서드는 보컬, 드럼, 반주처럼 트랙별로 나뉜 개별 음원인 **스템**(stem)을 먼저 불러온 뒤 `res.sum(0)`으로 더해 입력용 혼합음을 만든다. 설정에 따라 각 스템의 음량을 바꾸거나 합쳐진 혼합음에 오디오 압축처럼 소리를 변형하는 데이터 증강(augmentation)을 적용하기도 한다. 특정 악기 하나만 분리하도록 학습할 때는 전체 스템 가운데 목표 스템만 골라 반환한다.


이렇게 만든 데이터 쌍은 [모델 학습 처리](https://github.com/NAMUORI00/Music-Source-Separation-Training/blob/c941d0a7f260d9860a5af0e8e40f0b208d458036/train.py) 코드로 넘어간다. 학습 코드는 혼합음을 `x`, 정답 스템을 `y`로 받아 예측 오차인 손실(loss)을 계산하는데, 모델 계열에 따라 손실을 구하는 위치가 다르다. 일반 경로에서는 `model(x)`로 예측 파형을 먼저 얻은 뒤 학습 반복문에서 정답 `y`와 비교해 오차를 구하고 가중치를 갱신한다. 반면 RoFormer 계열 분기에서는 `model(x, y)`처럼 입력과 정답을 함께 모델에 넘기고, 모델 내부에서 손실 값까지 계산해 반환한다.

## 학습 기록과 가중치 파일의 구성


앞 절에서 계산한 손실은 학습 반복문에서 가중치를 갱신하고 진행 기록을 남기는 데 쓰인다. 학습 반복문은 GPU 메모리 한계를 보완하려고 여러 배치의 기울기를 모았다가 한 번에 반영하는 **기울기 누적**(gradient accumulation)을 사용한다. 또한 연산 정밀도를 섞어 계산 부담을 줄이는 혼합 정밀도(mixed precision) 처리도 함께 적용한다. 코드는 매 배치에서 구한 손실을 누적 단계 수로 나누어 역전파(backpropagation)로 가중치별 오차 영향을 계산한다. 그 뒤 지정된 반복 횟수에 도달했거나 마지막 배치일 때만 가중치 갱신 도구인 옵티마이저(optimizer)가 가중치를 바꾼다. 데이터를 처리한 배치 횟수와 실제 가중치 갱신 횟수가 일치하지 않으므로, 학습 기록의 스텝(step) 수를 읽을 때도 누적 주기를 함께 고려해야 한다.


화면에 출력되는 손실 숫자의 배율도 기록 위치마다 다르다. 진행 막대(progress bar)와 중간 로그에 찍히는 손실 값에는 원래 값에 `100`을 곱해 보여 준다. 반면 전체 데이터를 한 바퀴 학습한 단위인 한 에포크(epoch)가 끝날 때 요약하는 `Training loss`에는 `100`을 곱하지 않는다. 같은 에포크 안에서 나온 기록이라도 어느 위치의 로그인지에 따라 숫자 스케일이 100배 차이 나므로, 손실 추이를 비교할 때는 출력 위치부터 확인해야 한다.


검증 함수는 지정된 평가 지표를 계산해 이전 최고 기록보다 좋아질 때마다 가중치를 파일로 남긴다. 이때 `save_weights` 함수가 저장하는 대상은 일반 경로에서는 모델 파라미터 사전인 `state_dict`다. 모델 전체 대신 일부 추가 층만 학습하는 LoRA 경로에서는 해당 어댑터(adapter) 상태만 파일에 담는다. 이 파일 하나에 옵티마이저나 학습률 스케줄러(scheduler)의 모든 상태가 함께 들어 있다고 보기는 어렵다. 따라서 추론에 쓸 가중치를 불러오는 일과 중단된 학습을 직전 상태에서 그대로 이어 가는 일은 필요한 파일 조건을 나누어 다뤄야 한다. 또한 코드 안에 평가와 저장 로직이 있더라도, 학습 완료나 목표 품질 달성 여부는 데이터 분할 방식, 설정 파일, 실행 로그, 평가 결과를 함께 봐야 판단할 수 있다.

## 긴 곡의 분할 추론과 파형 결합


학습 단계에서 저장한 가중치 파일은 [학습된 모델로 음원을 분리하는 처리](https://github.com/NAMUORI00/Music-Source-Separation-Training/blob/c941d0a7f260d9860a5af0e8e40f0b208d458036/inference.py)에서 불러와 새 곡을 분리하는 데 사용한다. 이 코드는 설정 파일을 바탕으로 빈 모델 구조를 먼저 생성하고, 저장된 가중치 파일 위치인 체크포인트(checkpoint) 경로가 지정됐을 때만 가중치를 적재한다. 체크포인트 경로 없이 모델 객체만 만들면 초기화된 가중치 상태로 남기 때문에, 모델 생성과 학습된 가중치 로딩은 별개 단계로 나뉘어 있다.


오디오 파일을 읽은 뒤에는 설정된 초당 소리 측정 횟수인 샘플링 주파수(sampling rate)와 채널 조건에 맞춰 파형을 변환한다. 이후 실제 음원을 분리하는 공통 경로는 [음원 분할과 결합 처리의 demix](https://github.com/NAMUORI00/Music-Source-Separation-Training/blob/c941d0a7f260d9860a5af0e8e40f0b208d458036/utils.py) 함수에 모여 있다. 곡 전체의 긴 파형을 한 번에 모델에 넣기 어렵기 때문에, `demix`는 긴 파형을 서로 겹치는 여러 조각(chunk)으로 나누어 모델에 넣는다. 두 조각이 겹치는 시점에서 각 조각의 예측이 `0.2`와 `0.4`이고, 가중치가 모두 `0.5`인 경우를 가정한다. 합쳐진 결과값은 각 예측값에 가중치를 곱해 더한 뒤 가중치 합으로 나눈 `(0.2×0.5＋0.4×0.5)÷(0.5＋0.5)＝0.3`이 된다. 이처럼 `demix`는 각 조각의 예측 결과를 원래 시간 위치에 더하고 겹친 구간에 부여된 가중치의 합으로 나누어 파형을 복원한다. 조각을 겹치지 않고 바로 이어 붙이는 방식보다 조각 사이의 경계 구간을 완만하게 이어 줄 수 있다. 실제 `demix` 코드는 여기에 모델 종류별 분기와 여백 채우기(padding), 구간 가장자리에 가중치를 다르게 주는 경계 창(window) 처리까지 적용한다. 물론 구간을 겹쳐 합친다는 구조만으로 분리 결과에 잡음이나 경계 왜곡이 없다고 단정할 수는 없다.

추론이 끝날 때 출력되는 폴더 전체 처리 시간에는 순수 모델 연산뿐만 아니라 디스크에서 파일을 읽고 결과를 저장하는 입출력(I/O) 시간도 포함된다. 반면 모델을 메모리에 올리는 로딩 시간은 별도로 표시된다. 따라서 GPU 추론 속도를 비교할 때는 전체 처리 시간에 섞여 있는 파일 입출력 시간과 실제 모델 실행 시간을 구분해서 읽어야 한다.


## Docker 실행 환경의 구성


앞에서 본 학습 저장소와 달리, `MsstDocker` 저장소는 모델을 직접 학습하는 대신 음원 분리 웹 화면을 컨테이너로 띄우는 환경을 다룬다. `MsstDocker`의 [Dockerfile](https://github.com/NAMUORI00/MsstDocker/blob/70733f0285178fbb39fae0d8c7f925f174d322d8/Dockerfile)은 CUDA 12.1.1과 Ubuntu 22.04 기반 이미지를 사용한다. 이 이미지 위에 Python 3.10, FFmpeg, Python 패키지를 설치하고 `MSST-WebUI`를 복사한다. 즉, 이 컨테이너가 실행하는 대상은 앞에서 확인한 학습용 포크가 아니라 웹 인터페이스다.


두 저장소의 관계를 파악할 때는 저장소 이름보다 Git이 실제로 참조하는 주소를 확인하는 편이 정확하다. `MsstDocker`의 [외부 코드 연결 설정](https://github.com/NAMUORI00/MsstDocker/blob/70733f0285178fbb39fae0d8c7f925f174d322d8/.gitmodules)은 `SUC-DriverOld/MSST-WebUI` 저장소를 가리킨다. 상위 저장소의 Git 트리에는 그 하위 저장소의 `8c080404` 커밋이 기록되어 있다. [Git 문서](https://git-scm.com/docs/git-submodule)에서 설명하듯 **서브모듈**(submodule)은 상위 저장소가 하위 저장소의 특정 커밋을 고정해 참조하는 방식이다. 따라서 컨테이너에서 실제로 실행되는 소스 코드를 확인하려면 상위 폴더 목록과 서브모듈 구성을 함께 봐야 한다.

그림 4. MsstDocker가 웹 실행 코드와 의존성을 묶고 호스트의 모델과 출력 폴더를 연결하는 구조. 출처: Dockerfile, 컨테이너 실행 설정, 외부 코드 연결 설정을 바탕으로 직접 구성.


컨테이너 실행 시 파일이 저장되는 위치는 [Compose 설정](https://github.com/NAMUORI00/MsstDocker/blob/70733f0285178fbb39fae0d8c7f925f174d322d8/docker-compose.yml)에서 결정된다. 이 설정은 본체 컴퓨터인 호스트의 `models` 폴더와 `output` 폴더를 컨테이너 내부에 직접 연결한다. 반면 설정 파일이 들어가는 `configs`와 데이터 폴더인 `data`에는 같은 연결이 없다. 호스트 디렉터리를 컨테이너에 직접 연결하는 [Docker의 bind mount 설명](https://docs.docker.com/engine/storage/bind-mounts/)을 이 구성에 대입해 보면 저장 범위의 차이가 드러난다. 모델 가중치와 분리 결과 파일은 호스트 폴더에 그대로 남지만, 컨테이너 안에서 바꾼 설정이나 `data` 경로의 파일은 호스트와 따로 관리된다.


또한 Dockerfile에서 기반 CUDA 이미지 태그는 고정되어 있지만, `torch`를 설치하는 명령 줄에는 정확한 패키지 버전이 적혀 있지 않다. 실행 환경을 똑같이 재현하려면 서브모듈 커밋(`8c080404`), 실제 설치된 패키지 버전, `models` 폴더에 넣을 가중치 파일, 호스트 GPU 환경을 함께 맞춰야 한다.


## 결론


두 저장소의 코드와 설정을 따라가며 음원 분리 모델을 학습하고 추론하는 경로와 웹 실행 환경을 묶는 컨테이너 구성을 구분해 확인했다. 학습과 추론 코드는 혼합음 합성부터 조각 분할 결합까지 모델 연산을 다루고, 컨테이너 설정은 웹 인터페이스 서브모듈에 호스트의 모델과 출력 폴더를 연결한다. 이번 기록은 코드와 설정 파일을 기준으로 구조를 파악한 단계이며, 분리 품질이나 처리 속도는 아직 측정하지 않았다. 서브모듈 커밋과 패키지 버전, 가중치 파일을 먼저 고정한 뒤 이미지를 빌드해 웹 화면을 띄우고 실제 음원을 분리하는 실행 검증을 이어서 진행할 계획이다. 다음 글에서는 입력 음성의 특징을 추출해 다른 목소리로 바꾸는 Applio의 음성 변환과 검색 색인 구조를 다룬다.
