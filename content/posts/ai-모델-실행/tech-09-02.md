음원 분리 기능을 다루며 모델 학습과 서비스 추론의 준비 조건을 나누어 정리했다. 학습 코드가 요구하는 데이터와 Docker 환경에서 모델을 실행할 때 필요한 파일이 달라, 하위 저장소, 가중치, 실행 환경을 연결해 보는 것이 이번 글의 과제다.


## 구현과 확인 과정


분리 결과를 듣는 웹 화면을 띄우는 것과 분리 모델의 가중치를 학습하는 것은 준비할 자료부터 다르다. 앞 글의 파일 처리 흐름에 이어, Music-Source-Separation-Training의 학습 입력과 MsstDocker의 실행 환경을 따로 살펴봤다.


이 글은 앞선 글들에서 다룬 학습, 추론, 스펙트로그램, 파일 처리 흐름에 이어지는 내용이다. 살핀 저장소는 NAMUORI00/Music-Source-Separation-Training의 c941d0a와 NAMUORI00/MsstDocker의 70733f0 커밋이다.


전자는 ZFTurbo의 학습 프로젝트를 가져온 포크다. 아래 학습 기능을 개인이 새로 구현한 기여로 세지는 않았다.


## 혼합음과 개별 음원의 학습 구성


학습에서는 분리 결과를 비교할 대상이 필요하다. [학습용 혼합음 구성](https://github.com/NAMUORI00/Music-Source-Separation-Training/blob/c941d0a7f260d9860a5af0e8e40f0b208d458036/dataset.py)의 __getitem__은 개별 음원인 stem들을 준비한 뒤 res.sum(0)으로 혼합음을 만든다.


설정에 따라 각 stem의 크기를 바꾸거나 혼합음에 압축 증강을 적용하고, 특정 악기만 학습할 때는 목표 stem을 골라 반환한다.


보컬과 반주를 분리하는 작은 예를 생각해 봤다. 같은 시각의 보컬 값이 0.2, 반주 값이 0.3이라면 혼합 값은 0.5다. 모델에는 0.5에 해당하는 혼합 신호를 넣고, 출력한 보컬을 0.2와 비교한다. 실제 입력은 긴 파형이고 값 하나만으로 두 소리를 구별할 수는 없다. 이 예는 정답 음원과 혼합음이 왜 한 쌍이어야 하는지 보여 주기 위한 것이다.


[모델 학습 처리](https://github.com/NAMUORI00/Music-Source-Separation-Training/blob/c941d0a7f260d9860a5af0e8e40f0b208d458036/train.py)는 혼합음을 x, 정답 stem을 y로 받아 손실을 계산한다.


일반 경로에서는 model(x)의 예측과 y를 비교하고, RoFormer 계열 분기에서는 model(x, y)가 손실까지 반환한다. 같은 학습 반복문을 사용해도 손실이 계산되는 위치는 모델에 따라 달랐다.

## 가중치 파일과 학습 기록


학습 코드에는 기울기 누적과 혼합 정밀도 처리가 들어 있다. 손실을 누적 단계 수로 나누어 역전파하고, 정해진 반복 수 또는 마지막 배치에서 optimizer를 갱신한다. 기울기 누적이 적용되어 있으므로 배치 처리 횟수와 가중치 갱신 횟수가 일치하지 않고, 학습 기록의 step 수를 읽을 때 이 차이가 반영된다.


표시되는 숫자의 단위도 확인했다. 진행 막대와 일부 로그의 loss에는 100을 곱하지만, epoch 끝의 Training loss에는 그 배율을 적용하지 않는다. 같은 epoch 안에서도 로그 위치에 따라 숫자 스케일이 달라서, 손실 비교 시에는 어느 로그의 값인지를 먼저 확인하게 되는 구조였다.


검증 함수는 지정된 지표를 계산하고, 이전 최고값보다 좋아지면 가중치를 저장한다. 평가를 수행할 수 있는 구현이 갖춰져 있는 셈이다. 다만 학습 완료 여부나 특정 품질 달성 여부는 데이터 분할, 설정, 로그와 평가 결과까지 함께 있어야 확인 가능한 부분이었다.


save_weights가 저장하는 것은 일반 경로에서는 모델의 state_dict, LoRA 경로에서는 해당 어댑터 상태다. 이 파일 하나에 optimizer와 scheduler의 모든 상태가 함께 들어 있다고 보기는 어렵다. 추론에 가중치를 불러오는 일과 중단 직전의 학습 상태를 그대로 복구하는 일도 나누어 생각하게 됐다.


## 긴 곡을 나누었다가 다시 붙이는 추론


[학습된 모델로 음원을 분리하는 처리](https://github.com/NAMUORI00/Music-Source-Separation-Training/blob/c941d0a7f260d9860a5af0e8e40f0b208d458036/inference.py)는 설정에서 모델을 만들고, 체크포인트 경로가 지정됐을 때 가중치를 불러온다. 체크포인트 경로 없이 모델 객체만 생성하면 초기 가중치 상태로 남으므로, 모델 생성과 학습된 가중치 로딩은 별개 단계였다.


파일을 읽은 뒤에는 설정된 샘플링 주파수와 채널 조건에 맞춰 처리한다. 분리의 공통 경로는 [음원 분할과 결합 처리의 demix](https://github.com/NAMUORI00/Music-Source-Separation-Training/blob/c941d0a7f260d9860a5af0e8e40f0b208d458036/utils.py)에 모여 있다.


긴 파형을 겹치는 조각으로 나눠 모델에 넣고, 결과를 원래 위치에 더한 뒤 겹친 가중치의 합으로 나눈다. 조각을 단순히 이어 붙이는 방식보다 경계 구간을 함께 다룰 수 있는 구조다.


설명을 위해 한 시각에 두 조각의 예측이 0.2와 0.4이고 가중치가 각각 0.5라고 놓아 봤다. 합친 값은 (0.2×0.5＋0.4×0.5)÷(0.5＋0.5)＝0.3이다. 실제 코드는 모델별 분기, 패딩, 경계 창까지 처리한다. 겹침을 사용한다는 사실만으로 잡음이나 경계 왜곡이 없다고 단정하지는 않았다.


끝에 출력되는 폴더 처리 시간에는 파일 읽기와 저장도 포함되어 있었다. 모델 로딩 시간은 별도로 표시된다. GPU 속도를 비교할 때는 전체 처리 시간에 포함된 I/O와 모델 실행 시간을 구분해서 읽을 지점이 있었다.


## Docker 실행 환경의 구성


MsstDocker의 [Dockerfile](https://github.com/NAMUORI00/MsstDocker/blob/70733f0285178fbb39fae0d8c7f925f174d322d8/Dockerfile)은 CUDA 12.1.1, Ubuntu 22.04 기반 이미지에 Python 3.10, FFmpeg와 Python 패키지를 설치하고 MSST-WebUI를 복사한다. 실행 대상은 음원 분리 웹 화면이다. 위에서 읽은 학습 포크를 자동으로 실행하는 설정이라고 연결하지는 않았다.


두 저장소의 관계를 확인할 때는 이름보다 실제 참조가 도움이 됐다. [외부 코드 연결 설정](https://github.com/NAMUORI00/MsstDocker/blob/70733f0285178fbb39fae0d8c7f925f174d322d8/.gitmodules)은 SUC-DriverOld/MSST-WebUI를 가리키고, Git 트리에는 그 하위 저장소의 8c080404 커밋이 기록되어 있다.


[Git 문서](https://git-scm.com/docs/git-submodule)에서 설명하는 것처럼 상위 저장소는 하위 저장소의 특정 커밋을 참조한다. 소스 위치를 판단하려면 폴더 목록과 서브모듈 구성을 함께 확인해야 했다.

그림 2. MsstDocker가 웹 실행 코드와 의존성을 묶고 모델, 출력 폴더를 연결하는 구조. 출처: Dockerfile, 컨테이너 실행 설정, 외부 코드 연결 설정을 바탕으로 직접 구성. 학습 코드와 실행 환경의 구성 관계를 나타낸 그림이다.


[Compose 설정](https://github.com/NAMUORI00/MsstDocker/blob/70733f0285178fbb39fae0d8c7f925f174d322d8/docker-compose.yml)은 호스트의 models와 output을 컨테이너에 연결한다.


configs와 data에는 같은 연결이 없다. [Docker의 bind mount 설명](https://docs.docker.com/engine/storage/bind-mounts/)을 이 구성에 적용하면, 모델, 결과 파일의 보관 경로와 컨테이너 안에서 바꾼 설정의 보관 경로가 다르다는 점이 드러난다.


CUDA 이미지 태그는 고정되어 있지만 torch 설치 줄에는 정확한 패키지 버전이 명시되어 있지 않았다. 재실행 조건을 정리하려면 하위 저장소 커밋, 설치된 패키지 버전, 모델 파일, 호스트 GPU 환경을 함께 확인할 필요가 있다. 이미지 빌드, 웹 화면 구동, 가중치를 불러 실제 음원을 분리하는 단계는 아직 실행 검증이 남아 있다.


## 음성 변환 글과의 연결


두 저장소를 통해 정답 음원으로 가중치를 바꾸는 학습, 주어진 가중치로 소리를 나누는 추론, 실행 환경을 묶는 컨테이너의 역할을 정리했다. 이번 기록은 코드 검토까지이며 품질이나 속도는 측정하지 않았다. 다음 Applio 글에서는 입력 음성의 특징을 다른 목소리로 옮기는 처리를 살펴본다.


## 작업을 정리하며


학습과 추론의 환경을 각각 재현 가능한 단위로 남기는 것이 중요하다. 하위 저장소 커밋과 패키지 버전, 가중치 파일을 함께 고정하면 화면 실행과 실제 분리 성공을 단계별로 확인할 수 있다. 품질과 속도 비교는 그 조건을 맞춘 뒤 진행하려 한다.
