앞선 글에서는 이미 완성된 곡에서 보컬과 반주를 분리하는 음원 분리 모델을 다뤘다. 이와 달리 녹음된 음성의 발음과 억양은 유지하면서 목소리 특색만 다른 화자로 바꾸는 작업을 **음성 변환**(Voice Conversion)이라 한다.


오픈소스 음성 변환 도구인 Applio를 실행할 때는 입력 음성과 학습된 모델 파일인 **체크포인트**(checkpoint)를 기본으로 넣는다. 여기에 검색 색인(index) 파일과 `index_rate`, `protect` 같은 설정값도 함께 넘긴다. 각 파일과 설정이 어느 단계에 개입하는지 파악하기 위해 [NAMUORI00/Applio](https://github.com/NAMUORI00/Applio/blob/70f5f8be1fc247c2fee2bd5a83254f71fdebd55c/rvc/infer/infer.py) 저장소(`70f5f8b` 커밋)에서 모델을 실행하는 추론 코드를 분석했다. 이 저장소는 원본 Applio를 복제한 포크로, 기본 RVC(Retrieval-based Voice Conversion) 추론 구조를 그대로 담고 있다.


## 입력 음성과 모델 체크포인트의 역할


추론 코드의 데이터 흐름은 가장 기본 입력인 음성 파일과 모델 체크포인트를 받아 역할을 나누는 것에서 시작한다. 음성 변환의 진입점인 [VoiceConverter.convert_audio](https://github.com/NAMUORI00/Applio/blob/70f5f8be1fc247c2fee2bd5a83254f71fdebd55c/rvc/infer/infer.py) 함수는 변환할 입력 음성 경로와 목표 화자의 모델 체크포인트 경로를 인자로 받는다.


Applio는 글자를 음성으로 읽는 TTS(Text-to-Speech) 기능도 제공하지만, 글자가 음성 변환 모델로 곧바로 들어가지는 않는다. [Applio 공식 문서](https://docs.applio.org/)에서도 음성 변환과 TTS를 별도 항목으로 구분한다. 실제 [음성 변환 실행 연결 코드(](https://github.com/NAMUORI00/Applio/blob/70f5f8be1fc247c2fee2bd5a83254f71fdebd55c/core.py)[`core.py`](https://github.com/NAMUORI00/Applio/blob/70f5f8be1fc247c2fee2bd5a83254f71fdebd55c/core.py)[)](https://github.com/NAMUORI00/Applio/blob/70f5f8be1fc247c2fee2bd5a83254f71fdebd55c/core.py)를 봐도 TTS 경로는 글자를 먼저 음성 파일로 합성한 뒤 그 파일 경로를 `convert_audio`에 넘긴다. 녹음한 발화든 TTS가 만든 음성이든 변환 파이프라인의 출발점은 언제나 오디오 파일이다.


`convert_audio`는 1초의 소리를 16,000번 나누어 기록하는 16 kHz **샘플링 주파수**로 입력 오디오를 읽어들인다. 이어서 음성에서 발화 특징을 뽑아내는 특징 추출 모델을 준비해 변환 파이프라인으로 전달한다. 화자가 말한 내용과 시간에 따른 발음, 억양 정보는 모두 이 입력 음성에서 나온다.


반면 목표 화자의 목소리를 합성하는 조건은 모델 체크포인트에서 가져온다. 체크포인트 파일 안에는 학습된 신경망 가중치와 출력 오디오의 샘플링 주파수, 목소리 높낮이인 기본 주파수(F0) 사용 여부, 모델 버전 같은 설정값이 함께 들어 있다. 따라서 입력 파형을 읽는 주파수(16 kHz)와 모델이 최종 파형을 내보내는 출력 주파수가 서로 다를 수 있다. 후처리를 붙일 때 입출력 오디오의 샘플링 주파수를 같은 값으로 가정해서는 안 된다.

## FAISS 색인 검색과 특징 벡터 혼합


입력 음성과 체크포인트를 준비한 뒤에는 목표 화자의 음색을 보완하는 검색 색인이 개입한다. 음성에서 뽑아낸 발음과 음색 정보를 숫자 묶음으로 나타낸 값을 **특징 벡터**(feature vector)라고 한다. 입력 음성의 특징 벡터만으로도 목소리를 합성할 수 있지만, 학습 데이터와 발음 조건이 다르면 목표 화자의 음색이 옅어질 수 있다. RVC 파이프라인은 이를 보완하려고 목표 화자의 학습 특징들을 빠르게 찾아볼 수 있게 모아 둔 **검색 색인**(FAISS index)을 활용한다.


[변환 파이프라인의 voice_conversion 함수](https://github.com/NAMUORI00/Applio/blob/70f5f8be1fc247c2fee2bd5a83254f71fdebd55c/rvc/infer/pipeline.py)는 입력 음성을 특징 벡터로 변환한 뒤, 사용할 색인이 준비되어 있으면 FAISS 검색을 수행한다. 내부의 `_retrieve_speaker_embeddings` 메서드는 입력 음성의 각 시간 프레임 특징마다 색인에서 가장 가까운 이웃 벡터 8개를 찾는다. 그다음 검색에서 반환된 `score` 값으로 가중치를 계산해 이웃 벡터 8개를 하나로 합친다.


합쳐진 색인 특징은 원래 입력 음성의 특징과 `index_rate` 비율에 따라 섞인다. 예를 들어 원래 특징은 `h＝[1, 0]`이고 검색으로 합친 특징은 `v＝[0, 1]`이라 가정한다. 이때 `index_rate`를 `r＝0.25`로 설정하면 혼합된 특징은 `[0.75, 0.25]`가 되어 생성 모델로 넘어간다. 일반 수식으로 쓰면 최종 혼합 특징은 `r×v＋(1−r)×h`이며, `index_rate`가 커질수록 목표 화자의 색인 특징 비중이 높아진다. 다만 이 비율이 실제 청감이나 발음 보존 정도에 미치는 영향은 출력 음성을 직접 들어 봐야 판단할 수 있다.


![입력 특징 h와 FAISS 색인으로 이웃 8개를 검색해 가중 합 특징 v를 구하고 index_rate r로 r × v + (1 - r) × h를 계산하여 h=(1, 0), v=(0, 1), r=0.25일 때 (0.75, 0.25)가 되는 과정](/images/notion/tech-09-03/image-2.png)


그림 2. FAISS 색인에서 검색한 이웃 특징과 원래 입력 특징을 index_rate 비율로 혼합하는 경로와 계산 예(출처: `pipeline.py`의 _retrieve_speaker_embeddings를 바탕으로 직접 구성).


이웃 벡터의 가중치를 구할 때 쓰는 `score` 변수는 이름만 보고 값이 클수록 비슷한 코사인 유사도라고 단정할 수 없다. [FAISS 공식 문서](https://github.com/facebookresearch/faiss/wiki/MetricType-and-distances)에 따르면 L2 거리 기반 검색은 두 벡터 사이의 거리를 제곱한 제곱 유클리드 거리(squared Euclidean distance)를 반환한다. 두 벡터가 가까울수록 거리 값이 작아지므로, 코드는 `score`의 역수를 제곱해 가까운 이웃에 큰 가중치를 준다. 다만 역수의 제곱을 계산하는 부분에 분모가 0이 되는 상황을 피하는 보정이 직접 보이지 않았다. 색인에 입력과 정확히 같은 벡터가 들어오거나 전체 이웃 수가 8개보다 적은 색인을 만났을 때 어떻게 동작하는지는 별도로 확인해야 한다.


## 음정과 protect 설정의 작동 조건


특징 벡터를 검색하고 섞는 과정에는 `index_rate` 외에도 음정을 조절하는 `F0` 설정과 발음 손실을 줄이는 `protect` 설정이 함께 관여한다.


**F0**(Fundamental Frequency, 기본 주파수)는 성대가 진동하는 빠르기로, 시간에 따른 목소리의 높낮이를 나타낸다. 예를 들어 반음(semitone) 조절값인 `p`에 `p＝12`를 입력하면 주파수가 두 배가 되어 음정이 한 옥타브 올라간다. 파이프라인의 `get_f0` 메서드에서 일반 음정 변경 경로는 이처럼 기본 주파수에 `2^(p/12)`를 곱해 높낮이를 바꾼다. 다만 자동 음정 보정과 제안 음정 분기는 별도의 조건문으로 나뉘어 있어, 이 수식 하나를 모든 음정 옵션의 실행 결과로 일반화할 수는 없다.


함께 쓰이는 `protect`는 특징을 섞는 과정에서 원래 발음 특징을 보호할 구간의 반영 비율을 조정한다. 코드에서 F0를 사용하는 경로를 보면 `protect`가 `0.5`보다 작을 때만 추가 조정이 작동한다. 이 조건에서는 성대가 울리는 유성음과 성대가 울리지 않는 무성음 구간에 따라 검색을 거친 특징과 원래 입력 특징의 비중을 다시 조정한다. 코드 주석의 짧은 설명만 읽을 때보다 다차원 배열인 텐서를 실제로 어떻게 섞는지 수식과 조건문을 직접 대조해 보는 편이 작동 조건을 이해하는 데 도움이 됐다.

## 예외 처리 구조와 실행 확인 항목


입력 파일과 설정값이 결합되는 경로를 따라가 보면, 오류가 발생해도 호출자에게 드러나지 않고 넘어가는 예외 처리 구조가 두 군데 보인다.


첫째는 색인 파일을 읽는 단계로, 파이프라인은 색인 경로가 전달되었고 실제 파일이 존재하며 `index_rate`가 0보다 클 때만 색인 읽기를 시도한다. 그런데 파일을 읽다가 예외가 발생하면 색인을 빈 값인 `None`으로 두고 변환을 그대로 진행한다. 따라서 변환 결과 파일이 만들어졌다는 사실만으로 검색 색인이 정상적으로 반영됐다고 볼 수는 없다. 색인 없이 생성된 결과와 검색을 적용한 결과를 비교하려면 색인 로딩 성공 여부를 함께 기록해 두어야 한다.


둘째는 변환 함수와 실행 스크립트 사이의 오류 전달 방식이다. `convert_audio`는 내부에서 발생한 일부 오류를 잡아 로그에 출력한다. 그런데 `core.py`의 `run_infer_script`는 `convert_audio`를 호출한 뒤 곧바로 성공 문구와 예상 출력 경로를 반환한다. 내부에서 처리된 오류가 호출자에게 실패 값으로 전달되지 않기 때문에, 성공 문구가 표시되더라도 실제 출력 파일이 정상적으로 생성됐는지는 별도로 확인해야 한다.


![상단에는 FAISS 색인 읽기 중 예외 발생 시 None으로 설정해 색인 없이 변환을 계속하는 흐름이 있고 하단에는 convert_audio가 오류 로그만 기록한 뒤 run_infer_script가 성공을 반환해 출력 파일 생성을 별도로 확인해야 하는 흐름도](/images/notion/tech-09-03/image-4.png)


그림 4. 색인 읽기 예외 시 색인 없이 변환을 진행하는 경로와 내부 오류 발생 시에도 성공 문구가 반환되어 별도 확인이 필요한 구조.


## 결론


Applio의 추론 코드를 따라가며 입력 파일과 설정값이 음성 변환 파이프라인의 어느 단계에서 결합되는지 확인했다. 입력 음성은 변환할 발화 내용과 억양을 제공하고, 모델 체크포인트는 생성 모델의 가중치와 출력 조건을 정한다. 검색 색인은 목표 화자의 특징을 선택적으로 보태며, `index_rate`와 `F0`, `protect` 설정이 음정과 특징 혼합 비중을 조정한다. 다만 색인 읽기 예외와 변환 내부 오류가 성공 문구 뒤에 가려질 수 있어 실행 결과를 별도로 확인해야 한다.


이번 작업에서는 코드의 실행 경로와 수식을 먼저 분석했고, 실제 음성을 합성해 들어 보는 청취 평가는 아직 수행하지 않았다. 후속 실행에서는 모델 로딩 상태, 색인 사용 여부, 출력 파일 생성, 오디오 디코딩 정상 여부를 각각 점검할 계획이다. 같은 입력 음성과 체크포인트 조건에서 `index_rate`와 `protect` 값에 따른 출력 품질 차이도 직접 들어 보며 비교할 과제로 남겨 두었다. 다음 글에서는 텍스트와 오디오, OSC 이벤트가 전달되는 경로를 이어서 다룬다.
