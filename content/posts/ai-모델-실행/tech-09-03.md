음성 변환에 Applio를 활용할 때 필요한 입력, 모델, 검색 색인의 관계를 정리했다. 원본 Applio의 포크 코드를 기준으로 음성 특징이 검색 결과와 결합되고 합성으로 이어지는 경로를 따라갔다.


## 구현과 확인 과정


Applio의 음성 변환 코드를 읽으며 입력 음성, 모델 가중치, 검색 색인이 각각 어떤 역할을 하는지 정리했다. 앞 글에서 다룬 음원 분리와 달리, 여기서는 이미 녹음된 음성을 다른 화자의 목소리로 바꾸는 경로를 살펴봤다.


이번 글은 NAMUORI00/Applio의 70f5f8b 커밋을 기준으로 코드를 읽고 정리한 기록이다. 이 저장소는 Applio의 포크이며, 아래에서는 원본 Applio의 변환 구조를 따라 읽었다. 음성 합성과 음성 변환, 샘플링, 임베딩의 기초를 알고 있으면 각 입력의 역할을 구별하기 수월하다.


## 텍스트보다 먼저 음성이 들어오는 경로


[VoiceConverter.convert_audio](https://github.com/NAMUORI00/Applio/blob/70f5f8be1fc247c2fee2bd5a83254f71fdebd55c/rvc/infer/infer.py)는 입력 음성 경로와 변환 모델 경로를 받는다.


이 함수는 입력을 16 kHz 처리 경로로 읽고, 특징 추출 모델을 준비한 뒤 변환 파이프라인에 전달한다. 말한 내용과 시간에 따른 발음, 억양 정보는 이 입력 음성에서 출발한다.


변환 모델은 체크포인트의 설정과 가중치를 읽어 구성한다. 출력 샘플링 주파수, F0 사용 여부, 모델 버전 같은 조건도 여기에서 가져온다. 입력 파형을 읽는 주파수와 출력 모델의 주파수가 서로 다를 수 있으므로 같은 값으로 가정할 수 없다.


[Applio 공식 문서](https://docs.applio.org/)에서도 음성 변환과 TTS는 별도 항목으로 구분되어 있다.


확인한 포크의 [음성 변환 실행 연결](https://github.com/NAMUORI00/Applio/blob/70f5f8be1fc247c2fee2bd5a83254f71fdebd55c/core.py)에서도 TTS 경로는 먼저 텍스트를 음성 파일로 만드는 별도 처리를 호출한 뒤, 그 파일을 convert_audio의 입력으로 넘기고 있었다. 텍스트 입력은 TTS로 음성을 만든 뒤 변환 모델에 전달한다.

## 색인을 이용한 특징 검색


[음성 특징 변환과 검색 처리의 voice_conversion](https://github.com/NAMUORI00/Applio/blob/70f5f8be1fc247c2fee2bd5a83254f71fdebd55c/rvc/infer/pipeline.py)은 입력 음성을 특징 벡터로 바꾸는 함수다.


사용할 색인이 준비되어 있으면 그 벡터로 FAISS 검색을 수행한다. 검색 결과는 특징 벡터 형태로 반환된다.


_retrieve_speaker_embeddings는 각 입력 특징에 대해 이웃 8개를 찾고, 반환된 score로 가중치를 계산해 이웃 벡터를 합친다. 그 결과와 원래 특징을 index_rate 비율로 섞는다. 이때 r을 index_rate, h를 원래 특징, v를 검색으로 합친 특징이라고 쓰면 결과는 r×v＋(1−r)×h가 된다.


작은 숫자로 보면 더 분명하다. h＝[1, 0], v＝[0, 1], r＝0.25라면 혼합 특징은 [0.75, 0.25]다. 생성 모델에 전달할 특징을 섞는 비율을 계산한 예다. 실제 청감이나 발음 보존 정도는 출력 음성을 들어 봐야 확인할 수 있다.


![09-03-02.png](/images/notion/tech-09-03/image-2.png)


그림 2. 검색한 음성 특징과 입력 특징을 혼합하는 경로. 출처: 음성 특징 변환, 검색 처리의 _retrieve_speaker_embeddings를 바탕으로 직접 구성. index_rate는 특징 결합 비율을 조절하는 설정이다. 출력 음질과 화자 유사도는 별도 평가가 필요하다.


검색 score의 의미는 색인 설정에 따라 달라진다. [FAISS 문서](https://github.com/facebookresearch/faiss/wiki/MetricType-and-distances)에 따르면 L2 거리 검색은 제곱 유클리드 거리를 반환한다.


코드의 변수명이 score라는 이유만으로 코사인 유사도라고 부를 수는 없다. 또한 역수의 제곱을 쓰는 부분에 0을 피하는 보정이 직접 보이지 않았다. 정확히 같은 벡터가 들어오거나 이웃 수가 부족한 색인을 만났을 때 어떤 일이 일어나는지는 별도로 확인이 필요하다.


## 설정별 실행 조건


색인 경로가 있고 실제 파일이 존재하며 index_rate가 0보다 클 때만 읽기를 시도한다. 읽다가 예외가 나면 색인을 None으로 두고 변환을 계속 진행한다. 따라서 변환 결과가 만들어졌다는 사실만으로 검색 특징이 사용됐다고 볼 수는 없다. 색인 없이 생성된 결과와 검색을 적용한 결과를 비교하려면 색인 로딩 상태를 함께 기록해 둘 필요가 있다.


F0는 시간에 따른 기본 주파수다. get_f0의 일반 음정 변경 경로는 반음 수 p에 대해 2^(p/12)를 곱한다. p＝12라면 주파수가 두 배가 된다. 다만 자동 음정 보정과 제안 음정 분기는 별도의 조건문이므로, 이 계산을 모든 옵션의 실행 결과로 일반화하지는 않았다.


protect는 특징을 섞는 과정에서 보호할 구간의 반영 비율을 조정했다. F0를 사용하는 경로에서 protect가 0.5보다 작으면, 유성, 무성 구간에 따라 검색을 거친 특징과 원래 특징의 비중을 다시 조정한다. 코드 주석의 설명보다 실제로 어떤 텐서를 어떻게 섞는지 확인하는 쪽이 설정의 효과를 이해하는 데 도움이 됐다.


## 완료 응답과 출력 파일 확인


변환 함수는 일부 오류를 잡아 로그에 출력한다. 그런데 음성 변환 실행 연결의 run_infer_script는 convert_audio 호출 뒤 성공 문구와 예상 출력 경로를 반환한다. 내부에서 처리된 오류가 호출자에게 실패 값으로 전달되지 않으면, 성공 문구가 표시되더라도 실제 출력 파일이 정상적으로 생성됐는지는 별도로 확인해야 하는 구간이 생긴다.


모델 로딩, 색인 사용 여부, 출력 파일 생성, 오디오 디코딩은 후속 실행에서 각각 확인할 항목으로 정리했다. 같은 입력, 모델에서 검색 비율만 바꾸는 비교도 남아 있다. 이번에는 음성 생성이나 청취 평가를 수행하지 않아 특정 설정의 자연스러움까지 판단하지는 않았다.


입력 음성은 변환할 내용을, 체크포인트는 생성 모델의 조건을, 색인은 선택적으로 혼합할 특징을 제공하고 있었다. 이 역할을 나누어 보니 설정마다 영향을 주는 단계도 구분할 수 있었다. 다음 글은 텍스트, 오디오, OSC 이벤트의 전달 경로로 이어진다.


## 작업을 정리하며


index_rate와 protect는 처리 경로를 바꾸는 설정이므로 출력 품질은 직접 들어 보고 별도로 평가해야 한다. 입력 음성과 모델, 색인을 같은 조건으로 묶어야 설정 변화의 영향을 비교할 수 있다. 도구의 옵션을 결과 지표와 연결해 읽는 기준으로 남겨 두려 한다.
