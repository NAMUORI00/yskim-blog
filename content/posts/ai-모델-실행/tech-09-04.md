마이크로 들어온 목소리를 다른 기능에 연결할 때는 소리에서 문자를 얻는 **음성 인식**(STT)을 거쳐 소리 데이터가 문자열과 제어 메시지로 차례차례 바뀐다. 음성 인식 뒤에도 번역이나 언어 모델 호출, 네트워크 전송이 이어지는데 각 단계가 다루는 데이터 형식과 완료 조건은 서로 다르다. 전체 과정을 하나의 성공이나 실패로만 묶어 두면 어느 단계에서 지연이나 누락이 생겼는지 구분하기 어렵다.


이 단계별 경계를 확인하려고 `NAMUORI00/gptToVoice`의 `eda4f8b` 커밋과 `NAMUORI00/OSC-SRTC`의 `627b1a4` 커밋 코드를 읽었다. `gptToVoice`는 녹음한 오디오를 문자로 인식해 화면에 보여 준 뒤 언어 모델 응답을 요청한다. `OSC-SRTC`는 인식하고 번역한 문장을 제어 메시지에 담아 VRChat 채팅창으로 보낸다. `OSC-SRTC`의 README가 안내하는 원본 프로젝트는 `rera-vrc/OSC-SRTC`이며, 그 기능은 개인이 새로 구현한 결과에 넣지 않았다.


## gptToVoice의 녹음 파일 저장과 음성 인식


먼저 `gptToVoice`가 마이크 입력을 받아 문장으로 바꾸는 앞단 경로를 본다. [마이크 녹음 처리](https://github.com/NAMUORI00/gptToVoice/blob/eda4f8b6a3c3b039532077e793c7baf67e6bec4b/record.py) 코드는 `sounddevice` 라이브러리의 입력 콜백 함수가 받은 오디오 배열을 대기 줄인 큐(queue)에 넣는다. 그러면 별도 작업 흐름인 스레드가 큐에서 데이터를 차례로 꺼내 녹음 파일에 쓴다. 콜백 함수 안에서 파일 저장까지 직접 끝내지 않고 오디오 데이터 수집과 디스크 쓰기를 스레드로 나누어 두었다. 녹음 파일은 샘플링 주파수 16 kHz의 단일 채널(mono) 오디오로 만들어진다. 아날로그 소리를 일정한 시간 간격으로 측정해 압축 없이 디지털 숫자로 기록하는 16비트 **PCM**(Pulse Code Modulation) 형식으로 디스크에 저장한다.


사용자가 녹음을 마치면 [녹음 종료와 인식 연결](https://github.com/NAMUORI00/gptToVoice/blob/eda4f8b6a3c3b039532077e793c7baf67e6bec4b/module_mic.py)의 `end` 함수가 녹음을 멈추고 완성된 파일을 음성 인식 함수에 넘긴다. 이어서 [음성 인식 처리](https://github.com/NAMUORI00/gptToVoice/blob/eda4f8b6a3c3b039532077e793c7baf67e6bec4b/Scrap_code/translate.py)는 Google Cloud Speech의 `recognize`를 호출해 결과마다 첫 번째 후보 문장을 합친다. 말하는 도중에 중간 인식 결과를 계속 화면에 갱신하는 스트리밍 인식과 달리, 녹음 파일을 먼저 완성한 뒤 파일 단위로 한 번에 인식한다.

## 입력 문장 확인과 언어 모델 요청의 분리


음성 인식이 끝나 문장이 만들어져도 `gptToVoice`는 곧바로 언어 모델을 호출하지 않는다. [녹음과 문장 입력 화면](https://github.com/NAMUORI00/gptToVoice/blob/eda4f8b6a3c3b039532077e793c7baf67e6bec4b/app.py)은 버튼 상태를 `Record`, `Stop`, `Input` 순서로 바꾸면서 인식된 문장을 화면의 입력란에 먼저 채운다. 사용자는 입력란에 들어간 문장을 확인한 뒤에야 텍스트 생성 요청을 보낼 수 있다.


이 과정에서 화면의 진행 막대(progress bar)는 녹음, 인식, 요청 단계에 맞춰 `30`, `60`, `80`, `100`으로 바뀐다. 이 숫자는 처리 단계를 화면에 보여 주기 위해 코드에 고정해 둔 값이다. 다만 음성 인식과 텍스트 생성은 모두 버튼 콜백 안에서 응답이 올 때까지 기다리는 동기식으로 호출된다. 외부 API 응답이 길어질 때 화면 갱신이 멈추는지는 실제 실행에서 따로 확인해야 할 항목으로 남아 있다.


사용자가 전송을 누르면 [언어 모델 요청 처리](https://github.com/NAMUORI00/gptToVoice/blob/eda4f8b6a3c3b039532077e793c7baf67e6bec4b/main.py)가 실행되어 작성 당시의 OpenAI `Completion` 인터페이스와 `text-davinci-003` 모델 이름을 사용한다. 이는 저장된 코드의 연결 관계를 읽은 기록이며, 현재도 같은 설정으로 동작하는지는 확인하지 않았다. 또한 저장소 이름은 `gptToVoice`이지만 확인한 코드 경로에는 언어 모델의 응답 문자를 소리로 바꾸어 읽어 주는 **음성 합성**(TTS) 단계가 없다.


언어 모델이 응답을 돌려주면 프로그램은 이를 화면에 표시하고 입력 문장, 프리셋, 시각, 응답 내용을 JSON 파일과 표에 기록한다. 여기서 표에 저장된 대화 기록과 다음 요청에 들어가는 문맥은 서로 분리되어 있다. 언어 모델 호출 인자로는 현재 선택한 프리셋과 방금 입력한 문장만 넘어간다. 대화 내역을 파일과 표에 보관하는 기능과 이전 대화를 다음 프롬프트 문맥으로 이어 주는 기능은 별개로 동작한다.


![현재 프리셋과 입력 문장이 Completion 요청으로 들어가고 응답은 data.json과 표에 저장되지만 이전 대화 기록은 다음 요청에 포함되지 않음을 보여 주는 구조도](/images/notion/tech-09-04/image-2.png)


그림 2. gptToVoice에서 현재 프리셋과 입력 문장만 언어 모델 요청에 전달되고 저장된 대화 기록은 다음 요청 문맥에 포함되지 않는 구조.


## OSC-SRTC의 번역과 채팅 메시지 전송


`gptToVoice`가 한 컴퓨터 안의 화면 표시와 파일 기록에서 끝난다면, `OSC-SRTC`는 인식한 문장을 네트워크 너머의 다른 프로그램으로 전달한다. [음성 인식, 번역, 채팅 연결](https://github.com/NAMUORI00/OSC-SRTC/blob/627b1a431dfc11b7ea5f9a1a43a28096b7570134/OSC-SRTC.py)의 메인 반복문은 설정된 인식기로 음성을 인식한 뒤, 원문 언어와 목표 언어가 다르면 번역기를 호출한다. 두 번째 목표 언어가 설정되어 있으면 그 번역 결과를 괄호 안에 덧붙인다. 완성된 문장은 확장 처리기를 거친 뒤 `/chatbox/input` 주소로 참과 거짓을 나타내는 불리언(boolean) 값 `True`와 함께 전송된다.


문장을 보낼 때는 오디오 프로그램이나 미디어 기기 사이에 문자열과 숫자 같은 제어 데이터를 주고받는 네트워크 메시지 규격인 **OSC**(Open Sound Control)를 쓴다. [OSC 메시지 전송](https://github.com/NAMUORI00/OSC-SRTC/blob/627b1a431dfc11b7ea5f9a1a43a28096b7570134/modules/SRTC_OSC.py) 모듈은 목적지 주소와 인자를 UDP 클라이언트로 내보낸다. [VRChat 공식 문서](https://docs.vrchat.com/docs/osc-as-input-controller)를 보면 `/chatbox/input`의 불리언 인자가 `True`일 때 문장을 채팅창에 즉시 전송한다. 같은 OSC 규격을 쓰더라도 채팅 문자열 전송과 아바타 상태 값 제어는 주소 체계와 인자 형식이 서로 다르다.


기본 OSC 전송 직전에 실행되는 [문장 확장 처리](https://github.com/NAMUORI00/OSC-SRTC/blob/627b1a431dfc11b7ea5f9a1a43a28096b7570134/modules/SRTC_Extension.py)는 등록된 외부 확장 서버들에 HTTP 요청으로 문장을 차례대로 건넨다. 응답이 정상이면 돌려받은 문장을 다음 확장 서버로 넘기고, `{Sended-Already}`라는 특별한 문자열을 받으면 남은 확장 처리를 즉시 멈춘다. 메인 반복문도 `{Sended-Already}`를 확인하면 기본 OSC 전송 단계를 건너뛴다.


![마이크 입력 후 음성 인식과 목표 언어 비교를 거쳐 번역하고, 확장 서버 처리 결과에서 {Sended-Already} 여부에 따라 OSC 전송 또는 기본 전송 생략으로 분기하는 순서도](/images/notion/tech-09-04/image-3.png)


그림 3. OSC-SRTC에서 인식 및 번역된 문장이 확장 서버 결과에 따라 기본 OSC 전송이나 전송 생략으로 나뉘는 흐름(음성 인식, 번역, 채팅 연결 및 문장 확장 처리 코드를 바탕으로 재구성).


## 메시지 수신 확인과 단계별 상태 경계


확장 서버나 기본 OSC 모듈이 전송 단계를 마쳤다고 해서 대상 화면에 문장이 나타난 것은 아니다. 앞 절의 `{Sended-Already}`는 확장 서버가 메시지 전송까지 대신 맡았다고 메인 프로그램에 알리는 내부 약속일 뿐이다. VRChat 수신 화면에 문장이 실제로 나타났다는 확인 응답(ACK)을 뜻하지는 않는다. 기본 OSC 래퍼 모듈 또한 상대방과 연결을 맺지 않고 패킷만 보내는 UDP를 사용한다. 보낸 메시지가 도착했는지 응용 계층에서 확인하거나 재전송 상태를 관리하는 코드는 들어 있지 않았다.


확장 서버 호출 코드에는 잠금(lock)과 대기 시간의 한계도 남아 있다. 코드는 여러 스레드가 확장 목록을 동시에 바꾸지 못하게 막는 잠금을 잡은 상태에서 HTTP 요청을 보내는데, 이 요청에 대기 제한 시간인 `timeout` 인자가 없다. 외부 확장 서버의 응답이 늦어지면 채팅 메시지 전달이 밀리는 것은 물론이고, 확장 목록을 수정하려는 다른 실행 경로까지 잠금이 풀리기를 기다리며 멈춘다. 확장 서버별 처리 지연 시간은 실제 실행 환경에서 측정해야 할 항목으로 남아 있다.


예를 들어 마이크에 말한 "안녕하세요"가 음성 인식을 거쳐 "Hello"로 번역되었다고 해 보자. 메모리 안에서 번역 문자열 "Hello"가 만들어진 시점과 VRChat 화면에 "Hello"가 표시된 시점은 서로 다른 확인 지점이다. 이 예시처럼 각 단계의 완료 조건이 다르므로 음성 입력 처리는 단일한 성공 여부로 다루기 어렵다. 녹음 저장, 문자 인식, 번역 또는 응답 생성, 전송, 화면 표시 확인의 다섯 단계로 나누어 봐야 상태를 명확히 파악할 수 있다. 이번 작업에서는 코드의 연결 구조만 읽었으며 마이크 녹음, 외부 API 요청, 실제 채팅 전송은 실행하지 않았다. 위 예시는 각 단계의 완료 상태가 왜 다른지 설명하기 위해 든 것이다.

## 결론


`gptToVoice`와 `OSC-SRTC`의 코드를 따라가며 마이크 오디오가 녹음 파일, 인식 문장, 번역문이나 응답, 제어 메시지로 바뀌는 단계별 경계를 확인했다. 음성 기능을 서비스에 붙일 때는 결과 문자열이 생성된 시점과 대상 화면에 반영된 시점을 분리해 기록하는 편이 좋다. 단계별 상태와 소요 시간을 따로 남겨 두면 문제가 생겼을 때 외부 API 응답 대기 때문인지 네트워크 전송 누락 때문인지 바로 좁혀 볼 수 있다.


이번에는 코드에 적힌 호출 경로와 데이터 전달 구조만 읽었으며, 동기식 호출에 따른 화면 멈춤 여부나 외부 확장 서버별 지연 시간은 실제 실행에서 확인하지 않았다. 이후에는 앞서 본 고정값 진행 막대 표시도 실제 처리 단계에 맞춰 구성하려 한다. 다음 글에서는 오디오가 문자열 대신 MIDI와 악보로 바뀌는 `doremi-sketch`에서 자료형에 따라 어떤 도구를 거치고 변환 결과의 신뢰 범위를 어떻게 잡는지 다룬다.
