doremi-sketch에서는 오디오를 MIDI로 변환하고 다시 악보 PDF로 만드는 흐름을 연결했다. 채보 모델의 출력과 악보 도구의 입력 사이에서 음의 시작, 끝, 높이를 유지하는 것이 중심 과제였다.


## 구현과 확인 과정


doremi-sketch 저장소에서 오디오 입력이 MIDI를 거쳐 악보 PDF가 되는 경로를 읽어 봤다. MP3에서 음의 시작, 끝, 높이를 추정해 MIDI로 만들고, 그 결과를 악보로 배치하는 두 단계로 나뉘어 있었다.


[프로젝트 README](https://github.com/NAMUORI00/doremi-sketch/blob/f1c31f2b56a51c3d3d0aa4827697d710f57baff4/readme.md)에는 연주하고 싶은 곡의 악보를 구하기 어렵다는 출발점이 적혀 있었다.


오디오 파일과 영상 링크에서 악보를 만들어 웹으로 제공하겠다는 목표도 함께 있었다. 이번에는 그 기록을 바탕으로 f1c31f2 커밋의 실제 요청 경로를 읽었고, README에 언급된 여러 악기 지원 목표와 현재 코드가 호출하는 피아노 채보 모델의 범위를 구분해 두었다.


## 소리를 저장하는 파일과 연주를 적는 파일


MP3는 소리를 재생하기 위한 오디오 파일이다. MIDI는 음의 시작, 종료 시점 같은 연주 이벤트를 기록한다. MP3에서 MIDI로 넘어가려면 파형 속에서 음을 추정하는 과정이 필요하고, 확장자만 바꾸는 것으로는 음표가 생기지 않는다.


예를 들어 설명용 연주에서 도가 0초에 시작해 0.5초에 끝나고, 미가 0.5초에 시작한다고 놓으면, 파형에는 두 소리의 변화가 담기고, 채보 결과에는 음높이와 시작, 종료 시각이 남는다. 이를 악보로 그릴 때는 박자 안에 음표를 어떻게 배치할지도 해석해야 한다. 자료형의 차이를 설명하기 위해 구성한 예제다.


## 업로드 이후 채보와 악보 생성


[파일 업로드 요청 처리](https://github.com/NAMUORI00/doremi-sketch/blob/f1c31f2b56a51c3d3d0aa4827697d710f57baff4/app/route.py)의 /fileupload는 chooseFile 필드를 받고 확장자를 검사한다.


README의 목표에는 WAV도 등장하지만, 이 경로에서 허용하는 확장자는 mp3 하나였다. 파일명을 정리해 uploaded 폴더에 저장한 뒤 mp3_to_mid를 호출한다.


[음원을 음표로 변환하는 처리](https://github.com/NAMUORI00/doremi-sketch/blob/f1c31f2b56a51c3d3d0aa4827697d710f57baff4/app/doremi_module/core/core.py)는 오디오를 모노로 읽고 PianoTranscription 객체를 만들어 MIDI를 쓴다.


호출 장치는 CPU로 지정되어 있었다. 그다음 라우트에서 MIDI를 다운로드 폴더에 복사하고, midi_to_pdf를 호출한다.


![09-05-01.png](/images/notion/tech-09-05/image-1.png)


그림 1. 업로드 또는 영상 음원에서 MIDI를 얻고 PDF로 조판하는 실제 호출 흐름. 출처: 파일 업로드 요청 처리, 음원을 음표로 변환하는 처리, 음표를 악보로 만드는 처리, 영상에서 음원을 가져오는 처리를 바탕으로 직접 구성. 입력과 출력의 형식 변환을 설명한 그림이다.


[음표를 악보로 만드는 처리](https://github.com/NAMUORI00/doremi-sketch/blob/f1c31f2b56a51c3d3d0aa4827697d710f57baff4/app/doremi_module/midi_convert.py)는 music21의 converter.parse로 MIDI를 읽고, 제목을 설정한 뒤 lily.pdf 형식으로 쓴다.


[music21 문서](https://music21.org/music21docs/moduleReference/moduleConverter.html)에서도 parse는 음악 파일을 내부 음악 구조로 읽는 인터페이스로 설명한다. 이 단계는 음원에서 음을 새로 검출하는 모델 호출과 역할이 다르다.


현재 코드 구성을 보면, 채보와 악보 출력을 각각의 도구에 맡기고 Flask가 파일 경로를 연결하는 방식이었다. 다른 조판 도구와 비교해 LilyPond를 선택했다는 기록은 확인하지 못해서, 선택 배경은 다루지 않았다.


## 체크포인트를 지정하지 않은 호출의 의미


음원을 음표로 변환하는 처리에는 checkpoint_path=None이 지정되어 있었다. 이 값이 라이브러리 내부에서 어떻게 해석되는지 이어서 확인했다.


[사용한 패키지 버전 목록](https://github.com/NAMUORI00/doremi-sketch/blob/f1c31f2b56a51c3d3d0aa4827697d710f57baff4/requirements.txt)이 고정한 bellsky 패키지의 [변환 모델의 가중치 준비](https://github.com/bellsky/piano_transcription_inference/blob/9f2845fdc2192f511639a3591b9de66dae3e3917/piano_transcription_bellsky/inference.py)를 따라가 보니, 경로가 없으면 홈 폴더 아래 기본 체크포인트 경로를 사용했다. 파일이 없거나 크기 조건을 만족하지 않으면 다운로드를 시도한 뒤 가중치를 읽는 흐름이었다.


첫 실행 시에는 모델 다운로드와 외부 도구 설치 상태가 전체 소요 시간에 영향을 줄 수 있다. mp3_to_mid는 호출할 때마다 PianoTranscription 객체를 새로 생성하므로, 요청 간에 모델 객체를 유지하는 구조는 이 함수에 나타나지 않았다. 실제 로딩 시간이나 처리량은 측정하지 않았다.


의존 패키지의 설명은 피아노 녹음 채보를 대상으로 하고 있었다. 관련 [피아노 채보 논문](https://arxiv.org/abs/2010.01815)은 음의 시작, 종료와 페달 이벤트를 다룬다.


이 연구 배경을 웹 프로젝트에 연결할 수는 있지만, 논문의 평가 결과를 이 사이트의 정확도로 그대로 옮길 수는 없다. 여러 악기가 섞인 곡이나 특수한 연주법에 대한 처리 범위도 별도로 확인이 필요한 부분이다.


## 파일명 기반의 작업 식별


[remove_punctuation](https://github.com/NAMUORI00/doremi-sketch/blob/f1c31f2b56a51c3d3d0aa4827697d710f57baff4/app/doremi_module/app.py)은 ASCII 밖의 문자와 문장부호를 제거하는 함수였다.


출력 경로는 이렇게 정리된 파일명을 사용한다. 이름이 다른 두 요청이 같은 결과 경로를 가리킬 수 있다는 점을 작은 예로 확인해 봤다.


`song-1.mp`3와 song_`1.mp`3는 모두 song1mp3라는 문자열이 된다. 라우트가 이 값에 .mid를 붙이면 두 요청의 MIDI 경로가 같아진다. 파일명에서 특수문자를 제거하는 것과 요청마다 고유한 작업 식별자를 부여하는 것은 별개의 문제였다.


![readable-09-05-02.png](/images/notion/tech-09-05/image-2.png)


그림 2. 파일명 정리가 서로 다른 요청을 같은 경로로 모을 수 있는 예. 출처: remove_punctuation과 파일 업로드 요청 처리의 문자열 처리를 바탕으로 직접 구성. 오른쪽 작업 ID 저장은 후속 설계이며 현재 구현으로 표시하지 않았다.


## 처리 중 화면과 악보의 정확도를 따로 확인하기


[브라우저 스크립트](https://github.com/NAMUORI00/doremi-sketch/blob/f1c31f2b56a51c3d3d0aa4827697d710f57baff4/app/static/js/file_upload_func.js)는 요청을 보낼 때 회전 표시를 띄우고, 성공 응답의 pdfpath를 iframe으로 연다.


서버는 같은 요청 안에서 MIDI 생성과 PDF 출력을 모두 수행한다. 회전 표시는 있지만 백그라운드 작업 큐나 진행률 조회가 따로 구현되어 있지는 않았다.


PDF 출력 설정에는 프로젝트 안의 mac용 LilyPond 경로가 지정되어 있었고, Linux용 경로는 주석으로 남아 있었다. 환경 문제가 발생할 경우 Python 패키지 설치, 채보 모델 준비, LilyPond 실행, 브라우저 PDF 표시 중 어느 단계인지 나누어 볼 수 있다.


이 글에서 확인한 범위는 두 변환 도구가 연결되는 코드와 그 사이의 파일 흐름이다. 실제 음원을 입력해 채보 결과를 확인하거나 악보를 연주와 대조해 보지는 않았다.


후속 비교 항목은 피아노의 짧은 단음, 화음에서 음높이, 시작 시각, 음 길이, 악보 가독성을 각각 확인하는 것이다. 이후 인프라 글에서는 외부 실행 파일과 모델을 포함한 재실행 환경을 살펴본다.


## 작업을 정리하며


중간 파일의 형식이 분명해지면 문제를 찾을 위치도 나뉜다. 음높이와 길이는 MIDI 단계에서, 악보의 배치와 가독성은 PDF 단계에서 확인하는 방식이 적절하다. 다음 비교에서는 짧은 단음과 화음부터 입력해 두 단계의 결과를 따로 기록하려 한다.
