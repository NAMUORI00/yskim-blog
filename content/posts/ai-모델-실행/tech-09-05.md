연주하고 싶은 곡이 생겨도 그 곡에 맞는 악보를 바로 구하기는 쉽지 않다. `doremi-sketch`는 [프로젝트 README](https://github.com/NAMUORI00/doremi-sketch/blob/f1c31f2b56a51c3d3d0aa4827697d710f57baff4/readme.md)에 적혀 있듯 오디오 파일이나 영상 링크로 웹에서 바로 악보 PDF를 만들려는 목표에서 출발했다.


녹음된 소리를 악보로 바꾸려면 소리에서 각 음의 시작 시점과 끝 시점, 음높이를 찾아내 악보 그리는 도구로 빠짐없이 전달해야 한다. 이 글에서는 `doremi-sketch` 저장소의 `f1c31f2` 커밋을 기준으로 오디오 파일이 악보 PDF가 되기까지의 실제 요청 경로를 따라간다. 당시 README에 적어 둔 여러 악기 지원 목표와 달리 실제 코드가 호출하는 피아노 모델의 범위도 함께 구분했다.


## 오디오 파형과 MIDI, 악보의 차이


저장소 코드를 보면 변환 과정은 소리 파일에서 음의 높이와 길이를 찾아 기록하는 단계와, 그 기록을 받아 악보로 배치하는 단계로 나뉜다. 두 단계가 나뉘는 이유는 각 파일 형식이 담고 있는 정보가 서로 다르기 때문이다.


피아노로 '도'를 0초에 시작해 0.5초에 끝내고, 이어서 '미'를 0.5초에 시작하는 짧은 연주를 생각해 보자. 오디오 파일인 MP3에는 소리를 재생하기 위해 시간에 따른 파형의 높낮이(진폭) 변화만 연속해서 기록된다. 파일 확장자만 바꾼다고 오디오 파형이 음표로 바뀌지는 않으므로, 파형에서 음을 추정하는 **채보**(transcription) 과정이 먼저 필요하다.


채보를 거친 **MIDI**(Musical Instrument Digital Interface) 파일에는 어떤 음을 언제 누르고 떼었는지 같은 연주 이벤트가 기록된다. 앞서 본 연주라면 MP3 파형에는 두 소리의 연속적인 진폭 변화가 담기지만, MIDI 결과에는 각 음의 높이와 시작 시각, 종료 시각이 남는다. 이를 사람이 읽는 악보 PDF로 그릴 때는 시간 단위로 적힌 이벤트를 마디와 박자 안에 음표로 배치하는 **조판** 과정을 한 번 더 거친다.


![MP3 오디오 파형이 채보 모델을 거쳐 도와 미의 시간 정보가 담긴 MIDI 이벤트가 되고, 다시 악보 조판 도구를 거쳐 악보 PDF로 변환되는 흐름도](/images/notion/tech-09-05/image-1.png)


그림 1. 오디오 파형(MP3)에서 연주 이벤트(MIDI)를 추정하고 악보(PDF)로 조판하는 단계별 데이터 표현 차이.


## 업로드부터 악보 조판까지의 호출 경로


웹 서버는 앞서 본 채보 단계와 악보 조판 단계를 중간 파일 경로로 이어 붙인다. 먼저 [파일 업로드 요청 처리](https://github.com/NAMUORI00/doremi-sketch/blob/f1c31f2b56a51c3d3d0aa4827697d710f57baff4/app/route.py)의 `/fileupload` 라우트는 `chooseFile` 필드로 올라온 파일을 받아 확장자를 검사한다. README의 목표에는 WAV 파일도 적혀 있었지만, 이 커밋의 업로드 경로에서 허용하는 확장자는 `mp3` 하나였다. 서버는 파일 이름을 정리해 `uploaded` 폴더에 저장한 뒤 채보 함수인 `mp3_to_mid`를 호출한다.


[음원을 음표로 변환하는 처리](https://github.com/NAMUORI00/doremi-sketch/blob/f1c31f2b56a51c3d3d0aa4827697d710f57baff4/app/doremi_module/core/core.py)를 맡은 `mp3_to_mid`는 오디오를 단일 채널(모노)로 읽어 들인다. 그다음 모델 계산(추론) 장치를 CPU로 지정해 피아노 채보 모델인 `PianoTranscription` 객체를 만들고 MIDI 파일을 기록한다. MIDI 생성이 끝나면 라우트는 해당 파일을 다운로드 폴더로 복사하고, 이어서 악보 조판 함수인 `midi_to_pdf`를 호출한다.


[음표를 악보로 만드는 처리](https://github.com/NAMUORI00/doremi-sketch/blob/f1c31f2b56a51c3d3d0aa4827697d710f57baff4/app/doremi_module/midi_convert.py)에서는 파이썬 음악 분석 라이브러리인 `music21`의 `converter.parse`로 앞서 만든 MIDI를 읽어 들인다. [music21 문서](https://music21.org/music21docs/moduleReference/moduleConverter.html)에서도 `parse`를 음악 파일을 프로그램 내부의 음악 구조로 읽어 들이는 인터페이스로 설명한다. 음원에서 음을 새로 검출하는 채보 모델 호출과 달리, 이미 추출된 연주 이벤트를 악보 구조로 옮기는 단계다. 코드는 읽어 들인 객체에 제목을 설정한 뒤 외부 조판 도구인 LilyPond를 거쳐 `lily.pdf` 형식으로 악보를 출력한다.


![영상 URL과 MP3 업로드 입력이 Flask 요청 처리를 거쳐 피아노 채보 모델에서 MIDI 파일로 변환되고, MIDI 다운로드와 music21 파싱 및 LilyPond 조판을 거쳐 악보 PDF로 표시되는 파이프라인](/images/notion/tech-09-05/image-2.png)


그림 2. 업로드 또는 영상 음원에서 MIDI를 얻고 PDF로 조판하는 실제 호출 흐름(출처: 파일 업로드 요청 처리, 음원을 음표로 변환하는 처리, 음표를 악보로 만드는 처리, 영상에서 음원을 가져오는 처리 코드 기반 재구성).


이처럼 Flask 라우트는 채보와 악보 조판을 각각의 전용 도구에 맡기고 중간 파일 경로를 넘겨주며 두 도구를 연결한다. 다른 악보 조판 도구와 비교해 LilyPond를 선택한 배경은 당시 기록으로 남아 있지 않아 이 글에서는 다루지 않았다.


## 가중치 자동 준비와 채보 모델의 범위


앞선 호출 경로에서 채보를 맡은 `mp3_to_mid` 코드를 보면 `PianoTranscription`을 생성할 때 `checkpoint_path=None`을 넘긴다. 여기서 체크포인트는 인공지능 모델이 학습을 마친 뒤 저장해 둔 계산값인 **가중치** 파일을 가리킨다. 경로를 비워 두었을 때 가중치를 어떻게 준비하는지 확인하기 위해, [사용한 패키지 버전 목록](https://github.com/NAMUORI00/doremi-sketch/blob/f1c31f2b56a51c3d3d0aa4827697d710f57baff4/requirements.txt)에 고정된 `bellsky` 패키지의 구현을 따라가 보았다.


패키지 내부의 [변환 모델의 가중치 준비](https://github.com/bellsky/piano_transcription_inference/blob/9f2845fdc2192f511639a3591b9de66dae3e3917/piano_transcription_bellsky/inference.py) 코드는 경로 인자가 없을 때 사용자 홈 폴더 아래의 기본 체크포인트 경로를 참조한다. 그 위치에 가중치 파일이 없거나 파일 크기가 기준 조건을 만족하지 않으면, 외부에서 가중치 파일을 먼저 내려받은 뒤 모델을 초기화한다.


![mp3_to_mid 호출 시 checkpoint_path가 None이면 기본 경로의 가중치를 확인해 없을 경우 다운로드한 뒤 가중치를 로드하고 CPU 추론으로 MIDI를 생성하는 순서도](/images/notion/tech-09-05/image-3.png)


그림 3. 체크포인트 경로를 비워 두었을 때 기본 경로의 파일을 확인해 가중치를 내려받고 CPU에서 추론하는 흐름.


따라서 새로운 환경에서 처음 실행할 때는 모델 가중치 다운로드와 외부 도구 설치 상태가 전체 응답 시간에 영향을 줄 수 있다. 또한 `mp3_to_mid`는 호출될 때마다 `PianoTranscription` 객체를 새로 생성해, 서버 프로세스가 요청 사이에 모델을 메모리에 유지하지 않는다. 이번 코드 검토에서는 호출 구조만 확인했고 실제 모델 로딩 시간이나 처리량은 따로 측정하지 않았다.


사용한 채보 패키지는 여러 악기가 아니라 피아노 연주 녹음을 대상으로 만든 모델이다. 기반이 된 [피아노 채보 논문](https://arxiv.org/abs/2010.01815) 역시 피아노 음의 시작과 종료 시점, 페달 이벤트를 추정하는 방법을 다룬다. 논문에서 검증된 모델을 웹 서비스에 연결해 채보 기능을 구현했지만, 논문의 벤치마크 정확도를 사용자가 올리는 모든 음원에 그대로 적용할 수는 없다. 여러 악기가 섞인 곡이나 특수한 연주법이 들어간 음원을 넣었을 때 어디까지 처리되는지는 별도로 확인해야 한다.


## 파일명 기반 경로 생성과 요청 충돌


도구 사이의 연결을 따라가다 보니 중간 파일을 저장하고 구분하는 경로 생성 방식에서도 짚어 볼 점이 있었다. 예를 들어 서로 다른 요청에서 `song-1.mp3`와 `song_1.mp3`를 각각 업로드하는 상황을 생각해 보자. 서버는 업로드된 파일의 이름을 정리할 때 [remove_punctuation](https://github.com/NAMUORI00/doremi-sketch/blob/f1c31f2b56a51c3d3d0aa4827697d710f57baff4/app/doremi_module/app.py) 함수를 호출해 ASCII 범위 밖의 문자와 문장부호를 지운다.


이 함수를 거치면 문장부호가 제거되어 두 파일 이름 모두 `song1mp3`라는 같은 문자열이 된다. 라우트는 정리된 문자열을 그대로 출력 경로에 쓰기 때문에, 뒤에 `.mid`를 붙이면 두 요청의 MIDI 파일 경로가 `song1mp3.mid`로 겹친다. 이처럼 원래 이름이 달랐던 두 요청이라도 같은 결과 파일 경로를 가리킬 수 있다. 파일 이름에서 특수문자를 걸러 내는 일과 요청마다 고유한 작업 식별자(ID)를 부여해 결과물을 격리하는 일은 따로 다루어야 했다.


![song-1.mp3와 song_1.mp3가 문장부호 제거 후 song1mp3.mid라는 같은 경로로 충돌하는 현재 구조와 고유 작업 ID를 부여해 개별 저장하는 후속 설계를 비교한 그림](/images/notion/tech-09-05/image-4.png)


그림 4. 파일명에서 문장부호를 제거할 때 서로 다른 요청이 같은 결과 경로로 모이는 예와 작업 ID 분리 후속 설계 비교(출처: remove_punctuation 및 파일 업로드 요청 처리 코드 기반 재구성).


## 동기 요청 처리와 단계별 오류 구분


클라이언트 화면이 서버의 변환 결과를 받아 보여 주는 동작도 함께 확인했다. [브라우저 스크립트](https://github.com/NAMUORI00/doremi-sketch/blob/f1c31f2b56a51c3d3d0aa4827697d710f57baff4/app/static/js/file_upload_func.js)는 서버로 업로드 요청을 보낼 때 화면에 회전 표시(스피너)를 띄우고, 응답이 오면 그 안의 `pdfpath`를 `iframe`으로 열어 보여 준다. 서버는 하나의 HTTP 요청 안에서 MIDI 생성과 PDF 조판을 끝까지 마친 뒤 응답을 돌려주는 **동기 처리** 방식으로 동작한다. 이 때문에 작업을 뒤에서 따로 처리하는 백그라운드 작업 큐나 진행률 조회 API는 구현되어 있지 않았다.


한편 PDF 출력 설정 코드에는 프로젝트 폴더 안에 포함된 macOS용 LilyPond 실행 파일 경로가 지정되어 있었고, Linux용 경로는 주석으로 남아 있었다. 이처럼 외부 실행 파일과 파이썬 라이브러리가 함께 엮여 있을 때는 중간 파일의 경계를 알아 두면 문제를 찾기가 수월하다. 실행 중 오류가 나더라도 파이썬 패키지 설치, 채보 모델 가중치 준비, LilyPond 실행, 브라우저 PDF 표시 중 어느 단계에서 멈췄는지 나누어 확인할 수 있기 때문이다.


## 결론


`doremi-sketch`는 업로드된 MP3에서 피아노 채보 모델로 MIDI를 뽑아내고 `music21`과 LilyPond를 거쳐 악보 PDF를 조판한다. 코드를 따라가며 가중치 자동 다운로드, 요청마다 모델 객체를 새로 만드는 동작, 문장부호 제거로 인한 파일 경로 충돌 가능성을 확인했다.


이번 검토에서는 도구가 이어지는 코드 경로와 중간 파일 흐름만 살폈고, 실제 음원을 넣어 채보 결과를 원곡 연주와 대조해 보지는 않았다. 변환 품질을 점검할 때도 음높이와 음 길이는 MIDI 단계에서, 박자 배치와 악보 가독성은 PDF 단계에서 나누어 확인하는 편이 원인을 좁히기 좋다. 다음에는 피아노의 짧은 단음과 화음부터 입력해 두 단계의 결과를 각각 기록해 보고, 외부 실행 파일과 모델을 묶어 일관되게 재실행할 수 있는 인프라 환경도 이어서 다루려 한다.
