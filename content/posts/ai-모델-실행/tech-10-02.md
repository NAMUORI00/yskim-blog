ComfyUI를 실행할 Docker 환경을 정리하며 모델, 확장 노드, 사용자 데이터를 구분했다. 실행 래퍼의 설치와 볼륨 연결을 따라 컨테이너 교체 후 남는 파일과 추가 설치가 필요한 부분을 확인했다.


## 구현과 확인 과정


앞 글의 설치, 실행 구분에 이어, ComfyUI 래퍼가 모델, 노드 코드, 사용자 데이터를 어느 경로에 두는지 살펴봤다. 컨테이너를 새로 만들면 워크플로 JSON은 남아 있어도 모델 파일이나 확장 노드가 빠질 수 있어서, 무엇이 이미지 안에 들어가고 무엇이 호스트에 남는지 구분하는 데 초점을 뒀다.


NAMUORI00/ComfyUI의 088f323 커밋은 ComfyUI 실행용 Docker 환경을 제공하는 래퍼였다. [README](https://github.com/NAMUORI00/ComfyUI/blob/088f323a309092541d51fc7456013efcd412b52a/README.md)에도 이 범위가 명시되어 있다.


상위 ComfyUI의 생성 알고리즘 자체는 다루지 않았고, Dockerfile, Compose, 시작 스크립트가 관리하는 파일 배치와 실행 조건을 중심으로 읽었다.


## 워크플로, 노드, 모델 파일의 역할


워크플로는 어떤 노드를 어떤 순서와 연결로 실행할지 표현하는 파일이다. 노드는 계산을 수행하는 코드이고, 모델 파일은 그 계산에 쓰이는 학습 가중치를 담고 있다. [ComfyUI의 모델 설명](https://docs.comfy.org/basic-concepts/models)에서도 모델 파일과 이를 선택하는 로더 노드를 구분하고 있다.


[커스텀 노드 문서](https://docs.comfy.org/basic-concepts/custom-nodes)에는 외부 노드가 기본 기능을 확장하는 구조가 설명되어 있다.


같은 워크플로 파일이 "모델 A를 불러오는 노드"를 가리키더라도, 모델 A 파일이 없으면 실행되지 않는다. 노드 코드가 있어도 그 코드가 import하는 패키지가 빠지면 역시 멈출 수 있다. 이 세 종류(워크플로, 노드 코드, 모델 파일)가 각각 어디에 저장되는지부터 확인했다.

## 이미지에 들어가는 부분과 호스트에 남는 부분


[Dockerfile](https://github.com/NAMUORI00/ComfyUI/blob/088f323a309092541d51fc7456013efcd412b52a/Dockerfile)은 PyTorch, CUDA 기반 이미지 위에 FFmpeg 등의 도구를 설치하고, 상위 ComfyUI 저장소를 내려받아 Python 의존성을 설치하는 구조였다.


상위 저장소는 깊이 1의 clone으로 가져오는데, 특정 커밋을 지정하는 줄은 없었다. 래퍼 저장소의 커밋이 같더라도 빌드 시점에 가져온 본체 소스가 동일하다는 보장은 되지 않는다.


모델, 입력 파일, 생성 결과, 확장 기능, 사용자 설정과 임시 파일은 호스트의 폴더를 바인드 마운트로 연결해 보관하는 구조다. 컨테이너를 다시 만들 때 같은 폴더를 연결하면 이전 자료를 그대로 쓸 수 있다. 같은 디스크에 파일을 유지하는 구성이며, 백업은 별도 저장 장치에 마련해야 한다.


[컨테이너 실행 설정](https://github.com/NAMUORI00/ComfyUI/blob/088f323a309092541d51fc7456013efcd412b52a/docker-compose.yml)


앞 글의 설치기와 달리 이 Compose는 ComfyUI의 8188 포트를 직접 공개한다. 같은 ComfyUI 환경이라도 접속 경로와 인증 구성은 다를 수 있으므로 동일하다고 전제하지 않았다. 호스트의 사용자 ID, 그룹 ID로 실행하도록 설정되어 있어, Linux에서는 바인드 마운트된 폴더의 쓰기 권한이 해당 계정과 맞아야 한다.


## 최초 실행의 확장 설치


[시작 시 확장을 준비하는 스크립트](https://github.com/NAMUORI00/ComfyUI/blob/088f323a309092541d51fc7456013efcd412b52a/entrypoint.sh)에는 ComfyUI-Manager, Civicomfy, LoRA Manager, VoxCPM, FishSpeech 확장의 설치 로직이 들어 있었다.


해당 폴더가 없으면 저장소를 clone한다. 필요한 Python 패키지 목록이나 확장 설치 스크립트가 있으면 이를 실행한 뒤 ComfyUI 명령으로 프로세스를 넘기는 흐름이었다.


새 데이터 폴더에서 시작할 때 필요한 확장을 함께 준비할 수 있어 편리한 구성이다. 반면 시작 시점의 네트워크 상태와 각 확장 저장소의 최신 커밋이 실행 조건에 포함된다. 이미지 빌드가 성공했더라도 첫 시작의 확장 설치 단계에서 별도의 오류가 발생할 수 있는 구조다.

## 폴더가 있으면 설치를 건너뛰는 조건


설치 함수는 폴더가 이미 있으면 그 안의 패키지 상태를 다시 점검하지 않는다. 최초 실행에서 clone은 끝났지만 requirements 설치가 실패한 경우, 스크립트는 경고를 출력하고 다음 단계로 진행할 수 있다. 이후 재시작에서는 폴더가 존재하므로 설치 자체를 생략한다. 코드에서 도출한 실패 시나리오다.


확장 소스의 존재, 의존성 설치, 노드 등록, 워크플로 실행은 서로 다른 확인 단계로 정리했다. 폴더가 생긴 이후에도 설치 실패가 남을 수 있으므로 재시도 조건에는 패키지 설치 결과를 반영할 여지가 있다.


Python 패키지는 --user 설치와 PYTHONUSERBASE를 통해 user 디렉터리 아래에 보관되도록 설정되어 있다. 한편 PYTHONPATH에는 python3.11 경로가 직접 적혀 있어서, 기반 이미지의 Python 버전이 바뀌면 같은 위치를 읽지 못할 수 있다. 사용자 설치 폴더를 보존한다고 해서 이미지 교체 후의 의존성 호환성까지 보장되지는 않는다.


## 환경 재현에 필요한 기록


기반 이미지에는 버전 태그가 있지만, Dockerfile의 pip 설치와 시작 때 가져오는 외부 노드에는 빌드 시점에 따라 달라질 요소가 남아 있다. 재실행 조건은 래퍼와 본체 커밋, 확장별 커밋, 설치된 패키지 목록, 모델 파일의 식별값(해시 등), 워크플로와 입력 자료까지 묶어서 확인할 항목으로 정리했다.


README의 드라이버, CUDA 선택 설명은 당시 환경의 기록으로 읽었다. 현재 호환 범위를 판단하려면 [NVIDIA의 minor version compatibility 문서](https://docs.nvidia.com/deploy/cuda-compatibility/minor-version-compatibility.html)와 실제 사용 기능의 제한 사항을 함께 확인해야 한다. 드라이버가 표시하는 CUDA 버전 숫자 하나로 모든 라이브러리 조합의 호환성을 판정하기는 어렵다.


이번에는 Dockerfile, Compose, entrypoint 등 환경 코드를 읽는 데 그쳤고, 새 컨테이너를 시작하거나 모델을 내려받아 생성 작업을 실행하지는 않았다. 남은 확인 항목은 보관한 자료로 작은 워크플로를 실제로 다시 실행해 보는 것이다. 다음 글에서는 모델 생성 서비스에서 스트리밍 서버 쪽으로 범위를 옮겨, MediaMTX의 서버 접속과 실제 영상 재생 과정을 살펴본다.


## 작업을 정리하며


폴더가 존재하는 상태와 확장 노드를 사용할 준비가 된 상태를 구분해야 한다. 의존성 설치 기록과 데이터 보관 위치를 함께 남기면 재실행 문제를 좁히기 쉽다. 같은 디스크의 데이터 유지와 별도 백업도 각각 관리하려 한다.
