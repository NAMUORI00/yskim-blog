ComfyUI는 이미지나 음성을 만드는 여러 단계를 화면에서 블록처럼 이어 붙여 실행하는 프로그램이다. 이 프로그램을 실행 환경과 함께 하나로 묶어 구동하는 격리 공간이 Docker **컨테이너**(container)다. 컨테이너로 ComfyUI를 운영할 때는 작업 순서를 적은 JSON 파일만 따로 보관했다고 해서 같은 작업을 다시 실행할 수 있는 것이 아니다. 컨테이너를 새로 만들었을 때 그 작업에 필요한 인공지능 모델 파일이나 추가 기능 코드, 혹은 그 코드가 불러오는 Python 패키지가 빠져 있으면 실행이 멈춘다.


컨테이너를 교체해도 남는 파일과 새로 설치할 요소를 구분하려고 ComfyUI 저장소(`NAMUORI00/ComfyUI`, 코드 변경 기록인 `088f323` 커밋)를 확인했다. 저장소의 [README](https://github.com/NAMUORI00/ComfyUI/blob/088f323a309092541d51fc7456013efcd412b52a/README.md)에 적혀 있듯 이 코드는 원래의 상위 ComfyUI를 감싸서 Docker 실행 환경을 제공하는 래퍼(wrapper)다. 이 저장소는 상위 ComfyUI의 생성 알고리즘 자체는 다루지 않는다. 그래서 `Dockerfile`, `docker-compose.yml`, 시작 스크립트(`entrypoint.sh`)의 파일 배치와 실행 조건을 읽었다.


## 워크플로, 노드, 모델 파일의 역할


파일 배치와 실행 조건을 이해하려면 먼저 ComfyUI에서 작업 하나를 돌릴 때 어떤 요소들이 맞물려 돌아가는지 구분해야 한다. 예를 들어 이미지를 생성할 때는 모델을 읽어 오는 단계와 계산을 실행하는 단계를 순서대로 연결한 JSON 설정 파일인 **워크플로**(workflow)를 먼저 불러온다. 워크플로에 적힌 각 작업 단계에서 실제로 계산을 수행하는 코드가 **노드**(node)이며, 모델 파일은 그 계산에 쓰이는 인공지능의 학습 수치인 가중치를 담고 있다. [ComfyUI의 모델 설명 문서](https://docs.comfy.org/basic-concepts/models)에서도 가중치가 담긴 모델 파일과 이를 읽어 오는 로더 노드를 별개 요소로 구분한다. 또한 [커스텀 노드 문서](https://docs.comfy.org/basic-concepts/custom-nodes)에서는 외부 확장 노드 코드가 기본 기능을 넓히는 방식을 설명한다.


이 요소들은 서로 맞물려 있어서, 같은 워크플로 파일이 특정 모델을 불러오는 노드를 가리키더라도 해당 모델 파일이 지정된 경로에 없으면 실행되지 않는다. 마찬가지로 외부 확장 노드 코드가 있더라도 그 코드가 불러다 쓰는(`import`하는) Python 패키지가 환경에 빠져 있으면 실행이 멈출 수 있다. 따라서 본체 코드와 확장 노드, Python 패키지, 모델 가중치, 입출력 데이터가 컨테이너와 바깥 컴퓨터(호스트)의 어느 위치에 각각 저장되는지부터 파악해야 했다.

## 컨테이너 이미지와 호스트의 파일 배치


각 요소의 저장 위치를 구체적으로 나누어 보기 위해, 먼저 컨테이너를 찍어 내는 틀인 **이미지**(image) 안에 고정되는 파일부터 [Dockerfile](https://github.com/NAMUORI00/ComfyUI/blob/088f323a309092541d51fc7456013efcd412b52a/Dockerfile)에서 확인했다. 이 파일은 인공지능 연산에 쓰이는 PyTorch와 CUDA 기반 이미지 위에 FFmpeg 같은 시스템 도구를 설치한다. 그다음 상위 ComfyUI 저장소를 내려받아 기본으로 필요한 Python 의존성 패키지를 함께 설치한다. 이때 최근 기록 1개만 가져오는 얕은 복제(`--depth 1` 옵션을 준 `git clone`)로 받으며, 특정 커밋의 고유 식별값인 해시(hash)를 지정하는 줄은 없었다. 래퍼 저장소의 커밋이 같더라도 이미지를 빌드하는 시점에 따라 가져오는 ComfyUI 본체 소스가 달라질 수 있다.


반면 용량이 크거나 자주 바뀌는 파일은 이미지에 넣지 않고 호스트의 폴더를 컨테이너 내부 경로에 직접 연결하는 **바인드 마운트**(bind mount)로 보관한다. 모델 가중치(`models`), 입력 자료(`input`), 생성 결과(`output`) 폴더가 모두 이 방식을 쓴다. 외부 확장 노드(`custom_nodes`), 사용자 설정과 패키지(`user`), 임시 파일도 마찬가지로 호스트에 둔다. 컨테이너를 지우고 다시 만들더라도 같은 호스트 폴더를 연결하면 이전에 받았던 모델과 작업 파일을 그대로 이어서 쓸 수 있다. 다만 바인드 마운트는 같은 디스크 안에 파일을 유지하는 방식이므로, 디스크 장애에 대비한 백업은 별도 저장 장치에 마련해야 한다.


네트워크 접속과 권한 조건은 [컨테이너 실행 설정](https://github.com/NAMUORI00/ComfyUI/blob/088f323a309092541d51fc7456013efcd412b52a/docker-compose.yml)(`docker-compose.yml`)에 정의되어 있다. 다른 글에서 다룬 통합 설치기와 달리 이 설정은 ComfyUI의 `8188` 포트를 호스트에 직접 공개한다. 같은 ComfyUI 컨테이너라도 배포 방식에 따라 접속 경로와 인증 구성이 다를 수 있어 동일하다고 전제할 수 없다. 또한 컨테이너 프로세스를 호스트의 사용자 ID(UID)와 그룹 ID(GID)로 실행하도록 지정되어 있다. 따라서 Linux 환경에서는 바인드 마운트된 호스트 폴더의 쓰기 권한이 해당 계정과 맞아야 파일 저장 오류가 나지 않는다.


## 컨테이너 시작 시 확장 노드 자동 설치


바인드 마운트로 연결한 호스트의 `custom_nodes` 폴더에는 외부 확장 노드가 들어가는데, 이 노드들은 이미지 빌드 시점이 아니라 컨테이너가 처음 켜질 때 설치된다. [시작 시 확장을 준비하는 스크립트](https://github.com/NAMUORI00/ComfyUI/blob/088f323a309092541d51fc7456013efcd412b52a/entrypoint.sh)(`entrypoint.sh`)에는 확장을 내려받는 `install_node` 함수가 들어 있다. 이 함수는 ComfyUI-Manager, Civicomfy, LoRA Manager, VoxCPM, FishSpeech 다섯 가지 확장을 준비한다.


컨테이너가 시작되면 스크립트는 먼저 각 확장의 폴더가 `custom_nodes` 아래에 있는지 확인한다. 폴더가 없으면 원격 저장소를 `git clone`으로 받고, 그 안에 Python 패키지 목록(`requirements.txt`)이나 설치 스크립트가 있으면 차례로 실행한다. 이 준비 과정이 모두 끝나면 마지막에 ComfyUI 실행 명령으로 프로세스를 넘긴다.


이 방식은 빈 데이터 폴더만 마운트해 컨테이너를 띄워도 필요한 확장을 알아서 준비해 주므로 초기 구성이 간편하다. 대신 컨테이너를 처음 시작하는 시점의 네트워크 상태와 각 확장 저장소의 최신 커밋이 실행 조건에 개입한다. Docker 이미지 빌드가 정상으로 끝났더라도, 컨테이너를 처음 켜는 확장 설치 단계에서 외부 저장소 변경이나 네트워크 문제로 별도의 오류가 발생할 수 있다.


![컨테이너 시작 시 확장 폴더 유무를 확인해 폴더가 없을 때만 소스와 패키지를 설치하고, 실패 시 경고를 기록한 뒤 ComfyUI를 실행하는 순서도](/images/notion/tech-10-02/image-2.png)

## 확장 폴더 검사와 패키지 경로의 한계


앞선 `entrypoint.sh`의 `install_node` 함수를 따라가다 보니 컨테이너를 재시작할 때 문제가 될 수 있는 조건이 보였다. 스크립트는 확장 폴더가 이미 존재하면 그 안의 Python 패키지가 정상으로 깔렸는지 다시 점검하지 않고 설치 단계를 통째로 건너뛴다.


예를 들어 최초 실행에서 저장소 복제(`git clone`)는 성공해 폴더가 만들어졌지만, 이어진 `requirements.txt` 패키지 설치는 실패할 수 있다. 이때 스크립트는 경고만 출력하고 그대로 ComfyUI 실행 단계로 넘어간다. 이후 문제를 해결하려고 컨테이너를 재시작하면, 이번에는 폴더가 이미 존재하기 때문에 패키지 설치 자체를 생략해 버린다. 결국 확장 소스 폴더가 디스크에 있는 상태와 의존성 패키지가 설치된 상태는 같지 않다. 여기에 ComfyUI에 노드가 정상 등록된 상태와 실제 워크플로가 돌아가는 상태까지 네 단계를 서로 다른 확인 단계로 다뤄야 한다. 폴더가 생긴 뒤에도 의존성 누락이 남을 수 있으므로, 재시도 여부를 판단할 때는 패키지 설치 성공 여부까지 반영할 여지가 있다.


![1차 실행에서 custom_nodes 폴더만 생성되고 user 패키지 설치가 실패했을 때, 2차 실행에서 폴더가 있다는 이유로 재설치를 건너뛰어 노드 불러오기에 실패하는 흐름도](/images/notion/tech-10-02/image-3.png)


그림 3. 최초 실행에서 패키지 설치가 실패한 채 폴더만 남으면 재시작 시 설치를 건너뛰어 노드 오류가 이어지는 과정.


확장 노드가 설치하는 Python 패키지의 보관 경로에도 비슷한 주의점이 있었다. 스크립트는 `--user` 옵션과 `PYTHONUSERBASE` 환경 변수를 사용해 호스트와 연결된 `user` 디렉터리 아래에 패키지를 모아 둔다. 그런데 패키지를 찾는 `PYTHONPATH` 환경 변수에는 `python3.11` 경로가 직접 적혀 있었다. 나중에 기반 이미지를 교체하면서 컨테이너 안의 Python 버전이 바뀌면, 호스트의 `user` 폴더를 그대로 마운트하더라도 같은 위치를 읽지 못할 수 있다. 사용자 패키지 폴더를 호스트에 보존하는 것만으로는 이미지 교체 후의 의존성 호환성까지 보장되지 않는다.


## 실행 환경 재현 조건과 호환성 확인


이처럼 설치 시점과 패키지 경로가 나뉘어 있기 때문에, 같은 워크플로 실행 환경을 나중에 그대로 재현하려면 컨테이너 이미지 하나만 남겨서는 부족하다. 기반 이미지에 버전 태그가 붙어 있더라도, `Dockerfile`의 `pip` 패키지 설치와 첫 실행 때 내려받는 외부 확장 노드에는 시점마다 달라지는 요소가 남아 있다. 따라서 환경을 똑같이 맞추려면 래퍼 저장소와 상위 ComfyUI 본체의 커밋, 확장 노드별 커밋, 실제로 설치된 Python 패키지 목록을 함께 기록해야 한다. 여기에 모델 파일의 해시 같은 식별값과 워크플로 JSON, 입력 자료까지 묶어 남겨 두어야 문제를 좁히기 쉽다.

그림 4. 이미지 빌드, 컨테이너 첫 시작, 워크플로 실행 단계마다 달라질 수 있는 요소와 환경 재현을 위해 남겨야 할 기록.


또한 저장소 `README`에 적힌 GPU 드라이버와 CUDA 버전 선택 설명은 작성 당시 환경의 기록으로 읽어야 한다. 현재 운영 환경에서 호환 범위를 판단할 때는 드라이버가 표시하는 CUDA 버전 숫자 하나만 보아서는 부족하다. [NVIDIA의 minor version compatibility 문서](https://docs.nvidia.com/deploy/cuda-compatibility/minor-version-compatibility.html)와 실제로 사용하는 라이브러리의 제한 사항을 함께 대조해야 한다.


## 결론


이번 글에서는 ComfyUI 실행용 Docker 래퍼 저장소(`NAMUORI00/ComfyUI`, `088f323` 커밋)의 설정과 스크립트를 읽었다. 코드에서 이미지 안의 본체 소스와 호스트에 바인드 마운트로 남는 모델, 확장 노드, 작업 데이터의 경계를 확인했다. 확장 노드는 컨테이너 첫 실행 때 폴더가 없을 때만 설치되므로, 패키지 설치가 실패한 채 폴더만 남으면 재시작해도 설치를 건너뛰어 오류가 이어진다. 또한 호스트에 남긴 사용자 패키지의 `python3.11` 고정 경로와 빌드 시점마다 달라지는 커밋 때문에, 같은 환경을 재현하려면 버전 기록과 모델 해시를 함께 남겨야 한다.


이번 작업에서는 `Dockerfile`, `docker-compose.yml`, `entrypoint.sh` 코드를 읽으며 데이터 경계와 실패 조건을 파악하는 데 집중했다. 새 컨테이너를 띄우거나 모델을 받아 생성 작업을 직접 실행하지는 않았으므로, 호스트 데이터와 패키지 경로를 연결해 작은 워크플로를 실행해 보는 일은 다음 확인 항목으로 남았다. 이어지는 글에서는 모델 생성 서비스에서 스트리밍 서버 쪽으로 범위를 옮겨, MediaMTX 서버 접속과 실제 영상 재생 과정을 확인한다.
