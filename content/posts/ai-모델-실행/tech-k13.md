공개된 언어 모델 파일을 내려받았다고 해서 곧바로 문장을 넣고 답을 얻을 수 있는 것은 아니다. 파일만 있는 상태와 실제로 문장을 처리하는 상태 사이에는 세 가지 부품과 호환 조건이 놓여 있다. 숫자를 담은 **가중치 파일**, 글자와 번호를 잇는 **토크나이저**(tokenizer), 계산을 맡는 **런타임**(runtime)이 서로 맞아야 문장을 처리한다.


문장 하나가 들어가 답변으로 나오기까지의 흐름을 따라가 보면 세 부품의 경계가 드러난다. 먼저 토크나이저가 입력 문장을 작은 글자 조각인 토큰(token)으로 쪼개고 정수 번호인 토큰 ID 배열로 바꾼다. 런타임은 가중치 파일에서 모델 구조와 숫자 배열을 읽어 들인 뒤, 토큰 ID를 받아 다음 토큰의 점수를 계산한다. 점수에 따라 다음 토큰 ID를 고르는 과정을 끝날 때까지 반복하면, 토크나이저가 토큰 ID들을 다시 글자로 되돌려 출력 문장을 만든다.

## 가중치 파일의 구성


세 부품 가운데 가중치 파일에서 가장 큰 비중을 차지하는 데이터는 신경망이 학습한 숫자 값인 **가중치**(weight)다. 신경망의 각 층을 이루는 가로세로 숫자 표인 행렬들이 배열 형태로 저장되어 있다. 예를 들어 768×768 크기의 행렬 하나에는 소수점이 있는 실수(부동소수점) 값 589,824개가 들어간다. 파일 안에는 이런 행렬이 층마다, 그리고 문맥을 살피는 어텐션(attention)과 값을 변환하는 피드포워드(feed-forward) 구간마다 반복해서 들어 있다.


숫자 배열만으로는 그 값들을 어떤 순서와 모양으로 계산해야 하는지 알 수 없으므로, 파일에는 모델의 구조를 설명하는 메타데이터도 함께 담긴다. 전체 층 수와 각 층의 크기(차원), 어텐션 헤드 수 같은 정보가 여기에 해당한다. 예를 들어 [GGUF 형식](https://github.com/ggml-org/ggml/blob/master/docs/gguf.md)은 파일 맨 앞의 파일 헤더에 파일 종류를 알리는 매직 넘버와 버전을 둔다. 이어서 이름과 값을 짝지은 키-값 형태의 구조 메타데이터 구간에 층 수, 차원, 헤드 수 같은 모델 구조 정보를 기록한다. 그 뒤에는 다차원 배열인 각 텐서(tensor)의 이름, 크기, 데이터 타입, 파일 안 위치(오프셋)를 적은 텐서 정보 목록이 온다. 마지막에는 실제 행렬 숫자 값을 담은 가중치 바이트 배열이 메모리가 읽기 좋은 정렬 경계에 맞춰 배치된다.


![GGUF 가중치 파일 내부가 파일 헤더, 구조 메타데이터, 텐서 정보 목록, 가중치 바이트 배열 네 구간으로 나뉜 구조도](/images/notion/tech-k13/image-2.png)


그림 2. GGUF 가중치 파일 내부에 파일 헤더, 구조 메타데이터, 텐서 정보 목록, 가중치 바이트 배열이 순서대로 배치되는 구조를 나타낸 개념도다.


이처럼 파일 하나에 가중치와 구조 정보가 함께 들어 있으면, 런타임은 메타데이터만 읽어도 계산 순서를 잇는 연산 그래프를 구성할 수 있다. 다만 가중치 파일 자체는 숫자 배열과 설명서를 담아 둔 데이터일 뿐 스스로 계산을 수행하지는 않는다. 또한 런타임이 GGUF 같은 파일 형식을 읽을 수 있다고 해서 그 안에 담긴 모든 모델 구조(아키텍처)와 연산까지 실행할 수 있는 것은 아니다. 런타임 안에 해당 아키텍처의 연산 코드가 구현되어 있어야 실제로 모델을 돌릴 수 있다.


## 토크나이저의 변환 규칙


가중치 파일이 숫자로 이루어진 행렬을 담고 있으므로, 언어 모델에 문장을 넣으려면 텍스트도 정수 배열로 바꿔야 한다. 예를 들어 설명용 어휘표에서 `"hello"`에 12번, `" world"`에 38번을 붙였다면 입력 문장은 `[12, 38]`로 나타낼 수 있다. 이처럼 텍스트와 정수 번호인 토큰 ID 사이의 변환 규칙을 정의한 부품이 토크나이저다. 위 번호는 설명을 위해 임의로 붙인 예시이며, 실제 번호는 토크나이저마다 정해진 문자열 정규화 방식과 분할 규칙, 어휘표에 따라 달라진다.


토크나이저 파일에는 토큰과 번호를 짝지은 어휘 목록, 자주 등장하는 글자 쌍을 하나로 합치는 병합 규칙(BPE 방식의 경우)이 들어 있다. 문장의 시작과 끝을 표시하는 특수 토큰 정의도 함께 담기며, 구체적인 파일 구조는 [Hugging Face Tokenizers 라이브러리](https://huggingface.co/docs/tokenizers/index) 문서에서 확인할 수 있다.


가중치 파일과 토크나이저는 모델을 학습할 때 썼던 토큰 대응 관계를 그대로 공유해야 한다. 모델의 가중치는 특정 번호가 특정 글자 조각을 뜻한다는 전제로 학습되어 있기 때문이다. 다른 토크나이저를 써서 입력 숫자가 달라지면 모델이 학습할 때 기대했던 표현과 어긋나 엉뚱한 결과를 낸다. GGUF처럼 토크나이저 정보를 가중치 파일의 메타데이터에 함께 넣어 별도 토크나이저 파일이 필요 없는 구성도 있다.


## 런타임의 실행 단계


가중치 파일과 토크나이저가 준비되었다면 실제로 숫자를 읽고 계산을 수행할 프로그램인 런타임이 필요하다. 추론 엔진이라고도 부르는 런타임은 가중치 파일을 읽어 메모리에 올리고, 토큰 ID 배열을 받아 행렬 연산을 실행한 뒤 결과를 돌려준다. 대표적인 예로 llama.cpp는 GGUF 파일을 읽는 런타임이고, [ONNX Runtime](https://onnxruntime.ai/docs/)은 ONNX 파일을 읽는 런타임이다.


런타임이 내부에서 모델을 처리하는 과정은 파일 파싱, 메모리 배치, 연산 실행의 세 단계로 나뉜다. 먼저 파일 파싱(해석) 단계에서는 메타데이터를 읽어 층 수, 텐서 크기, 데이터 타입을 확인하고 연산 순서를 정하는 신경망 연산 그래프를 구성한다. 이어지는 메모리 배치 단계에서는 가중치를 시스템 메모리(RAM)나 그래픽카드 메모리(VRAM)에 올린다. llama.cpp 같은 런타임에서 GGUF 파일을 운영체제의 메모리 매핑(`mmap`) 방식으로 읽으면, 파일 전체를 메모리에 복사하지 않고 필요한 부분만 접근할 수 있다.


마지막 연산 실행 단계에서는 행렬 곱셈, 활성화 함수, 어텐션 계산을 실제 하드웨어에 맞춰 수행한다. 예를 들어 ONNX Runtime은 실행 공급자(Execution Provider) 구조로 CPU, CUDA, DirectML 같은 하드웨어별 계산 커널을 교체할 수 있다. 전체 모델의 연산 그래프를 작은 서브그래프로 나누어 각 하드웨어 가속기에 분배하는 방식이다.


![추론 런타임 내부의 파일 파싱, 메모리 배치, 연산 실행 3단계와 CPU, CUDA, DirectML 커널로의 분배 구조도](/images/notion/tech-k13/image-3.png)


그림 3. 추론 런타임이 파일 파싱과 메모리 배치를 거친 뒤 연산 서브그래프를 하드웨어별 커널에 분배하는 과정을 나타낸 개념도다.


런타임이 파일 해석부터 하드웨어 연결까지 맡기 때문에, 같은 가중치 파일이라도 런타임이 다르면 지원하는 연산과 메모리 사용 패턴, 추론 속도가 달라진다. 읽을 수 있는 파일 형식도 런타임에 종속적이므로 GGUF 파일을 변환 없이 ONNX Runtime에 직접 넣을 수는 없다.


## 가중치 양자화의 영향 범위


런타임이 메모리에 올리는 가중치 파일의 크기를 줄이기 위해 숫자를 더 적은 비트 수의 정밀도로 표현하는 **양자화**(quantization)를 적용하기도 한다. 추론 중 생성되는 활성값이나 이전 계산을 모아 두는 KV 캐시를 양자화하는 경우도 있지만, 여기서는 가중치 파일에 저장되는 값을 양자화하는 경우만 다룬다. 16비트 부동소수점인 FP16(값당 2바이트) 가중치를 8비트 정수 INT8(1바이트)이나 4비트 정수 INT4(0.5바이트)로 바꾸면 파일 크기가 줄어든다.


앞서 예로 든 768×768 크기의 단일 행렬(원소 589,824개)을 기준으로 값 자체의 저장량을 계산해 보면 차이가 분명하다. FP16으로 저장하면 1,179,648바이트(1.125MiB)가 필요하다. 이를 INT8로 바꾸면 589,824바이트(576KiB)가 되고, INT4 값만 세면 294,912바이트(288KiB)로 줄어든다.


![FP16 원본 가중치(1.125MiB)를 INT8(576KiB)과 INT4(288KiB)로 양자화했을 때의 용량과 각 런타임 커널 요구사항 비교도](/images/notion/tech-k13/image-4.png)


그림 4. 768×768 단일 행렬을 기준으로 양자화 수준에 따른 가중치 값의 저장량과 런타임 요구사항을 비교한 설명용 예제다.


위 계산은 행렬 원소 자체의 비트 수만 합산한 최소치에 가까운 비교다. 실제 양자화 파일에는 값의 범위를 복원하기 위한 비율 값인 스케일(scale)과 블록 메타데이터가 함께 들어간다. 여기에 다른 정밀도의 텐서가 섞일 수 있어 전체 파일 크기가 정확히 4분의 1이 되지는 않는다.


가중치를 양자화해도 층 수나 어텐션 헤드 수 같은 신경망 구조와 토크나이저는 바뀌지 않는다. 대신 양자화된 가중치를 읽으려면 런타임이 해당 양자화 형식을 지원해야 한다. 예를 들어 `Q4_K_M` 방식으로 양자화한 GGUF 파일은 llama.cpp에서 바로 읽히지만, 이 형식을 모르는 런타임에서는 파일을 불러오는 단계부터 실패한다.


양자화는 가중치 비트 수를 줄여 메모리 전송량을 낮추는 데 유리하다. 하지만 계산 과정에서 값을 원래 범위로 복원하는 역양자화(dequantization) 연산과 지원 커널의 영향도 함께 받는다. 정밀도 손실에 따른 출력 품질 변화도 남으므로, 양자화 구성을 고를 때는 파일 크기, 추론 속도, 답변 품질을 각각 비교해야 한다.


## 부품 교체와 호환 조건


가중치 파일, 토크나이저, 런타임은 맡은 역할이 나뉘어 있으므로 어느 부품을 바꾸느냐에 따라 영향 범위도 달라진다.


| 부품     | 담당 역할               | 교체 시 영향                     |
| ------ | ------------------- | --------------------------- |
| 가중치 파일 | 숫자 배열과 구조 메타데이터 저장  | 다른 모델이 된다                   |
| 토크나이저  | 텍스트와 토큰 ID 변환 규칙 정의 | 입출력 텍스트 해석이 달라진다            |
| 런타임    | 파일 읽기, 연산, 하드웨어 매핑  | 지원 형식, 추론 속도, 메모리 사용량이 달라진다 |


부품을 교체하거나 실행 환경을 옮길 때는 세 부품이 맞물리는 호환 조건을 확인해야 한다. 가중치 파일과 토크나이저 사이에서는 학습 당시의 토큰 대응 관계가 일치하는지 봐야 한다. 런타임에서는 파일 형식과 모델 연산, 양자화 형식 지원 여부를 확인해야 한다. 같은 가중치 파일 형식을 지원하는 다른 런타임으로 옮길 때는 별도 변환이 필요하지 않을 수도 있다.


## 결론


공개된 언어 모델을 실행하려면 숫자와 구조를 담은 가중치 파일, 텍스트와 토큰 ID를 잇는 토크나이저, 파일을 읽어 연산하는 런타임이 서로 맞아야 한다. 가중치를 양자화해 파일 크기를 줄이더라도 모델 구조와 토크나이저는 그대로 유지되지만, 런타임이 그 양자화 형식과 역양자화 연산을 지원해야 모델을 돌릴 수 있다.


이 글에서는 세 부품의 역할과 호환 조건, 그리고 가중치 파일 양자화가 바꾸는 범위를 확인했다. 런타임이 추론을 시작한 뒤 입력 문장을 처리해 첫 출력 토큰을 얻는 단계와 이후 토큰을 하나씩 이어 만드는 단계에서 대기 시간이 달라지는 현상은 아직 다루지 않았다. 추론 단계별 연산 특성과 토큰 생성 시간, 그리고 PyTorch 체크포인트를 GGUF로 옮길 때 보존되거나 손실되는 정보는 다음 글에서 이어서 다룬다.
