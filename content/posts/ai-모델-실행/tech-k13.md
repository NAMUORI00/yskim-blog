## 모델 실행에 필요한 구성


언어 모델을 실행하는 구성에서 가중치 파일, 토크나이저, 런타임의 역할을 정리했다. 파일을 확보한 상태와 문장을 처리할 수 있는 상태 사이에는 형식, 연산 지원과 토큰 변환의 호환 조건이 있다. 실행 경로를 이 조건에 맞춰 나누어 읽었다.


가중치가 담은 값, 입력 문장을 토큰으로 바꾸는 규칙, 연산을 수행하는 프로그램을 구분한 뒤 양자화가 바꾸는 부분을 살펴봤다.


## 가중치 파일이 담고 있는 것


모델 파일의 핵심은 가중치(weight)다. 신경망의 각 층에 있는 행렬이 숫자 배열로 저장되어 있다. 768×768 크기의 행렬이라면 589,824개의 부동소수점 값이 들어간다. 이런 행렬이 층마다, 어텐션, 피드포워드 등 구성 요소마다 존재한다.


가중치 외에도 구조 메타데이터가 포함된다. 층의 수, 각 층의 차원, 어텐션 헤드 수 같은 정보다. [GGUF 형식](https://github.com/ggml-org/ggml/blob/master/docs/gguf.md)의 경우 파일 앞부분에 매직 넘버, 버전이 오고, 키-값 메타데이터 구간에 모델 구조 정보가 기록되며, 그 뒤에 텐서별 이름, 차원, 데이터 타입, 오프셋이 나열된다. 마지막으로 실제 가중치 바이트가 정렬 경계에 맞춰 배치된다.


파일 하나에 가중치와 구조 정보가 함께 들어 있으므로 지원하는 아키텍처라면 런타임이 메타데이터를 읽어 필요한 연산 구성을 만들 수 있다. 파일 형식을 읽을 수 있다는 것과 그 안의 모든 아키텍처, 연산을 지원한다는 것은 다르다. 다만 가중치 파일 자체는 연산을 수행하지 않는다. 숫자 배열일 뿐이다.


## 토크나이저: 텍스트와 숫자 사이의 변환 규칙


언어 모델에 문장을 넣으려면 텍스트를 정수 시퀀스로 바꿔야 한다. 이 변환 규칙을 담은 것이 토크나이저다. 예를 들어 설명용 어휘표에서 "hello"에 12, " world"에 38을 붙였다면 입력은 `[12, 38]`로 표현할 수 있다. 이 번호는 임의의 예시이며 실제 번호는 토크나이저의 정규화, 분할 규칙과 어휘표에 따라 달라진다.


토크나이저 파일에는 어휘 목록, 병합 규칙(BPE 방식의 경우), 특수 토큰 정의가 들어 있다. [Hugging Face Tokenizers 라이브러리](https://huggingface.co/docs/tokenizers/index)에서 이 구조를 직접 확인할 수 있다.


가중치와 토크나이저는 학습 때 사용한 토큰 대응 관계가 맞아야 한다. 다른 토크나이저로 입력 숫자가 달라지면 모델이 기대한 표현과 어긋날 수 있다. GGUF에는 토크나이저 정보를 메타데이터로 포함할 수 있어 별도 파일이 필요하지 않은 구성도 있다.

## 런타임이 하는 일


런타임(추론 엔진)은 가중치 파일을 읽어 메모리에 올리고, 토큰 ID 배열을 받아 행렬 연산을 실행하고, 결과를 반환하는 프로그램이다. llama.cpp는 GGUF 파일을 읽는 런타임이고, [ONNX Runtime](https://onnxruntime.ai/docs/)은 ONNX 파일을 읽는 런타임이다.


런타임이 맡는 구체적인 일을 나누어 보면 다음과 같다.


**파일 파싱**: 메타데이터를 읽어 신경망 그래프를 구성한다. 층 수, 텐서 크기, 데이터 타입을 확인하고 연산 순서를 결정한다.


**메모리 배치**: 가중치를 RAM이나 VRAM에 올린다. llama.cpp 등에서 GGUF를 mmap으로 읽으면 파일 전체를 복사하지 않고 필요한 부분만 접근할 수 있다.


**연산 실행**: 행렬 곱, 활성화 함수, 어텐션 계산을 하드웨어에 맞춰 수행한다. ONNX Runtime은 Execution Provider라는 개념으로 CPU, CUDA, DirectML 등 하드웨어별 커널을 교체할 수 있도록 설계되어 있다. 모델 그래프를 서브그래프로 나누어 각 하드웨어 가속기에 분배하는 방식이다.


같은 가중치 파일이라도 런타임이 다르면 지원하는 연산, 메모리 사용 패턴, 속도가 달라진다. 파일 형식도 런타임에 종속적이므로, GGUF 파일을 ONNX Runtime에 직접 넣을 수는 없다.


## 양자화가 바꾸는 것과 바꾸지 않는 것


양자화는 숫자를 더 적은 정밀도로 표현하는 방법이다. 여기서는 가중치를 양자화하는 경우만 좁혀 보았고, 활성값이나 KV 캐시를 양자화하는 경우와 구분했다. FP16(16비트 부동소수점)으로 저장된 값을 INT4(4비트 정수)로 변환하면 파일 크기가 줄어든다.


앞서 예로 든 589,824개 값의 행렬을 기준으로 계산하면, FP16 값의 저장량은 1,179,648바이트 = 1.125MiB이고, 4비트 값만 세면 294,912바이트 = 288KiB가 된다.

그림 2. 양자화 수준에 따른 가중치 값의 저장량과 런타임 요구사항(설명용 예제, 숫자는 단일 행렬 기준)


위 계산은 값 자체의 비트 수만 센 하한에 가까운 비교다. 실제 파일에는 스케일, 블록 메타데이터와 다른 정밀도의 텐서가 섞일 수 있어 정확히 4분의 1이 되지는 않는다. 바꾸지 않는 것은 신경망의 구조(층 수, 어텐션 헤드 수)와 토크나이저다.


그리고 양자화된 가중치를 읽으려면 런타임이 해당 형식을 지원해야 한다. Q4_K_M으로 양자화한 GGUF 파일은 llama.cpp에서 읽히지만, 이 형식을 모르는 런타임에서는 로드 자체가 실패한다.


양자화는 비트 수를 줄여 메모리 전송량을 낮출 수 있지만 역양자화(dequantization) 연산과 지원 커널의 영향도 받는다. 정밀도 손실에 따른 품질 변화도 남는다. 그래서 크기, 속도, 품질을 각각 비교할 항목으로 정리했다.


## 부품 사이의 경계


| 부품     | 담당                 | 교체 시 영향                 |
| ------ | ------------------ | ----------------------- |
| 가중치 파일 | 숫자 배열 + 구조 메타데이터   | 다른 모델이 된다               |
| 토크나이저  | 텍스트 ↔ 토큰 ID 변환 규칙  | 입출력 해석이 달라진다            |
| 런타임    | 파일 읽기, 연산, 하드웨어 매핑 | 지원 형식, 속도, 메모리 사용이 달라진다 |


각 부품의 교체에는 호환 조건이 있었다. 가중치와 토크나이저는 학습 당시 대응 관계를, 런타임은 파일, 연산, 양자화 형식 지원을 확인할 대상이다. 같은 파일을 지원하는 다른 런타임으로 옮길 때에는 변환이 필요하지 않을 수도 있다.


첫 출력 토큰과 이후 토큰의 대기 시간이 달라지는 과정은 다음 내용으로 이어진다. PyTorch 체크포인트를 GGUF로 옮기는 경우처럼 가중치 형식을 변환할 때 보존되는 정보와 손실되는 정보도 따로 살펴볼 주제로 남겼다.
