[모델 파일, 토크나이저, 런타임 정리](https://blog.namuori.net/posts/tech-k13/)에서는 모델 파일과 런타임의 구분을 짚었다. 이번에는 런타임이 입력 토큰을 받아 응답 토큰을 만들어 내는 과정을 시간순으로 따라가 본다.


LLM에 프롬프트를 보내고 응답이 끝날 때까지 걸린 전체 시간만 보면, 첫 글자가 나오기까지 오래 걸린 것인지 글자가 이어지는 속도가 느린 것인지 구분하기 어렵다. 첫 출력까지의 대기와 그 뒤로 출력이 이어지는 간격은 서로 다른 원인으로 길어지기 때문이다.


추론 성능 지표에서는 첫 토큰이 나오기까지의 시간을 **TTFT**(Time To First Token), 이후 출력 토큰 사이의 간격을 **TPOT**(Time Per Output Token)라고 부른다. 런타임 내부의 추론 과정도 입력 전체를 한 번에 처리하는 **prefill** 단계와 토큰을 하나씩 생성하는 **decode** 단계로 나뉘며, 두 단계 사이를 **KV 캐시**가 잇는다. 각 단계의 연산 특성과 측정 기준을 알면 두 지표를 보고 어디서 지연이 생겼는지 좁혀 갈 수 있다.


![프롬프트 N 토큰이 Prefill 단계에서 처리되어 첫 토큰과 KV 캐시를 만들고, Decode 단계에서 이전 KV 캐시를 참조하고 새 값을 추가하며 다음 토큰을 반복 생성하는 흐름도](/images/notion/tech-k14/image-1.png)

## Prefill: 입력 전체를 한 번에 처리하기


사용자가 100개 토큰으로 이루어진 프롬프트를 보내면 모델은 이 100개 토큰을 한 번에 처리한다. 트랜스포머의 어텐션(attention) 메커니즘에서 100개 토큰 각각의 Query, Key, Value 텐서를 동시에 계산하고, 인과 마스크(causal mask)가 허용하는 앞쪽 토큰들에 대해 어텐션을 구한다. 인과 마스크는 현재 위치보다 뒤에 오는 토큰을 미리 참조하지 못하게 가리는 역할을 한다. 이렇게 입력 프롬프트 전체를 처리해 첫 토큰 출력을 준비하는 과정이 prefill이다.


프롬프트가 길어질 때 prefill 계산량이 왜 빠르게 커지는지는 어텐션 점수 행렬의 크기로 확인할 수 있다. 셀프 어텐션에서 입력이 N개 토큰이면 모든 토큰 쌍의 관계를 계산하므로 어텐션 점수 행렬의 크기는 N×N이 된다. 토큰이 10개면 100칸이지만, 100개면 10,000칸, 1,000개면 개념적으로 1,000,000칸 크기가 된다.


최적화된 구현은 이 행렬을 나누어 계산하는 방식으로 중간 결과의 메모리 저장 부담을 조정한다. 또한 실제 서빙 환경에서는 긴 입력을 여러 조각으로 나누어 처리하거나 이미 계산해 둔 앞부분(접두사)을 재사용하기도 한다. 실제 모델에서는 여기에 멀티헤드와 다층 구조가 곱해지지만, 입력 길이에 따라 계산량이 빠르게 늘어나는 경향은 이 N×N 관계로 드러난다.


따라서 다른 실행 조건이 같다면 긴 프롬프트가 prefill 시간을 늘리는 요인이 된다. 다만 사용자가 겪는 TTFT에는 순수한 prefill 계산 외에도 대기 시간과 캐시 재사용 여부가 함께 섞이므로, 프롬프트 길이만으로 지연 원인을 단정하기는 어렵다.


## KV 캐시: 한 번 계산한 결과를 보관하기


prefill 단계에서 계산한 Key와 Value 텐서는 이후 토큰을 생성할 때도 다시 필요하다. 새 토큰의 어텐션을 구하려면 새 토큰의 Query와 이전 토큰들의 Key로 점수를 계산하고, 그 가중치로 이전 Value들을 모아야 하기 때문이다. 토큰을 만들 때마다 앞선 입력을 처음부터 다시 계산하는 대신, prefill 결과를 GPU 메모리에 저장해 두고 재사용한다. 이 저장 공간이 KV 캐시다.


KV 캐시가 차지하는 크기를 손계산으로 확인해 보자. 층(layer)이 4개, KV 헤드가 4개, 헤드 차원이 8인 아주 작은 모델에서 시퀀스 길이가 10 토큰이라고 가정한다.

- 한 토큰이 한 층의 한 헤드에서 만드는 값: K 8개 + V 8개 = 16개
- 한 토큰 전체: 16 × 4헤드 × 4층 = 256개 값
- 10 토큰: 256 × 10 = 2,560개 값
- FP16(2바이트) 기준: 2,560 × 2 = 5,120바이트 = 5KiB

![한 토큰이 한 층과 한 헤드에서 만드는 16개 값에 4헤드와 4층, 10 토큰, FP16 2바이트를 차례로 곱해 5KiB가 되는 단계별 계산도](/images/notion/tech-k14/image-2.png)


그림 2. 4층, 4헤드, 헤드 차원 8인 모델에서 10 토큰 시퀀스의 KV 캐시 크기를 구하는 손계산 과정.


이 계산을 실제 모델 규모로 확장하면 메모리 사용량이 크게 달라진다. 32층, KV 헤드 32개, 헤드 차원 128인 모델에서 같은 계산을 하면 한 토큰당 2 × 128 × 32 × 32 = 262,144개 값, FP16 기준으로 0.5MiB가 된다. 시퀀스 길이가 1,000 토큰이면 요청 하나당 KV 캐시만 500MiB를 차지한다.


모든 이전 위치를 참조하는 기본 어텐션 가정에서는 토큰이 생성될 때마다 캐시에 새 행이 추가되므로 출력이 길어질수록 저장량도 늘어난다. 다만 GQA(Grouped-Query Attention)나 MQA(Multi-Query Attention)처럼 KV 헤드 수를 줄인 구조, 일정 범위만 참조하는 슬라이딩 윈도우, 캐시 저장 정밀도, 메모리 할당 방식이 다르면 계산식도 달라진다. [Hugging Face의 캐시 전략 문서](https://huggingface.co/docs/transformers/kv_cache)를 읽을 때 모델의 실제 구조와 조건을 먼저 확인해야 하는 이유다.


## Decode: 토큰을 하나씩 생성하기


prefill이 끝나면 추론은 decode 단계로 넘어간다. 한 번의 전방 패스(forward pass)로 토큰 하나만 생성하고, 방금 만든 토큰이 다시 다음 전방 패스의 입력이 되어 종료 토큰이 나올 때까지 반복한다.


prefill과 decode는 연산과 메모리 접근의 비율이 다르다. prefill은 여러 입력 위치를 한꺼번에 병렬로 처리하지만, decode는 매 단계마다 토큰 1개에 대한 어텐션과 피드포워드 연산만 수행한다. 반면 7B 규모 모델이라면 토큰 1개를 만들 때마다 수 GB의 가중치를 메모리에서 읽어야 한다.


![Prefill 단계는 N개 토큰을 병렬 처리해 연산량이 커지고 Decode 단계는 토큰 1개를 생성할 때마다 가중치와 KV 캐시를 읽어 메모리 대역폭이 병목이 되는 비교도](/images/notion/tech-k14/image-3.png)


그림 3. 입력 전체를 병렬로 처리하는 Prefill 단계와 매번 가중치를 읽어 토큰을 하나씩 생성하는 Decode 단계의 특성 비교.


이처럼 많은 가중치를 참조하는 데 비해 같은 가중치로 동시에 처리하는 토큰 수가 적기 때문에, 배치 크기가 작은 일반적인 밀집(dense) 모델에서는 메모리 전송 대역폭이 decode의 병목이 되기 쉽다. 물론 배치 크기, 일부 전문가 신경망만 활성화하는 MoE(Mixture of Experts) 구조, 누적된 캐시 길이, 가속기 사양이 바뀌면 병목 지점도 달라진다.


따라서 TPOT를 비교할 때는 모델 가중치 크기와 메모리 대역폭 외에도 연산 정밀도, 배치 크기, 캐시 길이를 함께 확인해야 한다. 여러 조건이 동시에 바뀐 결과를 두고 가중치 크기 하나의 효과로 해석하지 않도록 비교 항목을 나누어 살펴야 한다.


## 측정 경계: TTFT와 TPOT가 나뉘는 지점


지금까지 살펴본 추론 단계들이 성능 지표에서는 어떻게 나뉘는지 측정 기준을 짚어 보자. [Anyscale의 메트릭 문서](https://docs.anyscale.com/llm/serving/benchmarking/metrics)는 TTFT를 "프롬프트를 제출한 시점부터 첫 출력 토큰을 받는 시점까지의 경과 시간"으로 정의한다.


같은 클라이언트가 관찰한 시각을 기준으로 두 지표를 수식으로 나타내면 경계가 분명해진다. 요청 전송 시각을 t₀, 첫 토큰 수신 시각을 t₁, 마지막 m번째 토큰 수신 시각을 tₘ이라 두면 TTFT는 t₁−t₀이고, 평균 TPOT는 (tₘ−t₁)/(m−1)이다.


![요청 전송 시각 t0부터 첫 토큰 수신 시각 t1까지를 TTFT로, 첫 토큰 t1부터 마지막 토큰 tm까지의 시간을 m-1로 나눈 값을 평균 TPOT로 나타내는 타임라인](/images/notion/tech-k14/image-4.png)


그림 4. 클라이언트에서 정한 관찰 시각으로 계산하는 TTFT와 평균 TPOT 구간.


클라이언트에서 이 지표를 구할 때는 두 가지를 주의해야 한다. 출력이 0개나 1개이면 분모가 0 이하가 되어 평균 TPOT를 계산할 수 없다. 또한 스트리밍 응답에서는 네트워크 메시지 하나에 여러 토큰이 묶여 도착할 수도 있으므로, 메시지 수신 간격을 곧바로 토큰 생성 간격으로 취급해서는 안 된다.


서버 내부에서 재는 지표와 클라이언트에서 재는 지표는 기준 시각도 다르다. [vLLM의 메트릭 문서](https://docs.vllm.ai/en/latest/design/metrics/)를 보면 서버는 마지막 `SCHEDULED` 시점부터 첫 `NEW_TOKENS` 시점까지를 prefill 구간으로 구분하고, TTFT는 프런트엔드 요청 도착 시각(`arrival_time`)을 기준으로 계산한다. 서버와 클라이언트의 지표가 참조하는 시각이 다르면 대기나 입력 처리의 포함 범위도 달라진다. 지표를 기록할 때는 지표 이름과 함께 어느 프로세스의 어떤 두 시각을 뺐는지 명시해 측정 경계를 맞춰야 한다.


두 지표를 분리해 보면 지연이 생겼을 때 점검할 방향이 갈린다. TTFT가 크면 큐 대기, 입력 처리, 네트워크 전송 시간을 나누어 확인하고 프롬프트 길이를 줄이거나 prefill 최적화를 살핀다. 반대로 TPOT가 크면 배치 크기, 연산, 메모리 전송 가운데 어디가 병목인지 확인한 뒤 양자화로 모델 크기를 줄이거나 메모리 대역폭이 더 넓은 하드웨어를 고려할 수 있다.


## 후속 검토


단일 요청에서는 입력 처리와 토큰 생성이 차례대로 이어지지만, 여러 요청을 동시에 처리하는 서빙 환경에서는 prefill과 decode가 GPU 자원을 나누어 쓰는 방식과 KV 캐시의 메모리 관리가 중요한 과제가 된다. 운영체제의 가상 메모리와 페이징 기법을 KV 캐시 관리에 적용한 PagedAttention([Kwon et al., 2023](https://arxiv.org/abs/2309.06180))을 후속 주제로 이어 읽을 수 있다.
