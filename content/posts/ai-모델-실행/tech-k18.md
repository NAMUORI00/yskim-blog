MCP의 호스트, 클라이언트, 서버, 도구를 요청과 응답의 흐름으로 정리했다. 모델이 파일 읽기 호출을 제안한 뒤 실제 실행과 결과 반환을 맡는 코드는 별도로 있다. 각 구성 요소가 그 사이에서 담당하는 작업을 살펴봤다.


## 모델 출력과 도구 실행의 분리


LLM은 텍스트를 생성하는 프로세스로, 파일 시스템에 접근하거나 HTTP 연결을 맺는 능력이 없다. "날씨를 알려줘"라는 입력에 도구를 쓰겠다고 판단하더라도, 실제 날씨 API에 TCP 연결을 여는 코드는 모델 바깥에 있어야 한다.


호출 제안과 실제 실행을 구분하면 허용할 도구와 결과의 취급 범위도 나누어 볼 수 있다. 의도하지 않은 실행과 결과 해석의 오류는 각각 점검할 문제로 남는다.


MCP는 이 경계를 프로토콜 수준에서 정의한다. 이 예제에서는 모델이 도구와 인자를 제안하고, 실행, 연결 관리는 호스트, 클라이언트, 서버라는 세 계층이 처리한다. JSON-RPC 2.0 메시지로 통신하며, 각 계층의 책임이 명세에 고정되어 있으므로 구현체마다 역할이 달라지는 일을 줄인다.


## 네 역할의 구분


여기서는 MCP 2025-06-18 버전을 기준으로 역할과 메시지를 읽었다. 이 글은 명시한 문서 버전을 기준으로 기본 구성과 호출 흐름을 다룬다.


**호스트(Host)**: 사용자와 마주하는 애플리케이션이다. Claude Desktop이나 AI 기능을 탑재한 IDE가 여기 해당한다. 여러 클라이언트 인스턴스를 생성, 관리하며, 사용자에게 도구 실행 승인을 요청하는 것도 호스트의 역할이다. 전체 대화 기록은 호스트만 보유한다.


**클라이언트(Client)**: 호스트 내부에서 생성되어 특정 서버 하나와 1:1 세션을 유지하는 커넥터다. 하나의 호스트에 클라이언트 여러 개가 존재할 수 있고, 각 클라이언트는 자신이 연결된 서버와만 통신한다. 서버별 연결 경계를 유지하는 역할을 맡는다. 운영체제와 네트워크의 접근 권한은 프로토콜 연결과 별도로 설정해야 했다.


**서버(Server)**: 도구, 리소스, 프롬프트 템플릿 등 특정 기능을 노출하는 서비스다. 파일 시스템 접근, 데이터베이스 쿼리, 외부 API 호출처럼 각자 한 가지 책임에 집중하며, 필요한 문맥만 전달받도록 설계된다. 실제로 무엇을 보내는지는 호스트 구현과 권한 설정을 확인해야 했다.


**도구(Tool)**: 서버가 노출하는 실행 가능한 함수다. 이름, 설명, 입력 스키마(JSON Schema)로 정의되며, 모델은 이 정의를 보고 어떤 도구를 어떤 인자로 부를지 판단한다.

## 요청 한 쌍을 따라가기


“뉴욕 날씨를 알려줘”라는 입력을 받는 설명용 메시지를 구성했다. 초기화와 기능 협상이 끝난 세션에서 도구 조회, 호출, 응답이 이어지는 예다.


**1단계: 도구 목록 조회.** 세션 초기화 시 클라이언트가 서버에 `tools/list`를 보낸다. 서버는 자신이 노출하는 도구 이름, 설명, 입력 스키마를 응답으로 돌려준다.


```json
{ "jsonrpc": "2.0", "id": 1, "method": "tools/list", "params": {} }
```


**2단계: 모델의 판단.** 호스트가 사용자 메시지와 도구 목록을 LLM에 전달하면, 모델은 텍스트 생성의 일부로 "`get_weather`를 `location=New York`으로 호출하겠다"는 의사를 출력한다. 이 시점에서 실제 실행은 아직 일어나지 않았다.


**3단계: 도구 호출.** 이 예제처럼 개별 승인이 필요한 정책이라면 호스트가 승인을 확인한 뒤, 클라이언트가 서버에 `tools/call`을 보낸다.


```json
{ "jsonrpc": "2.0", "id": 2, "method": "tools/call",
  "params": { "name": "get_weather", "arguments": { "location": "New York" } } }
```


**4단계: 결과 반환.** 서버는 실제 API를 호출하고 결과를 클라이언트에 돌려준다. 클라이언트 → 호스트 → 모델 순서로 전달되며, 모델은 이 결과를 바탕으로 사용자에게 보여줄 응답을 생성한다.

## 분리가 만드는 경계


구성 요소를 나눈 뒤에는 실행 승인, 서버 간 문맥 전달, 기능 협상이 적용되는 위치를 살펴봤다.


**보안 경계.** 모델이 "삭제 도구를 호출하겠다"고 판단해도 호스트가 사용자 승인 없이는 실행하지 않으면 위험한 동작이 차단된다. MCP 명세는 "민감한 작업에 대해 사용자 확인을 요청해야 한다(SHOULD)"고 권고한다.


**서버 격리.** 파일 서버와 데이터베이스 서버가 별도 클라이언트를 통해 연결되므로, 호스트가 서버 간 문맥 전달을 통제할 수 있다. 다만 공유 파일, 자격 증명, 네트워크 권한이 있으면 별도 접근 경로가 생길 수 있다. 이를 프로토콜만으로 차단했다고 보지는 않았다.


**기능 협상.** 세션 시작 시 서버와 클라이언트가 각자 지원하는 기능(capability)을 선언한다. 도구 호출이 필요한 서버는 `tools` 기능을, 샘플링이 필요한 클라이언트는 `sampling` 기능을 선언한다. 선언하지 않은 기능은 세션에서 사용할 수 없으므로, 예상 밖의 동작이 줄어든다.


## 오류가 나타나는 두 경로


도구 호출 과정에서 오류는 두 계층에서 발생하며, 처리 방식이 다르다.


**프로토콜 오류**: 존재하지 않는 도구 이름을 요청하거나 인자 형식이 스키마와 맞지 않으면, JSON-RPC 표준 에러가 반환된다. 같은 잘못된 요청을 그대로 반복해도 해결되지 않는 경우가 많다. 도구 이름이나 인자를 바로잡아 다시 요청하는 복구는 가능하다.


**실행 오류**: 도구가 실행되었지만 외부 API 장애나 비즈니스 로직 문제로 실패한 경우, 응답의 `isError` 필드가 `true`로 설정된 결과가 돌아온다. 모델은 이 메시지를 읽고 사용자에게 상황을 설명하거나 다른 접근을 시도할 수 있다.


이 두 경로를 구분하면, 클라이언트 측에서 프로토콜 오류는 바로 보고하고, 실행 오류는 모델에게 판단을 위임하는 식으로 처리를 나눌 수 있다.


## 추가 확인 항목


도구는 MCP 서버가 노출하는 세 가지 기능 중 하나에 불과하다. 리소스(resources)는 모델이나 사용자가 참조할 데이터를, 프롬프트(prompts)는 미리 정의된 대화 템플릿을 제공한다.


도구, 리소스, 프롬프트를 한 서버에서 함께 제공하는 구성과 서버가 클라이언트에 샘플링을 요청하는 역방향 흐름은 다음 주제로 남겼다. 각각의 호출 조건과 필요한 문맥 범위를 이어서 살펴볼 수 있다.
