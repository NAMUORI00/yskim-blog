사용자가 "날씨를 알려줘"라고 입력했을 때 대규모 언어 모델(LLM)은 날씨 조회 도구를 쓰겠다고 답할 수 있다. 하지만 모델은 입력된 문맥에 이어질 텍스트를 생성하는 프로세스여서, 직접 파일 시스템에 접근하거나 외부 서버와 HTTP 연결을 맺지 못한다. 실제 날씨 API에 TCP 연결을 여는 코드는 모델 바깥에 있어야 한다. 도구 호출을 제안하는 단계와 실제로 실행하는 단계를 분리하면, 어떤 도구의 실행을 허용할지와 실행 결과를 어떻게 다룰지 나누어 통제할 수 있다. 모델이 의도하지 않은 동작을 요청하는 문제와 실행 결과를 잘못 해석하는 문제도 서로 다른 단계에서 점검하게 된다.


**MCP**(Model Context Protocol)는 모델과 외부 실행 코드 사이의 경계를 프로토콜 수준에서 정의한 규격이다. 모델은 호출할 도구와 도구에 넘길 입력값인 인자(argument)만 제안하고, 실제 실행과 연결 관리는 호스트, 클라이언트, 서버의 세 계층이 나누어 맡는다. 계층끼리는 원격 호출 규격인 JSON-RPC 2.0 메시지로 통신하며, 각 계층의 책임이 명세에 고정되어 있어 구현체마다 역할이 섞이는 일을 줄인다. 이 글에서는 MCP 2025-06-18 버전 명세를 기준으로 구성 요소의 역할과 도구 호출 과정, 역할 분리의 경계, 오류 처리 경로를 정리한다.


## 호스트, 클라이언트, 서버, 도구의 역할


모델 바깥에서 연결과 실행을 처리하기 위해 MCP는 사용자 애플리케이션부터 실제 실행 함수까지를 네 가지 구성 요소로 나눈다. 사용자가 직접 마주하는 Claude Desktop이나 AI 기능을 탑재한 통합 개발 환경(IDE) 같은 애플리케이션을 **호스트**(Host)라고 부른다. 호스트는 전체 대화 기록을 혼자 보관하며, 도구를 실행하기 전에 사용자에게 승인을 요청하고 내부에서 여러 클라이언트 인스턴스를 생성해 관리한다. 호스트 내부에서 생성되는 **클라이언트**(Client)는 특정 서버 하나와 1:1 연결인 세션을 유지하는 커넥터다. 호스트 하나에 클라이언트를 여러 개 둘 수 있지만, 각 클라이언트는 자신이 연결된 서버와만 통신하며 서버별 연결 경계를 유지한다. 다만 프로토콜이 정의하는 것은 세션 연결뿐이므로, 운영체제와 네트워크의 실제 접근 권한은 프로토콜 연결과 별도로 설정해야 한다.


클라이언트 건너편에서 파일 시스템 접근, 데이터베이스 질의, 외부 API 호출처럼 각자 맡은 작업에 집중하는 서비스가 **서버**(Server)다. 서버는 도구, 리소스, 프롬프트 템플릿 같은 기능을 외부에 노출하며, 작업에 필요한 문맥만 전달받도록 설계된다. 실제로 서버에 어떤 문맥을 어디까지 전달하는지는 호스트 구현과 권한 설정에서 따로 확인해야 한다. 서버가 노출하는 기능 가운데 실제로 실행할 수 있는 함수를 **도구**(Tool)라고 한다. 도구는 이름과 설명, 인자의 데이터 구조를 정의한 입력 스키마(JSON Schema)로 구성되며, 모델은 이 정의를 읽고 호출할 도구와 인자를 판단한다. 예를 들어 호스트 하나가 클라이언트 두 개를 통해 파일 시스템 서버와 날씨 API 서버에 각각 1:1로 연결되면, 각 서버는 자신이 담당하는 도구만 노출한다.

## 도구 조회부터 결과 반환까지의 과정


클라이언트와 서버가 세션을 초기화하고 사용할 기능을 맞춘 뒤, 사용자가 "뉴욕 날씨를 알려줘"라고 입력했을 때 요청과 응답이 오가는 과정은 네 단계로 이어진다. 먼저 세션을 초기화할 때 클라이언트가 서버에 `tools/list` 요청을 보내 사용할 수 있는 도구 목록을 조회한다. 서버는 자신이 노출하는 도구의 이름, 설명, 입력 스키마를 응답으로 돌려준다.


```json
{ "jsonrpc": "2.0", "id": 1, "method": "tools/list", "params": {} }
```


다음으로 호스트가 사용자의 질문과 서버에서 받은 도구 목록을 함께 LLM에 전달한다. 모델은 텍스트 생성 결과의 일부로 `get_weather` 도구를 `location=New York` 인자로 호출하겠다는 의사를 출력한다. 이 시점에는 모델이 호출 형태만 제안했을 뿐 실제 실행은 일어나지 않은 상태다.


모델의 제안을 받은 뒤 개별 승인이 필요한 정책을 쓰는 환경이라면, 호스트가 먼저 권한과 사용자 승인을 확인한다. 승인이 떨어지면 클라이언트가 서버에 `tools/call` 요청을 보내 실제 도구를 호출한다.


```json
{ "jsonrpc": "2.0", "id": 2, "method": "tools/call",
  "params": { "name": "get_weather", "arguments": { "location": "New York" } } }
```


마지막으로 서버는 외부 날씨 API를 실제로 호출한 뒤 그 결과를 클라이언트에 돌려준다. 결과는 클라이언트에서 호스트를 거쳐 다시 모델로 전달되며, 모델은 이 결과를 받아 사용자에게 보여 줄 최종 응답을 생성한다. 이 과정에서 모델의 호출 제안과 클라이언트의 실행 요청 사이에는 호스트의 권한과 승인 확인 단계가 자리한다. 승인이 거절되면 호스트는 서버의 도구를 실행하지 않고 곧바로 안내를 반환한다.

## 역할 분리와 통제 경계


앞서 본 호출 과정처럼 구성 요소를 호스트, 클라이언트, 서버로 나누면 실행 승인과 문맥 전달, 사용 기능을 각각 어느 위치에서 통제할지 분명해진다. 먼저 모델이 파일 삭제 도구를 호출하겠다고 판단하더라도, 호스트가 사용자 승인 없이 요청을 넘기지 않으면 위험한 동작은 실행 전에 차단된다. 이처럼 호스트가 실행 여부를 가로막는 보안 경계를 맡으며, MCP 명세도 민감한 작업을 실행할 때는 사용자 확인을 요청해야 한다(SHOULD)고 권고한다.


파일 서버와 데이터베이스 서버는 서로 다른 클라이언트를 통해 연결되므로, 호스트는 한 서버의 결과가 다른 서버로 넘어가는 문맥 전달을 중간에서 통제해 서버를 격리한다. 그러나 프로토콜 연결이 분리되어 있다고 해서 시스템 자원의 접근까지 자동으로 막히지는 않는다. 서버 프로세스들이 공유 파일이나 자격 증명, 네트워크 권한을 함께 쓰고 있다면 프로토콜 바깥에서 별도의 접근 경로가 생길 수 있기 때문이다.


세션이 시작될 때는 서버와 클라이언트가 각자 지원하는 기능(capability)을 서로 선언하는 기능 협상(capability negotiation)을 거친다. 예를 들어 도구를 제공하는 서버는 `tools` 기능을 선언하고, 서버로부터 LLM 생성 요청을 받을 수 있는 클라이언트는 `sampling` 기능을 선언한다. 초기화 단계에서 선언하지 않은 기능은 해당 세션에서 호출할 수 없으므로 예상 밖의 동작이 줄어든다.

## 프로토콜 오류와 실행 오류의 구분


기능 협상과 승인을 거쳐 도구를 호출하더라도 오류가 발생할 수 있는데, MCP는 오류를 두 계층으로 나누어 반환 형식과 처리 주체를 다르게 둔다. 서버에 존재하지 않는 도구 이름을 요청하거나 입력 스키마와 맞지 않는 인자 형식을 보냈을 때 나타나는 것이 **프로토콜 오류**다. 이때 서버는 JSON-RPC 표준 에러를 반환하는데, 같은 요청을 그대로 다시 보내도 해결되지 않는 경우가 많다. 따라서 도구 이름이나 인자 형식을 바로잡아 다시 요청해야 복구할 수 있다.


반면 요청 형식이 올발라 도구가 정상적으로 호출되었더라도, 외부 API 장애나 비즈니스 로직 조건 때문에 작업이 실패하면 **실행 오류**로 다룬다. 이때는 JSON-RPC 호출 자체는 성공으로 처리하되, 응답 결과 안에 `isError` 필드를 `true`로 설정해 오류 내용을 담아 돌려준다. 모델은 이 오류 메시지를 읽고 사용자에게 실패 원인을 설명하거나 다른 도구와 인자로 우회하는 시도를 할 수 있다. 두 경로를 구분하면 클라이언트는 프로토콜 오류를 즉시 감지해 호출 코드 수준에서 보고하고, 실행 오류는 결과 문맥에 담아 모델에 다음 판단을 맡길 수 있다.

## 결론


MCP는 텍스트만 생성하는 모델의 호출 제안과 모델 바깥의 실제 실행을 분리하기 위해 호스트, 클라이언트, 서버, 도구로 역할을 나눈다. 명세에서 확인한 것처럼 `tools/list`와 `tools/call` 호출 흐름에는 호스트의 승인 확인과 클라이언트별 1:1 연결, 기능 협상이 통제 경계로 작동한다. 오류가 발생했을 때도 요청 형식이 틀린 프로토콜 오류는 클라이언트가 즉시 처리하고, 작업이 실패한 실행 오류는 결과에 담아 모델이 다음 동작을 판단하게 한다.


다만 명세는 세션 연결과 메시지 형식만 정의하므로, 호스트의 실제 문맥 전달 범위나 운영체제 수준의 자원 격리는 구현 환경에서 따로 확인해야 한다. 또한 이 글에서 다룬 도구는 MCP 서버가 노출하는 세 가지 기능 가운데 하나다. 서버는 도구 외에도 모델이나 사용자가 참조할 데이터를 건네는 리소스(resources)와 미리 정의된 대화 템플릿인 프롬프트(prompts)를 함께 제공할 수 있다. 한 서버에서 세 기능을 함께 노출할 때 각 기능을 언제 호출하는지는 별도로 구분해야 한다. 세 기능의 호출 시점과 서버가 클라이언트에 역방향으로 모델 생성을 요청하는 샘플링(sampling)의 문맥 전달 범위는 다음 주제로 이어서 다룬다.
