## 오디오 처리의 시간 기준


파형, 샘플링 개념을 모델 입력과 특징 프레임, 출력 파형에 연결해 정리했다. 16kHz로 기록한 1초의 오디오를 48kHz로 다루는 예제에서 샘플 수와 재생 시간을 함께 계산했다.


여기서는 Applio의 음성 변환 코드와 MsstDocker의 실행 구성을 나누어 읽었다. 하나는 파형과 특징을 변환하는 계산 경로이고, 다른 하나는 음원 분리 도구가 사용할 파일과 실행 환경을 준비하는 구성이다. 두 저장소를 하나의 연결된 서비스로 가정하지 않았다.


## 샘플 수와 재생 길이


1초짜리 신호를 16kHz로 표현하면 16,000개 샘플이 된다. 이를 그대로 두고 파일에 48kHz라고만 적으면 재생 길이는 16,000÷48,000, 약 0.333초가 된다. 반면 올바르게 리샘플링해서 48,000개 샘플을 만들면 길이 1초를 유지할 수 있다. 샘플레이트를 바꾸는 일과 메타데이터 값만 바꾸는 일이 다른 이유다.


Applio의 [`Pipeline`](https://github.com/NAMUORI00/Applio/blob/70f5f8be1fc247c2fee2bd5a83254f71fdebd55c/rvc/infer/pipeline.py)은 내부 기준으로 16kHz와 160샘플 윈도우를 사용한다.


160÷16,000은 0.01초이므로 이 기준에서는 10ms 간격으로 해석할 수 있다. 출력 기준 `tgt_sr`는 별도 인자로 전달되고, 패딩을 제거할 길이도 입력과 출력 기준으로 따로 계산한다.


파이프라인의 상수에서 확인한 범위는 내부 기준이다. 파일 로더의 변환과 호출자가 제공하는 샘플레이트, 채널 구성은 호출 경로에서 따로 확인할 항목이다.


[librosa의 오디오 로딩 문서](https://librosa.org/doc/0.11.0/generated/librosa.load.html)처럼 라이브러리마다 기본 리샘플링과 모노 변환 동작도 다르므로 기본값을 생략한 호출을 주의해서 읽게 됐다.


## 피치와 내용 특징은 병렬 입력


코드의 `get_f0`는 음높이의 기초가 되는 F0를 추정하고, 조정된 연속값과 정수 버킷을 반환한다. F0를 멜 스케일로 옮기는 식은 `1127 × log(1 + f0/700)`이다. 이 코드의 하한 50Hz, 상한 1100Hz를 적용하면 멜 값은 각각 약 77.75와 1064.41이다.


440Hz의 멜 값은 약 549.64이므로 `(549.64−77.75)×254/(1064.41−77.75)+1`은 약 122.48이다. 코드의 반올림을 거치면 버킷 122가 된다. 버킷 번호가 소리의 실제 주파수는 아니며, 모델이 받는 피치 표현 중 하나다. 경계 밖 값은 1~255 범위로 제한된다.


내용 특징과 피치는 오디오에서 각각 얻는 입력으로 나누었다. `voice_conversion`은 추출한 특징과 별도의 피치 정보를 사용한다. F0에서 음성 내용이 만들어지는 흐름으로 읽히지 않도록 그림에서도 두 경로를 분리했다.

## 검색 특징과 평가 근거


`_retrieve_speaker_embeddings`는 특징마다 이웃 8개를 검색하고, 반환된 거리 값의 역수 제곱을 정규화해 이웃 특징을 합친다. 이후 `index_rate`로 원래 특징과 섞는다. 이 혼합 단계에서 0은 원래 특징 쪽, 1은 검색 특징 쪽 가중치를 뜻한다. 검색 특징을 섞은 뒤에도 보호 처리와 합성 단계가 이어진다.


FAISS의 거리 계산은 각 색인에 설정된 거리 함수와 자료구조를 기준으로 확인한다. 또한 검색하는 벡터는 음성 모델에서 얻은 특징이다. 벡터 검색이라는 이유로 학습되지 않은 표현이라고 부를 수 없다. [FAISS 문서](https://faiss.ai/index.html).


확인한 역수 계산에는 거리가 0인 경우를 위한 작은 상수 보정이 보이지 않는다. 완전히 같은 특징이나 유효하지 않은 이웃이 들어오면 어떤 값이 나오는지 살펴볼 지점이다. 수식에서 요구하는 입력 조건을 코드와 대조했다.


## 계산 결과가 파일로 남는 경로


[MsstDocker의 Dockerfile](https://github.com/NAMUORI00/MsstDocker/blob/70733f0285178fbb39fae0d8c7f925f174d322d8/Dockerfile)은 Python과 ffmpeg, PyTorch 및 MSST-WebUI 소스를 준비한다.


[Compose 설정](https://github.com/NAMUORI00/MsstDocker/blob/70733f0285178fbb39fae0d8c7f925f174d322d8/docker-compose.yml)은 모델과 출력 폴더를 호스트에 연결하고 GPU 장치를 요청한다. 그림은 실행에 필요한 배치를 나타내며, 다운로드 완료와 추론 성공은 실행 로그로 확인한다.

마지막 파형 처리에서는 최댓값을 기준으로 전체 크기를 줄이는 연산을 확인했다. 샘플을 개별적으로 자르는 클리핑과는 다르다. 길이, 샘플레이트, 채널, 비정상 수치, 파형 크기는 출력 형식의 확인 항목으로, 변환과 분리 품질은 별도 청취, 평가 범위로 두었다.


실시간 버퍼의 경계 처리와 배치 처리의 차이는 다음 주제로 남겼다. 겹치는 구간과 패딩이 연결부에 미치는 영향을 비교할 수 있다. Applio는 원본 프로젝트의 포크다. 이 글은 변환 구조를 다루며, 사용자 고유 변경 범위는 별도 이력 대조가 필요하다.
