항공우주 분야 문서를 다루는 질문 답변 시스템에 "이 위성의 발사 시점은 언제인가"를 물으면 위성 이름과 날짜가 한자리에 적힌 대목을 찾아야 한다. "탑재체가 어떤 관측을 수행하는가"라는 질문에는 기능을 풀어 쓴 설명이 필요하고, 표에서 찾은 수치는 행과 열 제목이 빠지는 순간 값의 맥락이 사라진다. 이처럼 위성 이름이나 모델 번호, 수치의 단위, 적용 시기가 맞물려 있어서 검색된 문장에 숫자가 적혀 있더라도 그 값만 떼어 내면 근거로 쓰기 어렵다. 어느 문서의 어떤 조건에서 나온 값인지 원문까지 따라갈 수 있어야 답변을 믿을 수 있다.


질문과 관련된 문서를 먼저 찾아 언어 모델의 입력에 넣어 주는 방식을 검색 증강 생성, 곧 **RAG**(Retrieval-Augmented Generation)라 부른다. 문서 내용이 바뀌었을 때 모델을 다시 학습하는 대신 검색 색인만 갱신할 수 있다는 이점이 있다. 다만 항공우주 문서는 정확한 고유명사와 풀어 쓴 기능 설명이 섞여 있어서 한 가지 검색 방식만으로는 부족하기 쉽다. 위성 이름이나 모델 번호는 단어가 정확히 일치해야 잘 찾아지고, 기능을 묻는 질문은 다른 표현으로 적힌 문장까지 후보로 넓혀야 하기 때문이다. 문제는 여러 검색 경로를 합칠 때 각 결과가 원본 문서의 어디에서 나왔는지 흐려지기 쉽다는 점이다. `aerospace-rag` 저장소는 잘게 나눈 문서 조각인 **청크**(chunk)마다 공통 식별자를 부여해 검색부터 답변 출처 반환까지 원문 위치를 추적한다. 이런 설계 때문에 코드를 읽을 때도 검색 방식보다 출처 경로를 먼저 따라갔다.

## 공통 청크 식별자와 원문 위치 정보의 분리


여러 검색 경로의 결과를 합치면서도 원문 위치를 잃지 않으려면, 문서를 나눌 때부터 시스템용 식별자와 사람용 위치 정보를 함께 남겨야 한다. `aerospace-rag`의 파이프라인은 색인을 만드는 단계와 질문을 처리하는 단계로 나뉜다. 먼저 `build_index()` 함수가 문서를 수집하고 청크 단위로 쪼개 로컬 색인을 만든다. 그다음 `ask()` 함수가 질문에 맞는 검색 결과를 모아 답변 생성기에 전달하고, 각 결과에서 출처 정보 객체인 `SourceRef`를 조립한다. `SourceRef`에는 식별자와 자료 형식, 점수, 경로를 담는 `chunk_id`, `modality`, `score`, `channels` 필드가 있다. 여기에 원문 위치를 가리키는 `source_file`, `excerpt`, `page`, `sheet`, `row` 필드가 함께 담긴다. 모든 문서에 페이지(`page`), 시트(`sheet`), 행(`row`) 정보가 동시에 들어가는 것은 아니며, 본문 문서나 표 같은 자료 형식에 맞는 위치 필드를 채운다. 이 두 단계의 전체 흐름은 [파이프라인 코드](https://github.com/NAMUORI00/aerospace-rag/blob/ac33be02be2ba6262b2529d0d663e46c1dbac228/aerospace_rag/pipeline.py)에서 확인할 수 있다.


이 필드들은 시스템 내부에서 결과를 묶는 식별자와 사람이 원문을 찾아가는 위치 정보로 역할이 나뉜다. `chunk_id`는 서로 다른 검색 채널이 같은 문서 조각을 찾아냈는지 판별하는 연결점이다. 서로 다른 두 검색 채널이 동일한 청크를 반환하면, `chunk_id`를 기준으로 각 채널의 기여도와 탐색 경로(`channels`)를 하나로 합칠 수 있다. 반면 사람이 답변의 근거를 검토할 때는 `chunk_id`만으로는 원문을 찾을 수 없다. 원본 파일 이름(`source_file`)과 발췌문(`excerpt`), 페이지나 시트, 행 번호가 이어져야 문서의 해당 위치로 돌아가 수치의 앞뒤 조건을 대조할 수 있다.

## 검색 채널 구성과 스키마에 정의된 경로의 구분


공통 청크 위에서 동작하는 현재 파이프라인의 검색 구성은 응답 부가 정보인 메타데이터에 `qdrant+bm25+graph-lite`로 기록된다. 그중 Qdrant는 자료를 숫자 배열인 벡터로 저장해 유사도를 비교한다. **BM25**는 질문을 쪼갠 단어 조각인 토큰이 문서에 얼마나 자주, 중요하게 등장하는지를 계산하는 키워드 검색 알고리즘이다. 여기에 문서 안의 가벼운 관계 정보를 활용하는 보강 경로인 `graph-lite`가 더해진다. 반면 결과를 합치는 융합 계층 스키마는 `vector_dense_text`, `vector_sparse`, `vector_image`, `graph`의 네 정규 채널을 정의한다. 스키마의 채널 이름만 보면 텍스트와 이미지, 그래프 검색이 모두 완비된 것처럼 보이지만 실제 구현 범위와는 구분해서 읽어야 한다.


먼저 현재 기본 가중치 설정과 자체 보정 후보에서 `vector_image` 채널의 가중치는 `0`이다. 융합 계층이 이미지 검색 결과를 받을 수 있도록 입력 통로는 열어 두었지만, 이미지에서 특징 값을 추출해 검색 데이터를 만드는 구현은 분리되어 있다. 멀티모달 RAG를 정리한 Mei 외(2025)의 [논문](https://arxiv.org/abs/2504.08748)([CC BY 4.0](https://creativecommons.org/licenses/by/4.0/))에서는 이미지와 표를 텍스트로 변환해 검색하는 구조를 MRAG1.0으로 분류한다. 이러한 문헌의 분류와 자체 프로젝트의 실제 구현도는 구분해서 읽어야 한다. `graph-lite` 역시 별도의 대규모 그래프 데이터베이스를 띄우는 구성이 아니다. 마이크로소프트가 그래프 기반 질의와 요약을 구현한 [Microsoft GraphRAG 프로젝트](https://www.microsoft.com/en-us/research/project/graphrag/)와 같은 수준으로 부르면, 그래프 구축에 드는 처리 단계와 운영 비용이 가려진다. `aerospace-rag`의 `graph-lite`는 저장소 문서 안에서 구현된 경량 범위에서만 동작한다. Microsoft GraphRAG의 질의 방식과 평가 도구는 추후 확장 방향을 검토하기 위한 참고 자료로 삼았다.

## 학습된 의미 임베딩과 해시 벡터의 차이


실제로 켜져 있는 벡터 검색 채널인 `vector_dense_text`도 내부에서 벡터를 어떻게 만드는지 코드까지 들어가 봐야 정확한 성격을 알 수 있다. 텍스트를 고정 길이 숫자 배열로 바꾸는 **임베딩**(embedding) 과정에서 현재 `EmbeddingService`는 `hash` 백엔드만 허용하며 기본 차원은 `384`다. 구체적인 벡터 변환 로직은 [임베딩 코드](https://github.com/NAMUORI00/aerospace-rag/blob/ac33be02be2ba6262b2529d0d663e46c1dbac228/aerospace_rag/retrieval/embeddings.py)에 정의되어 있다. 이 방식은 텍스트의 단어 토큰을 해시 함수로 계산해 `384`차원 벡터의 각 위치에 배치한다. 외부에서 무거운 언어 모델 가중치를 내려받지 않아도 되고, 같은 입력을 넣으면 언제나 똑같은 벡터를 재현할 수 있다는 장점이 있다.


하지만 이 해시 벡터는 문맥과 동의어를 학습한 신경망 기반의 의미 임베딩과는 동작 원리가 다르다. 고정된 크기의 해시 버킷에 토큰을 배치하다 보면 서로 다른 단어가 같은 위치에 들어가는 해시 충돌도 허용된다. 따라서 벡터 유사도 점수가 높게 나왔다고 해서 두 문장의 의미가 비슷하다고 판단하기는 어렵다. 흔히 "벡터 검색"과 "의미 검색"을 같은 뜻으로 쓰곤 하지만, 두 개념이 가리키는 범위는 다르다. 벡터 검색은 자료를 고정 길이 벡터로 표현해 내적이나 코사인 유사도로 비교하는 연산 형태를 뜻한다. 반면 의미 검색은 그 벡터 표현이 단어와 문맥의 의미 관계를 학습했는지까지 포함한다. 벡터 저장소 이름이나 차원 수만 보지 않고 벡터 생성 코드를 함께 확인한 이유도 이 차이를 분명히 해 두기 위해서였다. 현재 해시 벡터와 BM25는 모두 단어 토큰이 겹치는 정도에 크게 의존한다. 의미 임베딩 모델로 교체하기에 앞서, 두 채널이 같은 질문셋에서 실제로 얼마나 다른 문서를 찾는지 먼저 비교하고 교체 효과를 측정할 필요가 있다.


## 답변 생성 흐름과 출처 검증의 경계


각 채널에서 찾아낸 청크들이 답변으로 조립되는 `ask()` 함수는 문서 검색, 생성 제공자 선택, 답변 생성, 출처 조립 순서로 실행된다. 기본 답변 생성기는 vLLM을 사용하며, 생성 모델 없이 검색된 내용을 추려 내는 추출식 응답은 명시적인 별도 경로로 분리되어 있다. 검색과 생성 단계가 나뉘어 있어서 원하는 답이 나오지 않았을 때 문서를 못 찾은 것인지, 모델이 문맥을 잘못 읽은 것인지 실패 위치를 나누어 추적할 수 있다.

다만 현재 파이프라인의 출처 반환이 보장하는 범위에는 경계가 있다. 파이프라인은 검색된 청크들을 `SourceRef` 목록으로 묶어 답변과 함께 돌려주지만, 이 목록이 곧 답변의 모든 문장을 보증하지는 않는다. RAG 시스템의 응답이 믿을 만한지 확인하려면 세 가지를 따져 봐야 한다. 먼저 질문에 필요한 자료 조각을 찾았는지 확인하고, 그 조각이 위성 이름이나 시기, 표의 행과 열 제목처럼 질문이 요구한 조건을 온전히 담고 있는지 봐야 한다. 마지막으로 모델이 생성한 문장이 그 자료의 범위 안에 머무는지도 점검해야 한다. 이 가운데 표 데이터에서 추출한 수치가 원래 표의 행과 열 제목 정보를 잃지 않고 보존되는지는 따로 확인해야 한다. 내부 데이터가 아닌 독립된 질문셋으로 검색된 근거의 적합성을 평가하고, 답변의 개별 주장과 청크의 원문 문장을 일대일로 대조하는 검증도 현재 파이프라인 바깥에 남아 있다.


## 결론


`aerospace-rag`는 공통 청크 식별자인 `chunk_id`와 `SourceRef` 객체로 다중 검색 결과를 묶고 원본 문서의 위치까지 연결한다. 이 출처 구조를 고정해 두면 내부 검색 엔진이나 임베딩 모델을 바꾸더라도 원문 추적 경로를 유지한 채 검색 품질을 비교할 수 있다. 이번 코드 검토에서는 `qdrant+bm25+graph-lite` 검색 경로와 `384`차원 `hash` 벡터의 실제 구현 범위를 확인했다. 또한 `ask()` 함수가 검색과 답변 생성을 분리해 파일명과 페이지, 시트, 행 정보를 담은 `SourceRef`를 조립하는 흐름을 따라갔다.


반면 이번 코드 검토를 마친 시점에서 후속 실험과 구현으로 남겨 둔 과제도 있다. 해시 벡터와 BM25가 같은 질문셋에서 얼마나 다른 문서를 찾는지 비교해 의미 임베딩 교체 효과를 측정하는 실험과, 표 수치의 행과 열 제목 보존 여부 점검이 필요하다. 스키마에만 정의된 `vector_image` 채널의 실제 이미지 검색 구현과, 독립된 질문셋 기반의 근거 적합성 평가 및 문장 단위 대조 검증도 남아 있다. 코사인 유사도 계열의 벡터 점수와 BM25 점수는 척도와 단위가 달라 그대로 더할 수 없다. 다음 글에서는 점수 대신 채널별 순위를 합치는 **가중 RRF**(Reciprocal Rank Fusion) 방식과 내부 가중치 보정 결과를 독립 평가와 구분하는 방법을 다룬다.
