항공우주 RAG에서는 분야 문서를 검색하고 답변의 출처로 연결하는 구조를 다뤘다. 수치와 단위, 적용 시점이 중요한 자료여서 검색 채널을 결합하는 과정에서도 공통 청크 식별자로 원문을 추적하도록 구성했다.


## 구현과 확인 과정


aerospace-rag의 코드를 읽으며 검색 구조와 출처 관리를 살펴봤다. 항공우주 자료는 이름, 단위, 적용 시기가 중요해서, 검색된 문장에 수치가 있더라도 어느 문서의 어떤 조건에서 나온 값인지 원문까지 따라갈 수 있어야 근거로 쓸 수 있다. 이 저장소에서는 공통 청크 식별자가 그 연결의 시작점이었고, 검색 방식보다 출처 경로를 먼저 따라갔다.


![04-hybrid-roles.png](/images/notion/aerospace-rag-hybrid-retrieval/image-1.png)


그림 1. 공통 청크를 기반으로 벡터, 키워드 검색과 경량 그래프 보강을 결합하는 흐름. 현재 해시 임베딩 구현은 학습된 의미 임베딩과 구분된다.


## 문서 특성과 검색 조건


위성 이름이나 모델 번호를 찾는 질문은 정확한 단어 일치가 중요하다. 기능을 풀어 쓴 질문에서는 다른 표현으로 적힌 설명도 후보가 된다. 여러 검색 채널을 검토할 이유를 이 차이에서 생각해 볼 수 있었다. 다만 현재 해시 벡터가 BM25와 얼마나 다른 자료를 찾는지는 같은 질문셋으로 비교할 부분이 남아 있다.


## 검색 근거를 이용한 답변 생성


RAG는 검색한 자료를 모델의 입력 문맥에 넣는 구조다. 문서가 바뀌면 모델을 다시 학습하는 대신 검색 색인만 갱신할 수 있다. 이 구조에서도 두 가지 확인은 남는데, 필요한 자료를 찾았는지와 생성한 문장이 그 자료를 올바르게 반영했는지다.


예를 들어 "이 위성의 발사 시점은 언제인가"에는 위성 이름과 날짜가 함께 있는 부분이 필요하고, "탑재체가 어떤 관측을 수행하는가"에는 기능 설명이 필요하다. 표에서 찾은 수치라면 값만 분리하면 행, 열 제목이 빠져서 맥락이 사라진다.


## 검색 결과에 원문 위치를 함께 남기기


`build_index()`는 문서를 수집하고 분할한 뒤 로컬 인덱스를 구축한다. `ask()`는 검색 결과를 답변 생성기에 전달하고, 각 결과에서 `SourceRef`를 만든다.


이 객체에는 `chunk_id`, `source_file`, `modality`, `score`, `excerpt`, `page`, `sheet`, `row`, `channels`가 전달된다. 모든 문서에 페이지, 시트, 행이 동시에 존재하는 것은 아니며, 자료 형식에 맞는 위치 정보를 사용한다.


여기서 `chunk_id`는 여러 검색 결과가 같은 자료 조각을 가리키는지 판단하는 연결점이다. 키워드 검색과 벡터 검색이 같은 청크를 반환하면 그 청크의 기여를 합칠 수 있다. 원본 파일과 위치 정보는 독자가 근거로 되돌아가는 경로다.


식별자는 중복을 합치는 기준이 되지만, 사람이 내용을 검토할 때는 원문의 위치까지 이어져야 해당 문장을 찾아볼 수 있겠다고 보았다. [파이프라인 코드](https://github.com/NAMUORI00/aerospace-rag/blob/ac33be02be2ba6262b2529d0d663e46c1dbac228/aerospace_rag/pipeline.py)


## 검색 채널의 구성과 역할


현재 파이프라인이 응답 메타데이터에 기록하는 검색 구성은 `qdrant+bm25+graph-lite`다. Qdrant는 벡터의 저장과 유사도 검색을 담당하고, BM25는 질의에 포함된 토큰이 문서에 어떻게 등장하는지를 이용한다. graph-lite는 경량 관계 정보를 활용하는 보강 경로다. 대규모 그래프 데이터베이스를 띄우는 구성과는 구분된다.


융합 계층에는 `vector_dense_text`, `vector_sparse`, `vector_image`, `graph`라는 네 개의 정규 채널 이름이 있다. 하지만 스키마에 이미지 채널이 있다는 사실만으로 학습된 이미지 임베딩 검색이 구현되어 있다고 볼 수는 없다.


현재 기본 가중치와 자체 보정 후보에서 `vector_image`의 가중치는 0이다. 채널을 받을 수 있는 인터페이스는 정의되어 있지만, 실제 이미지 검색 데이터를 생성하는 구현과는 분리되어 있었다.


Microsoft GraphRAG는 그래프 기반 질의와 요약을 연구, 구현하는 별도의 프로젝트다. aerospace-rag의 graph-lite를 같은 구현으로 부르면 필요한 처리 단계와 운영 비용이 가려진다.


이 저장소의 경량 그래프는 문서에 구현된 범위에서 사용하며, GraphRAG의 검색, 질의 방식과 평가 도구는 확장 방향을 검토할 참고 자료로 삼았다. [Microsoft GraphRAG 프로젝트](https://www.microsoft.com/en-us/research/project/graphrag/)


## 학습 모델 대신 해시로 벡터 만들기


`EmbeddingService`는 현재 `hash` 백엔드만 허용하며 기본 차원은 384다. 텍스트의 토큰을 고정 길이 벡터에 해시로 배치한다. 모델 가중치를 내려받지 않고 같은 입력을 재현할 수 있다는 장점이 있지만, 동의어나 문맥을 학습한 임베딩과는 성격이 다르다.


[임베딩 코드](https://github.com/NAMUORI00/aerospace-rag/blob/ac33be02be2ba6262b2529d0d663e46c1dbac228/aerospace_rag/retrieval/embeddings.py)


해시 버킷에는 서로 다른 토큰이 같은 위치에 들어가는 충돌도 허용된다. 그래서 높은 검색 점수만으로 의미가 같다고 판단하기는 어려웠다. “벡터 검색”은 비교에 사용하는 표현과 연산의 형태를, “의미 검색”은 그 표현이 어떤 관계를 학습했는지까지 포함한다. 이 차이를 확인하기 위해 저장소 이름이나 벡터 차원과 함께 벡터를 만드는 코드를 읽었다.


여기까지 수집한 자료가 검색과 출처 반환으로 이어지는 구조를 확인했다. 의미 임베딩으로 교체했을 때의 효과는 별도 실험으로 남아 있다. BM25와 해시 벡터는 모두 토큰 겹침에 상당 부분 의존하고 있어, 교체에 앞서 두 채널이 실제로 얼마나 다른 자료를 찾는지 비교할 항목으로 남겼다.


## 생성과 출처 반환까지 이어지는 흐름


`ask()`의 실행 순서는 검색, 생성 제공자 선택, 답변 생성, 출처 조립으로 이어졌다. 기본 생성 구성은 vLLM을 사용하고, 추출식 응답은 명시적인 별도 경로로 두고 있었다. 실패 위치를 확인할 때도 검색 성공 여부와 모델의 생성 성공 여부를 나누어 볼 수 있는 구조였다.


현재 파이프라인은 검색된 청크를 출처로 연결하고 있었다. 이 목록만으로 답변의 모든 문장이 뒷받침되는지까지 확인되지는 않는다. 더 엄격하게 검토하려면 답변의 주장과 해당 청크의 문장을 대조하는 과정이 남는다. 자료를 찾았는지, 그 자료가 질문에 답하는지, 생성한 문장이 그 범위 안에 머무는지를 각각 확인 항목으로 정리했다.


## 검색 품질과 출처 연결의 후속 검토


청크 식별자와 출처 구조가 유지되면 검색 채널을 바꾸더라도 같은 연결점에서 비교를 시작할 수 있다. 의미 임베딩 교체 효과, 표의 위치 정보 보존, 이미지 검색 경로, 독립 질문셋의 근거 적합성은 아직 확인하지 않은 항목이다.


다음 주제는 채널별 점수의 단위가 다른 문제다. cosine 계열 점수와 BM25 점수를 그대로 더하는 대신 순위를 사용하는 가중 RRF, 그리고 내부 보정 결과를 독립 평가와 구분하는 방법을 다룬다.
