긴 문서를 검색할 때는 문서를 작은 조각인 **청크**(chunk)로 잘라 둔다. 단어를 대조하는 키워드 검색과 뜻을 비교하는 벡터 검색에 그래프 검색까지 함께 쓰면, 같은 청크가 채널마다 다른 순위와 점수로 돌아온다. [앞 글](https://blog.namuori.net/posts/aerospace-rag-hybrid-retrieval/)에서는 여러 검색 채널의 결과를 합치기 위해 공통 청크 식별자를 맞추는 구조를 다뤘다. 식별자를 맞춘 뒤에는 점수 기준이 서로 다른 결과를 어떻게 합칠지, 또 채널별 비중인 가중치를 언제 어떻게 정할지 결정해야 한다.


`aerospace-rag`는 점수 대신 순위에 비중을 곱해 더하는 **가중 RRF**(weighted Reciprocal Rank Fusion)로 최종 순서를 정한다. 여기에 쓰는 채널 가중치는 검색 색인인 **인덱스**(index)를 만들 때 임시 질문으로 미리 보정해 파일로 저장해 둔다. 그 뒤 실제 질문이 들어오면 질문 유형과 채널별 검색 결과 수에 따라 가중치를 다시 조정한다.

## 순위 기반 결합과 가중 RRF 계산


앞서 말한 가중 RRF가 왜 점수 대신 순위를 쓰는지부터 확인한다. 여러 검색기의 결과를 합칠 때는 각 검색기가 내놓는 원래 점수의 범위를 맞춰 더하는 방법과, 점수는 채널 안에서 줄을 세우는 데만 쓰고 순위만 합치는 방법이 있다. 검색기마다 점수가 퍼져 있는 모양과 기준이 달라서 현재 코드는 순위를 기준으로 합치는 방식을 쓴다. 점수 기준을 직접 맞추는 부담은 줄어들지만, 같은 채널 안에서 1위와 2위 사이에 있던 원래 점수 차이는 사라진다. 두 방식 가운데 어느 쪽이 이 문서 집합에 더 나은지는 같은 질문셋에서 비교해야 판단할 수 있으므로, 여기서는 현재 구현의 계산 방식과 한계를 먼저 짚는다.


[검색 순위를 합치는 처리](https://github.com/NAMUORI00/aerospace-rag/blob/ac33be02be2ba6262b2529d0d663e46c1dbac228/aerospace_rag/retrieval/fusion.py)에 있는 `weighted_rrf()` 함수는 네 가지 정규 채널의 결과를 하나로 합산한다. 뜻을 비교하는 텍스트 벡터(`vector_dense_text`)와 단어를 비교하는 희소 벡터(`vector_sparse`)가 여기에 포함된다. 이미지 벡터(`vector_image`)와 그래프(`graph`)까지 합쳐 모두 네 채널이다. 각 청크가 한 채널에서 받는 점수는 `채널 가중치 × 1 / (k + rank + 1)`이며, 상수 `k`의 기본값은 60이다. 코드의 순위 변수인 `rank`가 0(1위)부터 시작하므로 분모에 1을 더한다. 1부터 시작하는 순위 $r_c(d)$로 표기하면 청크 $d$의 최종 점수는 $\sum w_c / (60 + r_c(d))$가 된다. 모든 채널을 같은 비중으로 더하는 표준 RRF(`k=60`, 균등 가중치)에 채널별 가중치 $w_c$를 곱한 형태다.


벡터 검색과 단어 기반인 BM25 검색 두 채널만 두고, 가중치를 각각 0.6과 0.4로 설정한 예를 들어 본다. 청크 A는 두 채널에서 모두 2위를 했고, 청크 B는 벡터 검색에서 1위를 했지만 BM25 결과에는 없다고 가정한다. 분모가 `60 + 순위`이므로 청크 A는 `0.6 / 62 + 0.4 / 62 ≈ 0.01613`점, 청크 B는 `0.6 / 61 ≈ 0.00984`점이다. 네 채널의 점수를 모두 더하므로 두 목록에 함께 등장한 청크 A는 점수가 누적되어 한 채널에서만 1위를 한 청크 B보다 앞선다. 반대로 채널 가중치가 0이면 그 채널의 결과는 최종 점수에 반영되지 않는다. 이 계산은 순위 결합이 동작하는 원리를 확인하기 위한 예시이며, 실제 검색 성능을 뜻하지는 않는다.


![벡터 검색 가중치 0.6과 BM25 가중치 0.4일 때 청크 A와 청크 B의 가중 RRF 점수를 비교한 다이어그램](/images/notion/aerospace-rag-weighted-rrf/image-2.png)


그림 2. 벡터 검색 1위에만 나타난 청크 B보다 두 채널에서 모두 2위를 한 청크 A의 합산 점수가 높아지는 가중 RRF 계산 예.


이 계산식에서 보듯 RRF는 원래 점수의 간격 정보를 버린다. 청크 B의 1위 점수가 2위보다 압도적으로 높든 거의 비슷하든, 순위가 같으면 똑같은 점수를 더한다. 또한 두 검색기가 같은 단어 단서에 의존해 비슷한 문서를 끌어올린다면, 실제로는 겹치는 신호인데도 서로 독립된 근거인 것처럼 합산될 수 있다.


## 인덱스 생성 시점의 가중치 자기 보정


가중 RRF 계산식에 넣을 채널별 가중치 $w_c$는 인덱스를 생성할 때 미리 보정해 파일로 저장해 두고, 실제 질문이 들어올 때 불러와 사용한다. [검색 가중치 보정 처리](https://github.com/NAMUORI00/aerospace-rag/blob/ac33be02be2ba6262b2529d0d663e46c1dbac228/aerospace_rag/retrieval/profile.py) 코드는 인덱스에 들어 있는 청크로 임시 질문인 **의사 질의**(pseudo query)를 만들어 가중치 프로파일(설정 파일)을 생성한다. 구체적으로 `_pseudo_query()` 함수가 제목 메타데이터, 확장자를 뺀 원본 파일명의 어간(stem), 본문 앞의 단어 조각(토큰) 24개를 이어 붙인다. 기본 설정에서는 이 의사 질의를 최대 32개 사례까지 사용한다.


의사 질의가 준비되면 코드는 `DEFAULT_WEIGHT_GRID`에 정의된 8개 가중치 후보 조합을 차례로 순회한다. 각 가중치 조합으로 가중 RRF를 실행한 뒤, 정답이 몇 위에 나타나는지 확인해 순위의 역수를 구한다. 예를 들어 목표 청크가 1위에 나오면 1점(`1/1`), 2위에 나오면 0.5점(`1/2`)을 매기는 식이다. 이때 목표 청크뿐 아니라 같은 원본 파일에 속한 다른 청크가 처음 나타나는 순위도 정답으로 인정해 역수의 평균을 낸다. 코드에서는 이 평균을 `mrr_at_k`로 기록하지만, 목표 청크 하나만 정답으로 치는 일반 **MRR**(Mean Reciprocal Rank)보다는 느슨한 기준이다. 코드는 8개 조합 가운데 `mrr_at_k`가 가장 높은 가중치 조합을 골라 설정 파일로 저장한다.


![인덱스 청크에서 제목, 파일명 어간, 본문 앞 24토큰으로 의사 질의를 만들어 8개 가중치 후보를 평가하는 흐름도](/images/notion/aerospace-rag-weighted-rrf/image-3.png)


그림 3. 인덱스 청크에서 의사 질의를 조합해 8개 후보 가중치의 mrr_at_k를 비교하고 프로파일을 저장하는 구현 흐름.


보정은 인덱스를 만들 때 한 번 실행되고, 선택된 가중치는 파일로 남아 질의 시점에 읽힌다. 다만 이때 쓰는 의사 질의는 인덱스 본문에서 그대로 뽑아낸 문자열이므로, 사람이 직접 작성한 독립 평가셋으로 측정한 결과와는 성격이 다르다.


## 질의 시점의 가중치 선택과 결과 수 조정


인덱스를 만들 때 저장해 둔 자기 보정 프로파일이 있으면, 실제 질문이 들어왔을 때 그 가중치를 우선 불러와 초기값으로 쓴다. 만약 보정 프로파일 파일이 없으면 질문의 성격에 따라 미리 정해 둔 기본 가중치를 사용한다. [질문별 검색 가중치 선택](https://github.com/NAMUORI00/aerospace-rag/blob/ac33be02be2ba6262b2529d0d663e46c1dbac228/aerospace_rag/retrieval/weights.py) 코드는 입력된 질의를 단어 특징에 따라 세 구간으로 분류한다. 미리 정의된 주요 대상(엔티티) 힌트 토큰과 겹치는 질의는 `entity_rich`로 분류한다. 앞 조건에 해당하지 않으면서 토큰 수가 6개 이하인 짧은 질의는 `keyword_fact`가 되고, 두 조건에 모두 해당하지 않으면 일반 질의인 `general`이 된다. 보정 프로파일이 없을 때는 각 구간에 `DEFAULT_CHANNEL_WEIGHTS`에 정의된 정적(고정) 가중치를 배정한다. 그런 다음 `normalize_channel_weights()` 함수로 가중치의 비율은 유지하면서 전체 합이 1이 되도록 맞추는 **정규화**를 거친다.


초기 가중치가 정해지면 실제 검색을 수행한 뒤 채널별 결과 수를 보고 가중치를 한 번 더 다듬는다. `_apply_evidence_adjustment()` 함수는 세 검색 채널이 돌려준 결과 건수를 확인한다. 확인 대상은 텍스트 밀집(`vector_dense_text`), 희소(`vector_sparse`), 그래프(`graph`) 채널이다. 검색 결과가 0건인 채널은 가중치를 0으로 설정하고, 검색 결과가 2건 미만(1건)인 채널은 가중치를 절반으로 줄인다. 조정이 끝나면 다시 `normalize_channel_weights()`를 호출해 전체 가중치의 합을 1로 맞춘다.

그림 4. 질의 시점에 초기 가중치를 불러온 뒤 채널별 검색 결과 건수에 따라 가중치를 조정하고 다시 정규화하는 과정.


코드를 따라가 보면 결과가 0건인 채널은 가중치를 건드리지 않아도 어차피 합산할 점수가 없다. 따라서 이 처리는 잡음을 제거한다기보다, 빈 채널에 배정됐던 비중을 결과가 나온 나머지 채널들에 다시 배분하는 동작으로 읽혔다. 물론 검색 결과가 여러 건 나왔다는 사실만으로 문서 내용의 적합성까지 보장되지는 않는다. 이 조정 전후에 질문별 최종 순위가 실제로 어떻게 달라지는지는 추가로 확인해야 할 부분이다.


## 자기 보정과 독립 평가의 경계


앞서 본 자기 보정과 결과 수 조정은 검색기가 동작할 가중치를 정하는 내부 절차이므로, 실제 검색 성능을 검증하는 평가와는 구분해야 한다. 본문 앞부분과 제목을 이어 붙여 만든 의사 질의는 실제 사용자의 질문보다 원본 문서를 찾기 훨씬 쉽다. 게다가 목표 청크뿐 아니라 같은 파일의 다른 청크가 나와도 정답으로 인정하기 때문에, 긴 문서에서 정확한 문단을 짚어 내는 능력이 실제보다 높게 나올 수 있다. 자기 보정은 검색기가 동작할 초기 가중치를 잡는 장치일 뿐이며, 여기서 나온 `mrr_at_k` 점수가 실제 질문에 대한 검색 성능을 대표하지는 않는다.


[검색과 생성 테스트](https://github.com/NAMUORI00/aerospace-rag/blob/ac33be02be2ba6262b2529d0d663e46c1dbac228/tests/test_retrieval.py) 코드도 이 범위 안에서 작성되어 있다. 테스트 파일에는 RRF 점수 계산과 결과 수에 따른 가중치 조정 로직, 같은 입력에 항상 같은 값이 나오는지 보는 해시 임베딩의 결정론성을 검사하는 항목이 들어 있다. 여기에 `graph-lite` 이웃 탐색과 생성 모델 서버인 vLLM의 출력 파싱(형식에 맞춰 읽어 내는 처리)을 확인하는 테스트도 포함되어 있다. 이번에는 테스트 코드가 어떤 조건을 검사하는지 확인했고, 현재 실행 환경에서 모두 통과하는지는 직접 실행해 확인해야 한다. 단위 테스트와 자기 보정은 내부 로직의 일관성을 검증할 뿐 외부 벤치마크 성능을 측정하지 않는다.


그래서 후속 평가를 설계할 때는 가중치를 고르는 데 쓰는 자료와 최종 성능을 보고할 자료를 엄격히 나누기로 했다. 사용자가 직접 작성한 질문, 정답 청크와 허용 가능한 보조 청크, 문서 단위의 데이터 분리를 먼저 고정하는 방식이다. 또한 검색 순위가 높아졌다고 해서 생성된 답변이 근거를 정확히 반영한다고 단정할 수 없으므로, 답변의 인용 정확성도 별도 평가 항목으로 넣었다.

## 결론


`aerospace-rag`는 검색 채널마다 점수 기준이 다른 문제를 피하기 위해 순위의 역수에 비중을 곱해 더하는 가중 RRF로 네 채널의 결과를 합친다. 가중치 설정 파일을 생성하는 단계와 실제 질문이 들어올 때 적용하는 단계를 분리해 두어 어떤 조건으로 검색했는지 재현하기 쉽게 구성했다. 인덱스를 만들 때는 의사 질의로 8개 후보 가운데 초기 가중치를 고르고, 질의 시점에는 결과 건수에 따라 빈 채널의 비중을 나머지 채널에 다시 나눈다.


이번에는 코드와 단위 테스트 항목을 읽으며 순위 결합 계산식, 자기 보정 절차, 결과 수에 따른 가중치 조정 규칙을 확인했다. 다만 원래 점수 결합과 순위 결합 중 어느 쪽이 이 문서 집합에 더 나은지, 결과 수 조정이 질문별 최종 순위를 실제로 어떻게 바꾸는지는 독립 평가셋으로 비교해야 한다. 단위 테스트가 현재 실행 환경에서 모두 통과하는지와 보정용 의사 질의를 바꿨을 때 선택되는 가중치가 얼마나 달라지는지도 직접 실행해 기록해야 설정의 안정성을 판단할 수 있다. 다음 글에서는 검색 당시의 근거가 실행 전에 낡아질 때, `SmartFarm`의 상태 재검증 구조에서 시간에 따라 조건이 달라진 답변을 어떻게 다시 검토하는지 다룬다.
