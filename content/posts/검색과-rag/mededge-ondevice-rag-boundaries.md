외부 서버를 거치지 않고 기기 안에서 의료 문답 자료를 찾아 답을 만드는 **온디바이스**(on-device) 질의응답 프로토타입 MedEdge를 구현했다. 이 프로젝트는 Android 앱의 LiteRT-LM 실행 경로와 개발 및 평가용 Python의 Ollama 실행 경로를 함께 다룬다. 모델을 불러오지 못할 때는 찾아낸 문답을 미리 정한 양식에 넣어 돌려주는 **템플릿 대체 응답**(fallback) 경로가 대신 동작한다.


이런 구조를 검증할 때는 화면에 나타난 답변만으로는 두 가지 경계를 구분하기 어렵다. 먼저 기기 내부 실행을 목표로 설계하더라도 모델을 처음 내려받거나 개발 서버를 연결하고 품질을 평가하는 단계에서는 네트워크가 쓰일 수 있다. 또한 화면의 답변이 로컬 **대규모 언어 모델**(LLM)이 추론한 결과인지, 모델 호출 실패로 문답 양식을 그대로 보여 준 것인지도 겉으로는 드러나지 않는다. 두 경로를 코드 수준에서 나누어 기록하지 않으면 응답 시간이나 답변 품질을 잘못 평가하게 된다. 이 글에서는 모델 준비와 기기 내부 검색 및 생성, 품질 평가 단계의 경계를 나누어 전체 실행 경로를 점검한다. 이 프로토타입은 의료 질의응답의 실행 구조를 확인하기 위한 연구용 구현이며, 실제 진단이나 처방의 임상적 유효성과 안전성은 별도로 검증해야 한다.

## 실행 환경과 모델 준비 경로


세 단계 가운데 첫 번째인 모델 준비 단계에서는 언어 모델의 학습 결과인 가중치 파일과 실행 메모리를 기기에 먼저 갖추어야 한다. 저장소의 Android 배포 구성은 네트워크를 쓰는 준비 단계와 실제 추론 단계를 분리하려고 `offline`과 `bootstrap` 두 빌드로 나뉜다.


`offline` 빌드는 앱 설정 파일인 매니페스트에 인터넷 권한(`android.permission.INTERNET`) 자체가 없다. 모델 파일은 개발 PC에서 기기 연결 도구인 안드로이드 디버그 브리지(ADB)를 통해 기기에 미리 배치한다. 용량이 큰 모델 가중치를 앱 설치 파일(APK)이나 코드 저장소와 분리해 준비하는 경로도 함께 사용한다. 반면 `bootstrap` 빌드는 앱을 처음 실행할 때 네트워크로 모델 파일을 내려받는다. 이때 파일이 손상되지 않았는지 확인하려고 SHA-256 해시값으로 무결성을 검증하며, 다운로드가 끝난 뒤에는 로컬에서만 추론을 수행한다.

그림 2. Android 배포 구성에서 네트워크 권한이 없는 offline 빌드와 최초 실행 시 모델을 내려받는 bootstrap 빌드의 준비 과정 비교.


모델을 내려받는 `bootstrap` 빌드와 수명 주기 동안 네트워크를 전혀 쓰지 않는 `offline` 빌드는 개인정보와 데이터의 이동 경로가 다르다. 또한 SHA-256 검증은 내려받은 파일이 기대한 모델 파일과 일치하는지만 확인할 뿐, 그 모델이 생성하는 답변의 품질은 별도로 평가해야 한다.


저장소의 로컬 검증 구성은 Pixel 7 기반의 Android 15(API 35) 에뮬레이터다. 현재 [Google LiteRT-LM의 Gemma 4 문서](https://developers.google.com/edge/litert-lm/models/gemma-4)는 Gemma 4의 E2B와 E4B 모델 및 Android 실행 경로를 안내하고 있다. 다만 모바일용 실행 환경과 에뮬레이터 구성을 확인했더라도 실제 휴대전화의 속도, 발열, 메모리 사용량, 기기별 정확도는 따로 검증해야 한다. 실제 기기에 모델 파일과 런타임, 하드웨어 가속 설정을 맞춘 뒤의 성능 측정은 후속 과제로 남겨 두었다. 이 Android 배포 구분은 README의 설계 기록을 따르며 앱에서는 LiteRT-LM의 Kotlin API를 사용한다. 이어지는 검색 색인과 답변 생성, 품질 평가 함수는 개발용 Python 경로를 기준으로 설명한다.


## 해시 기반 로컬 벡터 검색


모델 준비에 이어 질문을 받아 근거 문서를 찾고 답변까지 잇는 흐름은 Python 경로의 [질문에서 답변까지 연결하는 처리](https://github.com/NAMUORI00/ondevice-medical-rag/blob/d5dd214987338e1e57664bb6143ce9d38436c14e/src/mededge_rag/pipeline.py) 모듈이 맡는다. 진입점 함수인 `ask(index_path, question, top_k=3, use_llm=True)`는 디스크의 검색 색인을 읽어 관련 문서 상위 3건을 찾는다. 그 뒤 답변을 만들어 근거 목록과 함께 `(answer, evidence)` 튜플로 반환한다. 함께 반환되는 근거(`evidence`) 목록에는 질문, 문답 항목의 식별자(`qa_id`), 의료 분야(`domain`), 질문 유형, 검색 점수가 담긴다. 답변 문자열만 남길 때보다 어떤 자료를 근거로 삼았는지 사후에 확인하기 쉽다.


[검색 색인 구현](https://github.com/NAMUORI00/ondevice-medical-rag/blob/d5dd214987338e1e57664bb6143ce9d38436c14e/src/mededge_rag/vector_store.py)의 `HashingVectorIndex` 클래스는 단어와 글자 조각을 일정한 규칙의 숫자인 해시값으로 바꾼다. 이 숫자를 이용해 4,096개의 칸 가운데 특징이 있는 칸에만 값을 채운 **희소 벡터**(sparse vector)를 만들고 질문과 문서를 비교한다. 문장을 벡터로 변환하는 작업은 `vectorize(text, dims)` 함수가 처리한다. 이 함수는 먼저 정규표현식 `TOKEN_RE = re.compile(r"[A-Za-z0-9]+|[가-힣]+")`로 영문, 숫자, 한글 토큰을 분리한다. 이어서 `strip_korean_suffix()` 함수가 미리 정해 둔 접미사 목록을 규칙 기반으로 적용해 한국어 접미사를 떼어낸 변형 토큰을 만든다. 원래 토큰과 변형 토큰에서 검색에 불필요한 불용어를 제외한 뒤, 추출한 단어 특징마다 가중치 2.0을 더한다. 3글자 이상인 한국어 토큰은 접미사를 뺀 문자열을 두세 글자씩 잘라 길이 2와 3인 **문자 n-gram**을 만들고 가중치 0.25를 더한다.


추출한 단어와 문자 n-gram 특징은 `stable_hash(value)` 함수로 4,096차원 버킷에 매핑한다. 이 함수는 `int(hashlib.sha1(value.encode("utf-8")).hexdigest()[:16], 16)`으로 해시 정수를 계산한다. 구한 정수를 전체 차원 수인 4,096으로 나눈 나머지를 칸 번호로 삼아 해당 차원 버킷에 값을 더한다. 마지막으로 문서 길이에 따라 벡터 크기가 달라지지 않도록 L2 정규화를 거친 희소 벡터를 반환한다.


![입력 텍스트에서 토큰과 접미사를 분리해 단어 특징과 문자 n-gram을 추출하고 SHA-1 해시 매핑으로 4,096차원 희소 벡터를 생성하는 파이프라인](/images/notion/mededge-ondevice-rag-boundaries/image-3.png)


그림 3. vectorize 함수가 한국어 접미사 처리와 문자 n-gram 추출, SHA-1 해시 매핑을 거쳐 4,096차원 희소 벡터를 만드는 흐름.


검색을 수행할 때는 질문 벡터와 색인 안의 전체 문서 벡터 사이에 같은 칸의 값을 곱해 더하는 내적(dot product)을 계산한다. 계산한 점수가 양수인 결과만 내림차순으로 정렬해 상위 $k$개를 돌려준다. 만들어진 색인은 버전 필드를 포함해 JSON 직렬화(`save`/`load`) 방식으로 디스크에 저장하고 불러온다. 이 방식은 신경망으로 학습된 의미 임베딩이 아니라 해시 기반 희소 벡터를 사용한다. 같은 글자 패턴이 겹치면 점수가 높지만, 같은 의학적 의미를 다른 어휘로 표현한 질문까지 잘 찾아내는지는 별도 실험으로 확인해야 한다.


## 로컬 추론과 템플릿 대체 응답


검색 색인에서 찾은 근거를 받아 답변을 작성하는 단계는 [답변 생성 처리](https://github.com/NAMUORI00/ondevice-medical-rag/blob/d5dd214987338e1e57664bb6143ce9d38436c14e/src/mededge_rag/generation.py) 모듈에 구현되어 있다. 이 모듈에서는 `OllamaClient`가 기본 모델명 `gemma4:e2b`로 로컬 추론 서버에 생성 요청을 보낸다.


Python 개발 경로를 실행할 때는 환경 변수와 서버 응답 상태를 구분해 확인해야 한다. 만약 `OLLAMA_HOST` 환경 변수가 기기 내부가 아니라 외부 서버 주소를 가리키면 추론 요청이 원격 서버로 나간다. 따라서 로컬 실행 여부를 검증할 때는 사용한 빌드 종류와 함께 실제 호스트 주소 설정을 기록에 남겨야 한다. 또한 Ollama 서버의 `/api/tags` 경로가 HTTP 200을 반환하더라도 이는 서버 프로세스가 켜져 있다는 뜻일 뿐이다. 지정한 모델이 실제로 설치되어 있고 추론까지 성공하는지는 이 응답만으로 보장하지 않는다. 실제 답변 생성은 제한 시간(타임아웃)을 60초로 설정한 `/api/chat` 경로에서 이루어진다.


답변을 만드는 `answer_question(question, hits, use_llm=True)` 함수는 기본적으로 언어 모델 호출을 시도한다. 이때 서버에 연결할 수 없거나 응답이 늦어져 `OSError`, `URLError`, `TimeoutError`, `JSONDecodeError`가 발생할 수 있다. 이러한 오류가 나면 `template_answer()` 함수로 전환해 템플릿 대체 응답을 만든다. 템플릿 대체 응답은 검색된 의료 QA의 원본 답변에 식별자(`qa_id`), 분야(`domain`), 검색 점수(`score`)를 덧붙여 그대로 출력한다. 언어 모델 추론과 템플릿 대체 응답 두 경로 모두 결과를 반환하기 전에 `_with_disclaimer()` 함수로 면책 문구를 붙인다.

그림 4. 로컬 LLM 추론 호출과 오류 발생 시 템플릿 대체 응답으로 전환되는 답변 생성 및 반환 흐름.


템플릿 대체 응답은 모델을 쓸 수 없는 상황에서도 검색된 근거 자료를 보여 줄 수 있는 경로다. 따라서 화면에 템플릿 QA가 표시된 경우에는 언어 모델 추론 성공과 분리해 검색 및 템플릿 대체 응답의 성공으로 기록해야 한다. 화면에 텍스트가 출력되었다는 이유만으로 두 경로를 섞어 집계하면 모델의 실제 추론 성공률과 응답 시간, 생성 품질을 모두 잘못 읽게 된다. 정상 반환되는 모든 답변 끝에는 `DISCLAIMER = "본 답변은 연구용 의료 정보이며 진단이나 처방을 대체하지 않습니다..."` 문구가 항상 붙는다. 두 경로 모두 연구용 안내를 포함하도록 강제한 것이며, 답변 내용 자체의 의학적 안전성은 별도의 검증 체계를 거쳐야 한다.


## 외부 심사 기반 품질 평가와 한계


생성 경로를 거쳐 나온 답변의 품질을 정량적으로 비교하는 코드는 [평가 처리](https://github.com/NAMUORI00/ondevice-medical-rag/blob/d5dd214987338e1e57664bb6143ce9d38436c14e/src/mededge_rag/evaluation.py) 모듈에 모여 있다. 평가는 비교용 벤치마크 답변 쌍을 만드는 단계와 심사 모델로 점수를 매기는 단계로 나뉜다.


먼저 `run_benchmark()` 함수는 AIHub 의료 QA 데이터셋의 질문마다 두 가지 조건의 답변을 쌍으로 생성한다. 검색 근거 없이 모델만 쓰는 `llm_only` 조건과 상위 3건의 검색 근거를 함께 넣어 주는 `rag_top3` 조건이다. 이어서 `run_ragas()` 함수가 심사 모델과 임베딩 제공자를 호출해 네 가지 RAGAS 지표를 구한다. 답변 측면에서는 답변 관련성(`answer_relevancy`)과 근거 충실도(`faithfulness`)를 평가한다. 문맥 지표로는 문맥 정밀도(`context_precision`)와 문맥 재현율(`context_recall`)을 함께 계산한다. 이후 `summarize_answer_relevancy()`와 `bootstrap_mean_ci()` 함수로 두 조건의 답변 관련성 점수 차이를 집계한다. 표본을 반복 추출하는 백분위 방식의 쌍별 **부트스트랩 신뢰구간**(반복 10,000회, 신뢰 수준 0.95, 시드 13)으로 차이의 범위를 추정한다.


![AIHub 의료 QA로 두 조건의 답변을 생성하고 외부 심사 모델을 통해 RAGAS 4개 지표를 평가한 뒤 부트스트랩 신뢰구간을 구하는 구조도](/images/notion/mededge-ondevice-rag-boundaries/image-5.png)


그림 5. llm_only와 rag_top3 조건의 답변 쌍을 생성한 뒤 외부 심사 모델로 RAGAS 지표를 계산하고 부트스트랩 신뢰구간을 추정하는 평가 흐름.


이 평가 과정에서는 답변을 생성하는 모델과 점수를 매기는 평가 모델의 실행 위치가 다르다. 저장소에 설정된 기본 심사 모델명은 `gemini-3-flash-preview:cloud`로, 기기 내부의 추론 경로와 분리되어 있다. 외부 클라우드 심사 모델을 쓰면 평가용으로 생성한 질문과 답변 데이터가 외부 서비스로 전달될 수 있다. 따라서 기기 안에서 도는 온디바이스 추론 실험과 외부 심사 기반 평가를 구분해서 다루어야 한다.


RAGAS 지표 자체의 한계와 데이터 분리 기준도 함께 확인해야 한다. 근거 충실도 점수는 답변이 검색 문서에 얼마나 충실한지만 평가할 뿐, 원본 QA 자료의 오류나 오래된 정보까지는 걸러내지 못한다. 따라서 높은 RAGAS 점수가 곧 임상적인 정확성을 뜻하지는 않는다. 또한 같은 질문이 검색 색인과 평가 데이터셋에 중복으로 들어가면 해시 검색 점수가 실제보다 쉽게 높아질 수 있어, 평가 전에 데이터 분리 기준부터 확인해야 한다.


## 결론


지금까지 모델 준비와 해시 기반 로컬 벡터 검색, 언어 모델 추론과 템플릿 대체 응답, 외부 심사 기반 품질 평가의 실행 경계를 코드로 확인했다. 화면에는 모두 정상적인 답변으로 보이더라도 모델 준비나 평가 단계의 네트워크 사용 여부와 템플릿 대체 응답 전환 여부에 따라 실제 동작 경로가 달라진다. 따라서 응답 시간과 답변 품질을 왜곡 없이 평가하려면 사용자가 본 답변에 어떤 준비 과정과 처리 경로가 쓰였는지 코드 수준에서 구분해 기록해야 한다.


후속 검증에서는 검색 성공과 모델 준비 상태, 언어 모델 추론 성공, 템플릿 대체 응답 사용 여부를 따로 기록해 같은 조건에서 비교할 계획이다. 아직 확인하지 못한 실제 기기의 최초 응답 시간과 연속 실행 시 메모리 사용량, 발열은 실제 단말에 런타임과 하드웨어 가속을 맞춘 뒤 측정해야 한다. 모델 부재나 시간 초과 동작과 독립 질문셋의 근거 적합성을 점검하고, 환경이 바뀌어도 비교할 수 있게 측정 조건과 결과를 함께 남기는 것이 다음 단계다.
