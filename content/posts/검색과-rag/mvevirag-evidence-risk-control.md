같은 현관 카메라 영상을 두고도 “문 앞에 사람이 있었는가”라는 질문과 “그 사람이 물건을 내려놓았는가”라는 질문은 답할 수 있는지가 달라진다. 사람이 서 있는 모습은 보여도 손의 움직임이나 바닥이 가려져 있으면 물건을 내려놓았는지는 확인할 수 없기 때문이다. 이처럼 질문과 관련된 영상을 찾는 일과 그 영상에서 실제로 답할 근거를 확보하는 일은 서로 다른 문제다.

그림 1. 같은 영상에서 질문과 시야 가림에 따라 답변 가능 여부가 갈리는 예시 개념도.


여러 각도에서 찍은 다중 시점 영상은 한 카메라가 놓친 장면을 다른 카메라가 보완하지만, 사각지대가 겹치거나 촬영 시간 구간이 어긋날 수 있다. 자료를 찾아 답을 만드는 멀티모달 RAG 연구에서도 영상을 다루는 두 방식을 구분한다. [Mei 외, 2025](https://arxiv.org/abs/2504.08748)에서 정리한 원본 시각 정보 유지 방식과 글 변환 검색 방식이다. 이 문헌은 [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/) 조건으로 공개되어 있다. 영상을 글 설명으로만 바꿔 두면 처리하기는 쉬워도 작은 손동작이나 세밀한 공간 관계가 요약 과정에서 빠지기 쉽다. 결국 의미상 관련된 자료를 찾았더라도 질문이 요구하는 장면이 실제로 보이는지는 따로 확인해야 한다. 이 글에서는 다중 시점 영상 질의응답 시스템인 MV-EviRAG가 영상 선택과 근거 판단, 답변 채택을 단계별로 나누어 제어하고 검증한 과정을 다룬다.


## 세 단계 판단 구조


질문에 필요한 장면이 영상에 온전히 담겨 있더라도, 답변을 만드는 생성 모델이 근거를 잘못 읽어 틀린 답을 내놓을 수 있다. 찾아낸 장면이 질문과 관련 있는가, 답변할 근거가 충분한가, 생성된 답변이 정확한가는 모두 따로 따져야 한다.


MV-EviRAG는 이 세 가지 문제를 구분하기 위해 판단 과정을 세 단계로 나누었다. 먼저 생성 모델을 호출하기 전에 입력 영상으로 답할 수 있는 가능성(가용성)을 추정해 호출 순서를 정하고, 호출 뒤에는 확보한 근거만으로 답할 수 있는지 따진다. 마지막 단계에서는 모델이 내놓은 확신도에 따라 답변을 최종 채택할지 보류할지 결정한다. 판단 단계마다 보정할 기준이 새로 추가되므로, 코드와 문서를 정리하며 단계별 오류가 서로 섞이지 않게 나누어 확인했다.


![여러 시점 영상이 가용성 라우팅과 답변자 호출을 거쳐 근거 충분성 판단과 확신도 선택을 통과하면 채택한 답변이 되고, 근거 부족이나 선택 기준 미달이면 보류로 빠지는 흐름도](/images/notion/mvevirag-evidence-risk-control/image-2.png)


그림 2. 생성 전 가용성 라우팅, 호출 후 근거 충분성 판단, 확신도 기반 선택을 분리한 MV-EviRAG의 3단계 판단 흐름도.


## 호출 전 가용성 라우팅


세 단계 가운데 첫 번째인 **가용성 라우팅**은 생성 모델을 호출하기 전에 질문과 근거 영상 쌍의 답변 가능성을 추정해 호출 순서를 정한다. 질문과 비슷한 영상을 찾는 일반 검색과 달리, 정해진 호출 예산 안에서 답변에 실제로 쓸 수 있는 입력 쌍을 먼저 고르는 것이 목적이다.


이 단계에서 계산하는 가용성 점수는 입력 영상에서 답변 근거를 확보할 가능성을 나타낸다. 아직 답변을 만들기 전이므로 실제 답변이 맞고 틀린지는 생성이 끝난 뒤에 따로 판정한다. 순서를 정하는 라우터가 알맞은 영상을 골라내도 답변자인 생성 모델이 근거를 잘못 읽을 수 있다. 반대로 라우터가 낮게 평가한 자료에 유용한 정보가 남아 있을 수도 있다. 라우팅 성능과 생성 정확도를 하나의 수치로 합쳐 적으면 어느 단계가 나아졌는지 가려지기 때문에 두 지표를 분리해 읽었다.


## 호출 후 근거 판단과 답변 보류


라우팅으로 고른 영상을 넣어 생성 모델을 호출한 뒤에는, 두 번째 단계로 제공된 영상 근거 안에서 질문에 답할 수 있는지 다시 판단한다. 근거가 충분하지 않으면 답변을 보류한다. 답변을 내놓지 않는 경우를 실패로 처리하지 않고, 근거 부족을 나타내는 출력으로 남겨 두려는 선택으로 읽혔다.


호출 후 근거 판단은 앞 단계의 가용성 라우팅을 그대로 되풀이하는 과정이 아니다. 라우팅은 어떤 영상을 먼저 호출할지 우선순위를 정하는 사전 추정이고, 호출 후 판단은 실제 답변 과정에서 근거가 질문의 요구 사항을 충족하는지 확인한다. 호출 전 가용성 점수가 높았다는 이유로 호출 후의 보류를 막으면, 사전 추정의 오류가 최종 결과까지 그대로 이어질 수 있어 두 판단을 호출 앞뒤로 나누었다.


## 응답 비율과 선택 위험


근거가 충분하다고 판단한 뒤에도 생성된 답변에 틀린 답이 섞일 수 있으므로, 마지막 세 번째 단계에서는 모델이 생성한 답변의 확신도로 선택 위험을 제어한다. 불확실할 때 보류를 허용하는 선택적 예측에서는 전체 후보 중 보류하지 않고 최종 채택한 답변의 비율인 **응답 비율**(coverage)을 먼저 확인한다. 채택한 답변 안의 오류 비율인 **선택 위험**(selective risk)을 낮추려고 확신도가 낮은 답을 보류하면, 실제로 제공하는 답변 수도 함께 줄어든다.


![확신도 순으로 정렬된 답변 후보에서 확신도 임계값 왼쪽은 채택 구간(응답 비율)이 되어 포함된 오류가 선택 위험으로 계산되고 오른쪽은 보류 구간이 되는 개념도](/images/notion/mvevirag-evidence-risk-control/image-3.png)


그림 3. 확신도 임계값 설정에 따라 채택 구간(응답 비율)과 그 안의 오류 비율(선택 위험)이 변하는 선택적 예측 개념도.


이 때문에 답변 채택 기준인 선택 정책을 비교할 때는 선택 위험과 응답 비율을 늘 함께 비교했다. 확실한 질문에만 적게 답하는 정책과 넓은 범위에 많이 답하는 정책은 응답 범위가 다르므로, 오류율과 응답 비율을 나란히 놓고 봐야 한다. 다만 모델의 확신도가 실제 정답 확률에 맞게 잘 보정되어 있는지는 따로 확인해야 한다. 다른 데이터에서도 채택과 보류를 가르는 같은 기준값(임계값)을 그대로 쓸 수 있는지도 후속 검증 과제로 남아 있다.


## 검증 단계와 데이터 노출 경계


앞서 본 세 단계 판단 규칙과 선택 정책을 평가할 때는 데이터의 사용 이력부터 따져야 한다. 실험 데이터의 사용 이력에 따라 [검증 단계와 데이터 경계](https://github.com/NAMUORI00/RoleSep-VQA/blob/775b34eafca5db8914522ac7a582a1d841a63773/README.md)를 나누었다. 저장소는 내부 검증 범위를 개발 실증, 노출 이력이 있는 자료의 준확증 비교, 답변자 LoRA 정렬, 사전 동결 재평가의 네 단계로 구분한다.


여기서 주의할 점은 네 번째 단계인 사전 동결 재평가 역시 과거에 노출된 이력이 있는 `heldout-C`의 96사건 패널을 사용한다는 사실이다. 실행 전에 평가 규칙이 바뀌지 않도록 해시로 절차를 고정한 내부 동결 방식이므로, 공개 시각 인증을 거친 사전등록이나 독립 확증으로 해석하지 않는다.


![개발 실증, 준확증 비교, 답변자 LoRA 정렬, heldout-C 96사건 사전 동결 재평가까지 네 단계가 과거 데이터 노출 이력이 있는 내부 동결 범위에 묶여 있고 데이터 노출 경계 너머에 미노출 신규 자료를 쓰는 독립 확증이 분리된 다이어그램](/images/notion/mvevirag-evidence-risk-control/image-4.png)


그림 4. 데이터 노출 이력을 기준으로 나눈 저장소의 4단계 내부 검증 범위와 미노출 자료 기반 독립 확증의 경계.


검증 단계를 나눌 때 중요하게 본 기준은 단계의 이름보다 데이터를 이전에 열어 본 이력이었다. 개발 중에 확인한 자료에서 정책을 고르면 그 자료에만 잘 맞는 선택이 남을 수 있기 때문이다. 나중에 실행 절차를 해시로 고정하면 사후 변경은 줄일 수 있지만, 이미 있었던 데이터 노출까지 되돌리지는 못하므로 다음 검증 단계에는 미노출 자료가 필요하다.


## 라우팅 평가 결과와 수치 감사


저장소에 기록된 평가 결론을 보면, 가용성 기반 라우팅은 성립했지만 사전에 동결한 안전 기준은 충족하지 못했다. 새 방식이 비교 기준보다 허용 범위 이상 나빠지지 않았는지 따지는 **비열등성**(non-inferiority) 마진을 넘지 못했기 때문이다. 따라서 답변에 쓸 수 있는 가용 쌍을 골라낸(회수한) 결과가 유리하더라도 안전성 판단은 따로 남는다.


평가 기록에 있는 `evidence_supported_correct_yield` 항목은 이름만 보면 생성 모델이 맞힌 정답 수처럼 읽기 쉽다. 하지만 실제 뜻은 규칙 기반으로 판정한 가용 쌍 가운데 라우터가 선택한 회수 수다. 응답 비율 50% 조건에서 기록한 764건이 바로 이 가용 쌍 회수량이며, 미리 고정한 응답과 실측 평균 생성 시간으로 계산한 오프라인 반사실 분석 결과다. 따라서 실제 배포 환경에서 정답 산출량이나 지연 시간, 비용 절감을 직접 측정한 결과와는 구분해야 한다.


답변 확신도와 호출 전 가용성 점수를 사후에 합친 융합 정책은 추가 효용이 없어 기각되었다. 각 점수가 개별 단계에서 유용하더라도 두 점수를 결합한 결과가 더 나아진다고 볼 수는 없었다. 나중에 점수 결합을 다시 검토할 때는 각 점수가 예측하는 대상과 두 점수가 담고 있는 정보가 겹치는 정도를 먼저 확인할 항목으로 남겼다.


저장소에는 고정된 평가 자료로 내부 동결 재평가를 다시 실행하는 러너 코드와, 원고 및 그림의 수치를 동결 산출물과 대조하는 감사 코드가 준비되어 있다. 이 감사 코드로 실험 산출물과 문서 기록 사이의 일관성은 확인할 수 있지만, 원천 라벨의 정확성과 독립 데이터에서의 일반화 성능은 코드 감사와 별개로 검증해야 한다.


## 결론


영상을 더 많이 호출해 보는 일은 비용의 문제이고, 질문에 필요한 장면을 확보하는 일은 근거의 문제다. MV-EviRAG는 입력 선택부터 근거 판단, 최종 답변 판정까지 세 단계를 같은 사례 ID로 연결해 추적하도록 구성했다. 이처럼 모든 과정을 이어서 추적하고 응답 비율과 선택 위험을 함께 비교해야 각 단계에서 무엇을 얻고 무엇을 포기했는지 드러난다.


남은 과제는 미노출 자료에 같은 규칙을 적용해 검증하는 일과, 동결한 안전 기준 아래에서 실제 호출량과 지연 시간을 함께 측정하는 일이다. 이후에는 이 단계별 구분을 모바일 기기의 로컬 검색, 생성, 평가 환경으로 옮기는 작업을 다룬다. 기기 화면에 답변이 표시됐다는 사실과 로컬 모델 추론이 실제로 성공했다는 사실 역시 별개로 확인해야 할 항목이다.
