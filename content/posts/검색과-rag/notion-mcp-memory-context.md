스스로 도구를 써서 작업을 수행하는 AI 에이전트가 이전 기록을 다음 대화에서 다시 찾아 쓰려면 외부 기억 저장소가 필요하다. 이때 전용 데이터베이스 대신 메모 서비스인 Notion을 원본 저장소로 삼으면, 사람이 직접 읽고 고치는 페이지와 도구가 읽는 기록을 한곳에 둘 수 있다. 이미 로그인해 둔 명령줄 도구(CLI)를 그대로 다시 쓸 수 있다는 점도 편리하다. 대신 검색 기능은 Notion이 제공하는 조건 필터와 저장 칸(필드)의 한계에 묶인다. 검색용 벡터 색인 저장소를 따로 두는 대안도 있지만, 검색에서 빠지는 기록이 생길 가능성과 두 저장소의 내용을 맞추는 동기화 비용을 함께 비교해야 했다.


Notion만 쓰는 구조에서 기록과 검색이 어떻게 맞물리는지 확인해야 했다. 그래서 `notion-native-basic-memory-mcp` 저장소의 고정 커밋 [프로젝트 README](https://github.com/NAMUORI00/notion-native-basic-memory-mcp/blob/502ec1b42c4f9032b2ec3079671a18375cbe2fe6/README.md)를 먼저 읽었다. 문서에 적힌 동작 규칙(계약)을 기준으로 노트 원문과 본문 일부를 뽑아낸 검색용 발췌, 관찰, 관계가 어디에 저장되는지 확인했다. 저장된 기록들이 어떤 경로로 모여 AI 모델에 넘길 배경 정보인 **문맥**(context)으로 조립되는지도 함께 따라갔다. 코드 안쪽에서 글자를 분석하는 파싱 로직이나 실제 도구를 실행한 결과는 이번 범위에 넣지 않고 다음 검증 항목으로 남겨 두었다.

## MCP 도구 연결과 Notion 기록 관리


앞에서 본 것처럼 AI 에이전트가 Notion에 기록을 남기고 다시 읽으려면 에이전트와 저장소를 이어 주는 도구 연결 방식이 먼저 정해져야 한다. 이 프로젝트는 AI 프로그램인 클라이언트와 외부 도구가 요청과 응답을 주고받는 통신 규약인 **MCP**(Model Context Protocol)를 사용한다. AI 모델을 다시 학습시켜 가중치에 지식을 새기는 대신, Notion 페이지와 부가 정보(메타데이터)에 기록을 두고 필요할 때마다 도구를 호출해 읽는다.


2025-11-25 기준 [MCP 기본 명세](https://modelcontextprotocol.io/specification/2025-11-25/basic)는 JSON-RPC 기반 메시지 형식과 연결을 유지하는 수명주기를 정의한다. 다만 도구 뒷단의 저장소 종류나 검색 알고리즘까지 하나로 강제하지는 않는다. 그래서 기존 Basic Memory 프로젝트와 MCP 도구 이름이 비슷하더라도, 실제 기록을 저장하는 방식과 검색 결과가 뜻하는 바는 구현마다 달라질 수 있다.


`notion-native-basic-memory-mcp`는 TypeScript 서버가 인증된 Notion CLI인 `ntn`을 실행해 기록을 다룬다. 서버가 외부에 제공하는 도구는 노트의 작성과 읽기, 수정부터 검색, 최근 활동 조회, 문맥 조립, 데이터 구조를 다루는 스키마 관리까지 포괄한다.


## 노트 원문과 관찰, 관계의 분리 저장


앞에서 본 MCP 도구들이 기록을 다루기 위해, 서버는 초기 구성 단계에서 다섯 가지 데이터 소스를 새로 만들거나 기존 것을 다시 쓴다. 다섯 가지 데이터 소스는 `Projects`, `Notes`, `Observations`, `Relations`, `Schemas`로 나뉜다. 노트 본문 전체는 `Notes`에 속한 Notion 페이지에 마크다운 문서로 저장된다. 이와 달리 관찰 데이터인 `Observations`와 관계 데이터인 `Relations`는 별도 데이터 소스에 구조화되어 들어간다. 기록 하나가 여러 데이터 소스에 나뉘어 담기므로 원문 페이지와 각 데이터 소스의 저장 규칙을 함께 봐야 한다.


예를 들어 "검색 인덱스 교체 결정"이라는 작업 기록을 남기는 경우가 있다. 결정을 내린 이유와 검토 과정처럼 앞뒤 맥락을 모두 담은 원문은 `Notes`의 페이지 본문에 들어간다. 본문에서 나중에 따로 참고할 만한 개별 사실은 **관찰**로 추려 `Observations`에 기록한다. 관련된 평가 기록 노트를 가리키는 연결 고리는 **관계**로 묶어 `Relations` 데이터 소스에 저장하고 다음 탐색에 쓴다.


![검색 인덱스 교체 결정 노트의 본문이 페이지에 저장되고 관찰과 관계가 별도 데이터 소스로 분리되어 관련 평가 기록 노트로 연결되는 구조도](/images/notion/notion-mcp-memory-context/image-2.png)


그림 2. 노트 원문 페이지와 구조화된 관찰, 관계 데이터 소스의 역할 분담 예시.


이렇게 긴 원문과 항목별로 정리된 구조화 기록을 나누어 두면 읽을 때의 장단점이 뚜렷해진다. 구조화된 관찰은 분량이 짧아 빠르게 훑어볼 수 있지만, 구체적인 전제 조건이나 예외 상황이 빠지기 쉽다. 반대로 페이지 원문에는 앞뒤 맥락이 그대로 남아 있는 대신 매번 읽어야 할 글자 수가 많아진다. 그래서 검색 도구가 처음에 어느 수준까지 정보를 돌려주고, 거기서 어떻게 원문으로 넓혀 읽는지 이어서 확인했다.


## 검색용 발췌와 필터 검색의 한계


원문과 구조화된 기록을 나누어 저장한 뒤 검색을 실행할 때, 서버는 Notion 페이지의 본문 전체를 곧바로 뒤지지 않는다. `Notes.Search Text` 칸(필드)에는 본문에서 일정 길이만큼만 떼어 낸 검색용 **발췌**가 따로 저장된다. 서버는 노트 제목과 이 발췌, 경로 필터를 조합해 후보 노트를 찾는다. 전체 본문이 Notion 페이지에 그대로 남아 있어도 찾으려는 단어가 `Notes.Search Text` 발췌 범위 밖에 있으면 검색에서 빠질 수 있다.


검색 범위뿐만 아니라 검색 방식 자체의 한계도 README 문서에 분명히 적혀 있다. 예를 들어 사용자가 "장비 유지보수"라는 말로 기록을 찾을 때, 실제 노트에는 "센서 교체 기록"이라고 적혀 있으면 두 표현은 글자가 서로 다르다. 이처럼 단어가 달라도 뜻이 비슷한 기록을 찾아 달라는 **의미 검색**(semantic search) 요청이 들어올 수 있다. 이때 서버는 문장 의미를 계산하는 신경망 임베딩 검색을 수행하지 않고, 경고를 함께 돌려주며 Notion의 네이티브 필터 검색으로 낮춰 처리한다. 글자가 일치하는지와 구조화된 칸의 조건만 비교하는 방식이어서, "장비 유지보수"를 검색했을 때 "센서 교체 기록" 노트가 찾아진다고 보장할 수 없다.


![장비 유지보수라는 의미 검색 요청이 경고와 함께 Notion 필터 검색으로 낮춰져 제목과 발췌 필드만 탐색하고 발췌 밖 본문이나 센서 교체 기록은 놓칠 수 있음을 보여 주는 그림](/images/notion/notion-mcp-memory-context/image-3.png)


그림 3. 의미 검색 요청의 필터 검색 전환과 발췌 필드 기반 검색의 누락 조건.


이 때문에 검색 도구가 후보가 없다는 응답을 돌려주더라도 Notion에 관련 기록 자체가 없다고 단정하기는 어렵다. 도구의 응답을 읽을 때는 함께 돌아온 실제 검색 방식과 경고 메시지를 먼저 확인해야 한다. 첫 검색에서 후보가 잡히지 않더라도 경로나 제목 조건을 바꿔 다시 조회하거나, 이미 찾은 노트의 관계를 따라가며 검색 범위를 보완할 수 있다.


## 관계를 따라가는 문맥 조립과 남은 조건


검색과 조건 조회로 후보 노트를 찾은 뒤에는 `build_context` 도구가 관련 기록들을 하나로 묶어 AI 모델에 넘길 문맥을 만든다. 문서에 설명된 설계를 보면 `build_context`는 먼저 기준이 되는 관련 노트를 찾고 `Relations`에 저장된 관계를 따라가며 연관 정보를 모은다. 그다음 각 기록이 어디에서 왔는지 출처를 유지한 채 모델에 전달할 문맥으로 조립한다.


다만 README의 설명만으로는 연결된 관계를 단계마다 계속 따라가는 재귀 탐색의 세부 규칙이나 기본 탐색 깊이를 확정할 수 없었다. 모은 문맥이 모델이 한 번에 처리할 수 있는 분량인 토큰 한도를 넘을 때 어떻게 잘라 내는지도 문서에 나와 있지 않다. 두 노트의 관계가 서로를 가리키며 끝없이 순환하거나 여러 경로에서 같은 노트가 중복으로 모일 때의 처리 방식도 남아 있다. 연결된 대상 노트가 삭제되었거나 본문이 지나치게 길 때 어떻게 다루는지도 앞으로 코드를 직접 열어 확인해야 할 항목이다.


관계를 넓게 따라가며 문맥의 범위가 커지면 현재 질문과 상관없는 오래된 결정 기록까지 함께 섞여 들어갈 수 있다. 가장 최근 기록만 우선해서 보여 줄지, 과거 변경 이력을 나란히 보여 줄지는 에이전트를 쓰는 목적에 맞춰 정해야 한다.


## 기록 가져오기와 노트 단위 멱등성


문맥 조립에 쓸 기록을 처음부터 Notion에 새로 적는 대신, 기존에 쓰던 외부 기록을 한꺼번에 옮겨 와야 할 때도 있다. 기록을 옮겨 오는 `import_basic_memory` 도구는 마크다운 디렉터리와 Basic Memory의 SQLite 데이터베이스 자료 가져오기를 지원한다. 그중 데이터베이스 가져오기는 일반 노트 저장 도구인 `write_note`와 똑같이 경로(path)와 고유 주소(permalink)를 조회해 노트를 식별한다. 이 조회 과정 덕분에 같은 작업을 반복 실행해도 결과가 달라지지 않는 노트 단위의 **멱등성**(idempotency)이 보장된다. 가져오기를 다시 실행하더라도 노트를 중복해서 만들지 않고 이미 있는 같은 노트를 찾아 처리하려는 계약이다.


![마크다운 디렉터리와 SQLite 데이터를 가져올 때 path와 permalink 조회로 노트 수준 멱등성을 보장하지만 중간 실패 시 관찰과 관계의 상태는 추가 검증 항목으로 남아 있음을 보여 주는 그림](/images/notion/notion-mcp-memory-context/image-4.png)


그림 4. 기록 가져오기 도구의 노트 수준 멱등성 보장과 추가 검증이 필요한 경계.


문서가 보장하는 멱등성의 범위는 개별 노트 하나를 처리하는 수준까지다. 가져오기 작업 전체가 한꺼번에 성공하거나 취소되는지, 도중에 멈췄을 때 이미 들어간 관계와 관찰 데이터가 어떤 상태로 남는지는 아직 확인되지 않았다. 노트 이름을 바꾼 뒤에 다시 가져왔을 때 같은 노트로 인식되는지도 추가로 확인해야 한다. 노트를 구분할 때 경로와 고유 주소(permalink)를 쓰므로, 화면에 보이는 제목만 바꾼 경우와 식별자까지 바꾼 경우의 처리 조건이 달라진다.


관계 데이터를 다루는 또 다른 도구인 `canvas`도 이름에서 흔히 떠올리는 기능과 README의 설명이 달랐다. 이 프로젝트의 `canvas` 도구는 메모 앱인 Obsidian의 `.canvas` 파일을 만드는 대신 그래프 형태의 JSON 데이터를 담은 Notion 페이지를 생성한다. 저장된 관계 데이터 자체와 이를 화면에 그림으로 보여 주는 시각화 기능은 서로 다른 층으로 나뉘어 있다.


## 결론


앞선 연재에서 다룬 출처, 순위, 상태, 영상 근거, 실행 위치 문제와 마찬가지로 외부 기억 저장소에서도 각 단계의 결과가 다음 단계로 어떻게 넘어가는지 구분해야 한다. 기억 도구가 Notion에 저장된 원문과 검색 단계에서 꺼낸 짧은 발췌를 분명하게 나누어 보여 줄수록 AI가 내놓은 답변의 근거를 추적하기 쉽다. 노트 원문 페이지와 구조화된 관찰, 관계 데이터를 함께 유지하는 저장 계약이 필요한 이유도 여기에 있다.


이번 글에서는 README 문서를 기준으로 노트 분리 저장과 발췌 기반 필터 검색, 관계 중심 문맥 조립, 노트 단위 멱등성까지 문서에 정의된 경계를 확인했다. 반면 내부 파싱 로직과 재귀 탐색 깊이, 토큰 한도 처리, 가져오기 중단 시 데이터의 상태는 문서만으로 알 수 없어 미확인 항목으로 남겼다. 다음에는 실제 코드와 실행 기록을 열어 본문 수정 뒤 `Notes.Search Text` 발췌의 자동 갱신 여부와 가져오기 재시도 시 중복 방지를 확인한다. 두 노트가 서로를 가리키는 순환 관계 처리와 검색 누락 경고가 실제 도구 응답에 어떻게 담기는지도 이어서 검증할 과제다.
