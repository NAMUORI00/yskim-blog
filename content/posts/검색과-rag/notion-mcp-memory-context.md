## Notion을 저장소로 사용하는 조건


Notion을 원본 저장소로 쓰면 사람이 고치는 기록과 도구가 다시 읽는 기록을 같은 곳에 둘 수 있다. 기존 인증을 사용하는 CLI도 재사용할 수 있다. 대신 검색 범위는 Notion의 필터와 저장 필드에 의존한다. 별도 벡터 색인을 두는 대안에는 검색 누락 가능성과 두 저장소의 동기화 비용을 함께 비교할 부분이 있었다.


## 도구 연결과 외부 기록 저장


MCP는 클라이언트와 외부 도구가 요청과 응답을 주고받는 프로토콜이다. 이 프로젝트에서 기록은 Notion 페이지와 메타데이터에 저장되고, 필요할 때 도구 호출로 읽힌다. 모델 가중치에 지식을 추가하는 학습과는 저장 위치와 사용 시점이 다르다.


2025-11-25 MCP 명세는 JSON-RPC 기반 메시지와 연결 수명주기 등을 정의한다. 검색 알고리즘이나 저장소를 하나로 강제하지는 않으므로, 같은 MCP 도구 이름을 사용해도 저장 방식과 검색 의미는 구현마다 다를 수 있다. [MCP 기본 명세](https://modelcontextprotocol.io/specification/2025-11-25/basic)


## 사람과 도구가 공유하는 기록


프로젝트 구성은 TypeScript 서버가 인증된 Notion CLI `ntn`을 통해 기록을 관리하는 형태다. 노트 작성, 읽기, 수정 외에 검색, 최근 활동, 문맥 조립, 스키마 관련 도구를 노출한다. 사용자가 Notion에서 읽는 기록과 모델이 참조하는 기록이 같은 저장소에 있다.


인터페이스가 비슷하다고 해서 기존 Basic Memory의 모든 동작과 동일하다고 보기는 어렵다. 고정 커밋의 README에 명시된 저장, 검색 계약을 확인했다. 함수 내부 파싱과 도구 실행 결과는 추가 검증 항목이다.

## 원문과 구조화된 기록을 나누어 읽기


초기 구성은 `Projects`, `Notes`, `Observations`, `Relations`, `Schemas` 데이터 소스를 만들거나 재사용한다. 전체 노트 본문은 Notion 페이지 마크다운으로 저장된다. 관찰과 관계는 별도 데이터 소스에 구조화해 저장하므로 원문 본문과 함께 각 데이터 소스의 계약을 읽어야 한다.


개념적으로 노트는 문맥을 포함한 원문, 관찰은 다시 참조할 만한 사실, 관계는 두 기록 사이의 연결을 나타낸다. 예를 들어 "검색 인덱스 교체 결정"이라는 노트가 있다면, 결정 이유와 검토 과정은 본문에 남고 관련 평가 기록으로 향하는 연결은 탐색에 쓰인다. 각 정보의 역할을 설명하기 위해 구성한 예시다.


구조화된 관찰은 짧게 읽을 수 있지만 조건과 예외가 빠질 수 있다. 원문 전체에는 문맥이 남는 대신 매번 읽어야 할 양이 늘어난다. 그래서 검색 결과가 제공하는 정보 수준과 원문으로 확장하는 경로를 함께 살펴봤다.


## 검색 누락과 원문 확인


`Notes.Search Text`에는 길이가 제한된 검색용 발췌가 들어간다. 전체 본문은 페이지에 남아 있고, 제목, 발췌, 경로 필터를 통해 후보를 찾는 구조다. 본문에 어떤 단어가 있더라도 그 단어가 검색용 필드에 반영되지 않았다면 검색에 잡히지 않을 수 있다.


서버는 의미 검색 요청을 받으면 경고와 함께 Notion 네이티브 필터 검색으로 낮춰 처리한다고 명시되어 있다. 문자열과 구조화된 정보에 기반한 검색이다. "장비 유지보수"라는 질문이 "센서 교체 기록"과 연결되는지는 단순 문자 필터만으로 보장되지 않는다.


검색 결과는 반환된 검색 방식과 경고를 기준으로 읽었다. 후보가 없다는 응답만으로 기록 자체가 없다고 판단하기는 어렵다. 경로나 제목을 바꾼 조회와 관련 노트 탐색은 검색 범위를 보완할 방법으로 남아 있다.


## 문맥 수집 범위


`build_context`는 검색과 문맥 구성 도구군에 포함되어 있다. 설계상으로는 먼저 관련 노트를 찾고, 관계를 따라 정보를 모은 뒤, 출처를 유지한 채 모델에 전달하는 경계로 읽힌다. README만으로는 재귀 탐색의 세부 규칙, 기본 깊이, 토큰 제한 처리까지 확정되지 않았다.


관계가 순환하거나 노트가 중복되는 경우, 대상이 삭제되거나 본문이 너무 긴 경우의 처리는 후속 구현 검토 항목으로 남았다. 문맥이 커지면 질문에 무관한 오래된 결정도 함께 들어갈 수 있다. 최신 기록을 우선할지 변경 이력을 함께 보여 줄지는 응용 목적에 따라 달라진다.


## 다시 가져왔을 때 같은 노트인지 확인하기


`import_basic_memory`는 마크다운 디렉터리와 Basic Memory SQLite 자료의 가져오기를 지원한다고 설명한다. 데이터베이스 가져오기는 일반 `write_note`와 같은 경로, permalink 조회를 이용해 노트 수준의 멱등성을 제공한다. 같은 작업을 다시 수행해도 동일 노트를 찾아 처리하려는 계약이다.


문서가 설명하는 멱등성의 범위는 노트 수준이었다. 전체 가져오기가 한꺼번에 성공하거나 취소되는지, 중간 실패 후 관계와 관찰이 어떤 상태가 되는지는 아직 확인되지 않았다. 이름 변경 후 같은 노트로 인식되는지도 남은 확인 항목이다. 식별에는 경로와 permalink가 관여하므로 표시 이름만 바꾸는 경우와 식별자를 바꾸는 경우의 조건이 다르다.


`canvas`는 이름에서 떠올리는 기능과 README의 설명이 달랐다. 이 프로젝트에서는 Obsidian의 `.canvas` 파일 대신 그래프 JSON을 담은 Notion 페이지를 만든다. 저장된 관계 데이터와 이를 시각적으로 렌더링하는 기능은 별개의 층에 놓여 있다.


## 기록 조회와 답변 근거의 연결


앞선 연재의 출처, 순위, 상태, 영상 근거, 실행 위치 문제와 이 저장소의 기록 저장을 함께 정리해 봤다. 각 단계에서 남는 결과가 다음 단계에 어떻게 전달되는지가 공통된 검토 지점이었다. 이 저장소에서도 노트 저장, 검색 후보 반환, 질문에 필요한 문맥 조립은 각각의 결과를 확인할 단계로 나뉜다.


README에서 확인한 계약은 원문 저장에서 문맥 조립까지 이어졌다. 본문 수정 후 발췌 갱신, 가져오기 재시도의 중복 방지, 관계 순환 처리, 검색 누락을 드러내는 반환 형식은 구현과 실행 기록을 더 살펴볼 부분으로 남았다.
