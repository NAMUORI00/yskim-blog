**검색 증강 생성**(RAG)은 질문과 관련된 문서를 먼저 찾아낸 뒤, 그 내용을 언어 모델에 함께 건네 답변을 짓게 하는 방식이다. 이때 찾아온 본문만 문자열 하나로 이어 붙여 넘기면 답변의 근거를 다시 추적하기 어렵다. 모델에 들어간 텍스트만 남고, 각 발췌문이 어느 원문에서 왔는지나 검색 점수가 얼마였는지는 사라지기 때문이다. 또한 문서를 잘라 놓은 조각인 **청크**(chunk)마다 길이가 달라, 검색 결과 개수만으로는 전체 입력 길이를 일정하게 맞출 수 없다. 여기에 비공개 자료가 섞여 있을 때 외부 모델로 전송되지 않게 막는 일도 함께 다뤄야 한다.


SmartFarm RAG가 이 문제를 처리하는 방식을 보려고, 검색 결과가 입력 문맥과 출처 목록으로 나뉘어 생성 단계까지 전달되는 런타임 경로를 따라가 봤다. 아래 내용은 `f2a644bf` 커밋을 기준으로 하며, 코드 링크는 저장소 접근 권한이 있어야 열람할 수 있다.


## 런타임 검색과 문맥 조립의 접점


실제 질문이 들어왔을 때 검색 결과가 어디서부터 문맥으로 조립되는지 보려면 먼저 저장소 안의 실행 경로를 구분해야 한다. 이 저장소에는 검색할 문서 모음(코퍼스)을 준비하고 평가하는 코드와 실제 질문에 답하는 런타임 코드가 함께 들어 있다. 평가용 질문에 참고 문서를 연결하는 코드만 봐서는 실제 답변이 만들어지는 과정을 알 수 없다. 그래서 사용자 요청을 받아 검색 근거를 묶고 언어 모델을 호출하는 런타임 경로를 기준으로 코드를 읽었다.


전체 실행 흐름은 단계별 실행 시간을 측정하는 [실행 프로파일링 경로](https://github.com/NAMUORI00/SmartFarm_RAG/blob/f2a644bf672810ed9e2628e9e2b5b97691d0c8c9/packages/runtime/src/smartfarm_rag/retrieval/service.py#L630)의 `profile_query_execution()` 함수에 모여 있다. 이 함수는 한 번의 질의 처리를 후보 수집, 검색 결과 결합, 문맥 조립, 답변 생성의 네 단계로 나누어 걸린 시간을 기록한다.


앞단 검색 단계에서는 가져올 결과 개수(`top_k`)를 기준으로 기본 후보 수를 `max(top_k * 3, 12)`로 잡는다. 다만 구조 기반 검색 경로의 프로파일 깊이에 따라 실제 후보 수는 달라질 수 있다. 또한 모든 검색 경로가 하나로 고정된 검색 가중치만 쓰는 것도 아니다. 그래서 앞단의 검색 가중치 자체보다, 여러 검색 결과를 하나로 합친 최종 목록(`fused_hits`)이 문맥 조립기로 넘어가는 접점부터 따라가는 편이 정확했다.


## 문맥 문자열과 출처 목록의 분리


앞 단계에서 하나로 합쳐진 검색 결과는 문맥 조립을 맡는 [`build_context()`](https://github.com/NAMUORI00/SmartFarm_RAG/blob/f2a644bf672810ed9e2628e9e2b5b97691d0c8c9/packages/runtime/src/smartfarm_rag/retrieval/context_builder.py#L9) 함수로 넘어간다. 이 함수는 결합된 검색 결과인 `RetrievalHit` 목록을 입력으로 받는다. 각 `RetrievalHit` 항목에는 본문 텍스트와 검색 점수뿐 아니라 공개 등급(`tier`), 자료 유형, 생성 시각, 원본 자산 참조, 메타데이터가 담겨 있다. 함수는 입력 목록의 정렬 순서를 그대로 유지하면서 다음 세 가지 값을 만들어 돌려준다.


| 반환값               | 담는 내용                        | 후속 단계에서의 역할              |
| ----------------- | ---------------------------- | ------------------------ |
| `context`         | 번호, 자료 유형, 점수와 본문을 이어 붙인 문자열 | 언어 모델에 전달할 입력 문맥         |
| `refs`            | `SourceRef` 객체 목록            | 청크 ID와 원문 위치 및 자산 정보 보존  |
| `private_present` | 비공개 항목 포함 여부                 | 생성 경로 선택과 외부 전송 정책 검사 입력 |


코드 흐름을 보려고 가상의 농장 메모로 공개 자료 한 건과 비공개 메모 한 건이 순서대로 들어온 경우를 예로 든다. 이때 `context` 문자열에는 `[Source 1 …]`, `[Source 2 …]` 머리말이 붙어 두 자료의 본문이 차례로 이어진다. 동시에 `refs`에는 두 자료의 원본 식별 정보가 따로 담기고, 두 번째 항목이 비공개 등급이므로 `private_present`는 참(`True`)이 된다.


![정렬된 RetrievalHit 목록이 build_context 함수를 거쳐 private_present, SourceRef 목록, 문맥 문자열 세 갈래로 나뉘어 후속 단계로 전달되는 흐름도](/images/notion/tech-02-03/image-1.png)


그림 1. `build_context()`의 반환값과 다음 단계의 연결 구조로, 같은 검색 결과에서 출처 목록과 모델 입력 문자열을 분리해 유지한다.


그림 1처럼 같은 검색 결과에서 모델 입력용 문자열과 출처 목록을 동시에 만들어 분리해 두면, 텍스트를 이어 붙인 뒤 출처를 거꾸로 추측할 필요가 줄어든다. 다만 출처 목록을 보존하는 것만으로 답변의 근거 검증이 끝나지는 않는다. 모델이 생성한 답변의 각 문장이 실제 원문과 대응하는지 확인하는 단계가 이어져야 한다. 현재 프로파일링 함수는 `refs` 목록에서 출처 개수 같은 통계만 집계할 뿐, 문장별 인용 검증을 수행하는 코드는 이 경로에서 보이지 않았다.


## 프롬프트 조립과 문맥 길이 예산


앞 절의 `build_context()`가 만든 문맥 문자열은 [`build_rag_prompt()`](https://github.com/NAMUORI00/SmartFarm_RAG/blob/f2a644bf672810ed9e2628e9e2b5b97691d0c8c9/packages/runtime/src/smartfarm_rag/retrieval/context_builder.py#L42) 함수로 넘어간다. 여기서 사용자 질문과 합쳐져 모델에 건네는 최종 입력 글인 **프롬프트**(prompt)가 된다. 이 함수는 주어진 문맥만 써서 답하고 근거가 부족하면 밝히라는 지시문 뒤에 `[Context]`, `[Question]`, `[Answer]` 구역을 차례로 배치한다.


```plain text
문맥 사용, 부족 시 알림 지시

[Context]
번호가 붙은 검색 발췌들

[Question]
사용자 질문

[Answer]
```


여기서 검색 결과 개수(`top_k`)와 실제 모델 입력 길이가 비례하지 않는다는 점이 드러난다. 예를 들어 `top_k`가 3으로 같더라도 각 청크가 100자일 때와 5,000자일 때의 프롬프트 길이는 크게 달라진다. 청크마다 길이가 다르면 검색 결과를 몇 개 가져올지 정하는 것만으로는 전체 입력량을 일정하게 통제할 수 없다.


작은 예로 800자, 600자, 450자짜리 자료 세 건이 검색된 경우를 생각해 본다. 세 건을 합치면 1,850자여서, 설명용 입력 문맥 예산을 1,600자로 잡았다면 예산을 250자 넘기므로 세 건을 그대로 다 넣을 수 없다.


![800자, 600자, 450자 청크 세 개가 합계 1,850자가 되어 1,600자 예산을 250자 초과한 채 build_rag_prompt로 전달되는 비교 그림](/images/notion/tech-02-03/image-2.png)


그림 2. 세 건의 청크(800자, 600자, 450자)가 합계 1,850자가 되어 설명용 문맥 예산(1,600자)을 넘기지만 별도 절단 규칙 없이 프롬프트로 조립되는 예.


그런데 현재 `build_context()`와 `build_rag_prompt()` 두 함수에는 길이를 세어 청크를 자르는 로직이 없었다. 조립기에서 예산에 맞춰 청크를 제외하는 규칙도 코드에서 확인되지 않았다. 프로파일링 결과에 기록되는 `context_chars` 역시 완성된 문맥의 글자 수를 사후에 세어 남기는 통계일 뿐이다. 따라서 문맥 예산을 넘지 않게 입력 길이를 제한하려면 조립기에 별도의 제외 조건이나 절단 규칙을 추가해야 하는 상태다.


위에서는 설명을 위해 글자 수(1,600자)를 예로 들었지만, 실제 언어 모델의 입력 한도는 글자 조각 단위인 **토큰**(token)으로 결정된다. 앞으로 길이 제한 로직을 넣을 때는 사용할 모델의 토크나이저(문장을 토큰으로 쪼개는 도구)를 기준으로 삼아야 한다. 이때 시스템 지시문과 사용자 질문이 차지하는 토큰 수, 그리고 모델이 답변을 생성할 출력 토큰 여유분까지 함께 고려해 문맥 예산을 잡아야 한다.


## 제공자 선택과 외부 전송 차단 검사


프롬프트 조립과 함께, 앞서 문맥 조립 단계에서 확인한 비공개 자료 포함 여부(`private_present`)는 언어 모델 호출 경로를 결정하는 데 쓰인다. [`ProviderRouter`](https://github.com/NAMUORI00/SmartFarm_RAG/blob/f2a644bf672810ed9e2628e9e2b5b97691d0c8c9/packages/runtime/src/smartfarm_rag/llm_gateway/router.py#L51)는 이 값을 받아 실행할 모델 제공자를 고른다. 비공개 자료가 들어 있으면 일반 경로에서는 로컬 제공자(`local`)를 선택하며, 설정에 따른 개발용 예외 분기도 별도로 두고 있다.


라우터에 예외 분기가 있다 보니 비공개 자료가 있을 때 무조건 로컬 모델로만 간다고 단정할 수는 없었다. 그래서 제공자 선택 직후에 실행되는 [`assert_egress_policy()`](https://github.com/NAMUORI00/SmartFarm_RAG/blob/f2a644bf672810ed9e2628e9e2b5b97691d0c8c9/packages/runtime/src/smartfarm_rag/privacy/egress_guard.py#L6) 함수까지 이어서 확인했다. 이 함수는 비공개 자료가 포함되어 있고 외부 전송 차단 설정이 켜져 있는데 선택된 제공자 이름이 `local`이 아니면 예외를 발생시켜 실행을 중단한다.


![문맥과 설정 입력이 ProviderRouter를 거쳐 assert_egress_policy 검사로 이어지고 정책 통과 시 제공자를 호출하며 위반 시 예외를 발생시키는 순서도](/images/notion/tech-02-03/image-3.png)


그림 3. `ProviderRouter`의 제공자 선택과 `assert_egress_policy()`의 실행 직전 외부 전송 검사를 나눈 실제 호출 흐름.


그림 3처럼 모델 제공자를 고르는 단계와 호출 직전에 외부 전송 정책을 다시 검사하는 단계를 나누어 두었다. 다만 이 보호 장치가 의도한 대로 작동하려면 앞단에서 각 검색 자료의 `tier` 등급이 빠짐없이 표시되어 있어야 하고, 런타임 실행 설정도 정확히 맞물려야 한다.


정책 검사를 통과해 로컬 경로로 들어가면 [`LocalLlamaProvider`](https://github.com/NAMUORI00/SmartFarm_RAG/blob/f2a644bf672810ed9e2628e9e2b5b97691d0c8c9/packages/runtime/src/smartfarm_rag/llm_gateway/local_provider.py#L10)가 설정된 호스트의 `/completion` 주소(엔드포인트)에 HTTP 요청을 보낸다. 그다음 돌아온 응답에서 `content` 또는 `response` 필드를 읽어 답변을 반환한다. 코드상의 제공자 이름이 `local`이더라도 실제 네트워크 요청이 향하는 목적지는 호스트 주소 설정에 따라 결정되므로 배포 설정을 함께 확인해야 한다. 또한 이 경로에서 HTTP 오류가 발생하면 곧바로 예외가 올라오므로, 빈 답변이나 호출 실패를 추론 성공으로 기록하지 않도록 주의해야 한다.


## 실행 모드별 측정 범위


앞서 본 답변 생성 경로가 실행 측정 기록에 언제 포함되는지 확인하려고, 처음에 본 프로파일링 함수 `profile_query_execution()`으로 돌아가 봤다. 이 함수는 실행 모드가 `end_to_end`일 때만 지금까지 본 답변 생성 경로까지 네 단계를 모두 호출한다. 그 외의 모드에서는 생성 경로를 호출하지 않으므로 결과 객체에 답변 문자열과 생성 제공자 이름이 비어 있을 수 있다. 프로파일링 기록을 읽을 때 검색 단계만 측정한 수치를 전체 질의응답의 지연 시간이나 품질로 오해하지 않으려면 이 실행 모드 구분부터 확인해야 한다.

## 결론


이번 글에서는 [원논문](https://arxiv.org/abs/2005.11401)의 기본 구조 위에서 SmartFarm RAG(`f2a644bf` 커밋)가 검색 결과와 출처, 비공개 정책을 연결한 코드를 확인했다. 함수 호출 관계와 반환값을 따라가며 검색 결과에서 입력 문맥, 출처 목록, 비공개 여부가 나뉘어 전달되고 외부 전송 검사까지 이어지는 흐름을 짚었다. 실제 모델 서버를 띄워 응답 지연이나 답변 품질을 측정하는 실험은 이번 확인 범위에 포함하지 않았다.


코드를 따라가며 확인한 다음 보완 과제는 문맥 길이 제한과 문장별 인용 검증 두 가지다. 첫째는 입력 한도에 맞춰 청크를 자르거나 제외할 문맥 길이 예산을 어디에서 강제할지 정하는 일이다. 이때 모델에 실제로 전달된 출처 목록과 예산 부족으로 빠진 자료 및 제외 이유를 함께 기록해 추적할 수 있어야 한다. 둘째는 출처 목록(`SourceRef`)을 보존하는 단계를 넘어, 생성된 답변의 각 문장이 해당 원문과 실제로 대응하는지 검증하는 흐름을 붙이는 일이다. 현재 문맥 조립기의 입력과 출력이 명확히 분리되어 있어, 다음 단계에서는 이 검증 흐름을 작은 단위로 붙여 볼 수 있다.
