SmartFarm RAG에서는 검색한 자료를 모델의 문맥과 출처 목록으로 연결했다. 검색 점수와 원문 위치를 유지하면서 질문에 필요한 내용을 전달하는 것이 과제였고, 문맥 조립과 출처 생성을 나누어 구성했다.


## 구현과 확인 과정


SmartFarm RAG에서 검색한 자료가 답변으로 이어지는 부분을 정리했다. 검색 결과를 몇 개 가져올지만 정하면 모델 입력도 적당한 길이가 될 것처럼 보이지만, 청크마다 길이가 다르면 결과 개수만으로는 입력량을 설명할 수 없었다.


예를 들어 800자, 600자, 450자짜리 자료 세 개는 합계 1,850자다. 설명용 입력 예산을 1,600자로 잡으면 그대로 넣을 수 없다. 이 작은 예제를 놓고 문맥 문자열과 출처 목록이 만들어지는 경로를 따라가 봤다. 예산을 적용하려면 입력 길이를 제한하는 조건이 추가로 필요하다.


## 코퍼스 준비와 런타임 검색 경로


이 저장소에는 검색용 자료를 준비하는 부분과 실제 질문에 답하는 부분이 함께 있다. 평가용 질문에 참고 문서를 붙이는 코드만으로 실제 답변이 만들어지는 과정을 알 수는 없다. 이번에는 검색 근거를 모델 입력으로 묶고, 요청 흐름을 연결해 언어 모델을 호출하는 부분을 살펴봤다. 아래 코드는 `f2a644bf` 커밋을 기준으로 하며 저장소 접근 권한이 필요하다.


[실행 프로파일링 경로](https://github.com/NAMUORI00/SmartFarm_RAG/blob/f2a644bf672810ed9e2628e9e2b5b97691d0c8c9/packages/runtime/src/smartfarm_rag/retrieval/service.py#L630)의 `profile_query_execution()`은 후보 수집, 결합, 문맥 조립과 생성의 시간을 구분한다.


기본 후보 수는 `max(top_k * 3, 12)`로 설정되어 있지만, 구조 기반 경로의 프로파일 깊이에 따라 달라질 수 있다. 모든 경로가 하나의 고정된 검색 가중치를 쓴다고 보기보다, 문맥 조립기에 최종 `fused_hits`가 전달되는 접점부터 확인하는 편이 정확했다.


## 한 목록에서 문자열과 출처를 함께 만들기


[`build_context()`](https://github.com/NAMUORI00/SmartFarm_RAG/blob/f2a644bf672810ed9e2628e9e2b5b97691d0c8c9/packages/runtime/src/smartfarm_rag/retrieval/context_builder.py#L9)의 입력은 `RetrievalHit` 목록이다.


각 항목은 텍스트와 점수뿐 아니라 `tier`, 자료 유형, 생성 시각, 자산 참조와 메타데이터를 가진다. 함수는 이 목록의 순서를 유지하면서 세 값을 돌려준다.


| 반환값             | 담는 내용                   | 후속 단계에서 읽는 의미         |
| --------------- | ----------------------- | --------------------- |
| context         | 번호, 유형, 점수와 본문을 연결한 문자열 | 모델에 전달할 문맥            |
| refs            | SourceRef 목록            | 청크 ID와 원문 및 자산 정보를 보존 |
| private_present | 비공개 항목 존재 여부            | 생성 경로의 정책 검사 입력       |


예를 들어 공개 자료 한 건과 비공개 메모 한 건이 순서대로 들어오면 문맥에는 `[Source 1 …]`, `[Source 2 …]`가 붙고, 두 번째 항목 때문에 `private_present`가 참이 된다. 코드 흐름을 설명하기 위해 가상의 농장 메모로 구성한 예제다.

그림 1. `build_context()`의 실제 반환값과 다음 단계의 관계. 출처 목록과 모델 입력 문자열을 같은 자료에서 만들지만 서로 다른 값으로 유지한다.


이 구조에서는 텍스트를 이어 붙인 뒤 출처를 역으로 추측할 필요가 줄어든다. 출처 목록을 만든 뒤 답변의 각 문장과 원문이 대응하는지 검증해야 한다. 프로파일링 함수는 이 목록에서 개수 등의 통계를 만들지만, 답변의 문장별 인용 검증을 수행하는 코드는 이 경로에서 보이지 않았다.


## 검색 개수와 문맥 길이 관리


[`build_rag_prompt()`](https://github.com/NAMUORI00/SmartFarm_RAG/blob/f2a644bf672810ed9e2628e9e2b5b97691d0c8c9/packages/runtime/src/smartfarm_rag/retrieval/context_builder.py#L42)는 문맥과 질문을 일정한 틀에 넣는다.


주어진 문맥만 사용하고 자료가 부족하면 부족하다고 밝히라는 지시 뒤에 `[Context]`, `[Question]`, `[Answer]`를 배치한다.


```plain text
문맥 사용, 부족 시 알림 지시

[Context]
번호가 붙은 검색 발췌들

[Question]
사용자 질문

[Answer]
```


이 두 함수에는 토큰 수를 세어 청크를 자르는 로직이 없었다. `top_k`가 3이면 세 청크를 선택할 수 있어도, 각각 100자인 경우와 5,000자인 경우의 입력 길이는 다르다. `context_chars`는 문맥 길이를 기록하는 통계였으며, 토큰 예산을 적용하려면 별도 제한 조건이 필요했다.


앞의 1,600자 예제처럼 결과 개수 제한만으로 문맥 길이가 제한되지는 않는다. 현재 조립기에 이 예산에 따른 제외 규칙은 확인되지 않았고, 입력 길이를 제한하려면 별도 처리가 필요한 상태다.


길이 제한을 추가할 경우 모델의 토크나이저, 지시문과 질문의 길이, 생성할 출력의 여유가 함께 고려 대상이 된다. 위에서 문자 수로 설명한 예제는 설명을 위한 것이고, 모델의 토큰 한도와는 별개다.


## 비공개 표시가 생성 경로로 전달되는 방식


[`ProviderRouter`](https://github.com/NAMUORI00/SmartFarm_RAG/blob/f2a644bf672810ed9e2628e9e2b5b97691d0c8c9/packages/runtime/src/smartfarm_rag/llm_gateway/router.py#L51)는 `private_present`를 받아 실행 제공자를 고른다. 비공개 자료가 있으면 일반 경로에서 로컬 제공자를 선택하고, 설정에 따른 개발용 예외 분기도 별도로 존재한다.


항상 로컬로만 간다고 단정하기보다, 경로 선택 뒤의 [`assert_egress_policy()`](https://github.com/NAMUORI00/SmartFarm_RAG/blob/f2a644bf672810ed9e2628e9e2b5b97691d0c8c9/packages/runtime/src/smartfarm_rag/privacy/egress_guard.py#L6)까지 함께 읽었다.


이 검사는 비공개 자료가 있고 외부 전송 차단이 활성화됐는데 제공자 이름이 `local`이 아니면 예외를 낸다. 경로 선택과 실행 직전 검사를 나눈 형태지만, 자료의 `tier` 표시와 실행 설정이 정확해야 의도한 조건이 성립한다.


![02-03-02.png](/images/notion/tech-02-03/image-2.png)


그림 2. 제공자 선택과 실행 직전 외부 전송 검사를 나눈 실제 호출 흐름. 로컬, 원격 여부는 설정과 자료 표시를 함께 확인해야 한다.


[`LocalLlamaProvider`](https://github.com/NAMUORI00/SmartFarm_RAG/blob/f2a644bf672810ed9e2628e9e2b5b97691d0c8c9/packages/runtime/src/smartfarm_rag/llm_gateway/local_provider.py#L10)는 설정된 호스트의 `/completion`에 HTTP 요청을 보내고 응답의 `content` 또는 `response`를 읽는다.


실제 통신 목적지는 호스트 주소로 결정되므로 배포 설정에서 확인해야 한다. 이 경로에서 HTTP 오류는 예외로 올라가므로, 빈 답변이나 호출 실패를 추론 성공으로 기록해서는 안 된다.


## 실행 단계의 측정값을 읽는 기준


프로파일링 함수는 `end_to_end`일 때 생성 경로까지 호출한다. 그 외 모드에서는 답변 문자열과 생성 제공자 이름이 비어 있을 수 있다. 검색만 측정한 결과를 전체 응답의 지연이나 품질로 읽지 않아야 하는 이유가 이 모드 구분에 드러나 있었다.


이번에 확인한 결과는 소스의 호출 관계와 반환값이다. 실제 모델 서버를 띄워 답변 품질이나 지연을 측정한 기록은 여기에 포함하지 않았다. RAG의 일반 원리는 [원논문](https://arxiv.org/abs/2005.11401)을 참고하되, 이 저장소의 구현은 위 커밋의 연결을 기준으로 구분했다.


다음 확인 대상은 문맥 예산을 어디에서 강제할지다. 청크 길이를 제한하면서 출처 목록과 제외 이유를 함께 보존하는 방식, 그리고 검색됐지만 모델에 전달되지 않은 자료를 추적하는 방식이 남아 있다. 문맥 조립기의 입력과 출력이 분리돼 있어서 이 부분을 작은 단위로 검증할 수 있겠다고 정리했다.


## 작업을 정리하며


검색 결과가 답변의 근거로 쓰이려면 원문까지 돌아갈 수 있어야 한다. 이 작업에서 중요하게 보는 것은 문맥의 양과 출처의 정확성을 따로 관리하는 일이다. 출처 목록에 더해 문장별 대응과 입력 예산을 확인하는 흐름이 다음 보완점이다.
