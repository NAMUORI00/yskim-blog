smartfarm-search에서는 질의 처리와 색인 적재, 사적 데이터 수집, 삭제를 하나의 앱으로 구성했다. 경량 실행을 정리하면서 서비스 초기화, 백엔드 준비 상태, 요청 기록의 경계를 나누어 확인했다.


## 구현과 확인 과정


smartfarm-search의 서버 구성을 코드 기준으로 살펴봤다. 질의 처리뿐 아니라 색인 적재, 사적 데이터 수집, 만료 삭제, 상태 확인까지 하나의 앱에 들어 있었고, 각 역할의 경계를 따라가며 경량 실행에 필요한 조건을 확인했다. 소스 열람에는 저장소 접근 권한이 필요하다.


## 서버의 엔드포인트 구성


[서버 구성 코드](https://github.com/NAMUORI00/smartfarm-search/blob/17b5a0b3e1f4637900121c2b17cb9047d755b6c7/core/main.py)를 보면, FastAPI 앱 하나에 네 개의 라우터가 등록되어 있었다.


| 라우터                     | 주요 엔드포인트                                                | 역할        |
| ----------------------- | ------------------------------------------------------- | --------- |
| `query_router`          | `POST /query`                                           | 질의 처리     |
| `private_ingest_router` | `POST /private/ingest/memo`, `/sensor`, `/conversation` | 사적 데이터 수집 |
| `admin_router`          | `POST /admin/purge/private`, `/private-expired`         | 데이터 삭제    |
| `health_router`         | `GET /health`, `/health/ready`                          | 상태 확인     |


네 라우터를 import하는 부분에서 구조가 확정된다. 검색과 함께 사적 메모, 센서, 대화 데이터의 수집, 삭제를 같은 프로세스에서 처리했다.

## 의존성 초기화와 싱글턴


[검색 서비스와 모델 연결 초기화](https://github.com/NAMUORI00/smartfarm-search/blob/17b5a0b3e1f4637900121c2b17cb9047d755b6c7/core/Api/dependencies.py)를 확인했다. `RetrievalService`와 `ProviderRouter`가 각 서버 프로세스의 모듈 초기화 시 생성되고 이후 재사용되는 구조였다.


여러 워커를 쓰면 각 프로세스 안에 서비스 인스턴스가 하나씩 생긴다. `get_retrieval_service()`와 `get_provider_router()`는 호출할 때마다 같은 인스턴스를 돌려주는 팩터리 함수다.


서비스 인스턴스와 클라이언트를 준비하며, 백엔드 연결 가능 여부는 별도 검사가 필요했다. [`health/ready`](https://github.com/NAMUORI00/smartfarm-search/blob/17b5a0b3e1f4637900121c2b17cb9047d755b6c7/core/Api/health.py)의 본문도 설정된 주소와 고정 문자열을 반환할 뿐이었다.


```python
@router.get("/health/ready")
async def ready() -> dict:
    return {
        "status": "ready",
        "qdrant": f"{settings.QDRANT_HOST}:{settings.QDRANT_PORT}",
        "falkordb": f"{settings.FALKORDB_HOST}:{settings.FALKORDB_PORT}",
    }
```


이 함수에는 Qdrant나 FalkorDB에 요청을 보내 상태를 확인하는 코드가 없다. `ready` 응답은 핸들러가 응답 가능하다는 것만 뜻하고, 실제 검색 가능 여부를 판정하려면 색인 접근과 대표 질의까지 별도로 확인해야 한다. 실제 검사 내용을 읽으며 함수의 확인 범위를 구분했다.


## 질의 한 건에서 검색과 생성을 나누기


[검색과 답변 요청 처리](https://github.com/NAMUORI00/smartfarm-search/blob/17b5a0b3e1f4637900121c2b17cb9047d755b6c7/core/Api/query.py)를 보면, 질문이 검색 서비스에 전달된 뒤 `build_context()`와 `build_rag_prompt()`가 호출된다.


생성 제공자 호출에서 예외가 나면 HTTP 503으로 변환된다. 검색 호출은 그 예외 처리 바깥에 있어서, 두 단계의 실패가 같은 응답 경로를 타지는 않았다.


정상 반환에는 답변과 `sources`, 생성, 임베딩 제공자 및 결합 정보가 함께 포함된다. `debug` 요청에서는 검색, 생성 시간과 출처 개수 등의 진단값도 붙는다. 이 값들은 오류 위치를 구분하는 기록 항목이다. 실제 환경의 지연은 별도 측정이 필요하다.


## 사적 데이터의 수집과 삭제


[사적 데이터 삭제 처리](https://github.com/NAMUORI00/smartfarm-search/blob/17b5a0b3e1f4637900121c2b17cb9047d755b6c7/core/Api/admin_purge.py)를 확인했다. `purge_private` 엔드포인트는 `farm_id`를 받아 해당 농장의 사적 데이터를 삭제한다.


삭제 대상은 overlay 행, Qdrant 포인트, 그래프 항목 세 곳이고, 삭제 결과는 각각의 건수로 응답된다.


`purge_private_expired`는 기준 시각을 받아 만료 자료를 정리하는 경로다. [저장소별 삭제 처리](https://github.com/NAMUORI00/smartfarm-search/blob/17b5a0b3e1f4637900121c2b17cb9047d755b6c7/core/retrieval/service.py#L656)의 호출을 보면, overlay와 그래프에는 `farm_id`를 넘기지만 Qdrant 쪽에는 넘기지 않는다.


실제 Qdrant 구현도 사적 등급과 시각을 기준으로 검색하므로, 요청의 농장 범위가 세 저장소 모두에 동일하게 적용된다고 설명할 수는 없었다. 반환 건수만으로는 이 차이가 드러나지 않고, 저장소별 필터 조건을 함께 봐야 확인할 수 있는 부분이었다.


삭제 이벤트는 `append_redacted_log`를 통해 기록된다. 이 함수는 `redact_event`를 호출해 이벤트를 수정한 뒤 로그 파일에 추가하는데, redaction 로직은 별도 모듈(`core/privacy`)에 있어 어느 필드를 가리는지는 그쪽을 보면 된다. 로그 기록 오류를 잡고 넘어가므로, 삭제 결과와 감사 로그 저장 결과를 각각 확인해야 한다.

## 엣지 실행의 조건


README에는 "엣지 환경용 경량 RAG 서버 (Qwen3 + llama.cpp)"라는 설명이 붙어 있었다. 서버 시작 코드의 `run_local` 함수는 uvicorn으로 포트 41177에서 서버를 띄우고, `run_edge_compose`는 엣지 환경용 Docker Compose 설정으로 컨테이너를 실행한다.


엣지에서 이 서버가 동작하려면 최소한 다음 조건이 갖춰져야 한다.

1. **Qdrant 인스턴스**: 벡터 색인을 적재하고 검색할 수 있어야 한다
2. **FalkorDB 인스턴스**: 그래프 데이터를 질의할 수 있어야 한다
3. **LLM 백엔드**: 환경 변수 `LLM_BACKEND`가 `llama_cpp` 또는 `openai_compatible`을 가리켜야 한다
4. **임베딩 API**: HuggingFace Inference API의 `feature_extraction` 엔드포인트에 접근 가능해야 한다

llama.cpp를 LLM 백엔드로 쓰면 외부 API 호출 없이 로컬에서 생성할 수 있지만, 임베딩 제공자 생성 함수는 [`HuggingFaceAPIEmbeddingProvider`](https://github.com/NAMUORI00/smartfarm-search/blob/17b5a0b3e1f4637900121c2b17cb9047d755b6c7/core/embeddings/factory.py)를 반환하고, 이 구현은 외부 HTTP API에 요청을 보낸다.


README의 설명과 실제 호출 경로가 일치하는지를 이렇게 코드로 확인할 수 있었다. 임베딩 경로를 별도로 교체하지 않는 한 완전한 오프라인 실행은 성립하지 않는다.


llama.cpp의 GGUF 양자화 모델을 이용한 엣지 추론에 대해서는 [llama.cpp GitHub 저장소](https://github.com/ggerganov/llama.cpp)를, Qdrant의 벡터 검색 및 페이로드 필터링에 대해서는 [Qdrant 공식 문서](https://qdrant.tech/documentation/)를 참고할 수 있다.


FastAPI의 라우터와 의존성 주입 구조는 [FastAPI 공식 문서](https://fastapi.tiangolo.com/)에서 확인할 수 있다.


## 색인 갱신의 경로


라우터 등록을 확인한 범위에서는 공개 코퍼스를 일괄 인덱싱하는 경로가 보이지 않았다. 공개 코퍼스의 색인 생성은 smartfarm-ingest 쪽에서 수행하고, 생성된 아티팩트를 매니페스트와 함께 엣지로 옮기는 구조다. 검색 서버가 직접 갱신하는 것은 사적 데이터(`/private/ingest/*`)뿐이었다.


이 분리만으로 공개 색인 교체에 서버 중단이 반드시 필요하다고 볼 수는 없다. 실제 갱신 방법은 배포 구성과 데이터베이스의 교체 절차를 함께 봐야 한다. 서버 실행 중에 공개 색인을 무중단 교체하는 메커니즘은 이번에 읽은 코드 범위에서 확인되지 않았다.


---


다음에 확인할 부분: HuggingFace Inference API 대신 로컬 임베딩 모델(예: sentence-transformers)을 엣지에서 직접 실행하면 완전 오프라인 구성이 가능한지, 그 경우 메모리 사용량이 llama.cpp 모델과 합산되어 엣지 디바이스에서 감당 가능한 범위인지.


## 작업을 정리하며


서버 프로세스가 살아 있는 상태와 검색을 처리할 준비가 된 상태를 구분하는 것이 중요하다. 초기화와 실제 연결 검사를 나누고, 삭제 결과와 감사 로그도 각각 기록하면 운영 중 문제를 좁히기 쉽다.
