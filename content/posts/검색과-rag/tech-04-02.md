MV-EviRAG의 호출 전 라우팅에서는 한정된 예산 안에서 어떤 영상 입력을 사용할지 다뤘다. 화면의 관련성과 답할 단서의 가용성을 구분하고, 필요한 점수가 없을 때 중단하도록 오프라인 선택 경로를 구성했다.


## 구현과 확인 과정


MV-EviRAG의 오프라인 라우팅 코드에서 호출 전 선택 경로를 읽었다. 앞 글에서 정리한 세 가지 판단 중 모델을 호출하기 전에 어떤 입력을 고를지 결정하는 부분에 해당한다. 카메라 화면에 사람이 잡혀 있어도 출구가 가려져 있으면 이동 방향을 묻는 질문에는 답하기 어렵고, 호출 예산이 한정돼 있을 때는 장면의 관련성뿐 아니라 질문에 답할 단서가 실제로 있는지도 선택 기준이 된다.


여기서 읽은 것은 커밋된 사전 동결 재평가 러너의 오프라인 분석 경로다. 오프라인 평가 코드의 라우팅 정책을 다룬다. 비용과 지연, 근거 부족과 호출 실패를 구분하는 보충편이 배경이 된다.


## 관련성 점수와 가용성 점수를 따로 비교하기


[입력별 평가 결과 구성](https://github.com/NAMUORI00/RoleSep-VQA/blob/775b34eafca5db8914522ac7a582a1d841a63773/scripts/operator/secondary_generalization_bc.py)의 routing_rows_real은 저장된 입력 행과 selector 예측, 이미지, 질문 특징을 읽어 들인다.


의미 관련성 비교에는 특징 벡터의 코사인 유사도를, 가용성에는 개발 자료에서 이전한 dev_transfer_score를 사용한다. 두 점수는 같은 정책 이름으로 묶이지 않고 별도 기준선으로 비교할 수 있게 구성돼 있었다.


이동 방향에 답하려면 대상의 위치와 출구가 이어지는 장면을 확인해야 한다. 질문과 장면이 관련돼 있어도 출구가 보이지 않거나 필요한 시간 구간이 빠져 있을 수 있다. 가용성을 따로 추정하려는 문제의식은 이 차이를 겨냥한다고 읽혔다. 다만 점수 이름이 availability라고 해서 모든 누락이나 가림을 정확히 감지한다고 결론 낼 수는 없다.

그림 1. 커밋된 러너에서 의미 관련성과 가용성을 별도 점수로 구성하는 경로. 출처: 입력별 평가 결과 구성을 바탕으로 직접 구성.


예측 행이 없거나 의미 특징의 노름이 0이면 러너는 오류를 낸다. 필요한 점수가 없으면 오류로 처리해 라우팅을 중단한다. 이 동작은 평가 입력 계약을 확인하는 것이고, 카메라가 끊긴 실제 서비스에서 대체 카메라를 호출하는 정책이 구현돼 있다는 뜻과는 별개다.


## 50% 선택의 표본 수 계산


selected_rows는 global과 within_category 두 모드를 지원한다. global은 전체 점수순으로, within_category는 범주마다 정한 비율만큼 선택한다. 동점인 경우 row_id로 순서를 정해 결과를 재현할 수 있도록 했다. 선택 수 계산에는 올림이 적용된다.


설명용으로 범주 A에 3행, B에 5행이 있다고 하자. 범주별 50%를 고르면 A에서 2행, B에서 3행으로 총 5행이 선택된다. 전체 8행의 정확한 절반인 4행과는 다르다. 작은 범주에서는 올림의 영향이 커지기 때문에, 요청한 coverage와 실제 selected_calls를 함께 확인해야 차이를 파악할 수 있다.


| 설명용 행 | 가용성 점수 | 규칙 기반 가용 라벨 | 상위 2행 선택 |
| ----- | ------ | ----------- | -------- |
| q1    | 0.9    | 1           | 선택       |
| q2    | 0.8    | 0           | 선택       |
| q3    | 0.7    | 1           | 제외       |
| q4    | 0.2    | 0           | 제외       |


이 네 행을 전역 50%로 고르면 가용 라벨 2개 중 1개가 회수된다. answerability_recall은 1/2, call_waste_rate는 선택한 2개 중 가용하지 않은 1개이므로 1/2이다. 이 표는 답변 생성 전 라우팅 결과를 다룬다. 정답률은 생성 후 평가한다. 계산 과정을 설명하기 위해 구성한 예제 값이다.


## yield의 정의와 계산 범위


routing_rows_real은 grounded_correct에 생성 답변의 정오가 아닌 입력의 label을 복사한다. metric_at의 evidence_supported_correct_yield는 이 값을 선택된 행에 대해 합산한다.


따라서 이 경로의 yield는 선택된 규칙 기반 가용 쌍의 수에 해당한다. calls_per_correct_answer도 이름만 보면 정답당 호출 수이지만, 실제 분모는 같은 가용 라벨의 합이다.


[README](https://github.com/NAMUORI00/RoleSep-VQA/blob/775b34eafca5db8914522ac7a582a1d841a63773/README.md)에도 이 해석이 명시돼 있었다.


필드 이름만으로는 논문 문장에 바로 대응시키기 어려웠고, 실제로 값을 넣는 행을 확인한 뒤에야 의미가 분명해졌다. 라우팅이 가용 입력을 잘 회수하는지와, 그 입력에서 답변자가 정답을 만드는지는 별도의 평가 대상이다.


![04-02-02.png](/images/notion/tech-04-02/image-2.png)


그림 2. 선택한 가용 쌍 수와 오프라인 시간 추정이 만들어지는 경로. 출처: metric_at과 routing_summary를 바탕으로 직접 구성.


시간 추정은 전체 행 수에 평균 생성 시간을 곱한 값에서, 선택 호출 수의 생성 시간과 전처리 시간을 빼는 방식이다. 설명용으로 100행, 선택 50행, 평균 생성 2초, 전처리 총 10초라면 200−100−10=90초가 된다.


이 계산은 고정 평균을 사용한 비교이며, 실제 운영에서는 입력 길이, 배치, 대기열, 재시도에 따라 시간이 달라질 수 있다. 실제 배치 환경의 시간 절감량은 병렬 실행과 대기 시간을 포함해 측정해야 한다.


이번 글에서는 가용성 라우팅이 답변 전에 무엇을 선택하는지까지 좁혀서 읽었다. 다음 글에서는 호출 이후의 확신 점수와 선택 위험을 다룬다. 가용 쌍을 먼저 고르는 문제와 답변 오류를 낮추는 문제가 어디서 갈라지는지, 평가 자료를 이미 본 이력이 결과 해석에 어떻게 남는지가 이어지는 내용이다.


## 작업을 정리하며


호출 전 판단은 이후 답변 평가와 분리해야 원인을 읽기 쉽다. 선택한 입력과 그때의 점수를 남기면 근거 부족과 생성 오류를 따로 확인할 수 있다. 시간 절감도 단순 호출 수 계산과 실제 실행 시간을 나누어 기록하려 한다.
