## 관련성 점수와 가용성 점수의 분리


호출 전 라우팅이 어떤 기준으로 입력을 고르는지 보려면 관련성과 가용성 점수를 읽어 들이는 코드부터 확인해야 한다. [입력별 평가 결과 구성](https://github.com/NAMUORI00/RoleSep-VQA/blob/775b34eafca5db8914522ac7a582a1d841a63773/scripts/operator/secondary_generalization_bc.py) 코드의 `routing_rows_real` 함수는 저장된 입력 행과 선택기(`selector`) 예측값, 이미지 특징 벡터, 질문 특징 벡터를 불러온다. 여기서 특징 벡터는 이미지나 질문의 의미 특징을 비교할 수 있도록 숫자 배열로 바꾼 값이다. 의미 관련성을 비교할 때는 이미지와 질문 특징 벡터의 방향이 얼마나 비슷한지 나타내는 **코사인 유사도**를 쓴다. 단서의 가용성을 비교할 때는 개발 데이터에서 이전한 점수인 `dev_transfer_score`를 사용한다. 두 점수는 하나의 정책 이름으로 묶이지 않고, 같은 선택 예산 아래에서 각각 별도 기준선으로 비교할 수 있게 나뉘어 있다.


이동 방향 질문에 답하려면 대상의 위치와 출구가 이어지는 장면을 확인해야 한다. 질문과 주제가 맞는 화면이라도 출구가 보이지 않거나 필요한 시간 구간이 빠져 있으면 답을 낼 수 없다. 관련성과 별개로 가용성 점수를 따로 추정한 것은 이러한 차이를 겨냥한 구성으로 읽혔다. 다만 점수 이름이 `availability`라고 해서 화면 가림이나 구간 누락을 빠짐없이 찾아낸다고 단정할 수는 없다.

점수를 비교하기 전에 예측 행이 비어 있거나 의미 특징 벡터의 크기(노름)가 `0`이면 러너는 곧바로 오류를 내고 라우팅을 멈춘다. 필요한 점수가 빠진 상태에서 임의로 선택을 이어 가지 않도록 평가 입력 계약을 강제한 것이다. 이 중단 동작은 오프라인 평가 데이터의 무결성을 확인하는 절차일 뿐이며, 실제 운영 환경에서 카메라 연결이 끊겼을 때 다른 카메라로 우회 호출하는 정책과는 별개다.


## 선택 방식과 올림에 따른 호출 수


앞 단계에서 입력마다 점수를 매겼다면, 다음에는 `selected_rows` 함수가 점수를 기준으로 상위 입력을 추려낸다. 이 함수는 **전역 선택**(`global`)과 **범주별 선택**(`within_category`) 두 가지 모드를 지원한다. `global`은 전체 입력을 한꺼번에 점수순으로 줄 세워 자르고, `within_category`는 질문 범주마다 정해진 비율만큼 따로 고른다. 점수가 같을 때는 행 식별자(`row_id`) 순서로 정렬해 언제 실행하든 같은 선택 결과가 나오도록 고정했다. 목표 비율에 맞춰 선택할 행 수를 구할 때는 소수점 아래를 올림해 계산한다.


예를 들어 범주 A에 3행, 범주 B에 5행이 들어 있어 전체 입력이 8행이라고 하자. `global` 모드로 50%를 고르면 전체 8행의 절반인 4행이 선택된다. 반면 `within_category` 모드로 범주별 50%를 고르면 범주 A에서 1.5행을 올림한 2행, 범주 B에서 2.5행을 올림한 3행이 뽑혀 총 5행이 선택된다. 이처럼 소수점 올림 규칙이 적용되면 선택 방식에 따라 실제 모델 호출 수가 달라진다. 범주 크기가 작을수록 올림의 영향이 커지므로, 설정한 목표 비율(`coverage`)만 보지 않고 실제 선택된 호출 수(`selected_calls`)를 함께 확인해야 한다.


![범주 A 3행과 범주 B 5행으로 구성된 전체 8행에서 전역 50% 선택은 4행을 고르지만, 범주별 50% 선택은 올림이 적용되어 A에서 2행, B에서 3행으로 총 5행을 고르는 비교 그림](/images/notion/tech-04-02/image-3.png)


그림 3. 전체 8행 예제에서 전역 선택(global)과 범주별 선택(within_category)의 50% 호출 수 계산 비교.


## 가용 라벨 기반 라우팅 지표 계산


호출할 입력 행을 추려낸 뒤에는 라우터가 단서가 있는 입력을 얼마나 잘 골랐는지 평가 지표를 계산한다. 이 계산 과정을 차례대로 확인하기 위해 4개 행으로 구성된 예제를 표로 정리하면 다음과 같다.


| 설명용 행 | 가용성 점수 | 규칙 기반 가용 라벨 | 상위 2행 선택 |
| ----- | ------ | ----------- | -------- |
| q1    | 0.9    | 1           | 선택       |
| q2    | 0.8    | 0           | 선택       |
| q3    | 0.7    | 1           | 제외       |
| q4    | 0.2    | 0           | 제외       |


이 네 행에서 `global` 모드로 상위 50%인 2행(`q1`, `q2`)을 고르면, 전체 데이터의 규칙 기반 가용 라벨(`1`) 두 개(`q1`, `q3`) 가운데 `q1` 하나만 회수된다. 이때 전체 가용 단서 가운데 건져 올린 비율인 가용 단서 재현율(`answerability_recall`)은 `1/2`이 된다. 동시에 선택한 2개 호출 가운데 `q2`는 가용 라벨이 `0`이므로, 불필요한 호출 비율을 뜻하는 호출 낭비율(`call_waste_rate`)도 `1/2`이 된다. 이 표의 수치는 계산 과정을 설명하려고 만든 예제 값이며, 모델을 호출해 답변을 생성하기 전에 라우팅 단계의 회수 성능만 따진다. 생성된 답변의 정답률은 모델을 실제로 호출한 이후 단계에서 따로 평가한다.


코드에서도 라우팅 지표는 모델의 실제 정답 여부가 아니라 규칙 기반 가용 라벨로 계산된다. `routing_rows_real` 함수는 `grounded_correct` 필드에 모델 답변의 정오답이 아니라 입력 데이터의 규칙 기반 가용 `label`을 그대로 복사한다. 이어서 `metric_at` 함수의 `evidence_supported_correct_yield`는 선택된 행들의 `grounded_correct` 값을 모두 더한다. 따라서 이 오프라인 라우팅 경로에서 말하는 **회수한 가용 쌍 수**(`yield`)는 모델이 맞힌 정답 수가 아니라, 라우터가 골라낸 규칙 기반 가용 쌍의 개수다. `calls_per_correct_answer` 역시 변수 이름만 보면 정답 하나를 얻는 데 든 호출 수 같지만, 실제 분모에는 같은 가용 라벨의 합계가 들어간다. 저장소의 [README](https://github.com/NAMUORI00/RoleSep-VQA/blob/775b34eafca5db8914522ac7a582a1d841a63773/README.md) 문서에도 이러한 오프라인 라우팅 지표의 정의가 따로 명시돼 있다. 변수 이름만 보아서는 논문 본문의 설명과 바로 짝짓기 어려웠는데, 값을 대입하는 코드 행을 따라가 보고서야 지표의 뜻이 명확해졌다. 라우팅이 단서가 있는 입력을 잘 추려내는지 평가하는 일과, 추려낸 입력으로 모델이 정확한 답을 작성하는지 평가하는 일은 서로 다른 단계의 문제다.


## 오프라인 시간 절감량 추정과 한계


러너는 선택된 행에서 회수한 가용 쌍 수를 구하는 것과 함께, 호출 수를 줄였을 때 절감되는 시간도 오프라인 수식으로 추정한다. 전체 행 수에 평균 생성 시간을 곱한 기준 시간에서, 선택된 호출 수의 생성 시간과 전체 전처리 시간을 빼는 방식이다. 예를 들어 전체 입력이 100행이고 그중 50행만 선택했으며, 행당 평균 생성 시간이 2초, 전처리 총시간이 10초라면 절감 시간은 `200−100−10=90초`로 계산된다.


![점수순으로 선택된 행에서 가용 라벨을 합산해 회수한 가용 쌍 수를 구하고, 선택 호출 수와 평균 생성 및 전처리 시간으로 오프라인 시간 차이를 계산하는 흐름도](/images/notion/tech-04-02/image-4.png)


그림 4. 선택된 행에서 회수한 가용 쌍 수(yield)와 오프라인 시간 절감 추정치를 계산하는 경로. 출처: metric_at과 routing_summary를 바탕으로 직접 구성.


다만 이 시간 절감량은 모든 호출에 고정된 평균 시간이 걸린다고 가정한 단순 비교치다. 실제 운영 환경에서는 입력 길이와 배치 묶음 처리, 대기열, 재시도 여부에 따라 응답 시간이 달라진다. 따라서 오프라인 수식으로 추정한 시간 차이는 병렬 실행과 대기 시간을 포함한 실제 측정값과 구분해 기록해야 한다.


## 결론


MV-EviRAG의 오프라인 평가 코드는 모델을 호출하기 전에 관련성과 가용성을 분리해 입력을 고르고, 규칙 기반 가용 라벨로 라우팅 단계의 회수 성능을 따로 평가한다. 호출 전 라우팅 판단을 이후 답변 평가와 분리해 두면 시스템이 실패했을 때 원인을 짚기가 한결 수월해진다. 어떤 입력을 어떤 점수로 골랐는지 따로 남겨 두어야 입력 단서가 부족했는지, 아니면 단서는 충분했는데 모델이 답변을 잘못 생성했는지 나누어 확인할 수 있다.


이번 분석에서는 올림 규칙에 따른 선택 호출 수 계산과 가용 라벨 기반 회수 지표(`yield`), 고정 평균 시간을 가정한 오프라인 시간 절감 수식을 확인했다. 반면 가용성 점수가 화면 가림과 구간 누락을 모두 찾아내는지, 병렬 실행이 포함된 실제 환경에서 시간이 얼마나 줄어드는지는 이 코드만으로 단정할 수 없다. 다음 글에서는 호출 이후의 확신 점수와 선택 위험을 다루며, 가용 쌍 선택과 답변 오류 억제가 어디서 갈라지고 평가 자료 확인 이력이 해석에 어떤 영향을 주는지 본다.
