CCTV RAG에서는 프레임 검색 결과를 답변의 인용으로 연결했다. 검색한 프레임과 실제 제공된 이미지가 같은 대상을 가리키도록 ID와 점수를 관리하고, 인용의 유효성을 검사하는 흐름을 정리했다.


## 구현과 확인 과정


CCTV_Video_Evidence_RAG_IEEE 저장소를 읽으며, 검색 결과에서 실제 영상 근거로 돌아가는 경로를 따라가 봤다. 답변에 '프레임 10'이라고만 적혀 있으면 어느 사건의 어느 카메라를 다시 열어야 할지 특정할 수 없고, 사건, 시점, 프레임을 함께 식별할 수 있는 구조가 필요하다.


저장소의 현재 문서는 CitationRAG와 Adaptive CitationRAG를 연구 패키지의 중심으로 설명하고 있었다. 프레임과 타임스탬프, 다중 시점, 근거 충분성에 관한 개념은 선행 글에서 다뤘으므로 여기서는 실제 관제 서비스의 운영 기록과 구분하여 코드의 데이터 경로만 읽었다.


## 사건, 시점, 프레임을 하나의 이름에 연결하기


[영상 근거 색인](https://github.com/NAMUORI00/CCTV_Video_Evidence_RAG_IEEE/blob/955287ba34233a9a87200cad62320c21b092c9e6/cctv_evr/evidence_index.py)의 EvidenceRecord에는 sample_id, view_id, video_name, frame_id, timestamp_sec, image_path가 들어간다.


record_id는 sample_id, view_id, 6자리 프레임 번호, 이미지 파일명을 이어 만든다. 프레임 번호만 같더라도 서로 다른 카메라의 장면이 같은 근거로 취급되지 않도록 각 축을 모두 포함하는 구조였다.


이 ID는 프레임의 식별 정보를 조합해 만든다. 이미지 내용의 무결성은 별도 해시로 확인해야 한다. 함수가 쓰는 것은 경로 전체가 아닌 마지막 파일명이라, 다른 디렉터리에서 같은 이름을 쓸 경우의 구분도 입력 계약에 달려 있다. 파일 이름이나 경로 구성 규칙이 바뀌면 식별자의 안정성이 어떻게 달라지는지도 생각할 필요가 있다.


색인 레코드를 만드는 함수는 method 이름에 oracle이 포함된 행을 제외한다. 정답 위치를 미리 알고 고른 프레임이 일반 검색 근거에 섞이지 않도록 하는 필터로 보인다. 다만 이름 필터 하나로 모든 정답 누출을 걸러내지는 못하므로, 상위 단계에서 행이 어떤 경로로 만들어졌는지까지 연결되어야 누출 여부를 판단할 수 있다.

## 30프레임을 1초로 읽는 가정


확인한 변환 함수는 frame_count가 있을 때 timestamp_sec를 frame_id/30.0으로 계산한다. 이 지점에 30fps라는 가정이 고정되어 있다.


설명용 프레임 300은 10초가 되지만, 실제 소스가 25fps라면 같은 번호는 단순 비율상 12초에 해당한다. 프레임 번호가 0부터인지 1부터인지, 영상에 가변 프레임 간격이 있는지도 정확한 시간 연결에 영향을 준다.


여러 카메라의 10초가 실제로 같은 사건 시각인지도 다른 문제다. 각 영상의 시작 시각이나 동기화 오프셋을 모르면 로컬 타임스탬프만으로 동시성을 보장할 수 없다. 그래서 이 코드를 읽으며 '초 단위 필드가 있다'와 '다중 카메라 시간이 검증됐다'를 나누어 적었다. 현재 함수가 제공하는 값은 명시된 변환 가정 아래의 시간이다.


[여러 단계의 영상 검색](https://github.com/NAMUORI00/CCTV_Video_Evidence_RAG_IEEE/blob/955287ba34233a9a87200cad62320c21b092c9e6/cctv_evr/multistage_retrieval.py)은 하위 질의별 후보를 합친 뒤 같은 sample과 view 안의 가까운 프레임을 추가한다.


temporal_window는 초가 아닌 프레임 번호 차이에 적용된다. 기본값 30은 30fps 가정에서 약 1초 범위에 대응되지만, 함수 자체가 영상의 실제 FPS를 참조하지는 않는다.


시간 확장 점수에도 구현 고유의 선택이 있었다. 추가 프레임에는 seed_scores 전체 최댓값에 0.95를 곱한 점수를 부여한다. 시간 거리에 따라 점수가 연속적으로 줄어드는 가중치와는 다른 방식이므로, 일반적인 시간 검색 원리와 이 구현의 점수 부여 규칙은 분리해서 읽었다.


## 유효한 인용이 확인하는 범위


[근거를 포함한 답변 생성](https://github.com/NAMUORI00/CCTV_Video_Evidence_RAG_IEEE/blob/955287ba34233a9a87200cad62320c21b092c9e6/cctv_evr/provenance_rag.py)은 선택한 근거 목록과 이미지를 모델 입력으로 조립하고, 답변에 인용 정보를 반환하도록 요청한다.


validate_citations는 인용 ID가 입력에 있거나 view_id, video_name, frame_id 조합이 입력과 맞으면 유효 인용으로 센다. 두 조건은 AND가 아닌 OR로, ID와 나머지 필드가 서로 모순되더라도 한쪽 조건만 충족하면 통과한다. 필드 간 일관성은 별도 검사가 필요하다.


![04-04-02.png](/images/notion/tech-04-04/image-2.png)


그림 2. 인용의 입력 목록 소속 여부와 내용의 의미적 지지를 구분한 검증 경로. 마지막 평가는 validate_citations의 검사 이후에 수행할 단계다. 출처: 직접 구성.


grounded_answer는 event_present가 참이고, 품질이 high 또는 medium이며, 보류 상태가 아니고, 유효 인용이 하나 이상인지를 조합한 값이다. 외부 정답과의 의미 비교는 이 조건에 포함되어 있지 않다.


invalid 인용이 0이어야 한다거나 answer_ko가 비어 있지 않아야 한다는 조건도 해당 식에는 없다. 따라서 이 값을 일반적인 자유서술 답변 정확도라고 읽기보다, 코드가 정의한 이벤트 중심 지표로 해석해야 한다.


예를 들어 입력 프레임 ID를 정확히 인용했어도 장면 해석 자체가 틀릴 수 있다. 반대로 답변 내용이 맞더라도 입력에 없는 프레임을 인용하면 출처 연결은 실패한다. 형식, 소속 검사와 의미 평가는 서로 다른 층위이고, 인용이 붙어 있다는 사실만으로 답변의 정확성이 보장되지는 않는다.


## 적응형 확장의 비용도 분리해서 보기


[두 검색 범위의 저장 결과를 선택하는 평가 코드](https://github.com/NAMUORI00/CCTV_Video_Evidence_RAG_IEEE/blob/955287ba34233a9a87200cad62320c21b092c9e6/scripts/wp59_adaptive_cost_router.py)는 저장된 K9와 K12 결과를 sample_id로 대응하고 결정에 따라 최종 행을 고른다.


최종 payload 값도 선택한 행에서 가져온다. 두 번의 실제 모델 호출 시간을 합산하는 계측과는 다른 경로다.


[README](https://github.com/NAMUORI00/CCTV_Video_Evidence_RAG_IEEE/blob/955287ba34233a9a87200cad62320c21b092c9e6/README.md)가 설명하는 추가 근거 재사용 가정과도 일치한다.


패킷 조립의 payload_bytes는 선택 프레임 수에 고정 바이트 상수를 곱한 값이다. 실제 네트워크 전송량이나 이미지 인코딩, API 과금과는 별도로 확인이 필요하다.


프레임 인용을 원본 영상으로 되짚는 경로를 정리하면서, 영상의 위치를 확인하는 것과 내용을 해석하는 것을 나누어 봤다. 다음 글에서는 같은 영상 안에서 사람의 ID가 프레임 사이에 이어지는 과정을 살펴본다. 위치를 특정한 뒤에도 이전 프레임의 사람과 같은 대상인지 판단하는 과정이 남는다.


## 작업을 정리하며


인용 ID의 유효성과 답변 내용의 정확성은 검사 단계를 나누는 편이 좋다. 프레임 식별자를 끝까지 유지하면 출처를 찾는 문제를 먼저 해결할 수 있고, 그 위에서 사건 해석의 정확성을 평가할 수 있다.
