여러 카메라로 찍은 CCTV 영상에서 필요한 화면을 찾아 답을 만드는 RAG 시스템은 답변과 함께 근거 프레임의 인용 정보를 내놓는다. 이때 답변에 '프레임 10'이라고만 적혀 있으면 어느 사건의 어느 카메라 영상을 다시 열어야 할지 알 수 없다. 답변의 인용에서 실제 영상 근거로 돌아가려면 사건과 카메라 시점, 프레임 번호를 하나로 묶어 식별해야 한다. 또한 모델이 인용한 프레임이 실제로 입력된 이미지 목록에 들어 있는지도 확인해야 한다.


`CCTV_Video_Evidence_RAG_IEEE` 저장소 문서는 연구 패키지의 중심으로 두 가지 경로를 설명한다. 인용을 바탕으로 답하는 `CitationRAG`와 검색 범위를 조절하는 `Adaptive CitationRAG`다. 프레임과 타임스탬프, 다중 시점, 근거 충분성 개념은 앞선 글에서 다뤘다. 여기서는 실제 관제 서비스의 운영 조건과 구분하여 코드가 프레임 식별자와 점수를 만들고 인용 유효성을 검사하는 경로를 따라간다.


## 사건과 시점을 묶은 프레임 식별자


답변의 인용을 실제 영상 위치로 되돌리려면 먼저 각 프레임에 사건과 카메라 정보를 담은 이름표를 붙여야 한다. 이 작업은 검색할 자료의 목록을 만드는 [영상 근거 색인](https://github.com/NAMUORI00/CCTV_Video_Evidence_RAG_IEEE/blob/955287ba34233a9a87200cad62320c21b092c9e6/cctv_evr/evidence_index.py) 모듈에서 시작한다. 이 모듈의 `EvidenceRecord` 데이터 구조에는 사건 식별자인 `sample_id`, 카메라 시점인 `view_id`, 영상 이름인 `video_name`이 들어간다. 여기에 프레임 번호인 `frame_id`, 초 단위 시간인 `timestamp_sec`, 이미지 경로인 `image_path`까지 함께 기록된다.


예를 들어 두 카메라 영상에서 똑같이 300번 프레임이 나왔더라도 사건이나 카메라 시점이 다르면 서로 다른 근거로 구별해야 한다. `make_record_id` 함수는 프레임마다 겹치지 않는 이름인 **고유 식별자** `record_id`를 만들어 이 문제를 푼다. 이 식별자는 `sample_id`와 `view_id`, 6자리로 맞춘 프레임 번호, 이미지 파일명을 차례대로 이어 붙인 문자열이다.


![사건 S의 카메라 A와 B에서 나온 프레임 300이 make_record_id를 통해 서로 다른 레코드 ID로 분리되어 색인과 검색 결과로 이어지는 흐름도](/images/notion/tech-04-04/image-1.png)


그림 1. 같은 프레임 번호라도 카메라별 레코드를 구분하고 검색 결과에 원본 위치를 남기는 구조(EvidenceRecord와 make_record_id를 바탕으로 직접 구성).


다만 이 식별자는 위치 정보만 이어 붙인 문자열이어서 이미지 파일 자체가 바뀌었는지는 알려 주지 못한다. 이미지 내용이 원본 그대로인지(무결성) 확인하려면 파일 내용에서 고유한 값을 뽑아내는 **파일 해시**가 따로 필요하다. 또한 `make_record_id`는 전체 폴더 경로가 아니라 마지막 파일 이름만 잘라 쓴다. 서로 다른 폴더에 이름이 같은 파일이 있을 때 식별자가 겹치지 않게 하려면 입력 데이터의 파일 이름 규칙에 의존해야 한다. 파일 이름이나 경로를 짓는 규칙이 바뀌면 식별자의 일관성도 영향을 받는다.


색인 레코드를 만드는 함수에는 `method` 항목에 `oracle`이라는 문자열이 들어간 행을 빼는 조건도 들어 있다. 정답 구간을 미리 알고 뽑아낸 프레임이 일반 검색 후보에 섞이지 않게 막는 필터로 보인다. 물론 `method` 이름만 검사해서는 정답이 새어 나오는 모든 경우를 걸러낼 수 없다. 실제로 정답 누출이 없는지 판단하려면 앞 단계에서 각 데이터 행을 어떤 경로로 만들었는지 함께 확인해야 한다.


## 시간 변환 가정과 주변 프레임 확장


앞서 색인 레코드에 식별자와 함께 기록한 시간 정보에도 코드만의 가정이 들어가 있고, 이 가정은 주변 프레임을 넓혀 찾는 단계까지 이어진다. 확인한 시간 변환 함수는 전체 프레임 수인 `frame_count`가 있을 때 `timestamp_sec`를 `frame_id / 30.0`으로 계산한다. 모든 영상을 1초에 30장씩 찍힌 초당 30프레임(30fps) 영상으로 고정해 해석하는 방식이다.


이 계산식에서 300번 프레임은 10초가 되지만, 실제 원본 영상이 25fps라면 같은 300번 프레임은 비율상 12초 지점이다. 프레임 번호를 0부터 매기는지 1부터 매기는지, 또는 영상의 프레임 간격이 일정하지 않고 바뀌는지에 따라서도 실제 시각은 달라진다.


여러 카메라에서 계산된 '10초'가 실제로 같은 순간에 일어난 장면인지도 별개의 문제다. 카메라별 녹화 시작 시각이나 시간 차이를 맞춘 보정값(동기화 오프셋)이 없으면 각 영상의 시간 값만으로 동시성을 보장할 수 없다. 따라서 레코드에 초 단위 항목이 있다는 사실과 여러 카메라의 시각이 동기화되었다는 사실은 구분해야 한다. 현재 함수가 기록하는 `timestamp_sec`는 명시된 30fps 변환 가정 아래에서 얻은 각 영상의 상대 시간이다.


이처럼 프레임 번호를 시간 대신 쓰는 방식은 [여러 단계의 영상 검색](https://github.com/NAMUORI00/CCTV_Video_Evidence_RAG_IEEE/blob/955287ba34233a9a87200cad62320c21b092c9e6/cctv_evr/multistage_retrieval.py) 모듈에서도 이어진다. 이 모듈은 하위 질의별로 찾은 후보 프레임을 합친 뒤 같은 `sample_id`와 `view_id` 안에서 시간상 가까운 주변 프레임을 후보군에 더한다. 이때 탐색 범위를 정하는 `temporal_window`는 초 단위가 아니라 프레임 번호 차이에 적용된다. 기본값인 `30`은 후보 프레임을 중심으로 앞뒤 30프레임까지 넓히는 값으로, 30fps 가정에서는 약 1초 범위에 해당한다. 그러나 함수 자체가 영상 파일에서 실제 FPS를 읽어 오지는 않는다.


![같은 sample_id와 view_id 안에서 frame_id 300을 중심으로 temporal_window 30 범위의 주변 프레임을 확장하고 최고 점수에 0.95를 곱해 부여하는 구조도](/images/notion/tech-04-04/image-2.png)


그림 2. 30fps 가정의 시간 변환과 프레임 번호 차이(temporal_window)를 기준으로 주변 프레임을 확장하고 점수를 부여하는 흐름.


주변 프레임을 후보에 추가할 때 점수를 매기는 규칙도 일반적인 시간 근접도 가중치와 다르다. 보통은 기준 프레임에서 시간 거리가 멀어질수록 점수를 조금씩 깎는 연속 감쇠 방식을 쓴다. 반면 이 코드는 초기 후보 점수 목록인 `seed_scores` 전체의 최댓값에 `0.95`를 곱한 값을 추가된 모든 프레임에 일괄 부여한다. 검색 점수를 해석할 때도 거리에 따른 감쇠가 아니라 이 고정 비율 규칙이 쓰였다는 점을 염두에 두어야 한다.


## 인용 유효성 검사와 답변 정확도의 구분


검색과 주변 프레임 확장을 거쳐 추려진 근거 목록과 이미지는 [근거를 포함한 답변 생성](https://github.com/NAMUORI00/CCTV_Video_Evidence_RAG_IEEE/blob/955287ba34233a9a87200cad62320c21b092c9e6/cctv_evr/provenance_rag.py) 모듈에서 모델의 입력으로 조립된다. 이 모듈은 이미지와 글을 함께 읽는 시각언어모델(VLM)에 근거 목록과 질문을 전달한다. 모델은 질문에 답하면서 자신이 참조한 근거 프레임의 인용 정보를 함께 돌려주도록 요청받는다.


모델이 돌려준 인용이 유효한지는 `validate_citations` 함수가 검사한다. 인용된 ID가 입력 근거 목록에 있거나, `view_id`와 `video_name`, `frame_id` 조합이 입력 목록과 일치하면 유효한 인용으로 센다. 여기서 두 조건은 둘 다 맞아야 하는 논리곱(AND)이 아니라 하나만 맞아도 되는 논리합(OR)으로 묶여 있다. 만약 모델이 입력 목록에 있는 ID를 적어 놓고 나머지 시점이나 프레임 번호는 엉뚱한 값으로 채워도 한쪽 조건이 맞으므로 유효 인용으로 통과한다. 따라서 인용 항목들 사이의 내적 일관성까지 보장하려면 별도의 교차 검사가 필요하다.


![validate_citations가 ID 또는 위치 조합 일치 여부로 유효 인용을 집계해 grounded_answer를 판정하고, 그 이후에 별도의 의미와 정답 평가를 수행하는 흐름도](/images/notion/tech-04-04/image-3.png)


그림 3. 인용의 입력 목록 소속 검사와 답변 내용의 의미 평가를 구분한 검증 경로(직접 구성).


유효 인용 개수는 근거 기반 답변 여부를 나타내는 후속 지표인 `grounded_answer`를 판정할 때 쓰인다. 코드에서 `grounded_answer`가 참이 되려면 사건 발생 여부를 뜻하는 `event_present`가 참이어야 한다. 동시에 답변 품질이 `high` 또는 `medium`이고, 답변 보류 상태가 아니며, 유효 인용이 하나 이상이어야 한다. 이 판정식에는 잘못된 인용(invalid)이 0개여야 한다거나 한국어 답변 항목인 `answer_ko`가 비어 있지 않아야 한다는 조건이 없다. 외부 정답 데이터와 답변의 의미를 비교하는 과정도 포함되지 않는다. 즉 `grounded_answer`는 자유서술형 답변의 내용 정확도가 아니라 코드가 정의한 이벤트 중심의 형식 지표다.


실제로 모델이 입력 목록에 있는 프레임 ID를 정확히 인용했더라도 장면 자체를 잘못 읽었으면 답변 내용은 틀릴 수 있다. 반대로 장면 설명은 사실과 맞더라도 입력에 없던 프레임 번호를 인용하면 출처 연결은 실패한다. 인용이 입력 목록에 속하는지 확인하는 **소속 검사**와 답변 내용이 타당한지 따지는 **의미 평가**는 서로 다른 층위의 문제다.


## 적응형 검색의 결과 선택과 비용 추정


인용 판정과 마찬가지로 검색 범위 확장에 따른 비용 지표도 코드의 계산 방식을 알아야 정확히 읽을 수 있다. [두 검색 범위의 저장 결과를 선택하는 평가 코드](https://github.com/NAMUORI00/CCTV_Video_Evidence_RAG_IEEE/blob/955287ba34233a9a87200cad62320c21b092c9e6/scripts/wp59_adaptive_cost_router.py)는 검색 범위를 달리해 미리 실행해 저장해 둔 `K9` 결과와 `K12` 결과를 읽는다. 두 결과를 `sample_id` 기준으로 대응시킨 뒤, 검색 범위를 넓힐지 정하는 라우터의 확장 결정에 따라 둘 중 하나를 최종 행으로 고른다.


이때 모델에 전달되는 데이터 양을 뜻하는 최종 비용 지표인 payload 값 역시 선택된 행의 기록을 그대로 가져온다. 1차 검색으로 모델을 호출한 뒤 근거가 부족할 때 2차로 모델을 다시 호출해 두 호출의 소요 시간이나 전송량을 합산하는 온라인 계측과는 다른 경로다. 이는 [README](https://github.com/NAMUORI00/CCTV_Video_Evidence_RAG_IEEE/blob/955287ba34233a9a87200cad62320c21b092c9e6/README.md) 문서에서 설명하듯 검색 범위를 넓힐 때 기존 근거를 재사용하고 추가 근거만 덧붙인다는 실험 가정과 맞닿아 있다.


![저장된 K9 결과와 K12 결과를 sample_id로 대응시켜 라우터가 최종 행을 고르고 그 행의 payload와 프레임 수 비례 payload_bytes를 산출하는 다이어그램](/images/notion/tech-04-04/image-4.png)


그림 4. 저장된 K9와 K12 결과를 sample_id로 대응해 최종 행과 비용 지표를 선택하는 평가 구조.


전송 데이터를 묶는 패킷 조립 단계의 바이트 크기인 `payload_bytes` 또한 선택된 프레임 수에 고정된 바이트 상수를 곱해 산출한다. 프레임 개수에 비례하는 추정치이므로 이미지 해상도나 압축 방식에 따라 달라지는 실제 네트워크 전송량은 별도로 측정해야 한다. 상용 API를 사용할 때의 실제 과금 단위 역시 따로 확인해야 한다.


## 결론


`CCTV_Video_Evidence_RAG_IEEE` 코드는 사건과 카메라 시점, 프레임 번호를 묶은 식별자를 끝까지 유지해 답변의 인용을 원본 영상 위치로 되돌려 놓는다. 인용된 프레임이 입력 목록에 있는지 따지는 소속 검사와 답변 내용을 따지는 의미 평가도 단계별로 분리되어 있다. 덕분에 모델이 실제로 입력받은 프레임을 인용했는지 먼저 확인한 뒤 그 위에서 장면 해석의 정확성을 따질 수 있다.


다만 코드에서 확인한 30fps 시간 변환, 0.95 고정 비율 점수, 논리합(OR) 인용 판정, 프레임 수 비례 비용은 실험용 계산 규칙이다. 이미지 변조 여부나 여러 카메라의 실제 시각 동기화, 서술형 답변의 내용 정확도는 이 규칙만으로 보장되지 않는다. 해상도와 압축 방식에 따른 실제 네트워크 전송량이나 상용 API 과금 단위 역시 별도로 측정해야 한다. 또한 특정 프레임의 위치를 정확히 찾아냈더라도 연속된 프레임에 등장하는 사람이 이전 프레임과 동일 인물인지 판단하는 문제는 여전히 남는다. 프레임 사이에서 객체 ID를 유지하고 끊어진 ID를 복구하는 과정은 `Detection_Track`을 다룬 글에서 이어진다.
