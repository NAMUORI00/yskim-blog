질문에 맞춰 답을 생성하는 언어 모델에게 사내 정비 매뉴얼이나 점검표처럼 학습 데이터에 없던 문서의 내용을 물으면 정확한 수치를 답하기 어렵다. 그렇다고 모델에 주는 입력문인 **프롬프트**(prompt)에 문서 전체를 매번 통째로 넣으면 한 번에 처리할 수 있는 입력 토큰 한도를 넘긴다. 한도를 넘기지 않더라도 질문과 무관한 내용이 섞여 답변 품질이 떨어진다.


[검색 증강 생성](https://arxiv.org/abs/2005.11401)(RAG, Retrieval-Augmented Generation)은 문서에서 질문과 관련된 부분만 찾아 프롬프트에 넣고 그 문맥으로 답을 얻는 방식이다. 다만 관련 문서를 찾아 넣었다고 해서 언어 모델이 언제나 그 문서에 맞는 답을 내놓는 것은 아니다. 이 글에서는 가상으로 만든 정비 문서 두 개와 질문 하나를 예로 삼아 문서 분할부터 검색, 프롬프트 조립, 답변 생성과 원문 대조까지의 과정을 따라간다. 각 단계가 어떤 결과를 만들고 어디서 원문과 어긋날 수 있는지 차례대로 확인한다.


## 문서 조각 분할과 식별 정보


질문에 필요한 부분만 문서에서 골라내려면 먼저 문서를 일정한 크기의 **조각**(chunk)으로 나누어야 한다. 분할 과정을 구체적으로 보기 위해 가상 정비 수치를 담은 문서 두 개를 가정한다.

- 문서 A(정비 매뉴얼): "엔진 오일은 5,000km마다 교환한다. 오일 필터는 오일 교환 시 함께 교체한다."
- 문서 B(안전 점검표): "타이어 공기압은 월 1회 점검한다. 브레이크 패드 두께가 3mm 이하이면 교체한다."

문서를 200자 단위로 자른다면 위 예제에서는 각 문서가 곧 하나의 조각이 된다. 긴 문서를 다루는 실제 시스템에서는 문장 중간이 잘리지 않도록 문단이나 문장 경계에 맞춰 자른다. 이때 이웃한 조각의 앞뒤 일부가 서로 겹치도록(overlap) 설정해 조각 경계에서 문맥이 끊기는 현상을 줄인다.


각 조각에는 본문 텍스트뿐 아니라 `문서 ID`, `조각 ID`, `원문 위치`를 함께 붙여 둔다. 나중에 언어 모델이 내놓은 답변이 근거 문장과 맞는지 대조할 때 원래 문서의 어느 문장에서 온 내용인지 추적하기 위해서다.


## 질문과 조각의 유사도 비교


문서를 조각으로 나누어 두었으면, 사용자가 "오일 교환 주기는?"이라고 질문했을 때 가장 관련 있는 조각을 찾아야 한다. 질문과 조각을 비교해 점수를 매길 때는 주로 키워드 기반 검색과 벡터 기반 검색 두 가지 방식을 쓴다.


**키워드 기반 검색**(BM25)은 질문과 조각에 공통으로 등장하는 단어의 출현 빈도와 희소성으로 점수를 계산한다. 설명을 위해 단어 경계와 활용형을 기본 형태로 맞추는 정규화를 거쳤다고 가정한다. 질문의 "오일"은 전체 2개 조각 중 조각 A 하나에만 등장하고, 조각 A 안에서 2회 출현한다. 모든 조각에 흔하게 나오는 단어보다 특정 조각에만 드물게 나오는 단어가 조각을 구별하는 데 유리하다. "교환" 역시 조각 A에만 등장하고 조각 B에는 두 단어 모두 빈도가 0이므로, 조각 B는 점수가 0에 가까워 조각 A가 선택된다.


**벡터 기반 검색**(임베딩 유사도)은 질문과 조각을 각각 고정 길이의 숫자 배열인 벡터로 변환한 뒤 코사인 유사도를 계산한다. 학습된 임베딩 모델이 "교환"과 "교체"처럼 뜻이 비슷한 단어를 가까운 벡터로 표현한다면, 질문과 조각의 단어가 글자 그대로 일치하지 않아도 관련 조각을 찾을 수 있다.

## 검색 결과의 프롬프트 조립


비교가 끝나면 검색 점수가 높은 상위 k개 조각을 골라 언어 모델의 프롬프트에 넣는다. 예제에서 가져올 개수인 k=1로 두면 점수가 가장 높은 조각 A만 선택된다. 선택된 조각 A와 질문을 합쳐 언어 모델에 전달하는 입력은 다음과 같다.


```plain text
[문맥]
출처: 문서 A (정비 매뉴얼)
엔진 오일은 5,000km마다 교환한다. 오일 필터는 오일 교환 시 함께 교체한다.

[질문]
오일 교환 주기는?
```


프롬프트에 들어간 조각 A는 언어 모델이 답변할 때 참조할 문맥이 된다. 다만 문맥을 입력에 넣어 주었다고 해서 모델이 그 내용을 충실하게 반영했는지는 보장되지 않으므로, 답변을 만든 뒤에 원문과 다시 대조해야 한다. 문맥 밖의 사실이 항상 틀린 말은 아니지만, 이 매뉴얼을 근거로 한 답이라고 제시하려면 해당 내용을 원문 문장에서 확인할 수 있어야 한다.


![문서 A와 문서 B를 조각으로 나눈 뒤 질문과 유사도를 비교해 상위 1개 조각으로 프롬프트를 구성하고 생성 모델이 답변과 출처를 내놓는 흐름도](/images/notion/tech-k05/image-2.png)

## 답변 생성과 근거 문장 대조


프롬프트를 받은 언어 모델은 주어진 문맥을 바탕으로 답변을 만들고, 시스템은 그 답변의 출처를 밝힌다. 모델이 "엔진 오일은 5,000km마다 교환합니다."라는 답을 내놓았다면, 이 답변의 근거 조각은 조각 A이고 출처는 문서 A다.


답변에 출처를 명시할 때는 모델이 직접 출력하게 하거나 후처리에서 연결하는 두 가지 방식을 쓴다. 하나는 프롬프트에 "답변에 사용한 문맥의 출처를 밝혀라"라는 지시를 함께 넣어 모델이 출처를 직접 출력하게 하는 방식이다. 다른 하나는 답변 생성이 끝난 뒤 후처리 단계에서 답변 문장과 검색된 조각을 대조해 연결하는 방식이다.


그런데 검색한 조각의 출처를 답변에 붙이기만 해서는 문장별 근거까지 검증되지 않는다. 예를 들어 문서 A를 찾아 놓고도 정작 답변에는 문서 B의 수치나 다른 숫자를 잘못 적을 가능성이 있다. 따라서 `검색에 사용한 자료`와 실제로 `해당 답변 문장을 지지하는 자료`를 구분해 두어야 생성된 답변이 근거 문장과 어긋나는 오류를 대조해 잡아낼 수 있다.


## 검색 누락과 생성 오류의 구분


근거 자료를 구분해야 하는 이유는 답변이 틀렸을 때 검색 단계의 실패인지 생성 단계의 오류인지 나누어 확인해야 하기 때문이다. 검색 단계에서 문서 A를 제대로 가져왔더라도 언어 모델이 숫자를 바꾸거나 다른 차종의 기준처럼 서술하면 답변이 어긋난다. 반대로 검색에서 문서 A를 놓쳤는데도 모델이 사전 학습 지식으로 우연히 같은 숫자를 답할 수도 있다. 최종 정답률 하나만 보면 검색이 실패한 것인지, 생성이 근거에서 벗어난 것인지 구분하기 어렵다.


![관련 조각 검색 여부를 먼저 확인해 검색 누락을 기록하고, 검색 성공 후에는 답변의 수치를 원문이 지지하는지 대조해 답변 공개 또는 수정과 보류를 결정하는 순서도](/images/notion/tech-k05/image-3.png)


그림 3. 검색 누락과 근거에 맞지 않는 생성을 나누어 확인하는 판단 흐름(설명용 예제).


검색, 문맥 구성, 답변 생성을 단계별로 나누어 확인하면 문제가 생겼을 때 수정할 대상도 분명해진다. 관련 조각 자체를 놓쳤다면 조각 분할 크기나 검색 조건을 손봐야 한다. 반면 알맞은 조각을 가져왔는데도 답이 어긋났다면 프롬프트 조립 방식이나 생성 후 원문 대조 단계를 점검해야 한다.


여러 RAG 구조를 비교할 때도 특정 프레임워크의 이름보다 검색, 문맥 조립, 근거 대조의 책임이 각각 어느 단계에 놓여 있는지를 먼저 보면 전체 흐름을 파악하기 쉽다. 각 단계의 세부 변형과 비교는 [Gao 등의 RAG 조사 논문](https://arxiv.org/abs/2312.10997)에서 더 넓게 확인할 수 있다.


## 결론


RAG는 문서 조각 분할, 유사도 검색, 프롬프트 조립, 답변 생성과 원문 대조가 차례로 이어지는 과정이다. 최종 답변의 정답 여부만 보면 검색에서 조각을 놓친 것인지, 생성에서 근거 문장을 벗어난 것인지 알 수 없다. 따라서 `검색에 사용한 자료`와 `해당 답변 문장을 지지하는 자료`를 구분하고, 검색 성공 여부와 원문 지지 여부를 단계별로 나누어 확인해야 한다.


이 글에서는 단어 정규화를 가정한 짧은 가상 문서 두 개와 k=1 조건으로 검색부터 근거 대조까지의 흐름을 확인했다. 실제 긴 문서의 조각 분할, 임베딩과 BM25의 세부 계산, 여러 조각을 조립할 때의 토큰 예산 관리는 이어지는 글에서 따로 다룬다.
