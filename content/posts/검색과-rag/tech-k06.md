문서 검색이나 분류 시스템을 만들다 보면 ‘엔진 점검’과 ‘동력 장치 정비’처럼 겹치는 단어가 없는 두 문장을 비교해야 할 때가 있다. 컴퓨터는 글자의 뜻을 곧바로 비교할 수 없으므로, 먼저 문장을 숫자를 나열한 배열인 벡터로 바꾼다. 이렇게 텍스트를 벡터 공간의 좌표로 옮긴 표현을 **임베딩**(embedding)이라 부른다. 문장을 벡터로 바꾸면 두 좌표가 얼마나 가까운지 숫자로 계산할 수 있다. 이때 자주 쓰는 **코사인 유사도**(cosine similarity)는 원점에서 두 벡터가 가리키는 방향을 비교하는 지표다.


검색 시스템은 사용자의 질의 문장과 문서를 각각 벡터로 바꾼 뒤, 코사인 유사도가 기준값 이상인 문서를 상위 결과로 고른다. 다만 유사도 점수가 높다고 해서 두 문장의 실제 뜻까지 비슷하다고 단정할 수는 없다. 질의와 문서를 벡터로 바꿔 점수를 매기는 흐름은 같더라도, 좌표를 만드는 규칙에 따라 같은 문장 쌍의 점수가 크게 달라지기 때문이다. 이 글에서는 코사인 유사도의 계산 과정을 2차원 예제로 먼저 확인하고, 해시 함수로 좌표를 정하는 방식과 신경망 학습으로 좌표를 정하는 방식이 어떤 차이를 내는지 비교한다.

## 2차원 벡터의 코사인 유사도 계산


앞서 소개한 코사인 유사도가 두 벡터의 방향을 어떻게 비교하는지 작은 예제로 계산해 본다. 실제 검색 시스템에서 쓰는 임베딩은 숫자가 수백 개를 넘는 수백 차원이지만, 유사도를 계산하는 원리는 숫자 두 개로 좌표를 찍는 2차원 평면에서도 똑같다. 설명을 위해 세 문장이 아래 표와 같은 2차원 벡터로 변환되었다고 가정하자.


| 문장             | 벡터      |
| -------------- | ------- |
| A: "우주 비행체 추진" | (3, 4)  |
| B: "로켓 엔진 추력"  | (2, 5)  |
| C: "항공 예약 오류"  | (5, −1) |


[코사인 유사도](https://sbert.net/docs/sentence_transformer/usage/semantic_textual_similarity.html)는 두 벡터의 내적을 각 벡터 크기의 곱으로 나눈 값이다. 내적은 A(3, 4)와 B(2, 5)에서 3×2 + 4×5를 계산하듯 같은 위치의 성분을 곱해 모두 더한 값이다. 벡터의 크기는 원점 (0, 0)에서 그 좌표까지의 거리이며, 내적을 두 벡터의 크기로 나누면 길이 차이는 상쇄되고 두 벡터 사이의 각도만 남는다. 계산 결과는 −1에서 1 사이로 나오고, 두 벡터가 같은 방향을 가리킬수록 1에 가까워진다.


```plain text
|A| = √(9+16) = 5,  |B| = √(4+25) ≈ 5.385,  |C| = √(25+1) ≈ 5.099

cos(A, B) = (3×2 + 4×5) / (5 × 5.385) = 26 / 26.93 ≈ 0.966
cos(A, C) = (3×5 + 4×(−1)) / (5 × 5.099) = 11 / 25.50 ≈ 0.431
cos(B, C) = (2×5 + 5×(−1)) / (5.385 × 5.099) = 5 / 27.46 ≈ 0.182
```


계산 결과를 좌표 평면에 옮기면 A와 B의 코사인 유사도는 약 0.966으로 두 벡터가 거의 같은 방향을 가리킨다. 반면 A와 C는 약 0.431이고, B와 C는 약 0.182에 그쳐 원점에서 뻗어 나가는 방향이 크게 벌어져 있다.


![2차원 좌표 평면의 원점에서 뻗어 나가는 세 벡터 A(3, 4), B(2, 5), C(5, -1)의 방향과 A-B 사잇각(cos 약 0.966), B-C 사잇각(cos 약 0.182)을 비교한 그림](/images/notion/tech-k06/image-2.png)

이처럼 코사인 유사도는 좌표의 절대적인 길이가 아니라 원점에서 뻗어 나가는 각도를 비교한다. 0이 아닌 벡터라면 계산 과정에서 크기 차이가 정규화되지만, 문장을 벡터로 만드는 단계에서는 원문의 길이가 임베딩의 방향 자체에 영향을 줄 수 있다. 또한 모든 성분이 0인 영벡터는 크기가 0이어서 나눗셈의 분모가 0이 되므로 코드에서 따로 예외 처리를 해야 한다.


## 해시 기반 벡터 생성 규칙과 한계


코사인 유사도로 방향을 비교하려면 먼저 문장을 숫자 좌표로 바꾸는 규칙이 필요한데, 가장 단순한 방법은 별도의 모델 없이 해시 함수를 쓰는 것이다. 해시 함수는 어떤 글자를 넣든 정해진 길이의 숫자로 바꿔 주는 계산 규칙이다. 해시 기반 벡터가 동작하는 방식을 구체적으로 보기 위해 다음과 같은 설명용 규칙을 세웠다.

1. 입력 문장을 단어 조각인 토큰으로 분리한다.
2. 각 토큰의 SHA-256 해시값을 구한다.
3. 해시값의 처음 4바이트를 384로 나눈 나머지(`해시값 mod 384`)로 384차원 벡터에서 값을 넣을 위치(인덱스)를 정한다.
4. 5번째 바이트로 그 위치에 더할 값의 양수, 음수 부호를 정한다.
5. 같은 토큰이 여러 번 나오면 나온 횟수에 따라 `1 + log(빈도)`로 가중치를 준다.
6. 모든 토큰을 처리한 뒤 벡터의 크기가 1이 되도록 나누는 **L2 정규화**(L2 normalization)를 거쳐 단위 벡터를 만든다.

이 방식의 가장 큰 특징은 데이터에서 단어의 뜻을 배우는 학습 과정이 전혀 없다는 점이다. "로켓"이라는 단어의 SHA-256 해시값은 어떤 문맥에서 등장하든 항상 같다. 그래서 뜻이 비슷한 "로켓"과 "발사체"도 글자가 다르므로 서로 다른 해시값을 얻게 되고, 384차원 공간에서 가까운 위치에 놓일 근거가 없다.


![입력 토큰 로켓과 발사체가 SHA-256 해시와 mod 384 연산을 거쳐 384차원 벡터의 서로 다른 인덱스에 배치된 뒤 L2 정규화 단위 벡터가 되는 과정](/images/notion/tech-k06/image-3.png)


그림 3. SHA-256 해시값으로 벡터 위치와 부호를 정하는 규칙에서 동의어가 서로 다른 인덱스로 배치되는 과정 (설명용 예제)


또한 같은 토큰은 언제나 같은 인덱스에 값을 더하지만, 뜻이 다른 토큰도 `mod 384` 연산 결과가 같으면 우연히 같은 인덱스에 들어갈 수 있다. 이렇게 서로 다른 단어가 같은 위치에 겹치는 해시 충돌은 단어 사이의 의미 관계를 학습해 가까워진 결과와는 전혀 다르다.


## 문맥 학습 기반 임베딩


해시 기반 벡터가 고정된 계산 규칙만 쓰는 것과 달리, 학습 기반 임베딩은 대량의 글을 읽으며 비슷한 문맥에 나오는 단어가 가까운 좌표를 갖도록 신경망 가중치를 조정한다. 2013년 Mikolov 등이 발표한 [word2vec](https://arxiv.org/abs/1301.3781)은 단어 표현을 신경망으로 학습하는 대표적인 초기 연구다. 이 논문에서 제시한 **Skip-gram**(스킵그램) 방식은 중심 단어 하나로 앞뒤에 나타날 주변 단어를 예측하는 과정을 반복한다. 이 학습을 거치면 비슷한 문맥에서 쓰이는 단어들이 벡터 공간의 가까운 곳으로 자연스럽게 모인다. 그 결과 "king − man + woman ≈ queen"처럼 단어 사이의 의미 관계가 벡터 연산으로 나타나는 공간이 만들어진다.


단어 단위의 표현을 문장 단위로 확장한 모델이 [Sentence-BERT](https://arxiv.org/abs/1908.10084)(Reimers & Gurevych, 2019)다. 이 모델은 가중치를 공유하는 두 신경망에 문장을 각각 통과시켜 비교하는 시아미즈 네트워크(Siamese network) 구조를 BERT 위에 올렸다. 문장 전체를 벡터 하나로 압축한 뒤 의미가 비슷한 문장 쌍의 코사인 유사도가 높아지도록 학습시킨다.


따라서 같은 입력 문장이라도 토큰 분리 뒤에 SHA-256 해싱을 거치는 해시 경로와 사전학습 가중치로 신경망 인코딩을 거치는 학습 경로는 서로 다른 벡터를 만든다. 사전학습 가중치를 거쳐 만든 벡터 공간에서는 단어가 겹치지 않는 "로켓 추진 원리"와 "발사체 엔진 작동"도 가까운 좌표에 놓일 수 있다. 다만 이런 근접성을 학습으로 얻으려는 구조라 하더라도, 다루는 분야의 문장 쌍이 실제로 가까이 배치되는지는 사용할 모델에서 직접 확인해야 한다.


![입력 문장이 토큰 분리 후 해시 경로(SHA-256 해싱, 고정 위치 벡터)와 학습 경로(사전학습 가중치, 신경망 인코딩, 의미 반영 벡터)로 나뉘어 코사인 유사도 비교로 이어지는 흐름도](/images/notion/tech-k06/image-4.png)

## 두 벡터 방식의 비교와 점검 조건


앞서 본 두 경로의 차이는 뜻이 비슷한 동의어나, 글자는 같고 뜻이 다른 단어가 들어간 문장을 비교할 때 뚜렷하게 드러난다. 예를 들어 단어가 겹치지 않는 "추진 시스템"과 "엔진 장치", 그리고 같은 글자가 다른 뜻으로 쓰인 "사과 재배"와 "사과하는 방법"을 비교하는 상황을 생각해 보자. 아래 표는 두 방식으로 만든 벡터를 검증할 때 확인해야 할 입력 조건을 정리한 것이다.


| 확인할 입력          | 해시 기반 벡터에서 점검할 것 | 학습 기반 임베딩에서 점검할 것     |
| --------------- | ---------------- | --------------------- |
| 같은 문장 두 번       | 동일 전처리와 해시 규칙인지  | 동일 모델과 입력 조건인지        |
| 추진 시스템 / 엔진 장치  | 공유 토큰과 해시 충돌     | 동의어를 가까이 두는지 실제 비교    |
| 사과 재배 / 사과하는 방법 | 같은 토큰의 겹침        | 서로 다른 문맥을 구분하는지 실제 비교 |


문장을 다듬고 토큰을 나누는 전처리 조건과 모델이 같다면, 0이 아닌 벡터를 자기 자신과 비교한 코사인 유사도는 항상 1이다. 하지만 서로 다른 두 문장의 유사도는 학습 데이터와 전처리 방식, 문맥에 따라 크게 달라진다. "추진 시스템"과 "엔진 장치"처럼 단어가 다른 동의어 표현은 해시 기반 벡터에서 공유하는 토큰이 없어 우연한 해시 충돌이 아니면 유사도가 낮게 나온다. 반대로 "사과 재배"와 "사과하는 방법"처럼 글자는 같고 뜻이 다른 동음이의어나 다의어가 들어가면, 해시 기반 벡터는 "사과"를 무조건 같은 위치에 넣는다. 반면 학습 기반 임베딩은 주변 단어의 문맥을 반영해 두 문장을 다른 방향으로 분리할 여지가 있다. 그렇다고 해서 의미 검색이라는 이름만으로 모든 동의어나 다의어를 잘 처리한다고 볼 수는 없으므로 실제 데이터로 비교해 봐야 한다.


해시 기반 벡터는 외부 모델을 메모리에 올리지 않고도 빠르게 계산할 수 있어 파이프라인의 기본 동작을 점검하는 출발점으로 쓰기 좋다. 학습 기반 임베딩은 단어 너머의 의미 관계를 반영할 수 있는 대신 모델을 불러오는 시간과 메모리, 도메인 검증 비용이 따른다.


## 결론


문장을 숫자 배열로 바꾼 임베딩과 코사인 유사도를 쓰면 두 문장의 벡터가 가리키는 방향을 −1에서 1 사이의 값으로 비교할 수 있다. 다만 유사도 점수가 문장의 실제 의미와 맞닿아 있는지는 좌표를 만드는 방식에 따라 달라진다. 해시 기반 벡터는 별도 모델 없이 파이프라인을 빠르게 점검할 수 있지만, 글자가 같은 토큰만 같은 위치에 넣을 뿐 동의어의 의미 관계는 반영하지 못한다. 반면 문맥을 학습한 임베딩은 단어가 달라도 뜻이 비슷한 문장을 가까이 두고 다의어가 들어간 문장을 문맥에 따라 다른 방향으로 나눌 여지가 있다. 다만 모델을 불러오는 비용이 따르고, 다루는 분야의 동의어를 실제로 가까이 두고 다의어를 잘 구분하는지는 실제 데이터로 직접 확인해야 한다.


임베딩과 코사인 유사도는 문장의 의미 방향을 비교하는 데 유리하지만, 실제 검색에서는 "추진"처럼 특정 단어가 정확히 들어간 문서를 찾아야 할 때도 많다. 다음 글에서는 단어가 등장한 문서를 빠르게 찾는 목록인 역색인과 단어 빈도 기반 점수인 BM25를 다룬다. 이어서 −1에서 1 사이인 코사인 유사도와 0에서 수십까지 나오는 BM25 점수처럼 단위가 서로 다른 검색 결과를 하나로 합치는 방법을 확인한다.
