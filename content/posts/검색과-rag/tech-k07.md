## 매번 문서를 모두 읽는 대신 단어 목록을 남기기


문서 모음에서 특정 단어가 들어간 문서를 찾을 때, 질문이 들어올 때마다 모든 본문을 처음부터 끝까지 읽으면 문서가 늘어날수록 탐색 시간이 길어진다. 단어가 포함된 문서를 골라냈더라도 어떤 문서가 질문과 더 밀접한지 순서를 정하는 기준이 추가로 필요하다.


단어 기반 검색은 이 과정을 후보 탐색과 순위 계산의 두 단계로 나눈다. 준비 단계에서는 단어마다 그 단어가 등장하는 문서 목록을 정리해 **역색인**(inverted index)을 만든다. 문서를 새로 추가할 때 색인을 갱신하는 비용이 들지만, 검색이 반복될 때 본문 전체를 읽지 않고도 후보 문서를 바로 추려 낼 수 있다. 이어서 검색 단계에서는 추려진 후보들을 대상으로 **BM25** 같은 점수식을 적용해 단어 빈도, 문서 길이, 단어의 희소성을 바탕으로 순위를 매긴다.


## 문서 세 개로 역색인 만들기


작은 예제로 역색인이 어떻게 만들어지고 쓰이는지 따라가 본다. 한국어를 실제로 처리할 때는 형태소 분석이나 서브워드 분할 같은 방법을 함께 검토해야 하지만, 여기서는 원리를 단순하게 보기 위해 공백으로 나눈 단위를 토큰으로 삼는다.


| 문서 | 내용                          | 토큰 수 |
| -- | --------------------------- | ---- |
| D1 | 추진 시스템 설계 추진 원리 분석          | 6    |
| D2 | 항공기 날개 설계                   | 3    |
| D3 | 추진 로켓 연료 분석 추진 체계 시스템 검증 성능 | 9    |


세 문서에서 단어를 뽑아 각 단어가 등장한 문서 번호를 묶으면 다음과 같은 역색인이 만들어진다.


| 단어  | 등장 문서  |
| --- | ------ |
| 추진  | D1, D3 |
| 시스템 | D1, D3 |
| 설계  | D1, D2 |
| 분석  | D1, D3 |
| 원리  | D1     |
| 항공기 | D2     |
| 날개  | D2     |
| 로켓  | D3     |
| 연료  | D3     |
| 체계  | D3     |
| 검증  | D3     |
| 성능  | D3     |


이제 사용자가 "추진"을 검색하면 역색인에서 "추진" 행만 찾아 D1과 D3을 바로 꺼낼 수 있다. 문서 세 개를 일일이 열어 보지 않아도 어느 문서가 후보인지 곧바로 드러난다.

## 빈도만으로 점수를 매기면 생기는 문제


역색인으로 후보 문서를 추렸다면 다음에는 어떤 문서가 검색어와 더 관련이 깊은지 순위를 매겨야 한다. 가장 단순한 기준은 문서 안에 검색어가 몇 번 나왔는지 세는 **단어 빈도**(tf, term frequency)다. 하지만 등장 횟수만 세면 두 가지 한계에 부딪힌다.


첫째는 문서 길이에 따른 비중 차이다. 앞선 예제에서 "추진"은 D1에 2번, D3에도 2번 등장한다. 등장 횟수만 비교하면 두 문서는 동점이지만, 전체 토큰 수를 함께 보면 D1은 6개 중 2개가 "추진"이고 D3은 9개 중 2개가 "추진"이다. 짧은 문서에서 같은 횟수로 등장한 단어가 문서 안에서 차지하는 비중이 더 크다. 문서 길이를 반영하지 않으면 단어가 많이 들어갈 수밖에 없는 긴 문서가 유리해진다.


둘째는 단어마다 다른 변별력이다. "설계"는 D1과 D2 두 문서에 나오지만 "로켓"은 D3 한 문서에만 나온다. 여러 문서에 흔하게 쓰이는 단어보다 특정 문서에만 드물게 나타나는 단어가 문서를 구별하는 데 더 중요한 단서가 된다. 세 문서 가운데 두 문서에 들어 있는 "설계"로는 대상을 좁히기 어렵지만, "로켓"은 D3을 바로 가리킨다.

## BM25로 세 문서의 점수 계산하기


BM25는 단어가 반복될수록 점수 증가 폭을 완만하게 줄이면서, 문서 길이와 단어의 희소성을 함께 점수에 반영한다. 라이브러리마다 문서 길이를 정규화하거나 상수를 처리하는 세부 방식은 조금씩 다르다. 여기서는 널리 쓰이는 BM25 식에 [Lucene의 BM25Similarity 문서](https://lucene.apache.org/core/9_12_1/core/org/apache/lucene/search/similarities/BM25Similarity.html)와 같은 양수 **역문서 빈도**(IDF, inverse document frequency) 식을 적용해 손으로 계산해 본다.


```plain text
score(D, Q) = Σ IDF(q) × tf(q,D) × (k₁ + 1) / (tf(q,D) + k₁ × (1 − b + b × |D| / avgdl))
```


점수식을 이루는 각 항목의 의미는 다음과 같다.

- `tf(q, D)`: 질의 단어 `q`가 문서 `D`에 등장하는 횟수다.
- `IDF(q)`: 역문서 빈도다. 전체 문서 가운데 단어 `q`가 등장하는 문서가 적을수록 값이 커진다.
- `|D|`: 문서 `D`의 전체 토큰 수다.
- `avgdl`: 전체 문서의 평균 토큰 수다.
- `k₁`: 단어 빈도가 점수에 반영되는 포화 속도를 조절하는 매개변수다. 값이 클수록 단어가 여러 번 나올 때 점수가 더 오래 올라간다.
- `b`: 문서 길이를 보정하는 강도다. `0`이면 문서 길이를 전혀 반영하지 않고, `1`이면 문서 길이 비율을 그대로 반영한다.

![질의 단어와 대상 문서에서 계산한 tf에 문서 길이 비율로 빈도 보정을 수행하고, 역색인에서 계산한 IDF와 합산해 BM25 점수를 구하는 흐름도](/images/notion/tech-k07/image-3.png)


그림 3. BM25 점수를 구성하는 단어 빈도, 문서 길이 보정, 역문서 빈도가 하나의 점수로 합쳐지는 흐름 (설명용 예제)


이제 앞선 세 문서에서 검색어 "추진"이 들어왔을 때의 점수를 `k₁ = 1.5`, `b = 0.75` 조건으로 계산해 본다.


먼저 "추진"의 `IDF`를 구한다. 전체 문서 수는 `N = 3`이고, "추진"이 등장하는 문서 수는 `n = 2`다.


```plain text
IDF("추진") = ln((3 − 2 + 0.5) / (2 + 0.5) + 1)
            = ln(0.6 + 1)
            = ln(1.6)
            ≈ 0.470
```


세 문서의 평균 토큰 수 `avgdl`은 `(6 + 3 + 9) / 3 = 6`이다. 문서 D1은 "추진"이 두 번 나오므로 `tf = 2`이고, 문서 길이는 `|D| = 6`이다.


```plain text
0.470 × (2 × 2.5) / (2 + 1.5 × (1 − 0.75 + 0.75 × 6/6))
= 0.470 × 5 / (2 + 1.5 × 1.0)
= 0.470 × 5 / 3.5
= 0.470 × 1.429
≈ 0.671
```


문서 D3도 "추진"이 두 번 나와 `tf = 2`이지만, 문서 길이가 `|D| = 9`로 평균보다 길다.


```plain text
0.470 × 5 / (2 + 1.5 × (1 − 0.75 + 0.75 × 9/6))
= 0.470 × 5 / (2 + 1.5 × 1.375)
= 0.470 × 5 / 4.0625
= 0.470 × 1.231
≈ 0.578
```


문서 D2에는 "추진"이 등장하지 않으므로 `tf = 0`이어서 점수도 `0`이 된다.


계산 결과를 나열하면 `D1(0.671) > D3(0.578) > D2(0)` 순이다. D1과 D3 모두 "추진"이 두 번씩 들어 있지만, 전체 길이가 더 짧은 D1에서 단어 밀도가 높다는 점이 점수 차이로 나타난다.


## 매개변수 b를 바꾸면 달라지는 것


문서 길이 보정 항이 실제 점수에 얼마나 영향을 주는지 확인하기 위해, 같은 예제에서 매개변수 `b`만 바꿔 비교해 볼 수 있다.


`b = 0`으로 두면 분모의 길이 보정 항 `(1 − b + b × |D| / avgdl)`은 문서 길이와 상관없이 항상 `1.0`이 된다. 이 경우 D1과 D3 모두 분모가 `2 + 1.5 × 1.0 = 3.5`가 되어 두 문서의 점수가 `0.671`로 같아진다. 문서 길이가 6이든 9이든 점수 차이가 사라지는 것이다.


반대로 `b = 1`로 두면 평균 길이 대비 문서 길이 비율인 `|D| / avgdl`이 분모에 그대로 반영되어 긴 문서가 받는 감점이 가장 커진다. D3의 길이 보정 항은 `(0 + 1 × 9/6) = 1.5`가 되어 `b = 0.75`일 때의 `1.375`보다 커지고, 분모가 커진 만큼 최종 점수는 더 낮아진다.


![b가 0일 때는 D1과 D3의 점수가 0.671로 같고, b가 0.75일 때는 D3 보정 항이 1.375가 되어 D1(0.671)이 D3(0.578)보다 높아지며, b가 1일 때는 D3 보정 항이 1.5로 커져 감점이 증가함을 비교한 그림](/images/notion/tech-k07/image-4.png)


그림 4. 매개변수 b 값에 따라 긴 문서 D3의 길이 보정 항과 D1 대비 점수 차이가 달라지는 양상을 비교한 예제.


이처럼 매개변수 값에 따라 점수 분포가 달라지는데, 검색 라이브러리마다 기본값도 조금씩 다르다. 앞선 계산에서는 `k₁ = 1.5`, `b = 0.75`를 썼지만, Lucene 9.12.1 문서의 기본 `k₁`은 `1.2`다. 같은 BM25를 쓰더라도 구현체의 기본 설정을 먼저 확인해야 하는 이유다.


문서 길이가 대체로 비슷한 문서 모음에서는 기본 설정을 기준선으로 삼아도 무리가 없다. 다만 짧은 메타데이터와 긴 본문이 한데 섞여 문서 길이 편차가 큰 환경이라면 `b` 값을 조절해 길이 보정 강도를 맞춰 볼 필요가 있다.


## 단어 일치 검색의 한계와 다음 질문


지금까지 살펴본 것처럼 역색인은 전체 문서를 훑지 않고 후보를 빠르게 추려 내고, BM25는 단어 빈도와 문서 길이, 단어의 희소성을 조합해 순위를 매긴다. 하지만 두 방법 모두 질문과 문서에 같은 토큰이 들어 있어야 동작한다. 앞선 예제에서 "추진" 대신 "엔진 구동"으로 검색하면 뜻이 비슷하더라도 겹치는 토큰이 없어 후보에서 빠진다.


이런 어휘 불일치 문제는 문장을 임베딩해 의미를 비교하는 벡터 검색으로 보완할 수 있다. 다만 키워드 검색과 벡터 검색을 함께 쓸 때는 두 점수를 합치는 방식이 새로운 문제가 된다. BM25 점수는 `0`에서 수십까지 커질 수 있는 반면 코사인 유사도는 `-1`에서 `1` 사이에 머물기 때문에, 두 점수를 그대로 더하면 값의 범위가 큰 쪽이 순위를 좌우하게 된다. 다음 글에서는 점수 척도가 다른 여러 검색 결과를 순위 기준으로 결합하는 방법을 이어서 다룬다.
