## 검색 평가용 질문의 구성


검색 방식을 비교하기 위해 관련 문서 판정 기준과 평가셋 구성을 먼저 정리했다. 맨 위 결과가 그럴듯해도 필요한 근거를 모두 찾았는지는 다른 문제다. 질문별 정답 목록을 준비한 뒤 순위를 계산하는 흐름으로 살펴봤다.


정보 검색 분야에서 이 정답 목록을 보통 qrel(query relevance judgment)이라 부른다. [TREC의 관련성 판정 자료](https://trec.nist.gov/data/qrels_eng/)도 질문과 문서의 관련성 목록을 따로 제공한다.


소수 질문은 계산과 실패 유형을 점검하는 데 사용할 수 있다. 전체 사용 상황의 성능으로 해석하려면 질문의 수와 범위, 관련성 기준도 함께 검토할 부분이다. 판정하지 않은 문서는 무관하다고 판정한 문서와 구분해 기록한다.

그림 1. 검색 평가의 기본 흐름: 설명용 도식. 질문 목록과 정답 목록이 준비된 상태에서, 시스템의 반환 순위를 정답과 대조해 지표를 산출한다.


## 평가 데이터 분할과 누출 방지


검색 모델을 학습시키거나 파이프라인 파라미터를 조정할 때, 같은 질문을 평가에도 쓰면 새 질문에서도 얻을 수 있는 점수인지 판단하기 어려워진다. 해당 질문에 유리한 설정을 선택했을 가능성이 있기 때문이다. 이것을 데이터 누출(data leakage)이라 한다.


[학습과 평가 누출을 분석한 Zhan 등의 연구](https://arxiv.org/abs/2206.14759)도 검색 평가에서 이 문제를 다룬다. 특정 실험의 수치를 모든 데이터셋에 적용하기보다, 내가 나눈 질문 사이에 중복이나 유사한 변형이 남아 있는지를 먼저 확인할 필요가 있었다.


누출을 줄이려면 질문셋을 학습, 검증, 평가 세 부분으로 나누고 서로 겹치지 않도록 관리한다. 평가 집합의 질문은 모델 개발이 모두 끝난 뒤에만 사용하는 것이 원칙이다.


검색 모델을 직접 학습하지 않는 소규모 프로젝트에서도 같은 문제가 생길 수 있다. chunk 크기나 유사도 임계값 같은 파라미터를 조정하면서 동일한 질문으로 결과를 확인하면, 그 질문에만 맞춰진 설정이 된다.


질문이 10개뿐이라면 분리한 평가 질문 몇 개의 점수도 크게 흔들릴 수 있다. 우선 계산과 실패 유형을 점검하는 소규모 검사로 쓰고, 질문을 늘리거나 그룹 단위 분할, 반복 비교를 설계하는 편이 해석에 맞았다. 분할 비율 하나만으로 이 문제가 해결되지는 않는다.

그림 2. 질문셋 분할과 누출 경로: 설명용 도식. 평가 질문을 보고 설정을 다시 선택하면 별도 평가의 의미가 약해진다. 점선은 그 정보 유입을 나타내며, 비율은 특정 값으로 고정하지 않았다.


## Recall@k: 정답 중 얼마나 찾았는가


Recall@k는 상위 k개 결과 안에 정답 문서가 몇 개 포함되었는지를 전체 정답 수로 나눈 값이다. 문서가 몇 위에 있는지는 따지지 않고, 상위 k개 안에 들어왔는지만 본다([Weaviate — Retrieval Evaluation Metrics](https://weaviate.io/blog/retrieval-evaluation-metrics)).


다섯 개 질문으로 직접 계산해 보자. 각 질문의 정답 문서와 시스템이 반환한 상위 3개 결과는 다음과 같다.


| 질문 | 정답 문서      | 반환 결과 (1→3위) | 상위 3개 중 정답 수 |
| -- | ---------- | ------------ | ------------ |
| q1 | d3, d7     | d7, d1, d3   | 2 / 2        |
| q2 | d2         | d5, d2, d4   | 1 / 1        |
| q3 | d1, d4, d6 | d1, d6, d8   | 2 / 3        |
| q4 | d5         | d9, d3, d5   | 1 / 1        |
| q5 | d8         | d10, d4, d8  | 1 / 1        |


각 질문의 Recall@3은 q1 = 1.0, q2 = 1.0, q3 ≈ 0.667, q4 = 1.0, q5 = 1.0이다. 평균 Recall@3 = (1.0 + 1.0 + 0.667 + 1.0 + 1.0) ÷ 5 ≈ **0.933**이다.


같은 결과에서 k를 1로 바꿔 보면 양상이 크게 달라진다. q1은 1위인 d7이 정답이므로 1/2 = 0.5이고, q2는 1위 d5가 정답이 아니므로 0/1 = 0.0, q3 = 1/3 ≈ 0.333, q4 = 0.0, q5 = 0.0이다.


평균 Recall@1 ≈ **0.167**이다. k를 3에서 1로 줄였을 뿐인데 점수가 0.933에서 0.167로 떨어졌다. k를 늘리면 점수가 오르는 것은 당연하지만, 사용자가 실제로 결과 목록을 어디까지 확인하는지에 따라 적절한 k가 달라진다.


## MRR: 첫 번째 정답이 몇 위에 있는가


Mean Reciprocal Rank는 각 질문에서 첫 번째 정답 문서의 순위를 구하고, 그 역수를 모든 질문에 대해 평균한 값이다. 1위에 정답이 있으면 1.0, 2위면 0.5, 3위면 약 0.333이 된다. Recall@k가 "얼마나 많이 찾았는가"를 측정한다면, MRR은 "얼마나 위에서 찾았는가"에 초점을 둔다.


| 질문 | 첫 정답 위치 | 역수          |
| -- | ------- | ----------- |
| q1 | 1위 (d7) | 1/1 = 1.0   |
| q2 | 2위 (d2) | 1/2 = 0.5   |
| q3 | 1위 (d1) | 1/1 = 1.0   |
| q4 | 3위 (d5) | 1/3 ≈ 0.333 |
| q5 | 3위 (d8) | 1/3 ≈ 0.333 |


이 예제의 MRR@3 = (1.0 + 0.5 + 1.0 + 0.333 + 0.333) ÷ 5 ≈ **0.633**이다.


Recall@3이 0.933이었던 것에 비해 MRR은 0.633이다. 정답 문서 자체는 대부분 상위 3개 안에 들어왔지만, 다섯 질문 중 세 질문에서는 첫 정답이 2위나 3위에 있었다는 뜻이다. 두 지표를 함께 보면 "찾기는 하지만 순위가 낮다"와 "아예 못 찾는다"를 구분할 수 있다.


이 조합은 재순위화를 검토할 단서가 될 수 있었다. 다만 질문별 실패와 관련성 판정의 완전성까지 확인해야 변경할 위치를 정할 수 있다. 상위 3개 안에 정답이 없는 질문의 MRR@3 기여값은 0으로 두며, 해당 질문도 평균의 분모에 남겨야 했다.


## 검색 지표와 생성 지표를 분리하기


RAG 파이프라인을 평가할 때, 검색 단계의 Recall@k와 최종 답변의 정확도를 한 숫자로 합치면 어디서 실패했는지 알 수 없다. 검색이 완벽해도 생성 모델이 문맥을 무시하면 답이 틀리고, 반대로 검색이 빈약해도 모델이 사전 지식으로 맞출 수 있다.


검색 결과는 관련 문서 목록과, 생성 결과는 기대 답변과 각각 비교하면 실패 위치를 좁힐 수 있다. 검색한 내용을 요약에서 빠뜨린 경우와 검색 자체가 누락된 경우를 나누어 볼 수 있는 구성이다.


## 후속 정리


다섯 질문의 계산에서 Recall@k와 MRR이 보는 측면을 구분할 수 있었다. 지표를 적용하기에 앞서 관련성 기준과 질문의 사용 목적을 정리했다. 이 작은 예제의 차이가 새로운 질문에서도 유지되는지는 별도 평가가 남는다.


관련성에 등급을 부여했을 때의 지표 확장과 소수 질문에서의 분산은 다음 내용으로 남겼다. 비교에 필요한 질문 수 역시 고정 숫자보다 변동성과 평가 목적에 맞춰 살펴볼 주제다.
