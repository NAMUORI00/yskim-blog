검색 방식을 바꿨을 때 질문 몇 개를 넣어 보고 맨 위 결과가 그럴듯한지만 확인해서는 검색 품질이 실제로 나아졌는지 알기 어렵다. 첫 번째 문서가 질문과 비슷해 보여도 답변에 꼭 필요한 다른 근거 문서를 놓쳤을 수 있기 때문이다. 방금 넣어 본 질문에서는 결과가 잘 나왔지만 다른 질문에서는 정답 문서의 순위가 뒤로 밀렸을 수도 있다.


검색 방식을 객관적으로 비교하려면 평가용 질문 목록과 각 질문에서 찾아야 할 정답 문서 목록을 먼저 준비해야 한다. 이 글에서는 정답 문서 목록을 만들고 평가용 질문을 나누는 기준을 정리한다. 이어서 질문 다섯 개를 예로 들어 정답 포함 비율(Recall@k)과 첫 정답 순위(MRR)를 계산하고, 두 지표가 보여 주는 차이를 비교한다.


## 평가용 질문과 정답 문서 목록


검색 품질을 숫자로 비교하는 첫걸음은 평가에 쓸 질문과 각 질문의 정답 문서를 짝지어 정리하는 일이다. 정보 검색 분야에서는 질문과 관련 문서의 대응 목록을 보통 **qrel**(query relevance judgment)이라 부른다. 검색 성능을 비교하는 공개 벤치마크인 [TREC의 관련성 판정 자료](https://trec.nist.gov/data/qrels_eng/)도 질문 묶음과 문서 집합 외에 질문별 관련성 판정 파일을 따로 제공한다.


정답 목록을 만들 때는 아직 확인하지 않은 문서와 직접 읽어 보고 무관하다고 판정한 문서를 구분해 기록한다. 전체 문서가 많을수록 모든 문서를 사람이 일일이 읽어 볼 수 없기 때문이다. 아직 판정하지 않은 문서를 모두 오답으로 단정하면 실제로는 관련 있는 문서를 찾아왔을 때도 점수가 깎인다.


평가에 쓰는 질문의 규모도 계산된 점수를 어디까지 해석할 수 있는지 결정한다. 질문이 열 개 안팎으로 적을 때는 지표 계산식이 맞게 돌아가는지 확인하거나 눈에 띄는 실패 유형을 빠르게 점검하는 데 쓸 수 있다. 반면에 시스템 전체의 검색 성능으로 해석하려면 질문 수와 다루는 주제의 범위, 관련성 판정 기준이 실제 사용 환경을 충분히 대변하는지 함께 따져야 한다. 이렇게 질문 목록과 정답 목록이 준비되면 검색 시스템이 반환한 문서 순위를 정답 목록과 대조해 평가 지표를 계산한다.

## 평가 질문 분할과 데이터 누출


앞 절에서처럼 정답 목록을 준비했더라도 시스템 설정을 고를 때 쓴 질문을 최종 성능 평가에 그대로 다시 쓰면 점수를 믿기 어렵다. 검색 모델을 직접 학습시키지 않는 소규모 프로젝트에서도 문서를 자르는 단위(chunk 크기)나 벡터 유사도 임계값 같은 설정값을 조정할 때 이 문제가 자주 생긴다. 설정값을 바꿀 때마다 같은 질문 묶음으로 점수를 확인하면 결국 그 질문들에만 맞춘 설정을 고르게 되기 때문이다. 이처럼 평가 데이터가 학습이나 파이프라인 설정 조정에 섞여 새로운 질문에 대한 일반화 성능을 제대로 재지 못하는 현상을 **데이터 누출**(data leakage)이라 한다.


누출을 막으려면 질문셋을 학습, 검증, 별도 평가 세 부분으로 나누고 서로 겹치지 않게 관리한다. 설정값을 고르거나 검색 방식을 비교할 때는 검증 질문만 사용하고, 별도 평가 질문은 모든 설정을 고정한 뒤 마지막에 한 번만 실행하는 것이 원칙이다.


![학습과 검증 질문으로 설정을 고정한 뒤 별도 평가 질문으로 최종 평가하는 흐름과, 평가 질문을 보고 설정을 다시 바꾸는 데이터 누출 경로를 나타낸 도식](/images/notion/tech-k09/image-2.png)


그림 2. 질문셋 분할 구조와 별도 평가 결과를 설정 조정에 다시 사용할 때 발생하는 데이터 누출 경로.


다만 질문 목록을 정해진 비율로 나눴다고 해서 누출이 저절로 사라지지는 않는다. [학습과 평가 누출을 분석한 Zhan 등의 연구](https://arxiv.org/abs/2206.14759)도 학습 질문과 평가 질문 사이에 의미가 비슷한 질문이 섞여 있을 때 검색 점수가 얼마나 부풀려지는지 다룬다. 선행 연구의 실험 수치를 그대로 가져다 쓰기보다, 직접 나눈 질문 집합 사이에 중복 질문이나 표현만 살짝 바꾼 변형이 남아 있지 않은지 먼저 확인해야 한다.


전체 질문이 10개뿐인 작은 평가셋이라면 그중 몇 개를 별도 평가용으로 떼어 놓아도 질문 한두 개의 성패에 따라 점수가 크게 흔들린다. 이럴 때는 분할 비율만 맞추려 하기보다 작은 질문셋으로 계산 과정과 실패 유형을 먼저 점검하는 편이 낫다. 그다음에 질문을 더 확보하거나 주제 묶음 단위의 분할과 반복 비교를 설계해야 한다.


## 정답 포함 비율과 Recall@k


평가 질문으로 검색을 실행한 뒤 가장 먼저 확인하는 것은 준비해 둔 정답 문서를 상위 결과 안에 얼마나 빠짐없이 건져 올렸는가이다. 다섯 개 질문(q1~q5)을 예로 들어 각 질문의 정답 문서와 검색 시스템이 반환한 상위 3개 결과를 비교한다.


| 질문 | 정답 문서      | 반환 결과 (1→3위) | 상위 3개 중 정답 수 |
| -- | ---------- | ------------ | ------------ |
| q1 | d3, d7     | d7, d1, d3   | 2 / 2        |
| q2 | d2         | d5, d2, d4   | 1 / 1        |
| q3 | d1, d4, d6 | d1, d6, d8   | 2 / 3        |
| q4 | d5         | d9, d3, d5   | 1 / 1        |
| q5 | d8         | d10, d4, d8  | 1 / 1        |


표에서 q1은 정답 문서 두 개(d3, d7)가 상위 3개 결과에 모두 들어와 찾은 비율이 2/2 = 1.0이다. 반면 q3은 정답 문서 세 개(d1, d4, d6) 가운데 두 개(d1, d6)만 상위 3개 안에 들어와 2/3 ≈ 0.667이 된다. 이처럼 시스템이 반환한 상위 k개 결과 안에 포함된 정답 문서 수를 그 질문의 전체 정답 문서 수로 나눈 값을 **Recall@k**(상위 k개 재현율)라 한다([Weaviate — Retrieval Evaluation Metrics](https://weaviate.io/blog/retrieval-evaluation-metrics)). 정답 문서가 1위에 있든 k위에 있든 구분하지 않고 상위 k개 안에 들어왔는지만 본다.


위 표에서 질문별 Recall@3을 구하면 q1 = 1.0, q2 = 1.0, q3 ≈ 0.667, q4 = 1.0, q5 = 1.0이다. 다섯 질문의 평균 Recall@3은 (1.0 + 1.0 + 0.667 + 1.0 + 1.0) ÷ 5 ≈ 0.933으로, 상위 3개 문서까지 보면 전체 정답의 대부분을 찾았다.


그런데 같은 반환 결과에서 확인 범위를 좁혀 k를 1로 바꾸면 점수가 크게 달라진다. 1위 문서만 남기므로 q1은 1위인 d7이 정답이어서 1/2 = 0.5이고, q2는 1위 d5가 오답이어서 0/1 = 0.0이다. 같은 방식으로 q3 = 1/3 ≈ 0.333, q4 = 0.0, q5 = 0.0이 되어 다섯 질문의 평균 Recall@1은 약 0.167로 떨어진다.


k를 3에서 1로 줄였을 뿐인데 평균 점수가 0.933에서 0.167로 낮아진 것처럼, 확인 범위 k를 넓힐수록 Recall@k는 자연스럽게 오른다. 따라서 어떤 k를 기준으로 삼을지는 사용자가 검색 목록을 몇 위까지 살펴보는지, 혹은 다음 단계의 언어 모델에 문서를 몇 개까지 넘기는지에 맞춰 정해야 한다.


## 첫 정답 순위와 MRR


앞선 예제에서 평균 Recall@3은 0.933으로 높았지만, q2와 q4, q5 세 질문에서는 1위에 오답 문서가 올라와 있었다. 상위 k개 안에 들어왔는지뿐 아니라 첫 번째 정답 문서가 얼마나 위쪽에 놓였는지를 따질 때는 **MRR**(Mean Reciprocal Rank, 평균 역순위)을 쓴다.


MRR은 각 질문에서 첫 번째로 등장한 정답 문서의 순위를 찾고, 그 순위의 역수(1/순위)를 모든 질문에 대해 평균한 값이다. 첫 정답이 1위에 있으면 1.0, 2위면 0.5, 3위면 약 0.333을 얻는다. 만약 상위 k개 안에 정답 문서가 하나도 없다면 그 질문의 역순위 값은 0으로 두고, 평균을 낼 때 분모(전체 질문 수)에도 그대로 포함해야 한다. Recall@k가 정답을 얼마나 많이 찾았는가를 재는 지표라면, MRR은 첫 정답을 얼마나 빨리 만나는가를 재는 지표다.


| 질문 | 첫 정답 위치 | 역수          |
| -- | ------- | ----------- |
| q1 | 1위 (d7) | 1/1 = 1.0   |
| q2 | 2위 (d2) | 1/2 = 0.5   |
| q3 | 1위 (d1) | 1/1 = 1.0   |
| q4 | 3위 (d5) | 1/3 ≈ 0.333 |
| q5 | 3위 (d8) | 1/3 ≈ 0.333 |


표의 역수를 모두 더해 질문 수로 나누면 이 예제의 MRR@3은 (1.0 + 0.5 + 1.0 + 0.333 + 0.333) ÷ 5 ≈ 0.633이다. 같은 결과인데도 Recall@3은 0.933이고 MRR@3은 0.633으로 차이가 난다. 정답 문서 자체는 대부분 상위 3개 안에 들어왔지만, 다섯 질문 가운데 세 질문에서 첫 정답이 2위나 3위로 밀려났다는 사실이 두 지표의 차이로 드러난다.


![상위 3개 안 포함 비율을 계산하는 Recall@3(0.933)과 첫 정답 순위의 역수를 계산하는 MRR@3(0.633)의 차이를 비교한 도식](/images/notion/tech-k09/image-3.png)


그림 3. 다섯 질문(q1~q5)의 상위 3개 반환 결과에서 포함 여부만 보는 Recall@3과 첫 정답 순위를 반영하는 MRR@3의 비교.


두 지표를 나란히 보면 후보 문서를 상위권으로 가져오지 못하는 문제와 순위가 뒤로 밀리는 문제를 구분할 수 있다. 후보 문서 자체를 못 찾으면 Recall@k가 낮게 나오고, 후보 문서는 가져왔지만 순위가 밀리면 Recall@k는 높고 MRR만 낮게 나온다. 이 예제처럼 Recall@3은 높은데 MRR@3이 낮다면, 1차 검색기가 가져온 후보들의 순서를 다시 매기는 재순위화(reranking) 단계를 검토할 단서가 된다. 다만 파이프라인을 고치기 전에 실패한 질문을 직접 열어 보고, 1위 문서가 실제로는 정답인데 정답 목록(qrel)에서 빠져 있지 않았는지부터 확인해야 한다.


## 검색 단계와 생성 단계의 분리 평가


앞에서 계산한 Recall@k와 MRR은 검색 단계의 품질을 재는 지표다. 검색 결과를 언어 모델에 넘겨 답변을 만드는 RAG(검색 증강 생성) 파이프라인에서는 검색 단계의 지표와 최종 답변의 정확도를 하나의 숫자로 합치지 않고 나누어 봐야 한다. 최종 답변만 채점해서는 답이 틀렸을 때 어느 단계에서 문제가 생겼는지 알 수 없기 때문이다.


예를 들어 검색 단계에서 필요한 근거 문서를 모두 찾아왔더라도 생성 모델이 문맥을 무시하거나 요약 과정에서 핵심 조건을 빠뜨리면 오답이 나온다. 반대로 검색이 엉뚱한 문서를 가져왔는데도 생성 모델이 미리 학습해 둔 사전 학습 지식으로 우연히 정답을 맞히는 일도 있다.


따라서 검색 단계의 반환 결과는 관련 문서 목록(qrel)과 대조해 Recall@k나 MRR로 평가하고, 생성 단계의 출력은 기대 답변과 대조해 따로 평가한다. 두 평가를 분리해 두면 답변 품질이 떨어졌을 때 검색 색인과 순위 결합을 손봐야 할지, 지시문(프롬프트)과 생성 모델을 손봐야 할지 범위를 좁힐 수 있다.

그림 4. RAG 파이프라인에서 반환 문서는 관련 문서 목록(qrel)과, 생성 답변은 기대 답변과 각각 대조해 실패 위치를 좁히는 분리 평가 구조.


## 결론


검색 품질을 객관적으로 비교하려면 질문별 정답 문서 목록(qrel)을 준비하고, 검증 질문과 별도 평가 질문을 나누어 데이터 누출을 막아야 한다. 다섯 개 질문 예제에서 보았듯 정답 포함 비율을 재는 Recall@3(0.933)과 첫 정답 순위를 재는 MRR@3(0.633)은 서로 다른 실패 원인을 드러낸다. 두 지표를 함께 확인하고 RAG 파이프라인에서 검색 평가와 생성 평가를 분리하면, 후보 문서 누락과 순위 밀림, 답변 생성 오류 가운데 어디를 고쳐야 할지 좁힐 수 있다.


지금까지 다룬 Recall@k와 MRR은 모두 문서를 정답 아니면 오답으로만 나누는 이진 판정(binary relevance)을 전제로 계산했다. 하지만 실제 문서 중에는 핵심 근거가 담긴 문서와 부수적인 배경만 적힌 문서가 섞여 있어서 관련성에 등급을 매겨야 할 때가 많다. 관련성 등급을 반영해 순위를 평가하는 지표로의 확장과 질문 수가 적을 때 점수 분산을 다루는 방법은 다음 글에서 이어서 다룬다.
