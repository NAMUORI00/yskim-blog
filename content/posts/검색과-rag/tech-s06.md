## 청크와 출처의 연결


문서 두 개를 네 조각으로 나누는 예제로 원문과 검색 결과의 연결을 정리했다. 같은 제목의 문서와 서로 다른 버전을 구분하려면 본문 외에도 식별 정보가 필요하다. 청크에서 원문으로 돌아가는 경로를 따라갔다.


앞에서 나눈 문서와 청크를 이번에는 식별자로 연결했다. 메타데이터는 출처, 위치, 처리 이력처럼 자료를 설명하는 정보다. 임베딩 계산에 앞서 자료가 어떤 관계로 저장되는지 표로 살펴봤다.


## 문서 두 개를 네 조각으로 나누기


가상의 장치 안내서 D1과 점검표 D2를 각각 두 청크로 나눈다고 하자. D1의 v1에는 설정 설명과 예외 조건이 있고, D2의 v3에는 일상 점검과 이상 징후가 있다. 아래 ID는 설명을 위해 정한 표기다.


| 청크 ID | 문서 ID | 버전 | 위치       | 내용    |
| ----- | ----- | -- | -------- | ----- |
| C11   | D1    | v1 | 2쪽, 설정 절 | 설정 설명 |
| C12   | D1    | v1 | 3쪽, 예외 절 | 예외 조건 |
| C21   | D2    | v3 | 1쪽       | 일상 점검 |
| C22   | D2    | v3 | 2쪽       | 이상 징후 |


문서 URL에 버전 또는 보존한 스냅샷 식별자를 더하는 구성을 비교했다. 같은 URL의 파일이 갱신되면 이전 검색 결과의 원문을 대조하기 어렵기 때문이다. 내용 해시는 바이트 동일성 확인에 쓸 수 있지만 작성자나 자료의 신뢰성까지 증명하지는 않는다.

## 문서 변환과 위치 정보


PDF의 3쪽이라는 표시는 사람이 원문을 열 때 유용하다. 반면 프로그램은 추출된 텍스트의 시작, 끝 위치를 쓰는 편이 편리할 수 있다. 두 위치가 저절로 일치하지는 않는다. 머리말을 지우거나 줄바꿈을 합치거나 OCR로 글자를 바꾸면 문자 위치가 달라진다.


예를 들어 정규화 전 문자열 `온도\n설정`에서 줄바꿈을 공백으로 바꾸는 것은 길이가 유지되지만, 줄바꿈을 아예 삭제하면 뒤쪽 오프셋이 한 칸 당겨진다. 여러 공백을 하나로 줄이는 작업이 반복되면 차이가 더 커진다. 정규화된 텍스트의 100번째 문자를 원본의 100번째 문자로 취급하면 다른 부분을 가리킬 수 있다.


그래서 위치를 저장할 때는 어느 표현을 기준으로 한 위치인지도 적는다. 원본 페이지, 추출 텍스트, 정규화 텍스트를 구분하거나, 변환 전후 위치의 대응 정보를 남기는 방법을 생각할 수 있다. 구현 비용을 줄이려면 위치 정보의 정밀도를 페이지와 절 제목 수준으로 정할 수도 있다.


## 생성한 질문, 답변의 검토


청크에서 학습용 질문, 답변을 만들 때는 파생 자료가 한 단계 더 생긴다. Q1은 C11과 C12를 함께 참고하고, Q2는 C22에서 만들었다고 하자. 답변에 예외 조건이 포함되어야 하는 Q1을 C11 하나에만 연결하면 생성 과정을 재검토할 때 정보가 부족하다.


```json
{
  "qa_id": "Q1",
  "source_chunk_ids": ["C11", "C12"],
  "source_document_version": "D1:v1",
  "transform_version": "qa-rule-2",
  "review_status": "unreviewed"
}
```


예제에서는 출처 연결과 답변 검토 상태를 따로 두었다. 출처가 남아 있어도 문장을 잘못 해석하거나 청크의 조건을 섞을 수 있기 때문이다. 검토 대상 원문 버전과 확인 항목이 함께 있어야 검토 결과의 재사용 범위도 정할 수 있다.


W3C PROV는 자료, 처리 활동, 관여 주체의 관계로 출처 이력을 표현한다. 이 예제에서는 원문과 청크, QA가 자료에, 추출, 정규화, QA 생성이 처리 활동에 대응한다. 여기서는 이 표준을 식별 정보 설계의 참고로 사용했다. 무엇이 무엇에서 파생되었는지 기록해야 한다는 구분을 빌려 읽었다.


## 답변의 인용 번호를 다시 펼쳐 보기


검색 결과 C12를 모델 입력에 넣으며 `[1]`이라는 인용 번호를 붙였다고 하자. `[1]`은 이 응답 안에서만 의미가 있는 표시다. 원문 식별자 자체를 대신하지는 않는다. 다음 질문에서 `[1]`이 다른 문서를 가리킬 수 있으므로 응답별 인용 맵이 필요하다.


![S06-02.png](/images/notion/tech-s06/image-2.png)


그림 2. 답변의 인용 표식을 청크와 원문 버전으로 되돌리는 과정. 직접 작성한 설명용 도식.


링크의 접속 여부, 원문과 발췌의 대응, 발췌와 주장의 관계를 각각 확인 항목으로 정리했다. 원문 접근 권한이 없는 독자에게는 확인 가능한 범위가 줄어드는 점도 남았다.


## 문서 수정 이후의 출처 관리


원문 D1이 v2로 바뀌는 경우에는 C11, C12에서 파생된 QA와 답변이 재검토 대상이 된다. 전체 재생성은 흐름이 단순하지만 바뀌지 않은 자료도 처리한다. 부분 갱신은 처리량을 줄일 수 있는 대신 파생 관계와 위치 변화의 추적이 필요하다.


이번 예제에서 남긴 파생 관계는 색인 갱신에도 사용할 수 있다. 다음에는 갱신 전후 자료를 구분하고 이전 버전의 결과가 새 답변에 섞이는 경로를 살펴볼 내용으로 두었다.
