검색 시스템에서 문서를 작은 조각인 청크(chunk)로 나누어 색인에 넣을 때 본문 텍스트만 저장하면, 나중에 검색된 조각이 어느 문서의 몇 쪽에서 나왔는지 다시 찾기 어렵다. 제목이 같은 문서가 여러 개 있거나 문서가 수정되어 새 판본이 나오면 혼란은 더 커진다. 임베딩을 계산하기 전에 원본 문서와 청크, 그리고 청크에서 파생된 자료들을 어떤 식별자와 메타데이터로 연결해야 원문으로 정확히 돌아갈 수 있는지 작은 예제로 따라가 본다.


## 문서 두 개를 네 조각으로 나누기


가상의 장치 안내서 `D1`과 점검표 `D2`를 각각 두 청크로 나눈다고 하자. `D1`의 버전 `v1`에는 설정 설명과 예외 조건이 있고, `D2`의 버전 `v3`에는 일상 점검과 이상 징후가 있다. 아래 표의 ID는 설명을 위해 붙인 식별자다. 출처와 위치, 처리 이력처럼 자료를 설명하는 데이터를 메타데이터(metadata)라고 부른다.


| 청크 ID | 문서 ID | 버전 | 위치       | 내용    |
| ----- | ----- | -- | -------- | ----- |
| C11   | D1    | v1 | 2쪽, 설정 절 | 설정 설명 |
| C12   | D1    | v1 | 3쪽, 예외 절 | 예외 조건 |
| C21   | D2    | v3 | 1쪽       | 일상 점검 |
| C22   | D2    | v3 | 2쪽       | 이상 징후 |


원본 문서를 가리킬 때 파일이 있는 URL만 적어 두면, 같은 주소의 파일이 새 내용으로 덮어써졌을 때 이전 검색 결과가 참조하던 원문을 대조하기 어렵다. 그래서 문서 URL에 버전 정보나 그 시점의 파일을 보존해 둔 스냅샷(snapshot) 식별자를 함께 붙여 두는 편이 안전하다. 파일 내용으로 계산한 해시(hash) 값은 두 파일의 바이트가 똑같은지 확인하는 데 쓸 수 있지만, 누가 작성했는지나 자료 자체를 신뢰할 수 있는지까지 증명해 주지는 않는다.

## 문서 변환과 위치 정보


앞선 표의 위치 칸에는 `3쪽, 예외 절`처럼 사람이 읽는 위치를 적었다. 사람이 PDF 원문을 열어 확인할 때는 페이지 번호가 유용하지만, 프로그램이 텍스트의 특정 구간을 가리킬 때는 추출된 문자열의 시작과 끝 위치인 오프셋(offset)을 쓰는 편이 다루기 쉽다. 문제는 두 위치가 저절로 일치하지 않는다는 점이다. 문서에서 머리말을 지우거나 줄바꿈을 합치거나 광학 문자 인식(OCR)으로 글자를 읽는 과정을 거치면 글자 위치가 달라진다.


예를 들어 정규화 전 문자열 `온도\n설정`에서 줄바꿈 문자(`\n`)를 공백으로 바꾸면 전체 길이가 그대로 유지되지만, 줄바꿈을 아예 삭제하면 뒤에 오는 글자들의 위치가 한 칸씩 앞으로 당겨진다. 연속된 공백을 하나로 줄이는 작업이 반복되면 원본과의 위치 차이는 더 벌어진다. 정규화된 텍스트의 100번째 글자를 원본 텍스트의 100번째 글자로 취급하면 전혀 다른 부분을 가리키게 된다.


![추출 텍스트 온도\n설정에서 줄바꿈을 공백으로 바꾸면 설의 위치가 3번째로 유지되지만 줄바꿈을 삭제하면 설의 위치가 2번째로 한 칸 당겨지는 비교 도식](/images/notion/tech-s06/image-2.png)


그림 2. 텍스트 정규화 방식에 따라 글자의 시작 위치(오프셋)가 유지되거나 당겨지는 차이.


따라서 위치를 저장할 때는 어느 단계의 텍스트를 기준으로 삼았는지도 함께 적어야 한다. 원본 페이지, 추출 직후의 텍스트, 정규화를 마친 텍스트를 구분해 기록하거나 변환 전후의 위치 대응 정보를 남기는 방법이 있다. 글자 단위의 세밀한 추적이 필요하지 않다면, 구현 비용을 줄이기 위해 위치 정보의 정밀도를 페이지 번호와 절 제목 수준으로 정할 수도 있다.


## 청크에서 파생된 질문과 답변의 출처 기록


청크를 바탕으로 학습이나 평가에 쓸 질문과 답변(QA)을 만들면 파생 자료가 한 단계 더 생긴다. 질문 `Q1`은 `C11`과 `C12`를 함께 참고해 만들고, `Q2`는 `C22`에서 만들었다고 하자. `Q1`의 답변에 설정 설명(`C11`)뿐 아니라 예외 조건(`C12`)도 들어가야 한다면, 출처를 `C11` 하나에만 연결해 두었을 때 나중에 생성 과정을 다시 검토하기 어렵다.


```json
{
  "qa_id": "Q1",
  "source_chunk_ids": ["C11", "C12"],
  "source_document_version": "D1:v1",
  "transform_version": "qa-rule-2",
  "review_status": "unreviewed"
}
```


이 예제에서는 출처 연결 정보와 답변 검토 상태(`review_status`)를 분리해 적었다. 출처가 남아 있어도 질문을 만드는 과정에서 문장을 잘못 해석하거나 서로 다른 청크의 조건을 섞었을 수 있기 때문이다. 검토 대상이 된 원문 버전(`D1:v1`)과 변환 규칙(`qa-rule-2`), 그리고 확인 항목이 함께 남아 있어야 나중에 검토 결과를 어디까지 재사용할 수 있을지 정할 수 있다.


이처럼 무엇이 무엇에서 파생되었는지 기록하는 구조는 데이터 출처 이력 표준인 W3C PROV 모델을 참고했다. W3C PROV는 출처 이력을 자료, 처리 활동, 관여 주체의 관계로 표현한다. 이 예제에 대입하면 원문과 청크, QA는 자료에 해당하고, 텍스트 추출과 정규화, QA 생성은 처리 활동에 해당한다.


## 답변의 인용 번호에서 원문으로 돌아가기


검색된 청크로 답변을 생성할 때도 출처 연결이 필요하다. 검색 결과로 나온 `C12`를 모델 입력에 넣으면서 `[1]`이라는 인용 번호를 붙였다고 하자. `[1]`은 이번 응답 안에서만 의미가 있는 임시 표식일 뿐, 원문 식별자 자체를 대신하지는 못한다. 다음 질문에 대한 응답에서는 `[1]`이 다른 문서를 가리킬 수 있으므로, 응답마다 인용 번호와 실제 청크를 이어 주는 인용 맵(map)이 필요하다.


![독자의 질문으로 생성된 답변의 인용 번호 1을 응답별 인용 맵에서 확인해 청크 C12와 보존된 원문 D1:v1으로 연결하거나 대응 항목이 없을 때 출처 연결 실패를 표시하는 흐름도](/images/notion/tech-s06/image-3.png)


그림 3. 답변의 임시 인용 표식을 응답별 인용 맵을 거쳐 청크와 원문 버전으로 되돌리는 과정. 직접 작성한 설명용 도식.


답변에 달린 인용을 따라가며 검증할 때는 단계마다 확인할 항목이 다르다. 원문 링크에 실제로 접속할 수 있는지, 발췌한 청크가 원문 내용과 일치하는지, 그리고 그 발췌 내용이 답변의 주장을 제대로 뒷받침하는지를 각각 나누어 확인해야 한다. 원본 문서에 접근할 권한이 없는 독자에게는 확인 가능한 범위가 줄어든다는 점도 고려해야 한다.


## 문서 수정 이후의 출처 관리


원문 `D1`이 `v2`로 바뀌면 기존 `D1:v1`에서 나온 `C11`, `C12`와 여기서 파생된 `Q1`, 그리고 이를 인용한 답변이 모두 재검토 대상이 된다. 문서가 바뀔 때 전체 자료를 처음부터 다시 생성하면 흐름은 단순하지만 바뀌지 않은 자료까지 다시 처리해야 한다. 반대로 바뀐 부분만 골라 갱신하면 처리량은 줄일 수 있지만, 앞서 기록해 둔 파생 관계와 텍스트 위치 변화를 추적해야 한다.


이번 예제에서 살펴본 문서, 청크, 파생 자료의 연결 관계는 검색 색인을 갱신할 때도 그대로 쓰인다. 다음에는 문서가 수정될 때 갱신 전후의 자료를 어떻게 구분하고, 이전 버전의 검색 결과가 새 답변에 섞여 들어가는 경로를 살펴본다.
