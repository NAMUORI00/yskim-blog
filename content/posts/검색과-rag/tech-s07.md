여러 검색기의 결과를 하나로 합칠 때 쓰는 **RRF**(Reciprocal Rank Fusion, 상호 순위 결합)는 각 항목이 받은 순위의 역수($1 / (k + \text{순위})$)를 더하는 방식이다. 계산식만 보면 단순한 덧셈이지만, 실제 검색 결과 목록 두 개를 놓고 점수를 합산하려면 먼저 무엇을 '같은 항목'으로 볼지 정해야 한다. 문서 단위로 묶으면 한 문서 안의 서로 다른 내용이 하나로 합쳐져 사라질 수 있고, 반대로 한 검색기가 중복해서 내놓은 결과를 그대로 더하면 점수가 부풀려진다.


이 글에서는 간단한 검색 목록 두 개를 예로 들어, 청크(chunk, 문서를 나눈 조각) 식별자를 기준으로 RRF 점수를 합산하는 과정과 중복 처리 규칙을 코드로 따라가 본다. 임베딩 모델의 내부 구조는 다루지 않고, 반환된 순위 목록과 식별자가 계산에 어떻게 쓰이는지에 집중한다.


## 청크 식별자 기준의 점수 합산


검색기 A가 `[a, b, c]`, 검색기 B가 `[b, d]`를 반환했다고 하자. 여기서 소문자 `a`, `b`, `c`, `d`는 같은 청크를 가리키는 안정적인 식별자라고 가정한다. 문서 제목 문자열을 식별자로 삼지 않은 이유는 제목이 같아도 본문 내용이 다를 수 있고, 같은 내용이 다른 제목으로 저장되기도 하기 때문이다.


두 검색기가 반환한 청크별 순위를 표로 정리하면 다음과 같다.


| 청크 | A 순위 | B 순위 |
| -- | ---- | ---- |
| a  | 1    | 없음   |
| b  | 2    | 1    |
| c  | 3    | 없음   |
| d  | 없음   | 2    |


손계산으로 확인하기 쉽게 RRF 상수 `k`를 `10`으로 놓으면, 양쪽 목록에 모두 등장한 `b`의 점수는 `1/12 + 1/11 ≈ 0.17424`가 된다. 한쪽에만 있는 `a`는 `1/11 ≈ 0.09091`, `d`는 `1/12 ≈ 0.08333`, `c`는 `1/13 ≈ 0.07692`다. 점수가 높은 순서대로 정렬하면 결합 결과는 `b, a, d, c`가 된다.


여기서 특정 검색기 목록에 없는 항목은 해당 검색기에서 기여하는 점수를 `0`으로 둔다. 순위 자리에 `0`을 넣는 것과는 다르다. 누락된 항목에 `1/(k+0)`을 주면 1위 항목(`1/(k+1)`)보다 오히려 높은 점수를 받기 때문이다.

## 한 검색기 안의 중복과 동점 처리


두 검색기가 각각 `b`를 찾은 경우와 달리, 한 검색기 안에서 같은 청크가 반복되는 경우도 있다. 예를 들어 검색기 A가 `[a, b, b, c]`를 반환했다면, 두 번째 `b`는 같은 목록 안의 중복으로 보고 첫 등장만 점수에 반영한다.


이때 중복을 제거한 뒤 다음 항목의 순위를 다시 매길지도 정해야 한다. 원래 반환된 위치를 그대로 유지하면 `c`의 순위는 4위가 된다. 검색기가 매긴 원래 순서를 보존한다는 장점이 있지만, 앞에 낀 중복이 다른 항목의 점수 기여도를 낮추는 영향은 남는다. 반대로 고유한 항목만 세어 순위를 3위로 다시 매기는 정책도 가능하므로, 둘 중 하나를 정해 일관되게 기록해야 한다.


![검색 목록 a, b, b, c에서 3위인 중복 b를 건너뛰고 c의 순위를 4위로 유지해 RRF 점수를 계산하는 도식](/images/notion/tech-s07/image-2.png)


그림 2. 한 검색 목록 안에서 중복된 청크를 건너뛰고 뒤 항목의 원래 순위를 유지하는 처리 흐름이다.


아래 코드는 원래 반환 위치를 유지하면서 첫 등장만 합산하는 방식으로 작성한 예다.


```python
from collections import defaultdict

def fuse(rankings, k=10):
    scores = defaultdict(float)
    for items in rankings:
        seen = set()
        for rank, chunk_id in enumerate(items, start=1):
            if chunk_id in seen:
                continue
            seen.add(chunk_id)
            scores[chunk_id] += 1 / (k + rank)
    return sorted(scores.items(), key=lambda pair: (-pair[1], pair[0]))

fuse([["a", "b", "c"], ["b", "d"]])
# b, a, d, c 순서
```


점수가 같을 때는 `sorted(scores.items(), key=lambda pair: (-pair[1], pair[0]))`처럼 식별자의 사전순(`pair[0]`)으로 순서를 정했다. 검색 품질을 높이는 규칙이라기보다, 같은 입력에서 결과 순서가 흔들리지 않게 하려는 선택이다. 이렇게 해 두면 정렬 결과를 비교하는 테스트나 사용자 화면에서 재현성을 확인하기 쉬워진다.


## 문서와 청크 단위의 중복 구분


식별 기준을 세울 때는 문서 단위와 청크 단위의 중복도 구분해야 한다. 문서 D의 첫 번째 청크에는 장치 설정이, 두 번째 청크에는 예외 조건이 들어 있다고 하자. 문서 ID만 보고 중복으로 처리해 하나를 지우면 답변에 필요한 예외 조건이 빠질 수 있다. 반대로 내용이 크게 겹치는 청크를 모두 넣으면 문맥 공간을 낭비하게 된다. 그래서 정확히 같은 청크의 점수를 합치는 작업과 관련 청크의 다양성을 조절하는 작업을 나누어 다루었다.

그림 3. 같은 청크의 결과 결합과 같은 문서 안의 서로 다른 청크 선택을 구분한 설명용 도식이다.


동일성 기준에는 문서 버전도 포함해야 한다. 문서가 갱신되기 전후의 청크가 같은 ID를 공유하면 서로 다른 내용을 한 항목으로 합칠 수 있기 때문이다. 문서 ID, 문서 버전, 청크 위치나 내용 식별자를 조합하면 갱신 전후의 청크가 섞이지 않고, 나중에 검색 결과에서 원문으로 돌아가는 경로와도 자연스럽게 연결된다.


## 점수 합산 이후에 남는 판단


계산한 RRF 점수는 여러 검색기가 매긴 순위를 합산한 값일 뿐이다. 여러 검색기가 똑같이 잘못된 자료를 상위에 올리면, 합산 점수가 높아도 실제 답변 근거는 부족할 수 있다. 검색기별 가중치를 바꾸면 목록별 영향력을 조절할 수 있지만, 답변 신뢰도를 보정하는 일은 별도로 평가해야 한다.


질문과 후보 본문을 다시 읽고 순서를 고치는 재순위화(reranking)는 RRF 뒤에 이어지는 후속 단계로 구분된다. 순위 숫자만 사용하는 RRF와는 평가 입력 자체가 다르다. 후보 목록이 정해진 뒤 이어지는 문맥 조립 단계에서는 후보 청크의 길이와 배치 순서, 그리고 길이가 잘린 청크의 출처 유지가 확인 항목으로 남는다.
