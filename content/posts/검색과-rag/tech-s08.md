## 문맥 조립 단계의 제약


앞 글에서 여러 검색 결과를 하나로 합치고 중복을 정리했다면, 다음 단계는 이 검색 발췌들을 언어 모델에 전달할 하나의 입력으로 조립하는 일이다. 검색 결과를 상위 몇 개로 자르는 설정만으로는 모델에 들어갈 입력 크기를 보장하기 어렵다. 발췌마다 길이가 다른 데다, 모델이 한 번에 다룰 수 있는 문맥 공간에는 검색 발췌뿐 아니라 시스템 지시문, 사용자 질문, 대화 이력, 답변이 생성될 출력 공간까지 함께 들어가기 때문이다.


문맥 크기를 계산할 때 기준이 되는 **토큰**(token)은 언어 모델이 텍스트를 쪼개 처리하는 단위다. 글자 수나 단어 수와 항상 같지 않으며, 같은 문장이라도 사용하는 토크나이저(tokenizer)에 따라 계산되는 토큰 수가 달라진다. 여기서는 검색 결과 개수 제한과 입력 길이 제한의 차이를 비교하기 위해 가상의 토큰 수를 예로 들어 문맥 조립 과정을 따져 본다.


## 결과 개수와 토큰 예산


가상의 모델 호출에서 입력과 출력이 함께 쓰는 전체 문맥 예산을 4,000토큰으로 가정해 보자. 시스템 지시문과 질문, 대화 이력, 도구 스키마에 900토큰을 쓰고, 모델의 최대 출력에 600토큰, 메시지 형식과 계산 오차를 감안한 여유분으로 100토큰을 먼저 배정한다. 그러면 검색 발췌에 실제로 쓸 수 있는 공간은 2,400토큰이 남는다. 물론 실제 API에서는 모델마다 전체 문맥 한도와 최대 출력 한도를 묶어 계산하는 방식이 다르므로, 이 수식을 그대로 고정된 설정값으로 쓰지는 않는다.


이제 이 2,400토큰 예산 안에 아래 세 개의 검색 후보를 넣는 상황을 생각해 보자.


| 후보 | 내용             | 예제 토큰 수 | 검색 순위 |
| -- | -------------- | ------- | ----- |
| A  | 기본 설정과 배경 설명   | 1,500   | 1     |
| B  | 적용할 수 없는 예외 조건 | 1,200   | 2     |
| C  | 같은 설정을 요약한 표   | 500     | 3     |


후보 세 개를 모두 넣으면 3,200토큰이 되어 발췌 예산인 2,400토큰을 넘긴다. 개수를 줄여 상위 두 개(`top_k=2`)인 A와 B만 골라도 합계가 2,700토큰이라 여전히 예산 안에 들어가지 않는다. `top_k` 설정은 가져올 문서의 개수만 제한할 뿐이므로, 실제 문맥의 총길이는 토큰 예산에 맞춰 별도로 계산해야 한다.


![전체 예산 4,000토큰에서 지시와 질문 900토큰, 출력과 여유 700토큰을 빼 발췌 예산 2,400토큰을 구하고 후보 A, B, C의 합계가 이를 초과하면 선택과 발췌를 조정해 직렬화된 모델 입력을 만드는 흐름도](/images/notion/tech-s08/image-1.png)


그림 1. 전체 문맥 예산에서 고정 비용을 빼고 발췌 예산(2,400토큰)을 계산해 후보 길이를 검사하는 흐름도(설명용 가정 수치).


## 순위대로 채우는 방법의 부담


가장 단순한 구현은 검색 순위대로 후보를 넣어 보면서 남은 공간에 들어가는 것만 채우는 방식이다. 위 표에서 1순위인 A(1,500토큰)를 먼저 넣으면 남은 예산은 900토큰이다. 2순위인 B(1,200토큰)는 공간이 부족해 건너뛰고, 3순위인 C(500토큰)를 넣으면 합계가 2,000토큰이 되어 예산 안에 들어간다. 하지만 사용자의 질문이 예외 상황을 묻고 있었다면, 정작 답변에 꼭 필요한 예외 조건인 B가 빠지게 된다. 검색 점수와 크기만 보고 후보를 고르면 질문의 핵심 근거가 누락될 수 있으므로, 선택된 발췌에 필요한 조건이 들어 있는지 대조하는 과정이 필요하다.


이 문제를 피하는 한 가지 대안으로, 1순위 후보 A에서 질문과 직접 관련된 문장만 600토큰 분량으로 추려 내고 2순위 후보 B(1,200토큰) 전체와 함께 묶는 구성을 생각해 볼 수 있다. 이렇게 조립하면 합계가 1,800토큰이어서 2,400토큰 예산을 지키면서도 기본 설정(A)과 예외 조건(B)을 모두 문맥에 남길 수 있다.


![발췌 예산 2,400토큰 안에서 순위순으로 후보 A(1,500)와 후보 C(500)만 넣으면 후보 B(1,200) 예외 조건이 누락되지만, 후보 A 핵심 문장(600)과 후보 B(1,200)를 결합하면 1,800토큰으로 예외 조건까지 보존하는 비교 그림](/images/notion/tech-s08/image-2.png)


그림 2. 발췌 예산 2,400토큰 안에서 순위대로 채워 후보 B가 빠지는 경우와 후보 A를 줄여 예외 조건(B)을 함께 보존하는 경우의 비교 도식.


다만 발췌 길이를 줄이는 방식에 따라 주의할 점이 다르다. 원문에서 일부 문장만 골라내는 방식은 앞뒤 문맥에 있던 주어나 단서가 잘려 나가기 쉽다. 반면 언어 모델을 한 번 더 호출해 요약문을 새로 만드는 생성 요약은 추가 호출 비용이 들고 요약 과정에서 원래 없던 오류가 섞일 가능성이 생긴다. 따라서 문장 선택과 생성 요약 중 어떤 변환을 거쳤는지 기록해 두고 원문 청크(chunk, 검색 단위로 나눈 문서 조각) 식별자와 연결해 두면, 축약 전후의 의미가 달라지지 않았는지 나중에 대조할 수 있다.


## 직렬화한 다음 한 번 더 세기


발췌할 내용을 골랐더라도 청크 본문의 토큰 수만 더해서는 실제 입력 길이를 정확히 알 수 없다. 모델에 전달할 때는 출처 인용 표식, 문서 제목, 영역 구분자, 메시지 역할(role) 정보 같은 형식 요소가 함께 붙기 때문이다. 그래서 후보 조각들을 최종 메시지 형태로 **직렬화**(serialization, 데이터 구조를 모델에 보낼 실제 문자열이나 메시지 배열 형태로 변환하는 과정)한 뒤, 사용할 모델의 토크나이저나 길이 계산 API로 전체 입력 토큰 수를 다시 확인해야 한다. 아래 의사 코드는 메시지 조립과 길이 계산 함수가 준비되어 있다고 가정했을 때의 검사 흐름이다.


```python
chosen = []
for excerpt in candidates:
    trial = chosen + [excerpt]
    messages = compose_messages(question, trial)
    if count_input_tokens(messages) <= input_budget:
        chosen = trial
    else:
        record_exclusion(excerpt.id, reason="input_budget")
```


이 코드는 후보를 하나씩 더해 실제 메시지를 조립(`compose_messages`)해 보고, 전체 입력 예산(`input_budget`)을 넘는 후보를 제외하며 그 이유를 기록(`record_exclusion`)한다. 다만 이 크기 검사 로직 자체는 제외된 후보가 답변에 꼭 필요한 예외 조건인지까지는 판단하지 못한다. 결국 어떤 내용을 우선 보존할지 결정하는 선택 정책과 최종 크기를 확인하는 검사 단계는 역할을 나누어 설계해야 한다. 만약 크기 검사를 거친 뒤 남은 후보가 하나도 없다면, 억지로 답변을 생성하지 않고 근거 부족으로 처리하는 분기를 두는 편이 안전하다.


## 발췌의 내용과 실행 지시를 나누기


검색된 문서를 직렬화해 문맥에 넣을 때는 본문 내용과 시스템의 실행 지시가 섞이지 않게 경계를 나눠야 한다. 검색 문서 안에는 일반 설명뿐 아니라 명령문처럼 보이는 문장이 들어 있을 수도 있기 때문이다. 예를 들어 문서 본문에 "앞의 지시를 무시하라" 같은 문구가 적혀 있더라도, 이는 어디까지나 참고용 인용 데이터로 취급해야 한다. 모델이 따라야 할 실행 지시는 애플리케이션이 정한 별도 경로로만 전달한다.


이를 위해 프롬프트를 조립할 때 발췌 본문을 별도의 자료 구분자로 감싸 모델이 참고 자료 영역임을 구분하도록 돕는다. 물론 구분자만으로는 문서 안에 숨긴 악의적 지시로 모델 동작을 흔드는 **프롬프트 인젝션**(prompt injection)을 모두 막을 수 없으므로, 외부 도구의 실행 권한 제어와 모델 출력 검증은 애플리케이션 단계에서 직접 관리해야 한다. 문서의 열람 권한을 확인하는 일도 마찬가지다. 권한이 없는 비공개 문서를 문맥에 넣어 두고 모델에게 "비공개 문장은 출력하지 말라"고 지시하기보다, 검색 후보를 문맥에 담기 전에 사용자의 열람 권한을 먼저 확인해 권한 밖의 자료는 아예 문맥에서 제외하도록 단계를 분리한다. 그림 3처럼 열람 권한 확인, 질문 관련 발췌 선택과 변환 기록, 직렬화 뒤의 최종 길이 확인, 모델 호출 후의 인용 연결과 출력 검사를 각각 독립된 단계로 나누면 어느 단계에서 후보가 빠지거나 문제가 생겼는지 추적하기 쉽다.


![검색 후보에서 열람 권한을 먼저 확인해 권한이 없으면 문맥에서 제외하고, 권한이 있으면 관련 발췌 선택과 변환 기록, 최종 입력 길이 확인을 거쳐 모델을 호출한 뒤 인용 연결과 출력 검사를 수행하는 가로 흐름도](/images/notion/tech-s08/image-3.png)


그림 3. 자료의 열람 권한 확인, 발췌 선택, 직렬화 뒤 길이 검사, 모델 호출 후 출력 검사를 단계별로 분리한 문맥 구성 흐름도.


## 입력 길이와 근거 활용의 평가


지금까지 살펴본 절차로 토큰 예산 안에 발췌를 맞춰 넣었더라도, 모델이 그 안의 근거를 모두 똑같은 비중으로 잘 활용하는 것은 아니다. Liu 외(2024)의 _Lost in the Middle_ [논문 원문](https://aclanthology.org/2024.tacl-1.9/)은 긴 문맥에서 정답 단서가 들어 있는 문서의 위치에 따라 모델의 질의응답 정확도가 크게 달라지는 현상을 보고했다. 문서 20개(약 4,000토큰)를 문맥에 넣은 실험에서 정답 문서가 맨 앞이나 맨 뒤에 있을 때보다 중간 위치에 놓였을 때 정확도가 뚜렷하게 떨어졌고, 일부 구간에서는 문서를 전혀 주지 않고 답하게 한 기준선(closed-book)보다도 낮은 정확도를 보였다. 그림 4는 [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/) 라이선스로 공개된 원문의 Figure 1을 발췌한 것이다.


![문서 20개 중 정답 문서의 위치가 1번째일 때 약 76%, 10번째 중간 위치일 때 약 54%로 기준선(56.1%) 아래로 떨어졌다가 20번째 끝 위치에서 약 63%로 다시 올라가는 U자형 정확도 그래프](/images/notion/tech-s08/image-4.png)

이 실험 결과를 현재의 모든 언어 모델에 그대로 일반화할 수는 없지만, 토큰 예산이 허락한다고 해서 후보 문서를 무조건 많이 채워 넣는 전략이 항상 유리하지는 않다는 점은 분명히 보여 준다. 앞으로 문맥 조립 방식을 비교할 때는 같은 핵심 근거를 입력의 앞, 중간, 뒤에 각각 배치해 보는 조건을 함께 두고 확인할 수 있다. 이때 단순 답변 정확도뿐 아니라 앞서 살펴본 예외 조건이 답변에서 누락되지 않았는지, 모델이 표시한 인용 표식이 실제 원문 청크와 제대로 대응하는지까지 함께 기록하면 문맥 조립 방식의 효과를 더 구체적으로 검증할 수 있다.
