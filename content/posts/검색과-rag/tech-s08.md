## 문맥 조립 단계의 제약


앞 글에서 합친 검색 결과를 토큰 예산 안에 배치하는 과정을 정리했다. 발췌의 개수뿐 아니라 각 길이와 질문, 대화 이력, 출력 공간을 함께 계산했다. 결과를 세 개로 제한하는 설정과 입력 길이 제한의 차이를 예제로 살펴봤다.


검색 발췌 세 개를 하나의 입력으로 조립했다. 토큰은 모델이 텍스트를 처리하는 단위이며 문자 수나 단어 수와 항상 같지는 않다. 실제 길이는 사용하는 토크나이저에 따라 달라지므로 예제의 수치는 예산 비교용으로 두었다.


## 결과 개수와 토큰 예산


가상의 모델 호출에서 입력과 출력이 함께 사용하는 문맥 예산을 4,000토큰으로 잡았다. 시스템 지시, 질문, 대화 이력, 도구 스키마에 900토큰, 최대 출력에 600토큰, 형식과 계산 오차를 위한 여유에 100토큰을 배정하면 발췌에 쓸 수 있는 공간은 2,400토큰이다. 실제 API에서는 모델마다 문맥과 출력 한도의 관계가 다르므로 이 계산을 그대로 설정값으로 가져가지는 않는다.


| 후보 | 내용             | 예제 토큰 수 | 검색 순위 |
| -- | -------------- | ------- | ----- |
| A  | 기본 설정과 배경 설명   | 1,500   | 1     |
| B  | 적용할 수 없는 예외 조건 | 1,200   | 2     |
| C  | 같은 설정을 요약한 표   | 500     | 3     |


세 개를 모두 넣으면 3,200토큰으로 발췌 예산을 넘는다. 상위 두 개만 골라도 2,700토큰이라 들어가지 않는다. `top_k=2`는 결과 개수를 제한하며, 문맥의 총길이는 별도로 계산해야 한다.

## 순위대로 채우는 방법의 부담


A부터 넣고 남은 공간에 C를 넣으면 2,000토큰이라 예산 안에 들어간다. 구현도 단순하다. 하지만 질문이 예외 상황을 묻고 있다면 가장 필요한 B가 빠진다. 검색 점수순 선택 후에도 답변에 필요한 근거가 포함됐는지 대조해야 한다.


여기서는 A에서 질문에 필요한 문장만 600토큰 분량으로 선택하고 B의 1,200토큰과 함께 넣는 대안을 생각해 보았다. 합계 1,800토큰이어서 예산을 지키면서 기본 조건과 예외를 함께 남길 수 있다. 선택 전략을 비교하기 위해 구성한 예시 토큰 수다.


발췌를 줄이는 방식에도 차이가 남았다. 문장 선택은 주어나 단서가 잘릴 수 있고, 생성 요약은 호출 비용과 새 오류의 가능성이 더해진다. 두 방식을 구분하고 원문 청크와 연결하면 축약 전후 의미를 비교할 수 있다.


## 직렬화한 다음 한 번 더 세기


청크 본문만 세면 인용 표식과 제목, 구분자 같은 형식 비용을 놓친다. 최종 메시지 형태로 조립한 다음 사용하는 모델에 맞는 방법으로 다시 확인해야 한다. 아래는 길이 계산 함수를 API나 토크나이저에 맞게 제공한다고 가정한 의사 코드다.


```python
chosen = []
for excerpt in candidates:
    trial = chosen + [excerpt]
    messages = compose_messages(question, trial)
    if count_input_tokens(messages) <= input_budget:
        chosen = trial
    else:
        record_exclusion(excerpt.id, reason="input_budget")
```


의사 코드는 크기를 넘는 후보를 제외하는 부분까지다. 예외 조건의 중요성은 판단하지 않는다. 보존할 내용을 고르는 정책과 크기 검사를 분리하고, 후보가 남지 않는 경우에는 근거 부족을 처리하는 경로를 두는 구성을 비교했다.


## 발췌의 내용과 실행 지시를 나누기


검색 문서에는 작성자의 설명뿐 아니라 명령처럼 보이는 문장도 들어갈 수 있다. 자료 속 “앞의 지시를 무시하라” 같은 문장은 인용 데이터로 취급하고, 실행 지시는 애플리케이션이 정한 경로에서 전달한다. 발췌를 자료 영역으로 구분하고, 도구 실행 권한과 출력 검증은 애플리케이션이 관리해야 한다.


자료 구분자는 모델의 해석을 돕는 요소로 두었다. 프롬프트 인젝션 대응에는 외부 행동의 권한과 출력 검증도 관련된다. 검색 전 접근 권한 확인 역시 모델에 비공개 문장을 출력하지 말라고 지시하는 일과 구분했다.

## 입력 길이와 근거 활용의 평가


입력 한도에 들어간다는 사실과 모델이 근거를 잘 활용한다는 사실도 다르다. _Lost in the Middle_은 긴 문맥에서 관련 정보의 위치에 따라 성능이 달라지는 현상을 보고했다. 이 결과를 모든 현재 모델에 그대로 적용할 수는 없지만, 필요한 근거를 무조건 많이 넣는 전략을 검증해야 할 이유는 된다.
