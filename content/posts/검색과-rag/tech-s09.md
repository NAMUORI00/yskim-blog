## 원문 버전과 검색 색인이 어긋나는 경우


문서를 검색해 답변을 생성하는 시스템에서는 원문과 별개로 청크나 벡터 같은 검색 표현을 따로 저장한다. 이때 원문이 수정되더라도 검색 색인이 즉시 갱신되지 않으면 두 저장소의 상태가 어긋난다. 원문이 저장된 시점과 검색 결과가 최신화되는 시점을 분리해 봐야 반영이 지연된 단계를 좁힐 수 있다. 아래 예제는 벡터 검색을 중심으로 설명하지만, 모든 검색 색인이 임베딩만 사용하는 것은 아니다.


예를 들어 설명용 문서 D의 버전 7에 "점검 간격 10분"이라고 적혀 있었고, 버전 8에서 이 문구를 "점검 간격 5분"으로 수정했다고 하자. **원문 저장소**는 이미 버전 8로 바뀌었더라도 **검색 색인**이 아직 버전 7의 청크를 반환하면, 생성 모델에는 여전히 "10분"이라는 근거가 전달된다. 모델이 검색 결과를 충실하게 인용하더라도 최신 답변은 되지 않는다.


검색 점수와 본문이 서로 다른 버전을 가리키는 더 헷갈리는 경우도 있다. 검색 색인의 벡터는 버전 7에서 만들었는데, 검색 직후 같은 문서 ID로 버전 8의 본문을 가져오면 계산된 검색 점수와 화면에 표시되는 근거가 서로 다른 버전을 설명하게 된다. 따라서 문서 ID뿐 아니라 청크 버전, 검색 표현을 만든 모델, 처리 설정까지 함께 연결해 두어야 한다.

검색 저장소 내부에서도 새 데이터를 기록한 뒤 검색에서 찾을 수 있는 시점과 검색 가속용 구조가 완성되는 시점은 구분해야 한다. Qdrant는 세그먼트 상태와 설정에 따라 인덱스가 아직 없는 데이터에 전수 검색을 사용할 수 있고, HNSW 그래프를 구축하는 중에도 구현에 따라 다른 탐색 경로로 검색할 수 있다. 어떤 조건에서 미최적화 데이터를 검색 대상에서 제외하는지도 설정과 함께 봐야 한다([Qdrant 색인 문서](https://qdrant.tech/documentation/manage-data/indexing/)).


## 여러 저장소를 다루는 코드의 갱신과 삭제 경계


`smartfarm-search`의 [`RetrievalService`](https://github.com/NAMUORI00/smartfarm-search/blob/17b5a0b3e1f4637900121c2b17cb9047d755b6c7/core/retrieval/service.py)를 보면 원문 오버레이와 검색용 저장소를 다루는 호출이 한 서비스에 모여 있다(비공개 저장소이므로 링크 열람에는 접근 권한이 필요하다).


메모를 등록하는 `ingest_private_memo`는 먼저 SQLite 기반의 오버레이에 기록한 뒤 정보를 추출하고, Qdrant와 그래프 저장소에 검색 지식을 반영하는 경로를 차례로 호출한다. 그러나 SQLite, Qdrant, 그래프 저장소 호출이 한 함수에 모여 있다는 사실만으로 분산 트랜잭션이 보장되지는 않는다. 뒤 단계가 실패한 후 남는 상태와 재시도 시 발생할 수 있는 중복은 별도로 확인해야 할 범위로 두었다.


삭제 경로에서도 비슷한 경계가 보인다. `purge_private`는 오버레이, Qdrant, 그래프 저장소의 삭제를 순서대로 호출하고 각 결과 수를 반환한다. 이 API는 농장 단위로 데이터를 정리하는 경로이지, 수정된 문서 한 건의 버전을 교체하는 API가 아니다. 문서 수정 후 이전 청크를 지우는 방법을 소개하면서 농장 전체 삭제를 같은 동작처럼 제시하면 기능의 범위가 어긋난다.


만료 삭제 경로에는 더 구체적인 차이가 있다. 확인한 코드에서 농장 식별자인 `farm_id`는 오버레이와 그래프 저장소 호출에는 전달되지만 Qdrant 호출에는 전달되지 않는다. 따라서 세 저장소를 같은 농장 범위로 모두 정리한다는 설명은 이 코드와 맞지 않는다.

## 검색 표현의 버전 관리와 색인 이전


원문이 같아도 임베딩 모델, 토큰화, 정규화 방식이 달라지면 검색 표현이 달라질 수 있다. 벡터의 차원 수가 같다는 이유만으로 서로 다른 모델이 만든 문서 벡터와 질의 벡터를 섞어 비교할 수 있다고 보기는 어렵다. 호환성을 별도로 확인하지 않았다면 문서 색인과 질의 처리를 같은 표현 체계로 맞추어야 한다.


설정 이름이나 이전 README보다 실제 호출 경로를 기준으로 `smartfarm-search` 코드를 확인해 보면 두 가지 표현 경로가 나뉘어 있다. [`임베딩 팩토리`](https://github.com/NAMUORI00/smartfarm-search/blob/17b5a0b3e1f4637900121c2b17cb9047d755b6c7/core/embeddings/factory.py)는 학습된 의미 임베딩을 위해 Hugging Face API 제공자를 만든다. 반면 Qdrant 클라이언트의 희소 표현에는 토큰 해시와 빈도 계산이 사용된다. 학습된 의미 임베딩과 입력을 표현하는 방식이 달라 두 경로를 나누어 살펴보았다.


새로운 검색 표현으로 옮길 때는 **후보 색인**을 따로 만들고 검색 결과와 문서 버전을 대조하는 방법을 생각할 수 있다. Qdrant의 컬렉션 별칭 변경은 검색 대상을 바꾸는 수단이지만, 애플리케이션의 질의 임베딩 모델까지 자동으로 맞춰 주지는 않는다([컬렉션 문서](https://qdrant.tech/documentation/manage-data/collections/)). 전환 중 유입된 원문 변경, 질의 제공자 설정, 원문 버전의 정합성은 애플리케이션이 함께 다뤄야 한다.

## 검색 결과에서 원문 버전까지 되짚기


색인 갱신이 반영되었는지 확인하려면 검색 시점에 원문 버전, 색인 버전, 질의의 표현과 필터를 함께 남기는 형식을 생각할 수 있다. 한편 코드에서 확인한 `health/ready` 함수는 설정된 주소만 반환하므로, 이 응답만으로 세 저장소의 현재 요청 성공 여부까지 확인할 수는 없다.


색인이 최신 원문으로 반영된 이후에는 이미 생성된 답변의 근거 버전 문제가 남는다. 새 색인을 만드는 일과 전달 대기 중인 답변을 다시 확인하는 일은 서로 다른 단계이므로, 다음 글에서는 답변의 상태 의존성과 재검증 범위를 이어서 다룬다.
