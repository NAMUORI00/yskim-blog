## 원문 버전과 검색 색인


원문과 검색 색인의 갱신 시점을 나누어 정리했다. 설명용으로 점검 간격을 10분에서 5분으로 바꾸는 문서를 두었다. 검색 표현을 별도로 저장하는 구조에서는 원문의 수정 이후 색인에 반영되는 흐름도 확인 대상이 된다.


원문 저장과 검색 결과의 최신성을 서로 다른 상태로 읽었다. 이 구분이 있어야 반영이 늦어진 단계를 좁힐 수 있다. 예제는 벡터 검색을 중심으로 두었으며 모든 색인이 임베딩을 사용하는 것으로 일반화하지 않았다.


## 문서 하나가 두 버전으로 존재하는 예제


설명용 문서 D의 버전 7에 “점검 간격 10분”이 있고, 버전 8에서 이를 “점검 간격 5분”으로 바꿨다고 하자. 원문 저장소는 버전 8인데 검색 색인이 버전 7의 청크를 반환하면, 생성 모델에 전달되는 근거도 10분일 수 있다. 모델이 검색 결과를 충실하게 사용해도 최신 답변은 되지 않는다.


더 헷갈리는 경우도 있다. 기존 벡터는 버전 7에서 만들었는데, 같은 문서 ID로 버전 8의 본문을 가져오면 검색 점수와 표시된 근거가 서로 다른 버전을 설명한다. 따라서 문서 ID뿐 아니라 청크 버전과 검색 표현을 만든 모델, 처리 설정까지 연결할 이유가 생긴다.

## 여러 저장소를 호출하는 한 함수


smartfarm-search의 [`RetrievalService`](https://github.com/NAMUORI00/smartfarm-search/blob/17b5a0b3e1f4637900121c2b17cb9047d755b6c7/core/retrieval/service.py)를 읽으면 원문 오버레이와 검색용 저장소를 다루는 호출이 한 서비스에 모여 있다.


저장소 접근 권한이 필요하다. `ingest_private_memo`는 먼저 오버레이에 기록한 뒤 정보를 추출하고 검색 지식 반영 경로를 호출한다.


코드에서는 오버레이 기록 뒤 정보 추출과 검색 지식 반영을 차례로 호출한다. SQLite, Qdrant, 그래프 저장소가 한 함수에 모여 있다는 사실만으로 분산 트랜잭션이 확인되지는 않는다. 뒤 단계의 실패 후 남는 상태와 재시도 중복은 추가 확인 범위로 두었다.


삭제 경로에서도 비슷한 경계가 보인다. `purge_private`는 오버레이, Qdrant, 그래프의 삭제를 순서대로 호출하고 각 결과 수를 반환한다. 이 API는 농장 단위 정리 경로이지 문서 한 건의 버전을 교체하는 API로 설명할 수 없다. 이전 청크를 지우는 방법을 소개하면서 농장 전체 삭제를 같은 동작처럼 제시하면 범위가 어긋난다.


만료 삭제에는 더 구체적인 차이가 있다. 확인한 코드에서 `farm_id`는 오버레이와 그래프 호출에는 전달되지만 Qdrant 호출에는 전달되지 않는다. 따라서 “같은 농장 범위로 세 저장소를 모두 정리한다”는 설명은 이 코드와 맞지 않는다. 소스에서 확인한 인자 전달 차이를 정리했다.


## 검색 표현의 버전 관리


원문이 같아도 임베딩 모델, 토큰화, 정규화 방식이 달라지면 검색 표현이 달라질 수 있다. 차원 수가 같다는 이유만으로 서로 다른 모델의 문서 벡터와 질의 벡터를 섞어 비교할 수 있다고 보기는 어렵다. 호환성을 별도로 확인하지 않았다면 같은 표현 체계로 맞추는 편이 필요하다.


확인한 저장소의 [`임베딩 팩토리`](https://github.com/NAMUORI00/smartfarm-search/blob/17b5a0b3e1f4637900121c2b17cb9047d755b6c7/core/embeddings/factory.py)는 Hugging Face API 제공자를 만든다.


Qdrant 클라이언트의 희소 표현에는 토큰 해시와 빈도 계산이 사용된다. 학습된 의미 임베딩과 입력을 표현하는 방식이 달라 두 경로를 나누었다. 제공자는 설정 이름이나 이전 README보다 실제 호출 경로를 기준으로 읽었다.


새 표현으로 옮길 때는 후보 색인을 따로 만들고 검색 결과와 문서 버전을 대조하는 방법을 생각할 수 있다. Qdrant의 컬렉션 별칭 변경은 대상을 바꾸는 수단이지만, 질의 임베딩 모델까지 자동으로 맞춰 주지는 않는다.


전환 중 유입된 변경, 질의 제공자 설정, 원문 버전의 정합성은 애플리케이션이 함께 다뤄야 한다. [컬렉션 문서](https://qdrant.tech/documentation/manage-data/collections/).

## 검색 결과에서 원문까지 되짚기


갱신 확인에는 원문 버전, 색인 버전, 질의의 표현과 필터를 함께 남기는 형식을 생각해 보았다. 확인한 `health/ready` 함수는 설정 주소를 반환한다. 이 응답으로 세 저장소의 현재 요청 성공 여부까지 확인할 수는 없다.


색인 반영 이후에는 이미 생성된 답변의 근거 버전이 남는다. 새 색인을 만드는 일과 전달 대기 중인 답변을 다시 확인하는 일을 나누어, 다음에는 답변의 상태 의존성을 살펴봤다.
