농업 RAG의 입력 자료를 마련하며 수집 문서와 검색용 청크를 연결했다. 자료마다 구조와 식별자가 달라 수집, 분할, 코퍼스 검사를 분리하고 검색 단계로 넘길 데이터 계약을 정리했다.


## 구현과 확인 과정


농업 관련 문서 두 저장소의 코드를 읽으며, 수집한 자료가 검색과 평가에 쓰이기까지 어떤 처리를 거치는지 정리했다. 본문 추출, 검색 단위 분할, 질문, 정답 준비, 원문 연결 보존이 각각 별도 단계로 나뉘어 있었다. smartfarm-corpus-pipeline과 smartfarm-ingest가 이 과정을 다루는 독립 저장소였고, 아래 내용은 두 도구의 역할을 구분해서 기록한 것이다. 실제 통합 실행은 전제하지 않았고, 소스 열람에는 저장소 접근 권한이 필요했다.


## 웹에서 자료를 모아 검색용으로 준비하기


### 수집한 자료가 검색에 쓰이기까지


처리 순서는 웹 자료 수집 → 본문 추출 → 문서 분할 → 품질 점검이었다. 전체를 한 번에 실행할 수도 있고, 이미 받아 둔 자료가 있으면 본문 추출부터 다시 시작할 수도 있었다. 분할 기준만 바꿀 경우 웹 수집까지 반복할 필요는 없었다. CLI 명령 이름은 순서대로 `collect`, `extract`, `chunk`, `report-quality`이고, 전체 실행은 `run-all`이다.


[전체 처리 순서를 실행하는 명령 도구](https://github.com/NAMUORI00/smartfarm-corpus-pipeline/blob/dfe7f265b4fb1b83f27078bc0acf9e3b541c2739/src/smartfarm_rag_pipeline/cli.py)

그림 1. smartfarm-corpus-pipeline의 네 단계 워크플로 (코드의 CLI 명령 순서 기준)


중간 결과는 세 종류로 나누어 저장되고 있었다. 수집 기록에는 어떤 자료를 받으려 했는지, 문서 목록에는 추출한 본문을, 문서 조각 목록에는 실제 검색에 사용할 짧은 내용을 담는다. 저장 형식은 한 줄에 한 항목을 담는 JSONL이다. 이렇게 단계별로 분리되어 있어서 원문을 다시 받지 않고도 분할 크기를 바꿔 결과를 비교할 수 있는 구조였다.


### 자료의 출처와 수집 방식을 나누기


자료를 모으는 설정은 학술 자료, 공식 농업 자료, 분류 체계 참고자료, 일반 웹 자료로 나뉘어 있었다. 각 설정에는 자료의 역할, 출처의 성격, 가져오는 방식이 따로 기록되어 있다. 검색 결과를 따라 수집하는 방식, 자료 저장소의 첫 페이지에서 출발하는 방식, 분류 정보나 메타데이터 API를 조회하는 방식이 서로 다른 수집 경로로 구분되어 있었다.


설정을 읽을 때 분류값이 허용된 목록에 있는지 검사하는 로직이 있었다. 다만 오타가 있으면 실행을 멈추는 대신 기본 수집 방식이나 기본 분류로 되돌리는 분기가 존재했다. 그래서 실행이 정상 종료되더라도 의도한 출처 분류로 수집됐는지는 결과를 별도로 확인해야 하는 구조였다.


### 문서 분할 기준


문서 분할은 길이와 함께 문서의 구분 구조를 고려했다. 분할 예정 구간의 뒤쪽 55%에서 문단, 줄바꿈, 마침표, 한국어 문장 끝을 차례로 살펴 자연스러운 경계를 찾는다. 각 구분자는 정해진 우선순위로 검사하며 구간 안에서 마지막으로 나타난 위치를 사용한다. 공개된 실행 예시에서는 한 조각 450자에 앞 조각과 90자를 겹치게 설정되어 있었고, 기본 설정은 1,200자와 160자였다.


예시 설정과 기본 설정의 값이 달라 비교할 때 조건을 맞춰야 한다. [문서 분할 처리](https://github.com/NAMUORI00/smartfarm-corpus-pipeline/blob/dfe7f265b4fb1b83f27078bc0acf9e3b541c2739/src/smartfarm_rag_pipeline/chunker.py)


설명용 예제로 계산하면: 1,200자짜리 문서를 `chunk_chars=450`, `overlap=90`으로 자를 때, 첫 청크는 0~450자 부근(경계 탐색으로 약간 이동)이고, 경계 이동이 없다고 가정하면 두 번째는 360자, 세 번째는 720자, 네 번째는 1,080자에서 시작한다.


구분자를 만나 일찍 자르면 다음 시작도 그 위치에서 overlap을 뺀 값으로 이동하므로, 실제 개수는 원문의 경계에 따라 달라진다.


### 수집 자료의 품질 점검


품질 리포트는 9개 항목을 검사한다. 문서 수 300~800, 청크 수 4,000~12,000, 키워드 적중률 75% 이상, 권위 있는 소스(scholarly + official + taxonomy) 비율 85% 이상 등이다.


[확인한 커밋의 README](https://github.com/NAMUORI00/smartfarm-corpus-pipeline/blob/dfe7f265b4fb1b83f27078bc0acf9e3b541c2739/README.md)에는 문서 626개, 청크 4,722개, 키워드 적중률 95.85%가 기록돼 있다. 저장소에 기록된 코퍼스 검사 결과다. 최신 수집 상태와 검색, 답변 정확도는 각각 별도 검증 항목이다.


## 문서의 본문, 표, 그림을 검색 자료로 바꾸기


### 글과 표, 그림을 구분해 읽기


PDF나 문서 파일을 읽을 때는 Unstructured 라이브러리를 사용한다. 각 문서 조각에는 식별번호, 내용, 부가정보를 붙인다. 부가정보에는 텍스트, 표, 그림, 수식 중 어떤 종류인지와 원문 위치가 들어가며, 표의 HTML 표현, 수식의 LaTeX 표현, 이미지 데이터의 참조도 담을 수 있다.


본문만 추출하면 잃기 쉬운 표, 수식, 이미지 정보를 함께 보관하는 구조였다. [문서 읽기와 변환 처리](https://github.com/NAMUORI00/smartfarm-ingest/blob/ea3c19e15e2d84539db6f58a9765f1b4af56cfdf/pipeline/document_parser.py)


![02-04-02.png](/images/notion/tech-02-04/image-2.png)


그림 2. smartfarm-ingest의 문서 파싱 경로와 폴백 구조 (코드에서 확인한 실제 분기)


[`DoclingParser`](https://github.com/NAMUORI00/smartfarm-ingest/blob/ea3c19e15e2d84539db6f58a9765f1b4af56cfdf/pipeline/docling_parser.py)는 `DocumentConverter`를 먼저 시도하고, 사용할 수 있는 청크가 없으면 부모 파서로 돌아가는 구조였다. 소스 주석에 VLM, MinerU라는 표현이 있었지만, 이 호출부만으로 특정 VLM 구성이 실제로 실행됐는지는 확인할 수 없었다.


라이브러리 버전에 따라 변환 결과의 구조가 달라질 수 있는 부분이었다. Docling 자체가 설치되지 않은 환경에서는 `_HAS_DOCLING = False`가 되어 부모 파서 경로로 넘어간다. 부모 파서도 유효한 세그먼트를 얻지 못하면 파일을 텍스트로 읽는 대체 경로가 있었다. PDF 같은 바이너리 파일에서 이 마지막 경로가 의미 있는 문서를 복원한다는 보장은 없다.


텍스트 분할의 `token`은 이 코드에서 정규식 `\S+`로 찾는 공백 구분 단위다. LLM 토크나이저의 토큰 수와 같다고 해석하지 않았다. 표, 이미지, 수식은 텍스트 윈도우와 다른 단일 청크 경로를 사용한다.


### 검색 결과에서 원문으로 돌아가기


이 저장소의 청크 ID 규칙은 `{문서이름}#{접두사}{순번}` 형식이었다. 텍스트 청크는 `#t`, 이미지는 `#i`, 수식은 `#f` 접두사가 붙는다.


테이블도 `modality[:1]`로 `#t`가 되어 텍스트와 접두사가 같지만, `metadata`의 `modality` 필드에서는 구분된다. `chunk_id`와 metadata를 함께 보면 어떤 문서의 몇 번째 세그먼트이고 어떤 모달리티인지 식별할 수 있는 구조였다.


README에 따르면, Qdrant 페이로드에는 `canonical_doc_id`, `canonical_chunk_id`, `doc_id`, `chunk_id`가 모두 포함된다. 기존 인덱스에는 canonical 키가 없으므로 backfill을 위해 reindex가 필요하다는 마이그레이션 노트도 명시되어 있다.


### 만든 검색 자료를 다른 기기로 옮기기


검색 자료를 내보낼 때는 벡터 검색용 Qdrant와 관계 검색용 FalkorDB의 파일 목록을 만든다. 목록에는 각 파일의 위치, 크기, SHA-256 해시가 기록된다. 가져오는 쪽에서는 복사 전에 기대한 해시와 대조해 내용 변경 여부를 확인하는데, 해시가 비어 있는 항목은 이 검사를 건너뛰게 되어 있었다.


작은 현장 기기로 검색 자료를 옮기는 경우에도 이 해시 검증 조건이 적용된다. [검색 자료 가져오기](https://github.com/NAMUORI00/smartfarm-ingest/blob/ea3c19e15e2d84539db6f58a9765f1b4af56cfdf/pipeline/artifact_import.py)


해시 검증은 `--skip-sha256-check` 플래그로 끌 수 있고, 기본값은 검증 활성이었다. `manifest_sha256`도 내보내기에 기록되지만, 읽어 본 가져오기 함수에서 이 필드를 다시 계산해 대조하는 처리는 없었다.


개별 파일의 해시가 있다는 것만으로 출처 인증이나 매니페스트 전체 검증이 이루어졌다고 보기는 어려웠다. 파일을 복사하는 과정과 실행 중인 데이터베이스의 일관된 스냅샷을 만드는 과정도 별도의 확인 항목으로 남았다.


## 두 저장소의 경계


smartfarm-corpus-pipeline은 웹 수집과 코퍼스 릴리즈에 집중하고, smartfarm-ingest는 이미 수집된 문서를 파싱하여 벡터, 그래프 인덱스에 넣고 엣지에 동기화하는 역할을 맡고 있었다.


두 저장소가 같은 파이프라인의 앞뒤 단계로 연결되는지는 코드에서 직접적인 import나 호출 관계를 찾지 못했다. 같은 JSONL 형식 안에서도 필드와 ID 규칙은 각각의 데이터 계약에 따라 달랐다. 한쪽 출력이 다른 쪽 입력에 그대로 들어가는지는 변환 코드를 별도로 확인할 필요가 있다.


답변 평가 자료는 기존 질문, 정답에 검색한 문서 조각을 붙여 만드는 구조였다. 질문과 정답은 Hugging Face 데이터셋 또는 JSONL 파일에서 읽고, 각 질문으로 수집 자료를 검색해 근거 문맥을 연결한다.


이렇게 만든 질문, 정답, 근거 묶음은 RAGAS 평가에 사용할 수 있다. 답변이 근거에 충실한지, 검색 결과에 필요한 내용이 얼마나 포함되어 있는지를 따로 계산하는 방식이다. [RAGAS 공식 문서](https://docs.ragas.io/en/stable/)


Qdrant 벡터 데이터베이스의 페이로드 구조와 필터링에 대해서는 [Qdrant 공식 문서](https://qdrant.tech/documentation/)를, FalkorDB 그래프 데이터베이스의 Cypher 쿼리와 스키마에 대해서는 [FalkorDB 공식 문서](https://docs.falkordb.com/)를 참고할 수 있다.


---


후속으로는 두 경로의 청크가 실제로 같은 인덱스에 들어가는 경우를 확인해 볼 수 있겠다. corpus-pipeline의 청크 파라미터(`chunk_chars=450`)와 ingest의 토큰 윈도우(`chunk_token_size=1200`)는 단위가 다르다. 두 결과를 함께 사용하는 경로가 있다면, 이 크기 차이가 검색 품질에 미치는 영향도 비교 대상이 된다.


## 작업을 정리하며


검색 품질을 비교하기 전에 입력 자료가 어떤 규칙으로 만들어졌는지 설명할 수 있어야 한다. 원문 ID, 청크 위치, 수집, 분할 설정을 함께 남기는 방식이 그 출발점이다. 이 연결이 있으면 수집 오류와 검색 오류를 나누어 살펴볼 수 있다.
