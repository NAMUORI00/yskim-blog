질문과 관련된 문서를 먼저 찾아 답을 만드는 **검색 증강 생성**(RAG)에서는 답변이 틀렸을 때 원인을 두 갈래로 나누어 찾아야 한다. 원래 문서를 잘못 모으고 잘라서 필요한 내용이 빠진 것인지, 아니면 검색 단계에서 엉뚱한 문서를 고른 것인지 구분해야 하기 때문이다. 이를 가리려면 원문에서 본문을 뽑아 검색용 조각으로 나누고, 질문과 정답을 묶어 평가하기까지 데이터 구조와 식별번호 규칙이 일관되어야 한다.


이 글에서는 농업 문서를 다루는 두 독립 저장소인 `smartfarm-corpus-pipeline`과 `smartfarm-ingest`의 코드를 읽고 자료 처리 흐름을 추적했다. 문서를 모아 자르는 단계부터 검색용 데이터베이스에 넣고 평가하는 단계까지 어떤 규칙으로 데이터를 다루는지 확인했다. 두 도구의 실제 통합 실행은 전제하지 않았으며, 소스 코드를 열람할 때는 저장소 접근 권한이 필요했다.


## 네 단계 수집 흐름과 출처 분류


두 저장소 가운데 먼저 살펴볼 `smartfarm-corpus-pipeline`은 웹에서 원문을 모아 검색용 문서 묶음인 **코퍼스**(corpus)를 만들고 품질을 점검한다. 명령줄 도구(CLI)는 `collect`, `extract`, `chunk`, `report-quality` 네 단계를 차례대로 수행한다. 웹 자료 수집과 본문 추출, 문서 분할, 품질 점검에 해당하며 전체 과정을 한 번에 실행할 때는 `run-all`을 쓴다. 각 단계가 끝나면 한 줄에 항목 하나씩 적는 JSONL 파일로 중간 결과를 나누어 저장한다. 수집 기록 파일에는 받으려 한 자료를 남기고, 문서 목록 파일에는 추출한 본문을 담는다. 이어지는 조각 목록 파일에는 실제 검색에 쓸 짧은 문서 조각인 **청크**(chunk)를 기록한다. 세부 구현은 [전체 처리 순서를 실행하는 명령 도구](https://github.com/NAMUORI00/smartfarm-corpus-pipeline/blob/dfe7f265b4fb1b83f27078bc0acf9e3b541c2739/src/smartfarm_rag_pipeline/cli.py)에서 확인할 수 있다.

그림 1. smartfarm-corpus-pipeline의 네 단계 CLI 처리 흐름과 단계별 중간 산출물 (코드의 CLI 명령 순서 기준).


이처럼 단계마다 입출력 파일이 분리되어 있어서 이미 받아 둔 원문이 있으면 `extract`부터 다시 시작할 수 있다. 문서를 자르는 크기만 바꿔 결과를 비교할 때도 웹 수집 과정을 되풀이할 필요가 없다.


첫 단계의 수집 설정은 학술 자료(`scholarly`), 공식 농업 자료(`official`), 분류 체계 참고자료(`taxonomy`), 일반 웹 자료의 네 가지로 나뉜다. 각 설정에는 자료의 역할과 출처 성격, 문서를 가져오는 방식이 따로 적혀 있다. 수집 경로 또한 검색 결과를 따라가는 방식, 저장소 첫 페이지에서 출발하는 방식, 분류 정보나 메타데이터 API를 조회하는 방식으로 구분된다.


프로그램은 설정을 읽어 들일 때 분류값이 허용된 목록에 있는지 검사한다. 그런데 설정 파일에 오타가 있으면 실행을 멈추는 대신 기본 수집 방식이나 기본 분류로 되돌리는 분기가 들어 있었다. 이 때문에 명령이 오류 없이 끝나더라도 의도한 출처 분류대로 자료가 모였는지는 결과 파일을 따로 열어 확인해야 한다.


## 문장 경계 기반 분할과 품질 점검


본문을 검색 단위로 자르는 `chunk` 단계는 조각 크기(`chunk_chars`)와 앞 조각과 겹치는 길이(`overlap`), 문장 경계를 함께 살핀다. 예를 들어 1,200자짜리 문서를 `chunk_chars=450`, `overlap=90` 조건으로 글자 수에 맞춰 자르면 첫 번째 청크는 0~450자 구간을 담는다. 두 번째 청크는 450자에서 겹치는 길이인 90자를 뺀 360자부터 시작하며, 세 번째는 720자, 네 번째는 1,080자에서 출발한다.


하지만 글자 수로만 자르면 문장이 중간에 끊기므로, [문서 분할 처리](https://github.com/NAMUORI00/smartfarm-corpus-pipeline/blob/dfe7f265b4fb1b83f27078bc0acf9e3b541c2739/src/smartfarm_rag_pipeline/chunker.py) 코드는 분할 예정 구간의 뒤쪽 55% 범위에서 자연스러운 경계를 탐색한다. 문단, 줄바꿈, 마침표, 한국어 문장 끝을 우선순위대로 검사해 해당 구간 안에서 가장 마지막에 나타난 위치를 자르는 지점으로 삼는다. 실제 문서에서 뒤쪽 55% 구간에 있는 구분자를 만나 450자보다 일찍 자르면 다음 청크의 시작 위치도 그 지점에서 `overlap`만큼 앞으로 당겨진다. 따라서 원문의 문장 경계 위치에 따라 최종 청크 개수가 달라진다.


![1,200자 원문을 450자 길이와 90자 겹침으로 나눈 4개 청크의 구간 배치도](/images/notion/tech-02-04/image-2.png)


그림 2. 1,200자 문서를 chunk_chars=450, overlap=90 조건으로 자를 때의 시작 위치와 뒤쪽 55% 경계 탐색 구간 예제.


공개된 실행 예시에서는 `chunk_chars`를 450자, `overlap`을 90자로 두었지만 코드의 기본 설정값은 1,200자와 160자다. 예시 설정과 기본 설정의 수치가 다르므로 검색 실험을 비교할 때는 이 분할 조건부터 맞춰야 한다.


마지막 `report-quality` 단계에서는 구축한 코퍼스가 기준을 충족하는지 9개 항목을 검사한다. 전체 문서 수가 300~800개 사이인지, 청크 수가 4,000~12,000개 범위인지, 주요 키워드 적중률이 75% 이상인지를 확인한다. 학술 자료와 공식 농업 자료, 분류 체계 참고자료를 합친 권위 있는 출처(`scholarly` + `official` + `taxonomy`) 비율이 85% 이상인지도 살핀다. [확인한 커밋의 README](https://github.com/NAMUORI00/smartfarm-corpus-pipeline/blob/dfe7f265b4fb1b83f27078bc0acf9e3b541c2739/README.md)에는 문서 626개, 청크 4,722개, 키워드 적중률 95.85%라는 코퍼스 검사 결과가 기록되어 있다. 다만 이 수치는 저장소에 남겨진 코퍼스 자체의 점검 기록이므로, 최신 수집 상태나 실제 검색과 답변 정확도는 별도로 검증해야 한다.


## 문서 요소별 추출과 파서 대체 경로


두 번째 저장소인 `smartfarm-ingest`는 앞선 도구와 달리 이미 수집된 PDF나 문서 파일을 읽어 검색 데이터베이스에 넣는다. 문서에서 일반 본문만 뽑아내면 표나 수식, 그림 정보가 사라지기 쉽다. 이를 막기 위해 [문서 읽기와 변환 처리](https://github.com/NAMUORI00/smartfarm-ingest/blob/ea3c19e15e2d84539db6f58a9765f1b4af56cfdf/pipeline/document_parser.py) 코드는 추출한 각 조각에 식별번호와 내용, 부가정보(`metadata`)를 함께 붙인다. 부가정보에는 글자, 표, 그림, 수식 가운데 어떤 자료 형태인지를 뜻하는 **모달리티**(modality)와 원문 위치가 기록된다. 표의 구조를 살린 HTML 표현이나 수식의 LaTeX 표현, 이미지 데이터 참조도 부가정보에 함께 담을 수 있다.


문서 파일에서 내용을 읽어 내는 도구인 **파서**(parser)는 앞선 방법이 실패하면 다음 방법으로 넘어가는 대체 경로를 갖추고 있다. [`DoclingParser`](https://github.com/NAMUORI00/smartfarm-ingest/blob/ea3c19e15e2d84539db6f58a9765f1b4af56cfdf/pipeline/docling_parser.py)는 먼저 Docling의 `DocumentConverter`를 시도하고, 쓸 수 있는 청크가 나오지 않으면 상위 파서인 Unstructured 라이브러리 경로로 넘어간다. Docling이 설치되지 않은 환경에서는 `_HAS_DOCLING = False`가 되어 곧바로 상위 파서로 이동한다. 상위 파서도 유효한 조각을 얻지 못하면 파일을 일반 텍스트로 읽어 들이는 마지막 대체 경로를 탄다. 다만 PDF 같은 바이너리 파일에서는 이 마지막 경로가 의미 있는 문서를 복원한다는 보장이 없다. 소스 코드 주석에는 VLM과 MinerU라는 표현이 적혀 있었으나, 이 호출부만으로는 특정 VLM 구성이 실제로 실행되었는지 확인할 수 없었다. 라이브러리 버전에 따라 변환 결과 구조가 달라질 여지도 있었다.


![Docling 변환기에서 Unstructured 파서와 단순 텍스트 읽기로 이어지는 문서 파싱 폴백 흐름도](/images/notion/tech-02-04/image-3.png)


그림 3. smartfarm-ingest의 문서 파싱 경로와 단계별 폴백 구조 (코드에서 확인한 실제 분기).


추출한 조각을 검색용 청크로 자르는 방식도 모달리티에 따라 나뉜다. 표와 이미지, 수식은 텍스트 분할 구간을 거치지 않고 각각 단일 청크로 만든다. 반면 일반 텍스트를 자를 때 기준이 되는 `token`은 이 코드에서 공백이 아닌 글자 덩어리를 찾는 정규식 `\S+` 단위다. 공백으로 구분한 어절을 세는 방식이므로 언어 모델(LLM) 토크나이저가 세는 토큰 수와는 다르다.


## 청크 식별자 규칙과 현장 기기 동기화


추출한 청크를 데이터베이스에 넣을 때는 검색 결과에서 다시 원문 위치를 찾아갈 수 있도록 고유한 식별번호를 붙인다. `smartfarm-ingest`는 `{문서이름}#{접두사}{순번}` 형식으로 청크 식별자(`chunk_id`)를 만든다. 예를 들어 일반 텍스트 청크에는 `#t`, 이미지에는 `#i`, 수식에는 `#f` 접두사가 차례대로 붙는다. 그런데 접두사를 모달리티 문자열의 첫 글자(`modality[:1]`)로 만들다 보니 표(`table`)도 텍스트(`text`)와 같은 `#t`를 쓰게 된다. 대신 부가정보(`metadata`) 안의 `modality` 필드에는 원래 종류가 그대로 남는다. 따라서 `chunk_id`와 `metadata`를 함께 읽으면 어떤 문서의 몇 번째 조각이고 텍스트인지 표인지 구분할 수 있다.


저장소 README를 보면 벡터 검색 엔진인 Qdrant에 데이터를 넣을 때 함께 저장하는 부가 데이터(페이로드)에 네 가지 식별자를 담는다. 기본 식별자인 `doc_id`, `chunk_id`와 함께 형식을 통일한 정규화 키인 `canonical_doc_id`, `canonical_chunk_id`가 모두 들어간다. 기존에 만든 인덱스에는 이 정규화 키가 비어 있어서 값을 채우려면 인덱스를 다시 만드는 재색인(reindex)이 필요하다는 마이그레이션 안내도 적혀 있다.


![텍스트와 표의 #t 접두사를 metadata.modality로 구분하고 Qdrant 페이로드에 저장하는 구조도](/images/notion/tech-02-04/image-4.png)


그림 4. smartfarm-ingest의 모달리티별 청크 식별자 규칙과 Qdrant 페이로드 키 구성.


완성한 검색 인덱스를 농장 현장의 소형 기기(엣지 기기)로 옮길 때는 벡터 검색용 Qdrant와 그래프 검색용 FalkorDB의 파일 목록(매니페스트)을 만든다. 이 목록에는 각 파일의 경로와 크기, 그리고 파일 내용이 바뀌면 값도 달라지는 요약값인 SHA-256 **해시**(hash)가 기록된다. 현장 기기에서 실행하는 [검색 자료 가져오기](https://github.com/NAMUORI00/smartfarm-ingest/blob/ea3c19e15e2d84539db6f58a9765f1b4af56cfdf/pipeline/artifact_import.py) 코드는 파일을 복사하기 전에 기록된 해시와 실제 파일의 해시를 대조해 내용이 바뀌었는지 검사한다. 해시 검증은 기본으로 켜져 있으며 `--skip-sha256-check` 플래그로 끌 수 있다.


다만 세부 구현을 보면 해시 필드가 비어 있는 항목은 검증을 그냥 건너뛰도록 작성되어 있었다. 또한 내보내기 단계에서는 매니페스트 전체의 해시인 `manifest_sha256`도 기록하지만, 확인한 가져오기 함수에는 이 값을 다시 계산해 대조하는 처리가 없었다. 결국 개별 파일의 해시가 적혀 있다는 사실만으로 출처가 인증되거나 매니페스트 전체의 무결성이 보장되지는 않는다. 실행 중인 데이터베이스에서 특정 시점의 상태를 일관된 스냅샷으로 떠서 복사하는 과정도 별도로 챙겨야 한다.


## 두 저장소의 데이터 규약과 평가 연결


지금까지 살펴본 두 저장소의 역할을 나란히 놓고 보면 다루는 구간이 뚜렷하게 나뉜다. `smartfarm-corpus-pipeline`은 웹 자료 수집과 코퍼스 품질 점검 및 배포에 집중한다. 반면 `smartfarm-ingest`는 수집된 문서를 파싱해 벡터 및 그래프 인덱스에 적재하고 엣지 기기로 동기화하는 일을 맡는다. 하지만 코드 안에서 한 저장소가 다른 저장소를 직접 `import`하거나 호출해 앞뒤 단계로 이어 주는 연결 고리는 찾지 못했다. 두 도구 모두 JSONL 형식을 다루지만 세부 필드 이름과 식별자 규칙은 각자의 데이터 계약에 따라 달랐다. 문서 분할 단위 또한 두 저장소가 서로 다른 기준을 쓴다. `smartfarm-corpus-pipeline`의 예시 설정은 글자 수 기준(`chunk_chars=450`)으로 문서를 자른다. 반면 `smartfarm-ingest`는 공백으로 구분한 어절 기준(`chunk_token_size=1200`)을 사용한다.


![두 저장소의 분할 단위 차이와 Qdrant 및 FalkorDB 인덱스의 엣지 기기 동기화 흐름 비교도](/images/notion/tech-02-04/image-5.png)


그림 5. smartfarm-corpus-pipeline과 smartfarm-ingest의 역할 경계와 데이터 계약 비교.


이 때문에 한쪽의 출력을 다른 쪽 입력으로 넣거나 두 경로의 청크를 같은 인덱스에 합쳐 쓰려면 변환 코드가 필요하다. 청크 크기 차이가 실제 검색 품질에 미치는 영향도 먼저 확인해야 한다.


준비한 코퍼스를 바탕으로 답변 품질을 평가할 때는 기존 질문과 정답 쌍에 검색된 문서 조각을 붙여 평가셋을 구성한다. Hugging Face 데이터셋이나 JSONL 파일에서 질문과 정답을 읽고, 각 질문으로 수집 자료를 검색해 찾아낸 근거 문맥을 연결하는 방식이다. 이렇게 묶은 데이터는 [RAGAS 공식 문서](https://docs.ragas.io/en/stable/)의 평가 지표에 넣어 답변이 근거 문서에 충실한지, 검색 결과가 필요한 정보를 담고 있는지 따로 계산할 수 있다. 검색 인덱스를 다루는 Qdrant의 페이로드 구조와 필터링 방식은 [Qdrant 공식 문서](https://qdrant.tech/documentation/)에서 자세히 다룬다. FalkorDB 그래프 데이터베이스의 Cypher 쿼리와 스키마 구성은 [FalkorDB 공식 문서](https://docs.falkordb.com/)에서 확인할 수 있다.


## 결론


검색 품질을 비교하기에 앞서 입력 자료가 어떤 규칙으로 만들어졌는지 설명할 수 있어야 문제의 원인을 좁힐 수 있다. 원문 식별자와 청크 위치, 수집 출처, 분할 설정을 데이터마다 함께 남겨 두어야 오답의 원인을 나누어 추적할 수 있다. 문서 수집과 파싱 단계에서 필요한 내용이 빠진 것인지, 검색 단계에서 순서를 잘못 매긴 오류인지 구분할 수 있기 때문이다.


이번에는 두 저장소의 코드를 읽으며 단계별 JSONL 파일 분리와 문장 경계 기반 분할, 모달리티별 청크 식별자 규칙, 현장 기기 동기화의 해시 검사 조건을 확인했다. 설정 오타 시 기본값으로 돌아가는 분기나 빈 해시 항목을 건너뛰는 처리, 두 저장소의 분할 단위 차이처럼 운영할 때 주의할 조건도 함께 드러났다. 다만 두 도구의 실제 통합 실행이나 최신 수집 상태, VLM의 실제 동작 여부, 검색과 답변 정확도는 코드만으로 확인하지 못했으므로 별도로 검증해야 한다.
