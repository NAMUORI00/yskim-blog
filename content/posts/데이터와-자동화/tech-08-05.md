손가락을 구부리는 동작으로 모바일 앱에서 음원을 재생하려면 연속으로 변하는 센서 값을 몇 단계의 숫자로 나누어 소리와 연결해야 한다. 양손 가운데 어느 손가락이 움직였는지 구분해야 하고, 손가락을 구부린 채로 멈춰 있을 때 같은 음이 거듭 울리지 않게 막는 처리도 필요하다. GoldenGlove는 다섯 손가락의 굽힘 센서 값을 소형 제어 보드인 ESP32로 읽어 블루투스로 보내고, 앱에서 이를 받아 음원을 재생하는 장갑이다.


이 글에서는 `NAMUORI00/GoldenGlove` 저장소의 `5a0ecf4` 커밋에 담긴 장갑 코드와 수신 앱(`GoldenGlove.aia`)을 함께 분석한다. 다섯 센서가 읽은 숫자를 네 단계 정수로 바꾸는 기준, 값을 문자열로 묶어 보내는 규칙, 같은 음의 반복 재생을 막는 조건이 어떻게 맞물리는지 확인한다. 코드를 읽고 동작 경로를 파악하는 데 초점을 두었으며, 손동작 인식 정확도나 실제 연주 지연 시간은 따로 측정하지 않았다.


## 센서 원시 값과 단계 변환


음원을 재생하려면 먼저 다섯 손가락에 붙은 굽힘 센서의 상태를 숫자로 읽어야 한다. 보드에 올리는 아두이노 프로그램인 [왼손 스케치](https://github.com/NAMUORI00/golden-glove/blob/5a0ecf46223335f8b1c197128f9daee767b6df72/Arduino/Golden_Glove_LEFT/Golden_Glove_LEFT.ino)는 다섯 손가락 센서를 보드의 GPIO 32, 33, 34, 39, 36번 핀에 연결해 둔다. 스케치는 이 다섯 핀에서 차례대로 `analogRead` 함수를 호출해 각 손가락의 센서 값을 읽어 들인다.


손가락을 구부릴 때 연속으로 변하는 아날로그 전압은 보드 안의 변환기인 **ADC**(Analog-to-Digital Converter)를 거쳐 디지털 숫자로 바뀐다. [Espressif의 ADC 설명](https://docs.espressif.com/projects/arduino-esp32/en/latest/api/adc.html)을 보면 `analogRead`는 별도 보정을 거치지 않은 ADC의 원래 측정값인 원시 값을 그대로 반환한다. 따라서 읽은 숫자가 750이라고 해서 손가락이 750도 구부러졌다고 해석할 근거는 없다. 실제 물리적 각도로 환산하려면 센서 원시 값과 손가락 굽힘 각도 사이의 대응 관계를 따로 측정해 맞추는 과정이 필요하다.


GoldenGlove 스케치는 각도를 계산하는 대신 센서마다 읽은 원시 값을 0~3 범위의 정수로 바꾼다. 연속으로 변하는 측정값을 네 단계의 정수로 줄인 뒤, 다섯 손가락의 값을 한 줄의 블루투스 메시지로 묶어 보낸다.


![손가락 움직임이 아날로그 입력과 analogRead를 거쳐 고정 하한과 시작 기준값 기반의 map 정수 변환을 통과한 뒤 쉼표와 슬래시 형식의 메시지로 조립되어 BluetoothSerial로 송신되는 흐름도](/images/notion/tech-08-05/image-1.png)


그림 1. Golden_Glove_LEFT와 RIGHT 스케치를 바탕으로 구성한 센서 입력부터 블루투스 메시지 송신까지의 경로(메시지 안의 숫자는 설명용 예시).


다만 장갑을 착용한 상태나 사용자 손 크기에 따라 같은 동작에서도 센서 원시 수치가 달라질 수 있다. 원시 값을 0~3으로 나눌 때 기준이 되는 하한과 상한을 코드에서 어떻게 정하는지 이어서 확인했다.


## 센서 기준값 설정과 정수 변환


센서 원시 값을 0~3 범위의 정수로 바꾸려면 센서마다 가장 작은 기준인 하한과 가장 큰 기준인 상한이 필요하다. 스케치의 초기 설정 함수인 `setup`에서 상한(`max_value`)은 전원이 켜질 때 센서마다 한 번 읽은 값으로 정해진다. 손가락을 여러 차례 구부리고 펴면서 움직이는 범위를 반복 측정해 최댓값을 찾는 코드는 들어 있지 않다. 하한(`min_value`)은 코드에 고정된 숫자로 적혀 있는데, 완성된 스케치에서는 앞의 세 센서가 500이고 나머지 두 센서는 각각 400과 200이다. 전원을 켜는 순간의 센서 상태가 이후 모든 변환에서 상한 기준으로 고정된다.


저장소에 함께 있는 [별도 센서 확인 스케치](https://github.com/NAMUORI00/golden-glove/blob/5a0ecf46223335f8b1c197128f9daee767b6df72/Arduino/Flex_sensor_Read_LEFT/Flex_sensor_read_LEFT.ino)는 일부 센서의 하한값과 컴퓨터 화면으로 값을 내보내는 시리얼 출력 주기가 본 스케치와 다르다. 파일 이름은 비슷하지만 센서를 시험하는 코드와 실제 앱으로 값을 보내는 코드의 설정이 서로 다르게 남아 있다.


하한과 상한이 정해지면 아두이노의 비례 변환 함수인 `map`으로 원시 값을 0~3 범위로 바꾼다. 예를 들어 하한을 500, 상한을 1000으로 두고 원시 값 750이 들어왔을 때의 선형 변환 계산식은 다음과 같다.


```plain text
(750 - 500) × (3 - 0) / (1000 - 500) + 0
= 750 / 500
→ 정수 결과 1
```


`map` 함수는 정수 나눗셈만 계산하므로 실수 1.5에서 소수점 아래가 버려지고 정수 1이 된다. 반대로 원시 값이 상한(1000)을 넘긴 1200이면 비례식 계산 결과가 그대로 4가 된다. `map`은 비례식만 계산할 뿐 결과값을 목표 범위인 0~3 안에 자동으로 가두지 않기 때문이다.


![원시 값 500, 750, 1000이 map 정수 변환을 거쳐 각각 0, 1, 3이 되고 상한을 넘긴 1200은 constrain이 없어 목표 범위를 벗어난 4가 되는 비교 그림](/images/notion/tech-08-05/image-2.png)


그림 2. 하한 500과 상한 1000 기준에서 map 함수의 정수 버림 처리와 상한 초과 입력(1200)이 0~3 범위를 벗어나는 계산 예시.


[ESP32의 현재 map 구현](https://github.com/espressif/arduino-esp32/blob/master/cores/esp32/WMath.cpp) 코드를 봐도 정수 연산만 수행할 뿐 상한과 하한 밖의 값을 잘라 내는 범위 검사가 없다. 다만 현재 아두이노 코어에서 하한과 상한이 같을 때 예외를 처리하는 방식이 프로젝트를 진행한 2023년 당시 버전과 똑같은지는 따로 확인하지 않았다.


전원을 켤 때 읽은 시작값(`max_value`)이 고정 하한(`min_value`)과 같거나 지나치게 가까우면 정상적인 변환 구간이 사실상 사라진다. 현재 스케치에는 시작값 역전을 검사하거나, `constrain` 함수로 출력 범위를 제한하거나, 여러 표본을 평균 내어 노이즈를 줄이는 처리가 없다. 앞으로 원시 값과 변환된 단계 값을 함께 로그로 남기면, 값의 흔들림이 센서 자체에서 생기는지 아니면 좁은 변환 구간 때문에 커지는지 구분할 수 있다.


## 블루투스 메시지 형식과 양손 구분


0~3 범위로 변환된 다섯 손가락의 센서 값은 하나의 문자열 메시지로 묶여 블루투스로 전송된다. 메시지는 다섯 센서 값을 쉼표(`,`)로 이어 붙이고 맨 끝에 슬래시(`/`)를 덧붙이는 형식이다. 쉼표는 각 손가락 센서 값 사이의 경계를 나타내고, 슬래시는 다섯 값으로 이루어진 한 묶음이 끝났음을 알린다. 이처럼 값의 경계를 표시하는 문자인 **구분자**를 넣어 문자열로 보내면 컴퓨터의 시리얼 모니터 화면에서 사람이 바로 읽고 확인하기 편하다. 대신 수신하는 앱에서는 구분자를 찾아 문자열을 자르고 값의 개수를 확인하는 해석 과정인 **파싱**(parsing)을 직접 처리해야 한다.


스케치는 블루투스 전송 함수인 `SerialBT.print`로 조립된 문자열을 보낸 뒤 100ms 동안 대기하는 `delay(100)`을 호출한다. 여기서 100ms는 코드에 적힌 단순 대기 시간일 뿐이며, 다섯 센서를 차례로 읽고 문자열을 조립해 전송하는 시간이 매 반복마다 더해진다. 따라서 실제 샘플링 주기와 연주 반응 시간에는 대기 시간뿐 아니라 보드의 계산 시간과 블루투스 통신 시간이 함께 영향을 준다.


양손 장갑을 동시에 쓸 때 왼손과 오른손은 [각기 다른 장치 이름의 스케치](https://github.com/NAMUORI00/golden-glove/blob/5a0ecf46223335f8b1c197128f9daee767b6df72/Arduino/Golden_Glove_RIGHT/Golden_Glove_RIGHT.ino)를 각각의 ESP32 보드에 올려 구분한다. 전송하는 메시지 본문 안에는 어느 손인지 알려 주는 식별자나 송신 순번, 측정 시각이 들어 있지 않다. 대신 수신 앱에서 왼손용과 오른손용 블루투스 연결을 따로 열어 두고, 어느 연결 통로로 들어온 문자열인지를 보고 손을 구분한다.


![왼손과 오른손 ESP32가 100ms 대기로 쉼표와 슬래시 형식의 메시지를 각각의 블루투스 연결로 보내고 10ms 타이머로 동작하는 수신 앱의 두 BluetoothClient가 DelimiterByte 47로 수신하는 구조도](/images/notion/tech-08-05/image-3.png)


그림 3. 양손 ESP32 스케치가 각기 다른 블루투스 연결로 구분자(/) 기반 메시지를 보내고 수신 앱이 연결 통로로 손을 구분하는 구조.


## 수신 앱의 메시지 파싱과 음원 호출


장갑이 보낸 문자열 메시지를 수신 앱이 받아 음원 재생으로 연결하는 과정은 앱 프로젝트 파일에서 확인할 수 있다. 앱 인벤터(App Inventor)로 만든 [`GoldenGlove.aia`](https://github.com/NAMUORI00/golden-glove/blob/5a0ecf46223335f8b1c197128f9daee767b6df72/GoldenGlove.aia) 압축 파일을 열면 화면 구성을 담은 `play.scm` 파일과 블록 로직을 담은 `play.bky` 파일이 나온다. 압축 파일 안에는 저전력 블루투스 규격인 **BLE**(Bluetooth Low Energy) 확장 기능 파일도 함께 들어 있다. 하지만 실제 수신 블록의 `BluetoothClient`는 고전 블루투스 직렬 통신 규격인 **SPP**(Serial Port Profile) 연결을 사용한다. 압축 파일 안의 목록만 보고 BLE 통신을 사용했다고 단정할 수 없었던 이유가 여기에 있다.


`play` 화면에는 왼손용과 오른손용 `BluetoothClient` 컴포넌트가 따로 배치되어 있다. 두 컴포넌트는 구분자 바이트 속성인 `DelimiterByte`가 모두 47로 설정되어 있다. ASCII 코드 47은 `/` 문자이므로 ESP32 송신 스케치가 메시지마다 끝에 붙이는 구분자와 정확히 맞물린다.


앱의 타이머 이벤트가 실행될 때마다 블록은 블루투스 연결 상태와 임시 저장 공간인 수신 버퍼에 쌓인 바이트 수를 먼저 확인한다. 읽을 데이터가 있으면 `ReceiveText(-1)`을 호출해 문자열을 가져온 뒤 쉼표 기준으로 나눈다. [App Inventor 문서](https://ai2.appinventor.mit.edu/reference/components/connectivity.html)를 보면 `ReceiveText`의 바이트 수 인자에 음수를 넣었을 때 `DelimiterByte`에 지정된 문자가 나올 때까지 텍스트를 끊어서 읽어 온다.


쉼표로 분리된 다섯 값 가운데 왼손 블록의 첫 번째부터 다섯 번째 값은 각각 도, 레, 미, 파, 솔 음원 재생 함수와 연결된다. 이때 센서 단계 값만 비교하면 같은 상태가 연속으로 들어오는 동안 타이머가 돌 때마다 같은 음원이 반복해서 호출된다. 이를 막기 위해 블록에서는 센서 값 조건과 함께 현재 재생 상태를 기록하는 변수인 **플래그**(flag)를 확인해 소리를 한 번만 호출한다. 이후 손가락이 반대 상태로 돌아왔을 때 플래그를 원래대로 되돌려 다음 연주를 준비한다.


![양손 수신 스트림을 슬래시까지 읽고 쉼표로 분리해 센서 값 목록을 만든 뒤 센서별 조건과 플래그를 확인하여 MP3 음원 재생 함수를 호출하고 소리를 출력하는 순서도](/images/notion/tech-08-05/image-4.png)


그림 4. GoldenGlove.aia의 play.scm과 play.bky를 바탕으로 구성한 수신 메시지 파싱과 플래그 기반 음원 재생 호출 경로.


다만 코드에 적힌 숫자 조건만으로는 장갑을 실제로 꼈을 때 손가락을 안쪽으로 굽힐 때와 펼 때 중 어느 쪽에서 소리가 나는지 직관적으로 알기 어렵다. 실제 착용 상태에서 손가락 움직임과 소리 재생 시점이 어떻게 맞물리는지는 따로 동작을 확인해야 한다.


## 송수신 주기와 양손 동기화 한계


장갑의 송신 코드와 앱의 수신 블록을 나란히 놓고 보면 데이터 전송 주기와 시각 비교에서 몇 가지 한계가 드러난다. 수신 앱의 타이머 주기는 10ms로 설정되어 있는 반면, 장갑 스케치의 송신 대기 시간은 100ms다. 앱에서 10ms마다 수신 버퍼를 자주 확인하더라도 장갑이 100ms보다 긴 주기로 값을 보내므로 새 센서 값이 더 빨리 도착하지는 않는다. 또한 메시지에 측정 시각이나 송신 순번이 없기 때문에, 양손으로 동시에 연주할 때 왼손과 오른손 입력이 시간상으로 얼마나 어긋나는지는 현재 코드만으로는 알 수 없다.


## 결론


지금까지 `NAMUORI00/GoldenGlove`의 소스 코드를 따라가며 다섯 손가락의 센서 입력이 모바일 앱의 음원 재생으로 이어지는 전체 경로를 확인했다. 장갑 스케치는 `analogRead`로 읽은 원시 값을 시작 기준값 기반의 `map` 함수로 0~3 정수로 바꾸고, 쉼표와 `/` 구분자를 붙여 블루투스로 보낸다. 수신 앱은 양손 연결을 따로 열어 `ReceiveText(-1)`로 메시지를 끊어 읽은 뒤, 센서 조건과 플래그를 함께 확인해 한 번의 동작에 음원을 한 번만 재생한다.


코드에 구현된 변환 식과 통신 규격은 확인했지만, 실제 착용 상태에서 소리가 나는 굽힘 방향이나 양손 입력의 시간차, 실제 연주 지연 시간은 코드만으로 알 수 없었다. 실제 연주에서 의도하지 않은 음이 나거나 반응이 늦어진다면 초기 `setup` 기준값 문제인지, 블루투스 통신 지연인지, 앱의 재생 처리 지연인지 나누어 봐야 한다. 다음 확인에서는 센서 원시 값과 송신 순번, 앱의 메시지 수신 시각, 음원 재생 호출 시각을 한 흐름으로 묶어 기록하는 로그부터 마련할 계획이다.
