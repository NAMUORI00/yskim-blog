ETF 추적 도구에서는 시점별 데이터를 계산 결과와 화면 표시에 연결했다. 수집 시각과 데이터 기준 시각, 값의 부재와 0을 구분해야 같은 숫자를 일관되게 해석할 수 있어 입력 계약부터 정리했다.


## 구현과 확인 과정


etf-track의 데이터 입력과 괴리율 계산 경로를 읽어 봤다. EOD 종가, NAV와 장중 시장가, iNAV는 기준 시각이 달라, 각 값이 들어오는 시점과 계산에 적용되는 시간 조건을 함께 정리했다.


595bdde 커밋 기준으로 EOD 릴리스, 장중 스냅샷, 괴리율 계산 경로를 읽었다. 시계열은 시점과 값을 함께 다루며 null은 값의 부재를 나타낸다는 구분을 바탕으로 코드를 따라갔다. 여기서 다루는 범위는 데이터의 비교 조건이며, 특정 상품의 투자 판단과는 관계없다.


## 시장가격과 기준 가치를 나누어 두기


ETF 시장가격은 거래소에서 거래되는 가격이고 NAV는 펀드의 순자산가치를 기준으로 한 주당 값이다. 두 값은 같지 않을 수 있으며, 시장가격이 NAV보다 높거나 낮은 상태를 프리미엄, 디스카운트로 설명한다.


[SEC의 ETF 안내](https://www.investor.gov/introduction-investing/general-resources/news-alerts/alerts-bulletins/investor-bulletins-24)에서도 이 차이를 구분한다.


이 저장소는 하루가 끝난 뒤의 EOD 종가, NAV와 장중 시장가, iNAV를 다른 입력으로 받는다. iNAV는 장중 추정 순자산가치로, [한국거래소 공시의 설명](https://kind.krx.co.kr/external/2026/01/29/000057/20260129000082/68648.htm)에서도 시장가격과 비교하는 기준으로 쓰인다. EOD와 장중 입력이 나뉘어 있어서, 전일 NAV와 현재 시장가가 의도 없이 한 계산에 섞이는 경우가 줄어든다.


[ETF 비교 지표 계산](https://github.com/NAMUORI00/etf-track/blob/595bddec4929a6a3376d75c6cc5105b1af7a3626/app/lib/etf-data.ts)의 기본 괴리율 계산은 다음과 같다.


```plain text
괴리율(%) = (시장가격 / 기준 가치 - 1) × 100
```


설명용으로 시장가격이 10,100원이고 같은 기준의 가치가 10,000원이면 1%다. 기준 가치가 없거나 0 이하이면 함수는 null을 반환한다. 화면의 formatPercent는 null을 대시로 표시한다. 값이 없는데 0%를 보여 주면 차이가 없는 것처럼 읽히므로, 계산 불가 상태는 null 그대로 남겨서 대시로 표시하는 구조였다.


## 데이터 기준일과 발행 시각


[장 마감 자료 읽기](https://github.com/NAMUORI00/etf-track/blob/595bddec4929a6a3376d75c6cc5105b1af7a3626/app/lib/eod-release.ts)는 최신 배포 정보에서 릴리스 정보를 얻고 해당 배포의 자료 목록을 읽는다.


asOf는 값의 기준일이고 publishedAt은 발행 시각이다. 같은 기준일의 데이터를 다음 날 정정해 발행할 수도 있으므로 두 필드를 하나로 합치지 않는다.


카탈로그는 릴리스 ID와 기준일이 manifest와 맞는지, 항목 수가 같은지, ETF 코드가 중복되지 않는지 검사한다. 현재 릴리스를 가리키는 latest는 새로 확인하고, 버전이 들어간 카탈로그는 캐시할 수 있도록 나누어 요청한다.


[릴리스 생성 코드](https://github.com/NAMUORI00/etf-track/blob/595bddec4929a6a3376d75c6cc5105b1af7a3626/scripts/build-eod-release.mjs)는 기준일과 입력 파일의 해시 일부로 releaseId를 만든다.


같은 날짜라도 입력 내용이 달라지면 다른 경로로 구분된다. 다만 이 해시는 원시 입력 문자열에 대한 값이므로, 공백처럼 의미를 바꾸지 않는 수정도 ID를 바꿀 수 있다.

## 수치 옆의 시각을 계산 조건으로 사용하기


[장중 관측값 검사](https://github.com/NAMUORI00/etf-track/blob/595bddec4929a6a3376d75c6cc5105b1af7a3626/app/lib/market-snapshot.ts)는 시장가와 lastPriceAt, iNAV와 inavAt이 각각 함께 있거나 함께 비어 있는지 검사한다. 전체 스냅샷의 관측, 발행, 만료 순서와 표시 허용 상태도 확인한다.


장중 괴리율을 계산하는 함수는 두 시각의 차이가 maxPriceInavSkewSeconds를 넘으면 null을 반환한다. 허용 차이를 60초로 둔 설명용 예에서는 시장가가 10시 00분 30초, iNAV가 10시라면 계산을 진행할 수 있다. iNAV가 9시 58분이라면 150초 차이여서 계산하지 않는다. 숫자가 둘 다 있다는 조건에 시간 조건이 추가된 것이다.


이 검사는 두 값의 동시성을 다룬다. 두 값이 똑같이 오래된 시각이어도 서로의 차이는 작을 수 있다. 따라서 스냅샷의 만료 확인과 시각 차이 확인이 모두 필요하다. 한 검사가 다른 검사를 대신하지는 않는다.


![12-01-02.png](/images/notion/tech-12-01/image-2.png)


그림 2. 입력 형식, 만료, 동시성을 별도로 검사하는 흐름. 출처: 장중 로더와 계산 함수를 바탕으로 직접 구성. 조회 이후 시간이 흐를 때의 재검사는 별도 과제로 남는다.


## 조회 이후의 갱신과 만료


로더는 응답을 받았을 때 expiresAt과 현재 시각을 비교한다. 그런데 [화면 코드](https://github.com/NAMUORI00/etf-track/blob/595bddec4929a6a3376d75c6cc5105b1af7a3626/app/page.tsx)의 장중 조회는 처음 열거나 다시 확인할 때 실행되고, 유효 상태를 시간 경과에 맞춰 바꾸는 타이머는 확인하지 못했다.


처음에 유효했던 스냅샷을 화면에 오래 남겨 두면, 조회 시점에는 통과했던 만료 조건이 표시 중에 어긋날 수 있다. 만료 시점에 표시를 끄거나 새 응답을 받는 동작은 "조회할 때 만료를 검사한다"와는 별개 요구사항이다. 오래 열어 둔 화면에서 실제로 재현한 결과는 아직 없고, 호출 경로를 읽으며 남긴 질문이다.


## 미계산 항목의 표시 기준


[데이터 계약](https://github.com/NAMUORI00/etf-track/blob/595bddec4929a6a3376d75c6cc5105b1af7a3626/docs/eod-data-contract.md)은 ETF와 기초지수의 1년 수익률을 단순히 빼서 추적오차라고 표시하지 않도록 구분한다.


기간, 통화, 산식이 맞는지 확인이 필요하고, 추적오차 계산에는 별도의 수익률 시계열이 들어간다. 화면은 제공받은 값을 구분해서 보여 주는 범위까지만 담당하는 것으로 읽었다.


정식 릴리스가 없을 때는 빈 목록과 상태를 보여 주고, 데모 데이터는 명시적인 환경 설정에서만 사용된다. 빈 화면을 피하려고 예시 가격을 실제 값처럼 섞는 일이 생기지 않도록 분리한 구조다.


입력 계약과 표시 경로를 코드에서 확인했다. 다음 글에서는 여러 금융 자료를 하나의 조건으로 필터링할 때 식별자와 날짜가 어떻게 연결되는지 이어서 살펴볼 예정이다.


## 작업을 정리하며


금융 데이터를 화면에 보여 줄 때는 계산값 옆에 기준 시각과 결측 상태도 함께 남기고 싶다. 숫자를 채우는 것보다 어떤 자료에서 계산됐는지 되짚을 수 있는 구성이 유지보수에 도움이 된다. 공급자 연결과 계산 검증도 그 기준으로 각각 확인하려 한다.
