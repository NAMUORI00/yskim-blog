금융 필터에서는 수집 응답을 정규화하고 조건에 맞는 항목을 화면에 표시하는 흐름을 구성했다. 외부 데이터 조회와 화면용 모의 값 생성이 함께 있어, 각 결과의 출처를 구분하는 문제를 중심으로 정리했다.


## 구현과 확인 과정


Fintel_Finviz_SEC_Filter 프로젝트의 코드를 읽으며 FINVIZ CSV를 가져와 Next.js 화면에 연결하는 경로를 확인했다. 화면에 주식 목록과 차트가 표시되더라도 실제 외부 응답인지 예시 데이터인지에 따라 그 값의 의미가 달라지므로, 수집 응답이 어느 단계에서 화면용 값으로 바뀌는지를 중심으로 살펴봤다.


기준은 7d843c3 커밋이다. 필터는 조건에 맞는 행을 남기는 작업이고, CSV 파싱은 문자열의 열을 이름 있는 필드로 바꾸는 작업이라는 정도에서 출발했다. 확인한 앱 경로에 Fintel, SEC 자료를 결합하는 구현은 없었고, 이 글은 FINVIZ 단일 출처의 수집, 변환, 표시 경로만 다룬다.


## 조건을 공급자 요청으로 바꾸는 부분


[스크리너 API](https://github.com/NAMUORI00/Fintel_Finviz_SEC_Filter/blob/7d843c329602dbc15d8f8337dce8a8306a7d84b7/finviz-stock-viewer/src/app/api/stocks/screener/route.ts)는 최소, 최대 가격, 거래량, 시가총액 구간과 업종 등을 공급자 필터 문자열로 바꾼다.


CSV 응답을 받은 뒤에는 내부 객체로 변환하고 일부 조건을 다시 적용한다. 마지막에는 결과 개수를 제한해 화면에 전달한다.


이 구조는 외부 데이터 형식이 화면 코드에 직접 퍼지지 않도록 가운데 변환 경계를 두는 방식이었다. [FINVIZ 스크리너 설명](https://finviz.com/help/screener)은 필터를 조건에 맞는 종목을 찾는 기능으로 정의하고, 평균 거래량과 당일 거래량을 별도 항목으로 다룬다. 조건 이름이 비슷해도 실제로 같은 뜻으로 전달되는지는 별도 확인이 필요한 부분이다.


현재 코드에서 minVolume은 외부 요청의 평균 거래량 조건에 들어가고, 내부 재필터에서는 stock.volume과 비교된다. 하나의 입력이 서로 다른 기간의 값에 두 번 적용되는 셈이다. 화면에서 "거래량"이라고만 표시하면 어느 조건이 적용된 결과인지 구분하기 어렵고, 공급자 값의 단위와 평균 기간에 따라 요청 조건과 후처리 조건이 다른 행을 걸러낼 수 있는 상태다.

그림 1. 필터 입력이 외부 조회와 내부 필터를 거쳐 화면으로 돌아오는 경로. 출처: 종목 검색 요청 처리와 표 형식 응답 해석을 바탕으로 직접 구성. 두 필터가 같은 의미를 갖는지는 별도 대조가 필요하다.


## CSV 파싱과 자료형 처리


[표 형식 응답 해석](https://github.com/NAMUORI00/Fintel_Finviz_SEC_Filter/blob/7d843c329602dbc15d8f8337dce8a8306a7d84b7/finviz-stock-viewer/src/lib/csv-parser.ts)은 첫 줄을 헤더로 읽고 행의 필드 개수가 다르면 해당 행을 건너뛴다.


따옴표 안의 쉼표를 분리하지 않는 처리도 있다. 다만 텍스트를 먼저 줄 단위로 나누기 때문에 따옴표 안에 줄바꿈이 들어가는 CSV는 정상 처리되지 않는다. [RFC 4180](https://www.rfc-editor.org/rfc/rfc4180)은 이런 인용 필드 안의 줄바꿈도 허용하는 형식을 정의하고 있다.


수치 변환에서도 결측과 실제 값이 섞이는 지점이 있었다. 비어 있거나 N/A인 숫자는 0으로 바뀌고, 가격은 최소 0.01로 보정된다. 평균 거래량이 없으면 현재 거래량 주변의 임의 값이 생성된다. 이 변환을 거치면 원본에 값이 없었다는 정보는 사라진다.


설명용으로 Price=N/A, Volume=100이라는 행을 넣었다고 해 보자. 현재 규칙에서는 가격이 0.01로, 평균 거래량은 무작위 보정값으로 바뀔 수 있다. 결과 객체만으로는 원본 가격 0.01과 결측을 보정한 0.01을 구분할 수 없다. 데이터 준비 여부를 화면 쪽에서 판단하려면 null이나 값의 출처를 나타내는 필드가 결과 객체에 포함되어야 한다.


코드의 parseChange는 현재 가격에 변화율을 곱한다. 설명용으로 변화율을 전일 대비 비율이라고 놓으면, 현재가 110에 변화율 10%인 전일 가격은 100이고 증감액은 10이다. 현재 구현식의 결과는 11이 된다. 공급자 필드의 기준을 확인한 뒤 전일 가격을 역산할지, 공급자가 제공하는 증감액을 사용할지 비교할 부분으로 남았다.


## 오류 시 예시 데이터 표시


[FinvizClient](https://github.com/NAMUORI00/Fintel_Finviz_SEC_Filter/blob/7d843c329602dbc15d8f8337dce8a8306a7d84b7/finviz-stock-viewer/src/lib/finviz-client.ts)는 단일 조회에서 404면 null을 반환하지만, 다른 예외는 generateMockData로 처리한다.


스크리너도 오류가 나면 임의 종목 데이터를 반환한다. 반환 타입에는 실제 응답인지 모의 데이터인지를 구분하는 출처 필드가 없다.


화면 개발 중에 빈 카드 대신 예시를 채우는 용도로는 편리한 구조다. 다만 이 대체 경로가 운영 요청에도 그대로 적용되면 API 실패가 그럴듯한 숫자 뒤에 가려진다. 화면이 정상처럼 보이는 것과 표시된 데이터가 신뢰할 수 있는 것은 다른 상태다.

## 갱신 시각과 가격의 기준 시각을 나누기


파서의 lastUpdate는 변환 시점에 새로 만든 시각이다. [주기적인 화면 데이터 갱신](https://github.com/NAMUORI00/Fintel_Finviz_SEC_Filter/blob/7d843c329602dbc15d8f8337dce8a8306a7d84b7/finviz-stock-viewer/src/hooks/useRealTime.ts)도 기본 30초마다 조회하고 값을 받으면 현재 시각을 기록한다.


이 두 시각은 수집, 변환 단계에서 만든 값이어서 공급자가 가격을 관측한 시각을 나타내지는 않는다. 모의 값을 반환받아도 갱신 시각은 최신으로 기록된다.


[가격 차트 표시](https://github.com/NAMUORI00/Fintel_Finviz_SEC_Filter/blob/7d843c329602dbc15d8f8337dce8a8306a7d84b7/finviz-stock-viewer/src/components/PriceChart.tsx)는 현재 가격을 바탕으로 무작위 과거 곡선을 만든다.


차트 컴포넌트가 연결되어 있다는 것과 과거 시세 데이터를 실제로 수집했다는 것은 다른 이야기다. 이 곡선은 무작위로 생성된 값이므로 실제 가격 이력이나 성능 검증의 근거로 쓸 수 없다.


## 후속 연동의 데이터 계약


확인한 구현은 FINVIZ 요청, CSV 변환, 필터, 시각화의 연결까지다. 실제 계정 조회나 금융 결과 검증은 수행하지 않았다. 원본 값, 결측, 모의 값, 관측 시각, 수집 시각을 반환 타입에서 구분하는 부분은 후속 검토 항목으로 정리했다.


Fintel이나 SEC 자료를 추가하는 경우에는 출처별 식별자와 기준 기간을 연결할 작업이 더해진다. 같은 종목 기호라도 날짜가 다르면 비교 대상이 달라질 수 있으므로 출처와 기준일이 연결 조건이 된다. 다음 글에서는 경매 자료의 식별자와 원문으로 돌아가는 경로를 살펴본다.


## 작업을 정리하며


같은 화면에 표시되더라도 실제 조회값과 모의 값은 출처가 다르다. 이 구분을 데이터와 상태 표시 양쪽에 남기면 화면을 완성하는 동안에도 확인한 범위를 추적할 수 있다. 이후에는 공급자 실패와 빈 결과도 각각의 상태로 다루려 한다.
