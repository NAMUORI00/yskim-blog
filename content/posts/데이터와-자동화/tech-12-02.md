화면에 주식 목록과 가격 차트가 정상적으로 나타난다고 해서 그 숫자가 모두 실제 외부에서 받아 온 값은 아니다. 비어 있는 값을 임의의 기본값으로 채우거나 조회 실패를 임시로 만든 값으로 덮으면, 화면은 멀쩡해 보여도 숫자를 그대로 믿기 어렵다. 주식 정보 사이트 FINVIZ는 표 데이터를 쉼표로 구분해 글자로 적은 **CSV** 형식으로 응답을 내려준다. `Fintel_Finviz_SEC_Filter` 저장소(`7d843c3` 커밋) 코드를 읽으며 이 응답이 화면용 값으로 바뀌고 생성된 값과 섞이는 지점을 추적했다.


저장소 이름에는 다른 금융 정보 출처인 Fintel과 SEC도 적혀 있지만, 확인한 코드 경로에는 두 자료를 합치는 기능이 없었다. 이 글에서는 FINVIZ 한 곳에서 데이터를 가져와 프로그램 내부 데이터로 바꾸고, 조건에 맞는 종목을 걸러 Next.js 화면에 보여 주는 과정만 다룬다.


## 검색 조건 변환과 거래량 재검사


데이터 수집의 첫 단계는 사용자가 화면에서 고른 검색 조건을 외부 사이트 요청으로 바꾸고 응답을 걸러 내는 일이다. 외부 데이터 형식이 화면 코드에 직접 퍼지지 않도록 중간에서 데이터를 주고받는 창구인 **API**가 변환 경계를 맡는다. 조건에 맞는 종목을 골라내는 [스크리너 API](https://github.com/NAMUORI00/Fintel_Finviz_SEC_Filter/blob/7d843c329602dbc15d8f8337dce8a8306a7d84b7/finviz-stock-viewer/src/app/api/stocks/screener/route.ts)는 최소와 최대 가격, 거래량, 시가총액 구간, 업종 조건을 FINVIZ용 필터 문자열로 바꿔 요청한다. 그 뒤 돌아온 CSV 응답을 프로그램 내부 데이터로 바꾸고, 일부 조건을 다시 검사해 결과 개수를 제한한 다음 화면으로 넘긴다.


![필터 선택부터 Next.js API, 공급자 필터 문자열, FINVIZ CSV 응답, 열 해석과 형 변환, 내부 재필터와 개수 제한을 거쳐 종목 목록으로 이어지는 흐름도](/images/notion/tech-12-02/image-1.png)


그림 1. 필터 입력이 외부 조회와 내부 재필터를 거쳐 화면 종목 목록으로 전달되는 흐름과 거래량 조건이 두 번 적용되는 구간.


이 과정에서 최소 거래량 입력값인 `minVolume`은 외부 요청과 내부 재검사에 서로 다른 기준으로 들어간다. [FINVIZ 스크리너 설명](https://finviz.com/help/screener)을 보면 종목을 걸러 낼 때 일정 기간의 평균 거래량과 당일 거래량을 별도 항목으로 구분한다. 그런데 코드는 외부 요청을 보낼 때 `minVolume`을 평균 거래량 조건에 넣고, 응답을 받은 뒤에는 당일 거래량인 `stock.volume`과 다시 비교한다.


같은 입력값 하나가 기준 기간이 다른 두 거래량 항목에 연달아 쓰이기 때문에, 화면에 "거래량"이라고만 적혀 있으면 사용자는 어느 기준인지 알기 어렵다. 또한 FINVIZ가 내려주는 값의 단위와 평균을 계산한 기간에 따라, 외부 요청을 통과한 종목이 내부 재검사에서 다시 탈락할 수도 있다.


## CSV 해석과 결측값 보정


외부 요청으로 받아 온 CSV 문자열은 글자를 읽어 프로그램 데이터로 바꾸는 **파서**(parser)인 [표 형식 응답 해석](https://github.com/NAMUORI00/Fintel_Finviz_SEC_Filter/blob/7d843c329602dbc15d8f8337dce8a8306a7d84b7/finviz-stock-viewer/src/lib/csv-parser.ts) 모듈로 넘어간다. 이 모듈은 첫 줄을 제목 줄(헤더)로 읽어 열 이름을 잡고, 다음 줄부터 칸 개수가 제목 줄과 다르면 그 줄을 건너뛴다. 큰따옴표 안에 들어 있는 쉼표를 열 구분자로 잘못 자르지 않는 처리도 들어 있다. 다만 전체 글자를 줄바꿈 문자 기준으로 먼저 나눈 뒤 한 줄씩 읽어서, 따옴표 안에 줄바꿈이 들어간 칸은 제대로 처리하지 못한다. CSV 표준 문서인 [RFC 4180](https://www.rfc-editor.org/rfc/rfc4180)은 따옴표로 감싼 칸 안의 줄바꿈을 허용하므로, 줄바꿈이 섞인 글자 칸이 들어오면 행이 깨질 수 있다.


글자를 숫자로 바꾸는 단계에서는 원래 비어 있던 값인 **결측값**을 기본값으로 채우고 가격 변화량을 계산한다. 비어 있거나 `N/A`로 적힌 숫자 칸은 `0`으로 바꾸는데, 가격은 최소 `0.01`로 맞추고 평균 거래량이 없으면 현재 거래량 주변의 무작위 값을 넣는다. 예를 들어 `Price=N/A`, `Volume=100`이고 평균 거래량이 빈 행은 파서를 거치면서 가격이 `0.01`로, 평균 거래량이 `100` 주변의 임의 숫자로 바뀐다. 또한 전일 대비 가격 변화량을 구하는 `parseChange` 함수는 현재가 `110`과 변화율 `10%`를 바로 곱해 증감액을 `11`로 계산한다.


![원본 CSV의 Price=N/A, 평균 거래량 결측, 현재가 110과 변화율 10%가 파서 수치 보정을 거쳐 가격 0.01, 임의 거래량, 증감액 11로 바뀌는 비교도](/images/notion/tech-12-02/image-2.png)


그림 2. CSV 파서의 수치 변환 과정에서 결측값 보정과 변화율 계산이 적용되어 원본 데이터의 결측 여부가 사라지는 예.


이렇게 파서가 결측값을 숫자로 채워 버리면 원본 데이터에 값이 비어 있었다는 사실이 사라진다. 변환된 결과만 받는 화면 코드로서는 원래 가격이 `0.01`인 종목인지 결측값이 보정된 결과인지 구분할 방법이 없다. 화면에서 데이터가 준비되었는지 판단해 빈칸이나 안내 문구를 보여 주려면, 결과에 빈값을 뜻하는 `null`을 허용하거나 값의 출처를 표시하는 칸을 따로 두어야 한다.


현재 가격에 변화율을 바로 곱하는 `parseChange` 함수의 계산 방식도 실제 등락 금액과 어긋날 수 있다. FINVIZ가 내려주는 변화율이 전일 대비 등락률이라면, 어제 가격 100에서 10%가 올라 오늘 가격이 `110`이 되었을 때 실제 오른 금액은 10이다. 하지만 현재 코드처럼 오늘 가격 `110`에 `10%`를 곱하면 결과가 `11`이 되어 원래 차이보다 커진다. 제공처의 항목 정의를 확인한 뒤 어제 가격을 거꾸로 계산해 차이를 구할지, 제공처가 직접 내려주는 증감액 항목을 쓸지 맞춰 보아야 한다.


## 조회 오류와 모의 데이터 대체


CSV 해석 단계뿐 아니라 외부 요청 자체가 실패할 때도 화면을 시험하려고 임시로 만든 가짜 값인 **모의 데이터**가 실제 응답 자리에 들어간다. 개별 종목이나 스크리너 목록을 가져오는 [FinvizClient](https://github.com/NAMUORI00/Fintel_Finviz_SEC_Filter/blob/7d843c329602dbc15d8f8337dce8a8306a7d84b7/finviz-stock-viewer/src/lib/finviz-client.ts)는 단일 종목을 조회할 때 대상이 없다는 뜻인 `404` 응답을 받으면 `null`을 돌려준다. 하지만 그 밖의 오류가 나면 `generateMockData` 함수를 호출해 가짜 종목 값을 만들고, 스크리너 조회에서 오류가 날 때도 임의로 만든 종목 목록을 반환한다. 이때 반환하는 데이터 형식에는 실제 외부 응답인지 내부에서 만든 모의 데이터인지 구분하는 출처 항목이 없다.


![클라이언트 조회 후 응답 결과에 따라 정상일 때의 API 반환 데이터와 그 밖의 오류일 때의 모의 값 생성이 같은 데이터 타입으로 합쳐져 가격 카드와 차트로 전달되는 분기 흐름도](/images/notion/tech-12-02/image-3.png)


그림 3. 조회 오류 발생 시 생성된 모의 값이 정상 응답과 동일한 데이터 타입으로 합쳐져 화면으로 전달되는 경로.


화면 배치를 개발할 때는 외부 연결이 실패해도 빈 화면 대신 예시 숫자가 채워지므로 모양을 확인하기 편하다. 그러나 이 대체 경로가 실제 조회 환경에 그대로 남아 있으면, 네트워크 오류가 나거나 외부 사이트에서 요청을 차단해도 그럴듯한 숫자 뒤에 실패 사실이 가려진다. 화면이 오류 없이 그려지는 것과 화면에 적힌 숫자를 믿을 수 있는 것은 서로 다른 문제다.


## 갱신 시각 기록과 무작위 차트 곡선


정상 응답을 받아 화면에 종목 정보를 그릴 때도 외부에서 가져온 현재 가격과 프로그램 내부에서 만든 시각, 차트 곡선이 한 화면에 함께 표시된다. 파서가 결과 데이터에 넣는 `lastUpdate` 항목은 CSV 문자열을 변환하는 시점의 현재 시각이다. [주기적인 화면 데이터 갱신](https://github.com/NAMUORI00/Fintel_Finviz_SEC_Filter/blob/7d843c329602dbc15d8f8337dce8a8306a7d84b7/finviz-stock-viewer/src/hooks/useRealTime.ts) 코드도 기본 30초 간격으로 API를 호출한 뒤, 응답을 받은 시각을 최신 갱신 시각으로 기록한다. 여기에 [가격 차트 표시](https://github.com/NAMUORI00/Fintel_Finviz_SEC_Filter/blob/7d843c329602dbc15d8f8337dce8a8306a7d84b7/finviz-stock-viewer/src/components/PriceChart.tsx) 화면 코드는 과거 시세를 따로 조회하지 않고, 전달받은 현재 가격 하나에 무작위 변동 폭을 더해 과거 곡선을 그린다.


![FINVIZ 응답에서 온 현재 가격과 내부에서 생성한 파서 변환 시각, 30초 주기 조회 시각, 현재가 기반 무작위 곡선이 화면 표시 요소로 연결되는 구조도](/images/notion/tech-12-02/image-4.png)


그림 4. 외부 응답에서 가져온 현재 가격과 애플리케이션 내부에서 만든 갱신 시각 및 무작위 차트 곡선이 화면에 함께 표시되는 구조.


화면의 두 시각 모두 데이터를 가져오거나 변환한 시점을 적을 뿐, FINVIZ가 실제 시장에서 그 가격을 관측한 기준 시각을 뜻하지는 않는다. 심지어 API 오류가 발생해 모의 데이터를 받아 온 경우에도 화면의 갱신 시각은 방금 조회한 최신 시각으로 바뀐다. 차트 역시 시간 순서대로 기록된 과거 가격인 시계열 데이터를 수집해 보여 주는 것과 화면 코드가 연결되어 돌아가는 것은 다르다. 이 곡선은 화면 구성을 확인하기 위해 현재 가격에서 만든 임의 값이므로 실제 가격 이력이나 분석 근거로 쓸 수 없다.


## 결론


이번에 코드를 따라가며 확인한 범위는 FINVIZ 요청 생성과 CSV 해석, 조건 재검사, 화면 표시 코드까지의 연결 경로다. 실제 외부 계정을 연동한 데이터 조회나 금융 수치의 정확성 검증은 진행하지 않았다. 화면을 개발하는 과정에서도 어디까지가 실제 데이터인지 구분하려면 원본 값과 결측값, 모의 데이터의 출처를 반환 형식에서 분리해야 한다. 또한 실제 시장의 가격 관측 시각과 프로그램의 수집 시각을 나누어 기록하고, API 호출 실패나 빈 결과도 별도 상태로 다루어야 화면의 숫자를 신뢰할 수 있다.


앞으로 저장소 이름에 적힌 대로 Fintel이나 SEC 자료까지 합치려면 출처마다 종목을 구분하는 이름(식별자)과 기준 기간을 맞추는 작업이 필요하다. 같은 종목 기호(Ticker)를 쓰더라도 자료마다 기준 날짜가 다르면 서로 다른 시점의 수치를 비교하게 되므로, 데이터 출처와 기준일을 먼저 맞추어야 한다. 다음 글에서는 경매 자료를 조회할 때 물건 식별자를 관리하고 원문 데이터로 돌아가는 경로를 다룬다.
