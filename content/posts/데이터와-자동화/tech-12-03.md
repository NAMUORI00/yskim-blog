원격 서버에서 관심물건 목록을 가져오는 데스크톱 앱에서는 로그인 상태가 만료되거나 응답 형식이 바뀌어 새 조회가 실패할 때가 있다. 이때 빈 화면 대신 마지막으로 성공한 조회 결과를 저장해 둔 **스냅샷**(snapshot)을 보여 주면 이전 목록을 계속 참고할 수 있다. 다만 화면의 목록이 방금 서버에서 가져온 결과인지 예전에 저장해 둔 기록인지 구분하지 않으면, 사용자가 오래된 상태를 현재 정보로 오해하기 쉽다.


경매 관심물건을 관리하는 Electron 앱인 `dooin_auction`(`46ea78a` 커밋)은 새 조회가 실패하면 마지막 스냅샷을 대신 보여 준다. 이때 그 목록이 현재 조회 결과인지 저장본인지 화면에 함께 표시한다. 앞 글에서 다룬 모의 데이터 화면과 비교하며, 실제 서버 응답을 연결할 때 물건의 고유 번호와 저장 시점이 어떻게 남는지 코드 흐름을 따라가며 확인했다. 경매 물건 자체의 가치를 판단하는 기능보다는, 원본 응답 항목을 앱이 쓰는 이름과 형식으로 맞추는 과정과 조회 상태를 분리하는 방법에 초점을 맞췄다.


## 관심물건 조회 경로


실제 서버 응답이 화면까지 어떻게 전달되는지 확인하기 위해 관심물건 조회 기능이 호출되는 경로와 구현 범위를 먼저 살폈다. 저장소의 `README`에는 초기 샘플 화면 설명과 함께, 서버 응답에서 필요한 값을 골라내는 코드인 **파서**(parser)가 추가됐다는 설명이 남아 있었다. 문서만으로는 연결 범위를 알기 어려워 [화면과 데이터 연결](https://github.com/NAMUORI00/dooin_auction/blob/46ea78a0203a197e81e2edd07d99e914e17c7bf3/src/store/appStoreController.ts) 코드부터 데스크톱 어댑터와 Electron 메인 프로세스까지 호출 경로를 따라갔다.


관심물건 새로고침 기능은 서비스와 유스케이스 계층을 거쳐 Electron 메인 프로세스의 `fetchAuthenticatedWatchlist`를 호출한다. 로그인 인증 상태가 바뀔 때도 상태를 갱신하며, 인증이 확인되면 서버에 새 목록을 요청하도록 연결되어 있다. 반면 이 조회 경로와 별개로 다른 대시보드나 알림, 이력 화면에는 초기 샘플 표시가 그대로 남아 있었다. 앱 전체가 완성된 자동 추적기라기보다는, 로그인을 거친 관심물건 조회와 저장본 표시가 먼저 연결된 상태였다. 이번 확인에서는 코드의 상태 흐름만 읽었으며, 실제 계정으로 로그인하거나 새로운 경매 자료를 조회하지는 않았다.


## 식별자 정규화


조회 경로를 통해 원격 서버에서 받아 온 관심물건 응답은 먼저 각 물건을 구별하는 값과 화면 표시용 문자열로 나뉜다. 주소 문자열이 같아 보이더라도 실제로 같은 물건이라는 보장이 없기 때문에, 목록을 시점별로 비교하거나 원문과 연결하려면 화면에 보이는 제목만으로는 부족하다. [로그인 후 관심물건 해석](https://github.com/NAMUORI00/dooin_auction/blob/46ea78a0203a197e81e2edd07d99e914e17c7bf3/electron/authenticatedWatchlist.ts)을 맡은 파서는 원본 응답의 `tid`를 `listingId`로, `interestIdx`를 `interestId`로 바꾼다. 대상을 구별하는 고유 번호인 **식별자**를 물건 자체(`listingId`)와 관심목록 항목(`interestId`)으로 나누어 표시 문자열과 분리해 둔다. 서로 다른 원본 필드를 앱이 쓰는 이름과 형식으로 맞추는 **정규화**(normalization)를 거치면 시점이 달라도 같은 물건을 찾을 수 있다.


화면 표시용 문자열을 정리할 때는 주소와 분류를 조합해 제목을 만들고, 메모와 특이사항에 들어 있는 HTML 태그 표현을 걷어 낸다. 상대 경로인 이미지 주소는 기준 도메인에 맞춰 전체 주소(절대 주소)로 바꾸고, 물건 식별자인 `listingId`로 상세 원문 링크도 만든다. 가공된 제목만 남기는 방식과 달리 원문 페이지로 돌아갈 경로가 그대로 유지된다.


반면 감정가나 최저입찰가 같은 금액은 이 파서에서 숫자 단위로 환산하지 않고 표시 문자열 그대로 남긴다. 금액을 화면에 보여 주는 단계와 수치 비교나 계산에 사용하는 단계는 역할이 다르기 때문이다. 앱 내부에 이 금액 문자열을 그대로 더하거나 비율을 계산하는 처리가 있는지는 확인하지 않았다.


![원본 관심물건 응답에서 tid와 interestIdx는 listingId와 interestId 식별자로 분리되고, 주소와 금액 문자열은 제목과 표시 형식으로 정리되어 정규화된 관심물건과 상세 원문 링크로 이어지는 흐름도](/images/notion/tech-12-03/image-1.png)

## 빈 목록과 파싱 실패의 구분


원본 응답을 정규화하기에 앞서, 파서는 서버에서 받은 데이터가 예상한 형식에 맞는지부터 확인한다. 이 입력 검사에는 데이터가 갖춰야 할 항목과 자료형 규칙인 **스키마**(schema)를 정의해 검증하는 도구인 Zod를 사용한다. [Zod의 catch 동작](https://zod.dev/api#catch)은 스키마 검증에 실패했을 때 오류를 내며 멈추는 대신 미리 지정한 대체 값을 반환한다. 이 파서는 `item` 배열 스키마에 `catch([])`를 붙여, 필드가 없거나 배열 검증이 실패하면 빈 배열(`[]`)을 돌려준다.


예를 들어 응답에 적힌 전체 물건 수는 3개인데 그중 한 항목의 필수 식별자 형식이 잘못된 경우가 있다. 배열 전체의 검증이 실패해 `catch([])`가 동작하면 형식이 정상인 나머지 두 항목도 결과 배열에 남지 않는다. 이때 화면에 "관심물건 0개"라고만 나오면 실제로 관심물건 목록이 비어 있는 것인지, 응답 형식을 읽지 못해 파싱에 실패한 것인지 구분할 수 없다.


이 문제를 피하려고 메인 프로세스와 화면은 응답의 전체 개수인 `totalCount`와 파싱된 배열 길이인 `itemCount`를 따로 전달해 함께 표시한다. 두 숫자를 대조하면 응답을 읽는 파싱 과정에서 일부 항목이 누락됐는지 바로 파악할 수 있다. 다만 현재 파서는 중복 제거 없이 응답 배열을 그대로 `map`으로 변환하므로, 같은 `tid`가 두 번 들어와도 합쳐지지 않는다.


![원본 응답의 totalCount가 3이지만 항목 2의 식별자 오류로 Zod의 catch가 빈 배열을 돌려줘 itemCount가 0이 되었을 때 두 개수를 대조해 파싱 누락을 감지하는 다이어그램](/images/notion/tech-12-03/image-2.png)

## 스냅샷 대체와 출처 표시


새 조회가 성공해 정상 응답을 파싱하면 앱은 다음번 조회가 실패할 때를 대비해 결과를 컴퓨터 내 파일로 남겨 둔다. [조회 결과 저장과 복원 처리](https://github.com/NAMUORI00/dooin_auction/blob/46ea78a0203a197e81e2edd07d99e914e17c7bf3/electron/main.ts) 코드는 조회 시각, 요청 URL과 최종 URL, 서버 응답 코드인 HTTP 상태, 총개수, 물건 항목을 로컬 파일에 기록한다.


다음번 조회에서 로그인 상태가 유효하지 않거나 응답 형식을 읽지 못해 실패하더라도 로컬에 저장본이 남아 있으면 이를 대신 불러온다. 이때 메인 프로세스는 데이터의 출처를 뜻하는 `dataSource`를 저장본이라는 의미의 `snapshot`으로 설정해 화면에 돌려준다. 방금 서버에서 받아 온 결과인 `live`나 저장본조차 없을 때의 `empty`와 구분된 상태다.


[화면 코드](https://github.com/NAMUORI00/dooin_auction/blob/46ea78a0203a197e81e2edd07d99e914e17c7bf3/src/App.tsx)는 전달받은 출처(`dataSource`)와 오류 메시지, 마지막 조회 시각을 화면에 함께 표시한다. 덕분에 원격 조회가 실패하더라도 지난 목록을 계속 참고할 수 있으면서, 오래된 기록이 방금 확인한 정보처럼 보이지 않는다.

## 한계


마지막 스냅샷으로 화면을 복원하고 출처를 표시하는 경로는 갖춰졌지만, 시간에 따른 물건의 변화를 추적하는 데에는 아직 한계가 있다. 현재 저장 함수는 정해진 스냅샷 경로의 단일 파일에 새 JSON 데이터를 그대로 덮어쓴다. 파일 하나를 덮어쓰면 직전 기록만 남으므로 과거 여러 시점의 목록이 보존되거나 물건별 변화가 자동으로 계산되지 않는다. 화면에는 이전과 이후를 비교하는 `before/after` 패널과 알림 UI가 준비돼 있었고, 실제 수집 결과를 연결한 차이 분석은 추가 구현 항목으로 남아 있었다.


나중에 시점별 비교 기능을 연결하더라도, 새로 조회한 목록에서 기존 물건이 보이지 않는 경우를 곧바로 삭제로 판정하기는 어렵다. 로그인 문제나 불완전한 서버 응답, 파싱 실패 때문에 목록에서 일시적으로 빠졌을 수도 있기 때문이다. 변화 추적을 붙인다면 조회가 완전한지 먼저 확인해 같은 `listingId`끼리 비교하고, 빠진 이유가 불명확한 항목은 확인 대기로 분류해야 한다.

## 결론


지금까지 `dooin_auction`(`46ea78a` 커밋)의 관심물건 조회 경로를 따라가며 원격 응답 정규화와 스냅샷 대체 구조를 확인했다. 스냅샷을 화면에 대신 보여 줄 때 가장 먼저 드러내야 할 정보는 언제 확보한 자료인지다. 저장 시각과 수집 상태(`live`, `snapshot`, `empty`)를 함께 보여 주면 조회가 실패했을 때도 사용자가 자료의 기준 시점을 판단할 수 있다. 전체 개수(`totalCount`)와 파싱된 개수(`itemCount`)를 대조하면 누락 여부도 가려낼 수 있다. 여기에 물건 식별자인 `listingId`를 남겨 두어야 이후 시점별 차이 분석을 붙일 수 있다.


이번에는 코드 흐름을 따라 인증된 관심물건 조회와 단일 파일 스냅샷 복원까지만 확인했다. 실제 로그인 조회 실행이나 금액 문자열의 수치 계산 여부는 확인하지 않았다. 여러 시점의 스냅샷을 비교해 `before/after` 패널과 알림에 연결하는 차이 분석 기능도 아직 추가 구현 과제로 남아 있다. 다음 글에서는 더 큰 규모의 수집 작업인 `Dataset_Crawl`에서 같은 원문을 반복해서 내려받지 않으려면 어떤 기록이 필요한지 다룬다.
