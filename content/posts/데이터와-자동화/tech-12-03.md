경매 관심물건 도구에서는 원격 조회 결과와 저장한 스냅샷을 연결했다. 현재 조회와 마지막 저장본을 화면에서 구분하고, 두 시점의 자료를 비교할 수 있는 형태를 중심으로 작업을 정리했다.


## 구현과 확인 과정


dooin_auction의 관심물건 조회 흐름을 살펴봤다. 새 조회가 실패했을 때 마지막 스냅샷을 대체로 표시하면서, 그것이 현재 결과인지 저장본인지 화면에 구분해 보여주는 구조였다. 앞 글의 모의 데이터와 비교하며 원문 식별자와 저장 시점이 어떻게 남는지 확인했다.


46ea78a 커밋의 관심물건 파서와 상태 흐름을 읽었다. 경매 물건의 가치 판단보다는 자료의 식별자, 출처, 조회 상태를 중심으로 봤다. 여기서 정규화는 서로 다른 원본 필드를 앱이 사용하는 이름과 형식으로 맞추는 작업이고, 스냅샷은 특정 시점에 확보한 상태를 저장한 것이다.


## 관심물건 조회의 호출 경로


README에는 초기 샘플 화면을 설명하는 부분과 실제 관심물건 파서가 추가됐다는 설명이 함께 남아 있었다. 둘 중 한 문장만으로는 현재 범위를 정하기 어려워서, [화면과 데이터 연결](https://github.com/NAMUORI00/dooin_auction/blob/46ea78a0203a197e81e2edd07d99e914e17c7bf3/src/store/appStoreController.ts)에서 데스크톱 어댑터와 메인 프로세스까지 호출 경로를 따라갔다.


관심물건 새로고침은 서비스와 유스케이스를 거쳐 Electron 메인 쪽 fetchAuthenticatedWatchlist를 호출한다. 인증 상태가 바뀌었을 때도 상태를 갱신하고, 인증된 경우 새 목록을 요청하도록 연결되어 있다. 이 경로와 별개로 다른 대시보드, 알림, 이력 화면에는 샘플 표시가 남아 있었다.


앱 전체가 완성된 자동 추적기라기보다, 인증된 관심물건 조회와 저장본 표시가 연결된 범위로 읽혔다. 실제 계정 로그인이나 새로운 경매 자료 조회를 이번에 실행하지는 않았다.


## 화면 제목 대신 물건 ID를 남기기


[로그인 후 관심물건 해석](https://github.com/NAMUORI00/dooin_auction/blob/46ea78a0203a197e81e2edd07d99e914e17c7bf3/electron/authenticatedWatchlist.ts)은 원본의 tid를 listingId로, interestIdx를 interestId로 바꾼다.


하나는 물건을, 다른 하나는 관심목록 항목을 가리키는 식별자로 분리되어 있다. 주소가 같아 보이더라도 같은 물건이라는 보장이 없으므로, 문자열 표시와 식별자가 별도 필드로 나뉘어 있는 구조다.


주소와 분류를 조합해 제목을 만들고, 메모, 특이사항의 HTML 표현을 정리한다. 이미지 주소는 기준 도메인에 맞춰 절대 주소로 바꾸고, 물건 ID로 상세 원문 링크도 만든다. 제목만 남기는 방식에 비해 원문으로 돌아갈 경로가 유지되는 구성이다.


금액은 이 파서에서 숫자 단위로 환산하지 않고 표시 문자열 그대로 남긴다. 감정가나 최저입찰가를 화면에 보여주는 단계와 수치 비교, 계산에 사용하는 단계는 역할이 다르다. 이 문자열을 그대로 더하거나 비율을 계산하는 처리가 있는지는 확인하지 않았다.

## 빈 목록과 파싱 실패 처리


입력 검사는 Zod 스키마를 사용한다. [Zod의 catch 동작](https://zod.dev/api#catch)은 검증에 실패했을 때 지정한 대체 값을 반환한다. 이 파서의 item 필드는 배열 스키마에 catch([])를 붙인다. 따라서 필드가 없거나 배열 검증이 실패하면 빈 배열이 될 수 있다.


설명용으로, 총개수는 3인데 한 항목의 필수 식별자 형식이 잘못된 응답을 생각해 볼 수 있다. 배열 전체의 검증이 실패하면 정상인 나머지 항목도 결과 배열에 남지 않을 수 있다. 화면에 "관심물건 0개"라고만 나오면 실제로 목록이 비었는지, 형식을 읽지 못한 것인지 구분이 안 된다.


메인 프로세스와 화면은 totalCount와 itemCount를 별도로 전달하고 표시한다. 두 수치를 대조하면 일부 항목이 누락됐는지 파악하는 데 쓸 수 있다. 다만 현재 파서에는 ID 기준 중복 제거가 없고 응답 배열을 그대로 map하므로, 동일 tid가 두 번 들어왔을 때 자동으로 합쳐지지는 않는다.


## 오류 시 저장 스냅샷 표시


[조회 결과 저장과 복원 처리](https://github.com/NAMUORI00/dooin_auction/blob/46ea78a0203a197e81e2edd07d99e914e17c7bf3/electron/main.ts)는 정상 응답을 파싱한 뒤 조회 시각, 요청, 최종 URL, HTTP 상태, 총개수와 항목을 로컬 파일에 쓴다.


로그인 상태가 유효하지 않거나 응답 형식을 읽지 못했을 때 저장본이 있으면 dataSource를 snapshot으로 돌려준다. 새 조회 결과의 live와 다른 상태다.


[화면 코드](https://github.com/NAMUORI00/dooin_auction/blob/46ea78a0203a197e81e2edd07d99e914e17c7bf3/src/App.tsx)도 이 출처와 오류 메시지, 조회 시각을 함께 표시한다. 지난 목록을 계속 참고할 수 있되 방금 확인한 정보처럼 보이지 않도록 구분하는 구성이다.

## 스냅샷과 변경 이력의 관리 범위


현재 저장 함수는 정해진 스냅샷 경로에 JSON을 덮어쓴다. 이 구조만으로는 과거 여러 시점의 목록이 보존되거나 물건별 변화가 자동 계산되지 않는다. before/after 패널과 알림 UI는 준비돼 있었고, 실제 수집 결과를 연결한 차이 분석은 추가 구현 항목이었다.


새로 조회한 목록에서 물건이 보이지 않는 경우도 곧바로 삭제로 판정하기는 어렵다. 로그인 문제, 불완전한 응답, 파싱 실패가 원인일 수 있기 때문이다. 향후 변화 추적을 붙인다면, 조회가 완전하다는 조건 아래 같은 listingId의 상태를 비교하고, 목록에서 빠진 이유가 불명확한 항목은 확인 대기로 분류하는 방식이 있다.


이번에 확인한 범위는 관심물건 응답의 정규화와 원문 연결, live, snapshot, empty 상태의 분리였다. 다음 글에서는 더 큰 수집 작업에서 같은 원문을 반복해서 내려받지 않으려면 어떤 기록이 필요한지 Dataset_Crawl 쪽으로 이어간다.


## 작업을 정리하며


스냅샷을 쓸 때 가장 먼저 드러내고 싶은 정보는 언제 확보한 자료인지다. 저장 시각과 수집 상태를 보여 주면 원격 조회 실패 때도 사용자가 자료의 기준을 판단할 수 있다. 차이 분석을 추가할 때는 항목별 식별자를 먼저 안정적으로 맞추려 한다.
