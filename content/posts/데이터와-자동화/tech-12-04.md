Common Crawl 자료를 다루며 색인 조회와 실제 파일 다운로드를 분리했다. 필요한 URL의 위치를 찾는 응답과 원문 데이터의 저장 위치가 달라, 주소, 압축, 범위 요청이 이어지는 과정을 정리했다.


## 구현과 확인 과정


Dataset_Crawl의 검색 결과와 다운로드 경로를 읽어 봤다. 색인에서는 WARC 안의 레코드를 찾고, 다운로드에서는 그 레코드가 포함된 보관 파일 전체를 받는다. 두 단계에서 다루는 자료의 단위가 달라 용량 계산과 실제 저장 범위를 함께 정리했다.


fbd41e8 커밋의 CC-Collect는 Common Crawl 색인에서 도메인을 찾고 용량을 계산한 뒤 외부 다운로드 도구를 호출하는 CLI다. URL, 중복 제거, 재수집의 기초를 바탕으로, 검색한 페이지 수와 예상 용량이 실제 산출물에 연결되는 과정을 살펴봤다.


## Common Crawl 수집 색인 조회


Common Crawl에는 이미 수집된 웹 응답이 들어 있다. 색인을 질의하면 원문 전체 대신 URL, 수집 시각, 상태 코드, 파일 위치 같은 정보를 얻는다. 이 경로는 대상 웹사이트를 새로 순회하는 크롤러와 다르게, 선택한 수집 회차에 남아 있는 자료를 찾는 방식으로 읽힌다.


[도메인별 기록 검색](https://github.com/NAMUORI00/Dataset_Crawl/blob/fbd41e8787607e139b56d3d1a4e7d3c6906abeff/src/cc_collect/domain_searcher.py)의 WarcRecord에는 filename, offset, length가 함께 들어간다.


filename은 보관 파일, offset은 그 파일 안에서 레코드가 시작하는 위치, length는 해당 압축 레코드의 길이를 나타낸다. 책 이름과 시작 쪽, 분량을 함께 적은 찾아보기처럼 생각하면 구분하기 쉬웠다.


여기서 WARC는 수집된 응답과 요청, 메타데이터를 담는 형식이다. 정제된 본문 텍스트만 남는 WET와도 다르다. 따라서 WARC 파일 확보를 학습용 텍스트 데이터셋 완성으로 이어 읽지는 않았다. [Common Crawl의 데이터 형식 설명](https://commoncrawl.org/get-started)도 원시 수집 자료와 추출된 평문을 구분한다.


## 레코드와 WARC 파일의 다운로드 단위


설명용으로 레코드 세 개를 놓았다. A 파일에 20KB와 30KB 레코드가 있고, B 파일에 40KB 레코드가 있다고 해 보자. 선택된 레코드의 합은 90KB다. 그러나 A와 B 파일 전체가 각각 500MB라면 파일을 통째로 받는 경로의 전송량은 약 1GB가 된다. 단위를 비교하기 위해 구성한 다운로드 용량 예제다.


[보관 파일 다운로드 처리](https://github.com/NAMUORI00/Dataset_Crawl/blob/fbd41e8787607e139b56d3d1a4e7d3c6906abeff/src/cc_collect/downloader.py)의 _create_paths_file은 레코드를 filename으로 묶고, 중복되지 않는 파일 경로만 내려받을 파일의 경로 목록에 쓴다.


offset과 length는 이 목록에 전달되지 않는다. 이어지는 cc-downloader download 호출은 그 목록의 파일을 받는 형태다. [공식 cc-downloader 사용법](https://github.com/commoncrawl/cc-downloader)에서도 경로 목록과 파일 다운로드가 별도 단계로 제시된다.


![12-04-01.png](/images/notion/tech-12-04/image-1.png)


그림 1. 색인에서는 레코드를 골랐지만 현재 다운로드 경로에서는 해당 WARC 파일 전체를 받는다. 용량은 설명용 예제이며, 도식은 보관 파일 다운로드 처리의 경로 생성 로직을 바탕으로 직접 구성.


다운로드 직전 공간 검사는 record.length의 합을 사용한다. 파일 전체를 받는 현재 경로에서는 이 합보다 더 많은 저장 공간이 필요할 수 있다. 같은 WARC에 다른 도메인의 레코드도 들어갈 수 있어, 저장된 파일과 선택 도메인의 자료 범위 역시 일치하지 않을 수 있었다.


## 중복 제거가 어느 단계에 적용되는지 확인하기


[중복 기준별 용량 계산](https://github.com/NAMUORI00/Dataset_Crawl/blob/fbd41e8787607e139b56d3d1a4e7d3c6906abeff/src/cc_collect/size_calculator.py)은 digest, url, none 세 전략을 제공한다.


digest는 같은 콘텐츠 해시를 한 번 남기고, url은 같은 URL의 최신 수집 시각을 남긴다. 해시가 없는 레코드는 digest 전략에서도 포함한다.


두 전략은 서로 다른 질문에 답한다. 주소가 다른 두 문서가 같은 내용을 담으면 digest 기준에서 합쳐질 수 있다. 같은 주소의 내용이 바뀌었다면 url 기준은 이전 내용을 제외하고 최신 관측을 남긴다. 현재 자료만 필요한지, 문서 변화 이력까지 필요한지에 따라 보존할 정보가 달라지는 셈이다.


![12-04-02.png](/images/notion/tech-12-04/image-2.png)


그림 2. 같은 세 레코드도 중복의 기준에 따라 남는 자료가 달라진다. 입력 순서는 ①→②→③인 설명용 예제이며, 중복 기준별 용량 계산을 바탕으로 직접 구성.


다만 [검색, 용량 계산, 다운로드를 연결하는 명령 도구](https://github.com/NAMUORI00/Dataset_Crawl/blob/fbd41e8787607e139b56d3d1a4e7d3c6906abeff/src/cc_collect/cli.py)에서 이 전략은 용량 계산에 전달되고, 다운로드에는 원래 search_result가 넘어간다.


호출 경로상 중복 제거 전략은 용량 계산에 적용된다. 다운로드에 넘어가는 결과는 원래 목록이므로, 이 옵션을 켠 상태를 중복 제거 데이터셋의 저장 완료로 해석하지 않았다. 파일 이름 중복과 콘텐츠 중복을 나누어 볼 지점이었다.


압축 해제 크기와 텍스트 크기는 고정 계수를 적용한 추정치다. 파일을 실제로 풀고 본문을 추출해 측정한 결과와는 다르다. 계산값을 검증할 때는 합산 대상과 계수를 함께 비교할 필요가 있다.


## 수집 회차별 실패와 결과 기록


검색은 수집 회차별로 동시에 최대 세 작업을 진행한다. 일부 회차에서 예외가 발생하면 로그를 남기고 성공한 결과만 모은다. 또 색인 요청의 404는 빈 결과로 처리한다. 결과 목록이 있다는 사실만으로 요청한 모든 회차를 조회했다고 판단하기 어려운 이유다.


다운로드 결과 집계도 다시 읽을 필요가 있었다. 출력 폴더 아래의 모든 *.warc.gz를 찾아 개수와 크기를 계산하므로 이전 실행 파일이 남아 있으면 이번 집계에 포함될 수 있다. 외부 프로세스의 성공 여부와 이번 실행에서 새로 확보한 파일 수는 별도 확인 항목으로 남는다. 여기서는 실제 대량 다운로드를 실행하지 않고 이 호출 경로까지 확인했다.


## 수집 명세와 산출물 관리


이 구성은 색인 검색에서 보관 파일 확보까지 연결하고 있었다. 선택 레코드만 필요한 작업에는 위치와 길이를 이용한 부분 다운로드가 대안이 될 수 있다. 파일 전체를 쓰는 작업에는 파일 단위 용량 계산과 후속 도메인 필터가 추가 검토 항목으로 남았다.


재수집 기록에는 실행 ID, 요청 회차와 성공과 실패 회차, 선택 레코드 목록, 실제 확보 파일을 연결하는 수집 명세가 필요해 보였다. 이 대응이 있으면 새 파일과 기존 파일의 재집계를 나누어 읽을 수 있다. 이어지는 엑셀 변환 글에서는 확보한 자료를 다른 형식으로 옮길 때 남는 값과 형식을 살펴본다.


## 작업을 정리하며


대규모 공개 자료를 수집할 때는 필요한 범위를 먼저 좁히는 일이 중요하다. 색인 결과와 실제 받은 바이트를 대응시키고 압축 형식까지 기록해 두면 재시도와 검증이 수월해진다. 다운로드 완료 기준도 파일 존재와 내용 확인으로 나누어 두려 한다.
