Common Crawl은 인터넷의 웹페이지를 주기적으로 모아 공개하는 대규모 데이터 저장소다. 여기서 특정 도메인의 문서를 모을 때는 사이트를 직접 방문하지 않고, 주소(URL)별 파일 위치를 적어 둔 **색인**(index)을 먼저 검색한다. `Dataset_Crawl` 저장소(`fbd41e8` 커밋)에 있는 명령줄 도구 `CC-Collect`는 이 색인에서 원하는 도메인을 검색한다. 검색이 끝나면 예상 용량을 계산한 뒤 외부 다운로드 도구를 호출해 파일을 내려받는다.


하지만 이 도구의 검색과 다운로드 경로를 따라가 보면 두 단계가 다루는 자료의 단위가 서로 다르다. 색인 조회에서는 보관 파일 안에 담긴 웹페이지 한 건의 기록인 **레코드**(record)를 찾지만, 다운로드 단계에서는 보관 파일 전체를 내려받는다. 색인에서 검색한 문서 수와 예상 용량이 실제 내려받는 파일과 어떻게 달라지는지 코드의 호출 경로를 따라 확인했다.


## Common Crawl 색인 조회와 WARC 형식


검색과 다운로드의 단위 차이를 이해하려면 먼저 Common Crawl이 웹 문서를 어떤 형식으로 보관하고 색인에 무엇을 기록하는지 알아야 한다. Common Crawl에는 여러 수집 회차에 걸쳐 저장된 웹 응답이 들어 있다. 웹사이트를 새로 돌아다니는 일반 수집기(크롤러)와 달리, 여기서는 원하는 수집 회차를 골라 이미 저장된 기록의 위치를 찾는다. 색인에 질의를 보내면 웹페이지 원문 전체가 아니라 자료의 특징과 위치를 요약한 **메타데이터**(metadata)가 돌아온다. 여기에는 웹 주소(URL)와 수집 시각, 응답 결과를 뜻하는 HTTP 상태 코드, 그리고 파일 위치가 들어 있다.


도서관에서 책의 특정 대목을 찾을 때 책 이름과 시작 쪽수, 읽을 분량을 함께 적어 두는 찾아보기와 비슷하다. [도메인별 기록 검색](https://github.com/NAMUORI00/Dataset_Crawl/blob/fbd41e8787607e139b56d3d1a4e7d3c6906abeff/src/cc_collect/domain_searcher.py)(`domain_searcher.py`)이 반환하는 `WarcRecord` 객체에도 위치 정보로 `filename`, `offset`, `length` 세 값이 함께 담긴다. `filename`은 데이터가 들어 있는 보관 파일 경로이고, `offset`은 그 파일 안에서 대상 레코드가 시작하는 바이트 위치다. 마지막으로 `length`는 압축된 레코드 한 건이 차지하는 바이트 길이를 나타낸다.


![Common Crawl 색인의 WarcRecord에 담긴 filename, offset, length가 WARC 보관 파일 안의 대상 레코드 시작 위치와 길이를 가리키는 도식](/images/notion/tech-12-04/image-1.png)


그림 1. Common Crawl 색인 조회로 얻는 WarcRecord 위치 정보와 WARC 보관 파일 내부 레코드 구간의 대응 구조.


여기서 보관 파일 형식인 **WARC**(Web ARChive)는 수집 당시의 HTTP 요청과 응답, 메타데이터를 그대로 묶어 둔 원시 자료다. 웹페이지에서 HTML 태그 같은 코드를 걷어 내고 정제된 본문 글자(평문)만 남긴 **WET**(WARC Encapsulated Text) 형식과는 다르다. [Common Crawl의 데이터 형식 설명](https://commoncrawl.org/get-started)에서도 원시 수집 자료인 WARC와 추출된 평문인 WET를 구분한다. 따라서 WARC 파일을 내려받았다고 해서 곧바로 학습에 쓸 수 있는 텍스트 데이터셋이 완성되는 것은 아니다.


## 레코드 단위 검색과 파일 단위 다운로드


색인에서 개별 레코드의 시작 위치(`offset`)와 길이(`length`)를 찾더라도, 다운로드 단계에서 그 구간만 잘라 받는지는 따로 확인해야 한다. [보관 파일 다운로드 처리](https://github.com/NAMUORI00/Dataset_Crawl/blob/fbd41e8787607e139b56d3d1a4e7d3c6906abeff/src/cc_collect/downloader.py)(`downloader.py`)의 `_create_paths_file` 함수는 검색된 레코드들을 `filename` 기준으로 먼저 묶는다. 그런 다음 중복된 파일 이름을 걷어 내고 고유한 파일 경로만 추려서 다운로드 목록 파일을 만든다.


이 과정에서 각 레코드의 `offset`과 `length`는 목록 파일에 기록되지 않는다. 뒤이어 호출하는 `cc-downloader download` 명령은 이 목록에 적힌 WARC 보관 파일 전체를 통째로 내려받는다. [공식 cc-downloader 사용법](https://github.com/commoncrawl/cc-downloader)에서도 경로 목록 생성과 파일 다운로드를 별도 단계로 안내하며 보관 파일 단위로 동작한다.


색인 검색으로 찾은 레코드 세 건 가운데 `A` 파일에 20KB와 30KB 레코드가 있고, `B` 파일에 40KB 레코드가 있는 경우를 예로 들 수 있다. 이때 선택한 레코드 세 건의 크기를 모두 더하면 90KB에 불과하다. 하지만 `A`와 `B` 파일 하나의 전체 크기가 각각 500MB라면, 보관 파일을 통째로 내려받는 현재 경로에서는 실제 전송량이 약 1GB로 불어난다.


![색인에서 찾은 20KB, 30KB, 40KB 레코드가 파일 이름 A, B로 묶여 각각 500MB인 전체 WARC 파일 다운로드로 이어지는 흐름도](/images/notion/tech-12-04/image-2.png)


그림 2. 색인에서는 개별 레코드를 찾지만 다운로드 경로에서는 파일 이름만 묶어 WARC 보관 파일 전체를 내려받는 흐름으로, 용량 수치는 설명용 예제이며 보관 파일 다운로드 처리 로직을 바탕으로 구성했다.


검색과 다운로드의 단위 차이는 사전 저장 공간 검사에도 영향을 준다. `CC-Collect`는 다운로드 직전에 남은 디스크 공간을 검사할 때 검색된 레코드 크기인 `record.length`의 합계를 기준으로 삼는다. 실제로는 보관 파일 전체를 내려받기 때문에 `record.length` 합계보다 훨씬 많은 저장 공간이 필요할 수 있다. 또한 하나의 WARC 파일 안에는 여러 웹사이트의 응답이 함께 묶여 있어, 내려받은 파일에는 검색한 도메인 외에 다른 도메인의 레코드도 섞여 들어간다.


## 중복 제거 기준과 적용 범위


레코드 단위 계산과 파일 단위 다운로드의 차이는 중복된 문서를 걸러 내고 예상 용량을 어림잡는 과정에서도 나타난다. [중복 기준별 용량 계산](https://github.com/NAMUORI00/Dataset_Crawl/blob/fbd41e8787607e139b56d3d1a4e7d3c6906abeff/src/cc_collect/size_calculator.py)(`size_calculator.py`) 모듈은 `digest`, `url`, `none` 세 가지 중복 제거 기준을 지원한다. 여기서 `digest`는 문서 본문을 일정한 길이의 문자열로 바꾼 콘텐츠 **해시**(hash) 값을 비교하는 방식이다. 본문 해시가 같으면 한 건만 남기고, 해시 정보가 없는 레코드는 그대로 포함한다. 반면 `url` 기준은 주소(URL)가 같을 때 수집 시각이 가장 늦은 최신 레코드 한 건만 남기며, `none`은 중복을 제거하지 않는다.


주소가 다른 `/a`와 `/b` 두 문서에 똑같은 내용(해시 `X`)이 들어 있다면 `digest` 기준에서는 하나로 합쳐진다. 반대로 같은 `/a` 문서의 내용이 9월 1일(해시 `X`)에서 9월 3일(해시 `Y`)로 바뀌면, `url` 기준은 이전 기록을 버리고 최신인 9월 3일 기록만 남긴다. 사이트의 현재 상태만 필요한지, 아니면 시간에 따른 문서의 변화 이력까지 필요한지에 따라 선택할 기준이 달라진다.


![세 개의 레코드 입력이 중복 제거 기준인 내용 해시(digest)와 주소별 최신 관측(url)으로 갈라져 각각 ①, ③과 ②, ③만 남아 집계되는 비교 도식](/images/notion/tech-12-04/image-3.png)


그림 3. 입력 순서가 ①→②→③인 세 레코드 예제에서 중복 제거 기준(digest, url)에 따라 용량 집계에 남는 자료가 달라지는 과정으로, 중복 기준별 용량 계산 로직을 바탕으로 구성했다.


다만 이 중복 제거 옵션이 전체 흐름의 어디까지 반영되는지는 [검색, 용량 계산, 다운로드를 연결하는 명령 도구](https://github.com/NAMUORI00/Dataset_Crawl/blob/fbd41e8787607e139b56d3d1a4e7d3c6906abeff/src/cc_collect/cli.py)(`cli.py`)를 함께 봐야 한다. `cli.py`의 호출 경로를 보면 사용자가 지정한 중복 제거 기준은 용량 계산기(`size_calculator`)에만 전달된다. 다운로더(`downloader`)에는 중복을 제거하기 전의 원래 검색 결과(`search_result`)가 그대로 넘어간다.


![cli.py에서 검색 결과가 용량 계산 경로와 다운로드 경로로 나뉘며 중복 제거 옵션은 용량 계산에만 적용되고 다운로드는 원래 검색 결과를 사용하는 구조도](/images/notion/tech-12-04/image-4.png)


그림 4. `cli.py`에서 중복 제거 옵션이 용량 계산 경로에만 전달되고 다운로드 경로에는 원래 검색 결과가 넘어가는 호출 흐름.


따라서 `digest`나 `url` 옵션을 켜더라도 화면에 나오는 예상 용량 수치만 줄어든다. 다운로드 대상 파일 목록이 줄어들거나 중복이 제거된 데이터셋이 저장되는 것은 아니다. 다운로더 단계에서 일어나는 중복 제거는 여러 레코드가 같은 보관 파일을 가리킬 때 파일 이름(`filename`)을 한 번만 적는 수준에 그친다. 또한 용량 계산기가 보여 주는 압축 해제 크기와 추출 텍스트 크기는 실제 파일을 풀고 본문을 발라내어 잰 값이 아니다. 미리 정해 둔 고정 계수를 곱해 어림잡은 추정치이므로 실제 데이터 크기와 차이가 날 수 있다.


## 예외 처리와 산출물 집계 방식


용량 계산과 다운로드의 연결 경로에 이어, 여러 수집 회차를 조회할 때 발생하는 예외 처리와 다운로드 뒤의 결과 집계 로직도 코드를 따라 확인했다. 도메인 검색기는 여러 수집 회차를 조회할 때 동시에 최대 세 작업까지 병렬로 실행한다. 이때 일부 수집 회차에서 예외가 발생하면 기록(로그)만 남기고 성공한 회차의 결과만 모아서 반환한다. 색인 서버가 404 상태 코드를 돌려줄 때도 오류로 멈추지 않고 빈 결과로 처리한다. 그래서 검색 결과 목록이 나왔다는 사실만으로는 처음 요청한 모든 수집 회차가 빠짐없이 조회되었다고 단정하기 어렵다.


다운로드가 끝난 뒤 확보한 산출물을 집계하는 방식에도 주의할 점이 있다. 다운로더는 지정된 출력 폴더 아래의 모든 `*.warc.gz` 파일을 찾아 개수와 크기를 합산한다. 만약 이전 실행에서 내려받은 파일이 같은 폴더에 남아 있었다면 이번 실행 집계에 함께 포함된다. 외부 도구인 `cc-downloader` 프로세스가 정상 종료되었는지, 그리고 이번 실행에서 새로 확보한 파일이 몇 개인지는 폴더 전체 집계와 분리해서 확인해야 한다.


## 보완 과제와 수집 명세


앞선 코드 분석에서 드러난 단위 불일치와 집계 문제를 해결하려면 수집 목적에 맞게 다운로드 방식과 검증 절차를 보완해야 한다. 특정 도메인의 선택된 레코드만 필요한 작업이라면 보관 파일 전체를 내려받지 않는 편이 낫다. 이 경우 `WarcRecord`의 `offset`과 `length`를 활용해 필요한 바이트 구간만 부분 다운로드하는 방식이 대안이 될 수 있다. 반대로 WARC 파일 전체를 내려받는 구조를 유지한다면, 디스크 공간 검사를 파일 단위로 바꾸고 다운로드 뒤에 대상 도메인 레코드만 걸러 내는 후처리가 필요하다.


반복해서 자료를 모으고 검증하려면 실행 이력을 남기는 수집 명세도 갖추어야 한다. 실행 ID를 기준으로 요청한 수집 회차와 성공 및 실패 회차, 색인에서 선택한 레코드 목록, 압축 형식, 실제로 확보한 파일을 연결해 기록해 두어야 한다. 이렇게 실행별 기록을 남겨 두면 기존 파일과 새 파일이 한 폴더에서 섞여 집계되는 문제를 막을 수 있다. 다운로드 완료 기준 역시 폴더에 파일이 존재하는지 확인하는 단계와 실제 내용을 확인하는 단계로 나누어 두면 재시도와 검증이 한결 수월해진다.


## 결론


이번에는 실제 대량 다운로드를 실행하지 않고, `CC-Collect`의 코드 호출 경로를 따라 색인 조회부터 보관 파일 다운로드와 산출물 집계까지의 동작을 확인했다. 색인 조회와 용량 계산, 디스크 공간 검사는 개별 레코드(`offset`, `length`) 단위로 이루어지고 중복 제거 옵션도 용량 계산에만 적용된다. 반면 실제 다운로드는 중복 제거 전의 검색 결과를 받아 레코드가 속한 WARC 보관 파일 전체를 통째로 내려받는다.


또한 수집 회차 조회 오류를 건너뛰고 출력 폴더의 `*.warc.gz` 파일을 일괄 합산하므로, 검색 결과나 집계 수치만으로는 실제 확보한 데이터를 정확히 알기 어렵다. 따라서 계산과 저장의 단위를 맞추고 도메인별 후처리와 실행별 수집 명세를 더해 수집 결과를 검증해야 한다. 이어지는 엑셀 변환 글에서는 확보한 자료를 다른 형식으로 옮길 때 남는 값과 형식을 다룬다.
