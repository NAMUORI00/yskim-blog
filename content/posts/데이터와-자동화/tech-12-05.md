엑셀이나 값을 쉼표로 구분해 적은 **CSV** 표를 다른 양식으로 옮길 때는 화면에 보이는 모양과 셀의 실제 값이 다를 수 있다. 빈 셀, 숫자로 된 식별자, 수식, 날짜는 화면의 표시 형식과 실제로 저장된 값이 어긋나기 쉬운 항목이다. 이런 항목은 값을 바꾸는 단계와 셀을 화면에 배치하는 단계를 나누어 봐야 어디서 정보가 달라지는지 파악할 수 있다.


이를 확인하려고 코드 저장소 두 곳에서 `ExcelDataConverter`의 `e083174` 커밋과 `ExcelAutomationTool`의 `488316a` 커밋을 비교했다. 두 저장소는 이름이 비슷하지만 구현된 범위가 달라, 실제로 표를 변환하는 코드는 `ExcelDataConverter`에만 들어 있다. `ExcelDataConverter`는 엑셀과 CSV 파일을 읽어 여러 행의 데이터를 한 줄의 셀로 펼쳐 주는 애플리케이션이다. 반면 `ExcelAutomationTool`은 [README](https://github.com/NAMUORI00/ExcelAutomationTool/blob/488316a7c5aa11cf76b792dae1a02cae74ccf0a3/README.md)에 엑셀 양식 생성과 여러 파일을 기준 값으로 묶는 **조인**(join) 목적이 적혀 있다. 하지만 현재 C# [데스크톱 창 구성 코드](https://github.com/NAMUORI00/ExcelAutomationTool/blob/488316a7c5aa11cf76b792dae1a02cae74ccf0a3/Form1.cs)와 폼 디자이너에는 기본 창을 여는 초기화 코드만 남아 있다. 따라서 이 글에서는 실제 변환 경로가 구현된 `ExcelDataConverter`를 따라가며 숫자, 수식, 표시 형식 가운데 무엇이 결과 파일로 옮겨지는지 확인한다.


## 입력 형식별 첫 행과 열 목록


`ExcelDataConverter`는 먼저 파일을 읽어 각 줄의 데이터를 이름표인 키(key)와 값으로 묶은 행 **객체**(object) 배열로 만든다. [엑셀 입력 처리](https://github.com/NAMUORI00/ExcelDataConverter/blob/e083174005c0524e3b0905054c03d93a29eabe7d/src/main.ts) 코드는 ExcelJS 라이브러리로 첫 번째 워크시트를 읽는다. 이때 각 셀의 값을 `col1`, `col2`처럼 열 번호로 만든 키에 담아 행 객체를 생성한다. 표의 첫 번째 행을 열 이름인 **헤더**(header)로 분리하는 처리는 따로 하지 않는다.


반면 CSV 입력은 Papa Parse 라이브러리의 `header: true` 옵션을 켜서 읽는다. [Papa Parse 문서](https://www.papaparse.com/docs#config)에 나온 설명대로 파일의 첫 줄을 필드 이름으로 삼아 두 번째 줄부터 행 객체를 만든다. 이 때문에 똑같은 표를 XLSX 파일과 CSV 파일로 준비해도 XLSX에서는 첫 줄이 일반 데이터 행으로 들어가고, CSV에서는 열 이름이 된다.


여기에 더해 엑셀을 읽을 때는 비어 있는 셀을 별도의 기본값으로 채우지 않는다. 그런데 변환 화면에서 사용자가 고를 수 있는 열 목록은 첫 번째 행 객체의 키 목록인 `Object.keys(data[0])`로만 만든다. 만약 첫 행에서 비어 있던 열에 뒤쪽 행부터 값이 나타나면, 그 열은 `data[0]`에 키가 없어 기본 선택 목록에서 빠질 수 있다. 첫 행 하나가 어떤 열을 어떤 순서와 자료형으로 다룰지 정한 규칙인 **스키마**(schema)를 대표한다고 가정한 코드이기 때문이다.


![XLSX는 셀 위치(col1, col2)로 읽어 첫 행도 데이터로 취급하고, CSV는 첫 줄을 헤더로 읽어 둘째 줄부터 데이터로 취급한 뒤 첫 데이터 행의 키를 Object.keys로 읽어 열 목록을 만드는 흐름도](/images/notion/tech-12-05/image-1.png)

## 한 줄 배치와 셀 간격 계산


입력 단계에서 만든 행 객체와 열 목록은 [여러 행을 한 행으로 펼치는 처리](https://github.com/NAMUORI00/ExcelDataConverter/blob/e083174005c0524e3b0905054c03d93a29eabe7d/src/renderer/components/DataTransform.tsx)로 넘어간다. 이 코드는 사용자가 활성화한 열을 행 순서대로 읽어 `resultCells` 배열 하나에 차례대로 이어 붙인다. 그다음 최종 결과를 `[resultCells]` 형태로 감싸 바깥 배열에 원소가 하나뿐인 2차원 배열로 만든다. 이 과정을 거치면 원래 여러 행이었던 표가 가로로 길게 이어진 단일 행으로 펼쳐진다.


`이름`과 `수량` 두 열에 첫 행으로 `사과`, `2`, 둘째 행으로 `배`, `3`이 들어 있는 표를 예로 들면 셀 간격 계산 방식을 확인할 수 있다. 각 값을 펼칠 때의 간격은 셀 길이(`cellLength`) 설정과 데이터 포함 옵션이 결정한다. 각 열의 `cellLength`를 `2`로 두고 데이터 포함 옵션을 끄면, 원래 값 한 칸 뒤에 빈 추가 칸 두 개가 붙어 값 하나가 총 세 칸을 차지한다. 한 행에 값 두 개가 있으니 여섯 칸이 되고, 두 행을 모두 펼치면 총 열두 칸이 된다. 반대로 데이터 포함 옵션을 켜면 원래 값과 추가 칸을 합쳐서 두 칸을 맞추므로, 값 한 칸 뒤에 추가 칸이 하나만 붙어 전체 여덟 칸이 된다. 여기에 헤더 포함 옵션까지 켜면 열 이름 묶음이 같은 배치 규칙을 따라 맨 앞에 추가된다.


![입력 값 4개(사과, 2, 배, 3)에 셀 길이 2를 적용할 때 데이터 포함 켜짐이면 총 8칸, 꺼짐이면 총 12칸의 단일 행 배열로 변환되는 비교도](/images/notion/tech-12-05/image-2.png)

화면에서 고르는 구분자(`separator`) 설정은 원래 값 뒤에 붙는 추가 칸을 무엇으로 채울지 정하는 용도다. 반면 변환 결과를 CSV 파일로 내보내는 작업은 `Papa.unparse`가 따로 처리한다. 화면에서 구분자로 `|`를 골라도 추가 셀에 들어갈 문자열만 바뀔 뿐, 저장되는 CSV 파일의 열 구분자가 쉼표에서 `|`로 바뀌지는 않는다.


## 수식 셀의 문자열 변환과 서식 보존 범위


셀을 한 줄로 배치하는 변환 반복문은 각 셀 안의 값을 모두 문자열로 바꾸어 저장한다. 비어 있는 값인 `null`과 `undefined`는 빈 문자열(`""`)로 바꾸고, 숫자 `2` 같은 나머지 값은 `String(value)`에 넣어 문자열 `"2"`로 만든다.


단순한 숫자나 글자에서는 이 방식이 문제없이 동작하지만, 수식이 들어 있는 엑셀 셀에서는 결과가 달라진다. [ExcelJS의 수식 값 설명](https://github.com/exceljs/exceljs#formula-value)을 보면 수식 셀의 값은 수식 자체인 `formula`와 계산된 값인 `result`를 함께 담은 객체 형태를 띤다. 이때 ExcelJS는 수식을 직접 다시 계산하지 않고 저장된 객체를 그대로 가져온다. 따라서 셀 값인 `cell.value`가 객체일 때 구분 없이 곧바로 `String(value)`를 호출하면 계산 결과인 `result`를 꺼내지 못한다. 그 대신 일반 객체를 문자열로 바꾼 기본 표기인 `[object Object]`가 결과 셀에 들어갈 수 있다.


![null과 undefined는 빈 문자열로, 숫자 2는 문자열 2로 바뀌지만, formula와 result가 담긴 수식 셀 객체는 String(value) 적용 시 객체의 기본 문자열 표기로 바뀌는 구조도](/images/notion/tech-12-05/image-3.png)


그림 3. 변환 루프에서 셀 값을 문자열로 일괄 변환할 때 자료형에 따라 달라지는 결과.


표를 변환할 때는 수식 문자열 그 자체, 이전에 저장된 계산 결과, 화면에 보이는 표시 텍스트 가운데 목적에 맞는 대상을 골라야 한다. 현재 변환 반복문에서는 셀 값을 자료형별로 나누는 처리를 찾지 못해, 셀 객체를 문자열로 바꾸는 부분이 그 구분을 검토할 지점으로 남았다.


또한 파일을 읽는 단계에서는 `cell.value`만 가져오므로 숫자 표시 형식, 셀 배경색, 병합 상태 같은 서식 정보는 옮겨지지 않는다. 결과를 엑셀로 저장할 때도 새 워크북의 `Sheet1`에 변환된 문자열 배열만 새로 써 넣는다. 결과를 엑셀 파일로 저장했다는 사실과 원본 엑셀의 의미 및 서식을 그대로 보존했다는 사실은 별개로 확인해야 한다.


## 변환 한도 검사와 미리보기 범위


셀 값을 문자열로 바꾸어 배열에 모으는 방식은 데이터 양이 많을 때의 처리 흐름과 검증 범위에도 영향을 준다. 변환 반복문은 한 번에 1,000행씩 묶어 처리하면서 중간에 화면이 갱신될 틈을 준다. 하지만 변환된 셀을 결국 메모리 안의 배열 하나에 모두 모으므로, 파일에 조금씩 기록하는 **스트리밍**(streaming) 변환과는 다르게 동작한다.


여러 행을 한 줄로 펼친 총 셀 수가 16,384개를 넘으면 변환 단계에서 작업이 바로 중단된다. 이 셀 개수 검사는 사용자가 파일 저장 형식(XLSX 또는 CSV)을 고르기 전에 먼저 실행된다. 화면의 안내 문구에는 셀 수가 많을 때 CSV 형식을 선택하라고 적혀 있다. 그러나 현재 함수 호출 순서에서는 나중에 CSV로 저장하려 해도 변환 단계의 16,384개 검사를 건너뛰지 못한다.


![1,000행 단위 변환 후 총 셀 수 16,384개 초과 검사를 먼저 통과해야 앞 50열 미리보기와 XLSX 또는 CSV 저장 형식 선택으로 넘어가는 흐름도](/images/notion/tech-12-05/image-4.png)


그림 4. 셀 수 한도 검사와 미리보기를 거쳐 파일 저장 형식 선택으로 이어지는 실행 순서.


변환이 끝난 뒤 화면에 나타나는 [변환 결과 미리보기](https://github.com/NAMUORI00/ExcelDataConverter/blob/e083174005c0524e3b0905054c03d93a29eabe7d/src/renderer/components/DataPreview.tsx)는 결과 행의 처음 50열만 잘라서 보여 준다. 파일 쓰기 완료를 알리는 저장 메시지에도 저장된 파일을 다시 열어 원본과 전체 셀을 대조한 결과는 포함되지 않는다. 이번 정리는 소스 코드의 처리 흐름을 따라가며 확인한 기록이며, 실제 저장 파일을 열어 대조하는 검증까지는 수행하지 않았다.


## 결론


`ExcelDataConverter`의 변환은 표의 값들 사이에 일정한 칸 간격을 두고 한 줄의 문자열 배열로 재배치하는 작업이다. 코드 흐름을 따라가며 입력 형식에 따라 첫 행의 역할이 달라지고, 수식 객체와 서식이 원본 그대로 보존되지 않는다는 점을 확인했다. 파일 저장 형식을 고르기 전에 16,384개 셀 한도 검사가 먼저 실행되고 미리보기는 앞 50열만 보여 준다는 점도 함께 드러났다. 반면 원본 시트의 서식을 유지하거나 여러 파일을 기준 키로 묶는 조인 처리는 이 도구와 목적이 다르다. `ExcelAutomationTool`의 `README.md`에 조인 기능이 적혀 있었지만 현재 `Form1.cs` 코드만으로는 실제 동작을 확인할 수 없었다. 따라서 두 도구가 맡은 역할과 실제 코드의 구현 상태는 서로 구분해 두어야 한다.


실제 저장 파일을 대조하는 후속 검증에는 첫 행에 빈 셀이 있는 표, 숫자로 된 식별자, 수식 셀, 날짜가 들어간 작은 파일을 사용할 수 있다. 읽기 전의 원본 값과 저장 후의 결과 값을 자료형별로 나란히 비교하면 어디서 정보가 손실되는지 바로 찾을 수 있다. 다음 확장에서도 값, 표시 형식, 조인 키를 서로 다른 검사 항목으로 나누어 두려 한다. 이어지는 글에서는 같은 자료형 문제가 CSV를 JSON API 응답으로 바꾸는 과정에 어떻게 연결되는지 다룬다.
