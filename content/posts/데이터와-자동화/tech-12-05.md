엑셀 자동화 작업에서는 표의 값을 읽어 다른 셀 배치로 옮기는 흐름을 다뤘다. 빈 셀, 숫자 식별자, 날짜처럼 표시와 실제 값이 달라지는 경우가 있어 값 변환과 화면 배치를 구분해 정리했다.


## 구현과 확인 과정


엑셀 변환, 자동화 저장소에서 입력 자료가 결과 파일로 이어지는 경로를 살펴봤다. 셀의 값과 화면에 보이는 형식은 서로 다를 수 있어, 숫자, 수식, 표시 형식 가운데 실제로 옮겨지는 대상을 중심으로 정리했다.


ExcelDataConverter의 e083174 커밋과 ExcelAutomationTool의 488316a 커밋을 읽었다. 이름은 비슷하지만 확인되는 구현 범위는 달랐다.


전자는 엑셀, CSV를 읽어 여러 행을 한 줄의 셀로 펼치는 앱이고, 후자는 README에 엑셀 양식 생성과 조인 목적이 적혀 있으나 현재 C# 소스는 기본 폼 초기화까지 남아 있다. 두 저장소의 범위를 나눈 뒤, 실제 변환 경로가 있는 전자를 따라갔다.


## 입력 형식별 첫 행 처리


[엑셀 입력 처리](https://github.com/NAMUORI00/ExcelDataConverter/blob/e083174005c0524e3b0905054c03d93a29eabe7d/src/main.ts)는 ExcelJS로 첫 번째 워크시트를 읽는다. 셀 값을 col1, col2 같은 키에 넣고 행 객체를 만든다. 첫 행을 헤더로 해석하는 별도 처리는 없다.


CSV 쪽은 Papa Parse의 header: true를 사용한다. 첫 줄이 필드 이름이 되어 뒤의 행을 객체로 만든다. [Papa Parse 문서](https://www.papaparse.com/docs#config)의 헤더 처리와 같은 방식이다. 동일한 표를 XLSX와 CSV로 준비해도 한쪽에서는 첫 줄이 데이터이고 다른 쪽에서는 열 이름이 되는 차이가 생긴다.


또한 엑셀을 읽을 때 비어 있는 셀을 별도 값으로 채우지 않고, 변환 화면의 열 목록은 Object.keys(data[0])로 정한다. 첫 행에 없는 열이 뒤에서 나타나면 그 열이 기본 선택 목록에 잡히지 않을 수 있다. 첫 행이 전체 스키마를 대표한다는 가정이 숨어 있는 셈이다. 스키마는 여기서 어떤 열을 어떤 순서와 자료형으로 다룰지 정한 규칙을 뜻한다.

그림 1. 입력 형식에 따라 열 이름과 첫 행의 역할이 달라지는 과정. 출처: 엑셀 입력 처리와 여러 행을 한 행으로 펼치는 처리를 바탕으로 직접 구성.


## 셀 길이 설정과 배치 칸 수


[여러 행을 한 행으로 펼치는 처리](https://github.com/NAMUORI00/ExcelDataConverter/blob/e083174005c0524e3b0905054c03d93a29eabe7d/src/renderer/components/DataTransform.tsx)는 활성화한 열을 행 순서대로 읽고 resultCells에 이어 붙인다.


결과는 [resultCells]이므로 여러 행을 한 행으로 펼친다. 셀 길이 설정은 값 뒤에 배치할 칸 수를 결정한다.


이름, 수량 두 열에 사과, 2, 배, 3이 들어 있는 설명용 표를 놓았다. 각 열의 cellLength가 2이고 데이터 포함 옵션이 꺼져 있으면 값 한 칸 뒤에 추가 두 칸이 붙는다. 한 행당 여섯 칸, 두 행은 열두 칸이다. 데이터 포함 옵션을 켜면 값과 추가 칸을 합쳐 두 칸이 되어 전체 여덟 칸이 된다. 헤더를 포함하면 같은 배치 규칙을 적용한 한 묶음이 앞에 더해진다.


![12-05-02.png](/images/notion/tech-12-05/image-2.png)


그림 2. 셀 길이 2를 값 포함 여부에 따라 다르게 해석하는 예제. 세로선은 설명용 셀 경계 표기다. 출처: 여러 행을 한 행으로 펼치는 처리의 반복문을 바탕으로 직접 구성.


앱의 separator는 값 뒤의 추가 셀에 넣을 내용이었다. CSV 저장은 Papa.unparse가 따로 맡는다. 화면에서 |를 고르는 설정과 CSV 파일의 열 구분자를 |로 바꾸는 설정은 연결되어 있지 않았다.


## 수식 셀의 문자열 변환


변환 루프는 null, undefined를 빈 문자열로, 나머지는 String(value)로 바꾼다. 숫자 2도 결과에서는 문자열이 된다. ExcelJS 셀 값은 수식과 계산 결과를 함께 담는 객체일 수 있는데, 그 객체에 곧바로 String을 적용하면 수식의 결과값을 고르는 동작과는 다르다. 일반 객체라면 [object Object] 같은 표현이 될 수 있다.


[ExcelJS의 수식 값 설명](https://github.com/exceljs/exceljs#formula-value)은 formula와 result를 구분하고, 라이브러리가 수식을 직접 계산하지 않는다고 설명한다.


수식 자체, 저장된 계산 결과, 표시 텍스트는 변환 목적에 따라 선택할 대상이 다르다. 현재 루프에서는 이를 자료형별로 나누는 처리를 찾지 못했다. 셀 객체를 문자열로 바꾸는 부분이 그 구분을 검토할 지점으로 남았다.


읽기 단계에서는 cell.value를 옮기며, 표시 형식, 색, 병합 상태는 별도 복사 처리가 필요하다. 결과 저장은 새 워크북의 Sheet1에 변환 배열을 추가한다. “엑셀로 저장했다”와 “원본 엑셀의 의미와 서식을 보존했다” 사이에 확인할 항목이 남는다.


## 미리보기와 저장 파일 비교


변환은 천 행씩 묶어 진행하고 중간에 화면이 갱신될 기회를 준다. 다만 결과 전체를 배열로 모으므로 디스크에 조금씩 쓰는 스트리밍 변환으로 보기는 어려웠다. 총 셀 수가 16,384를 넘으면 변환 단계에서 막히며, 이 검사는 출력 형식을 선택하기 전에 실행된다. 안내 문구에 CSV 선택이 나와도 현재 호출 순서에서는 CSV를 선택하는 것만으로 이 검사를 건너뛰지 못한다.


[변환 결과 미리보기](https://github.com/NAMUORI00/ExcelDataConverter/blob/e083174005c0524e3b0905054c03d93a29eabe7d/src/renderer/components/DataPreview.tsx)는 변환 결과의 처음 50열을 표시한다.


미리보기에서 확인하는 범위는 결과의 앞부분이다. 파일 쓰기 완료를 알리는 저장 메시지에도 전체 셀을 다시 열어 원본과 대조한 결과는 포함되지 않는다. 이번 기록 역시 소스 흐름 확인까지이며 저장 파일 검증은 수행하지 않았다.


## 변환 범위와 후속 개선


확인한 변환은 값 사이에 정해진 간격을 두고 한 줄로 배치하는 방식이었다. 원본 시트의 보존이나 여러 파일의 키 기반 조인은 이 흐름과 다른 목적의 처리로 읽었다.


ExcelAutomationTool의 [README](https://github.com/NAMUORI00/ExcelAutomationTool/blob/488316a7c5aa11cf76b792dae1a02cae74ccf0a3/README.md)에는 조인 목적이 남아 있지만, 현재 [데스크톱 창 구성 코드](https://github.com/NAMUORI00/ExcelAutomationTool/blob/488316a7c5aa11cf76b792dae1a02cae74ccf0a3/Form1.cs)와 폼 디자이너만으로 그 기능의 실행을 설명할 수는 없었다.


후속 검증에는 첫 행의 빈 셀, 숫자로 된 식별자, 수식, 날짜가 들어간 작은 파일을 사용할 수 있다. 읽기 전후의 값을 나란히 놓으면 각 자료형에서 보존되는 정보를 확인할 수 있다. 이어지는 CSV→JSON API 글에서는 같은 자료형 문제가 네트워크 응답에 연결되는 과정을 살펴본다.


## 작업을 정리하며


표 변환에서는 예쁘게 배치된 결과와 원본 의미의 보존을 함께 확인해야 한다. 숫자 식별자와 빈칸을 포함한 작은 파일을 먼저 비교하면 자료형 문제를 빠르게 찾을 수 있다. 다음 확장에서도 값, 표시 형식, 조인 키를 서로 다른 검사 항목으로 두려 한다.
