## 서버 시작 시 JSON 로딩


CSV를 JSON으로 바꾸는 함수는 각 행의 열 이름과 값을 한 묶음으로 읽어 저장한다. 입력 표와 출력 파일의 위치를 정해 이 함수를 호출하는 보조 함수도 있다. 다만 프로그램을 시작하는 흐름에서는 이 보조 함수를 직접 호출하지 않는다.


[csv_to_json](https://github.com/NAMUORI00/FASTAPI_PANDAS_CSV2JSON/blob/ee7ec277a5321f84da4a3424f5e41a270129fffe/main.py#L8)


프로그램을 시작할 때는 이미 변환해 둔 JSON을 pandas로 읽어 표를 만들고, 그 표를 다시 파일에 쓴다. 이어 한글 열 이름을 name, category, region, menu 같은 이름으로 바꾼다.


필요한 JSON이 없거나 실행 위치가 달라 파일을 찾지 못하면, API가 준비되기 전에 실패할 수 있다. 변환 함수가 존재한다는 것과 시작할 때 변환이 자동 실행된다는 것은 다른 이야기다.

## JSON 응답의 자료형 확인


csv.DictReader는 첫 행의 필드 이름을 키로 사용하고 각 행을 딕셔너리로 읽는다. 이 코드에서는 숫자나 날짜를 별도로 변환하지 않는다. [Python csv 문서](https://docs.python.org/3/library/csv.html#csv.DictReader)를 기준으로 보면 일반적인 필드 값은 문자열로 들어온다.


예를 들어 식별자 0012와 가격 12000이 CSV에 있으면 둘 다 문자열로 출발할 수 있다. 하지만 이후 `pd.read`_json에는 열별 dtype을 지정하지 않는다.


[pandas의 read_json 설명](https://pandas.pydata.org/docs/reference/api/pandas.read_json.html)에 따르면 기본 경로에서 자료형 추론이 적용될 수 있다. 따라서 숫자처럼 보이는 식별자의 앞자리 0을 끝까지 보존하는지 별도 확인이 필요하다.


날짜도 같은 문제를 가진다. “2026-09-15” 같은 날짜 문자열을 해석할 때는 시간대와 기준 시각을 별도로 정해야 한다. 코드에서 데이터기준일자를 update-time으로 이름을 바꾸지만, 이름 변경 자체가 날짜 파싱이나 시간대 정규화를 수행하지는 않는다.


직렬화는 값을 전송 가능한 JSON 표현으로 옮기는 과정이다. 열 이름이나 파일 형식이 바뀌더라도 값의 의미를 정하는 규칙까지 새로 생기는 것은 아니어서, 자료형과 기준 시각을 별도 항목으로 읽었다.


## 검색 조건이 불리언 마스크가 되는 과정


검색 경로는 /test/이고, 쿼리 매개변수 이름은 코드에 적힌 그대로 colums와 search다. colums로 열을 고르고 search를 포함하는 행을 찾는다. 예를 들어 /test/?colums=menu&search=국수는 menu 열에서 국수라는 글자가 포함된 행을 고르는 요청으로 읽을 수 있다.


fillterjson 내부의 str.contains에는 regex=False가 지정되어 있다. 입력한 문자열 자체를 그대로 검색한다.


[pandas의 contains 문서](https://pandas.pydata.org/docs/reference/api/pandas.Series.str.contains.html)는 이 옵션과 결측값 처리 옵션을 따로 설명한다.

## 전역 변수를 참조하는 검색 처리


함수 이름과 인자만 보면 전달받은 데이터프레임을 검색하는 것처럼 보였다. 하지만 실제 식은 df[df2[str_parm1].str.contains(str_parm2, regex=False)]다. df_parm1은 사용하지 않고, 전역 df2에서 조건을 만든 다음 전역 df의 행을 고른다.


현재 df2는 df의 열 이름을 바꾼 결과라 인덱스가 대응하는 동안 같은 행을 고를 수 있다. 다른 데이터프레임을 인자로 전달해도 그 입력을 검색하지는 않는다. 정렬이나 행 제거가 추가되면 두 전역 변수의 대응도 달라질 수 있다. 검색 열과 반환 데이터를 하나의 명시적 입력에 묶는 방식은 이 함수를 재사용할 때 검토할 대안이다.


검색에는 menu처럼 바뀐 열 이름을 쓰지만 결과는 df에서 가져오므로 응답에는 원래 한글 열 이름이 남는다. 검색 매개변수와 응답 키의 언어가 서로 다른 구조였다. 클라이언트에서 사용할 이름도 이 대응을 기준으로 정리할 부분이다.


## 빈 검색 결과와 처리 실패를 나누기


요청에는 열 이름 허용 목록이 없다. 없는 열을 지정하면 열 접근에서 오류가 날 수 있고, 문자열 검색이 불가능한 자료형도 별도 분기가 없다. 결측값에 대한 na 값 역시 명시하지 않는다. 결측값 처리의 기본 동작은 pandas 버전과 열 자료형에 영향을 받으므로, 이 저장소의 실행 결과로 단정하기보다 작은 입력에서 확인할 조건으로 남겼다.


read_item은 선택 결과를 to_dict('records')로 바꿔 JSONResponse에 넘긴다. 빈 배열은 검색 결과가 없다는 정상 응답이 될 수 있지만, 잘못된 열이나 직렬화하기 어려운 값은 다른 문제다. 현재 코드에는 이 경우들을 사용자에게 서로 다른 오류로 설명하는 처리가 없다. 이번에는 서버를 실행해 API 성능이나 응답 성공률을 측정하지 않았다.


## API 응답 규칙의 후속 정리


짧은 코드에서 파일 읽기와 검색 응답까지 이어지는 흐름을 확인했다. 열 이름 매핑, 식별자의 문자열 보존, 빈 값의 표현, 갱신 시점은 보완할 규칙으로 남았다. 응답을 사용하는 쪽에서 값의 의미를 해석하는 데 필요한 조건들이다.


검증 입력으로는 선행 0이 있는 식별자, 빈 메뉴, 존재하지 않는 열, 결과가 없는 요청을 정리했다. 정상 배열과 잘못된 요청을 나누고, 각 경우에 표의 값이 API 응답에서도 같은 의미로 남는지 확인하는 작업이 이어진다.


## 작업을 정리하며


형식 변환의 완료 기준은 JSON이 생성되는 시점보다 값의 의미가 유지되는지에 있다. 날짜의 기준과 문자열 검색 규칙을 명시해 두면 화면과 API가 같은 값을 해석할 수 있다. 작은 원본 표와 기대 응답을 한 쌍으로 남기는 방식을 계속 쓰려 한다.
