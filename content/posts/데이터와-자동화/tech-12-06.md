표 데이터를 읽어 웹 요청에 JSON 형식으로 답하는 [`FASTAPI_PANDAS_CSV2JSON`](https://github.com/NAMUORI00/FASTAPI_PANDAS_CSV2JSON/blob/ee7ec277a5321f84da4a3424f5e41a270129fffe/main.py#L8) 저장소의 `ee7ec27` 커밋은 82줄로 이루어진 실습 코드다. 한 파일 안에 CSV 표를 JSON으로 바꾸는 함수와 파이썬의 pandas로 표를 다루는 코드, FastAPI의 요청 경로가 모두 들어 있다.


그런데 코드를 위에서 아래로 읽는 순서와 서버가 실제로 동작하는 순서는 달랐다. 빈칸이나 날짜, 숫자처럼 보이는 문자열이 파일을 변환하고 표를 읽는 단계에서 원래 뜻을 유지하는지도 코드만 봐서는 바로 드러나지 않았다. 그래서 서버가 켜질 때와 검색 요청을 받을 때 각각 어떤 코드가 실행되는지 먼저 나누어 살폈다. 그다음 열 이름을 바꾸고 값을 찾는 과정에서 데이터의 뜻이 어떻게 달라지는지 단계별로 따라가 봤다.


## 서버 시작 흐름과 파일 변환 경로


실행 흐름을 따라가려면 먼저 파일 맨 위에 적힌 변환 함수와 서버가 켜질 때 실제로 돌아가는 구간을 구분해야 한다. 코드 맨 위에는 CSV 파일을 읽어 JSON 파일로 저장하는 [`csv_to_json`](https://github.com/NAMUORI00/FASTAPI_PANDAS_CSV2JSON/blob/ee7ec277a5321f84da4a3424f5e41a270129fffe/main.py#L8) 함수가 정의되어 있다. 각 행의 열 이름과 값을 한 쌍으로 묶은 파이썬 딕셔너리로 읽어 저장하는 함수다. 그 아래에는 입력 표와 출력 파일의 위치를 지정해 이 함수를 부르는 보조 함수도 함께 들어 있다. 하지만 프로그램을 시작하는 흐름에서는 이 보조 함수를 직접 호출하지 않는다.


서버가 켜질 때 실제로 실행되는 코드는 이미 변환해 둔 JSON 파일을 pandas의 `read_json`으로 읽는 부분부터다. 코드는 행과 열로 된 표를 메모리에 담아 다루는 구조인 **데이터프레임**(DataFrame) `df`로 파일을 읽어들인 뒤 다시 파일에 쓴다. 이어서 `df`의 한글 열 이름을 `name`, `category`, `region`, `menu` 같은 영문 이름으로 바꾼 데이터프레임 `df2`를 만든다.

파일 변환 함수가 코드에 적혀 있다고 해서 서버를 띄울 때 변환이 자동으로 실행되지는 않는다. 실행 위치가 달라 파일을 찾지 못하거나 필요한 JSON 파일이 없으면, API가 준비되기 전인 모듈 시작 단계에서 바로 실패할 수 있다.


원본 CSV 파일을 수정하더라도 실행 중인 API 서버 메모리의 데이터프레임(`df`, `df2`)이 곧바로 바뀌지도 않는다. 요청이 들어올 때마다 CSV나 JSON 파일을 다시 읽는 경로가 없기 때문이다. 이 구조에서 데이터를 갱신하려면 변환 파일을 새로 만드는 작업과 서버 메모리의 데이터를 교체하는 작업을 각각 따로 처리해야 한다.


## 파일 읽기와 자료형 추론


앞 절에서 본 것처럼 데이터는 CSV에서 JSON 파일을 거쳐 데이터프레임으로 넘어오며, 이 과정에서 값의 자료형이 달라질 수 있다. 예를 들어 원본 CSV에 식별자 `0012`와 가격 `12000`이 적혀 있다고 하자. 변환 함수 안의 `csv.DictReader`는 첫 행의 필드 이름을 키(key)로 삼고 각 행을 딕셔너리로 읽는다. [Python csv 문서](https://docs.python.org/3/library/csv.html#csv.DictReader)를 기준으로 보면, 숫자나 날짜를 따로 변환하지 않는 한 일반적인 필드 값은 모두 문자열로 들어온다. 따라서 JSON 파일로 옮겨질 때까지 `0012`와 `12000`은 둘 다 문자열로 출발한다.


하지만 서버 시작 시점에 호출하는 `pd.read_json`에는 열별 자료형(`dtype`)이 지정되어 있지 않다. [pandas의 read_json 설명](https://pandas.pydata.org/docs/reference/api/pandas.read_json.html)에 따르면 기본 경로에서는 값의 생김새를 보고 자료형을 스스로 정하는 **자료형 추론**(type inference)이 일어날 수 있다. 가격 `12000`이 정수로 변환되는 것은 자연스럽지만, 숫자처럼 보이는 식별자 `0012`까지 정수로 추론되면 맨 앞의 `0`이 사라질 수 있다. 이 때문에 식별자가 응답까지 문자열로 보존되는지 별도로 확인해야 한다.


날짜 값도 같은 문제를 안고 있어서, `"2026-09-15"` 같은 날짜 문자열을 해석할 때는 시간대와 기준 시각을 따로 정해야 한다. 코드에서는 한글 열 이름인 `데이터기준일자`를 `update-time`으로 바꾼다. 하지만 열 이름을 바꾼다고 해서 문자열을 날짜로 해석하거나 시간대 기준을 맞추는 처리가 함께 이루어지지는 않는다.


![식별자 0012, 가격 12000, 날짜 2026-09-15 문자열이 pd.read_json의 자료형 추론을 거치며 정수와 시간대 미지정 값으로 바뀌는 과정](/images/notion/tech-12-06/image-2.png)


그림 2. CSV에서 문자열로 읽힌 값들이 dtype을 지정하지 않은 read_json을 거칠 때 발생할 수 있는 자료형 추론 예시.


데이터를 전송 가능한 JSON 표현으로 옮기는 **직렬화**(serialization)나 파일 형식 변환은 값을 담는 형식을 바꿀 뿐이다. 열 이름이나 파일 형식이 바뀌더라도 값의 의미를 정하는 규칙까지 새로 생기지는 않으므로, 자료형과 기준 시각은 별도 항목으로 챙겨야 한다.


## 문자열 검색과 불리언 마스크


데이터프레임 준비가 끝나면 서버는 웹 주소로 들어오는 검색 요청을 받아 조건에 맞는 행을 걸러낸다. 예를 들어 `/test/?colums=menu&search=국수`는 `menu` 열에서 `국수`라는 글자가 들어 있는 행을 고르는 요청이다. 이 요청에서 주소 경로(라우트)는 `/test/`이고, 조건을 넘기는 쿼리 매개변수는 코드에 적힌 철자 그대로 `colums`와 `search`다. `colums`로 대상 열을 고르고 `search` 문자열을 포함하는 행을 찾는다.


실제 필터링을 맡은 `fillterjson` 함수 내부의 `str.contains`에는 `regex=False`가 지정되어 있다. 검색어를 기호 규칙으로 문자열 패턴을 찾는 정규표현식으로 해석하지 않고 입력한 문자열 자체를 그대로 비교한다. [pandas의 contains 문서](https://pandas.pydata.org/docs/reference/api/pandas.Series.str.contains.html)는 이 옵션과 함께 표에서 비어 있는 칸인 **결측값**(missing value)을 다루는 옵션을 따로 설명한다.


예를 들어 `menu` 열에 `국수`, `비빔밥`, `칼국수` 세 행이 들어 있다고 하자. `str.contains`는 각 행에 `국수`가 들어 있는지를 따져 순서대로 참(`True`), 거짓(`False`), 참(`True`) 결과를 낸다. 이처럼 조건 충족 여부를 참과 거짓의 배열로 만들어 참인 위치의 행만 걸러내는 방식을 **불리언 마스크**(boolean mask)라고 한다. 마스크를 통과한 `국수`와 `칼국수` 행만 선택되어 최종 JSON 배열 응답으로 반환된다.


![menu 열의 국수, 비빔밥, 칼국수 행에 str.contains를 적용해 True, False, True 불리언 마스크를 만들고 국수와 칼국수 행만 JSON 배열로 반환하는 흐름](/images/notion/tech-12-06/image-3.png)


그림 3. 문자열 포함 여부를 불리언 마스크로 만들어 조건에 맞는 행만 걸러내는 과정. 출처: fillterjson과 read_item을 바탕으로 직접 구성.


## 전역 데이터프레임의 교차 참조


앞 절의 불리언 마스크 검색을 코드로 따라가 보면, 함수가 전달받은 표 대신 함수 바깥의 전역 변수 두 개를 섞어 쓰는 구조가 드러난다. `fillterjson` 함수는 세 인자(`df_parm1`, `str_parm1`, `str_parm2`)를 받으므로 첫 번째 인자인 표를 검색하는 것처럼 보였다. 하지만 함수 안에 적힌 실제 식은 `df[df2[str_parm1].str.contains(str_parm2, regex=False)]`다. 인자로 받은 `df_parm1`은 쓰지 않고, 전역 변수 `df2`에서 검색 조건을 만든 다음 전역 변수 `df`에서 행을 고른다.


![인자 df_parm1은 사용되지 않고 전역 df2에서 만든 행 인덱스 마스크를 전역 df에 적용해 한글 키를 가진 응답 JSON을 반환하는 구조도](/images/notion/tech-12-06/image-4.png)


그림 4. 함수 인자를 쓰지 않고 전역 변수 df2에서 검색 조건을 만든 뒤 전역 변수 df에서 한글 열 이름의 행을 꺼내는 검색 처리 구조.


현재 코드에서 `df2`는 `df`의 열 이름만 바꾼 데이터프레임이라 두 변수의 행 번호(인덱스)가 대응하는 동안에는 같은 행을 고를 수 있다. 그러나 다른 데이터프레임을 함수 인자로 전달해도 그 입력은 검색에 쓰이지 않는다. 중간에 행을 정렬하거나 지우는 작업이 추가되면 두 전역 변수의 인덱스 대응이 어긋날 수도 있다. 이 함수를 다른 곳에서도 재사용하려면 검색할 열과 반환할 데이터를 함수가 직접 넘겨받는 입력 데이터프레임 하나로 묶는 편이 낫다.


두 전역 변수를 교차 참조하기 때문에 요청과 응답의 열 이름 언어도 서로 다르다. 검색 조건은 `df2`에서 계산하므로 요청 매개변수에는 `menu`처럼 바뀐 영문 열 이름을 써야 한다. 반면 반환할 행은 `df`에서 가져오므로 응답 JSON에는 원래의 한글 열 이름이 남는다. API를 호출하는 클라이언트에서도 이 대응 관계를 기준으로 요청 매개변수와 응답 키 이름을 맞춰야 한다.


## 빈 검색 결과와 오류의 구분


걸러낸 행을 최종 응답으로 돌려줄 때는 조건에 맞는 행이 없는 정상 상황과 요청이나 데이터에 문제가 생긴 오류 상황을 구분해야 한다. 라우트 함수인 `read_item`은 선택된 행을 `to_dict('records')`로 변환해 `JSONResponse`에 그대로 넘긴다. 조건에 맞는 행이 없을 때 빈 배열(`[]`)을 돌려주는 것은 정상 응답이다. 하지만 잘못된 열 이름을 요청하거나 직렬화하기 어려운 값이 들어온 경우는 정상적인 빈 결과와 구별해야 한다.


현재 코드에는 요청 가능한 열 이름의 허용 목록이 없어서, 존재하지 않는 열을 지정하면 열 접근 단계에서 바로 오류가 날 수 있다. 문자열 검색이 불가능한 자료형을 만났을 때 따로 나누어 처리하는 코드도 없으며, 결측값을 어떻게 다룰지 정하는 `na` 인자 역시 적혀 있지 않다. 결측값 처리의 기본 동작은 pandas 버전과 열 자료형에 영향을 받기 때문에 실행 결과를 미리 단정하지 않고 작은 입력 표로 확인할 조건으로 남겼다. 잘못된 요청과 데이터 처리 실패를 사용자에게 서로 다른 오류 응답으로 안내하는 처리도 앞으로 보완할 부분이다.


## 결론


82줄의 실습 코드에서 파일 읽기부터 검색 응답까지 이어지는 흐름을 따라가며 데이터의 형태와 의미가 어떻게 달라지는지 살폈다. 서버가 켜질 때는 CSV 변환 함수가 아니라 기존 JSON 파일을 읽는 코드가 먼저 실행된다. 이때 자료형을 지정하지 않은 `pd.read_json`을 거치면서 문자열이던 숫자와 날짜의 자료형이 바뀔 수 있다. 또한 검색 함수가 영문 열 이름의 `df2`와 한글 열 이름의 `df`를 교차 참조하므로 요청 매개변수와 응답 키의 언어가 달라진다는 점도 확인했다.


이번에는 서버를 직접 실행해 API 성능이나 응답 성공률을 측정하지 않았다. 대신 열 이름 대응과 식별자의 문자열 보존, 결측값 표현, 데이터 갱신 시점처럼 응답을 쓰는 쪽에서 값의 의미를 해석할 때 필요한 조건을 추려 냈다. 다음 단계로는 맨 앞에 `0`이 있는 식별자와 비어 있는 메뉴 칸, 존재하지 않는 열 이름, 결과가 없는 검색어를 담은 작은 원본 표를 준비할 계획이다. 이 표와 기대 응답을 한 쌍으로 맞춰 보며 정상 배열과 오류 요청이 의도대로 나뉘고 표의 값 의미가 API 응답까지 그대로 유지되는지 확인하려 한다.
