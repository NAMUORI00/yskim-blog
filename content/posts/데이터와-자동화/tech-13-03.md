HanQuote는 명언 문장을 주기적으로 모아 파일에 저장하고 웹 페이지에 보여 주는 서비스다. 방문자의 웹 브라우저는 명언을 모으는 서버에 매번 요청을 보내지 않고, 사이트와 함께 올라간 데이터 파일인 JSON 파일을 그대로 읽어 화면을 그린다. 이렇게 미리 만들어 둔 파일을 그대로 보여 주는 화면을 **정적 웹 페이지**라고 부른다. 새 문장을 주기적으로 모아 정적 웹 페이지에 보여 주려면, 같은 문장이 중복해서 쌓이지 않게 걸러내고 바뀐 파일을 사이트에 다시 배포해야 한다.


앞 글에서 다룬 퀴즈 앱의 데이터 로딩 흐름에 이어, 이번에는 HanQuote의 `e6a7e19` 버전 기록을 기준으로 문장 수집부터 화면 표시까지의 과정을 따라갔다. 수집 스크립트와 화면 코드, 자동 배포 설정을 차례로 읽으며 수집과 중복 검사, 파일 쓰기, 정적 배포의 상태 변화와 예외 조건을 살폈다. 매일 실행되는 수집 작업이 실제로 성공했는지와 현재 사이트의 배포 상태는 확인 범위에 넣지 않았다.


## 문장 수집 경로와 저장 형식


문장이 화면에 오르기까지의 첫 단계는 외부 서비스나 내부 예시 목록에서 문장 후보를 가져와 일정한 형식으로 정리하는 일이다. [명언 수집 처리](https://github.com/NAMUORI00/HanQuote/blob/e6a7e197782045d4d22225772618e87e2c47f8f4/scripts/fetch_quotes.mjs) 스크립트는 먼저 외부 명언 서비스인 Quotable에 요청을 보내 무작위 문장을 받아 오는 API 경로를 호출한다. 여기서 값을 얻지 못하면 다른 API 경로를 시도하거나, 코드 안에 미리 준비해 둔 기본 예시 문장인 로컬 **시드**(seed) 자료에서 후보를 가져온다. 외부 연결 없이 동작하는 `OFFLINE_MODE`에서는 처음부터 로컬 시드 자료를 선택한다.


가져온 문장 후보는 데이터 한 건을 묶은 단위인 레코드 하나로 정리된다. 레코드 하나에는 원문, 작성자, 출처 이름, 출처 URL, 언어, 태그, 수집 시각(`fetched_at`), 중복 확인용 해시값이 들어간다. 외부 API에서 받은 문장과 로컬 시드 문장이 똑같은 레코드 형식으로 저장되므로, 정적 화면 코드는 문장이 들어온 경로를 구분하지 않고 그대로 표시한다. 반대로 파일에 새 레코드가 추가되었다는 사실만으로는 이번 실행에서 외부 API 수집이 성공했는지, 아니면 실패해서 로컬 시드로 대체되었는지 알 수 없다.


수집 도구는 새 문장을 관리용 목록 파일에 먼저 반영한 뒤, 같은 내용을 사이트 배포용 목록 파일에 복사한다. 자료 수집과 화면 표시가 파일로 나뉘어 있어, 새 문장을 저장해도 다음 배포가 끝나기 전까지는 파일과 방문자 화면 사이에 시차가 생긴다.

그림 1. 온라인 응답과 로컬 시드를 같은 레코드로 정리한 뒤 파일에 저장하는 과정. 재시도 횟수에는 제한이 있으며 마지막 화면은 별도 배포 후 반영된다. 출처: 명언 수집 처리와 사이트 코드를 바탕으로 직접 구성.


## 문장 정규화와 해시 중복 검사


앞 단계에서 가져온 문장 후보를 파일에 바로 넣으면 같은 명언이 여러 번 쌓일 수 있으므로, 수집 스크립트는 이미 저장된 문장인지 먼저 확인한다. 예를 들어 설명용 문장인 “Read  slowly”와 “ read slowly ”는 띄어쓰기 개수와 대소문자만 다를 뿐 같은 문장이다. 수집 스크립트는 이처럼 글자의 겉모습 차이를 일정한 규칙으로 통일하는 **정규화**(normalization)부터 진행한다. 원문에서 연속된 공백을 공백 하나로 줄이고 앞뒤 공백을 잘라낸 뒤 모든 알파벳을 소문자로 바꾸면, 두 문장은 모두 “read slowly”가 된다. 반면 “Read slowly.”는 끝에 붙은 마침표가 지워지지 않고 그대로 남아 “read slowly.”가 된다. 문장 부호는 건드리지 않고 공백과 대소문자 차이만 없애 같은 문장인지 비교하는 방식이다.


정규화를 마친 문자열은 [Node.js crypto 문서](https://nodejs.org/api/crypto.html#cryptocreatehashalgorithm-options)의 기능으로 일정한 길이의 고유한 값을 뽑아내는 **해시**(hash) 계산에 들어간다. SHA-256 방식으로 계산한 이 해시값은 입력 문자열이 같으면 언제나 똑같이 나온다. 정규화로 같은 해시 입력이 된 두 문장은 해시값도 같아 중복으로 걸러지고, 마침표가 붙은 문장은 다른 해시 입력으로 처리된다.


![공백과 대소문자만 다른 두 문장은 정규화 후 동일한 해시 입력이 되고 마침표가 붙은 문장은 다른 해시 입력이 되는 비교 도식](/images/notion/tech-13-03/image-2.png)


그림 2. 정규화가 흡수하는 차이와 남겨 두는 차이. 문장은 중복 규칙을 설명하기 위해 만든 예제이며, 직접 구성한 도식이다.


이때 해시값을 계산하는 입력에는 원문 글자만 들어가고 작성자나 출처 정보는 빠진다. 같은 문장이 서로 다른 작성자 이름으로 기록되어도 이 기준에서는 해시값이 같아 하나로 묶인다. 문장 중복은 줄일 수 있지만, 같은 문장에 작성자 표기가 부딪히는 사례를 남겨 두고 검토하려면 원문 해시값 외에 추가 정보가 필요하다. 해시값이 일치하는지와 출처가 믿을 만한지를 별개의 문제로 나누어 읽은 이유다.


새 문장의 해시값을 대조할 기존 목록의 해시 집합은 파일에 이미 저장된 레코드들의 `hash` 항목을 모아서 만든다. 만약 이전에 저장된 레코드 가운데 해시값이 빠진 항목이 있다면 수집 단계의 중복 검사에서 걸러지지 않으므로 별도의 보완 처리가 필요하다.


저장소에는 기존 목록을 정리하기 위한 [중복 문장 정리](https://github.com/NAMUORI00/HanQuote/blob/e6a7e197782045d4d22225772618e87e2c47f8f4/scripts/deduplicate.mjs) 스크립트가 따로 있다. 이 스크립트는 저장된 레코드들의 원문에서 해시값을 다시 계산하지만, 실제로 중복된 문장이 발견됐을 때만 파일을 새로 쓴다. 중복된 문장이 없는 자료에서 빠진 해시값까지 언제나 채워 저장한다고 볼 수는 없었다.


## 임시 파일 쓰기와 두 목록의 일관성


중복 검사를 통과한 새 문장은 기존 목록과 합쳐 관리용 JSON 파일과 사이트용 JSON 파일에 차례로 기록한다. 파일 하나를 쓸 때는 원래 파일을 곧바로 덮어쓰지 않고, 임시 파일에 내용을 먼저 다 쓴 다음 원래 파일 이름으로 바꾸어 교체한다. 파일을 쓰는 도중에 중간 상태로 읽히는 상황을 줄이려는 방식으로 볼 수 있다.


하지만 파일 하나는 이렇게 안전하게 교체하더라도, 관리용 파일과 사이트용 파일 두 개는 순서대로 따로 저장한다. 첫 번째 관리용 파일을 쓴 뒤 두 번째 사이트용 파일을 쓰는 과정에서 실패하면 두 파일의 내용이 서로 달라질 수 있다.


![관리용 JSON 갱신 뒤 사이트용 JSON 쓰기에 실패하면 두 파일의 내용이 달라지는 순차 저장 구조도](/images/notion/tech-13-03/image-3.png)


그림 3. 개별 파일은 임시 파일로 교체해 쓰더라도 관리용 파일과 사이트용 파일을 순서대로 별도 저장할 때 발생할 수 있는 불일치 구조.


기존 JSON 파일을 읽어 오는 `readJsonArray` 함수에도 짚어 볼 조건이 있다. 이 함수는 파일이 아예 없을 때와, 파일에 적힌 글자를 데이터 목록으로 읽어 내는 JSON **파싱**(parsing)에 실패했을 때 모두 빈 목록(빈 배열)을 돌려준다. 처음 실행할 때 파일이 없어도 시작하기는 간단하지만, 기존 파일이 손상되어 읽기에 실패했을 때도 자료가 없는 상태로 이어져 그동안 쌓아 둔 목록을 잃을 수 있다. 새로 설치해 파일이 없는 상태와 읽기 실패 상태를 분리하는 처리는 모아 둔 목록을 보존하기 위한 보완 항목으로 남았다.


## 배포 작업별 입력 파일과 커밋 시점


파일 저장이 끝나면 자동 실행 도구인 GitHub Actions의 [정기 수집과 배포 작업](https://github.com/NAMUORI00/HanQuote/blob/e6a7e197782045d4d22225772618e87e2c47f8f4/.github/workflows/schedule.yml) 워크플로가 바뀐 파일을 사이트에 올리는 후속 단계를 진행한다. 먼저 수집 작업은 변경된 데이터를 저장소에 기록하는 **커밋**(commit)을 만든다. 이어서 화면 파일이 담긴 `site` 폴더를 작업 단계 사이에 전달하는 결과물 묶음인 Pages용 **아티팩트**(artifact)로 올린다.


뒤이어 실행되는 GitHub Pages 배포 작업은 이 아티팩트를 그대로 받아 사이트를 배포한다. [GitHub Pages 공식 문서](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)에서도 아티팩트 업로드와 배포를 연결하는 같은 방식을 설명한다.


반면 선택적으로 켜는 Cloudflare 배포 작업은 앞 단계의 아티팩트를 받지 않고, 저장소에서 파일을 다시 꺼내 오는 체크아웃(`checkout`)을 실행한다. GitHub Actions에서 [checkout의 기본 동작](https://github.com/actions/checkout)은 워크플로를 처음 일으킨 커밋을 기준으로 파일을 가져오는 것이다.


![수집 작업이 만든 아티팩트를 쓰는 GitHub Pages 배포와 워크플로 시작 커밋을 다시 체크아웃하는 Cloudflare 배포의 차이 도식](/images/notion/tech-13-03/image-4.png)


그림 4. 수집 작업이 올린 아티팩트를 그대로 받는 GitHub Pages 배포와 저장소를 다시 체크아웃하는 Cloudflare 배포의 입력 경로 비교.


앞선 수집 작업이 실행 도중에 새로 커밋한 데이터가 별도의 Cloudflare 배포 작업에도 곧바로 포함되는지는 추가 확인이 남았다. 같은 워크플로 실행 안에 묶여 있더라도 각 배포 작업이 어떤 시점의 커밋과 파일을 입력받는지에 따라 화면에 반영되는 결과가 달라질 수 있다.


## 화면의 갱신 시각과 원문 표시


배포가 끝난 뒤 방문자가 보는 [명언 목록 화면](https://github.com/NAMUORI00/HanQuote/blob/e6a7e197782045d4d22225772618e87e2c47f8f4/site/index.html)은 배포된 JSON 파일을 읽어 수집 시각(`fetched_at`) 기준 최신순(내림차순)으로 정렬한 뒤 최대 열 개를 표시한다. 화면에 나오는 마지막 갱신 시각도 가장 최근 레코드의 `fetched_at` 값이다. 즉, 이 시각은 사이트가 배포된 시점이 아니라 수집 스크립트가 문장을 파일에 기록한 시점이다.


화면 위쪽에는 원문과 번역을 함께 소개하는 문구가 남아 있지만, 실제 명언 카드에서 읽는 항목은 원문을 담은 `text_original`뿐이다. 저장소의 안내 문서인 README도 번역 기능이 꺼져 있다고 설명한다. 화면 문구만 보고 번역 결과까지 만들어지는 서비스로 범위를 넓히지 않고, 코드에서 확인된 원문 수집과 표시 경로만 분석 대상으로 삼았다.


## 결론


HanQuote의 `e6a7e19` 커밋 코드를 따라가며 문장 수집과 중복 검사, 파일 저장, 배포 설정이 정적 화면 갱신으로 이어지는 경로를 확인했다. 외부 API 응답과 로컬 시드가 같은 레코드 형식으로 묶이고, 공백과 대소문자만 정리한 원문 해시값으로 중복을 걸러 두 개의 JSON 파일에 차례로 저장된다. 화면의 마지막 갱신 시각은 배포 시점이 아니라 최근 문장의 수집 시각(`fetched_at`)이며, 명언 카드는 번역 없이 원문(`text_original`)만 보여 준다.


화면 갱신이 멈췄을 때는 외부 자료 수집 성공, 로컬 시드 대체, 중복으로 인한 건너뜀, 파일 읽기 실패를 실행 기록에서 나누어 확인해야 한다. 원문을 가져온 시점과 방문자가 보는 배포 시점을 구분하고, 관리용 JSON과 사이트용 JSON, 배포 파일의 해시값을 차례로 대조하면 갱신이 멈춘 단계를 좁힐 수 있다. 다만 매일 실행되는 수집 작업의 실제 성공 여부와 현재 사이트의 배포 상태는 이번 확인 범위에 넣지 않았다. 수집 작업이 실행 도중에 새로 커밋한 데이터가 저장소를 다시 체크아웃하는 Cloudflare 배포에 곧바로 포함되는지도 추가 확인이 남았다. 오래된 레코드에 빠진 해시값을 채우고 파일 없음과 읽기 실패를 분리하는 처리도 앞으로 보완할 과제다. 다음 글은 지역별 공공데이터 파일과 지도 API가 만나는 GoodPriceJeju로 이어진다.
