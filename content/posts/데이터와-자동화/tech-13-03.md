HanQuote에서는 수집한 문장을 JSON으로 저장하고 정적 페이지에서 보여 주는 흐름을 구성했다. 같은 문장의 반복 수집과 화면 갱신 시점이 맞물리므로, 정규화, 중복 검사, 파일 저장, 배포를 단계별로 나누어 정리했다.


## 구현과 확인 과정


HanQuote의 수집 스크립트와 정적 화면을 함께 읽었다. 스크립트가 JSON 파일을 만들고 브라우저는 배포된 파일을 읽는 구조였다. 앞 글의 문제 데이터 로딩과 연결해 수집 시점과 표시 시점 사이의 흐름을 정리했다.


e6a7e19 커밋에서 수집, 중복 검사, 파일 쓰기, 배포 설정을 따라갔다. 문장 하나가 수집된 뒤 화면에 표시되기까지의 상태 변화가 이번 기록의 범위다. 매일 수집이 성공했는지와 현재 배포 상태는 확인하지 않았다.


## 외부 응답을 먼저 파일로 남기는 구성


[명언 수집 처리](https://github.com/NAMUORI00/HanQuote/blob/e6a7e197782045d4d22225772618e87e2c47f8f4/scripts/fetch_quotes.mjs)는 Quotable의 무작위 문장 경로를 시도하고, 값을 얻지 못하면 다른 API 경로 또는 미리 준비해 둔 예시 문장 목록에서 후보를 가져온다. OFFLINE_MODE에서는 처음부터 시드 자료를 선택한다.


레코드에는 원문, 작성자, 출처 이름, 출처 URL, 언어, 태그, fetched_at, 해시가 들어간다. 외부 API와 로컬 시드가 같은 형식으로 저장되어 화면은 입력 경로와 무관하게 표시할 수 있다. 따라서 레코드 생성만으로 이번 실행의 외부 자료 수집 성공까지 확인되지는 않는다.


방문자의 브라우저는 수집 서버에 매번 요청하지 않고, 사이트에 함께 배포된 명언 목록을 읽는다. 수집 도구는 관리용 목록을 갱신한 뒤 같은 내용을 사이트용 목록에 복사한다. 자료 수집과 화면 표시가 분리되어 있지만, 수집 후 다음 배포까지는 새로 저장한 문장과 방문자가 보는 문장 사이에 시차가 생긴다.

그림 1. 온라인 응답과 로컬 시드를 같은 레코드로 정리한 뒤 파일에 저장하는 과정. 재시도 횟수에는 제한이 있으며 마지막 화면은 별도 배포 후 반영된다. 출처: 명언 수집 처리와 사이트 코드를 바탕으로 직접 구성.


## 문장을 같다고 보는 기준부터 정하기


중복 검사는 원문에서 연속 공백을 하나로 줄이고 앞뒤 공백을 없앤 뒤 소문자로 바꾸는 것으로 시작한다. 그 결과를 SHA-256으로 해시한다. [Node.js crypto 문서](https://nodejs.org/api/crypto.html#cryptocreatehashalgorithm-options)의 해시 기능을 사용한 부분이다.


설명용 문장 “Read  slowly”와 “ read slowly ”는 정규화 뒤 같은 입력이 된다. 반면 “Read slowly.”는 마침표가 남으므로 다른 입력이다. 정한 정규화 규칙 아래에서 텍스트의 일치 여부를 검사하는 구조다.


![13-03-02.png](/images/notion/tech-13-03/image-2.png)


그림 2. 정규화가 흡수하는 차이와 남겨 두는 차이. 문장은 중복 규칙을 설명하기 위해 만든 예제이며, 직접 구성한 도식이다.


해시 입력에는 작성자나 출처가 없다. 같은 문장이 다른 작성자로 기록되어도 이 기준에서는 하나로 묶일 수 있다. 텍스트 중복은 줄일 수 있지만 저자 표기의 충돌을 보존해 검토하는 데는 추가 정보가 필요하다. 해시 일치와 출처 신뢰도를 따로 읽은 이유다.


또한 기존 목록의 해시 집합은 이미 저장된 hash 필드에서 만든다. 해시가 빠진 기존 레코드는 별도의 보완 처리가 필요하다.


별도의 [중복 문장 정리](https://github.com/NAMUORI00/HanQuote/blob/e6a7e197782045d4d22225772618e87e2c47f8f4/scripts/deduplicate.mjs)는 원문에서 해시를 다시 계산하지만, 실제 중복이 발견됐을 때만 파일을 쓴다. 중복이 없는 자료의 누락 해시까지 반드시 채워 저장한다고 설명할 수는 없었다.


## 원자적 파일 쓰기와 두 파일의 일관성


파일 쓰기는 임시 파일에 내용을 쓴 다음 이름을 바꾸는 방식이다. 파일 하나를 중간 상태로 읽는 상황을 줄이려는 구성으로 해석할 수 있다. 그러나 관리용 파일과 사이트용 파일은 순서대로 별도 저장한다. 첫 파일을 쓴 뒤 두 번째 쓰기에 실패하면 둘의 내용이 달라질 수 있다.


readJsonArray는 파일 부재와 JSON 파싱 실패에 모두 빈 배열을 반환한다. 첫 실행을 시작하기는 간단하지만 기존 파일이 손상된 경우에도 자료가 없는 상태로 이어질 수 있다. 새 설치와 읽기 실패의 상태 분리는 축적한 목록을 보존하기 위한 보완 항목으로 남았다.


## 배포 작업의 입력 파일도 같은지 확인하기


[정기 수집과 배포 작업](https://github.com/NAMUORI00/HanQuote/blob/e6a7e197782045d4d22225772618e87e2c47f8f4/.github/workflows/schedule.yml)은 수집 후 변경된 데이터를 커밋하고 site 폴더를 Pages 아티팩트로 올린다.


GitHub Pages 배포 작업은 이 아티팩트를 사용한다. [GitHub Pages 공식 문서](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)에서도 업로드와 배포를 연결하는 구성을 설명한다.


선택적으로 켜는 Cloudflare 작업은 같은 아티팩트를 받지 않고 저장소를 다시 체크아웃한다. [checkout의 기본 동작](https://github.com/actions/checkout)은 워크플로를 일으킨 커밋을 기준으로 한다.


앞 작업이 새로 커밋한 데이터가 별도 배포 작업에도 포함되는지는 추가 확인이 남았다. 같은 워크플로 실행이라도 각각 어떤 커밋과 파일을 입력받는지에 따라 결과가 달라질 수 있다.


## 화면에 표시하는 갱신 시각


[명언 목록 화면](https://github.com/NAMUORI00/HanQuote/blob/e6a7e197782045d4d22225772618e87e2c47f8f4/site/index.html)은 fetched_at 내림차순으로 정렬해 최대 열 개를 표시한다.


화면의 마지막 갱신도 가장 최근 레코드의 fetched_at이다. 이 시각은 수집 스크립트의 기록 시점이다.


상단에는 원문과 번역을 소개하는 문구가 남아 있지만 실제 카드에서 읽는 필드는 text_original이다. README도 번역 비활성화를 설명한다. 화면 문구만 보고 번역 결과까지 생성되는 서비스로 확대하지 않고, 확인된 원문 수집과 표시 경로를 범위로 삼았다.


수집 성공, 시드 대체, 중복으로 추가 없음, 파일 읽기 실패는 실행 기록에서 나누어 확인할 상태로 정리했다. 관리용 JSON, 사이트용 JSON, 배포 파일의 해시를 대조하면 갱신이 멈춘 단계도 좁힐 수 있다. 다음 글은 지역별 공공데이터 파일과 지도 API가 만나는 GoodPriceJeju로 이어진다.


## 작업을 정리하며


수집 자동화는 원문을 가져오는 시점과 독자가 보는 시점을 함께 기록해야 이해하기 쉽다. 텍스트 정규화와 해시 규칙을 고정하고 저장, 배포 상태를 따로 남기면 변경 원인을 추적할 수 있다. 오래된 레코드의 해시 보완도 같은 데이터 계약 안에서 다루려 한다.
