센서가 14:00:03에 온도 25.1°C를 재고, 서버는 그 값을 14:00:07에 받는 상황이 있다. 센서가 값을 잰 순서와 서버에 도착한 순서가 다르면, 두 시각이 모두 있어야 실제 온도 변화를 제대로 읽을 수 있다. 센서 데이터를 저장하고 평균을 계산할 때는 기준 시각뿐 아니라 시각 숫자의 단위, 빠진 값의 해석, 늦게 도착한 데이터의 반영 기준도 결과값을 바꾼다. 이 글에서는 네 가지 기준에 따라 기록되는 시각과 계산 결과가 어떻게 달라지는지 구체적인 값으로 비교한다.


## 측정 시각과 수집 시각


네 가지 기준 가운데 가장 먼저 구분할 것은 데이터가 이동하며 남기는 세 가지 시각이다. 센서가 값을 실제로 만든 순간을 **측정 시각**(event time), 데이터가 서버에 들어온 시각을 **수집 시각**(ingestion time)이라 한다. 여기에 평균 계산 같은 특정 연산이 실제로 실행되는 **처리 시각**(processing time)이 더해진다. 서버에 들어온 데이터가 대기열(메시지 큐)에서 차례를 기다리면 수집 시각과 처리 시각 사이에도 간격이 생긴다.


센서가 네트워크가 없는 상태에서 내부의 로컬 저장소에 값을 기록해 두었다가 나중에 한꺼번에 보내면, 측정 시각과 수집 시각의 차이는 수 분에서 수 시간까지 벌어진다. 따라서 데이터를 조회할 때는 분석 목적에 맞는 기준 시각(시간축)을 먼저 정해야 한다. "14시의 온도"처럼 실제 현상의 변화를 보려면 측정 시각으로 정렬해야 하고, "서버 부하 분석"처럼 시간대별로 들어오는 데이터 양을 보려면 수집 시각을 쓰는 편이 맞다.


측정 순서와 도착 순서가 다르면 같은 값으로도 변화의 흐름이 다르게 보인다. 센서와 서버의 시계가 서로 맞춰져 있다고 가정하고, 센서 하나가 차례로 보낸 온도 값 세 건을 비교하면 다음과 같다.


| 값         | 측정 시각    | 수집 시각    |
| --------- | -------- | -------- |
| A: 24.8°C | 14:00:00 | 14:00:02 |
| B: 25.1°C | 14:00:05 | 14:00:14 |
| C: 25.0°C | 14:00:10 | 14:00:11 |


측정 시각 순서로 보면 A → B → C이지만, 수집 시각 순서로 보면 A → C → B다. 네트워크 전달 경로가 달랐거나, B 전송이 실패해 다시 시도하는 사이에 C가 먼저 도착했을 수 있다.


이 데이터를 수집 시각 순서대로 그리면 온도가 24.8°C → 25.0°C → 25.1°C로 계속 올라가는 것처럼 보인다. 반대로 측정 시각 기준으로 그리면 24.8°C → 25.1°C → 25.0°C가 되어 온도가 올랐다가 내려간다.

그림 1. 값 B의 전송 지연으로 측정 순서(A → B → C)와 수집 순서(A → C → B)가 달라지는 설명용 예제.


## 타임스탬프 단위 설정


기준 시각을 정했더라도, 시각을 숫자로 저장할 때 단위가 어긋나면 데이터가 전혀 다른 시점에 기록된다. 컴퓨터는 1970년 1월 1일 00:00:00 UTC부터 흐른 시간을 숫자로 나타낸 유닉스 시각을 타임스탬프로 자주 쓴다. 시간순으로 데이터를 저장하는 시계열 데이터베이스 InfluxDB의 입력 형식(line protocol)은 이 타임스탬프를 나노초(ns, 10억분의 1초) 단위로 받는다. 시간 단위를 지정하는 파라미터인 precision을 생략하면 `1631700000`이라는 값을 기본값인 나노초로 해석한다. 이 값을 초(s) 단위로 넣으려 했다면 원래 의도한 시각은 2021-09-15 10:00:00 UTC인데, 나노초로 읽히면서 1970-01-01 00:00:01 부근이 된다.


직접 나눗셈으로 날짜를 계산해 보면 단위에 따른 시각 차이가 바로 드러난다. 하루는 86,400초이므로 `1631700000`을 초로 해석하면 `1631700000 ÷ 86400 ≈ 18885일 ≈ 2021-09-15`다. 같은 숫자를 나노초로 해석하면 `1631700000 ÷ 1000000000 ≈ 1.63초 → 1970-01-01 00:00:01`에 머문다.


![타임스탬프 1631700000을 초 단위로 지정하면 2021-09-15가 되고 단위를 생략해 나노초로 읽히면 1970-01-01이 되는 비교 도식](/images/notion/tech-k37/image-2.png)


그림 2. InfluxDB에 타임스탬프 1631700000을 넣을 때 단위(precision) 설정에 따라 해석된 시각이 달라지는 계산 예.


똑같은 타임스탬프 숫자가 단위 설정 하나에 따라 약 51년이나 차이 나는 시점으로 기록된다. 시계열 데이터베이스에 값을 넣을 때 precision 설정을 빠뜨리면 최근 그래프가 아니라 1970년대에 점 하나가 찍힌다. [InfluxDB line protocol 문서](https://docs.influxdata.com/influxdb/v2/reference/syntax/line-protocol/)에서는 초, 밀리초, 마이크로초, 나노초 네 가지 단위를 명시하도록 안내한다.


## 결측값과 0의 구분


시각과 단위를 맞춰 저장했더라도, 중간에 데이터가 빠져 비어 있는 **결측값** 구간을 만날 수 있다. 앞선 센서가 5초 간격으로 값을 보내다가 14:00:15에 값이 없다면 세 가지 해석이 가능하다.

1. 하드웨어 문제로 센서가 측정하지 못했다.
2. 센서는 측정했지만 네트워크 문제로 전송에 실패했다.
3. 측정값이 0이고, 수집 규칙에서 0을 생략했다.

세 번째처럼 측정값 0을 생략한다는 수집 규칙이 있는지 따로 확인해야 하며, 이런 규칙이 없다면 값이 오지 않은 상태를 0으로 해석할 근거는 없다. 결측이 발생한 원인은 센서 상태와 수집 로그 같은 추가 정보로 구분한다.


저장소에는 결측 구간에 행 자체가 없거나, 비어 있음을 뜻하는 null이 들어가거나, 숫자 0이 들어가는 식으로 서로 다르게 남을 수 있다. 이때 결측의 의미를 어떻게 정하느냐에 따라 평균 같은 통계값이 바로 달라진다. 앞서 도착한 세 온도 `[24.8, 25.1, 25.0]`만 모아서 계산하면 평균은 24.97이다. 만약 빠진 값을 0으로 채워 `[24.8, 25.1, 25.0, 0]`으로 만들면 평균은 18.73으로 떨어진다.


![14:00:15 결측값을 제외하면 평균이 24.97°C이지만 0으로 채우면 18.73°C로 낮아지는 비교 도식](/images/notion/tech-k37/image-3.png)


그림 3. 14:00:15의 결측값을 계산에서 제외할 때와 0으로 채울 때 평균 온도가 달라지는 계산 예.


모니터링 시스템인 Prometheus는 시간순 데이터 흐름(시계열)이 끊겼을 때 이를 구분하려고 staleness marker라는 표시를 따로 둔다. 주기적으로 데이터를 가져오던(scrape) 대상이 이전에 보고하던 시계열을 더 이상 반환하지 않으면, Prometheus는 해당 시계열을 오래된 상태(stale)로 표시한다. 이렇게 표시된 시계열은 이후 데이터를 조회(쿼리)할 때 값을 반환하지 않는다. 또한 [Prometheus querying basics 문서](https://prometheus.io/docs/prometheus/latest/querying/basics/)에 따르면 과거 데이터를 되돌아보는 기본 lookback 기간은 5분이다. 조회 시점 기준 이 5분 안에 새로 들어온 값(샘플)이 없으면 그 데이터는 결과에서 제외한다.


## 늦게 도착한 값과 워터마크


값이 끝내 오지 않는 결측과 달리, 앞선 표의 값 B(측정 시각 14:00:05, 수집 시각 14:00:14)처럼 데이터가 9초 늦게 도착하는 경우도 있다. 일정한 시간 구간(윈도우)별로 데이터를 모아 계산하는 시스템은 끝없이 기다릴 수 없으므로, "14:00:05 이전의 데이터는 이제 다 도착했다"라고 판단할 시점이 필요하다. 실시간 데이터 처리 도구인 Apache Flink는 이 판단을 **워터마크**(watermark)라는 구조로 처리한다.


워터마크는 측정 시각(event time) 처리가 몇 시 데이터까지 진행되었는지를 나타내는 기준점이다. 워터마크가 시간 구간의 종료 시각을 넘으면 시스템은 그 구간의 계산 결과를 내보낼 수 있다. 다만 워터마크보다 이른 측정 시각을 가진 데이터가 뒤늦게 도착할 가능성은 남으므로, 이후 도착한 데이터는 별도의 지연 정책으로 다룬다.


예를 들어 지금까지 관측한 가장 늦은 측정 시각에서 2초를 뺀 시각을 워터마크로 삼는 규칙을 가정한다. 측정 시각이 14:00:10인 C가 먼저 도착하면 워터마크는 2초를 뺀 14:00:08로 앞으로 나아간다. 그 뒤 측정 시각이 14:00:05인 B가 도착하면 시스템은 B를 워터마크(14:00:08)보다 이른 지연 데이터로 취급한다.


![측정 시각 14:00:10인 C가 워터마크를 14:00:08로 갱신한 뒤 측정 시각 14:00:05인 B가 도착해 늦은 데이터 정책으로 처리되는 흐름도](/images/notion/tech-k37/image-4.png)


그림 4. 최대 관측 시각 14:00:10에서 2초를 뺀 14:00:08을 워터마크로 사용하는 가상 정책에서 뒤늦게 도착한 B를 처리하는 직접 작성 도식.


뒤늦게 도착한 B를 해당 시간 구간에서 받아들여 계산 결과를 갱신할지, 아니면 이전 상태를 보존하지 않고 버릴지는 추가 설정으로 정한다. 마감 뒤에도 지연 데이터를 얼마나 더 기다려 줄지 정하는 **허용 지연**(allowed lateness)과 재계산 조건인 트리거 설정에 따라 처리 방식이 달라진다. [Flink 공식 문서](https://nightlies.apache.org/flink/flink-docs-stable/docs/concepts/time/)에서는 event time과 processing time의 구분, 워터마크를 만드는 방식을 설명한다.


## 결론


센서 데이터를 수집해 계산할 때는 기준 시각, 타임스탬프 단위, 결측값 처리, 지연 데이터 마감 기준이라는 네 가지 설정이 결과값을 직접 바꾼다. 측정 시각과 수집 시각 중 무엇을 고르느냐에 따라 온도 변화의 순서가 달라지고, 타임스탬프 단위(precision)를 생략하면 2021년의 시각이 1970년으로 기록된다. 빠진 값을 제외할지 0으로 채울지에 따라 평균 온도가 24.97°C에서 18.73°C로 달라지며, 늦게 도착한 값의 반영 여부는 워터마크와 허용 지연 설정이 결정한다.


이 글의 예제는 센서와 서버의 시계가 정확히 맞춰져 있다고 가정한 상태에서 각 기준의 영향을 확인했다. 워터마크 지연 설정 역시 대기 시간을 무작정 짧게 하거나 길게 잡기보다, 지연으로 빠지는 데이터 비율과 결과 확정까지 걸리는 시간을 나누어 비교해 볼 문제다. 여러 센서가 함께 데이터를 보낼 때 서로 다른 센서 시계의 기준점과 동기화 오차를 어떻게 보정할지는 다음 확인 과제로 남는다.
