파일이나 메시지를 보낼 때 중간에 내용이 바뀌었는지 확인하려고 해시값을 함께 붙이는 경우가 있다. 하지만 전송 경로에서 데이터를 가로채 고칠 수 있는 상대는 바꾼 메시지에 맞춰 해시값까지 새로 계산해 바꿔치기할 수 있다. 단순한 해시값만으로는 메시지가 원래 보낸 그대로인지 보증하기 어렵다.


**HMAC**(Hash-based Message Authentication Code)은 해시 계산에 송신자와 수신자만 아는 공유 비밀키를 넣어 이 문제를 해결한다. 이 글에서는 HMAC이 인증 태그를 만드는 두 단계 해시 구조와 바이트 단위 검증 예제, 그리고 변조 검사의 한계를 다룬다.


## 비밀키와 메시지의 두 단계 해시 구조


공유 비밀키로 메시지 변경을 막으려면 해시 계산의 어느 위치에 비밀키를 넣을지 정해야 한다. [RFC 2104의 정의](https://www.rfc-editor.org/rfc/rfc2104.html#section-2)를 보면 HMAC은 해시 함수 H, 메시지 M, 블록 길이에 맞춘 키 K′를 두 번의 해시 계산에 사용한다. 수식에서 $\oplus$는 두 비트가 서로 다를 때 1이 되는 비트 단위 배타적 논리합(XOR)이고, $\parallel$는 두 **바이트열**을 순서대로 이어 붙이는 연산이다.


$$
\operatorname{HMAC}_K(M)=H((K'\oplus opad)\parallel H((K'\oplus ipad)\parallel M))
$$


먼저 공유 비밀키 K를 해시 함수가 데이터를 묶어 처리하는 단위인 블록 길이에 맞춰 K′로 정리한다. 원래 키가 블록 길이보다 길면 먼저 해시해 줄이고, 짧으면 오른쪽을 0으로 채워 블록 길이에 맞춘다. 수식의 ipad와 opad는 각각 0x36과 0x5c 바이트를 블록 길이만큼 반복한 상수다.


계산은 내부 해시와 외부 해시 두 단계로 나뉜다. 먼저 K′와 ipad를 XOR한 값 뒤에 메시지 M을 이어 붙여 내부 해시를 계산한다. 이어서 K′와 opad를 XOR한 값 뒤에 방금 구한 내부 해시 결과를 이어 붙여 외부 해시를 계산하면 최종 인증 태그가 나온다. 이때 해시 함수의 블록 길이와 내부 해시의 출력 길이는 서로 다른 값이다. 오른쪽에 0을 채워 블록 길이를 맞추는 과정은 처음 키 K′를 정리할 때만 쓰인다. 내부 해시의 출력 결과에는 별도의 0 패딩을 더하지 않고 그대로 외부 해시 입력에 이어 붙인다.

## 태그 생성과 바이트 단위 검증


두 단계 해시 구조로 만든 인증 태그는 송신 측과 수신 측이 같은 비밀키로 계산한 결과를 대조할 때 검증된다. 이전 노트에 남겨 둔 Python 예제는 호출자가 키와 메시지를 제공하는 형태였다. 이번에는 송신 측이 만든 태그와 수신 측이 다시 계산한 결과를 대조해 검증하는 과정까지 한 예제로 묶었다.


```python
import hashlib
import hmac
import secrets

key = secrets.token_bytes(32)  # 설명용: 실제 서비스의 키 전달 과정은 생략
message = b"amount=100"

received_tag = hmac.new(key, message, hashlib.sha256).digest()

def verify(payload, tag):
    expected = hmac.new(key, payload, hashlib.sha256).digest()
    return hmac.compare_digest(expected, tag)

print(verify(message, received_tag))
print(verify(b"amount=900", received_tag))
```


이 예제를 실행하면 원래 메시지인 `b"amount=100"`은 `True`, 숫자만 바꾼 `b"amount=900"`은 `False`가 출력된다. 실행할 때마다 무작위 키를 새로 만들기 때문에 태그를 고정된 값과 비교하지 않고 그때 생성한 `received_tag`와 비교했다. 실제 운영 서비스에서는 양쪽이 이 비밀키를 안전하게 공유하고 주기적으로 갱신하는 별도 과정이 필요하다.


![원본 바이트열 b"amount=100"은 compare_digest 비교 결과 True가 되고, 변경된 바이트열 b"amount=900"은 False가 되는 비교 도식](/images/notion/hmac-message-verification/image-2.png)


그림 2. Python 예제에서 원본 메시지와 변경된 메시지 바이트를 각각 검증했을 때의 결과 비교.


예제의 `b"amount=100"`처럼 HMAC은 눈에 보이는 문자열이 아닌 실제 바이트열을 기준으로 태그를 계산한다. 사람 눈에는 내용이 같아 보여도 공백이나 줄바꿈, 문자 인코딩이 바뀌면 바이트열이 달라져 다른 태그가 나온다. JSON 데이터를 인증할 때도 데이터를 전송 형태로 바꾸는 **직렬화** 결과를 어떻게 맞출지 먼저 정해야 한다. 전송받은 원시 본문을 그대로 검증할지, 필요한 필드를 뽑아 다시 조합해 검증할지에 따라 양쪽이 계산에 넣을 바이트열 규칙을 미리 맞춰 두어야 한다.


태그를 대조할 때는 일반적인 문자열 비교 대신 [Python의 compare_digest](https://docs.python.org/3.13/library/hmac.html#hmac.compare_digest)를 사용했다. 두 인자는 반드시 같은 자료형과 형식으로 맞춰야 한다. 이 예제에서는 양쪽 모두 `bytes`를 넣었으며, 만약 태그를 16진수(hex) 문자열로 바꾸어 전송한다면 수신 측에서도 그 형식에 맞춰 해석한 뒤 비교해야 한다.


## 변조 검사의 한계와 재전송 문제


바이트 단위로 태그를 비교하면 메시지가 중간에 바뀌었는지는 확인할 수 있지만 모든 보안 문제를 해결하지는 못한다. HMAC은 메시지 변조 여부를 확인할 뿐 메시지 내용 자체를 숨기지는 않는다. 또한 공유키를 가진 송신자와 수신자 양쪽 모두 유효한 태그를 만들 수 있으므로, 공개키 전자서명처럼 제삼자에게 작성자를 입증하는 수단으로도 바로 사용할 수 없다.


메시지 변조 검사와 이전 메시지를 다시 보내는 **재전송**(replay) 차단은 서로 다른 조건이다. 위 예제의 `verify` 함수에 똑같은 메시지와 태그를 두 번 넣으면 두 번 모두 `True`가 나온다. 메시지와 태그의 짝이 맞기만 하면 이전에 보냈던 요청이 그대로 다시 들어와도 유효한 것으로 통과하기 때문이다.


![1차 전송된 메시지와 태그 쌍을 그대로 다시 보내는 동일 요청 재전송 시 verify 함수가 두 번 모두 True를 반환하는 흐름도](/images/notion/hmac-message-verification/image-3.png)


그림 3. 동일한 메시지와 태그를 다시 보냈을 때 변조 검사만으로는 재전송 여부를 구분하지 못하는 흐름.


웹훅처럼 같은 경로로 요청이 재전송될 수 있는 환경에서는 이 문제를 막을 추가 장치가 필요하다.


## 결론


지금까지 공유 비밀키를 결합하는 HMAC의 두 단계 해시 구조와 바이트 단위 검증 과정을 확인했다. HMAC은 블록 길이에 맞춘 키를 ipad, opad와 각각 XOR해 내부 해시와 외부 해시를 계산한다. 송신 측과 수신 측이 바이트열 규칙과 태그 형식을 맞춰 대조하면 메시지 변조를 잡아낼 수 있다.


반면 이번 예제에서는 비밀키를 안전하게 공유하고 갱신하는 운영 과정은 다루지 않았고, HMAC만으로는 메시지 암호화나 작성자 입증, 동일 요청의 재전송 차단을 해결할 수 없다. 인증 대상에 전송 시각이나 요청 식별자를 함께 넣을지, 이미 처리한 요청을 어떻게 기록해 걸러낼지는 다음 글에서 이어서 다룬다.
