## 저장소의 단계별 실행 구조


작업이 시작되고 끝나는 시점을 구분하려면 먼저 `SetWindowShookEx` 저장소가 어떤 단계로 나뉘어 동작하는지 확인해야 한다. 이 저장소는 Windows가 제공하는 훅 기능(API) 하나만 보여 주는 짧은 예제보다 다루는 범위가 넓다. ## 훅 등록과 이벤트 처리


저장소의 첫 단계인 초기 연결에서 훅을 걸 때는 등록이 성공한 시점과 실제 이벤트가 처리된 시점을 나누어 봐야 한다. 이 차이를 분명히 보려고 창의 상태 변화를 감시하는 작은 관찰 프로그램을 떠올려 봤다. 감시 기능을 등록한 직후 화면에 '관찰 중'이라고 표시할 수는 있지만, 이벤트가 아직 한 번도 발생하지 않았다면 '상태 갱신을 확인했다'고 기록할 수는 없다.


Windows에서는 `SetWindowsHookEx` 함수를 호출해 메시지나 이벤트를 가로채는 훅을 설치한다. 이때 개발자가 직접 호출하는 대신 이벤트가 발생할 때 시스템이 대신 실행해 주는 함수인 **콜백**(callback)을 함께 등록한다. [Microsoft의 훅 개요](https://learn.microsoft.com/en-us/windows/win32/winmsg/about-hooks)와 [등록 함수의 반환값](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowshookexw) 문서를 보면, 이 함수는 성공했을 때 자원을 가리키는 식별값인 **핸들**(handle)을 반환한다. 이는 시스템이 관리하는 훅 목록(훅 체인)에 콜백이 등록되었다는 뜻일 뿐이다. 반환된 핸들만으로는 목표한 이벤트가 실제로 도착했는지, 콜백 안의 후속 작업까지 끝났는지 알 수 없다. 그림 2의 관찰 프로그램 흐름처럼 등록 여부와 마지막 이벤트 처리 시각을 따로 표시해야 등록 성공과 처리 완료의 차이가 드러난다.

## 훅 해제와 자원 정리 시점


등록과 처리 시점이 다른 것처럼, 훅을 해제할 때도 함수가 반환된 시점과 실제 작업이 끝나는 시점을 구분해야 한다. 프로그램 안에서는 코드를 동시에 실행하는 작업 흐름인 **스레드**(thread)가 여러 개 돌아갈 수 있다. [해제 함수의 동시 실행 조건](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-unhookwindowshookex) 문서에는 `UnhookWindowsHookEx`가 반환된 뒤에도 다른 스레드에서 이미 시작된 콜백이 실행 중일 수 있다고 나와 있다. 훅 목록에서 제거되는 시점과 실행 중이던 콜백이 완전히 끝나는 시점이 반드시 일치하지는 않는다.


다른 스레드에서 콜백이 아직 실행 중인데 해제 함수가 반환됐다는 이유만으로 데이터를 곧바로 정리하면, 실행 중인 콜백이 이미 해제된 상태를 참조해 충돌할 수 있다. 실행 순서를 그려 보니 콜백이 참조하는 상태의 수명과 종료 확인을 별도 항목으로 다뤄야 했다. 그림 3처럼 자원을 소유한 스레드와 종료 요청을 확인하는 쪽, 마지막 콜백 실행이 끝났음을 알리는 방법을 함께 맞춰야 자원을 안전하게 정리할 수 있다.


![종료 요청 스레드에서 해제 함수가 반환된 뒤 콜백 실행 스레드의 실행 종료 알림을 확인하고 자원을 정리하는 타임라인](/images/notion/tech-01-04/image-3.png)


그림 3. 해제 함수가 반환된 뒤에도 다른 스레드에서 실행 중인 콜백이 끝날 때까지 기다려 자원을 정리하는 개념도.


저장소 전체 구조에서도 초기 훅 해제와 전체 작업 종료를 나누어 봐야 했다. 저장소의 [개발 문서](https://github.com/NAMUORI00/SetWindowShookEx/blob/faaa1a62143b5959a06c0e4418bec343262c1b93/docs/PROJECT.md)에는 초기 연결 이후 상시 통신을 별도로 이어 가는 구조가 기록되어 있다. 초기 훅을 해제했다고 해서 이후의 통신이나 화면 갱신까지 모두 종료되었다는 뜻은 아니다. 문서의 구조 설명과 실제 코드의 진입점 분리를 대조해 보며 초기 연결 해제와 전체 통신 종료가 별개라는 점을 확인했다. 다만 문서에 적힌 강한 안정성 표현을 모든 환경에서 검증된 결과로 받아들이지는 않았다.


## 시간 초과와 후속 처리


훅 해제뿐만 아니라 요청을 보내고 응답을 기다리는 **시간 초과**(timeout) 처리에서도 대기 종료와 실제 작업 종료를 구분해야 한다. 요청자가 제한 시간을 넘겨 더 기다리지 않기로 했다고 해서, 실행자 쪽의 작업이 자동으로 취소되지는 않기 때문이다. 저장소에서 요청 전달과 대기 처리를 묶어 다루는 [요청 완료와 시간 초과 처리](https://github.com/NAMUORI00/SetWindowShookEx/blob/faaa1a62143b5959a06c0e4418bec343262c1b93/src/injector/core/bridge.cpp) 경로를 보면, 시간 초과 뒤에도 늦은 처리가 들어올 수 있다는 주석이 적혀 있다. 이와 함께 대기 중인 요청을 무효화하고 실패를 반환하는 처리도 들어 있다. 요청의 실제 수명이 호출자의 대기 시간보다 길어질 수 있다는 점을 고려한 코드로 읽혔다.


작은 예로 요청 A의 대기 시간이 끝난 직후 새 요청 B가 시작되는 경우를 생각해 볼 수 있다. 뒤늦게 도착한 A의 결과가 B의 결과처럼 표시되면, 값 자체는 맞아도 요청과 응답의 대응 관계가 틀어진다. 그림 4처럼 요청마다 번호를 붙여 응답이 왔을 때 현재 기다리는 요청 번호와 대조하면 이 혼동을 막을 수 있다. 이 번호 대조 흐름은 저장소의 요청 무효화 코드와 똑같은 구현이 아니라, 늦은 응답으로 인한 혼동을 막기 위한 일반적인 설계 예다.

## 결론


비동기 처리에서는 첫 등록 성공을 확인하는 것보다 종료 조건을 맞추는 일이 더 까다롭다. 이번에 저장소 코드와 공식 문서를 읽으며 세운 기준은 등록 성공, 작업 처리 완료, 대기 종료, 자원 정리 완료를 각각 별개의 상태로 기록하고 다루는 것이다. 콜백이 끝났다는 확인 뒤에 자원을 해제하고, 늦은 응답에는 요청 번호를 대조하거나 무효화하는 기준이 있어야 시작과 종료의 수명이 어긋나지 않는다.


이번에 확인한 범위는 소스 코드의 흐름과 API 문서의 동작 계약을 읽은 것까지다. 프로그램을 대상 프로세스에 실제로 연결하거나, 종료 요청과 콜백 실행이 동시에 겹치는 경쟁 조건을 재현한 결과는 포함하지 않았다. 후속 확인 항목으로는 독립적인 예제 창에서 일부러 지연시킨 콜백과 종료 요청을 겹치게 하여 어떤 상태가 끝까지 유지되어야 하는지 살펴보는 실험을 남겼다. 다음 글에서는 규모가 큰 도구를 수정할 때 원본 기능과 직접 바꾼 화면 표현의 범위를 구분한 내용을 다룬다.
