Windows 훅을 다루며 등록, 콜백 전달, 해제와 자원 정리의 순서를 정리했다. 종료 요청과 이미 실행 중인 콜백이 겹칠 수 있어 객체의 수명과 요청 및 응답의 대응을 함께 확인했다.


## 이벤트 등록과 실행 시점


앞 글에서 접근 권한을 살펴본 데 이어, 이번에는 작업이 끝나는 시점의 문제를 정리했다. SetWindowShookEx 저장소의 코드와 문서를 읽으며 훅의 등록, 이벤트 처리, 자원 정리를 나누어 실행 흐름을 따라가 봤다.


이 저장소는 Windows 훅 API만 소개하는 짧은 예제보다 범위가 넓었다. 프로그램 시작 코드를 확인해 보니 설치, 진단, 제어, 외부 화면 경로가 서로 다른 진입 함수로 분기되어 있었다. 개발 문서에서도 초기 연결과 이후의 통신, 화면 갱신을 별도 단계로 나누어 설명하고 있었다.


이런 구조를 보고, 저장소 이름만으로 모든 상태 전달이 하나의 훅 콜백 안에서 이루어진다고 가정하지 않았다. [프로그램 진입점](https://github.com/NAMUORI00/SetWindowShookEx/blob/faaa1a62143b5959a06c0e4418bec343262c1b93/src/main.cpp)


이번 글에서는 이벤트, 콜백, 스레드의 기본 뜻을 이어받아 등록 성공, 처리 완료, 정리 완료를 구분하는 데 초점을 두었다. 특정 대상에 훅을 설치하는 절차 자체보다는 비동기 작업의 수명을 읽는 쪽에 무게를 뒀다.


## 훅 등록과 이벤트 처리


콜백은 직접 호출하는 함수와 달리, 미리 등록해 두면 특정 사건이 발생할 때 시스템이 호출하는 함수다. `SetWindowsHookEx`가 성공해서 핸들을 반환했다면 그것은 등록이 이루어졌다는 뜻이다. 그 핸들만으로는 원하는 이벤트가 도착했는지, 콜백의 후속 작업까지 끝났는지 알 수 없다.


[Microsoft의 훅 개요](https://learn.microsoft.com/en-us/windows/win32/winmsg/about-hooks), [등록 함수의 반환값](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowshookexw)


설명용 창 프로그램을 하나 떠올려 봤다. 창의 상태 변화를 관찰하도록 등록한 직후 화면에 '관찰 중'이 표시될 수 있지만, 이벤트가 한 번도 발생하지 않은 상태라면 '상태 갱신을 확인했다'고 기록할 수는 없다. 등록 여부와 마지막 처리 시각을 별도로 표시하면 두 상태의 차이가 드러난다.

## 해제 함수의 반환과 콜백 종료 사이


Microsoft 문서에는 `UnhookWindowsHookEx`가 반환한 뒤에도 다른 스레드에서 콜백을 호출 중일 수 있다고 명시되어 있다. 훅 체인에서 제거되는 시점과, 이미 시작된 콜백의 실행이 끝나는 시점이 반드시 일치하지는 않는 셈이다.


[해제 함수의 동시 실행 조건](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-unhookwindowshookex)


콜백이 아직 실행 중이라면 해제 직후 데이터를 정리하는 과정과 충돌할 수 있다. 실행 순서를 그려 보니 콜백이 참조하는 상태의 수명과 종료 확인이 별도 항목으로 남았다. 자원을 소유한 스레드, 종료 요청을 확인하는 쪽, 마지막 실행이 끝났음을 알리는 방법을 함께 볼 필요가 있었다.


저장소의 개발 문서에는 초기 연결 이후 상시 통신을 별도로 이어가는 구조가 기록되어 있었다. 초기 훅을 해제했다는 것이 이후 통신이나 화면 갱신까지 종료되었다는 뜻은 아닌 셈이다. 이 글에서는 문서의 구조 설명과 실제 진입점 분리를 대조하며 이 점을 확인했다.


다만, 문서에 등장하는 강한 안정성 표현을 모든 환경에서 검증된 결과로 받아들이지는 않았다. [개발 문서](https://github.com/NAMUORI00/SetWindowShookEx/blob/faaa1a62143b5959a06c0e4418bec343262c1b93/docs/PROJECT.md)


## 시간 초과와 후속 처리


시간 초과에서도 비슷한 구분이 필요했다. 요청자가 더 기다리지 않기로 했다고 해서 실행자 쪽의 작업이 자동으로 취소되지는 않는다. 요청 전달, 대기 처리의 배치 처리 경로를 보면, 시간 초과 후에도 늦은 처리가 들어올 수 있다는 주석이 있었고, 대기 중인 요청을 무효화하고 실패를 반환하는 처리도 들어 있었다.


이 부분은 요청의 수명이 호출자의 대기 시간보다 길어질 수 있다는 점을 고려한 코드로 읽혔다. [요청 완료와 시간 초과 처리](https://github.com/NAMUORI00/SetWindowShookEx/blob/faaa1a62143b5959a06c0e4418bec343262c1b93/src/injector/core/bridge.cpp)


작은 예로, 요청 A의 대기 시간이 끝난 직후 요청 B가 시작되는 경우를 생각해 볼 수 있다. A의 늦은 결과가 B의 결과처럼 표시되면 값 자체는 맞아도 요청과 응답의 대응 관계가 틀어진다. 요청 번호를 붙여 결과를 대조하면 이 혼동을 막을 수 있다. 아래 번호 대조는 요청과 응답의 혼동을 방지하기 위한 일반적인 설계 예제다.

## 종료 상태와 확인 기록


이 저장소를 읽으며 남긴 기준은 등록, 작업 처리, 대기 종료, 자원 정리를 각각 별개의 상태로 기록하는 것이었다. 이번 확인 범위는 소스의 흐름과 API 계약을 읽은 것에 한정되며, 프로그램을 대상 프로세스에 실제로 연결하거나 종료 경쟁 조건을 재현한 결과는 포함되지 않는다.


후속 확인 항목으로는 독립적인 예제 창에서 지연된 콜백과 종료 요청을 겹치게 하는 실험을 남겼다. 그 상황에서 어떤 상태가 마지막까지 유지되어야 하는지 살펴보는 과정이다. 다음 글에서는 큰 도구를 수정할 때 원본 기능과 직접 바꾼 화면 표현을 구분한 내용을 정리한다.


## 작업을 정리하며


비동기 처리에서는 등록 성공보다 종료 조건을 설명하는 일이 더 까다롭다. 콜백이 끝났다는 확인 뒤에 자원을 해제하고, 늦은 응답에는 요청 번호를 대조하는 기준이 필요하다. 시작과 종료를 한 흐름으로 설계하는 데 참고할 만한 사례다.
