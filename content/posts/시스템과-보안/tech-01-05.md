Cheat Engine 포크의 화면 문구를 바꾸는 작업에서 표시 문자열과 기능 식별자를 분류했다. 치환 규칙이 코드와 데이터의 역할을 충분히 구분하는지 확인하며 변경 범위를 정리했다.


## 원본 기능과 UI 수정 범위


cheat-engine-custom 저장소에는 원본에서 이어받은 GUI, 스크립트, 보조 모듈과 이후 추가된 UI 변경이 함께 들어 있다. 화면의 버튼 문구를 바꾸는 작업과 메모리 검색 기능을 새로 만드는 작업은 수정 범위가 다르므로, 최근 화면 수정이 어느 부분을 건드렸는지 기준 버전과 대조하며 확인했다.


확인 시점의 GitHub 메타데이터는 이 저장소를 공식 fork로 표시하지 않았지만, README는 원본 Cheat Engine을 안내하고 빌드 점검 문서는 공식 7.5 태그의 커밋을 기준으로 적고 있었다.


GitHub가 fork로 표시하지 않더라도 코드의 유래는 별도로 확인할 수 있었다. [README](https://github.com/NAMUORI00/cheat-engine-custom/blob/8088992c054bf16a34ebb9a371fa856f018168ae/README.md)


이 글에서는 전체 메모리 도구의 기능 설명 대신 최근 UI 수정과 빌드 기록을 중심으로 범위를 잡았다. Git 커밋과 GUI 구성 요소의 기본 개념을 전제로, 표시 문자열이 데이터 문자열과 구분되어야 하는 이유를 작은 예와 함께 정리한다.


## 기준 버전과 최근 변경을 따로 확인하기


빌드 점검 문서가 적은 기준은 공식 7.5의 `59930b5…` 커밋이다. 최근 이력에는 텍스트 중심 테마 적용, 핵심 UI에 미치는 영향 축소, 선택적인 문자 장식 적용이 차례로 남아 있다. 확인한 마지막 커밋은 `CustomUITheme.pas`와 여러 기본 컨트롤의 표시 호출을 바꾼다.


이 커밋의 변경 목록이 과거 수정 전체를 설명하지는 않지만, 화면 표현 변경을 특정하는 직접적인 근거였다. [최근 변경](https://github.com/NAMUORI00/cheat-engine-custom/commit/8088992c054bf16a34ebb9a371fa856f018168ae)


같은 저장소 안에서 코어 모듈의 빌드 확인과 이후 테마 변경은 별개로 구분했다. 이전 점검에서 만들어진 바이너리의 해시가 이후 UI 커밋의 동작까지 검증하는 것은 아니기 때문에, 결과물을 소개할 때는 기준 커밋과 산출물 버전을 함께 기록하는 편이 정확하다.

## 표시 문자열과 데이터 문자열


`CustomUITheme.pas`에는 표시용 문자열을 변환하는 함수와 변환 대상을 고르는 함수가 나뉘어 있다. 주소처럼 보이는 값, 코드 토큰, 파일 경로, 상태 문자열은 장식 대상에서 제외한다. 구성 요소 이름에 `address`, `status`, `value` 같은 단서가 있는지도 확인한다.


[테마의 판정 코드](https://github.com/NAMUORI00/cheat-engine-custom/blob/8088992c054bf16a34ebb9a371fa856f018168ae/Cheat%20Engine/CustomUITheme.pas)


예를 들어 버튼의 'Open'은 표시용 문구지만 `0xA0`은 해석 대상인 값이고 `C:/app/tool.exe`는 경로다. 같은 알파벳이 들어 있어도 의미가 다르다. 문구를 장식하려고 값이나 경로까지 바꾸면 복사한 내용이나 눈으로 읽는 주소가 원본과 달라질 수 있다. 이 변경에서는 치환할 문자열의 역할을 먼저 분류해야 했다.


기본 판정에는 빈 문자열 여부, 길이, 특정 문자의 포함 여부와 제외 패턴이 들어 있다. 짧은 UI 문구인지 판단할 때에는 길이와 단어 수, 일부 구두점도 확인한다.


이 규칙은 텍스트 패턴을 이용한 휴리스틱이다. 새 컨트롤의 이름이나 번역된 문구가 예상 밖의 패턴을 가지면 오분류될 수 있고, 몇 가지 예시가 통과했다고 모든 화면에서 안전한 분리가 보장되지는 않는다.

## 글꼴 변경과 컨트롤 배치


테마는 아이콘 표시를 줄이고 버튼에 텍스트를 넣는 방식이다. `EnsureSpeedButtonTextSize`는 폰트를 적용한 실제 텍스트 폭에 여백을 더해 버튼 폭을 확보하고 최소 높이도 확인한다. 아이콘이 있던 자리를 글자로 바꾸면 문자열 길이가 레이아웃에 직접 영향을 준다.


화면이 나중에 추가되거나 활성화되는 경우를 처리하는 테마 관리자도 있었다. 프로그램 시작 시 열린 창 하나에만 색을 지정하는 방식과는 적용 범위가 다르다. 다만 폭 계산 코드가 있다는 것과 DPI 변경, 번역 문자열, 키보드 접근성까지 검증되었다는 것은 별개이며, 이 글에서 확인한 것은 코드에 마련된 조정 경로까지다.


## 빌드 기록과 기능 확인 범위


빌드 점검 문서에는 GUI와 보조 모듈별로 컴파일, PE, ELF 형식, 내보낸 함수, 해시 등의 확인 수준이 기록되어 있다. 드라이버 로드나 다른 프로세스에 연결하는 통합 실험은 수행되지 않았다는 범위 한정도 명시되어 있었다.


[빌드 점검 기록](https://github.com/NAMUORI00/cheat-engine-custom/blob/8088992c054bf16a34ebb9a371fa856f018168ae/CORE_MODULE_BUILD_AUDIT.md)


파일 생성과 아키텍처를 확인한 단계와 실제 기능을 검증한 단계는 나누어 읽었다. 문서에는 빌드 검사 결과가 기록되어 있었고, 이번에는 그 기록과 UI 변경 소스를 대조했다. 새로 모듈을 로드하거나 통합 동작을 실행하는 검증은 포함하지 않았다.


다음으로 확인할 부분은 테마를 적용한 실제 화면에서 동적 값이 원문 그대로 유지되는지, 긴 문구가 잘리지 않는지다. 원본 도구의 큰 기능 목록을 나열하기보다 작은 변경이 어디에 영향을 주는지 짚는 쪽이 이 저장소의 작업을 더 정확하게 드러냈다.


다음 글에서는 화면의 표시값에서 장치의 응답 쪽으로 넘어가, NVMe로 인식되는 것과 데이터를 지속 보관하는 것이 어떻게 다른지 살펴본다.


## 작업을 정리하며


화면 변경도 문자열의 위치와 역할을 알아야 안전하게 적용할 수 있다. 휴리스틱으로 후보를 좁힌 뒤 리소스, 식별자, 설정값을 대조하는 방식이 필요하다. 검색으로 찾은 항목과 실제 바꾼 항목을 따로 남기는 기준이 유용하다.
