프로그램의 메모리를 분석하는 도구인 Cheat Engine은 화면에 여러 종류의 문자열을 띄운다. 버튼을 가리키는 `'Open'`, 메모리 주소나 값을 뜻하는 `0xA0`, 파일 경로인 `C:/app/tool.exe`가 한 화면에 함께 표시된다. 이때 화면 글자에 일괄로 장식을 입히면 버튼 이름뿐 아니라 주소와 경로까지 바뀌어, 눈으로 읽거나 복사한 값이 실제 데이터와 달라질 수 있다.


개인 저장소인 `cheat-engine-custom`에는 원본 Cheat Engine에서 물려받은 화면 코드(GUI)와 스크립트, 보조 모듈이 들어 있다. 여기에 나중에 추가한 사용자 화면(UI) 테마 수정 코드가 합쳐져 있는데, 메모리 검색 기능을 새로 만드는 일과 버튼 문구를 손보는 일은 수정 범위가 전혀 다르다. 이 글에서는 저장소의 기준 버전과 최근 변경 기록을 대조해 실제 수정 범위를 짚어 보고, 표시용 문구와 데이터 값을 구분하는 규칙을 코드로 확인한다.


## 기준 버전과 화면 변경 이력


원본 코드를 이어받아 일부 기능을 고친 저장소를 분석할 때는 어디까지가 원본이고 어디부터가 새로 추가된 변경인지 먼저 갈라야 한다. 확인 시점의 GitHub 메타데이터에는 이 저장소가 원본 저장소를 복제해 연결한 공식 포크(fork)로 표시되어 있지 않았다. 하지만 저장소의 [README](https://github.com/NAMUORI00/cheat-engine-custom/blob/8088992c054bf16a34ebb9a371fa856f018168ae/README.md)는 원본 Cheat Engine을 안내하고, 빌드 점검 문서는 공식 7.5 태그의 `59930b5…`를 기준 버전으로 적고 있었다. GitHub에 포크 표시가 없더라도 문서와 코드 변경 기록인 커밋(commit)을 대조하면 코드의 유래와 기준점을 확인할 수 있다.


기준 커밋 이후의 최근 이력을 보면 텍스트 중심의 테마를 적용한 뒤, 핵심 UI에 미치는 영향을 줄이고 선택적으로 문자 장식을 입히는 수정이 차례로 이어진다. 확인한 [최근 변경 커밋](https://github.com/NAMUORI00/cheat-engine-custom/commit/8088992c054bf16a34ebb9a371fa856f018168ae)은 `CustomUITheme.pas` 파일과 화면의 버튼이나 입력창 같은 단위 요소인 **컨트롤**의 표시 함수 호출을 바꾼다. 이 커밋 하나가 과거의 모든 수정을 보여 주지는 않지만, 화면 표현을 어느 경로에서 바꿨는지 알려 주는 직접적인 근거가 된다.


여기서 코어 모듈의 빌드 점검 기록과 그 뒤에 이어진 UI 테마 변경 커밋은 검증 시점과 대상이 다르므로 따로 떼어 읽어야 한다. 이전 빌드 점검에서 파일이 바뀌지 않았음을 확인하려고 기록한 고유 요약값인 바이너리 해시가 이후에 추가된 UI 커밋의 실행 동작까지 보증하지는 않기 때문이다. 공식 7.5 기준 버전에서 갈라진 빌드 점검 기록 경로와 후속 UI 변경 커밋 경로를 나누어 두어야 결과물의 버전과 검증 범위를 혼동하지 않는다.

## 표시 문자열과 데이터 문자열의 분리


최근 커밋 이력에서 핵심 UI에 미치는 영향을 줄이고 선택적으로만 문자를 장식하도록 고친 이유는 화면에 놓인 문자열의 역할이 서로 다르기 때문이다. 앞서 본 버튼의 `'Open'`은 기능을 안내하는 **표시 문자열**이지만, `0xA0`은 프로그램과 사용자가 해석할 값이고 `C:/app/tool.exe`는 파일 경로다. 같은 알파벳으로 적혀 있어도 실제 값을 담은 **데이터 문자열**까지 장식용 문자로 치환하면 화면에 찍힌 주소나 복사한 경로가 원본과 달라진다.


이 문제를 피하려고 [테마의 판정 코드](https://github.com/NAMUORI00/cheat-engine-custom/blob/8088992c054bf16a34ebb9a371fa856f018168ae/Cheat%20Engine/CustomUITheme.pas)(`CustomUITheme.pas`)는 문자열을 실제로 변환하는 함수와 변환 대상을 고르는 판정 함수를 분리해 두었다. 판정 함수는 먼저 컨트롤의 이름(식별자)을 확인해 `address`, `status`, `value`처럼 데이터나 상태를 뜻하는 단서가 들어 있으면 변환 대상에서 뺀다. 이어서 메모리 주소처럼 보이는 값이나 코드 조각인 토큰, 파일 경로, 상태 문자열도 데이터 항목으로 보아 원문을 그대로 유지한다. 마지막으로 빈 문자열인지 확인한 뒤 문자열 길이와 단어 수, 특정 문자나 제외 패턴, 일부 구두점까지 함께 검사한다. 이 검사를 통과해 허용된 짧은 UI 문구로 판정된 문자열만 문자 장식을 거쳐 컨트롤 화면에 표시된다.


![표시할 문자열이 값, 경로, 상태인지 먼저 판정하여 원문을 유지하고, 짧은 UI 문구일 때만 표시용 문자 장식을 거쳐 컨트롤 화면에 표시하는 흐름도](/images/notion/tech-01-05/image-2.png)


그림 2. 문자열의 의미를 보존하기 위해 데이터 항목을 제외하고 짧은 UI 문구만 장식하는 판정 흐름(출처: CustomUITheme.pas, 자체 제작).


다만 이 판정 규칙은 문자열의 겉모습과 컨트롤 이름 패턴으로 대상을 어림잡아 가려내는 **휴리스틱**(어림규칙)이다. 새로 추가된 컨트롤의 이름이나 번역된 문구가 예상하지 못한 패턴을 가지면 데이터 문자열이 장식되거나 반대로 UI 문구가 누락될 수 있다. 몇 가지 예시 문구가 검사를 통과했다고 해서 모든 화면의 문자열이 안전하게 분리된다고 단정할 수는 없다. 안전하게 화면 문구를 바꾸려면 휴리스틱으로 후보를 좁히더라도 화면 문구와 설정을 모아 둔 리소스 파일, 컨트롤 식별자, 설정값을 함께 대조해야 한다. 또한 검색으로 찾은 문자열과 실제로 치환한 항목을 구분해 기록하는 편이 낫다.


## 버튼 문구 적용과 크기 조정


문자열의 의미를 가려내는 일 못지않게 화면 테마를 수정할 때 신경 써야 할 부분은 화면 배치(레이아웃)다. 이 저장소의 커스텀 테마는 기존 화면의 아이콘 표시를 줄이고 버튼에 텍스트 문구를 넣는 방식을 쓴다. 고정된 크기의 아이콘이 있던 자리에 글자를 넣으면 문자열 길이가 버튼 크기와 주변 배치에 바로 영향을 준다. `CustomUITheme.pas`에 있는 `EnsureSpeedButtonTextSize` 함수는 이 크기 변화를 코드에서 계산해 처리한다. 글꼴을 적용했을 때의 실제 텍스트 폭을 계산하고, 여기에 좌우 여백을 더해 버튼 폭을 확보한 뒤 최소 높이 조건도 확인한다.


![아이콘 축소와 문구 적용 후 EnsureSpeedButtonTextSize 내부에서 글꼴 적용 텍스트 폭 계산, 좌우 여백 추가, 최소 높이 확인을 거쳐 버튼 폭과 높이를 확보하는 과정도](/images/notion/tech-01-05/image-3.png)


그림 3. 버튼에 텍스트 문구를 적용할 때 EnsureSpeedButtonTextSize가 폭과 최소 높이를 계산해 레이아웃에 반영하는 흐름.


또한 프로그램이 시작될 때 열린 창 하나에만 색을 입히는 데 그치지 않고, 실행 도중에 나중에 추가되거나 활성화되는 화면까지 처리하는 테마 관리자도 함께 두었다. 물론 폭을 계산하고 창을 관리하는 코드가 들어 있다는 사실과 실제 화면에서 모든 배치가 검증되었다는 사실은 구분해야 한다. 화면 배율(DPI) 변경이나 다국어 번역 문자열, 키보드 접근성까지 실행 환경에서 확인한 것은 아니며, 이번 검토에서 확인한 범위는 코드에 마련된 크기 조정 경로까지다.


## 빌드 점검 기록과 검증 범위


화면 배치 코드를 실제 실행 실험과 구분해 읽었듯이, 저장소 전체에서 확인된 범위도 파일 생성 점검과 실행 검증으로 나누어 보아야 한다. 저장소의 [빌드 점검 기록](https://github.com/NAMUORI00/cheat-engine-custom/blob/8088992c054bf16a34ebb9a371fa856f018168ae/CORE_MODULE_BUILD_AUDIT.md)(`CORE_MODULE_BUILD_AUDIT.md`)에는 GUI 실행 파일과 보조 모듈별 산출물 검사 결과가 정리되어 있다. 여기에는 소스 코드를 실행 파일로 변환한 컴파일 성공 여부와 운영체제별 실행 파일 형식(Windows의 PE, Linux의 ELF)이 포함된다. 모듈이 외부에서 호출할 수 있게 공개한 내보낸 함수(export) 목록과 파일 해시도 함께 기록되어 있다. 반면 운영체제 핵심 영역에서 동작하는 커널 드라이버를 메모리에 올리거나 다른 프로세스(실행 중인 프로그램)에 연결하는 통합 실행 실험은 수행하지 않았다고 적어 두었다.


파일이 올바른 아키텍처와 형식으로 생성되었는지 확인하는 정적 점검 단계와 프로그램을 직접 실행해 기능을 검증하는 단계는 서로 다르다. 이번 작업에서는 기존 빌드 점검 기록과 이후에 추가된 UI 변경 소스 코드를 대조해, 어떤 규칙으로 문자열을 판정하고 레이아웃을 조정하는지 확인했다. 모듈을 새로 로드하거나 다른 프로세스를 대상으로 통합 동작을 실행하는 검증과 동적 값 유지, 긴 문구 잘림, 화면 배율(DPI) 확인은 남은 실행 검증 범위다.

## 결론


원본 도구의 방대한 메모리 분석 기능을 나열하기보다 작은 UI 변경이 코드의 어느 지점에 영향을 주는지 좁혀 보는 편이 저장소의 실제 작업 범위를 더 정확하게 보여 준다. 공식 7.5 기준의 빌드 점검 기록과 후속 UI 커밋을 대조해, `CustomUITheme.pas`가 데이터 문자열을 걸러 내고 버튼 폭을 조정하는 코드 경로를 확인했다. 반면 커널 드라이버를 메모리에 올리거나 다른 프로세스에 연결하는 통합 실행과 화면 배율 변경에 따른 배치 동작은 아직 실행 환경에서 검증하지 않았다. 다음 과제는 테마가 적용된 실제 실행 화면에서 동적으로 바뀌는 주소나 상태값이 원문 그대로 유지되는지, 그리고 길어진 버튼 문구가 화면에서 잘리지 않는지 직접 점검하는 일이다.
