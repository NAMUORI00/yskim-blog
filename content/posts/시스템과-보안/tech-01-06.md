운영체제의 장치 관리자에 고속 저장장치 규격인 NVMe(Non-Volatile Memory Express) 장치가 정상으로 표시될 때가 있다. 읽기와 쓰기 명령까지 오류 없이 끝나면, 장치가 연결된 컴퓨터인 호스트에는 실제 SSD가 꽂힌 것처럼 보인다. 하지만 앞선 글에서 장치의 표시 이름과 가상주소, 물리주소, 메모리 접근 경로를 구분해 보았듯 장치 인식과 실제 동작은 다르다. 운영체제가 장치를 인식하는 것과 호스트 메모리에 접근하거나 전원을 끈 뒤에도 데이터를 보존하는 것은 서로 다른 문제다.


이 글에서는 하드웨어 회로를 코드로 설계해 넣는 반도체인 FPGA로 NVMe 장치를 구현한 사례를 다룬다. [저장소 설명](https://github.com/NAMUORI00/Pcileech-DMA-NVMe-VMD2/blob/7a122a9171b9a7e9087f42b7e6b95c498ebccec1/README.md)과 소스 코드를 읽으며 호스트가 보는 NVMe 장치와 FPGA 내부의 저장 구조가 어떻게 연결되는지 따라가 보았다.


## 장치 인식과 휘발성 저장 공간


호스트가 보는 장치와 내부 저장 구조의 차이는 검토한 `Pcileech-DMA-NVMe-VMD2` 저장소의 README에서 바로 드러난다. 문서에는 NVMe 제어기 활성화와 작업 대기열인 큐, 알림 신호인 도어벨, 읽기와 쓰기, 로그 처리 과정이 나와 있다. 데이터를 저장하는 공간은 전원이 꺼져도 남는 비휘발성 NAND 플래시가 아니라, 전원이 끊기면 지워지는 **휘발성 FPGA 캐시**라고 명시되어 있다. 저장장치 규격에 맞춰 명령을 주고받는 기능과 데이터를 영구히 보관하는 매체의 특성이 분리되어 있다.


이 글은 저장소의 문서와 하드웨어 설계 언어인 SystemVerilog 소스 코드를 읽고 분석한 기록이다. 실제 FPGA 보드에 회로 파일인 비트스트림을 올리거나 호스트 운영체제의 메모리 보호 설정을 바꾸는 실행 검증은 하지 않았다. 대신 코드에 구현된 명령 처리 경로와 캐시 구조를 확인하는 데 초점을 두었다.


## NVMe 요청 처리와 DMA 전송


명령을 주고받는 첫 단계는 읽기나 쓰기처럼 호스트가 저장장치에 시키는 작업인 NVMe 요청을 전달하는 과정이다. 호스트 드라이버가 메모리의 명령 큐에 작업을 넣고 도어벨(Doorbell) 레지스터에 신호를 보내면, 제어기는 새 작업이 들어왔음을 감지한다. 이어서 제어기는 명령이 가리키는 메모리 공간인 호스트 버퍼와 데이터를 주고받은 뒤 완료 큐에 처리 결과를 기록한다. 이때 장치가 CPU를 거치지 않고 호스트 메모리와 직접 데이터를 주고받는 경로가 **DMA**(Direct Memory Access)다.


여기서 CPU가 명령을 준비해 큐에 넣는 단계와 장치가 DMA로 호스트 버퍼를 읽고 쓰는 단계는 나누어 봐야 한다. 운영체제가 장치를 NVMe 제어기로 인식했더라도, 장치가 접근할 수 있는 호스트 메모리 범위는 별도의 메모리 보호 정책을 따르기 때문이다. 하드웨어 계층에서는 **IOMMU**(Input-Output Memory Management Unit)가 장치의 주소 변환과 접근 범위를 통제한다. 운영체제에서도 Microsoft의 [Kernel DMA Protection](https://learn.microsoft.com/en-us/windows/security/hardware-security/kernel-dma-protection-for-thunderbolt) 문서가 설명하듯 드라이버와 메모리 격리 조건에 따라 장치의 DMA 접근을 제한한다. 제어기가 명령 큐와 완료 큐에 접근하는 과정 역시 이러한 메모리 접근 정책 안에서 이루어진다.

그림 1. NVMe 요청 처리에서 명령 전달, 메모리 매핑 정책을 거치는 DMA 버퍼 접근, FPGA 내부 휘발성 캐시의 역할을 구분한 구조도(출처: 저장소 제어기 코드와 Microsoft DMA 보호 문서 기반 자체 제작).


## 캐시 슬롯과 데이터 유지 범위


DMA를 거쳐 FPGA 내부로 들어온 데이터는 캐시의 각 저장 칸인 슬롯(slot)에 나누어 보관된다. [캐시 읽기와 쓰기 코드](https://github.com/NAMUORI00/Pcileech-DMA-NVMe-VMD2/blob/7a122a9171b9a7e9087f42b7e6b95c498ebccec1/src/pcileech_nvme_dma_disk.sv)가 담긴 `pcileech_nvme_dma_disk.sv`에는 슬롯별 정보를 관리하는 세 가지 배열이 선언되어 있다. 실제 블록 데이터를 담는 `block_store`, 유효한 데이터가 있는지 나타내는 `block_valid`, 어느 논리 블록인지 구분하는 `block_tag`다.


호스트는 저장 공간의 위치를 가리킬 때 논리 블록 번호인 **LBA**(Logical Block Addressing)를 사용한다. 읽기 요청이 들어오면 제어기는 해당 슬롯의 `block_valid`가 유효한지, 그리고 `block_tag`에 기록된 값이 호스트가 요청한 LBA와 일치하는지 검사한다. 두 조건을 모두 만족하면 `block_store`에 저장된 값을 돌려주고, 하나라도 맞지 않으면 `0`을 반환한다.


![읽기 요청이 들어왔을 때 FPGA 캐시 슬롯의 block_valid와 block_tag를 검사해 LBA가 일치하면 block_store의 값을 반환하고 불일치하면 0을 반환하는 흐름도](/images/notion/tech-01-06/image-2.png)


그림 2. `pcileech_nvme_dma_disk.sv`에서 캐시 슬롯의 유효 여부와 태그를 확인해 저장된 블록 값 또는 0을 반환하는 읽기 처리 흐름도.


이 구조에서는 전원이 꺼지거나 장치가 재설정되지 않아도 데이터를 잃을 수 있다. FPGA 내부 캐시는 슬롯 개수가 한정되어 있어 호스트의 블록 번호를 제한된 슬롯 인덱스에 배정하기 때문이다. 예를 들어 슬롯 1에 블록 A를 쓴 뒤, 같은 슬롯 1에 배정되는 다른 블록 B를 이어서 쓰는 경우를 본다. 이때 슬롯 1에서는 나중에 들어온 블록 B가 기존 블록 A의 태그와 데이터를 덮어쓴다.


이처럼 서로 다른 논리 블록이 같은 슬롯에 배정되는 현상이 **슬롯 충돌**(slot collision)이며, 코드에서는 이 교체 횟수를 따로 기록한다. 충돌 뒤에 호스트가 다시 블록 A를 읽으려고 하면, 슬롯 1의 `block_tag`에는 이미 B가 들어 있어 태그가 일치하지 않는다. 결국 제어기는 이전에 썼던 블록 A의 데이터를 찾지 못하고 `0`을 반환한다. 블록 하나를 쓴 직후 다시 읽는 동작이 성공하더라도, 장치가 호스트에 표시하는 전체 용량에 걸쳐 데이터가 보존되는 것은 아니다.


![슬롯 1에 블록 A를 쓴 뒤 같은 슬롯에 블록 B를 써서 태그가 B로 교체된 후, 다시 블록 A를 읽으면 태그 불일치로 0을 반환하는 순서도](/images/notion/tech-01-06/image-3.png)


그림 3. 제한된 슬롯에서 다른 논리 블록 B가 기존 블록 A를 덮어쓴 뒤 블록 A를 다시 읽을 때 0이 반환되는 설명용 예제(출처: backing_slot, block_tag, block_valid 처리 기반 자체 제작).


## Flush 처리와 VMD 경로 구분


캐시 슬롯의 한계처럼 명령 응답이나 저장소 이름만 보고 실제 동작을 판단하면 안 되는 항목으로 Flush 처리와 VMD 경로가 있다. 일반적인 SSD에서 Flush 명령은 캐시에 임시로 머물고 있는 데이터를 비휘발성 메모리에 완전히 기록하라고 지시하는 명령이다. 이 저장소의 소스 코드에도 Flush 명령을 처리하는 분기가 있어 입력 필드를 검사하고 통계를 갱신한 뒤 완료 응답을 돌려준다. 하지만 이 구현의 저장 매체는 휘발성 캐시뿐이고 별도의 영구 NAND 저장 경로가 없다. 제어기가 Flush 명령을 받아 정상 완료를 반환하는 것과 정전 뒤에도 데이터가 남는 것은 서로 다른 속성이다.


운영체제 도구로 큐와 명령의 호환성을 살펴보는 실험 장치라도 이 구분이 드러나는 편이 낫다. 실제 데이터를 보관하는 SSD처럼 내구성과 지속성을 기대하는 용도와는 전제가 다르다. 따라서 README의 읽기와 쓰기 지원 목록도 이러한 휘발성 한계와 함께 읽어야 한다.


저장소 이름에 포함된 **VMD**(Volume Management Device) 역시 실제 장치 역할과 구분해 확인해야 한다. VMD는 메인보드의 고속 연결 통로인 PCIe 루트 포트에서 여러 NVMe 장치를 묶어 관리하는 제어기 기술이다. 반면 저장소의 [빌드 및 장치 역할 설명](https://github.com/NAMUORI00/Pcileech-DMA-NVMe-VMD2/blob/7a122a9171b9a7e9087f42b7e6b95c498ebccec1/build.md) 문서는 통로 끝에 연결된 FPGA 엔드포인트가 VMD 제어기가 아니라 NVMe 장치로 동작한다고 역할을 구분한다. 호스트에서 어느 포트가 VMD 경로에 속하는지는 운영체제에 표시되는 장치 이름만으로 결정되지 않는다. 결국 PCIe 연결 경로와 드라이버의 장치 인식, DMA 메모리 보호, 캐시의 데이터 보존은 각각 분리해서 확인해야 한다.


## 소스 검사와 하드웨어 검증 단계


앞서 구분한 연결 경로와 캐시 구조가 실제 보드에서도 의도대로 동작하는지 확인하려면 검증 범위 역시 단계별로 나누어야 한다. 첫 단계로 저장소에 포함된 [소스 일관성 검사](https://github.com/NAMUORI00/Pcileech-DMA-NVMe-VMD2/blob/7a122a9171b9a7e9087f42b7e6b95c498ebccec1/tools/sanity_check.ps1) 스크립트(`sanity_check.ps1`)는 문자열 패턴을 찾는 정규식으로 소스 코드를 점검한다. 단계별 동작 규칙인 상태 머신의 기본 분기와 필수 필드, 정의, 보드 설정이 코드에 빠짐없이 있는지 확인하는 과정이다. 코드를 실행하지 않고 살펴보는 이러한 정적 검사는 빠진 조건이나 설정 불일치를 찾는 데 쓰인다. 하지만 서로 다른 속도로 동작하는 회로 사이의 클럭 경계 처리와 실제 PCIe 전송의 정확성까지 보장하지는 못한다.


빌드 문서에서도 CaptainDMA 계열 두 보드의 빌드 확인 상태와 ZDMA 보드의 미완료 상태를 구분해 두었다. 따라서 정적 소스 검사 뒤에는 코드를 회로로 바꾸는 합성과 배치배선 결과, 신호가 제시간에 도달하는 타이밍 수렴 여부를 먼저 확인해야 한다. 이어서 제한된 캐시 슬롯의 교체 조건과 장치 재설정 뒤의 읽기 결과를 시뮬레이션과 보드별 실행 기록으로 각각 검증해야 한다.

## 결론


`Pcileech-DMA-NVMe-VMD2`의 문서와 소스 코드를 분석해 운영체제의 NVMe 장치 인식과 내부 데이터 보존이 별개의 문제임을 확인했다. 장치가 호스트 메모리에 접근하는 DMA 전송은 IOMMU와 운영체제의 메모리 보호 정책을 따르며, 내부 저장은 휘발성 캐시 슬롯의 유지 조건에 좌우된다. 코드에서 제어기는 명령 큐와 완료 큐를 거쳐 읽기나 쓰기, Flush 요청에 완료 응답을 돌려주지만, 데이터는 비휘발성 메모리가 아닌 제한된 캐시 슬롯에만 머문다. 따라서 슬롯 충돌로 다른 블록이 같은 슬롯을 덮어쓰거나 전원이 꺼지면 기존 데이터는 사라지고 읽기 요청에 `0`이 반환된다.


이번에는 문서와 SystemVerilog 코드를 바탕으로 명령 처리 경로와 캐시 배열 구조, VMD 제어기와 NVMe 장치의 역할 구분을 확인했다. 실제 FPGA 보드에 비트스트림을 올리거나 호스트의 메모리 보호 설정을 바꾸는 실행 검증은 아직 진행하지 않았다. 합성과 배치배선, 타이밍 수렴, 슬롯 교체와 재설정 뒤의 읽기 결과는 시뮬레이션과 보드별 실행 기록으로 추가 확인이 필요하다. 휘발성 저장 구조의 제약을 분명히 알면 전원이나 재설정 조건에 맞춘 시험 범위를 정하고, 소스 검사와 시뮬레이션, 보드 실행을 단계별 근거로 연결할 수 있다.
