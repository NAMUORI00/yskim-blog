## 바이트 배열과 해석 규칙


메모리 도구의 표시를 이해하려고 바이트 순서, 자료형, 정렬을 정리했다. 예를 들어 `01 00 00 00`은 리틀 엔디언 32비트 정수로 읽으면 1이고, 바이트 배열로 읽으면 1, 0, 0, 0 네 값이다. 저장된 내용은 같아도 적용하는 규칙에 따라 표시가 달라진다.


구조체 표시에서도 숫자만으로 원래 자료형을 확정하기는 어렵다. 작은 덤프를 여러 규칙으로 읽으며 시작 위치와 해석 조건이 결과에 들어가는 지점을 살펴봤다.


## 바이트 하나의 범위


아래 예제는 한 바이트가 8비트인 일반적인 x86/x64 환경을 기준으로 삼았다. 8비트로 나타낼 수 있는 범위는 0에서 255까지 총 256가지다. 메모리 덤프에서 바이트를 16진수 두 자리로 표기하는 이유가 여기에 있다.


16진 한 자리는 4비트(0~F)를 나타내므로, 8비트를 정확히 두 자리로 적을 수 있다. `0xFF`는 이진수 `11111111`, 십진수 255와 같다.


주소 `0x1000`부터 8바이트를 읽었다고 하자.


```javascript
주소   : 0x1000  0x1001  0x1002  0x1003  0x1004  0x1005  0x1006  0x1007
바이트 :   78      56      34      12      01      00      00      00
```


이 8바이트를 어떤 단위로 묶고 어떤 방향으로 읽느냐에 따라 결과가 완전히 달라진다.


## 엔디언: 바이트를 쌓는 방향


여러 바이트를 하나의 정수로 합칠 때, 낮은 주소에 어떤 바이트를 놓느냐가 바이트 순서(endianness)다.


**리틀 엔디언(little-endian)** 은 낮은 주소에 최하위 바이트(LSB)를 둔다. x86/x64 계열 프로세서가 이 방식이다. 앞 4바이트 `78 56 34 12`를 리틀 엔디언 `uint32_t`로 읽으면 다음과 같다.


```javascript
값 = 0x78 + 0x56 × 256 + 0x34 × 65,536 + 0x12 × 16,777,216
   = 120 + 22,016 + 3,407,872 + 301,989,888
   = 305,419,896
   = 0x12345678
```


낮은 주소의 `0x78`이 값의 최하위 바이트가 되어 결과에서 가장 오른쪽에 위치한다. 반면 **빅 엔디언(big-endian)** 이라면 낮은 주소가 최상위 바이트다. 같은 `78 56 34 12`가 `0x78563412`, 즉 2,018,915,346이 된다. TCP/IP 헤더의 여러 바이트 정수 필드처럼 네트워크 바이트 순서를 정한 형식에서는 그 약속에 맞춰 읽고 써야 했다.


페이로드의 바이트 순서는 해당 형식의 규약에 맞춰 처리한다. 라이브러리가 이미 변환한 값인지, 원시 바이트인지도 구분해야 중복 변환을 피할 수 있다. [MDN의 바이트 순서 설명](https://developer.mozilla.org/en-US/docs/Glossary/Endianness)을 이 구분의 참고로 삼았다.

## 자료형에 따라 달라지는 해석


같은 8바이트를 C 자료형별로 나눠 읽어보자. 리틀 엔디언 기준이다.


| 해석         | 주소 범위         | 바이트         | 값                        |
| ---------- | ------------- | ----------- | ------------------------ |
| `uint32_t` | 0x1000~0x1003 | 78 56 34 12 | 0x12345678 (305,419,896) |
| `uint32_t` | 0x1004~0x1007 | 01 00 00 00 | 0x00000001 (1)           |
| `uint16_t` | 0x1000~0x1001 | 78 56       | 0x5678 (22,136)          |
| `uint8_t`  | 0x1000        | 78          | 120                      |


`uint8_t`일 때 `0x78`은 120이다. 만약 이 바이트가 `0xFF`였다면 `uint8_t`으로는 255, `int8_t`으로는 -1이 된다. 2의 보수 표현에서 최상위 비트가 1이면 음수로 해석되기 때문이다. 값은 같은 비트 패턴이지만, 부호 해석 하나로 의미가 완전히 뒤집어진다.


읽기 시작 위치에 따른 차이도 계산했다. `uint16_t`으로 `0x1000`부터 읽으면 `0x5678`이지만, `0x1001`부터 16비트를 읽으면 `56 34`가 `0x3456`(13,398)이 된다.


시작 위치가 1바이트 바뀌면서 다른 값이 나오는 예다. 여기에 구조체 정렬 조건이 더해지면 필드 크기의 합만으로 다음 위치를 정하기 어려울 수 있다.


## 구조체 정렬: 빈 바이트가 끼어드는 이유


필드 크기를 단순히 더했을 때 구조체의 크기와 맞지 않는 경우가 있었다. 필드마다 요구하는 정렬 경계에 맞추려면 사이에 패딩이 들어갈 수 있기 때문이다. 여기서는 `uint8_t`, `uint16_t`, `uint32_t`의 정렬 요구가 각각 1, 2, 4바이트인 일반적인 기본 배치를 가정했다. 정렬 요구는 자료형과 ABI의 배치 규칙에 따라 정해진다.


ABI, 컴파일러 옵션, 명시적 정렬 지정에 따라 확인할 값이 달라진다. [MSVC의 배치 규칙](https://learn.microsoft.com/en-us/cpp/c-language/padding-and-alignment-of-structure-members?view=msvc-170)에서도 자료형과 packing 조건을 함께 다루고 있었다.


```c
struct A {
    uint8_t  a;   // 1바이트, 오프셋 0
                   // 패딩 3바이트 (오프셋 1~3)
    uint32_t b;   // 4바이트, 오프셋 4
    uint8_t  c;   // 1바이트, 오프셋 8
                   // 패딩 1바이트 (오프셋 9)
    uint16_t d;   // 2바이트, 오프셋 10
};
// sizeof(struct A) = 12
```


필드 순서만 바꿔도 전체 크기가 줄어든다.


```c
struct B {
    uint32_t b;   // 4바이트, 오프셋 0
    uint16_t d;   // 2바이트, 오프셋 4
    uint8_t  a;   // 1바이트, 오프셋 6
    uint8_t  c;   // 1바이트, 오프셋 7
};
// sizeof(struct B) = 8
```


위 가정으로 오프셋을 계산하면 같은 필드 네 개가 각각 12바이트와 8바이트에 들어갔다. 메모리 덤프에서 구조체를 읽을 때 패딩을 고려하지 않으면 필드 오프셋이 어긋나고, 구조체 배열에서는 이 오차가 원소마다 누적된다. 컴파일러가 패딩을 넣는 이유는, 정렬되지 않은 주소에서 다중 바이트 값을 읽으면 CPU에 따라 성능 저하가 발생하거나 아예 하드웨어 예외가 나기 때문이다.

그림 2. 같은 필드를 두 순서로 배치한 바이트 오프셋. 점선 회색 칸은 패딩이며, 위에서 가정한 기본 정렬 조건으로 직접 계산했다.


## 확인 범위와 추가 검토


덤프를 해석하는 조건은 시작 위치, 자료형과 바이트 순서, ABI와 구조체 정렬로 정리했다. 실제 코드의 `sizeof`, `alignof`, `offsetof`는 가정한 배치를 대조할 값이다.


필드 순서를 바꿔 공간을 줄일 수 있어도, 이미 저장한 파일이나 외부 프로그램과의 계약을 깨뜨리면 더 큰 비용이 생길 수 있다. 그래서 배치를 바꾸는 결정과 배치를 정확히 읽는 작업을 분리해 두었다.


다음에는 같은 주소 `0x1000`이 프로세스마다 다른 메모리를 가리키는 구조와 다른 프로세스의 메모리를 읽는 절차를 살펴본다. 바이트 해석에서 주소의 소속과 접근 조건으로 범위를 넓히는 내용이다.
