실행 중인 프로그램인 프로세스의 메모리를 메모리 도구로 열어 보면, 저장된 바이트는 같은데도 읽는 규칙에 따라 전혀 다른 값이 표시된다. 예를 들어 연속된 4바이트 `01 00 00 00`은 32비트 정수 하나로 읽으면 `1`이지만, 1바이트 배열로 읽으면 `1, 0, 0, 0` 네 값이 된다. 여러 값(필드)을 하나로 묶은 구조체를 표시할 때도 화면에 찍힌 숫자만으로는 원래 자료형이나 필드 경계를 확정하기 어렵다. 메모리 내용을 그대로 옮겨 놓은 **메모리 덤프**를 어디서부터 어떤 자료형과 정렬 규칙으로 읽는지에 따라 결과가 어떻게 달라지는지 작은 예제로 따라가 봤다.


## 메모리 덤프와 16진수 바이트 표기


메모리 덤프를 읽으려면 먼저 메모리의 기본 단위인 바이트가 화면에 어떤 숫자로 적히는지 알아야 한다. 아래 예제는 한 바이트가 8비트인 일반적인 x86/x64 환경을 기준으로 삼았다. 예를 들어 16진수 `0xFF`는 이진수 `11111111`이고 십진수로는 255다. 8비트로 나타낼 수 있는 값은 0부터 255까지 모두 256가지이며, 16진수 한 자리는 4비트(`0`~`F`)에 대응한다. 따라서 메모리 덤프에서는 8비트인 한 바이트를 16진수 두 자리로 정확히 적을 수 있다.


이 표기법으로 주소 `0x1000`부터 연속된 8바이트를 읽었다고 하자.


```plain text
주소   : 0x1000  0x1001  0x1002  0x1003  0x1004  0x1005  0x1006  0x1007
바이트 :   78      56      34      12      01      00      00      00
```


이 8바이트를 몇 바이트씩 묶고 어느 방향으로 읽느냐에 따라 해석 결과가 완전히 달라진다.


## 바이트 순서와 엔디언


앞에서 본 8바이트 덤프의 첫 4바이트 `78 56 34 12`를 정수 하나로 합치면 읽는 방향에 따라 `0x12345678`이나 `0x78563412`가 된다. 이처럼 여러 바이트를 묶어 하나의 정수로 합칠 때, 낮은 메모리 주소에 어느 자리의 바이트를 놓느냐를 **바이트 순서**(endianness)라고 한다.


**리틀 엔디언**(little-endian)은 자릿값이 가장 작은 최하위 바이트(LSB)를 낮은 주소에 두는 방식이며, x86/x64 계열 프로세서가 이 방식을 쓴다. 앞의 덤프에서 처음 4바이트 `78 56 34 12`를 리틀 엔디언 방식의 부호 없는 32비트 정수(`uint32_t`)로 읽으면 다음과 같이 계산된다.


```plain text
값 = 0x78 + 0x56 × 256 + 0x34 × 65,536 + 0x12 × 16,777,216
   = 120 + 22,016 + 3,407,872 + 301,989,888
   = 305,419,896
   = 0x12345678
```


가장 낮은 주소(`0x1000`)에 있는 `0x78`이 최하위 바이트가 되어 16진수 결과 `0x12345678`의 맨 오른쪽에 자리 잡는다. 반대로 **빅 엔디언**(big-endian)은 자릿값이 가장 큰 최상위 바이트(MSB)를 낮은 주소에 둔다. 같은 `78 56 34 12`를 빅 엔디언으로 읽으면 `0x78563412`가 되고, 십진수로는 2,018,915,346이다.


![주소 0x1000부터 0x1003에 저장된 78 56 34 12가 리틀 엔디언에서는 0x12345678로, 빅 엔디언에서는 0x78563412로 해석되는 비교도](/images/notion/tech-k01/image-1.png)


그림 1. 주소 0x1000~0x1003의 4바이트(78 56 34 12)를 리틀 엔디언과 빅 엔디언으로 읽었을 때의 값 비교(직접 계산한 예).


프로그램이 외부와 데이터를 주고받을 때도 이 바이트 순서 약속을 맞춰야 한다. TCP/IP 헤더의 여러 바이트 정수 필드처럼 네트워크 바이트 순서를 정한 형식에서는 그 규약에 맞춰 읽고 써야 한다. 반면 패킷 안에 담기는 실제 데이터인 페이로드의 바이트 순서는 해당 데이터 형식의 규약을 따른다. 이때 라이브러리가 바이트 순서를 이미 변환해 준 값인지, 변환 전의 원시 바이트인지도 구분해야 같은 값을 두 번 뒤집는 중복 변환을 피할 수 있다. 이 구분은 [MDN의 바이트 순서 설명](https://developer.mozilla.org/en-US/docs/Glossary/Endianness)을 참고했다.


## 자료형과 읽기 시작 주소


바이트 순서를 리틀 엔디언으로 고정하더라도, 몇 바이트짜리 자료형으로 끊어 읽고 어디서부터 읽는지에 따라 값은 다시 달라진다. 앞의 8바이트 덤프를 리틀 엔디언 기준에서 C 언어의 부호 없는 정수 자료형별로 나눠 읽으면 다음과 같다.


| 해석         | 주소 범위         | 바이트         | 값                        |
| ---------- | ------------- | ----------- | ------------------------ |
| `uint32_t` | 0x1000~0x1003 | 78 56 34 12 | 0x12345678 (305,419,896) |
| `uint32_t` | 0x1004~0x1007 | 01 00 00 00 | 0x00000001 (1)           |
| `uint16_t` | 0x1000~0x1001 | 78 56       | 0x5678 (22,136)          |
| `uint8_t`  | 0x1000        | 78          | 120                      |


![메모리 덤프 78 56 34 12를 LE uint32, BE uint32, uint8 배열, LE uint16 배열로 각각 읽었을 때 나오는 값 비교도](/images/notion/tech-k01/image-2.png)


그림 2. 같은 4바이트를 자료형과 바이트 순서에 따라 해석한 결과(직접 계산한 설명용 예제).


한 번에 읽는 바이트 폭뿐 아니라 부호 유무도 결과를 바꾼다. 표에서 주소 `0x1000`의 `0x78`은 부호 없는 1바이트 정수(`uint8_t`)로 읽으면 120이다. 만약 이 자리에 `0xFF`(이진수 `11111111`)가 들어 있다면 `uint8_t`로는 255가 되지만, 부호 있는 1바이트 정수(`int8_t`)로는 -1이 된다. 컴퓨터가 음수를 표현하는 2의 보수 규칙에서는 가장 앞 비트인 최상위 비트가 1일 때 음수로 해석하기 때문이다. 메모리에 저장된 비트 패턴은 같아도 부호 해석 하나로 값의 의미가 뒤집어진다.


읽기 시작하는 주소가 달라질 때의 차이도 계산해 봤다. 주소 `0x1000`부터 2바이트를 부호 없는 16비트 정수(`uint16_t`)로 읽으면 `78 56`이 묶여 `0x5678`(22,136)이 된다. 그런데 시작 주소를 1바이트 뒤인 `0x1001`로 옮겨 16비트를 읽으면 `56 34`가 묶여 `0x3456`(13,398)이 된다.


![0x1000–0x1001 구간을 읽은 0x5678과 1바이트 밀린 0x1001–0x1002 구간을 읽은 0x3456을 비교한 메모리 구간 그림](/images/notion/tech-k01/image-3.png)


그림 3. 읽기 시작 주소가 0x1000에서 0x1001로 1바이트 밀렸을 때 달라지는 uint16_t 해석 값(직접 계산한 예).


시작 주소가 1바이트만 밀려도 전혀 다른 값이 나오는 것이다. 단일 변수가 아니라 여러 필드를 묶은 구조체를 읽을 때는 각 필드의 시작 위치를 잡기가 더 까다롭다. 구조체 정렬 조건이 더해지면 앞 필드들의 크기를 단순하게 더한 값만으로는 다음 필드의 위치를 정하기 어렵기 때문이다.


## 구조체 정렬과 패딩


앞 절에서 본 것처럼 구조체에 들어 있는 각 필드의 크기를 그냥 더했을 때 실제 구조체 전체 크기(`sizeof`)와 맞지 않는 경우가 있었다. 예를 들어 1바이트, 4바이트, 1바이트, 2바이트 필드 네 개를 순서대로 묶으면 데이터 크기의 합은 8바이트지만 구조체 크기는 12바이트가 될 수 있다. 컴파일러가 각 필드가 요구하는 정렬 경계(alignment boundary)에 시작 주소를 맞추려고 사이에 빈 바이트인 **패딩**(padding)을 넣기 때문이다. 정렬되지 않은 주소에 걸친 다중 바이트 값을 읽으면 CPU에 따라 접근 성능이 떨어지거나 아예 하드웨어 예외가 발생한다.


각 필드의 정렬 요구치는 자료형과 플랫폼 ABI(이진 인터페이스 규약)의 배치 규칙에 따라 정해지며, 컴파일러 옵션이나 명시적 정렬 지정에 따라서도 달라진다. [MSVC의 배치 규칙](https://learn.microsoft.com/en-us/cpp/c-language/padding-and-alignment-of-structure-members?view=msvc-170) 문서에서도 자료형별 정렬 기준과 패킹(packing) 조건을 함께 다루고 있었다. 여기서는 `uint8_t`, `uint16_t`, `uint32_t`가 각각 1, 2, 4바이트의 배수 주소에 놓이는 기본 배치를 가정했다. 이 조건에서 구조체 시작점으로부터 떨어진 바이트 거리인 오프셋을 두 구조체별로 계산했다.


```c
struct A {
    uint8_t  a;   // 1바이트, 오프셋 0
                   // 패딩 3바이트 (오프셋 1~3)
    uint32_t b;   // 4바이트, 오프셋 4
    uint8_t  c;   // 1바이트, 오프셋 8
                   // 패딩 1바이트 (오프셋 9)
    uint16_t d;   // 2바이트, 오프셋 10
};
// sizeof(struct A) = 12
```


`struct A`에서는 1바이트 필드 `a` 뒤에 4바이트 정수 `b`가 온다. `b`는 4의 배수 주소에서 시작해야 하므로 오프셋 1부터 3까지 3바이트가 패딩으로 비워진다. 마찬가지로 오프셋 8에 놓인 `c` 뒤에도 2의 배수 주소를 요구하는 `d`를 맞추기 위해 오프셋 9에 패딩 1바이트가 들어간다. 실제 데이터는 8바이트뿐이지만 구조체 크기는 12바이트가 된다.


같은 필드 네 개라도 선언 순서만 바꾸면 전체 크기가 줄어든다.


```c
struct B {
    uint32_t b;   // 4바이트, 오프셋 0
    uint16_t d;   // 2바이트, 오프셋 4
    uint8_t  a;   // 1바이트, 오프셋 6
    uint8_t  c;   // 1바이트, 오프셋 7
};
// sizeof(struct B) = 8
```


`struct B`처럼 크기가 큰 필드부터 배치하면 모든 필드가 패딩 없이 자신의 정렬 경계(0, 4, 6, 7)에 바로 놓여 8바이트 안에 들어간다.


![선언 순서 a, b, c, d일 때 패딩이 포함되어 12바이트가 되는 배치와 b, d, a, c일 때 패딩 없이 8바이트가 되는 배치 비교도](/images/notion/tech-k01/image-4.png)


그림 4. 같은 필드를 두 순서로 배치한 바이트 오프셋 비교(점선 칸은 패딩이며, 본문에서 가정한 기본 정렬 조건으로 직접 계산한 예).


메모리 덤프에서 구조체를 읽을 때 패딩을 고려하지 않으면 필드 오프셋이 어긋나고, 구조체 배열에서는 이 오차가 원소마다 누적된다. 가정한 구조체 배치가 실제 실행 파일과 맞는지 검증할 때는 코드에서 `sizeof`, `alignof`, `offsetof` 결과를 출력해 대조할 수 있다. 또한 필드 순서를 바꿔 메모리 공간을 줄일 수 있더라도, 이미 저장한 파일이나 외부 프로그램과 주고받는 데이터 형식이 정해져 있다면 함부로 배치를 바꿀 수 없다. 기존 계약을 깨뜨리면 데이터를 읽는 쪽이 모든 필드를 어긋난 위치에서 읽게 되어 더 큰 수정 비용이 생기기 때문이다. 그래서 새 구조를 설계할 때 배치를 바꾸는 결정과, 이미 정해진 배치를 덤프에서 정확히 읽어 내는 작업은 분리해 두었다.


## 결론


지금까지 따라가 본 예제들은 메모리 덤프에 적힌 같은 바이트라도 읽는 규칙에 따라 전혀 다른 값으로 해석된다는 점을 보여 준다. 메모리 덤프를 정확히 해석하려면 읽기 시작 위치, 자료형의 크기와 부호와 바이트 순서, 컴파일 환경의 ABI와 구조체 정렬 규칙을 먼저 확인해야 한다.


이 글에서는 주소 `0x1000`에 놓인 8바이트 덤프와 C 구조체 예제를 계산해 이 규칙들이 읽히는 값을 어떻게 바꾸는지 확인했다. 반면 그 주소 `0x1000` 자체가 프로세스 안에서 어떻게 정해지고 관리되는지는 아직 다루지 않았다. 다음 글에서는 같은 주소 `0x1000`이 왜 프로세스마다 서로 다른 메모리를 가리키는지, 다른 프로세스의 메모리를 읽으려면 어떤 절차를 거쳐야 하는지 다룬다.
