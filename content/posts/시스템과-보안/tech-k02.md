앞 글에서는 메모리의 바이트 열을 자료형에 맞춰 해석하는 방법을 다뤘다. 하지만 실행 중인 프로그램의 메모리를 읽을 때는 자료형을 정하기 전에 먼저 확인해야 할 조건이 있다. 두 프로그램이 똑같이 `0x00401000` 주소를 읽어도 서로 다른 값이 나온다. 또한 외부 도구가 대상 프로그램의 `0x00401000`을 읽으려 할 때는 운영체제의 권한 검사를 통과해야 한다.


실행 중인 프로그램인 프로세스(process)는 각자 분리된 주소 공간을 쓰므로, 주소 숫자가 같아도 프로세스에 따라 실제 메모리 위치가 달라진다. 여기에 더해 다른 프로세스의 메모리에 접근하려면 주소 변환과 별개로 운영체제가 정한 접근 규칙을 충족해야 한다. 이 글에서는 Windows 환경을 기준으로 프로세스별 주소 공간이 분리되는 원리와 다른 프로세스의 메모리를 읽을 때 거치는 권한 검사 과정을 다룬다.


## 가상 주소 공간의 구조


두 프로세스가 같은 주소 숫자에서 서로 다른 값을 읽는 이유를 이해하려면, 먼저 운영체제가 프로세스에 메모리 주소를 나누어 주는 방식을 알아야 한다. 프로그램이 다루는 메모리 주소는 실제 RAM의 물리 주소가 아니라 운영체제가 프로세스마다 따로 제공하는 **가상 주소**(virtual address)다. Windows의 주소 공간 문서를 읽을 때도 메모리 주소를 담는 포인터로 표현할 수 있는 가상 주소의 범위와 실제 물리 RAM에 확보된 용량을 구분해서 봐야 한다.


가상 주소가 모인 전체 범위인 가상 주소 공간은 크게 일반 프로그램이 사용하는 사용자 영역과 운영체제 핵심부가 사용하는 커널 영역으로 나뉜다. 다음 표는 32비트 Windows에서 기본으로 삼는 2GB 대 2GB 분할 구조다. 이 분할 비율은 부팅 설정이나 운영체제 조건에 따라 달라질 수 있으며, 실제 물리 RAM에 올라와 있는 메모리양은 주소 범위와 별도로 관리된다.


| 영역     | 주소 범위                       | 용도                   |
| ------ | --------------------------- | -------------------- |
| 사용자 영역 | `0x00000000` ~ `0x7FFFFFFF` | 프로세스의 코드, 데이터, 힙, 스택 |
| 커널 영역  | `0x80000000` ~ `0xFFFFFFFF` | 운영체제 커널이 사용          |


64비트 환경에서는 표현할 수 있는 주소 범위가 훨씬 넓어지는데, 정확한 상한선은 Windows 버전과 프로세스 구성 조건에 따라 달라진다. 다만 메모리를 읽고 분석할 때는 버전별 상한 숫자를 외우기보다, 다루려는 주소가 프로세스의 사용자 영역과 운영체제의 커널 영역 중 어디에 속하는지 구별하는 일이 중요하다.

## 페이지 테이블과 주소 변환


앞 절에서 본 사용자 영역의 주소 공간은 프로세스마다 서로 겹치지 않는 **사적**(private) 공간으로 분리된다. 예를 들어 프로세스 A의 `0x00401000`과 프로세스 B의 `0x00401000`은 주소 숫자만 같을 뿐, 실제 물리 메모리에서는 서로 다른 위치에 연결된다.


운영체제는 메모리를 일정한 크기의 조각인 페이지(page) 단위로 나누어 관리한다. 가상 주소를 실제 물리 주소로 바꾸는 작업은 가상 페이지와 물리 메모리 위치를 짝지어 기록한 표인 **페이지 테이블**(page table)이 중개한다. 운영체제는 프로세스마다 별도의 페이지 테이블을 유지하고, CPU는 메모리에 접근할 때 현재 프로세스의 페이지 테이블에 정의된 연결 정보(매핑)를 따라 주소를 변환한다. 이때 최근 변환 결과를 CPU 내부 캐시인 TLB(Translation Lookaside Buffer)에 보관해 두면 매번 페이지 테이블을 다시 읽는 비용을 줄일 수 있다.


[Microsoft의 주소 공간 설명](https://learn.microsoft.com/en-us/windows/win32/memory/virtual-address-space)을 바탕으로 사용자 영역의 주소가 프로세스마다 다르게 연결되는 예를 들면 다음과 같다. 프로세스 A의 페이지 테이블에는 가상 주소 `0x00401000`을 물리 주소 `0x1A3000`으로 연결하는 매핑이 들어 있다. 이 상태에서 프로세스 A가 `0x00401000`을 읽으면, CPU는 물리 메모리 `0x1A3000`에서 데이터를 가져온다. 반면 프로세스 B가 같은 가상 주소 `0x00401000`을 읽으면, CPU는 프로세스 B의 페이지 테이블을 따라 `0x5B7000` 같은 전혀 다른 물리 주소를 참조한다.


![프로세스 A와 프로세스 B의 같은 가상 주소 0x00401000이 각 페이지 테이블을 통해 물리 주소 0x1A3000과 0x5B7000에 각각 매핑되는 다이어그램](/images/notion/tech-k02/image-2.png)


그림 2. 같은 가상 주소가 프로세스별 페이지 테이블을 거쳐 서로 다른 물리 주소에 연결되는 구조(설명용 예제).


그림 2처럼 서로 다른 물리 페이지에 연결된 사적 메모리는 한 프로세스가 값을 써도 다른 프로세스의 데이터를 덮어쓰지 않는다. 다만 운영체제가 허용한 공유 메모리 영역에서는 여러 프로세스가 같은 물리 페이지를 함께 가리킬 수 있다. 따라서 모든 가상 페이지가 언제나 서로 다른 물리 메모리에 연결된다고 단정할 수는 없다.


이처럼 프로세스마다 분리된 페이지 테이블은 주소 공간 격리의 기반이 된다. 페이지 테이블을 여러 단계로 나누어 관리하는 이유와 TLB가 주소 변환 비용을 줄이는 구체적인 과정은 주소 변환을 자세히 다루는 다음 글로 남겼다.


## 핸들 발급과 메모리 조회


앞 절에서 보듯 가상 주소 공간이 프로세스마다 분리되어 있으므로, 한 프로세스가 다른 프로세스의 메모리를 포인터로 직접 읽을 수는 없다. 다른 프로세스의 주소 공간에 접근하려면 운영체제에 중개를 요청해야 하는데, Windows에서 이 경로의 시작점이 **핸들**(handle)이다. 핸들은 프로세스나 파일처럼 운영체제가 관리하는 자원에 접근할 때 운영체제가 발급해 주는 식별값이다.


대상 프로세스의 핸들은 `OpenProcess` 함수를 호출해 얻는다. 이때 대상 프로세스 ID와 함께 어떤 작업을 수행할지 나타내는 접근 권한을 지정해야 한다.


```c
HANDLE hProc = OpenProcess(
    PROCESS_VM_READ,   // 메모리 읽기 권한 요청
    FALSE,             // 핸들 상속 여부
    targetPid          // 대상 프로세스 ID
);
```


`OpenProcess`가 호출되면 운영체제는 호출자를 실행한 계정과 권한 정보가 담긴 보안 토큰(token)을 확인한다. 대상 프로세스에는 보안 정보를 담은 보안 서술자(security descriptor)가 있다. 이 서술자 안의 DACL(Discretionary Access Control List)에는 누구에게 어떤 접근을 허용하거나 거부할지 적힌 규칙 목록이 들어 있다. 운영체제는 호출자의 보안 토큰과 요청한 권한을 대상 프로세스의 DACL과 대조해 핸들 발급 여부를 결정한다.


권한 검사에서 접근이 거부되면 `OpenProcess`는 `NULL`을 반환하고 오류 코드로 `ERROR_ACCESS_DENIED`를 남긴다. 다만 대상 프로세스 ID가 유효하지 않은 경우처럼 권한 외의 이유로도 호출이 실패할 수 있다. 따라서 반환값이 `NULL`인지 확인하는 것에 그치지 않고 오류 코드까지 함께 확인해 실패 원인을 구분해야 한다.


유효한 핸들을 얻은 뒤에는 `ReadProcessMemory` 함수에 핸들과 대상 프로세스의 가상 주소를 넘겨 데이터를 읽어 온다. 아래 코드는 직접 만든 테스트 프로세스에서 메모리를 읽는 흐름을 발췌한 예제다.


```c
uint8_t buffer[4];
SIZE_T bytesRead = 0;
BOOL ok = ReadProcessMemory(hProc, (LPCVOID)0x00401000,
                            buffer, sizeof(buffer), &bytesRead);
// hProc의 유효성, ok와 bytesRead를 확인한 뒤에만 buffer를 해석한다.
// 사용을 마친 유효한 핸들은 CloseHandle(hProc)로 해제한다.
```


이 코드는 대상 프로세스의 가상 주소 `0x00401000`에서 4바이트를 읽어 `buffer`에 복사한다. 여기서 주의할 점은 핸들 발급이 성공했다고 해서 메모리 읽기까지 자동으로 성공하지는 않는다는 것이다. `ReadProcessMemory`가 성공하려면 핸들에 읽기 권한(`PROCESS_VM_READ`)이 있어야 한다. 여기에 더해 요청한 주소 범위의 페이지가 대상 프로세스 안에서 실제로 매핑되어 있고 읽을 수 있는 상태여야 한다. 따라서 핸들의 유효성과 함수 반환값(`ok`), 실제로 읽힌 바이트 수(`bytesRead`)를 모두 확인한 뒤에만 `buffer`의 값을 해석해야 한다.


## 접근 권한 플래그의 조합


앞 절에서 `OpenProcess`에 전달한 `PROCESS_VM_READ`처럼, 접근 권한은 이진수 자리마다 권한 하나를 배정한 비트 플래그로 정의되어 있다. 프로세스를 다룰 때 자주 쓰는 접근 권한 플래그는 다음과 같다.


| 플래그                         | 값      | 의미                              |
| --------------------------- | ------ | ------------------------------- |
| `PROCESS_VM_READ`           | 0x0010 | `ReadProcessMemory`로 메모리 읽기     |
| `PROCESS_VM_WRITE`          | 0x0020 | `WriteProcessMemory`로 메모리 쓰기    |
| `PROCESS_VM_OPERATION`      | 0x0008 | 주소 공간 조작 (`VirtualProtectEx` 등) |
| `PROCESS_QUERY_INFORMATION` | 0x0400 | 토큰, 종료 코드, 우선순위 등 조회            |
| `PROCESS_TERMINATE`         | 0x0001 | `TerminateProcess`로 종료          |


여러 권한이 동시에 필요할 때는 같은 자리의 비트를 합치는 비트 OR(`|`) 연산으로 플래그를 조합한다. 예를 들어 `PROCESS_VM_READ | PROCESS_VM_OPERATION`을 지정하면 `0x0010 | 0x0008`을 계산해 `0x0018`이 된다. 이 값을 전달하면 메모리 읽기와 주소 공간 조작 권한을 한꺼번에 요청하게 된다. 두 값에 겹치는 비트가 없으므로 결과값은 두 숫자를 그대로 더한 값과 같다.


![PROCESS_VM_READ(0x0010)와 PROCESS_VM_OPERATION(0x0008)을 비트 OR 연산으로 합쳐 0x0018을 만드는 과정](/images/notion/tech-k02/image-3.png)


그림 3. 필요한 접근 권한 플래그만 비트 OR 연산으로 조합해 최소 권한을 요청하는 계산 예.


모든 접근 권한을 한 번에 요청하는 `PROCESS_ALL_ACCESS` 플래그도 있다. 하지만 메모리 읽기만 필요한 도구에서는 쓰기나 프로세스 종료 같은 불필요한 권한을 빼고 최소 권한만 요청하는 편이 낫다. 수행할 작업에 맞춰 요청 범위를 좁혀 두면 권한이 거부되었을 때 어느 작업 조건에서 막혔는지도 파악하기 쉽다.


## 보호 프로세스와 접근 경계


최소 권한만 골라 요청하더라도 일반 프로세스의 접근 검사 규칙만으로 모든 결과를 설명할 수는 없다. Windows의 **보호 프로세스**(protected process)는 보안상 중요한 프로세스를 보호하기 위해 메모리 읽기나 쓰기 같은 접근 권한에 추가 제한을 둔다. 따라서 관리자 권한이나 디버깅 권한이 있다는 이유만으로 모든 대상 프로세스에 접근할 수 있을 것이라 예상하면 실제 결과와 어긋날 수 있다.


보호 프로세스를 상대로 어떤 접근 권한이 허용되는지는 [프로세스 보안과 접근 권한 문서](https://learn.microsoft.com/en-us/windows/win32/procthread/process-security-and-access-rights)에서 대상별 조건을 따로 확인해야 한다. 지금까지 다룬 핸들 발급 단계의 접근 검사와 실제 메모리 읽기 단계의 페이지 상태 검사를 하나의 흐름으로 묶으면 그림 4와 같다.

## 결론


다른 프로세스의 메모리를 읽는 과정은 페이지 테이블을 통한 주소 변환과 운영체제의 접근 검사로 나뉜다. 페이지 테이블은 가상 주소가 물리 메모리의 어느 위치로 연결되는지를 정하고, 핸들의 접근 권한과 대상 페이지의 상태는 그 메모리를 읽을 수 있는지를 정한다. 두 단계를 구분하면 메모리 읽기 도구를 만들 때 대상 프로세스 ID, 요청할 권한과 주소 범위, 단계별 반환값과 오류 코드를 왜 따로 기록하고 확인해야 하는지가 분명해진다.


이번 글에서는 가상 주소가 이미 물리 메모리에 매핑되어 있는 상황을 가정하고 주소 분리와 권한 검사 흐름을 확인했다. 참조하려는 가상 주소에 물리 메모리 매핑이 아직 없거나 페이지 권한이 맞지 않을 때 CPU와 운영체제가 이를 처리하는 과정은 아직 확인하지 않았다. 이러한 예외 처리 과정과 함께, 페이지 테이블을 여러 단계로 나누는 구조와 각 단계에서 가상 주소의 어떤 비트를 인덱스로 쓰는지는 다음 글에서 이어서 다룬다.
