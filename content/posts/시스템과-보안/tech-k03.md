여러 프로그램이 공통으로 쓰는 기능은 공유 라이브러리(`.so`, `.dll`) 파일로 따로 묶어 둔다. 라이브러리의 함수 이름을 `getData`에서 `fetchData`로 바꾸면, 소스 코드를 기계어로 번역(컴파일)할 때 곧바로 오류가 난다. 반면 소스 코드와 이미 빌드된 프로그램은 그대로 두고 공유 라이브러리 버전만 올려 교체하면, 실행 중에 엉뚱한 값을 읽거나 함수를 찾지 못해 멈추는 경우가 있다.


똑같이 라이브러리를 수정했는데도 문제가 드러나는 시점과 양상이 다른 이유는 각 단계에서 기대는 약속이 서로 다르기 때문이다. 이 글에서는 소스 코드가 의존하는 약속인 API와 컴파일된 기계어 파일(바이너리)이 의존하는 약속인 ABI가 각각 무엇을 규정하는지 작은 예제로 비교한다.


## 소스 코드 사이의 약속인 API


두 약속 가운데 먼저 소스 코드를 작성하고 컴파일할 때 적용되는 규칙을 아래 C 함수 선언으로 본다.


```c
int add(int a, int b);
```


이 선언을 가져다 쓰는 소스 코드는 함수 이름이 `add`이고, 정수(`int`) 입력값 두 개를 받아 정수 결과를 돌려준다는 형식에 의존한다. 이처럼 소스 코드 수준에서 함수를 호출하는 쪽과 호출되는 쪽이 맺는 약속을 **API**(Application Programming Interface)라고 한다. 함수 이름과 입력값(매개변수, 인자)의 타입, 반환값의 타입, 함수를 호출하는 순서가 여기에 속한다. 라이브러리에서 함수 이름을 `add`에서 `sum`으로 바꾸면 호출하는 쪽 소스 코드도 함께 고쳐서 다시 컴파일해야 한다. 또한 매개변수 타입이 바뀌더라도 컴파일러가 타입을 자동으로 맞춰 주는 암시적 형변환 덕분에 컴파일이 그대로 통과할 수 있다. 따라서 문법 형식뿐 아니라 반환값의 의미나 예외 처리 방식 같은 동작 규칙도 API의 일부로 함께 확인해야 한다.


## 바이너리 사이의 약속인 ABI


소스 코드가 API에 맞춰 컴파일을 통과한 뒤에는 기계어로 번역된 바이너리 파일 사이의 약속이 필요하다. **ABI**(Application Binary Interface)는 컴파일된 바이너리들이 서로 맞물려 실행될 때 유지되어야 하는 규칙이다. 함수를 호출할 때 인자를 CPU 안의 임시 저장 공간인 레지스터 가운데 어디에 넣을지, 반환값을 어디에 저장할지가 ABI에 들어간다. 여러 데이터를 묶은 구조체에서 각 항목(필드)이 시작 주소로부터 몇 바이트 떨어진 위치(오프셋)에 놓이는지도 ABI가 정한다.


이 가운데 인자와 반환값을 주고받는 규칙을 **호출 규약**(calling convention)이라고 부른다. 예를 들어 x86-64 리눅스의 [System V AMD64 호출 규약](https://refspecs.linuxbase.org/elf/x86_64-abi-0.99.pdf)에서는 처음 여섯 정수 인자를 RDI, RSI, RDX, RCX, R8, R9 레지스터에 차례로 넣는다. 그리고 함수의 계산 결과인 반환값은 RAX 레지스터에 담아 돌려준다. 이 규약에서 `add(3, 5)`를 호출하면 컴파일러는 RDI에 3, RSI에 5를 넣는 기계어 코드를 생성하고, 호출된 함수는 두 값을 더한 8을 RAX에 넣는다.


![호출자가 RDI에 3, RSI에 5를 넣어 add 연산을 호출하고 RAX에 담긴 8을 반환값으로 읽는 흐름도](/images/notion/tech-k03/image-1.png)


그림 1. System V AMD64 호출 규약에서 add(3, 5)를 호출할 때 인자와 반환값이 레지스터를 거치는 흐름을 나타낸 설명용 예제다.


호출하는 쪽은 System V AMD64 규약을 따르고 호출되는 쪽은 첫 두 정수 인자를 RCX와 RDX로 받는 Windows x64 규약을 따르면 값이 어긋난다. 같은 소스 코드를 컴파일했더라도 바이너리끼리 따르는 규약이 달라 인자를 엉뚱한 레지스터에서 읽으면서 값이 꼬이기 때문이다.


## 구조체 필드 순서와 메모리 배치


레지스터 호출 규약과 마찬가지로 구조체가 메모리에 놓이는 배치 또한 소스 코드 표현과 별개로 ABI가 결정한다. 아래 C 구조체 `Sensor`처럼 소스 코드에서 필드에 접근하는 표현은 같아도 바이너리의 메모리 배치는 달라질 수 있다.


```c
struct Sensor {
    char  id;     // 1바이트
    int   value;  // 4바이트
    char  flag;   // 1바이트
};
```


이 예제에서는 `char`가 1바이트, `int`가 4바이트이고, `int`가 4바이트의 배수 주소에 놓여야 하는(4바이트 정렬 요구) 기본 ABI를 가정한다. 이 조건에서 컴파일러는 `int` 필드인 `value`를 4바이트 경계에 맞추려고 `id` 뒤에 빈 공간인 **패딩**(padding) 3바이트를 넣는다. 마지막 `flag` 뒤에도 구조체 전체 크기를 4바이트 정렬에 맞추기 위해 패딩 3바이트가 붙어, `sizeof(Sensor)`는 12바이트가 된다(배치 A).


반면 필드 선언 순서를 `int value; char id; char flag;`로 바꾸면 4바이트인 `value`가 오프셋 0에 먼저 놓인다. 그 뒤에 1바이트인 `id`와 `flag`가 차례로 놓이고 끝에 패딩 2바이트만 붙어 전체 크기가 8바이트로 줄어든다(배치 B).


![12바이트인 배치 A에서는 value가 오프셋 4에 놓이고 8바이트인 배치 B에서는 value가 오프셋 0에 놓이는 구조체 메모리 배치 비교도](/images/notion/tech-k03/image-2.png)


그림 2. Sensor 구조체의 필드 순서에 따라 패딩 위치와 value 필드의 오프셋이 달라지는 두 메모리 배치를 비교한 개념도다.


| 배치                   | id 오프셋 | value 오프셋 | flag 오프셋 | 패딩 위치     | 전체 크기 |
| -------------------- | ------ | --------- | -------- | --------- | ----- |
| A: id → value → flag | 0      | 4         | 8        | 1–3, 9–11 | 12바이트 |
| B: value → id → flag | 4      | 0         | 5        | 6–7       | 8바이트  |


소스 코드에서는 어느 배치든 `s.value`라고 쓰면 컴파일러가 선언에 맞는 오프셋으로 접근 코드를 만들어 준다. 하지만 기존 프로그램을 다시 컴파일하지 않고 공유 라이브러리만 배치 B로 빌드된 버전으로 교체하면 문제가 생긴다. 한쪽 바이너리는 오프셋 4에서 `value`를 읽고 다른 쪽 바이너리는 오프셋 0에서 읽으므로, 같은 메모리를 두고 서로 다른 바이트를 가져가게 된다.


## 함수 이름과 매개변수 타입 변경


앞서 본 규칙들은 라이브러리를 배포한 뒤 인터페이스를 고칠 때 실제 호환성 문제로 이어진다. 사용자가 이미 프로그램을 컴파일해 쓰고 있는 상황에서 라이브러리를 수정하면 어떤 일이 일어나는지 두 가지 경우로 나누어 본다.


첫째로 헤더 파일에서 내보내는 함수 이름을 `getData`에서 `fetchData`로 고치면, 호출하는 소스 코드도 수정해 다시 컴파일해야 하므로 API가 바뀐다. 동시에 컴파일된 바이너리 안에서 함수 이름과 주소를 기록해 두는 목록인 **심볼 테이블**(symbol table)에서도 이름이 바뀐다. 따라서 기존 실행 파일을 다시 컴파일하지 않은 채 새 라이브러리에 연결하면 `getData` 심볼을 찾지 못해 ABI 변경도 함께 일어난다.


둘째로 매개변수 타입을 `int`에서 `long`으로 바꾸면 소스 코드에서 형변환이 필요할 수 있어 API가 바뀐다. 컴파일된 바이너리에서도 인자를 전달하는 레지스터 폭이나 메모리(스택) 배치가 달라질 수 있어 ABI까지 영향을 받는다. 이때 같은 64비트 환경이라는 말만 보고 자료형 크기를 단정해서는 안 된다. 리눅스 등에서 주로 쓰는 LP64 데이터 모델에서는 `int`가 4바이트이고 `long`이 8바이트다. 반면 Windows 64비트 환경의 LLP64 데이터 모델에서는 `int`와 `long`이 모두 4바이트다. 정확한 판단을 위해서는 [Windows x64 ABI 문서](https://learn.microsoft.com/en-us/cpp/build/x64-software-conventions?view=msvc-170)처럼 대상 플랫폼 ABI의 자료형 크기 표를 직접 확인해야 한다.


![LP64에서는 int가 4바이트, long이 8바이트이고 LLP64에서는 int와 long 모두 4바이트임을 비교한 그림](/images/notion/tech-k03/image-3.png)


그림 3. 64비트 환경의 LP64 모델과 Windows x64의 LLP64 모델에서 int와 long 자료형의 바이트 크기를 비교한 개념도다.


## 컴파일과 링크 과정의 호환성 경계


이처럼 함수 선언 하나를 고쳐도 API와 ABI가 함께 흔들릴 수 있으므로, 빌드와 실행 과정에서 두 경계가 어디에 놓이는지 구분해야 한다. 프로그램을 빌드할 때 소스 코드가 컴파일러로 넘어가는 단계에는 API 경계가 놓인다. 컴파일된 오브젝트 파일과 공유 라이브러리가 연결 도구인 링커(linker)로 묶이는 단계에는 ABI 경계가 놓인다. 컴파일 오류로 API 변화의 일부를 찾아낼 수 있지만, 함수의 동작 의미가 달라진 것까지 컴파일러가 잡아 주지는 못한다. ABI 역시 링커가 심볼 테이블에서 함수 이름을 찾는 데 성공하더라도, 구조체 크기나 호출 규약이 다르면 실행 중에야 문제가 드러난다.


![소스 코드에서 컴파일러로 넘어갈 때 API 경계가 적용되고 오브젝트 파일과 공유 라이브러리가 링커로 연결될 때 ABI 경계가 적용되는 빌드 흐름도](/images/notion/tech-k03/image-4.png)


그림 4. 컴파일과 링크 과정에서 API 경계와 ABI 경계가 놓이는 위치를 나타낸 설명용 구조도로, ABI 호환성은 링크가 성공한 뒤에도 실행 시점까지 별도로 확인해야 한다.


따라서 라이브러리를 수정하거나 버전을 올릴 때는 사용하는 쪽이 라이브러리에 연결되는 방식에 따라 확인 대상을 두 갈래로 나누어 점검한다. 소스를 다시 컴파일하는 경우(API 경계)에는 함수 이름, 매개변수 타입, 반환 타입과 함께 함수의 동작 의미가 그대로 유지되는지 확인해야 한다. 이미 컴파일된 바이너리에 연결하는 경우(ABI 경계)에는 심볼 이름뿐 아니라 호출 규약, 자료형 크기, 구조체 필드 오프셋이 이전 바이너리와 일치하는지 확인해야 한다.


## 결론


라이브러리를 고쳤을 때 컴파일 단계에서 곧바로 오류가 나는지, 아니면 실행 도중에야 문제가 터지는지는 수정 내용이 건드린 약속에 따라 갈린다. API는 소스 코드가 컴파일될 때 기대는 함수 형식과 동작 의미의 약속이고, ABI는 컴파일된 바이너리끼리 레지스터와 메모리를 주고받을 때 기대는 약속이다. 기존 실행 파일은 그대로 두고 공유 라이브러리(`.so`, `.dll`) 파일만 새 버전으로 교체하는 운영 환경이 두 경계의 차이가 드러나는 대표적인 상황이다.


이 글에서는 레지스터 호출 규약, 구조체 메모리 배치, 64비트 데이터 모델 예제로 API와 ABI가 갈리는 지점과 호환성 확인 기준을 정리했다. 다만 링크 방식에 따른 ABI 검사 시점이나, C++에서 매개변수 타입까지 함수 이름에 인코딩하는 이름 장식(name mangling)은 아직 다루지 않았다. 정적 링크와 동적 링크에서 ABI 경계가 실제로 검사되는 시점이 어떻게 다른지, 그리고 이름 장식이 심볼 테이블에서 어떤 역할을 하는지는 다음 주제로 남겨 둔다.
