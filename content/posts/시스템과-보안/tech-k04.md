프로그램이 메모리를 읽고 쓸 때 CPU는 실제 메모리 위치를 직접 다루지 않는다. 실행 중인 프로그램인 프로세스마다 독립된 가상 주소를 쓰고, 하드웨어가 이를 실제 위치인 물리 주소로 바꾸면서 접근 권한을 검사한다.


네트워크 카드(NIC)나 NVMe 저장장치, GPU 같은 주변장치도 메모리에 직접 데이터를 읽고 쓴다. 이때 CPU가 쓰던 가상 주소를 장치에 그대로 넘겨줄 수는 없고, 물리 주소를 그대로 열어 주면 장치가 허용되지 않은 메모리 영역까지 침범할 수 있다. 이 글에서는 같은 물리 메모리에 CPU와 장치가 각각 어떤 경로로 접근하는지, 주소 변환과 메모리 영역 격리가 어디서 이루어지는지 차례로 다룬다.


## CPU의 가상 주소와 MMU


두 접근 경로 가운데 먼저 CPU가 메모리에 접근할 때 주소를 변환하고 권한을 검사하는 과정을 본다. CPU가 사용하는 주소는 프로세스마다 따로 부여된 **가상 주소**(VA, Virtual Address)다. 운영체제는 메모리를 일정한 크기인 페이지 단위로 나누어 관리한다. CPU 안의 **MMU**(Memory Management Unit, 메모리 관리 장치)는 주소 변환 표인 페이지 테이블을 참조한다. MMU는 이 표에 따라 가상 주소를 실제 메모리 위치인 **물리 주소**(PA, Physical Address)로 바꾼다.


페이지 크기가 4KB(`0x1000`바이트)인 환경에서 CPU가 가상 주소 `0x0040_1A3C`에 접근하는 경우를 숫자로 계산해 본다. 4KB는 $2^{12}$바이트이므로 16진수 하위 세 자리(12비트)인 `0xA3C`는 페이지 안에서의 상대 위치를 뜻하는 오프셋(offset)이 된다. 나머지 앞부분인 `0x00401`은 몇 번째 페이지인지를 나타내는 페이지 번호가 된다.


![가상 주소 0x0040_1A3C가 페이지 번호 0x00401과 오프셋 0xA3C로 나뉘고, MMU 페이지 테이블을 통해 물리 프레임 0x00123과 결합되어 물리 주소 0x00123A3C가 되는 과정](/images/notion/tech-k04/image-1.png)


그림 1. 4KB 페이지 기준 가상 주소 0x0040_1A3C를 물리 주소 0x00123A3C로 변환하는 손계산 예제.


MMU는 페이지 테이블에서 페이지 번호 `0x00401`에 대응하는 실제 메모리 구역인 물리 프레임 번호를 찾는다. 여기에 물리 프레임 `0x00123`이 연결되어 있으면 페이지 번호 자리에 물리 프레임 번호를 넣는다. 그 뒤에 오프셋 `0xA3C`를 그대로 붙여 최종 물리 주소 `0x00123A3C`를 만든다. 만약 페이지 테이블에 해당 항목이 없거나 권한이 맞지 않으면 접근 예외 신호인 페이지 폴트(page fault)가 발생한다. 이때는 운영체제가 개입해 새로운 주소를 연결하는 매핑을 추가하거나 잘못된 접근을 차단한다.


이 변환 과정 덕분에 프로세스 A와 프로세스 B의 가상 주소 `0x0040_1000`은 숫자가 같아도 서로 다른 물리 프레임을 가리킬 수 있다. 한 프로세스가 다른 프로세스의 메모리를 함부로 읽거나 쓰지 못하게 막는 프로세스 격리는 바로 이 MMU와 페이지 테이블에서 나온다.


## 장치의 직접 메모리 접근


CPU가 MMU를 거쳐 메모리에 접근하는 것과 달리, 주변장치는 큰 데이터를 빠르게 옮기기 위해 메모리에 직접 접근하는 경로를 쓴다. 네트워크 패킷이나 디스크 블록을 옮길 때마다 CPU가 모든 바이트를 직접 복사하면 그사이에 다른 연산을 처리하기 어렵다. 이 부담을 줄이는 방식이 **DMA**(Direct Memory Access, 직접 메모리 접근)다. DMA에서는 장치가 CPU를 거치지 않고 물리 메모리에 직접 데이터를 읽거나 쓴다.


장치가 데이터 전송을 직접 맡더라도 모든 과정을 혼자 처리하지는 않는다. 운영체제 커널에서 장치를 제어하는 프로그램인 장치 드라이버가 먼저 데이터를 담을 메모리 공간인 버퍼를 준비한다. 이어서 드라이버가 장치가 사용할 DMA 주소를 매핑해 장치에 알려 주면, 장치가 메모리 전송을 마치고 완료 신호를 보낸다. 실제 데이터 복사는 장치가 수행하고, 버퍼 준비와 주소 매핑, 완료 후 처리는 CPU와 드라이버가 관리한다.


![CPU와 드라이버가 DMA 주소를 장치에 전달하면 장치가 물리 메모리의 할당된 DMA 버퍼에 직접 전송하지만, 검사가 없으면 다른 프로세스 영역에도 접근할 수 있음을 보여 주는 구조도](/images/notion/tech-k04/image-2.png)


그림 2. DMA 전송에서 드라이버와 장치의 역할 분담 및 장치 경로에 주소 검사가 없을 때 생기는 격리 공백 개념도.


이때 드라이버가 장치에 건네는 DMA 주소는 부품 간 데이터 통로인 버스에서 쓰이므로 버스 주소라고도 부르며, CPU의 가상 주소와 체계가 다르다. 단순한 시스템에서는 DMA 주소가 CPU의 물리 주소와 같기도 하다. 그러나 중간에 CPU와 주변장치 버스를 잇는 하드웨어인 호스트 브리지나 별도의 변환 장치를 거치는 환경에서는 물리 주소와 다른 값을 가질 수 있다. 따라서 주소 숫자가 같은지보다 현재 플랫폼에서 그 주소를 어떤 조건으로 매핑했는지가 기준이 된다.


이처럼 장치가 물리 메모리에 직접 접근할 때 보안과 안정성 문제가 드러난다. CPU 쪽 경로는 MMU가 페이지 테이블을 검사해 프로세스 격리를 보장하지만, 장치가 버스를 통해 메모리에 직접 접근하는 경로에는 기본적인 권한 검사가 없다. 장치가 내보내는 주소에 아무런 제한이 없다면, 오작동하는 장치나 장치를 제어하는 악성 펌웨어가 할당된 버퍼 바깥의 임의 물리 메모리 영역에 접근할 수 있다.


## IOMMU의 주소 변환과 격리


장치의 직접 접근 경로에서 생기는 권한 검사 공백은 CPU의 MMU와 비슷한 하드웨어로 메운다. 이 역할을 맡는 장치가 **IOMMU**(Input/Output Memory Management Unit, 입출력 메모리 관리 장치)다. 장치가 버스 주소로 DMA 요청을 보내면, IOMMU는 자체 변환 테이블을 참조해 그 장치에 허용된 물리 주소로 바꿔 준다. 변환 테이블에 등록되지 않은 주소를 요청하면 메모리 접근을 차단한다.


![CPU는 가상 주소를 MMU로 변환해 메모리에 접근하고 미매핑 주소는 페이지 폴트를 일으키며, NVMe나 NIC 장치는 버스 주소를 IOMMU로 변환해 메모리에 접근하고 미등록 주소는 차단되는 비교 구조도](/images/notion/tech-k04/image-3.png)


그림 3. CPU 경로(MMU)와 장치 경로(IOMMU)의 주소 변환 및 미등록 주소 차단 지점 비교 구조도.


이처럼 IOMMU를 거치면 장치마다 접근할 수 있는 물리 메모리 영역을 분리할 수 있다. 네트워크 카드는 패킷 수신 버퍼만, GPU는 화면 출력용 프레임 버퍼만 접근하도록 변환 테이블을 제한하는 방식이다.


인텔(Intel) 플랫폼에서는 이 기술을 VT-d(Virtualization Technology for Directed I/O)라 부른다. 운영체제는 하드웨어 구성이 달라도 드라이버가 일관된 방식으로 주소를 다룰 수 있게 인터페이스를 제공한다. [리눅스 커널 DMA 매핑 문서](https://docs.kernel.org/core-api/dma-api-howto.html)를 보면, 커널의 DMA API는 드라이버에 장치가 사용할 주소를 반환하며 플랫폼에 따라 내부에서 IOMMU 매핑이나 필요한 변환을 처리한다. 따라서 `dma_map` 계열의 DMA API는 IOMMU 전용 제어 함수라기보다 드라이버가 플랫폼별 주소 변환 조건을 커널에 위임하는 인터페이스다.


## 버퍼 수명과 캐시 동기화


IOMMU와 DMA API로 적법한 주소를 매핑해 장치에 전달했더라도 데이터 전송 준비가 모두 끝나는 것은 아니다. 같은 메모리 버퍼를 시간차를 두고 장치와 CPU가 번갈아 다루므로, 주소 변환 외에도 버퍼의 소유권 수명과 동기화 조건을 맞춰야 한다.


수신 버퍼 하나를 준비해 장치에서 데이터를 받는 과정을 순서대로 보면 이렇다. 드라이버가 수신 버퍼를 할당하고 DMA 매핑을 마치면 버퍼를 쓸 권한은 장치로 넘어간다. 장치가 버퍼에 데이터를 쓰는 도중에 CPU가 전송 완료를 확인하지 않고 버퍼를 재사용하거나 덮어쓰면 데이터가 손상될 수 있다. 전송 완료와 동기화를 거친 뒤에야 버퍼 소유권이 CPU로 넘어오며, 그제야 CPU가 데이터를 안전하게 읽고 해석할 수 있다.


![수신 버퍼 준비와 DMA 매핑 후 장치가 쓰는 버퍼를 완료 전에 덮어쓰면 데이터가 손상될 수 있으며, 전송 완료 후 동기화와 소유권 전환을 거쳐야 CPU가 데이터를 해석할 수 있음을 보여 주는 순서도](/images/notion/tech-k04/image-4.png)


그림 4. 수신 버퍼의 준비부터 장치 전송, 동기화와 소유권 전환, CPU 처리로 이어지는 수명 주기 개념도. 실제 동기화와 해제 순서는 플랫폼과 DMA API의 계약을 따른다.


CPU 안의 임시 고속 저장소인 캐시와 장치가 바라보는 물리 메모리의 데이터가 일치하는지도 별도로 따져야 한다. CPU는 연산 속도를 높이기 위해 메모리 값을 캐시에 복사해 두고 다루지만, 장치는 물리 메모리에 직접 접근한다. 하드웨어가 캐시와 물리 메모리의 값을 같게 유지하는 캐시 일관성(cache coherence)을 자동으로 보장하는 플랫폼도 있다. 반면 그렇지 않은 플랫폼에서는 전송 전후에 드라이버가 명시적으로 캐시 동기화를 수행해야 한다. 안전한 DMA 통신이 이루어지려면 유효한 주소 매핑, 버퍼 소유권 전환, 캐시 동기화가 함께 맞물려야 한다.


## 결론


같은 물리 메모리를 다루더라도 CPU와 주변장치는 서로 다른 주소 체계와 보호 장치를 거쳐 접근한다. CPU는 MMU로 가상 주소를 물리 주소로 변환하며 프로세스 격리를 얻고, 장치는 DMA 주소를 사용하며 IOMMU 구성을 통해 접근 경로를 제한받는다. 드라이버 코드에서는 `dma_map` 계열 호출이 플랫폼별 주소 매핑과 동기화 계약을 맺는 지점이 된다. 시스템에 IOMMU 하드웨어가 존재하는 것과 운영체제가 해당 장치에 보호 정책을 실제로 활성화한 것은 별개다. 따라서 보안 상태를 점검할 때는 하드웨어 존재 여부와 보호 정책 활성화 여부를 나누어 확인해야 한다.


이 글에서는 단일 운영체제 안에서 CPU와 장치가 물리 메모리에 접근하는 경로를 다뤘다. 가상 머신(VM)에 물리 장치를 직접 할당(passthrough)하는 환경에서는 가상 머신이 알고 있는 게스트 물리 주소와 실제 호스트 물리 주소가 나뉜다. 이 두 주소 사이를 IOMMU가 어떻게 연결하는지는 다음 주제로 남겨 둔다.
