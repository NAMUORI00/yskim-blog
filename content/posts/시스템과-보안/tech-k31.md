프로그램에서 파일 내용을 메모리로 읽어 들일 때는 `read(fd, buf, 128)` 같은 함수를 호출한다. 코드만 보면 열린 파일 번호 `fd`에서 최대 128바이트를 꺼내 임시 메모리 공간인 버퍼 `buf`에 채우는 단순한 동작처럼 보인다. 하지만 일반 사용자 프로그램은 저장 장치나 운영체제 내부 자료구조에 직접 접근할 권한이 없다. 운영체제의 핵심부인 커널(kernel)에 파일 번호와 버퍼 주소를 넘겨 검사를 거친 뒤에야 데이터를 받을 수 있다. 호출이 끝난 뒤에도 함수가 돌려준 반환값을 확인해야 실제로 몇 바이트가 채워졌는지 판별할 수 있다.


이처럼 프로그램이 커널에 작업을 요청하는 통로를 **시스템 호출**(system call)이라 한다. 리눅스 시스템 호출의 동작 조건은 [read(2) 명세](https://man7.org/linux/man-pages/man2/read.2.html)에 정의되어 있다. 이 명세를 보면 요청한 길이보다 적은 바이트가 반환되거나 `0`, `-1`이 돌아오는 조건이 세세하게 나뉘어 있다. 일반적인 x86-64 리눅스 환경에서 `read(fd, buf, 128)` 호출이 시작되어 복귀하기까지의 흐름을 단계별로 따라간다. 그 과정에서 주소 공간과 실행 권한의 경계에서 무엇을 확인하고 반환값을 어떻게 다루어야 하는지 짚어 본다.


## 사용자 영역과 사용자 모드의 구분


시스템 호출이 지나는 경계를 이해하려면 먼저 메모리 주소 범위와 CPU 실행 권한을 구분해야 한다. 프로그램의 버퍼 `buf`와 기계어 코드, 힙, 스택은 일반 프로그램용 가상 주소 공간인 **사용자 영역**(user space)에 놓인다. 반면 CPU는 하드웨어 제어 명령이나 커널 전용 메모리에 직접 접근할 수 없도록 권한이 제한된 **사용자 모드**(user mode)에서 코드를 실행한다. 즉 사용자 영역은 가상 주소의 범위를 가리키고, 사용자 모드는 CPU의 실행 권한 상태를 가리킨다.


실행 중인 프로그램 단위인 프로세스 A와 프로세스 B는 모두 `0x400000`이라는 같은 가상 주소를 사용할 수 있다. 사용자 영역의 가상 주소는 프로세스마다 독립된 주소 변환표인 **페이지 테이블**(page table)을 거쳐 실제 물리 메모리 주소로 바뀌기 때문이다. 두 프로세스가 같은 `0x400000` 주소를 쓰더라도 각자의 페이지 테이블을 거치면 서로 다른 물리 메모리에 연결된다. 한쪽 프로세스에서는 유효한 주소가 다른 프로세스에서는 물리 메모리에 아예 연결(매핑)되지 않은 상태일 수도 있다.


이와 달리 같은 프로세스 안에서 나뉘어 돌아가는 작업 흐름인 여러 스레드는 하나의 가상 주소 공간을 공유한다. 대신 각 스레드는 현재 실행 중인 명령어 위치와 호출 스택 같은 실행 상태를 따로 유지한다. 스레드들이 같은 힙 메모리를 볼 수 있다고 해서 접근 순서까지 자동으로 맞춰지지는 않는다. 따라서 여러 스레드가 동시에 같은 버퍼를 읽고 쓸 때는 접근 순서를 맞추는 동기화 장치가 따로 필요하다.


CPU의 메모리 접근 검사는 사용자 모드 코드가 커널 전용으로 표시된 메모리 구역(페이지)을 일반 읽기나 쓰기 명령으로 참조하지 못하게 막는다. 다만 이 하드웨어 검사만으로 운영체제 전체의 무결성이 무조건 보장되는 것은 아니다. 페이지 테이블 설정과 커널 코드 자체의 구현, 하드웨어의 동작 조건이 함께 맞물려야 보호 경계가 유지된다.


리눅스 커널의 가상 주소 배치 역시 컴퓨터의 실행 환경 설정에 따라 달라진다. x86-64 [주소 배치](https://docs.kernel.org/arch/x86/x86_64/mm.html)는 페이지 테이블이 4단계인지 5단계인지에 따라 주소 범위가 다르다. 또한 하드웨어 취약점 완화 기능인 PTI(Page Table Isolation)가 켜진 환경에서는 사용자 모드용 페이지 테이블에 커널 메모리 전체를 매핑해 두지 않는다. 커널의 [PTI 문서](https://docs.kernel.org/arch/x86/pti.html)에 나오듯 사용자 실행용 테이블에는 커널 진입에 필요한 최소한의 영역만 남겨 둔다. 시스템 호출이나 하드웨어 신호인 인터럽트로 커널에 들어갈 때 쓰는 입구만 열어 두는 방식이다. 모든 프로세스의 페이지 테이블에 커널 메모리 전체가 항상 그대로 매핑되어 있다는 단순한 도식만으로는 현재 리눅스 구성을 온전히 설명하기 어렵다.

## 시스템 호출 진입과 커널의 검사 과정


사용자 모드 코드는 커널 메모리나 저장 장치에 직접 접근할 수 없으므로 정해진 진입점을 통해 **커널 모드**(kernel mode)로 실행 권한을 넘겨야 한다. x86-64 리눅스의 전형적인 경로에서 프로그램은 먼저 시스템 호출을 감싸 둔 C 표준 라이브러리의 `read` 래퍼 함수를 호출한다. 이 함수는 CPU 내부 저장소인 레지스터에 인자(`fd`, `buf`, `128`)를 담은 뒤 `syscall` 명령어를 실행해 커널 진입점으로 넘어간다.


커널에 진입하면 먼저 열린 파일 번호인 파일 디스크립터 `fd`가 현재 프로세스에서 열려 있는 유효한 객체인지, 읽기 권한이 있는지 확인한다. 이 검사를 통과하면 해당 객체에 연결된 커널 내부의 읽기 구현 함수를 호출한다. 이때 같은 `read` 호출이라도 대상이 일반 파일인지, 프로세스 간 통신용 파이프인지, 장치 파일인지에 따라 내부 동작이 달라진다. 모든 `read` 호출을 디스크에서 데이터를 읽어 오는 과정으로만 설명할 수 없는 이유가 여기에 있다. 일반 파일을 읽을 때도 디스크를 매번 직접 읽는 대신 커널 메모리의 임시 저장소인 페이지 캐시에 올라와 있는 데이터를 먼저 참조한다. 원하는 데이터가 페이지 캐시에 없을 때만 저장 장치에 실제 입출력을 요청한다.


읽어 올 데이터를 준비한 뒤에는 사용자 영역의 버퍼 `buf`로 바이트를 복사해야 한다. 이때 커널은 사용자 프로그램이 건넨 `buf` 주소를 그대로 믿고 쓰기 작업을 할 수 없다. 잘못된 주소나 커널 영역 주소를 넘겼을 때 그대로 복사하면 메모리가 손상되거나 보호 경계가 무너지기 때문이다. 또한 시작 주소는 유효하더라도 128바이트 구간 중간에 매핑되지 않은 페이지나 쓰기 권한이 없는 페이지가 섞여 있으면 복사 도중에 오류가 발생할 수 있다. 그래서 커널의 사용자 메모리 복사 도우미 함수는 복사 전에 주소 범위가 사용자 영역 안에 있는지 먼저 검사한다. 실제로 바이트를 복사하는 도중에도 아직 물리 메모리가 연결되지 않아 생기는 페이지 폴트나 접근 오류를 함께 처리한다.

## 반환값 해석과 부분 읽기 처리


커널이 데이터 복사를 마치고 사용자 모드로 복귀하면 `read` 함수는 처리 결과를 정수 반환값으로 돌려준다. 앞선 예처럼 `read(fd, buf, 128)`로 최대 128바이트를 요청했더라도 파일 끝까지 50바이트만 남아 있었다면 커널은 50바이트만 복사하고 `50`을 반환한다.


반환값이 `50`이라면 이번 호출로 채워진 유효한 범위는 `buf[0]`부터 `buf[49]`까지뿐이다. 프로그램이 반환값을 확인하지 않고 128바이트가 모두 채워졌다고 가정해 `buf[50]`부터 `buf[127]`까지 함께 읽으면 문제가 생긴다. 버퍼에 남아 있던 이전 데이터나 초기화하지 않은 메모리 값을 파일 내용과 섞어 읽게 되기 때문이다.


반환값이 `0`인 경우는 읽을 위치가 이미 파일 끝(EOF, End of File)에 도달해 더 이상 가져올 바이트가 없다는 뜻이다. 반대로 `-1`이 반환되면 디스크립터 오류나 잘못된 버퍼 주소, 외부 신호인 시그널 개입 등으로 읽기에 실패했다는 신호다. 이 경우에는 오류 번호가 담기는 `errno` 값을 확인해 실패 원인을 구분해야 한다.


결국 양수 길이를 요청했을 때 요청량보다 작은 양수가 돌아오는 부분 읽기는 그 자체로 오류가 아니다. 읽으려는 데이터가 128바이트 고정 크기 헤더처럼 반드시 정해진 길이를 모두 모아야 하는 형식일 때가 있다. 이때는 상위 코드에서 지금까지 읽은 누적 길이를 기록하며 남은 바이트만큼 반복 호출해야 한다. 그 과정에서 반환값이 `0`이 되어 파일 끝에 먼저 닿았는지, 혹은 `-1` 오류가 발생했는지를 함께 검사해야 안전하다.

## 시스템 호출 횟수와 버퍼링


지금까지 본 파일 읽기 경로를 따라가면 작은 단위 읽기를 여러 번 반복하는 방식을 왜 피하려 하는지도 드러난다. 파일에서 1바이트씩 128번 성공적으로 읽는 경우와 한 번의 호출로 128바이트를 받는 경우는 전달받는 데이터 총량이 같다. 하지만 `read`를 호출할 때마다 사용자 모드에서 커널 모드로 진입하고 파일 디스크립터와 버퍼 주소를 검사한 뒤 복귀하는 고정 비용이 든다. 같은 양의 데이터를 읽더라도 두 방식의 시스템 호출 횟수는 128배 차이 난다.


여기서 사용자 모드와 커널 모드를 오가는 권한 전환은 실행 중인 프로세스를 다른 프로세스로 교체하는 **문맥 교환**(context switch)과는 구분된다. 시스템 호출이 페이지 캐시에서 데이터를 바로 복사해 돌아온다면 같은 프로세스 안에서 실행 모드만 바뀌었다가 복귀한다. 다만 요청한 데이터가 아직 메모리에 없어 저장 장치 입출력을 기다려야 하는 상태가 되면 상황이 달라진다. 실행 순서를 관리하는 커널 스케줄러가 현재 프로세스를 대기 상태로 돌리고 다른 프로세스로 실행을 넘기는 문맥 교환이 일어날 수 있다.


C 표준 입출력 라이브러리(`fread` 등)가 내부에 버퍼를 두는 이유도 이 호출 비용 차이로 설명할 수 있다. 사용자 영역에 적당한 크기의 버퍼를 마련해 두고 커널에는 큰 덩어리로 한 번에 읽기를 요청한다. 그 뒤 프로그램이 요청하는 작은 단위 읽기는 사용자 영역 버퍼에서 바로 꺼내 주면 시스템 호출 횟수를 줄일 수 있다. 물론 버퍼를 무조건 크게 잡는다고 좋은 것은 아니며, 메모리 사용량과 응답 대기 시간, 대상 장치의 특성에 따라 알맞은 묶음 크기가 달라진다.


## 결론


`read(fd, buf, 128)` 호출은 사용자 모드에서 커널 모드로 넘어가 파일 디스크립터와 버퍼 주소를 검사받고 데이터를 복사해 오는 과정이다. 사용자 영역의 가상 주소는 프로세스별 페이지 테이블로 분리되며, 사용자 모드 코드는 커널 전용 메모리에 직접 접근할 수 없다. 커널은 시스템 호출로 받은 버퍼 주소 범위와 페이지 연결 상태를 확인하며 데이터를 복사하고, 프로그램은 반환값으로 부분 읽기와 파일 끝, 오류를 구분해야 한다.


이 글에서는 시스템 호출의 검사 경계와 호출 횟수 차이만 짚었으며, 실제 CPU 아키텍처별 시스템 호출 지연 시간과 처리량 변화는 따로 측정하지 않았다. 또한 이번 예에서는 커널이 연속된 바이트 버퍼의 시작 주소와 길이만 받는 경우를 다뤘지만, 장치 제어나 네트워크 설정처럼 복잡한 구조체 포인터를 넘기는 시스템 호출도 많다. 다음에는 사용자 프로그램이 넘긴 구조체의 길이와 내부 필드를 커널이 어느 단계에서 검사하는지, 호출 권한 검사와 입력값 유효성 검사가 어떻게 구분되는지 짚어 볼 수 있다.
