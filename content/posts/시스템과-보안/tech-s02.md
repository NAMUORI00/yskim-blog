## 표시명, 저장 키, 타입 식별자


표시 이름과 저장 식별자의 역할을 나누어 정리했다. CoolingLevel을 화면에서 “냉각 출력”으로 바꾸는 일과 저장 파일의 키를 바꾸는 일은 영향을 받는 대상이 다르다. API, ABI 개념을 설정 파일과 플러그인의 호환성에 연결해 살펴봤다.


설명용 장치 설정 편집기를 두었다. 화면에는 `CoolingLevel`이 표시되고 JSON 파일에도 같은 키가 저장된 상황에서, 화면을 한국어로 바꾸는 범위를 비교했다. 실제 제품의 변경 이력이 아닌 호환성 경계를 살펴보기 위한 예제다.


## 표시 이름과 저장 키를 분리해 보기


화면에는 “냉각 출력”을 보여 주되 파일은 계속 `cooling_level`을 쓰도록 모델을 구성할 수 있다. C#에서는 코드 속성 이름과 JSON 이름도 별도로 둘 수 있다. 다음 코드는 그 차이만 보여 주는 예제다.


```c#
public class CoolingSettings
{
    [System.Text.Json.Serialization.JsonPropertyName("cooling_level")]
    public int CoolingPercent { get; set; }
}
```


화면용 번역은 이 타입 밖에서 선택하고, 직렬화 키는 속성으로 고정했다. 코드 속성을 읽기 좋은 이름으로 바꾸어도 저장 키를 유지할 여지가 생긴다.


[System.Text.Json의 이름 지정 문서](https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/customize-properties)에서 확인한 것은 이 속성이 직렬화와 역직렬화에 적용되며 일반 명명 정책보다 우선한다는 점이다. 생성자 매개변수 매칭까지 같은 방식으로 바꾼다고 확대하지는 않았다.

표시 이름도 접근성 레이블이나 자동화 테스트에서 사용될 수 있다. 화면 문구의 변경 범위와 저장 형식의 호환성 검사를 나누면 각각 어떤 영향을 확인해야 하는지 구체적으로 정리할 수 있다.


## 저장 키 변경과 마이그레이션


새 파일 형식에서 키를 `cooling_percent`로 바꾸기로 했다고 가정했다. 구버전은 새 키를 모르고, 신버전은 옛 파일에 아직 남은 `cooling_level`을 만날 수 있다. 신버전이 구버전 파일을 읽는 방향과 구버전이 신버전 파일을 읽는 방향을 각각 적어 보니, “호환된다”는 말만으로는 설명이 부족했다.


| 읽는 프로그램 | 파일         | 이 예제에서 필요한 확인              |
| ------- | ---------- | -------------------------- |
| 신버전     | 구버전 키      | 변환기나 별칭 규칙으로 읽을 수 있는가      |
| 구버전     | 신버전 키      | 알 수 없는 키를 무시하는가, 오류로 처리하는가 |
| 신버전     | 두 키가 함께 있음 | 충돌 시 어느 값을 채택하는가           |


두 키를 모두 받아 주면 이전 파일을 읽기 쉬워지지만, 서로 다른 값이 들어왔을 때의 우선순위도 정해야 한다. 조용히 하나를 선택하는 대신 충돌 오류로 표시하는 방법도 있다. 저장할 때는 한 가지 정규 형식만 쓰고 읽기 경로에서 변환하는 설계를 비교 대상으로 두었다. 규칙이 늘어날수록 검증해야 할 과거 형식도 늘어나는 부담이 남는다.


## 플러그인의 타입 식별자


플러그인이 타입을 문자열로 찾는다면 화면 번역과 무관한 이름이 계약으로 남는다. .NET의 타입 이름에는 네임스페이스와 어셈블리 정보가 포함될 수 있다.


[AssemblyQualifiedName 문서](https://learn.microsoft.com/en-us/dotnet/api/system.type.assemblyqualifiedname)는 이 표현을 확인하는 기준으로 삼았다. 실제 로더가 어떤 이름을 사용하는지 읽지 않고 네임스페이스 변경의 영향을 판단하기는 어려웠다.


가령 설정 파일에 타입 이름을 저장하는 구조라면, 클래스 이름 변경 후 파일을 열 때 타입을 찾지 못할 수 있다. 파일 키가 그대로인데도 역직렬화가 실패하는 경로다. 반대로 명시적 ID와 레지스트리를 쓰는 로더라면 클래스 이름 변경의 영향을 다른 방식으로 줄일 수 있다. 어느 쪽이 적용되는지는 플러그인 검색, 등록, 로드 코드를 따라가며 확인해야 한다.

## 이름 변경을 검증하는 작은 단위


화면 문구, 기존 파일의 읽기, 플러그인의 검색과 로딩을 각각 확인 대상으로 두었다. 서로 다른 계약이므로 소스에서 옛 이름이 사라졌다는 검색 결과만으로 세 동작을 모두 확인했다고 보기는 어렵다.


포크의 이름 변경을 읽을 때도 표시 문구와 외부 식별자를 나누는 기준을 사용할 수 있다. 남아 있는 옛 이름은 단순한 잔재일 수도 있고 호환성을 유지하는 부분일 수도 있다. 저장 파일과 로더에서 그 이름을 어떻게 사용하는지가 다음 확인 항목으로 남았다.
