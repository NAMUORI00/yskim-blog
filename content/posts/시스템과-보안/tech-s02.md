프로그램의 화면을 다른 언어로 번역하거나 포크한 프로젝트의 이름을 바꿀 때는 코드 곳곳에 있는 문자열을 손보게 된다. 이때 모든 이름을 같은 기준으로 바꿀 수는 없다. 화면에 보이는 `CoolingLevel`을 "냉각 출력"으로 바꾸는 일과, 설정 파일에 기록되는 키나 플러그인이 읽어 들이는 클래스 이름을 바꾸는 일은 영향을 받는 대상이 다르다. API(Application Programming Interface)와 ABI(Application Binary Interface)의 호환성 경계를 설정 파일과 플러그인 구조에 대입해 보려고 가상의 장치 설정 편집기 예제를 구성했다.


처음 상태에서 이 편집기는 화면에 `CoolingLevel`을 표시하고 JSON 설정 파일에도 똑같은 이름을 키로 저장한다고 가정하자. 여기서 기존에 저장된 설정 파일과 플러그인의 호환성을 깨뜨리지 않고 이름을 바꾸려면, 프로그램 안의 이름을 **표시 이름**, **저장 키**, **타입 식별자** 세 가지로 나누어 다루어야 한다.


## 표시 이름과 저장 키 분리하기


화면에 보이는 문구를 "냉각 출력"으로 바꾸더라도 설정 파일에는 기존 키인 `cooling_level`을 그대로 유지할 수 있다. C#을 비롯한 많은 언어에서는 코드에서 다루는 속성(Property) 이름과 파일에 기록하는 JSON 키 이름을 분리하는 기능을 제공한다.


```c#
public class CoolingSettings
{
    [System.Text.Json.Serialization.JsonPropertyName("cooling_level")]
    public int CoolingPercent { get; set; }
}
```


위 코드는 데이터 모델의 속성 이름을 `CoolingPercent`로 바꾸면서 직렬화 키는 `"cooling_level"`로 고정한 예다. 객체를 파일에 쓸 수 있는 문자열 형태로 바꾸는 직렬화(Serialization)와, 파일 내용을 다시 객체로 읽어 들이는 역직렬화(Deserialization)는 모두 이 속성에 지정한 이름을 따른다. 화면에 출력할 한국어 번역("냉각 출력")은 이 클래스 바깥의 화면 표시 계층에서 연결하면 된다. 이렇게 역할을 나누면 코드 안의 속성 이름을 읽기 좋게 고치거나 화면 문구를 번역해도 기존 설정 파일을 그대로 읽고 쓸 수 있다.


[System.Text.Json의 이름 지정 문서](https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/customize-properties)를 확인해 보면 `JsonPropertyName` 특성은 직렬화와 역직렬화 양쪽에 모두 적용되며, 이름을 일괄 변환하는 일반 명명 정책보다 우선한다. 다만 이 문서에서 확인한 범위는 속성 이름과 JSON 키의 매핑까지이며, 생성자 매개변수 이름 매칭까지 똑같이 바뀐다고 단정할 수는 없다.

물론 화면에 보이는 표시 이름이라고 해서 아무런 제약 없이 바꿀 수 있는 것은 아니다. 화면 읽기 프로그램이 참조하는 접근성 레이블이나 화면 문구를 기준으로 동작하는 UI 자동화 테스트가 있다면 표시 이름을 바꿨을 때 함께 영향을 받는다. 그래도 화면 문구의 변경 범위를 점검하는 일과 저장 파일의 호환성을 검증하는 일을 분리하면 각 단계에서 무엇을 확인해야 하는지 명확해진다.


## 저장 키를 바꿀 때 생기는 버전 간 호환성 문제


만약 새 버전에서 설정 파일의 키 자체를 `cooling_level`에서 `cooling_percent`로 바꾸기로 했다면 상황이 달라진다. 구버전 프로그램은 새로 도입된 `cooling_percent`를 알지 못하고, 신버전 프로그램은 사용자가 예전에 저장해 둔 파일에서 `cooling_level`을 만날 수 있다. 신버전이 구버전 파일을 읽는 방향과 구버전이 신버전 파일을 읽는 방향을 나누어 적어 보면, 단순히 "호환된다"는 말만으로는 동작을 설명하기 어렵다.


| 읽는 프로그램 | 읽는 파일 상태   | 필요한 확인 항목                    |
| ------- | ---------- | ---------------------------- |
| 신버전     | 구버전 키만 있음  | 변환기나 별칭 규칙으로 옛 키를 읽을 수 있는가   |
| 구버전     | 신버전 키만 있음  | 알 수 없는 키를 무시하는가, 오류로 처리하는가   |
| 신버전     | 두 키가 함께 있음 | 값이 충돌할 때 어느 쪽을 채택하거나 오류를 내는가 |


신버전 프로그램이 두 키를 모두 읽을 수 있게 허용하면 예전 파일을 열기는 쉬워진다. 하지만 사용자가 파일을 직접 편집하거나 버전이 섞이면서 한 파일 안에 `cooling_level`과 `cooling_percent`가 동시에 들어오는 예외 상황이 생길 수 있다. 두 키의 값이 다를 때 어느 키를 우선할지 규칙을 정해 두거나, 임의로 하나를 고르는 대신 충돌 오류를 띄워 알려 주어야 한다.


![구버전 파일과 신버전 파일을 읽기 변환으로 받아들이고 두 키가 함께 있을 때는 충돌을 판정한 뒤, 저장할 때는 cooling_percent 정규 형식으로만 기록하는 흐름도](/images/notion/tech-s02/image-2.png)


그림 2. 저장 키 변경 시 읽기 경로의 별칭 변환과 단일 정규 형식 저장 흐름.


이를 관리하는 한 가지 방법은 파일을 읽을 때는 구버전 키와 신버전 키를 모두 받아 변환하되, 파일로 저장할 때는 한 가지 정규 형식(Canonical Format)인 `cooling_percent`만 기록하는 것이다. 다만 이런 변환 규칙을 추가할수록 프로그램이 계속 지원하고 테스트해야 하는 과거 형식의 가짓수도 함께 늘어난다.


## 플러그인 로더와 타입 식별자 계약


설정 파일의 키뿐만 아니라 클래스와 네임스페이스 이름도 외부와의 계약이 될 수 있다. 프로그램이 플러그인을 불러오거나 설정 파일을 읽을 때 타입(Type)을 문자열 이름으로 찾아 생성한다면, 화면 번역과는 아무 관련이 없는 코드 식별자가 호환성을 좌우한다.


예를 들어 .NET 환경에서는 타입을 특정할 때 클래스 이름에 더해 네임스페이스와 어셈블리 정보까지 포함한 문자열을 쓸 수 있다. [AssemblyQualifiedName 문서](https://learn.microsoft.com/en-us/dotnet/api/system.type.assemblyqualifiedname)를 기준으로 보면, 이 전체 이름 문자열은 타입이 속한 어셈블리 이름과 버전 정보까지 담는다. 따라서 플러그인 로더가 실제로 어떤 형식의 문자열로 타입을 찾는지 코드를 확인하지 않고서는 클래스나 네임스페이스 이름을 바꿨을 때의 영향을 판단하기 어렵다.


설정 파일에 클래스의 타입 이름을 그대로 기록해 두는 구조라면, 코드에서 클래스나 네임스페이스 이름을 바꾼 뒤 기존 파일을 열었을 때 해당 타입을 찾지 못해 역직렬화가 실패할 수 있다. JSON 파일의 속성 키는 하나도 바뀌지 않았는데도 파일을 읽지 못하는 경우다. 반대로 각 플러그인에 고정된 문자열 ID를 부여하고 별도의 등록소(Registry)에서 ID와 클래스를 연결하는 로더라면, 등록된 ID만 유지한 채 클래스 이름을 비교적 안전하게 바꿀 수 있다. 실제 시스템이 어느 쪽에 해당하는지는 플러그인을 검색하고 등록하고 불러오는 코드를 직접 따라가며 확인해야 한다.

세 가지가 서로 다른 계약으로 동작하므로, 소스 코드 전체에서 예전 이름 문자열이 모두 사라졌다는 검색 결과만으로는 변경이 안전하게 끝났다고 볼 수 없다. 화면에 의도한 문구가 나타나는지, 기존 파일과 새 파일을 열었을 때 값이 제대로 읽히는지, 플러그인 검색과 로딩이 정상으로 이어지는지를 각각 작은 단위로 나누어 검증해야 한다.


포크한 프로젝트의 이름 변경 이력을 분석할 때도 이 기준을 그대로 적용할 수 있다. 코드에 옛 프로젝트 이름이 남아 있다면 미처 고치지 못한 잔재일 수도 있고, 기존 설정 파일이나 플러그인과의 호환성을 유지하려고 일부러 남겨 둔 식별자일 수도 있다. 남은 이름이 파일 파서와 플러그인 로더에서 실제로 어떻게 쓰이는지 확인하는 일이 다음 단계다.
