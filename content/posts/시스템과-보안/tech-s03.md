메모리 읽기 요청이 거부되거나 커널 드라이버 로딩이 막혔을 때, 원인을 뭉뚱그려 Windows 보안 기능 때문이라고만 두면 어느 단계에서 막혔는지 좁히기 어렵다. 일반 프로그램이 CPU를 통해 메모리를 읽는 경로, 운영체제가 부팅 구성요소나 커널 드라이버의 실행 조건을 검사하는 경로, 외부 장치가 **DMA**(Direct Memory Access, CPU를 거치지 않고 장치가 메모리에 직접 접근하는 방식)로 데이터를 옮기는 경로는 검사 주체와 시점이 모두 다르기 때문이다.


그래서 접근 실패를 해석하려면 먼저 그 현상을 어느 경로에서 관찰했는지부터 구분해야 한다. 여기서는 공식 문서를 기준으로 **Secure Boot**, **VBS**(Virtualization-Based Security), **메모리 무결성**(HVCI, Hypervisor-Protected Code Integrity), 프로세스 페이지 권한, **Kernel DMA Protection**이 각각 언제 무엇을 검사하는지 비교하고, 실패 원인을 추적할 때 기록해 둘 항목을 정리했다. 특정 장비에서 보호 기능을 우회하거나 비활성화한 실험 결과는 다루지 않는다.


## 부팅 단계의 신뢰 검사와 실행 중인 커널의 코드 무결성


먼저 구분할 기준은 코드를 검사하는 시점이다. 컴퓨터가 켜질 때 올라오는 코드를 검증하는 일과, 운영체제가 이미 실행 중인 상태에서 커널 코드를 검증하는 일은 서로 다른 기능이 맡는다.


[Windows 부팅 보호 설명](https://learn.microsoft.com/en-us/windows/security/operating-system-security/system-security/secure-the-windows-10-boot-process)에 나와 있듯, Secure Boot는 부팅 단계에서 실행할 펌웨어와 부트로더 같은 구성요소를 신뢰 정책에 따라 검사한다. 운영체제가 시작되기 전에 신뢰 사슬이 깨지지 않았는지 확인하는 역할이므로, 운영체제가 올라온 뒤에 일반 프로세스가 요청하는 메모리 읽기까지 Secure Boot가 심사한다고 보면 역할이 뒤섞인다.


운영체제가 시작된 뒤 커널 영역에서 실행할 코드를 보호하는 기능은 VBS와 메모리 무결성(HVCI)이다. [Microsoft의 메모리 무결성 문서](https://learn.microsoft.com/en-us/windows/security/hardware-security/enable-virtualization-based-protection-of-code-integrity)를 보면 두 개념은 기반과 개별 보안 기능의 관계로 나뉜다. VBS는 하드웨어 가상화를 이용해 일반 운영체제와 분리된 격리 영역을 만드는 기반이다. HVCI는 그 격리 영역 위에서 커널 코드와 드라이버의 무결성 검사를 수행한다. 따라서 시스템에 VBS라는 기반이 마련되어 있다는 사실과, 개별 보안 기능인 HVCI가 실제로 실행 중이라는 사실은 따로 확인해야 한다.

그림 1. 부팅 단계의 신뢰 검사와 운영체제 시작 뒤 가상화 격리 영역에서 수행하는 코드 무결성 검사를 구분한 개념도. 보호 기능의 역할에 초점을 맞춰 부팅 흐름을 단순화했다(출처: Microsoft의 부팅 보호, 메모리 무결성 문서를 바탕으로 재구성).


드라이버 파일의 서명 여부와 특정 환경에서의 로딩 성공 여부도 나누어 보아야 한다. 드라이버에 서명이 있더라도 취약한 드라이버 차단 목록에 포함되어 있거나, HVCI가 요구하는 메모리 호환성 조건을 만족하지 못하거나, 운영체제 설정과 맞지 않으면 로딩이 거부될 수 있다. 드라이버 로딩 실패의 원인을 HVCI로 좁히려면 단순히 설정 상태만 볼 것이 아니라, 실패 기록에서 해당 코드 무결성 검사 단계의 오류가 실제로 남았는지 확인해야 한다.


## CPU의 주소 변환과 장치의 DMA 접근 경계


실행할 코드를 검증하는 문제와 별개로, 이미 실행 중인 주체가 메모리에 접근할 때도 CPU를 거치는지 외부 장치가 직접 접근하는지에 따라 검사 경계가 달라진다.


사용자 프로그램이 CPU를 통해 메모리를 읽을 때는 해당 프로세스의 가상주소 공간과 페이지 권한이 기준이 된다. CPU가 가상주소를 물리주소로 변환하는 과정에서 현재 프로세스가 그 메모리 페이지에 접근할 권한이 있는지 확인한다. 반면 외부 장치는 DMA를 통해 메모리와 직접 데이터를 주고받을 수 있으므로, 사용자 프로그램에 적용되는 페이지 접근 검사만으로는 장치 경로의 접근 범위까지 설명하기 어렵다.


장치가 접근할 수 있는 물리 메모리 범위를 매핑하고 제한하는 하드웨어 기반은 **IOMMU**(Input-Output Memory Management Unit, 입출력 메모리 관리 장치)가 제공한다. Windows의 Kernel DMA Protection은 지원되는 시스템에서 이 IOMMU를 이용해 외부 장치의 DMA 접근을 허용된 영역으로 제한하는 기능이다. [공식 문서](https://learn.microsoft.com/en-us/windows/security/hardware-security/kernel-dma-protection-for-thunderbolt)에서 안내하듯, 이 보호가 실제로 적용되려면 하드웨어의 IOMMU 지원, 장치 드라이버의 DMA 리매핑 호환성, 장치 연결 시점과 시스템 상태 조건이 함께 맞아야 한다. 또한 운영체제가 IOMMU를 제어하기 전인 초기 부팅 단계까지 이 기능 하나로 모두 보호한다고 범위를 넓혀 해석해서는 안 된다.


![사용자 프로그램의 CPU 메모리 접근은 프로세스와 페이지 권한 검사를 거치고 외부 장치의 DMA 요청은 장치별 IOMMU 매핑 검사를 거쳐 물리 메모리에 도달하거나 차단되는 과정을 나란히 나타낸 도식](/images/notion/tech-s03/image-2.png)


그림 2. 사용자 프로그램의 CPU 메모리 접근과 외부 장치의 DMA 접근이 각각 거치는 검사 경계를 비교한 개념도. 모든 하드웨어 구성의 세부 동작을 나타내지는 않는다(출처: Windows 가상주소, Kernel DMA Protection 문서를 바탕으로 재구성).


이처럼 CPU와 외부 장치는 같은 물리 메모리에 접근하더라도 거치는 검사 주체와 조건이 다르다. CPU 경로에서 메모리 읽기에 성공했다고 해서 외부 장치도 같은 메모리에 DMA로 접근할 수 있다고 일반화할 수 없다. 반대로 장치의 DMA 접근이 실패했을 때도 프로세스 권한 검사만으로는 원인을 설명할 수 없다.


## 보호 설정과 관측 결과를 구분해 기록하기


보안 기능의 이름이나 설정 화면의 한 항목만으로는 현재 시스템의 전체 보호 상태가 드러나지 않는다. 하드웨어가 기능을 지원하는지, 설정에서 기능을 켜 두었는지, 현재 부팅된 환경에서 실제로 실행 중인지가 서로 다를 수 있기 때문이다. 또한 한 경로에서 확인한 결과를 다른 경로의 안전성이나 허용 범위로 건너뛰어 해석하기 쉽다.


그래서 설정과 관찰 결과를 기록할 때는 실제로 확인한 조건과 그 정보만으로는 단정할 수 없는 영역을 나누어 적는 편이 안전하다. 아래 표는 네 가지 관찰 대상별로 남겨야 할 정보와, 그 기록만으로 말하기 어려운 범위를 구분한 예제다. 실제 장비에서 측정한 수치를 적은 표가 아니라, 지원 여부와 사용 설정, 현재 실행 상태를 분리해 기록하기 위한 틀이다.

| VBS와 HVCI | 지원, 설정, 실행 상태, 호환 오류  | 모든 드라이버의 무결점      |

## 실패 원인을 좁힐 때 확인할 항목


실제로 접근 실패나 로딩 오류가 발생했을 때 찾아보아야 할 근거 자료도 앞서 나눈 경로에 따라 달라진다. 드라이버 로딩이 막혔을 때는 코드 무결성 이벤트 로그와 로더 오류 코드를 확인해야 하고, 일반 프로세스의 메모리 읽기가 실패했을 때는 프로세스 권한과 요청한 가상주소 범위를 살펴보아야 한다. 외부 장치의 DMA 접근이 차단되었다면 장치와 드라이버의 리매핑 상태부터 점검해야 한다.


![드라이버 로딩 실패, 프로세스 읽기 실패, 장치 DMA 접근 실패를 경로별로 나누어 각각 코드 무결성 이벤트, 프로세스 권한, IOMMU 매핑 상태와 대조하고 하단에 운영체제 빌드와 드라이버 버전을 고정 조건으로 둔 도식](/images/notion/tech-s03/image-3.png)


그림 3. 관찰된 실패 현상에 따라 접근 경로를 나누고 대응하는 확인 항목과 고정 조건을 대조하는 절차도.


보안 설정을 바꾸기 전과 후의 결과를 비교할 때는 운영체제 빌드 번호와 드라이버 버전도 함께 기록해 두어야 한다. 설정 외에 운영체제 패치나 드라이버 버전 같은 여러 조건이 동시에 바뀌면, 결과가 달라졌을 때 무엇이 실제 원인인지 분리하기 어렵다. 고정해 둔 환경 조건과 변경한 설정을 나누어 기록해 두면, 이후 개별 프로젝트를 점검할 때도 어느 경계에서 접근이 허용되거나 막혔는지 범위를 좁혀 확인할 수 있다.
