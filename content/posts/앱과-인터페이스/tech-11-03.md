포트폴리오 사이트의 프로젝트 목록 카드와 상세 글, GitHub 프로필은 같은 프로젝트를 서로 다른 분량으로 보여 준다. 같은 소개 문단을 여러 화면에 그대로 복사해 넣으면 목록 카드는 지나치게 길어지고 상세 글은 구현 과정이나 실험 근거가 부족해진다.


앞선 글에서는 Notion 문서를 페이지 속성과 본문, 페이지 주소에 쓰는 고유 이름인 `slug`로 나누어 다루는 방법을 보았다. 이번에는 포트폴리오 저장소(`yskim-portfolio`, 커밋 `55ff295`)와 GitHub 프로필 저장소(`NAMUORI00`, 커밋 `e468da3`) 코드를 읽었다. 두 저장소 코드를 대조하며 각 화면이 맡는 정보의 범위와 화면 사이를 연결하는 방식을 확인했다.


## 카드 요약과 상세 본문의 분리


먼저 포트폴리오 사이트가 Notion에 적힌 프로젝트 정보를 목록 카드와 상세 글로 나누어 담는 과정을 본다. [yskim-portfolio의 수집 코드](https://github.com/NAMUORI00/yskim-portfolio/blob/55ff29588b66d75168313936872cdaca99da8684/scripts/notion-content.mjs)는 Notion 문서를 읽어 화면 부품을 넣을 수 있는 마크다운 문서인 MDX 파일을 만든다. 이때 프로젝트의 이름, 기간, 요약, 분류, 태그, 링크는 문서 맨 앞의 **머리말 메타데이터**(frontmatter)로 옮기고 페이지 본문은 MDX 본문으로 남긴다. 목록 화면에서 짧게 훑어볼 정보와 상세 화면에서 깊게 읽을 정보를 문서 하나 안에 위아래로 나누어 담는다.


만약 Notion에서 프로젝트 요약이나 성과 속성을 비워 두면 수집기는 본문에서 대신할 내용을 찾아 채운다. 구체적으로 프로젝트 요약 속성이 비어 있으면 본문의 첫 문단을 가져와 대체 요약으로 쓴다. 별도 성과 속성도 비어 있으면 본문에서 `Metric`, `성과`, `Evidence`, `증거`라는 표지를 찾아 성과 항목을 채운다.


예를 들어 본문 첫 문단에 설치 경로를 적어 두면 목록 화면의 카드 요약에도 그 설치 경로가 맨 먼저 노출된다. 빈 카드를 줄이려는 대체 규칙이지만 본문 첫 문단이 늘 카드 요약에 어울리지는 않기 때문이다. 본문을 쓰는 순서가 대체 요약에 영향을 주므로, 카드에는 입력과 역할, 결과를 담고 상세 본문에는 설치 순서와 비교 근거를 두는 편이 이 규칙에 맞는다.

## 두 축 필터와 근거 메타데이터의 경계


앞 절에서 분리한 머리말 메타데이터는 목록 화면에서 프로젝트를 골라내는 분류 필터와 근거 수준 표시에도 쓰인다. 목록 화면의 [프로젝트 분류 필터](https://github.com/NAMUORI00/yskim-portfolio/blob/55ff29588b66d75168313936872cdaca99da8684/client/src/lib/projectEvidence.ts)는 `category`와 `focus`라는 두 축을 기준으로 삼는다. `category`는 커리어와 토이로 나뉘고, `focus`는 연구, 제품, 도구, 실험 등으로 나뉜다. 예를 들어 `category`에서 토이를 고르고 `focus`에서 도구와 실험을 고르면, 토이 프로젝트이면서 동시에 도구 또는 실험에 해당하는 항목만 화면에 남는다. 같은 축 안에서 여러 값을 고르면 그중 하나만 맞아도 통과하고(OR 조건), 서로 다른 축을 함께 고르면 양쪽 조건을 모두 만족해야 남기 때문이다(AND 조건). 사용한 기술 이름 하나로만 묶지 않고도 관심 있는 작업을 좁혀 볼 수 있다.


근거 수준을 나타내는 `proofLevel`은 이러한 분류 필터와 역할이 다르다. 화면에 붙는 "핵심 증거"나 "탐색" 같은 표시는 머리말 메타데이터에 적힌 값을 읽어 보여 주는 꼬리표일 뿐이다. 실험 근거가 실제로 타당한지는 연결된 로그와 자료를 따로 열어 확인해야 하며, 지표의 출처와 측정 범위도 상세 본문에서 설명해야 한다.


화면 코드가 읽을 수 있는 데이터 형식과 현재 수집기가 실제로 내보내는 데이터도 대조해 보았다. 문서를 읽어 화면에 표시하는 콘텐츠 로더와 화면 표시 함수는 구조화된 `metrics`와 `evaluation` 데이터를 처리할 수 있게 작성되어 있다. 하지만 현재 수집기의 `entryProjectFrontmatter` 함수가 내보내는 항목은 짧은 문자열 하나인 `metric`과 `proofLevel` 정도다. 화면을 그리는 렌더러 코드에 기준선, 데이터셋, 검증 방식을 표시하는 자리가 있다는 것만으로 현재 Notion 수집 경로가 그 값을 모두 채운다고 해석하지는 않았다.


![entryProjectFrontmatter가 내보내는 category, focus와 proofLevel, 단일 metric은 화면 필터와 라벨에 쓰이고, 구조화된 metrics와 evaluation은 수집기에서 전달되지 않으며 실제 근거는 MDX 본문과 실험 로그에서 확인하는 구조도](/images/notion/tech-11-03/image-2.png)

## 빌드 입력의 공개 경계와 다국어 연결


머리말 메타데이터로 화면 표시 항목을 나누는 것 못지않게, 어떤 문서를 사이트에 공개하고 한국어와 영어 문서를 어떻게 이을지도 수집 단계에서 정해진다. 수집기는 Notion 데이터베이스에서 `Published`가 참이면서 `Private` 체크가 없는 항목만 조회해 MDX 파일을 만든다. 이어서 화면 쪽의 [콘텐츠 로더](https://github.com/NAMUORI00/yskim-portfolio/blob/55ff29588b66d75168313936872cdaca99da8684/client/src/content/index.ts)가 생성된 MDX 파일들을 `import.meta.glob`으로 읽어 들인다. 이 코드는 [Vite의 glob import](https://vite.dev/guide/features.html#glob-import) 기능으로, 경로 규칙에 맞는 모든 파일을 한꺼번에 불러와 사이트 빌드 입력으로 묶는다.


사이트를 배포하기 전에 화면 파일을 미리 만들어 두는 **정적 빌드**에서는 브라우저 화면에서 카드를 숨기는 것과 빌드 입력에서 파일을 빼는 것이 다르다. 비공개 원문이 MDX 파일로 만들어져 정적 빌드 결과물에 들어오면, 화면에 카드가 보이지 않더라도 파일 경로로 직접 접근할 수 있다. 이 저장소에서는 앞단의 수집기가 공개 여부를 거르는 경계를 맡으므로, 수동으로 MDX 파일을 추가하거나 다른 경로로 빌드할 때도 같은 제외 조건을 확인해야 한다.


공개 조건을 통과한 프로젝트의 영어 설명도 한국어와 별도 콘텐츠로 관리되며, 자동 번역을 실행하는 코드로 읽히지는 않았다. `Locale` 속성으로 언어를 구분하고, 짧은 항목은 `Key`를, 상세 글은 `slug`를 공통 **식별자**로 삼아 한국어와 영어 문서를 잇는다. 제목을 영어로 번역하더라도 연결 기준인 `Key`나 `slug` 값을 바꾸면 두 언어 문서의 대응 관계가 끊어진다.


![Notion 항목이 Published 참, Private 거짓 조건을 통과해야 생성된 MDX 파일이 되어 import.meta.glob으로 정적 빌드 결과물에 포함되는 파이프라인](/images/notion/tech-11-03/image-3.png)

## GitHub 프로필과 상세 근거의 연결


포트폴리오 사이트에 공개된 프로젝트 상세 글은 외부 첫 화면 역할을 하는 GitHub 프로필과도 이어진다. [GitHub 프로필 소개 문서](https://github.com/NAMUORI00/NAMUORI00/blob/e468da3aa4488d6926d12cfd19f9d11572e18cc3/README.md)는 포트폴리오 주소와 기술 스택 배지, 활동 카드, 연락처를 한곳에 모은다. 계정 이름과 같은 공개 저장소에 안내 문서인 `README.md`를 두어 프로필 첫 화면에 띄우는 방식은 [GitHub 문서](https://docs.github.com/en/account-and-profile/how-tos/profile-customization/managing-your-profile-readme)의 안내를 따른다.


이 문서에 넣은 활동 통계 이미지는 저장소 안의 파일이 아니라 외부 서비스 주소를 참조한다. 따라서 저장소에 `README.md` 파일이 정상적으로 들어 있더라도 외부 이미지 서비스의 응답 상태에 따라 카드는 보이지 않을 수 있다. 또한 커밋 활동 수치나 기술 배지만으로는 개별 프로젝트의 성능과 검증 수준을 알 수 없다. 구체적인 실험 결과와 비교 근거는 프로필에서 연결된 포트폴리오의 각 프로젝트 상세 글에서 다루게 된다.


이처럼 읽기 흐름은 이어지지만, 포트폴리오 사이트는 Notion을 콘텐츠 원본으로 삼는 반면 GitHub 프로필의 `README.md`는 별도로 관리하는 파일이다.


![방문한 독자가 README.md 기반 GitHub 프로필에서 Notion 원본 기반 포트폴리오 목록과 프로젝트 상세 글을 거쳐 저장소와 실험 기록으로 이동하는 흐름도](/images/notion/tech-11-03/image-4.png)

## 결론


포트폴리오 사이트와 GitHub 프로필은 화면마다 맡는 역할에 맞춰 같은 프로젝트의 정보 분량과 원본을 나누어 구성한다. 포트폴리오 저장소는 Notion에서 공개 조건을 통과한 문서만 수집해 머리말 메타데이터로 카드 요약과 분류 필터를 만들고, 상세 본문으로 구현 과정과 실험 근거를 전달한다. GitHub 프로필 저장소는 `README.md`에 짧은 소개와 활동 요약, 포트폴리오 링크를 두어 방문자를 상세 근거로 안내한다.


다만 이번에 읽은 두 저장소 코드만으로는 양쪽의 소개 문장이 자동으로 일치한다고 볼 근거가 없었다. 프로젝트 이름과 대표 주소, 한 줄 요약 가운데 어디까지를 두 저장소에서 똑같이 유지하고 어디부터 각 화면에 맞게 풀어 쓸지는 추가로 정해야 한다. 실제 브라우저 화면의 렌더링 결과와 방문자 이동 흐름이 의도대로 이어지는지도 앞으로 점검할 과제로 남았다. 다음 글에서는 이 프로젝트 설명들의 바탕이 되는 개인 노트 저장소의 동기화와 백업 범위를 이어서 다룬다.
