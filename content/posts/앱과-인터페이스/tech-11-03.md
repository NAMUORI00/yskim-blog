포트폴리오와 GitHub 프로필에서는 짧은 소개에서 프로젝트 설명과 근거 자료로 이어지는 읽기 흐름을 구성했다. 카드의 분류와 상세 본문, 외부 링크를 연결하면서 공개할 정보의 범위도 함께 정리했다.


## 구현과 확인 과정


포트폴리오 사이트의 카드 화면과 상세 글은 같은 프로젝트를 서로 다른 분량으로 보여 준다. 같은 설명을 그대로 복사하면 카드에서는 길고 상세 글에서는 부족해지는 경우가 생긴다. yskim-portfolio와 GitHub 프로필 저장소가 이 정보를 나누는 방식을 비교해 봤다.


yskim-portfolio의 55ff295 커밋과 프로필 저장소 NAMUORI00의 e468da3 커밋을 함께 읽었다. 같은 설명을 여러 곳에 복사하기보다, 각 화면이 보여 주는 정보의 범위와 역할에 초점을 맞췄다. 페이지 속성, 본문, slug의 구분은 앞선 콘텐츠 변환 글에서 이어 온다.


## 카드의 짧은 문장과 상세 본문을 나누기


[yskim-portfolio의 수집 코드](https://github.com/NAMUORI00/yskim-portfolio/blob/55ff29588b66d75168313936872cdaca99da8684/scripts/notion-content.mjs)는 프로젝트의 이름, 기간, 요약, 분류, 태그, 링크 등을 frontmatter로 만들고, 페이지 본문은 MDX 문서의 본문으로 남긴다. 화면에서 짧게 훑을 정보와 자세히 읽을 정보를 같은 문서 안에서 구분한 구조였다.


프로젝트 요약 속성이 비어 있으면 본문의 첫 문단을 대체 요약으로 사용한다. 성과 항목도 별도 속성이 없으면 본문에서 Metric, 성과, Evidence, 증거라는 표지를 찾는다. 빈 카드를 줄이는 대체 규칙이지만, 본문의 첫 문단이 항상 카드에 적합한 요약이 되지는 않는다.


첫 문단에 설치 경로가 적혀 있으면 목록의 대체 요약에도 그 경로가 먼저 나온다. 입력, 하는 일, 결과를 카드에 담고 설치 순서와 비교 근거를 상세 본문으로 보내는 방식이 이 구성에 맞는 편집안으로 보였다. 본문 순서가 카드의 내용에도 영향을 주는 지점이다.

## 프로젝트 분류와 근거 수준


[프로젝트 분류 필터](https://github.com/NAMUORI00/yskim-portfolio/blob/55ff29588b66d75168313936872cdaca99da8684/client/src/lib/projectEvidence.ts)에는 category와 focus라는 두 필터 축이 있다.


category는 커리어, 토이, focus는 연구, 제품, 도구, 실험 등으로 나뉜다. 한 축 안에서 여러 값을 고르면 그중 하나와 일치하면 되고, 서로 다른 축 사이에서는 양쪽 조건을 모두 만족해야 한다.


예를 들어 category에서 토이를, focus에서 도구와 실험을 선택하면, 남는 것은 "토이이면서, 도구 또는 실험인 프로젝트"다. 기술 이름 하나로만 분류하지 않아도 관심 있는 작업을 좁힐 수 있는 구성이었다.


근거 수준을 나타내는 proofLevel은 이 분류와 또 다르다. 화면의 "핵심 증거"나 "탐색" 표시는 작성된 메타데이터를 읽어 붙이는 라벨이다. 실험 근거의 진위는 연결된 로그와 자료를 별도로 검토해야 한다. 지표를 담는 구조가 있더라도 실제 수치의 출처와 측정 범위는 본문 쪽에서 따로 설명하는 영역으로 남아 있다.


UI가 읽을 수 있는 데이터와 현재 수집기가 쓰는 데이터를 대조해 봤다. 콘텐츠 로더와 표시 함수는 구조화된 metrics와 evaluation을 다룰 수 있지만, 현재 entryProjectFrontmatter가 내보내는 필드는 단일 metric과 proofLevel 등이다.


렌더러가 기준선, 데이터셋, 검증 방식을 보여 줄 수 있다는 것만으로 Notion의 현재 수집 경로가 그 정보를 모두 채운다고 해석하지 않았다.


## 콘텐츠 생성 단계의 공개 범위


수집기는 Published이면서 Private 체크가 없는 항목을 조회한다. 이후 [콘텐츠 로더](https://github.com/NAMUORI00/yskim-portfolio/blob/55ff29588b66d75168313936872cdaca99da8684/client/src/content/index.ts)가 생성된 MDX 파일을 import.meta.glob으로 읽는다.


이 방식은 [Vite의 glob import](https://vite.dev/guide/features.html#glob-import)를 사용해 경로 패턴에 맞는 파일들을 빌드 입력으로 모으는 구조다.


브라우저에 보여 주는 단계에서 숨기는 것과 빌드 입력에서 제외하는 것은 다르다. 비공개 원문이 정적 결과물에 포함되면 카드 표시 여부와 관계없이 파일 주소로 접근할 수 있다. 이 저장소에서는 수집 조건이 앞쪽 경계를 맡고 있으므로, 수동으로 생성 파일을 추가하거나 다른 경로로 빌드하는 경우에도 같은 조건이 적용되는지가 확인 대상으로 남아 있다.


같은 프로젝트의 영어 설명도 별도 콘텐츠다. Locale로 언어를 구분하고, 짧은 항목은 Key, 프로젝트 상세는 slug를 기준으로 연결하는 경로를 확인했다. 제목을 번역하더라도 연결에 쓰는 식별자가 바뀌면 대응 관계가 끊어지는 구조다. 자동 번역을 실행하는 코드로 읽지는 않았다.


## GitHub 프로필과 상세 글의 연결


[GitHub 프로필 소개 문서](https://github.com/NAMUORI00/NAMUORI00/blob/e468da3aa4488d6926d12cfd19f9d11572e18cc3/README.md)는 포트폴리오 링크, 기술 스택, 활동 카드와 연락 경로를 모은다.


계정과 같은 이름의 공개 저장소에 둔 README를 프로필에 표시하는 방식은 [GitHub 문서](https://docs.github.com/en/account-and-profile/how-tos/profile-customization/managing-your-profile-readme)에 설명되어 있다.


프로필의 통계 이미지는 외부 서비스 주소를 참조한다. README 자체가 존재하는 것과 외부 카드가 현재 정상적으로 응답하는 것은 별개다. 활동 수치나 기술 배지는 프로젝트의 성능, 검증 수준과는 다른 정보이므로, 구체적인 결과는 해당 프로젝트 설명 쪽에서 다루는 구조가 된다.

## 공통 콘텐츠의 관리 범위


포트폴리오는 Notion을 콘텐츠 원본으로 삼지만 GitHub 프로필 README는 별도 파일이다. 이번에 확인한 두 저장소만으로 모든 소개 문장이 자동으로 일치한다고 말할 근거는 없었다. 공통으로 유지할 프로젝트 이름, 대표 주소, 짧은 요약의 범위와, 각 화면에서 자세히 풀 내용의 경계가 다음 검토 대상으로 남았다.


소스와 생성 경로를 비교한 범위에서 카드, 상세 본문, 외부 근거를 나누는 구조를 확인했다. 방문자 반응과 화면별 렌더링은 별도 확인 항목이다. 다음 글에서는 이 설명의 바탕이 되는 개인 노트의 동기화와 변경 이력 관리를 이어서 살펴본다.


## 작업을 정리하며


프로필은 정보를 많이 넣기보다 독자가 다음 근거로 이동할 수 있게 만드는 것이 중요하다. 카드의 짧은 설명과 상세 본문의 역할을 나누면 프로젝트를 이해하는 순서도 선명해진다. 공개 범위는 화면 표시와 빌드 입력 양쪽에서 확인해야 한다.
