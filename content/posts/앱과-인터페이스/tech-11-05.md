명함 관리 시스템인 `orim-namecard-cms`에서는 프로필 하나가 세 곳에서 서로 다른 상태로 존재한다. 관리자가 브라우저에서 고치는 초안, Git 저장소에 기록된 설정 파일, 외부에 공개된 HTML이 각각 별도의 수명을 갖는다. 데이터를 만들고 읽고 고치고 지우는 작업(CRUD)도 어느 단계의 상태를 다루느냐에 따라 처리 경로가 달라진다.


편집 화면의 미리보기가 실제 공개 화면과 같으려면 화면을 그리는 규칙이 같고 브라우저 초안이 서버 배포본과 어긋나지 않아야 한다. 또한 관리자가 발행 버튼을 눌렀을 때 저장소 반영과 실제 사이트 배포가 동시에 끝나는지도 확인해야 한다. 이 질문들을 확인하려고 `orim-namecard-cms`의 `be2f29a` 커밋에서 입력 폼과 미리보기, 배포 API로 이어지는 코드 경로를 따라가 봤다.


## 미리보기와 공개 화면의 공통 렌더러


먼저 편집 화면의 미리보기와 실제 배포된 명함 화면이 어떻게 같은 모양을 유지하는지 코드에서 확인했다. [공개 페이지](https://github.com/NAMUORI00/orim-namecard-cms/blob/be2f29a89b031765ee842c8ff29e5873053497ea/src/pages/index.astro)는 저장소에 기록된 프로필 정보와 Discord 동기화 결과를 먼저 읽어 들인다. 읽어 온 프로필이 정해진 데이터 형식인 **스키마**(schema)에 맞는지 검사한 뒤 `renderNamecardDocument` 함수가 만든 HTML을 그대로 출력한다.


[관리자 화면](https://github.com/NAMUORI00/orim-namecard-cms/blob/be2f29a89b031765ee842c8ff29e5873053497ea/src/pages/admin.astro)도 미리보기 전용 HTML을 따로 작성하지 않고 같은 `renderNamecardDocument` 함수를 가져와 쓴다. 이 함수가 반환한 HTML 문자열을 웹 페이지 안의 작은 화면 영역인 `iframe`의 `srcdoc` 속성에 넣어 바로 보여 준다. 화면용 HTML을 만드는 **렌더러**(renderer)를 한 곳에서 관리하므로 두 화면에 같은 표현 규칙이 적용되어 구조가 벌어지는 일을 줄일 수 있다.


![브라우저 초안과 저장소 프로필이 각각 공통 카드 렌더러인 renderNamecardDocument를 거쳐 관리자 iframe 미리보기와 배포된 공개 HTML로 출력되는 흐름도](/images/notion/tech-11-05/image-1.png)


그림 1. 같은 카드 렌더러를 공유하면서 서로 다른 입력 상태를 받아 미리보기와 공개 HTML을 만드는 흐름. 출처: index.astro와 admin.astro를 바탕으로 직접 구성.


다만 그림 1처럼 렌더러를 공유하더라도 두 화면에 들어가는 입력 데이터는 서로 다르다. 공개 페이지는 빌드 시점에 고정된 설정 파일을 읽지만, 관리자 미리보기는 현재 브라우저에서 편집 중인 초안을 입력으로 받는다. 업로드 파일의 임시 주소와 브라우저 환경은 미리보기와 공개 화면에서 각각 확인해야 하며, 두 화면의 입력 상태도 따로 대조해야 한다.


## 브라우저 초안과 배포본의 해시 비교


앞 절에서 관리자 미리보기의 입력으로 쓰인 브라우저 초안은 서버로 바로 전송되지 않고 브라우저 내부에 먼저 저장된다. 입력 중인 내용은 웹 페이지의 출처(origin)별로 분리된 브라우저 저장소인 [localStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage)에 기록된다. 여기에 초안을 저장해도 다른 기기나 GitHub 저장소로 전달되지 않으며, 초안을 복원하는 기능과 서버에 반영하는 기능은 완전히 분리되어 있다.


예를 들어 배포본 A를 기준으로 작성하던 초안이 브라우저에 남아 있는 동안, 다른 기기나 경로를 통해 배포본 B가 새로 반영되었다고 해 보자. 만약 배포본 A를 기준으로 쓰던 초안을 배포본 B 위에 그대로 덮어씌우면, B에서 새로 바뀐 항목이 예전 값으로 되돌아갈 수 있다. 이런 시점 어긋남을 막기 위해 `persistDraft` 함수는 편집 중인 프로필 데이터와 저장 시각을 `localStorage`에 기록한다. 이때 현재 배포본 내용을 일정한 길이의 문자열로 요약한 **해시값**(hash)인 `publishedProfileHash`도 함께 남겨 둔다. 나중에 관리자 화면을 다시 열면 저장된 초안의 해시값이 현재 배포본의 해시값과 같을 때만 초안을 복원한다. 원본 내용이 조금만 달라져도 해시값이 바뀌므로, 두 해시값이 다르면 기존 초안을 지우고 현재 배포본을 불러와 편집을 새로 시작한다.


![localStorage에 저장된 초안 해시와 현재 배포본 해시를 publishedProfileHash로 비교해 일치하면 초안을 복원하고 불일치하면 초안을 삭제한 뒤 새 배포본에서 편집을 시작하는 순서도](/images/notion/tech-11-05/image-2.png)


그림 2. 브라우저에 남은 초안의 기준 해시와 현재 배포본 해시를 비교해 초안 복원 여부를 결정하는 흐름.


그림 2의 해시값 비교는 이처럼 오래된 초안이 새 배포본을 덮어쓰는 충돌을 막기 위한 장치로 보였다. 반대로 초안을 작성하는 도중에 서버 배포본이 바뀌면 기존에 브라우저에서 쓰던 초안은 복원되지 않고 버려진다.


## 배포 API의 권한 검증과 저장소 반영


브라우저에서 초안 편집을 마치고 관리자가 발행을 요청하면, 브라우저에만 있던 상태가 서버와 Git 저장소로 넘어간다. 요청을 받는 [배포 API](https://github.com/NAMUORI00/orim-namecard-cms/blob/be2f29a89b031765ee842c8ff29e5873053497ea/functions/api/deploy.ts)는 먼저 요청 형식과 출처(origin), Cloudflare Access 인증을 차례로 확인한다. 인증을 마친 뒤에는 앞서 본 스키마 규칙인 `profileSchema`로 프로필 데이터 구조를 검사한다.


여기서 권한 검사는 관리자 화면의 버튼 노출 여부와 상관없이 서버에서 독립적으로 이루어진다. 인증 검증 함수는 사용자 신원을 서명해 담은 JSON 웹 토큰(JWT)의 발급자와 대상 애플리케이션을 대조한다. 환경 설정에 이메일 허용 목록이 있으면 요청자의 이메일이 그 목록에 포함되는지도 함께 검사한다. 이 과정은 [Cloudflare의 JWT 검증 문서](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/)에서 안내하는 서버 측 토큰 검증 방식과 맞닿아 있다. 브라우저 화면에 로그인 상태가 보이는 것과 별개로 서버가 요청마다 토큰을 직접 확인하는 경로가 코드에 구현되어 있었다. 물론 코드에 검증 로직이 있다는 사실과 실제 운영 환경에 관련 설정값이 올바르게 들어가 있는지는 따로 확인해야 한다.


그림 3처럼 인증과 스키마 검사를 통과하면 [commitProfileAndDispatch](https://github.com/NAMUORI00/orim-namecard-cms/blob/be2f29a89b031765ee842c8ff29e5873053497ea/functions/_shared/github.ts) 함수가 GitHub 저장소 작업을 이어받는다. 이 함수는 프로필이 참조한 업로드 파일이 실제로 존재하는지 확인한 뒤, 작업용 갈래인 변경 **브랜치**(branch)를 새로 만들고 수정된 프로필을 커밋한다. 이어서 임시 경로에 올라와 있던 업로드 파일을 정식 경로로 옮기고, 더 이상 참조하지 않는 기존 업로드 파일 일부를 정리한다. 파일 정리가 끝나면 원래 브랜치에 변경 내용을 합쳐 달라는 변경 요청(PR)을 생성한다. 충돌이 없는 정상 경로에서는 여러 변경을 커밋 하나로 묶어 합치는 단일 커밋 병합(squash merge)으로 이 PR을 `main` 브랜치에 반영한다. 그다음 `production` 브랜치를 강제 갱신(force update) 없이 방금 병합한 위치로 앞당긴다.


![배포 API 검증, GitHub 저장소의 PR 생성과 브랜치 병합, 배포 워크플로의 테스트와 빌드를 거쳐 Cloudflare 공개 페이지가 갱신되는 3단계 파이프라인 다이어그램](/images/notion/tech-11-05/image-3.png)


그림 3. 프로필 발행 요청이 서버 검증과 GitHub 브랜치 반영을 거쳐 공개 페이지 배포로 이어지는 흐름. 출처: 배포 요청 처리, 저장소 변경 처리, 공개 사이트 배포 작업을 바탕으로 직접 구성.


## 요청 완료 응답과 실제 배포 시점의 차이


저장소 브랜치 갱신을 마친 배포 API는 마지막으로 GitHub Actions에 자동 배포 절차인 **워크플로**(workflow) 실행을 요청한다. 그 직후 생성된 커밋과 PR, 병합 여부(`merged`), 워크플로 주소를 담아 브라우저에 응답을 돌려준다. 관리자 화면은 이 API 응답이 성공하면 곧바로 화면에 `Published` 상태와 배포 시작 안내 문구를 띄운다.


여기서 주의할 점은 배포 API가 Cloudflare Pages의 사이트 빌드와 업로드가 끝날 때까지 기다리지 않는다는 것이다. 더구나 관리자 화면의 클라이언트 코드는 성공 여부를 판단할 때 HTTP 응답 상태와 `data.ok` 값만 확인한다. 응답 본문에 함께 들어 있는 `merged` 값은 클라이언트에서 따로 검사하지 않는다.


![배포 API 응답 시점에 관리자 화면에 Published가 표시되지만, 저장소 병합 여부와 워크플로 완료 후 실제 공개 화면 갱신은 별도의 시점에 결정됨을 나타내는 타임라인 다이어그램](/images/notion/tech-11-05/image-4.png)


그림 4. 관리자 화면의 발행 완료 표시 시점과 저장소 병합, 실제 공개 화면 갱신이 확정되는 시점의 차이.


결국 그림 4처럼 발행 요청 접수와 저장소 변경 병합, 실제 사이트 배포 완료는 서로 다른 시점에 확정되는 별개의 상태다. API 호출이 정상으로 끝났더라도 그 뒤에 이어지는 [배포 워크플로](https://github.com/NAMUORI00/orim-namecard-cms/blob/be2f29a89b031765ee842c8ff29e5873053497ea/.github/workflows/deploy-cloudflare.yml)에서 나머지 검사들과 빌드가 차례로 실행된다. 타입 검사, 테스트, 선택적 Discord 동기화, 사이트 빌드와 Pages 업로드 가운데 한 단계라도 실패하면 공개 화면은 바뀌지 않는다. 이 경우 Git 저장소에는 변경 이력이 남았지만 외부 사용자가 보는 공개 명함은 여전히 이전 버전인 상태가 될 수 있다. 이번 코드 검토에서는 워크플로 정의 파일의 실행 순서만 확인했고, 실제 운영 저장소에서 개별 워크플로 실행이 통과했는지는 따로 조회하지 않았다.


## 결론


코드를 따라가며 확인한 `orim-namecard-cms`는 공통 렌더러로 미리보기와 공개 화면의 표현 규칙을 맞추고 프로필 변경과 업로드 파일을 Git 이력으로 남긴다. 다만 렌더러가 같더라도 브라우저 초안과 빌드 설정이라는 입력 데이터 상태가 서로 다르다. 임시 업로드 파일이 정식 경로로 옮겨지는 시점과 최종 빌드가 끝나는 시점 사이에도 시간차가 존재한다. 특히 여러 단계를 거치는 배포 과정이 관리자 화면에는 `Published`라는 단일 상태로 먼저 표시된다. 그 때문에 중간 단계가 실패했을 때 관리자가 어디까지 반영되었는지 바로 파악하기 어렵다는 한계가 남는다.


이번에는 코드를 직접 실행하지 않고 함수 호출 경로와 상태가 바뀌는 조건을 읽는 데까지 진행했다. 후속 확인에서는 특정 프로필 값 하나를 기준으로 브라우저 초안, 변경 커밋, 워크플로 빌드 입력, 최종 공개 페이지를 차례로 대조해 볼 필요가 있다. 이때 중간 단계가 실패했을 때 어느 지점까지 반영되었는지 함께 기록해 두면 재시도 판단에 쓸 수 있다. 다음 글에서는 대시보드와 이전 블로그 자료를 옮길 때 원문과 링크, 그림이 어떻게 연결되는지 이어서 다룬다.
