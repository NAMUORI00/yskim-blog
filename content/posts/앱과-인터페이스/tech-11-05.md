명함 CMS에서는 편집 화면의 미리보기와 배포 화면에 같은 렌더링 규칙을 적용했다. 편집 중인 초안과 서버에 저장된 값, 임시 업로드 주소의 수명이 달라 각 상태가 화면으로 전달되는 경로를 정리했다.


## 구현과 확인 과정


orim-namecard-cms의 코드를 읽으며 편집 화면의 미리보기가 만들어지는 경로와 변경이 공개 화면에 반영되는 경로를 정리했다. 브라우저 초안, 저장소 설정 파일, 배포된 HTML은 각각 별도의 상태를 갖고 있었다.


orim-namecard-cms의 be2f29a 커밋에서 입력 폼, 미리보기, 배포 API, GitHub 작업을 이어 읽었다. CRUD는 데이터를 만들고 읽고 고치고 지우는 동작을 뜻하는데, 이 CMS에서는 같은 프로필 데이터가 브라우저 초안, 저장소 설정 파일, 배포된 HTML에 각각 다른 상태로 존재한다. 어느 쪽을 고치는지에 따라 흐름이 달라지는 구조였다.


## 같은 렌더러로 두 화면을 만들기


[공개 페이지](https://github.com/NAMUORI00/orim-namecard-cms/blob/be2f29a89b031765ee842c8ff29e5873053497ea/src/pages/index.astro)는 저장된 프로필 정보와 Discord 동기화 결과를 읽는다. 프로필을 스키마로 검사한 뒤 renderNamecardDocument가 만든 HTML을 출력한다.


[관리자 화면](https://github.com/NAMUORI00/orim-namecard-cms/blob/be2f29a89b031765ee842c8ff29e5873053497ea/src/pages/admin.astro)도 같은 렌더러를 가져와 미리보기 iframe의 srcdoc에 넣는다.


미리보기 전용으로 비슷한 HTML을 따로 작성하지 않고 같은 출력 함수를 쓰는 구조다. 카드 마크업을 한 곳에서 관리하므로 두 화면이 따로 변경되는 경우가 줄어든다.


다만 입력은 다르다. 공개 페이지는 빌드에 포함된 설정을, 미리보기는 현재 편집 상태를 사용한다. 업로드 파일의 임시 주소와 브라우저 환경은 미리보기와 배포 화면에서 각각 확인해야 한다. 렌더러를 공유해 미리보기와 배포 화면에 같은 표현 규칙을 적용했다. 두 화면의 입력 상태는 별도로 대조해야 한다.

## 브라우저 초안과 기준 배포본


persistDraft는 프로필과 저장 시각, publishedProfileHash를 localStorage에 남긴다. 다시 열 때는 저장된 초안의 해시가 현재 배포본의 해시와 같을 때만 초안을 복원한다. 다르면 이전 초안을 제거하고 현재 배포본에서 편집을 시작한다.


예를 들어 A 배포본에서 작성하던 초안이 브라우저에 남아 있는데 다른 경로에서 B가 배포되었다고 하자. A를 기준으로 한 초안을 B 위에 그대로 복원하면 오래된 필드를 다시 덮을 수 있다. 해시 비교는 이런 충돌을 줄이기 위한 기준으로 읽었다. 반대로 배포본이 달라지면 작성 중이던 초안은 복원되지 않고 버려진다.


[localStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage)는 출처별 브라우저 저장소다. 초안을 저장했다는 사실만으로 다른 기기나 GitHub에 전달되지는 않는다. 이 구조에서 로컬 초안 복원과 서버 반영은 별도 기능이다.


## 발행 요청의 변경 범위


[배포 API](https://github.com/NAMUORI00/orim-namecard-cms/blob/be2f29a89b031765ee842c8ff29e5873053497ea/functions/api/deploy.ts)는 요청 형식과 출처, Access 인증을 확인하고 profileSchema로 프로필을 검사한다.


배포 API는 관리자 화면의 버튼 노출 여부와 별개로 서버 측에서 권한을 검사한다. Access 검증 함수에서는 서명된 토큰의 발급자와 대상 애플리케이션을 확인하고, 설정되어 있으면 이메일 허용 목록도 적용한다.


이 구분은 [Cloudflare의 JWT 검증 문서](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/)에서 설명하는 서버 측 검증과 연결된다.


브라우저의 로그인 표시와 서버 측 검증은 별개이며, 이 코드에서는 서버 측에서 토큰을 직접 검증하는 경로가 있었다. 다만 코드에 검증 경로가 존재한다는 것과 운영 환경에서 설정이 올바르게 적용되어 있는지는 별도의 확인 영역이다.


[commitProfileAndDispatch](https://github.com/NAMUORI00/orim-namecard-cms/blob/be2f29a89b031765ee842c8ff29e5873053497ea/functions/_shared/github.ts)는 참조된 업로드 파일이 존재하는지 확인한 다음 변경 브랜치를 만들고 프로필을 커밋한다.


임시 업로드 자산을 옮기고 더 이상 참조하지 않는 일부 자산을 정리한 뒤 PR을 만든다. 정상적인 병합 경로에서는 main에 squash merge하고 production 브랜치를 강제 갱신 없이 앞으로 이동시킨다.

그림 2. 프로필 변경 요청이 정상적으로 공개 카드에 반영되는 경로. 출처: 배포 요청 처리, 저장소 변경 처리, 공개 사이트 배포 작업을 바탕으로 직접 구성. API 응답은 마지막 공개 화면까지 기다리지 않는다.


## 요청 완료와 배포 진행 상태


API는 GitHub workflow 실행을 요청한 뒤 커밋, PR, 병합 정보와 workflow 주소를 반환한다. 관리자 화면은 응답이 성공하면 Published와 배포 시작을 알리는 문구를 표시한다. 하지만 이 호출이 Cloudflare 빌드와 업로드 완료를 기다리지는 않는다.


클라이언트의 성공 분기는 HTTP 응답과 data.ok를 확인하지만 반환된 merged 값은 별도로 판정하지 않는다. 따라서 "요청이 접수됨", "변경이 병합됨", "배포가 끝남"은 서로 다른 시점에 확정되는 별개 상태다. API 이후 테스트나 배포가 실패할 경우, 저장소 변경은 남고 공개 화면은 이전 버전일 수 있다.


[배포 워크플로](https://github.com/NAMUORI00/orim-namecard-cms/blob/be2f29a89b031765ee842c8ff29e5873053497ea/.github/workflows/deploy-cloudflare.yml)는 타입 검사와 테스트, 선택적 Discord 동기화, 빌드 이후 Pages에 올리는 순서로 구성되어 있다. 이번에는 워크플로 정의를 읽었으며, 특정 실행의 통과 여부는 확인하지 않았다.


## 배포 상태 표시의 후속 정리


이 CMS는 편집 결과를 같은 렌더러로 미리 확인할 수 있고, 설정 변경이 Git 이력에 남는 구조였다. 코드를 읽으면서 남은 부분은 여러 단계를 거친 결과가 관리자에게 얼마나 정확하게 전달되는지였다.


후속 확인에서는 프로필 값 하나를 기준으로 로컬 초안, 커밋, 빌드 입력, 공개 페이지를 대조하고, 중간 실패 시 어디까지 반영되었는지를 함께 기록해 두면 재시도 판단에 쓸 수 있다. 이번에는 실행까지 진행하지 않고 호출 경로를 확인하는 데까지 정리했다. 다음 글에서는 대시보드와 이전 블로그 자료 이전 시 원문, 링크, 그림의 연결을 살펴본다.


## 작업을 정리하며


같은 렌더러를 쓰면 표현 규칙을 맞추기 쉬워지지만 입력 상태는 각각 대조해야 한다. 저장 완료 표시와 배포 확인을 나누고, 임시 파일이 실제 공개 자산으로 바뀌는 지점을 기록하는 구성이 중요하다.
