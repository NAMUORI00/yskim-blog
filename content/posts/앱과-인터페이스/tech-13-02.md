Vue 퀴즈 앱에서는 답안 선택에 따라 점수, 현재 문제, 오답 목록과 종료 화면이 함께 바뀌도록 구성했다. 같은 문제를 다시 푸는 복습 단계까지 이어지면서 최초 점수와 현재 진행 상태를 구분하는 문제가 생긴다. 이 글에서는 그 상태 전이를 중심으로 구현을 정리한다.


## 구현과 확인 과정


JsQuizApp의 답안 선택 함수를 따라 점수와 화면 상태가 바뀌는 과정을 정리했다. 현재 문제 번호, 오답 목록, 종료 화면 조건이 함께 사용되고 있어 한 번의 입력이 바꾸는 값을 차례로 살펴봤다.


6fd768e 커밋은 Vue와 Vite로 만든 객관식 퀴즈 앱이다. 핵심 흐름은 Quiz.vue에 모여 있었다. 답안 선택 이후의 상태 변화와 다음 화면을 결정하는 분기를 중심으로 코드를 읽었다.


## 문제 자체와 현재 위치를 나누기


문제 데이터는 question, answers, correct로 구성된다. correct는 답안 배열에서 정답의 위치를 가리킨다. 예를 들어 답안이 빨강, 파랑, 초록이고 correct가 1이면 두 번째 답안이 정답이다. 배열의 인덱스는 0부터 시작하지만 사람에게 보이는 선택지 번호는 1부터 시작하므로 출력할 때 하나를 더한다.


[Quiz.vue](https://github.com/NAMUORI00/js-quiz-app/blob/6fd768e4010a525c5ea07b8bc58f4ca05092820a/my-quiz-app/src/Quiz.vue)의 questions에는 문제 배열이, currentQuestionIndex에는 현재 위치가 들어간다.


currentQuestion은 이 두 값으로 계산한다. [Vue의 계산된 속성 설명](https://vuejs.org/guide/essentials/computed.html)처럼 파생 값을 따로 수정하는 대신 원래 상태에서 읽어 오는 구성으로 볼 수 있다.


getQuestions는 문제 목록 파일을 받아 배열을 섞는다. 답안 배열을 섞는 코드는 없어 correct의 위치는 문제 안에서 유지된다. 화면에는 10문제라고 안내하지만 진행률과 총점은 questions.length를 사용하고, 열 개만 고르는 처리도 없다. 문제 수가 바뀌면 안내 문구와 실제 배열 길이가 달라질 수 있는 구성이다.


## 답안 선택 시 상태 변경


정상 풀이 중 정답을 고르면 correctAnswers가 증가한다. 틀리면 현재 문제의 인덱스를 incorrectAnswers에 넣는다. 같은 인덱스가 이미 있는지 검사하므로 오답 목록에 같은 문제가 반복해서 쌓이는 것은 막는다.

그림 1. 최초 풀이에서 답안 선택이 점수와 오답 목록을 거쳐 화면 전환으로 이어지는 과정. 출처: Quiz.vue의 checkAnswer를 바탕으로 직접 구성.


오답 목록에는 고유 ID 대신 섞인 문제 배열의 위치가 저장된다. 현재 배열을 유지하는 동안에는 같은 문제를 가리키지만, 다시 섞거나 다음 실행으로 기록을 넘기면 대응이 달라질 수 있다. 안정적인 문제 ID는 이 기능을 확장할 때 검토할 항목이다. 현재 컴포넌트에는 영속 저장 경로가 없다.


restart와 start는 점수, 현재 위치, 오답 목록을 초기화한다. 두 함수 모두 새 문제를 요청하거나 다시 섞지는 않는다. 따라서 재시작은 현재 불러온 문제 배열의 순서를 유지하는 흐름으로 읽었다.


## 오답 복습과 최초 점수 유지


showResult가 참이면 정답을 맞혀도 correctAnswers를 올리지 않는다. 대신 현재 문제를 오답 목록에서 제거하고, 남은 첫 오답으로 이동한다. 모두 해결하면 showQuiz를 거짓으로 바꾼다. 이 동작은 최초 평가 점수와 복습 진행을 구분하는 데 사용할 수 있다. 이는 현재 코드에 대한 해석이며 당시 선택 이유는 별도 기록 확인이 필요하다.


화면도 두 종류의 정보를 함께 보여 준다. 처음 맞힌 개수는 결과 점수에 남고, 해결하지 않은 문제는 오답 목록에서 줄어든다. 예를 들어 다섯 문제 중 셋을 맞힌 뒤 나머지를 모두 복습해도 최초 점수는 3이다. 분기 조건을 설명하기 위해 구성한 점수 예제다.

## 전체 정답 후의 화면 상태


마지막 문제를 처리하는 분기는 currentQuestionIndex를 incorrectAnswers[0]으로 바꾸고 showResult를 참으로 만든다. 전부 맞혔다면 오답 배열은 비어 있으므로 첫 항목은 undefined가 된다. 이때 showQuiz는 여전히 참이고 showTitle은 거짓이다.


문제 제목은 currentQuestion의 존재를 검사하지만 선택지 반복문은 currentQuestion.answers를 직접 읽는다. 전부 맞힌 경우에는 없는 문제의 answers에 접근할 수 있는 조건이 이어진다. 브라우저 오류를 재현한 결과는 아니며 빈 오답 목록의 코드 경로를 따라 확인한 내용이다.


문제 로딩도 비슷했다. getQuestions가 실패하면 콘솔에 오류를 남기지만 별도의 로딩, 실패 상태를 화면에 두지 않는다. 응답이 오기 전에 시작 버튼을 누르거나 빈 배열을 받았을 때는 아직 없는 현재 문제를 참조할 가능성을 따져야 한다. “시작 화면을 닫았다”와 “표시할 문제가 준비됐다”는 서로 다른 조건이었다.


## 화면 갱신과 중복 입력 처리


checkAnswer에는 다음 문제로 이동하기 전 await this.$nextTick()이 있다. [Vue의 nextTick 설명](https://vuejs.org/api/general.html#nexttick)은 반응형 상태 변경 뒤 DOM 갱신 완료를 기다리는 용도로 설명한다. 이 대기는 화면 갱신 시점을 넘기는 역할을 한다. 선택 표시 시간과 중복 클릭 제어는 각각 타이머와 입력 상태로 관리해야 한다.


현재 함수에는 처리 중 여부 검사나 답안 버튼 비활성화 조건이 없다. 빠르게 이어진 입력이 한 답변으로 처리될지 다음 문제의 입력이 될지는 실행 확인이 남아 있다. 문제별 채점 완료 상태를 두는 방법이 이 조건을 명확하게 만들 구조 개선 후보로 보였다.


## 화면 전환 조건의 후속 정리


현재는 showTitle, showResult, showQuiz라는 여러 불리언으로 화면을 표현한다. 작을 때는 읽기 쉽지만 로딩, 오류, 완료 조건이 늘면 허용하지 않을 조합도 함께 늘어난다.


loading, answering, reviewing, completed처럼 하나의 단계 값을 두는 방식도 비교 대상으로 정리했다. 아직 적용한 변경은 아니며 여러 불리언 조합을 줄이기 위한 대안이다.


로딩 중 시작, 빈 문제 배열, 전부 정답, 마지막 오답 해결, 재시작을 확인 목록으로 남겼다. 상태 전환 검증과 문제 데이터의 정답 검토도 따로 수행할 부분이다. 다음 글에서는 HanQuote의 수집 자료가 파일과 정적 화면으로 이어지는 경로를 살펴본다.
