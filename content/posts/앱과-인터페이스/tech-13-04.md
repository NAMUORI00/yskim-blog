GoodPriceJeju에서는 공공데이터의 업소 목록을 지역 검색과 지도 표시로 연결했다. 목록의 주소를 좌표로 바꾸고 카드와 마커를 함께 갱신하면서, 검색 조건과 화면 상태를 같은 업소 기준으로 맞추는 문제를 다뤘다.


## 구현과 확인 과정


GoodPriceJeju에서 업소 목록과 지도 표시가 연결되는 과정을 읽었다. 지역별 파일에서 가져온 업소의 주소를 지도 서비스에 보내 좌표로 바꾸는 구조였다. 목록 데이터의 갱신과 지도 응답이 다루는 범위를 나누어 정리했다.


6c4be14 커밋을 기준으로 목록 항목이 지도 마커로 이어지는 경로를 살펴봤다. README에는 공공데이터 포털의 착한가격 업소 자료로 지역별 정보를 제공하려는 목적이 남아 있었다. 이번에는 저장된 자료와 지도 표시의 연결을 확인했다. 최신 영업 상태와 가격은 별도 조회가 필요하다.


## 정적 파일 기반의 업소 조회


[업소 검색 화면](https://github.com/NAMUORI00/good-price-jeju/blob/6c4be143a24b58f8e0ff559d7bb8646eec74833f/index.html)은 contentsJSON 아래의 지역별 JavaScript 파일을 먼저 불러온다.


이어 지역, 업종 검색과 지도 표시가 jejuContents 같은 배열을 참조한다. 업소 검색 버튼은 웹에서 받아 둔 파일을 대상으로 검색한다.


정적 페이지에서 확보한 자료를 필터링할 수 있는 구성이다. 새 업소나 변경 내용을 반영하려면 데이터 파일과 배포물도 갱신되어야 한다. 지도 SDK의 응답 시점과 업소 목록의 기준 시점은 별도로 읽었다.


[지역과 업종 검색과 지도 표시](https://github.com/NAMUORI00/good-price-jeju/blob/6c4be143a24b58f8e0ff559d7bb8646eec74833f/app.js)의 checkRegionValue는 선택한 지역에 해당하는 배열을 반환한다.


업종 선택은 그 배열에서 음식점, 이미용, 세탁업, 숙박업을 나누고, 검색은 menu 문자열에 검색어가 포함되는 항목을 찾는다. 메뉴 검색은 지역 배열 전체를 대상으로 하며, 선택한 업종과의 AND 조건은 별도로 구성해야 한다.

## 화면 문자열에서 다시 주소를 꺼내는 방식


addList는 title, category, phone, menu, address를 HTML 문자열에 넣는다. addressFunction은 화면의 주소 요소에 클릭 이벤트를 붙이고, 표시된 “주소 : ” 앞부분을 잘라 searchMap으로 넘긴다. 업소 이름도 같은 목록 요소의 자식 위치를 따라 읽는다.


주소와 업소 이름을 화면 요소에서 읽으므로 문구나 자식 요소의 순서가 바뀌면 전달값도 영향을 받는다. 업소 객체를 이벤트에 연결하거나 고유 식별자를 data 속성으로 남기는 방법이 대안으로 보였다. 표시 형식과 데이터 전달을 분리하기 위한 선택이다.


원문 값을 innerHTML로 넣는 경로에는 별도의 이스케이프 처리가 보이지 않는다. 현재 입력은 배포 때 관리하는 정적 자료다. 외부 입력을 실시간으로 받도록 확장한다면 문자열의 HTML 해석 여부를 다시 검토할 부분으로 남았다.


## 주소 조회와 비동기 좌표 응답


searchMap은 geocoder.addressSearch의 성공 콜백에서 첫 결과를 사용한다. 응답의 y를 위도, x를 경도로 LatLng에 넣고 마커를 만든다. 주소는 사람이 읽는 위치 표현이고 좌표는 지도 위의 위치를 가리키므로, 이 변환을 지오코딩이라고 부른다.


[Kakao 지도 API 문서](https://apis.map.kakao.com/web/documentation/#services_Geocoder_addressSearch)에서 주소 검색과 좌표 객체의 역할을 확인할 수 있다.


![13-04-02.png](/images/notion/tech-13-04/image-2.png)


그림 2. 주소 검색 성공 뒤 지도와 로드뷰로 나뉘는 경로. 로드뷰 자료의 존재 여부는 지도 좌표 성공과 별도로 확인할 조건이다. 출처: 지역, 업종 검색과 지도 표시의 searchMap을 바탕으로 직접 구성.


이어 getNearestPanoId에 반경 50m를 넣고 반환된 ID로 로드뷰를 설정한다. [공식 문서](https://apis.map.kakao.com/web/documentation/#RoadviewClient_getNearestPanoId)는 범위 안에 결과가 없으면 null이 전달된다고 설명한다.


현재 콜백에는 결과가 없는 경우를 나누는 검사가 없다. 주소 검색, 마커 생성, 로드뷰 제공은 같은 성공 상태로 묶기 어려운 단계였다.


또한 주소 A를 선택한 뒤 바로 B를 선택했을 때, 두 요청의 완료 순서가 클릭 순서와 같다는 보장은 없다. 현재 searchMap에는 최신 요청 ID를 비교하는 조건이 없다. 실제 화면에서 뒤바뀜을 재현한 것은 아니지만, 마지막 선택과 마지막 응답을 구분할 작은 확인 사례로 남겼다.


## 빈 검색 결과와 이전 화면 처리


검색 결과가 없으면 alert를 띄우고, 결과가 있을 때만 contentsList를 새 목록으로 바꾼다. 따라서 빈 결과라는 안내 뒤에도 이전 목록이 화면에 남을 수 있는 흐름이다. 사용자 입장에서는 그 목록이 새 검색의 결과인지 이전 상태인지 혼동할 여지가 있다.


지역 변경은 목록을 숨기고 지도 마커를 지운다. 업종 변경은 목록을 다시 보여 주지만 메뉴 검색 경로에는 같은 표시 복원 호출이 없다. 값의 필터링뿐 아니라 목록의 표시 상태까지 함께 추적해야 했던 이유다.


초기 위치 표시는 navigator.geolocation의 존재를 검사하지만, getCurrentPosition에는 오류 콜백이 없다. 기능이 존재하는 것과 사용자가 위치 권한을 허용하는 것은 다른 조건이다.


[Geolocation 문서](https://developer.mozilla.org/en-US/docs/Web/API/Geolocation/getCurrentPosition)도 권한과 실패 콜백을 구분한다. 기본 지도 중심, 위치 획득 실패, 업소 주소 검색 실패는 각각 다른 표시 상태로 다룰 수 있는 보완 항목이다.


## 데이터와 화면의 식별자 연결


파일 연결에서도 확인할 지점이 있었다. HTML은 ulsanContents.js를 요청하지만 Git 트리에 기록된 이름은 ulsancontents.js다. 대소문자를 구분하는 호스팅에서는 다른 경로가 될 수 있다. 로컬에서 파일이 열리는 것과 배포 서버에서 같은 경로가 제공되는지를 분리해서 확인해야 한다.


CSV 변환 코드는 업소 검색 화면과 분리된 표 데이터 변환 실습으로 남아 있다. 이 함수를 현재 사이트의 실시간 수집기로 소개하지 않고, 자료 준비 과정의 실습 기록으로 구분했다.


업소 ID로 원본 항목, 목록 카드, 지도 마커를 연결하는 방식은 후속 개선안으로 정리했다. 검색 결과 없음, 좌표 없음, 로드뷰 없음은 작은 예제로 확인할 상태다. 이 대응이 있으면 화면 표현을 바꾼 뒤에도 표시 중인 원본 자료를 추적할 수 있다.
