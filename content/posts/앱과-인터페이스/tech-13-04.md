공공데이터 포털의 착한가격 업소 자료를 웹에서 검색하고 지도에 표시할 때는, 목록에서 고른 업소와 지도가 가리키는 위치가 항상 같아야 한다. GoodPriceJeju는 지역별 업소 자료를 파일로 불러와 화면 목록으로 보여 주고, 사용자가 누른 주소를 지도 서비스에 보내 마커와 로드뷰로 표시한다. 저장소의 `6c4be14` 커밋을 기준으로 업소 목록이 지도 마커까지 이어지는 코드 흐름을 따라가 봤다. 이 과정에서 검색 조건과 화면 표시 상태, 외부 지도 응답이 서로 어긋나는 조건을 확인할 수 있었다.


## 지역별 업소 파일과 검색 경로


업소 목록이 지도에 표시되기까지는 먼저 지역별 업소 자료를 불러와 검색 조건으로 거르는 단계를 거친다. [업소 검색 화면](https://github.com/NAMUORI00/good-price-jeju/blob/6c4be143a24b58f8e0ff559d7bb8646eec74833f/index.html)은 페이지를 열 때 `contentsJSON` 폴더 아래에 있는 지역별 JavaScript 파일을 먼저 읽어 온다. 이후 지역 선택, 업종 분류, 메뉴 검색, 지도 표시는 모두 `jejuContents`처럼 코드 어디서나 읽을 수 있는 전역 배열을 참조한다. 검색할 때마다 서버에 요청을 보내지 않고, 내용을 미리 적어 둔 **정적 파일**의 배열에서 조건에 맞는 항목을 거른다.


저장소에는 CSV 변환 코드도 남아 있지만, 검색 화면과 연결된 실시간 수집기가 아니라 자료를 준비할 때 작성한 표 데이터 변환 실습 코드다. 앱이 배포 시점의 정적 파일만 읽으므로, 새 업소를 추가하거나 기존 정보를 고치려면 데이터 파일과 배포물을 함께 갱신해야 한다. README에 적힌 목적처럼 지역별 착한가격 업소 정보를 안내할 수는 있지만, 최신 영업 상태나 실시간 가격 변동을 반영하려면 별도 조회 경로가 필요하다. 또한 `index.html`은 `ulsanContents.js`를 요청하지만 Git 트리에 기록된 실제 파일 이름은 `ulsancontents.js`다. 대소문자를 구분하지 않는 로컬 환경에서는 파일이 열려도, 대소문자를 구분하는 호스팅 서버에서는 다른 경로로 처리된다. 따라서 실제 배포 환경에서는 파일 경로의 대소문자 일치 여부를 따로 점검할 필요가 있다.


불러온 지역별 배열을 거르는 동작은 [지역과 업종 검색과 지도 표시](https://github.com/NAMUORI00/good-price-jeju/blob/6c4be143a24b58f8e0ff559d7bb8646eec74833f/app.js) 코드가 맡는다. 사용자가 지역을 고르면 `checkRegionValue` 함수가 해당 지역의 업소 배열을 돌려준다. 이어 업종을 선택하면 그 배열에서 음식점, 이미용, 세탁업, 숙박업 항목을 걸러 낸다. 검색창에 단어를 입력할 때는 `menu` 문자열에 검색어가 포함된 항목만 추려 낸다. 그런데 메뉴 검색은 앞서 선택한 업종 결과를 이어받지 않고 지역 배열 전체를 처음부터 다시 뒤진다. 업종과 메뉴를 동시에 만족하는 교집합(AND) 검색을 지원하려면 두 조건을 함께 적용하는 경로를 따로 구성해야 한다.

## 화면 목록과 주소 전달 방식


추려 낸 업소 배열을 화면 목록으로 그리고 클릭한 주소를 지도로 넘기는 일은 `addList`와 `addressFunction` 함수가 맡는다. `addList`는 업소의 `title`, `category`, `phone`, `menu`, `address` 값을 HTML 문자열로 이어 붙여 `innerHTML`에 넣는다. 현재 입력값은 배포할 때 함께 관리하는 정적 자료여서 문제가 드러나지 않는다. 하지만 문자열이 HTML 태그로 해석되지 않게 바꾸는 **이스케이프**(escape) 처리가 없어, 외부 입력을 실시간으로 받아 표시하도록 확장한다면 이 처리를 추가해야 한다.


목록이 화면에 그려진 뒤에는 `addressFunction`이 각 주소 요소에 클릭 이벤트를 붙인다. 사용자가 주소를 누르면 화면에 적힌 문자열에서 `"주소 : "` 앞부분을 잘라 내고 남은 문자열을 지도 검색 함수인 `searchMap`으로 넘긴다. 지도 마커에 띄울 업소 이름도 화면 요소를 나무 모양으로 묶은 **DOM** 구조에서 클릭한 요소의 부모와 자식 위치를 따라가며 화면 글자로 다시 읽어 온다.


이 방식은 화면에 표시된 문구와 DOM 구조가 데이터를 전달하는 통로 역할까지 겸한다는 한계가 있다. 예를 들어 화면 문구를 `"주소 : "`에서 다른 말로 바꾸거나 자식 요소 순서를 조정하면, `searchMap`에 넘어가는 주소와 업소 이름도 함께 깨진다. 화면 표시 형식과 데이터 전달을 분리하려면 이벤트를 등록할 때 원본 업소 객체를 직접 연결하는 편이 안전하다. 또는 각 목록 요소의 `data` 속성에 고유 식별자(ID)를 남겨 두고 원본 배열에서 다시 조회하는 방식으로 바꿀 수 있다.

## 주소의 좌표 변환과 로드뷰 조회


화면에서 넘겨받은 주소 문자열을 지도 위 마커로 바꾸려면 사람이 읽는 주소를 위도와 경도 좌표로 변환해야 하는데, 이를 **지오코딩**(geocoding)이라고 부른다. `searchMap`은 카카오 지도 SDK의 `geocoder.addressSearch`를 호출해 주소를 좌표로 바꾼다. 외부 서버에서 응답이 올 때까지 화면을 멈추지 않는 **비동기** 방식이어서, 응답이 도착한 뒤 실행할 작업을 **콜백 함수**로 함께 넘긴다. [Kakao 지도 API 문서](https://apis.map.kakao.com/web/documentation/#services_Geocoder_addressSearch)에서 안내하듯 주소 검색이 성공하면 이 콜백 함수로 결과 배열이 넘어온다. 코드는 첫 번째 결과의 `y`를 위도로, `x`를 경도로 삼아 `LatLng` 좌표 객체를 만들고 지도 위에 마커를 찍는다.


마커를 표시한 뒤에는 같은 좌표를 기준으로 `getNearestPanoId`에 반경 50m를 넘겨 가까운 로드뷰 파노라마 ID를 찾고 로드뷰 화면을 갱신한다. 그러나 주소 좌표를 찾았다고 해서 반경 50m 안에 로드뷰 자료까지 항상 존재하지는 않는다. [공식 문서](https://apis.map.kakao.com/web/documentation/#RoadviewClient_getNearestPanoId)를 보면 지정한 반경 안에 로드뷰가 없을 때 콜백 함수에 `null`이 전달된다. 현재 `searchMap` 콜백 함수에는 반환된 ID가 `null`인지 확인하는 분기가 없다. 그 때문에 주소 좌표 변환 성공과 마커 생성, 로드뷰 표시를 하나의 성공 상태로 묶어 처리하고 있다.


![선택한 업소 주소를 검색해 응답이 OK일 때 위도와 경도로 변환한 뒤 마커 생성과 반경 50m 로드뷰 조회로 나뉘는 비동기 콜백 순서도](/images/notion/tech-13-04/image-3.png)


그림 3. 주소 검색 성공 뒤 지도 마커 생성과 반경 50m 로드뷰 조회로 나뉘는 비동기 콜백 흐름. 출처: 지역, 업종 검색과 지도 표시의 searchMap 코드를 바탕으로 직접 구성.


비동기 응답이 도착하는 순서도 함께 따져 봐야 한다. 사용자가 목록에서 업소 A의 주소를 누른 직후 업소 B의 주소를 연달아 눌렀을 때, 두 네트워크 요청의 응답이 클릭한 순서대로 도착한다는 보장은 없다. 현재 `searchMap`에는 마지막으로 요청한 항목이 무엇인지 비교하는 요청 ID 검사가 없다. 실제 화면에서 응답 순서가 뒤바뀌는 현상을 직접 재현한 것은 아니다. 다만 사용자가 마지막에 고른 업소와 지도에 찍히는 마커를 일치시키려면 최신 요청인지 확인하는 조건이 필요하다.


## 빈 검색 결과와 화면 표시 상태


외부 지도 응답뿐 아니라 업소 배열을 거르는 코드와 화면 요소의 표시(visibility) 상태가 따로 움직이는 구간도 있었다. 검색어를 입력했을 때 일치하는 업소가 없으면 코드는 `alert`로 안내창만 띄우고, 검색 결과가 있을 때만 `contentsList`를 새 목록으로 교체한다. 그 결과 검색 결과가 없다는 경고창을 닫은 뒤에도 화면에는 직전 검색 목록이 그대로 남는다. 사용자 입장에서는 남아 있는 목록이 방금 입력한 검색어의 결과인지 이전 화면인지 헷갈릴 수 있다.


지역과 업종을 바꿀 때 목록 영역을 숨기고 다시 보여 주는 흐름도 경로마다 달랐다. 지역을 바꾸면 기존 목록을 숨기고 지도 마커를 지운다. 이후 업종을 고르면 숨겨진 목록 영역을 다시 화면에 표시하지만, 업종을 거치지 않고 곧바로 메뉴 검색을 실행하는 경로에는 목록 표시를 복원하는 호출이 빠져 있다. 배열 값을 거르는 일 못지않게 화면 요소의 숨김과 표시 상태를 모든 검색 경로에서 일관되게 맞추는 일이 중요했다.


![지역 변경, 업종 선택, 메뉴 검색, 검색 결과 없음 네 가지 동작에 따라 목록 배열 갱신과 화면 표시 상태가 달라지는 과정을 비교한 그림](/images/notion/tech-13-04/image-4.png)


그림 4. 지역 변경, 업종 선택, 메뉴 검색, 빈 결과 발생 시 목록 내용과 화면 표시 상태가 바뀌는 실제 코드 흐름.


처음 페이지를 열 때 현재 위치를 지도에 표시하는 코드에서도 비슷한 생략이 보였다. 코드는 브라우저에 `navigator.geolocation` 기능이 있는지는 먼저 검사한다. 그러나 실제 위치를 가져오는 `getCurrentPosition` 호출에는 실패했을 때 실행할 오류 콜백 함수를 넘기지 않았다. 브라우저가 위치 조회 기능을 지원하는 것과 사용자가 위치 권한을 허용하는 것은 별개의 조건이다. [Geolocation 문서](https://developer.mozilla.org/en-US/docs/Web/API/Geolocation/getCurrentPosition)에서도 권한 거부나 위치 획득 실패를 처리하는 오류 콜백을 성공 콜백과 구분한다. 기본 지도 중심 표시, 현재 위치 권한 거부, 업소 주소 검색 실패를 각각 별도의 화면 상태로 나누어 다룰 여지가 있다.


## 결론


GoodPriceJeju의 코드를 따라가 보니, 정적 파일의 업소 목록과 지도의 비동기 응답을 연결하려면 화면 상태와 원본 데이터를 잇는 기준이 분명해야 했다. 화면 글자를 잘라 주소를 넘기거나 검색 결과가 없을 때 이전 DOM 요소를 그대로 두면, 사용자가 보는 목록과 지도가 가리키는 위치가 쉽게 어긋난다.


다음에 이 구조를 손본다면 원본 업소 배열과 화면 목록 항목, 지도 마커에 공통 업소 ID를 붙이는 일부터 시작할 수 있다. 공통 식별자로 세 요소를 묶어 두면 화면 문구나 마크업 구조를 바꾸더라도 선택된 원본 자료를 정확히 찾을 수 있다. 검색 결과 없음이나 좌표 변환 실패, 반경 50m 내 로드뷰 없음 같은 예외 상태도 단계별로 나누어 안내하기 쉬워진다.
