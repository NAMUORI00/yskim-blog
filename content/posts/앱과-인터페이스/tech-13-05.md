FoodScan에서는 음식 사진을 올리고 인식 후보를 영양정보와 연결하는 앱 흐름을 만들었다. Flutter 화면과 FastAPI 서버를 연결하는 과정에서 중요한 문제는 외부 API의 음식 이름과 앱에 저장한 이름을 어떻게 맞추고, 사용자가 어느 단계에서 결과를 확인하게 할지였다.


## 구현과 확인 과정


학부 팀 프로젝트 FoodScan에서 음식 사진을 올리고 영양정보 후보로 연결하던 흐름을 다시 정리했다. 사진을 보내면 성분표가 바로 나올 것처럼 보이지만, 실제 코드는 이미지 검색과 영양정보 조회를 서로 다른 단계로 처리하고 있었다.


이 차이가 흥미로웠다. 외부 API가 돌려주는 음식 이름 후보를 앱에 넣어 둔 영양정보와 연결하고, 마지막에는 사용자가 확인해야 한다. 팀 전체 구현을 개인 성과로 옮기기보다 `a8b8fbf` 커밋의 Flutter 화면과 FastAPI 서버가 어떤 값을 주고받는지 살펴봤다. 이 글은 음식 인식, 영양정보 연결 코드의 구조를 다룬다. 정확도와 영양성분 추정 성능은 별도 평가 대상으로 남아 있다.


## 서버의 이미지 검색 후보 응답


현재 메인 화면에서 사용하는 [ImageSearchWidget](https://github.com/NAMUORI00/food-scan/blob/a8b8fbf58589798607435339c3d86983a675f5f5/Flutter_Client/lib/image_search/image_search_widget.dart)은 선택한 이미지를 multipart 요청으로 /upload/web에 보낸다.


서버는 파일을 저장하고 web_annotate를 호출한다. [사진의 웹 검색 처리](https://github.com/NAMUORI00/food-scan/blob/a8b8fbf58589798607435339c3d86983a675f5f5/FASTAPI_SERVER/vision_fastapi-master/module/web_detect.py)는 Google Cloud Vision의 Web Detection 결과를 돌려준다.


[공식 Web Detection 설명](https://docs.cloud.google.com/vision/docs/detecting-web)은 이미지와 관련된 웹 개체와 웹 참조를 찾는 기능으로 소개한다.


이 저장소의 /upload/web은 그중 web_entities의 description과 score를 추려 응답한다. 영양성분을 이미지에서 직접 측정하거나 서버 데이터베이스에서 조회하는 함수는 이 경로에 없다.


클라이언트는 별도로 앱에 포함된 영양정보 목록을 읽는다. 영어 이름과 라틴 표기는 소문자로 바꿔 비교하고, 한글 이름은 그대로 비교한다. 이름이 맞는 로컬 항목을 찾으면 영양정보 객체와 검색 점수를 FoodInfo로 묶는다.


[Flutter의 loadString](https://api.flutter.dev/flutter/services/AssetBundle/loadString.html)을 사용한 번들 파일 읽기이므로, 이 단계는 매 요청마다 외부 영양정보 데이터베이스를 갱신하는 방식과 다르다.

## 검색 점수 표시와 해석 범위


클라이언트는 WebEntity의 score에 배율을 적용해 반올림한 값을 확인창의 일치율로 표시한다. 코드에 쓰인 배율은 100이다. 이 표시를 해석하기 위해 외부 API가 설명하는 점수의 의미를 함께 확인했다.


[WebEntity 공식 명세](https://docs.cloud.google.com/vision/docs/reference/rest/v1/AnnotateImageResponse#WebEntity)는 score를 관련성 점수로 설명하며, 정규화되어 있지 않고 서로 다른 이미지 질의 사이에서 비교할 수 없다고 밝힌다.


따라서 0.8을 80으로 바꿔 표시했다고 “이 음식일 확률 80%”라는 근거가 생기지는 않는다. 음식명과 영양정보가 맞는지, 실제 섭취량이 얼마인지는 별도의 확인이다. 높은 검색 관련성은 이런 질문에 직접 답하지 않는다.


설명용으로 검색 후보가 Kimchi stew이고 로컬 자료의 이름이 Kimchi-jjigae라고 해 보자. 사람이 같은 음식을 가리킨다고 읽더라도 현재의 문자열 일치 규칙에서는 연결되지 않을 수 있다. 반대로 이름이 같아도 조리법이나 제공량이 다르면 실제 영양량까지 같다고 가정하기 어렵다. 문자열 연결 규칙을 설명하기 위해 구성한 예제다.


## 등록 요청과 비동기 응답 처리


등록 버튼은 uploadImage를 호출한 직후 foodData.isNotEmpty를 검사한다. 호출에 await가 없으므로 새 응답이 오기 전에 기존 목록을 읽을 수 있다. uploadImage 안에서도 응답 스트림에 listen을 등록하고, 나중에 도착한 값에서 foodData에 항목을 추가한다.


첫 요청에서는 목록이 비어 확인창이 열리지 않을 수 있고, 다음 요청에는 이전 이미지의 결과가 남을 수 있다. 요청마다 목록을 비우거나 요청 식별자로 응답을 구분하는 코드도 보이지 않았다. 실제 모바일 재현은 수행하지 않았으며 코드의 비동기 호출 순서를 확인한 내용이다.

그림 2. 새 응답이 도착하기 전에 후보 목록을 확인하는 현재 호출 순서. 출처: 등록 버튼과 uploadImage 콜백을 바탕으로 직접 구성.


응답 스트림의 각 문자열 조각을 곧바로 JSON 파서에 넣는 경로도 확인했다. 네트워크 조각과 JSON 문서의 경계는 같다고 보장되지 않는다. 전체 응답을 모아 상태 코드와 구조를 검사한 뒤 파싱하는 방식은 업로드와 후보 준비 상태를 구분할 개선 후보로 남았다.


## 후보 전달과 편집 화면 완성도 나누어 보기


사용자가 확인하면 음식 이름, 제공량, 열량, 영양소를 DataEdit 경로의 매개변수로 보내려는 코드가 있다. 하지만 [DataEditWidget](https://github.com/NAMUORI00/food-scan/blob/a8b8fbf58589798607435339c3d86983a675f5f5/Flutter_Client/lib/data_edit/data_edit_widget.dart)의 현재 생성자는 protein과 dataIndex만 받는다. 여러 필드로 입력창을 초기화하던 부분도 주석 처리되어 있다.


더 앞의 [라우터](https://github.com/NAMUORI00/food-scan/blob/a8b8fbf58589798607435339c3d86983a675f5f5/Flutter_Client/lib/flutter_flow/nav/nav.dart)도 DataEditWidget을 매개변수 없이 만든다.


후보 생성 이후 편집 화면으로 값을 전달하는 계약은 아직 이어서 확인할 부분이 있었다. 편집 화면 버튼에도 로그 출력만 남아 있어 이 경로에서 식단의 영속 저장 완료까지 확인할 수는 없었다. README의 목표와 현재 코드가 전달하는 값을 나누어 정리했다.


## 이미지 처리 상태의 후속 정리


외부 검색과 번들 영양정보를 연결하면 작은 이름 대응표부터 구성할 수 있다. 다만 이름 비교, 후보 선택, 제공량 확인은 각각 별도의 판단이다. 현재 확인창은 전체 후보의 첫 항목을 사용하고 있어 그 선택 기준도 추가 검토 항목으로 남았다.


이미지 선택 취소, 후보 없음, 같은 이름의 여러 항목, 이전 응답의 늦은 도착을 확인 예제로 정리했다. 요청별 후보 목록과 응답 완료 상태, 편집 화면이 받는 객체를 차례로 대조할 수 있다. 이번 기록은 코드 연결 검토까지이며 음식 인식 정확도나 성분 추정 성능은 측정하지 않았다.


## 작업을 정리하며


이 작업을 정리하며 가장 중요하게 보는 부분은 인식 후보가 식단 기록으로 확정되는 경계다. 이름 대응표, 후보 선택, 제공량 확인을 나누면 사용자가 고칠 수 있는 지점도 분명해진다. 다음 보완에서는 후보 객체가 편집 화면과 저장 단계까지 같은 의미로 전달되는지부터 확인하려 한다.
