학부 팀 프로젝트인 FoodScan에서는 음식 사진을 올리면 인식 후보를 영양정보와 연결해 보여 주는 앱 흐름을 만들었다. 겉보기에는 사진을 서버로 보내면 영양성분표가 바로 돌아올 것 같지만, 실제 코드는 이미지 검색과 영양정보 조회를 서로 다른 단계로 나누어 처리한다. FastAPI 서버가 외부에서 음식 이름 후보를 받아 오면, Flutter 앱이 내부의 영양정보 목록과 이름을 대조해 후보를 만들고 사용자의 확인을 거친다.


외부 검색으로 얻은 음식 이름과 앱 안의 영양정보를 어떻게 맞추고, 그 결과를 편집 화면까지 어떻게 넘기는지 보려고 `a8b8fbf` 커밋 시점의 코드를 다시 따라가 보았다. 팀 전체의 구현을 개인 성과로 돌리기보다 당시 Flutter 화면과 FastAPI 서버가 실제로 어떤 값을 주고받는지 코드의 연결 구조만 짚어 본 기록이다. 음식 인식 정확도와 영양성분 추정 성능은 별도의 평가 대상이므로 이 글에서는 다루지 않는다.


## 외부 이미지 검색과 내부 영양정보 연결


먼저 사용자가 고른 음식 사진이 서버의 이미지 검색을 거쳐 앱 내부의 영양정보와 합쳐지는 과정을 따라간다. 메인 화면에서 동작하는 [ImageSearchWidget](https://github.com/NAMUORI00/food-scan/blob/a8b8fbf58589798607435339c3d86983a675f5f5/Flutter_Client/lib/image_search/image_search_widget.dart)은 사용자가 고른 사진을 파일을 담아 보내는 `multipart` 요청에 넣는다. 앱은 이 요청을 FastAPI 서버의 `/upload/web` 경로로 보낸다. 서버는 전송받은 파일을 저장한 뒤 `web_annotate` 함수를 호출한다. 이 함수가 들어 있는 [사진의 웹 검색 처리](https://github.com/NAMUORI00/food-scan/blob/a8b8fbf58589798607435339c3d86983a675f5f5/FASTAPI_SERVER/vision_fastapi-master/module/web_detect.py) 모듈은 Google Cloud Vision API의 Web Detection 결과를 돌려준다.


[공식 Web Detection 설명](https://docs.cloud.google.com/vision/docs/detecting-web)을 보면 이 기능은 사진만으로 음식 성분을 분석하는 도구가 아니라 이미지와 관련된 웹 개체와 웹 참조를 찾는 기능이다. 서버의 `/upload/web` 경로 역시 응답 가운데 `web_entities`의 설명 문자열(`description`)과 검색 점수(`score`)만 추려 반환한다. 사진에서 영양성분을 직접 측정하거나 서버 데이터베이스에서 영양정보를 조회하는 함수는 이 경로에 없다.


서버가 이름 후보와 점수만 돌려주기 때문에 영양정보를 찾아 붙이는 작업은 Flutter 앱이 맡는다. 앱은 [Flutter의 loadString](https://api.flutter.dev/flutter/services/AssetBundle/loadString.html)을 사용해 앱 안에 미리 묶어 둔 영양정보 파일을 읽는다. 매 요청마다 외부 영양정보 데이터베이스를 새로 조회하지 않고, 앱에 포함된 고정 목록과 서버가 돌려준 검색 후보의 이름을 맞대어 비교한다. 영어 이름과 라틴 표기는 소문자로 바꾼 뒤 비교하고 한글 이름은 원래 글자 그대로 비교한다. 이름이 일치하는 앱 내부 항목을 찾으면 영양정보 객체와 검색 점수를 `FoodInfo` 하나로 묶어 후보 목록에 넣는다.

## 검색 점수 해석과 이름 비교의 한계


앞 단계에서 만든 후보 목록은 사용자 확인창에 표시되는데, 이때 함께 보여 주는 검색 점수와 이름을 비교하는 규칙에는 한계가 있다. 예를 들어 서버가 `WebEntity`의 `score`로 `0.8`을 돌려주면, 앱은 여기에 배율 `100`을 곱하고 반올림해 확인창에 일치율 `80`으로 표시한다. 그러나 외부 API 명세를 확인해 보면 이 숫자를 사진 속 음식이 그 항목일 확률이 80%라는 뜻으로 해석하기는 어렵다.


[WebEntity 공식 명세](https://docs.cloud.google.com/vision/docs/reference/rest/v1/AnnotateImageResponse#WebEntity)는 `score`를 정답 확률이 아니라 검색 관련성 점수로 설명한다. 점수를 일정한 기준으로 맞추는 **정규화**가 되어 있지 않고, 서로 다른 이미지 검색 요청 사이에서 점수를 비교할 수도 없다고 밝힌다. 검색 관련성이 높더라도 음식 이름과 영양정보가 실제로 맞는지, 사용자가 섭취한 양이 얼마인지는 별도로 확인해야 한다.


영어 소문자 변환만 거쳐 글자가 똑같아야만 이어지는 이름 비교 규칙에도 한계가 있다. 예를 들어 서버의 검색 후보가 `Kimchi stew`이고 앱 내부 자료의 이름이 `Kimchi-jjigae`인 경우가 있다. 사람은 같은 음식으로 읽지만 현재의 문자열 일치 규칙에서는 글자가 달라 두 이름이 연결되지 않는다. 반대로 이름이 같아도 조리법이나 제공량이 다르면 실제 영양성분까지 같다고 보기 어렵다. 게다가 현재 확인창은 이름이 일치한 전체 후보 가운데 첫 번째 항목만 꺼내 보여 주므로, 여러 후보가 잡혔을 때 어떤 기준으로 고를지도 검토가 필요하다.


![Kimchi stew와 Kimchi-jjigae가 문자열 불일치로 누락되는 과정과 WebEntity score 0.8에 배율 100을 적용해 80%로 표시하지만 비정규화 관련성 점수임을 비교한 도식](/images/notion/tech-13-05/image-2.png)

## 등록 버튼의 비동기 호출과 응답 파싱


후보를 고르는 기준뿐만 아니라, 사진을 올리고 확인창을 여는 등록 버튼의 실행 순서와 서버 응답을 읽는 과정에도 빈틈이 있다. 서버에 사진을 보내고 응답을 받는 작업은 시간이 걸리므로, 앞 작업이 끝나기를 기다리지 않고 다음 코드를 실행하는 **비동기** 방식으로 처리한다. 그런데 등록 버튼은 사진을 올리는 `uploadImage`를 호출한 직후, 완료를 기다리는 `await` 없이 곧바로 `foodData.isNotEmpty`를 검사한다. 이 때문에 서버에서 새 응답이 도착하기 전에 기존 `foodData` 목록을 먼저 읽게 된다. 정작 `uploadImage` 안에서는 데이터를 조각내어 차례대로 흘려보내는 응답 **스트림**에 `listen`을 등록해 둔다. 서버 응답이 나중에 도착하면 그때서야 `foodData` 목록에 새 후보 항목을 추가한다.


실제 모바일 기기에서 재현 실험을 하지는 않았지만 코드의 비동기 호출 순서만 따라가 보면 첫 요청에서는 목록이 비어 있어 확인창이 열리지 않을 수 있다. 반대로 다음 요청에서는 이전에 올린 사진의 결과가 목록에 남아 있을 수 있다. 요청마다 목록을 비우거나 요청 식별자로 응답을 구분하는 코드도 보이지 않았다.

도착한 문자열을 프로그램이 다룰 수 있는 데이터 구조로 바꾸는 **파싱** 부분도 마찬가지다. 현재 코드는 응답 스트림이 내보내는 각 문자열 조각을 곧바로 JSON 파서에 넣는다. 하지만 네트워크 조각의 경계와 JSON 문서의 경계는 항상 같다고 보장되지 않는다. 전체 응답을 끝까지 모은 뒤 상태 코드와 문서 구조를 검사하고 파싱해야 이미지 업로드 완료와 후보 목록 준비 상태를 명확히 구분할 수 있다.


## 확인창과 편집 화면의 값 전달 경계


응답이 무사히 도착해 사용자가 확인창에서 후보를 확정하더라도, 그 값을 다음 편집 화면으로 넘기는 단계에서 연결이 한 번 더 끊긴다. 사용자가 확인창에서 후보를 확정하면 코드는 음식 이름, 제공량, 열량, 영양소를 화면 사이에 전달하는 값인 **매개변수**에 담아 `DataEdit` 경로로 보내려 한다. 하지만 값을 받는 편집 화면 쪽 코드를 확인해 보면 연결이 완결되지 않은 상태다.


먼저 화면 이동을 이어 주는 [라우터](https://github.com/NAMUORI00/food-scan/blob/a8b8fbf58589798607435339c3d86983a675f5f5/Flutter_Client/lib/flutter_flow/nav/nav.dart)는 전달받은 값을 넘기지 않고 `DataEditWidget`을 매개변수 없이 생성한다. 편집 화면인 [DataEditWidget](https://github.com/NAMUORI00/food-scan/blob/a8b8fbf58589798607435339c3d86983a675f5f5/Flutter_Client/lib/data_edit/data_edit_widget.dart)을 처음 만들 때 값을 받는 생성자 역시 `protein`과 `dataIndex`만 매개변수로 받는다. 여러 영양소 필드로 입력창을 초기화하던 코드도 주석으로 막혀 있어 실행되지 않는다. 편집 화면의 버튼에도 로그 출력만 남아 있어, 저장소 `README`에 적힌 목표와 달리 이 경로에서 식단 기록을 남기는 영속 저장 완료까지는 확인할 수 없었다.

## 결론


지금까지 `a8b8fbf` 커밋 시점의 FoodScan 코드를 따라가며 사진 업로드부터 식단 편집 화면까지의 연결 구조를 확인했다. FastAPI 서버가 외부 이미지 검색에서 음식 이름 후보와 관련성 점수를 받아 오면, Flutter 앱이 내부 영양정보 파일과 이름을 대조해 후보 목록을 만든다. 그러나 비정규화 점수의 백분율 표시, 문자열 완전 일치 비교, `await` 없는 비동기 호출과 스트림 조각 파싱, 라우터와 편집 화면의 매개변수 단절이 코드에 남아 있었다.


이번 검토는 코드의 연결 경로만 따라간 것이며, 음식 인식 정확도나 실제 모바일 기기에서의 재현 실험, 식단 기록의 영속 저장 완료까지는 확인하지 않았다. 사진에서 찾은 인식 후보가 식단 기록으로 확정되려면 외부 검색어와 앱 내부 이름을 잇는 이름 대응표, 후보 선택 기준, 제공량 확인 단계를 각각 나누어 다뤄야 한다. 그래야 사용자가 편집 화면에서 직접 값을 고칠 수 있는 지점도 분명해진다. 다음 보완에서는 이미지 선택 취소, 일치 후보 없음, 같은 이름의 여러 항목, 이전 응답의 늦은 도착 같은 예외 상황을 먼저 점검하려 한다. 그 과정에서 후보 객체가 라우터와 편집 화면을 거쳐 저장 단계까지 같은 의미로 전달되는지부터 확인할 계획이다.
