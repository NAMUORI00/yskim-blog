영어 학습 앱에서는 한글 문장을 보여 주고 일정 시간이 지나면 영어를 공개하는 흐름을 구성했다. 사용자가 다음 문장으로 이동할 때 기존 타이머가 남아 있으면 다른 문장의 공개 상태를 바꿀 수 있어, 문장 전환과 예약 취소를 함께 다뤘다.


## 구현과 확인 과정


study-english-app의 문장 표시와 타이머를 함께 읽었다. 한글을 먼저 보여 주고 3초 뒤 영어를 드러내는 구성이다. 앞 글의 비동기 요청과 이어서, 문장이 바뀔 때 기존 예약을 취소하고 새 타이머를 만드는 과정을 정리했다.


5d98010 커밋의 문장 처리 코드와 HTML을 살펴봤다. README의 과제 요구사항은 문장 불러오기, 무작위 순서, 3초 공개 지연, 진행률, 다음 문장, 번역 페이지 연결이었다. 현재 코드에는 학습 기록 저장 경로가 없어 타이머와 화면 상태를 중심으로 정리했다.


## 두 언어를 함께 받은 뒤 한쪽만 잠깐 숨기기


[문장 읽기와 화면 상태 처리](https://github.com/NAMUORI00/study-english-app/blob/5d980100d47c7e29cb30ec65d79d9fe0d4674f70/index.js)는 고정된 Gist 리비전의 JSON을 fetch로 읽는다.


각 항목의 en과 ko를 함께 받아 인덱스 배열을 섞고 그 순서로 sentences를 만든다. 각 문제는 미리 준비한 문장 데이터를 사용한다.


displaySentence는 영어, 한글 요소의 textContent를 먼저 채운다. 이어 영어 요소의 opacity를 0으로 바꾸고 번역 버튼을 잠근다. 영어 데이터는 준비된 상태에서 잠시 화면 표시만 숨겨 둔다.


코드 주석 일부에는 한글을 숨긴다는 표현이 있지만 실제 대입 대상은 enTitle이었다. 이 구분은 요구사항의 “한글을 보고 영어를 떠올리기”와도 맞는다.


번역 버튼은 영어가 드러난 뒤 활성화되고, 현재 영어 문장을 encodeURIComponent로 URL에 넣어 Google 번역 페이지를 연다. 번역 확인은 외부 페이지에서 수행하는 흐름이다.

## 다음 문장으로 넘어가기 전에 이전 예약을 지우기


displaySentence는 기존 setTimeout을 clearTimeout으로 취소한 뒤 새 공개 타이머를 만든다. 진행 막대를 갱신하는 setInterval도 clearInterval로 지우고 다시 시작한다. 다음 문장을 누를 때마다 두 종류의 예약이 새 문장을 기준으로 초기화되는 구성이다.


설명용으로 첫 문장을 읽다가 1초 뒤 다음 버튼을 눌렀다고 해 보자. 이전 공개 타이머가 남아 있다면 새 문장은 자체 시작에서 2초가 지난 시점에 드러날 수 있다. 기존 예약을 취소하고 새로 3초를 잡으면 이런 간섭을 줄일 수 있다. 코드의 실행 순서를 설명하기 위해 구성한 시간표다.

그림 2. 다음 버튼이 이전 문장의 공개 예약과 진행 표시를 함께 초기화하는 예제. 출처: displaySentence의 타이머 정리 순서를 바탕으로 직접 구성.


현재 문장뿐 아니라 공개 예약과 진행 표시도 문장이 바뀔 때 갱신되고 있었다. 타이머를 화면 상태에 연결된 자원으로 읽으면 currentIndex 변경과 예약 취소가 함께 필요한 이유를 따라갈 수 있다.


## 타이머 호출과 진행률 계산


진행 막대의 반복 주기는 10ms다. 하지만 콜백 호출 횟수에 일정 값을 더하지 않고 `Date.now`()에서 시작 시각을 빼 실제 경과 시간을 계산한다. 진행률은 경과 시간 ÷ 3000 × 100이며 최대 100으로 제한한다. 반복 호출이 다소 늦어져도 횟수만으로 시간을 세는 방식보다 현재 경과를 반영하기 쉽다.


setTimeout의 3000은 최소 대기 조건이며, 실제 화면 갱신 시점은 실행 큐의 상태에 따라 늦어질 수 있다. [브라우저 타이머 문서](https://developer.mozilla.org/en-US/docs/Web/API/Window/setTimeout)는 실행 환경과 다른 작업 때문에 콜백 실행이 늦어질 수 있다고 설명한다. 배경 탭으로 옮겼다가 돌아오거나 주 스레드가 오래 바쁜 경우도 별도 확인 조건으로 남는다.


공개 타이머와 진행 막대는 독립적인 예약이다. 진행률 100%와 영어 공개를 하나의 상태 변경으로 묶는다면 경과 시간 판단을 공유하는 방식이 대안이 될 수 있다. 현재 구조의 시점 차이는 측정하지 않았다.


## 마지막 문장의 순환 처리


nextSentence는 currentIndex를 (currentIndex + 1) % sentences.length로 바꾼다. 문장이 세 개면 위치는 0→1→2→0으로 돌아간다. 한 바퀴 뒤 다시 섞는 코드는 없으므로 같은 순서를 반복한다.


이 순환에는 배열이 비어 있지 않다는 조건이 필요하다. fetchSentences는 응답 JSON의 배열 형태와 각 항목의 en, ko를 검사하지 않고 displaySentence로 넘긴다. 빈 배열이나 다른 구조의 응답이면 현재 항목에 접근하는 곳에서 문제가 생길 수 있다.


요청 실패는 콘솔에 기록하지만 로딩 표시를 오류 화면으로 바꾸지는 않는다. HTTP 상태 코드 검사도 따로 없다. 실패 메시지와 재시도 동작은 자료를 기다리는 중인지 요청이 끝내 실패했는지 구분하기 위한 보완 항목으로 남았다.


## 현재 학습 위치와 저장된 진도를 구분하기


현재 위치, 문장 순서, 타이머는 모두 페이지 안의 변수다. localStorage나 서버에 진도를 쓰고 복원하는 코드가 없으므로 새로고침 뒤 같은 지점에서 이어 공부하는 기능으로 설명하지 않았다. 여기서의 상태는 현재 화면을 움직이는 데 필요한 메모리상의 값이다.


진도 저장을 추가한다면 currentIndex만 저장해서는 부족할 수 있다. 다음 실행에서 문제 순서를 다시 섞기 때문이다. 문장 ID나 사용한 데이터 리비전, 순서와 함께 무엇을 저장할지 정해야 이전 위치의 의미가 유지된다. 3초 공개 여부를 학습 완료로 취급할지도 별도 선택이다.


빠른 연속 다음 입력, 마지막 문장 이후의 순환, 빈 데이터, 네트워크 실패를 확인 목록으로 정리했다. 이 앱에서 읽을 수 있었던 상태는 문장의 표시 시점과 화면 전환까지다. 대기 시간이 지났다는 사실을 학습 성취로 평가하는 기능은 이 기록의 범위에 포함하지 않았다.


## 작업을 정리하며


타이머도 화면 상태와 함께 수명이 끝나는 자원이라는 점이 이 작업의 핵심이다. 진도 저장을 확장할 때는 현재 번호에 더해 문장 ID와 섞인 순서를 함께 보관해야 이전 학습 위치를 복원할 수 있다. 표시 시간과 학습 완료 기준도 구분해 설계하려 한다.
