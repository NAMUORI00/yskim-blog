영어 학습 앱(`study-english-app`)은 화면에 한글 문장을 먼저 보여 주고 3초 뒤에 영어 문장을 드러낸다. 사용자가 한글만 보고 영어 표현을 먼저 떠올려 보게 하려는 방식이다. 이때 3초가 지나기 전에 다음 문장으로 넘어가도 이전 문장에서 걸어 둔 타이머가 남아 있으면 문제가 생긴다. 새 문장을 보고 있는 도중에 이전 타이머가 실행되어 영어가 일찍 공개될 수 있기 때문이다.


이 글에서는 `study-english-app` 저장소의 `5d98010` 커밋 코드와 HTML을 바탕으로 문장 전환과 타이머 취소 흐름을 확인한다. 설명서(README)에 적힌 과제 요구사항은 문장 불러오기, 무작위 순서 섞기, 3초 공개 지연, 진행률 표시, 다음 문장 이동, 번역 페이지 연결이다. 현재 코드에는 학습 기록을 따로 저장하는 경로가 없으므로, 서버에서 데이터를 받아 온 뒤 화면 상태와 타이머를 어떻게 맞물려 다루는지에 초점을 맞췄다.


## 문장 배열 구성과 영어 투명도 조절


타이머로 표시 시점을 조절하려면 먼저 서버에서 문장 목록을 받아 순서를 섞고 화면에 배치해야 한다. 앱이 시작되면 [문장 읽기와 화면 상태 처리 코드](https://github.com/NAMUORI00/study-english-app/blob/5d980100d47c7e29cb30ec65d79d9fe0d4674f70/index.js)의 `fetchSentences`가 고정된 Gist 리비전의 JSON을 `fetch`로 가져온다. 응답 데이터에는 각 문장의 영어(`en`)와 한글(`ko`)이 한 쌍으로 들어 있다. 코드는 문장 개수만큼 위치 번호인 **인덱스** 배열을 만들어 무작위로 섞은 뒤, 그 순서에 맞춰 `sentences` 배열을 채운다. 문제를 풀 때마다 서버에 새로 요청하지 않고 미리 받아 둔 `sentences` 배열에서 문장을 차례대로 꺼내 쓴다.


화면에 문장을 그리는 `displaySentence`는 영어 요소와 한글 요소의 글자 내용(`textContent`)을 동시에 채운다. 영어 데이터를 3초 뒤에 넣는 대신 두 언어를 화면 요소에 함께 넣어 두고, 영어 요소의 투명도(`opacity`)만 `0`으로 바꾼 뒤 번역 버튼을 잠근다. 코드 주석 일부에는 한글을 숨긴다고 적혀 있지만, 실제로 투명도를 조절하는 대상은 영어 요소인 `enTitle`이다. 이는 한글을 보고 영어를 떠올리게 한다는 과제 요구사항과도 일치한다.


3초가 지나 영어 문장이 화면에 드러나면 잠겨 있던 번역 버튼이 활성화된다. 이 버튼을 누르면 현재 영어 문장을 웹 주소용 문자열(`encodeURIComponent`)로 변환해 URL에 넣고 Google 번역 페이지를 연다. 앱 안에서 번역 결과를 직접 그리지 않고 외부 번역 페이지로 연결한다.

## 문장 전환과 이전 타이머 취소


앞서 숨겨 둔 영어 문장을 3초 뒤에 보여 주려면 타이머가 필요하며, 문장을 중간에 넘길 때는 이전 타이머를 취소해야 한다. 예를 들어 첫 문장을 읽다가 1초 만에 다음 버튼을 눌렀다고 해 보자. 첫 문장의 3초 타이머를 그대로 두면, 두 번째 문장으로 넘어간 지 2초 만에 첫 타이머가 실행되어 새 문장의 영어를 일찍 드러내게 된다.


사용자가 한 문장에 머무르는 동안에는 두 가지 타이머가 동시에 돌아간다. 3초 뒤 영어 문장을 한 번 보여 주는 공개 타이머(`setTimeout`)와 일정 간격으로 흐른 시간을 진행 막대에 표시하는 반복 타이머(`setInterval`)다. 사용자가 3초가 되기 전에 다음 문장으로 넘어가면 이전 문장에서 시작한 두 예약은 더 이상 유효하지 않다.


이전 예약이 새 문장에 끼어들지 않도록 `displaySentence`는 기존 `setTimeout`을 `clearTimeout`으로 취소하고 새 공개 타이머를 등록한다. 진행 막대를 갱신하는 `setInterval` 역시 `clearInterval`로 지운 뒤 처음부터 다시 시작한다.


![사용자가 1초 뒤 다음 버튼을 누르면 문장 화면이 공개 타이머와 진행 막대의 이전 예약을 취소하고 새 3초 예약과 진행률을 시작하는 시퀀스 다이어그램](/images/notion/tech-13-06/image-2.png)


그림 2. 다음 버튼이 이전 문장의 공개 예약과 진행 표시를 함께 초기화하는 예제. 출처: displaySentence의 타이머 정리 순서를 바탕으로 직접 구성.


문장이 바뀔 때는 화면의 글자와 현재 위치(`currentIndex`)만 바뀌는 것이 아니다. 그 문장에 걸려 있던 공개 예약과 진행 표시도 화면 상태에 속한 자원이므로, 문장을 전환할 때 이전 예약을 함께 정리해야 화면과 타이머가 어긋나지 않는다.


## 경과 시간으로 계산하는 진행률과 타이머 지연


새 문장의 타이머를 시작한 뒤에는 3초가 흐르는 동안 진행 막대를 얼마나 채울지 계산해야 한다. 진행 막대를 갱신하는 `setInterval`의 호출 주기는 `10ms`(0.01초)로 설정되어 있다. 예약해 둔 함수인 **콜백**이 실행될 때마다 고정된 수치를 더하지 않고, 현재 시각(`Date.now()`)에서 타이머 시작 시각을 빼서 실제 경과 시간을 구한다. 진행률은 `경과 시간 ÷ 3000 × 100`으로 계산하며 최댓값은 `100`으로 제한한다.


![시작 시각을 기록한 뒤 10ms마다 Date.now()와의 차이로 진행률을 계산해 진행 막대를 갱신하는 경로와 3000ms 대기 뒤 영어를 공개하는 경로를 나란히 나타낸 구조도](/images/notion/tech-13-06/image-3.png)


그림 3. 시작 시각과의 차이로 진행 막대를 갱신하는 반복 타이머와 독립된 영어 공개 타이머의 동작 구조.


호출 횟수를 세지 않고 시각 차이로 계산하는 이유는 브라우저 타이머의 동작 방식과 관련이 있다. `setTimeout`에 넘긴 `3000`이나 `setInterval`의 `10`은 정확한 실행 시각을 보장하는 값이 아니라 최소 대기 시간이다. [MDN의 브라우저 타이머 문서](https://developer.mozilla.org/en-US/docs/Web/API/Window/setTimeout)에서도 설명하듯, 대기열인 실행 큐의 상태나 브라우저 주 스레드의 다른 작업 때문에 콜백 실행은 예정보다 늦어질 수 있다. 호출 횟수만 세면 실행이 지연된 만큼 진행 막대도 늦게 차오른다. 반면 `Date.now()`를 기준으로 경과 시간을 계산하면 호출이 밀리더라도 다음 콜백에서 실제 흐른 시간을 반영할 수 있다. 사용자가 브라우저를 다른 탭 뒤의 배경 탭으로 두었다가 돌아오거나 주 스레드가 오래 바쁜 상황에서 화면이 어떻게 보이는지는 별도로 확인해야 할 조건이다.


또한 현재 코드에서 영어 공개용 `setTimeout`과 진행 막대용 `setInterval`은 서로 독립된 예약으로 돌아간다. 진행률이 100%에 도달하는 시점과 영어가 공개되는 시점을 하나로 맞추려면, 경과 시간 판단을 한곳에서 공유하는 방식도 대안이 될 수 있다. 현재 코드에서 두 시점이 실제로 얼마나 차이 나는지는 따로 측정하지 않았다.


## 마지막 문장의 순환 처리와 예외 조건


한 문장의 표시와 진행률 계산이 끝나면, 다음 버튼을 눌렀을 때 몇 번째 문장으로 이동할지와 데이터가 비정상일 때의 동작을 확인해야 한다. 예를 들어 전체 문장이 3개라면 위치 번호는 `0 → 1 → 2` 순서로 커지다가 마지막 문장 뒤에는 다시 첫 번호인 `0`으로 돌아가야 한다. 다음 버튼을 누를 때 호출되는 `nextSentence`는 나머지 연산(`%`)으로 현재 인덱스를 `(currentIndex + 1) % sentences.length`로 갱신한다. 마지막 문장을 본 뒤 배열을 다시 섞는 코드는 없어서, 처음에 섞어 둔 순서가 그대로 반복된다.


![섞인 문장 배열에서 인덱스 0, 1, 2가 다음 문장 이동에 따라 진행되고 마지막 인덱스 2에서 나머지 연산으로 다시 인덱스 0으로 돌아가는 순환도](/images/notion/tech-13-06/image-4.png)


그림 4. 문장이 3개일 때 나머지 연산으로 마지막 문장 뒤 첫 인덱스로 돌아가는 순환 흐름.


이 나머지 연산이 정상적으로 동작하려면 `sentences` 배열이 비어 있지 않아야 한다. 하지만 현재 `fetchSentences`는 응답 JSON이 배열인지와 각 항목에 `en`, `ko` 속성이 있는지 검사하지 않고 `displaySentence`를 호출한다. 만약 빈 배열이나 예상과 다른 구조의 응답이 오면 현재 인덱스의 문장 속성에 접근하는 단계에서 오류가 날 수 있다.


네트워크 요청이 실패했을 때의 화면 처리도 비어 있다. 요청 중 오류가 발생하면 개발자 도구의 콘솔에 로그만 남길 뿐, HTTP 상태 코드를 검사하거나 화면의 로딩 표시를 오류 안내로 바꾸지는 않는다. 사용자가 데이터를 기다리는 중인지 요청이 실패했는지 구분하려면 실패 메시지와 재시도 동작을 보완해야 한다.


## 화면 상태와 학습 진도 저장의 구분


앞 절들에서 다룬 현재 위치(`currentIndex`), 섞인 문장 배열(`sentences`), 두 종류의 타이머는 모두 페이지 메모리 안에만 머무는 변수다. 브라우저 저장소(`localStorage`)나 서버에 상태를 기록하고 복원하는 코드가 없으므로, 페이지를 새로고침하면 처음부터 다시 시작한다. 이 앱에서 다루는 상태는 학습 이력이 아니라 현재 화면을 전환하고 표시 시점을 제어하기 위한 일시적인 값이다.


새로고침 뒤에도 이어서 학습하는 진도 저장 기능을 추가한다면 `currentIndex` 하나만 저장해서는 이전 위치를 복원할 수 없다. 앱을 다시 실행할 때마다 문장 순서를 새로 섞기 때문에 같은 번호라도 다른 문장을 가리키게 된다. 이전 학습 위치를 그대로 이어 가려면 사용한 데이터 리비전이나 문장 ID, 섞인 순서 배열을 함께 보관해야 한다. 또한 3초가 지나 영어 문장이 표시된 것을 학습 완료로 볼지도 별도 선택이며, 표시 시간과 학습 완료 기준은 구분해 설계하려 한다.


## 결론


`study-english-app`의 `5d98010` 커밋 코드에서는 두 언어 문장을 함께 받아 영어 투명도만 조절하고, 문장을 넘길 때 이전 타이머를 취소해 간섭을 막는다. 진행 막대는 타이머 지연에 대비해 `Date.now()` 기준 경과 시간으로 계산하며, 문장 위치는 나머지 연산으로 순환한다. 반면 빈 응답이나 네트워크 오류 처리, 배경 탭이나 주 스레드 지연 시의 실제 화면 동작, 공개 타이머와 진행 막대 사이의 시점 차이는 코드에 없거나 이번에 측정하지 않았다.
