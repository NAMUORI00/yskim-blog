프로필 페이지와 포털 수업 코드에서는 외부 기능의 결과를 화면과 저장 데이터에 연결하는 작업을 다뤘다. orim과 class-potalservice2023을 각각의 사례로 두고, 요청을 맡기는 위치와 반환값이 상태에 반영되는 지점을 정리했다.


## 구현과 확인 과정


orim의 프로필, 음악 페이지와 class-potalservice2023의 Java 수업 코드를 읽었다. 두 저장소는 독립된 사례지만 외부 기능에 요청을 보내고 반환 결과를 화면이나 객체 상태에 반영하는 흐름을 함께 비교할 수 있었다.


기준 커밋은 orim의 e305a24와 class-potalservice2023의 c3ea7a4다. 실제 호출을 따라 화면과 컨트롤러가 맡기는 작업, 돌아오는 결과, 그 결과가 반영되는 위치를 정리했다.


## orim: 프로필은 HTML에, 재생 상태는 플레이어에


[orim의 프로필 화면 구성](https://github.com/NAMUORI00/orim/blob/e305a2404e552118533b210253c0455554eb8973/index.html)에는 프로필 내용과 스타일, 플레이어 코드가 함께 들어 있다.


프로필 화면은 저장된 데이터로 Discord와 비슷한 표현을 구성한다. 확인한 파일에서 프로필 API를 주기적으로 조회하는 경로는 찾지 못했다.


음악은 YouTube IFrame Player API에 맡긴다. 스크립트 준비 콜백에서 플레이어를 만들고, 플레이어의 onReady에서 음량을 설정하고 재생목록을 불러온다. 이후 PLAYING, PAUSED, ENDED 이벤트에 따라 버튼과 진행 표시를 바꾼다.


[YouTube 공식 문서](https://developers.google.com/youtube/iframe_api_reference)는 API 코드 준비와 플레이어 준비, 재생 상태 변경을 구분한다.


재생 요청 이후에는 플레이어의 상태 이벤트와 오류 응답이 이어진다. 영상 부재나 임베드 제한 때문에 재생하지 못하는 경우도 있다. 현재 코드는 오류 코드별 안내와 재생목록을 불러오지 못했을 때 외부 페이지로 이동하는 링크를 제공한다.

## 재생 화면의 시각 효과


BackgroundManager는 재생 이벤트를 받으면 100ms 간격으로 막대 높이를 바꾼다. 높이는 현재 시각에 대한 사인 함수로 계산한다. 실제 오디오 샘플을 읽거나 주파수 분석을 하는 코드는 이 경로에 없다. 따라서 스펙트럼처럼 보이는 막대는 재생 상태에 반응하는 시각 효과로 읽었다.


진행 막대는 플레이어의 현재 시간과 전체 길이로 비율을 계산한다. 장식용 막대와 같은 화면에서 움직여도 입력값이 다르다. 각 표시를 만드는 값을 따라가며 시각 효과와 재생 위치의 역할을 나누어 읽었다.


곡 제목은 우선 Track 번호로 표시한 뒤 oEmbed로 보완한다. 제목 수집에 실패하면 해당 영상을 잠깐 재생해 정보를 읽고 정지하는 대체 경로도 있다. 이 처리는 메타데이터 수집이 재생 상태를 건드릴 수 있음을 뜻한다. 원래 선택한 곡을 보존하는지와 사용자 조작과 충돌하지 않는지는 다음 확인 대상으로 남겼다.


## 포털 수업 코드: SQL과 연결 관리의 역할 나누기


class-potalservice2023에는 userdao부터 userdao-6까지 여러 단계의 코드가 있다. 폴더 번호만으로 실행 환경의 완성도를 판단하기보다 같은 작업이 어떻게 표현되는지 비교했다. 초기 UserDao는 연결 생성, PreparedStatement, 결과 매핑, 자원 해제를 직접 적는다.


[userdao-6의 UserDao](https://github.com/NAMUORI00/class-potalservice2023/blob/c3ea7a4690ea7c045e862129f28e80a3ba4df63c/userdao-6/src/main/java/kr/ac/jejunu/user/UserDao.java)는 JdbcTemplate을 생성자로 받는다.


SQL과 매개변수, ResultSet에서 User로 옮기는 부분은 남고 반복적인 JDBC 처리는 템플릿에 맡긴다. [Spring JDBC 문서](https://docs.spring.io/spring-framework/reference/data-access/jdbc/core.html)도 이런 역할 분담을 설명한다.

그림 2. 웹 요청의 ID가 SQL 매개변수와 조회 결과 매핑으로 이어지는 과정. 출처: userdao-6의 UserController와 UserDao를 바탕으로 직접 구성.


후기 조회 SQL에는 where id = ?가 있고 ID를 값으로 전달한다. 초기 예제에는 where ?만 남아 있어, 자리 표시자를 썼다는 사실과 ID 비교 조건을 올바르게 작성했다는 사실도 구분해야 했다. 조회 결과가 없는 경우 초기 코드가 바로 다음 행을 가정하는 것과 후기 코드가 [rs.next](http://rs.next/)()를 검사하는 차이도 보였다.


삽입은 GeneratedKeyHolder에서 생성된 키를 꺼내 User의 ID에 넣는다. 객체에 ID가 생기는 시점과 삽입 요청을 시작한 시점을 구분하면 이후 재조회 예제를 이해하기 쉽다. 저장소에는 삽입 후 조회값을 비교하는 테스트 코드가 있다. 이번 확인 범위는 그 코드의 검증 흐름까지다.


## 외부 기능별 결과 확인


orim은 플레이어의 상태 이벤트를, 포털 코드는 DAO가 반환한 행과 오류를 다음 상태의 근거로 사용한다. 외부 작업의 결과를 반영한다는 흐름은 비슷하지만 재생 시작과 데이터 조회 완료는 각각의 결과로 확인할 단계다.


포털의 UserController는 Controller이고 /user에 text/html을 지정한다. 엔티티를 반환한다는 이유만으로 JSON REST API라고 소개하지 않았다. 파일 업로드 역시 서버의 웹 경로에 쓰는 예제이므로, 파일이 저장된 위치와 브라우저에서 접근하는 URL의 매핑을 별도로 확인해야 한다.


orim의 제목 수집이 재생 상태에 미치는 영향과 DAO의 빈 조회 결과 처리는 후속 확인 예제로 남겼다. 두 저장소 모두 정상 결과가 돌아오지 않는 경우를 읽으면 화면과 데이터 상태의 경계를 더 구체적으로 정리할 수 있다.


## 작업을 정리하며


화면에 보이는 값의 출처를 따라가면 정적 소개, 외부 조회, 데이터베이스 저장의 역할이 분명해진다. 다음 작업에서도 값이 언제 만들어지고 어디에 남는지부터 표시해 두려 한다. 이 기준이 있으면 화면 표현을 바꾸면서도 데이터의 의미를 유지하기 쉽다.
