웹 화면에서 음악 재생 버튼을 눌렀다고 해서 곧바로 음원이 재생되는 것은 아니다. 데이터베이스에 데이터를 넣는 삽입 메서드를 호출해도, 호출 직후부터 자바 객체에 식별자(ID)가 들어 있지는 않다. 이처럼 외부 기능(API)이나 라이브러리에 작업을 맡기는 코드를 읽을 때는 요청을 보낸 시점과 실제 상태가 바뀌는 시점을 구분해야 한다.


프로필과 음악 재생 페이지인 `orim`(커밋 `e305a24`)과 자바 포털 서비스 수업 코드인 `class-potalservice2023`(커밋 `c3ea7a4`)을 나란히 읽으며 이 경계를 따라가 보았다. 두 저장소는 서로 다른 프로젝트지만, 외부 도구에 작업을 맡긴 뒤 돌아온 상태 알림(이벤트)이나 반환값을 받아 화면과 객체 상태를 갱신한다는 점이 닮아 있다.


## 정적 프로필과 플레이어 상태 이벤트


먼저 웹 브라우저에서 동작하는 `orim`을 보면 화면에 고정된 프로필 정보와 외부 플레이어의 신호로 바뀌는 음악 재생 영역이 한 파일에 모여 있다. [orim의 프로필 화면 구성](https://github.com/NAMUORI00/orim/blob/e305a2404e552118533b210253c0455554eb8973/index.html) 파일 하나에 프로필 내용과 화면 스타일, 음악 플레이어 코드가 함께 들어 있다. 프로필 영역은 HTML에 미리 적어 둔 데이터로 메신저 서비스인 디스코드(Discord)와 비슷한 화면을 그린다. 확인한 파일 안에서는 외부 프로필 API를 주기적으로 조회하는 경로가 없었다.


반면 음악 재생은 웹 페이지에 유튜브 영상을 끼워 넣어 제어하는 **YouTube IFrame Player API**에 맡긴다. [YouTube 공식 문서](https://developers.google.com/youtube/iframe_api_reference)는 스크립트 준비와 플레이어 객체 준비, 재생 상태 변경을 별도 단계로 구분하는데, `orim` 코드도 이 순서를 따른다. 스크립트 준비가 끝났을 때 자동 실행되는 콜백 함수가 플레이어 객체를 만들고, 준비 완료를 알리는 `onReady` 이벤트에서 음량을 설정한 뒤 재생목록을 불러온다.


사용자가 재생이나 정지 버튼을 누른 뒤에도 화면 표시는 버튼 클릭만으로 바로 바뀌지 않는다. 플레이어가 `PLAYING`, `PAUSED`, `ENDED` 같은 상태 이벤트를 내보내야 비로소 버튼 모양과 진행 시간 표시가 갱신된다. 만약 영상이 없거나 외부 페이지 삽입(임베드)이 제한된 영상이라면 상태 이벤트 대신 오류 응답이 돌아온다. 현재 코드는 오류 코드별 안내 문구를 띄우고, 재생목록을 불러오지 못했을 때는 외부 페이지로 이동하는 링크를 보여 준다.

## 화면 시각 효과와 곡 제목 조회


재생 화면에서는 음악이 나오는 동안 배경 막대와 재생 진행 막대가 함께 움직이지만, 각 막대를 만드는 입력값을 따라가 보면 역할이 전혀 다르다.


배경 효과를 맡은 `BackgroundManager`는 페이지 내부의 이벤트 전달 통로인 `EventBus`로 재생 이벤트를 받으면 100ms 간격으로 막대 높이를 바꾼다. 이때 막대 높이는 현재 시각에 대한 사인(sine) 함수로 계산하며, 실제 오디오 샘플을 읽거나 주파수를 분석하는 코드는 이 경로에 없다. 음향 분석기(스펙트럼 분석기)처럼 보이는 배경 막대는 실제 오디오 파형이 아니라 재생 여부에만 반응하는 시각 효과다.


반면 재생 진행 막대는 플레이어에서 현재 재생 시간과 전체 길이를 받아 비율을 계산한다. 같은 화면에서 나란히 움직이는 막대라도 어떤 값을 입력으로 받는지에 따라 장식용 시각 효과와 실제 재생 위치 표시로 역할이 나뉜다.


![현재 시간과 전체 길이로 비율을 계산하는 재생 진행 막대와, 재생 상태와 현재 시각의 100ms 주기 사인 함수로 높이를 바꾸는 배경 스펙트럼 막대의 비교도](/images/notion/tech-13-07/image-2.png)


그림 2. orim 재생 화면에서 진행 막대와 배경 스펙트럼 막대가 서로 다른 입력값으로 갱신되는 구조 비교.


곡 제목을 표시하는 경로에서도 외부 정보 조회와 플레이어 상태가 서로 맞물린다. 화면에는 우선 트랙(`Track`) 번호를 표시해 두고, 외부 콘텐츠의 기본 정보를 가져오는 **oEmbed** 규격으로 실제 제목을 조회해 채운다. 만약 oEmbed로 제목을 가져오지 못하면 해당 영상을 잠깐 재생해 플레이어에서 정보를 읽은 뒤 바로 정지하는 대체 경로가 동작한다. 곡의 부가 정보(메타데이터)를 수집하는 작업이 실제 플레이어의 재생 상태를 직접 건드리는 방식이다. 이 대체 경로가 원래 선택했던 곡을 그대로 유지하는지, 그리고 사용자의 재생 조작과 충돌하지 않는지는 다음 확인 대상으로 남겨 두었다.


## UserDao와 JdbcTemplate의 역할 분담


브라우저 화면이 외부 플레이어에 음악 재생을 맡긴다면, 서버 쪽 자바 코드인 `class-potalservice2023` 저장소는 데이터베이스에 조회와 저장을 맡긴다. 이 저장소에는 데이터베이스 접근 객체인 **DAO**(Data Access Object)를 단계별로 고쳐 나간 `userdao`부터 `userdao-6`까지의 폴더가 있다. 폴더 번호만으로 완성도를 단정하기보다 같은 데이터베이스 작업이 단계마다 어떻게 나뉘어 표현되는지 비교했다.


초기 `UserDao`는 데이터베이스 연결 생성과 SQL 문을 담는 `PreparedStatement` 준비, 결과 옮기기(매핑), 자원 해제를 한 클래스 안에 모두 적는다. 반면 [userdao-6의 UserDao](https://github.com/NAMUORI00/class-potalservice2023/blob/c3ea7a4690ea7c045e862129f28e80a3ba4df63c/userdao-6/src/main/java/kr/ac/jejunu/user/UserDao.java)는 생성자를 통해 스프링의 **JdbcTemplate**을 주입받는다. 반복되는 연결 관리와 자원 해제는 템플릿에 맡기고, `UserDao` 안에는 실행할 SQL과 매개변수, 조회 결과(`ResultSet`)를 `User` 객체로 옮기는 코드만 남긴다. 이는 [Spring JDBC 문서](https://docs.spring.io/spring-framework/reference/data-access/jdbc/core.html)가 설명하는 역할 분담과 같은 방식이다.

## SQL 결과 반영과 웹 응답 형태


반복 처리를 템플릿에 넘겼더라도 SQL 조건을 정확히 적고 반환된 결과를 객체와 웹 응답에 반영하는 일은 여전히 DAO와 컨트롤러의 몫이다. 웹 요청을 받는 `UserController`부터 `UserDao`까지 따라가며 초기 예제와 후기 예제를 비교해 보면 쿼리 작성과 결과 확인에서 두 가지 차이가 드러난다.


![사용자 조회 요청이 UserController, UserDao, JdbcTemplate을 거쳐 userinfo 테이블을 조회하고, 반환된 결과 행이 User 객체로 매핑되어 컨트롤러로 돌아오는 흐름도](/images/notion/tech-13-07/image-4.png)


그림 4. 웹 요청의 ID가 SQL 매개변수와 조회 결과 매핑으로 이어지는 과정. 출처: userdao-6의 UserController와 UserDao를 바탕으로 직접 구성.


첫째는 SQL의 조건절로, `userdao-6`의 조회 SQL에는 `where id = ?`가 들어가고 매개변수로 ID 값을 전달한다. 반면 초기 예제에는 `where ?`만 적혀 있어서, 매개변수 자리 표시자(`?`)를 썼다는 사실과 ID 비교 조건을 올바르게 작성했다는 사실을 구분해서 봐야 했다. 둘째는 조회 결과가 비어 있을 때의 처리로, 초기 코드는 결과 행이 무조건 있다고 가정하고 바로 값을 읽는다. 반면 후기 코드는 `rs.next()`를 호출해 다음 결과 행이 실제로 존재하는지부터 먼저 검사한다.


새 데이터를 추가하는 삽입(insert) 과정에서는 데이터베이스가 생성한 키를 보관하는 `GeneratedKeyHolder`에서 값을 꺼내 `User` 객체의 ID 필드에 넣는다. 삽입 요청을 시작한 시점과 `User` 객체에 실제로 ID가 채워지는 시점을 구분해 두면, 삽입 직후 같은 ID로 데이터를 다시 조회하는 예제를 이해하기 쉽다. 저장소에는 데이터를 넣은 뒤 다시 조회해 값을 비교하는 테스트 코드가 있으며, 이번에는 그 테스트 코드의 검증 흐름까지 확인했다.


포털 수업 코드에서 조회 결과를 웹 브라우저로 돌려주는 부분도 실제 응답 형태에 맞춰 구분했다. `UserController`는 일반 스프링 `Controller`로 선언되어 있고 `/user` 경로에 웹 문서 형식인 `text/html` 응답을 지정한다. 코드에서 데이터 객체(엔티티 객체)를 반환한다고 해서 곧바로 JSON을 주고받는 REST API라고 단정할 수 없다. 파일 업로드 예제 역시 서버의 웹 경로에 파일을 직접 기록하는 방식이므로, 파일이 저장되는 물리적 위치와 브라우저에서 접근하는 URL 경로가 어떻게 연결되는지 따로 확인해야 한다.


## 결론


두 저장소를 나란히 비교한 결과, 외부 기능에 작업을 맡긴 코드는 응답이 돌아온 뒤에야 다음 상태를 결정한다는 공통된 흐름을 확인했다. `orim`은 플레이어가 내보내는 상태 이벤트를, 포털 수업 코드는 DAO가 반환한 결과 행과 생성된 키, 오류를 다음 상태의 근거로 삼는다. 재생을 요청한 시점과 실제 재생이 시작된 시점이 다르듯, 쿼리를 호출한 시점과 조회 결과가 객체에 반영된 시점도 각각의 반환값으로 확인해야 한다. 화면에 보이는 값의 출처를 따라가며 값이 언제 만들어지고 어디에 남는지 구분해 두면 각 영역의 역할이 분명해진다. 고정된 정적 소개와 외부 조회, 데이터베이스 저장의 경계가 뚜렷해져 화면 표현을 바꾸더라도 데이터의 의미를 유지하기 쉽다.


정상적인 결과가 돌아오지 않는 예외 경로는 두 저장소 모두 후속 확인 과제로 남겼다. `orim`에서는 제목 조회가 실패했을 때 영상을 잠깐 재생하는 대체 경로가 기존 재생 상태나 사용자 조작에 미치는 영향을 확인해야 한다. 포털 수업 코드에서는 DAO가 빈 조회 결과를 처리하는 방식과 파일 업로드의 물리적 저장 위치가 브라우저 URL 경로와 연결되는 과정을 이어서 확인할 예정이다.
