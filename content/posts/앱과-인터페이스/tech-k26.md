웹 화면의 입력창에 할 일을 적고 목록에 추가했는데, 브라우저를 새로고침하자마자 방금 입력한 항목이 사라지는 일이 있다. 화면에 값이 보이는 것과 그 값이 실제로 저장된 것은 서로 다른 일이기 때문이다. 사용자가 입력한 값을 새로고침이나 탭 종료 뒤에도 남기려면, 메모리에 있던 값을 브라우저 저장소나 서버에 따로 기록하고 화면을 다시 열 때 불러와야 한다. 이 글에서는 데이터가 놓이는 위치에 따라 값이 어디까지 유지되는지 비교하고, 저장과 복원이 제대로 되었는지 확인하는 방법을 다룬다.


## 메모리의 화면 상태


새로고침했을 때 입력한 값이 왜 사라지는지 보려면, 먼저 브라우저가 화면의 값을 어디에 들고 있는지 확인해야 한다. 아래 코드는 할 일 항목을 배열 변수에 추가하고 화면 목록을 다시 그리는 예제다.


```javascript
let todos = [];

function addTodo(text) {
  todos.push({ text, done: false });
  renderList();
}
```


이 코드의 `todos` 배열처럼 브라우저가 JavaScript를 실행하는 동안(런타임) 메모리에 들고 있는 값을 **화면 상태**(UI state)라고 부른다. 변수에 담긴 배열뿐 아니라 화면 구조를 나타내는 DOM(문서 객체 모델)에 추가된 요소, 입력창에 적힌 현재 문자열이 모두 여기에 해당한다.


`addTodo("우유 사기")`를 호출하면 `renderList()`가 실행되어 화면에 새 항목이 나타난다. 하지만 `todos` 배열은 메모리에만 있으므로, 브라우저 탭을 닫거나 새로고침하면 JavaScript 실행 환경(실행 컨텍스트)이 초기화되면서 빈 배열로 돌아간다. 화면에 이미 그려진 값이라도 별도의 저장소에 기록하지 않으면 실행 환경이 끝날 때 함께 사라진다.


그렇다고 해서 메모리에 있는 모든 화면 상태를 계속 보존해야 하는 것은 아니다. 화면에 띄운 모달 창이 열려 있는지, 드롭다운 메뉴가 펼쳐져 있는지, 스크롤이 어디까지 내려갔는지 나타내는 값도 화면 상태에 속한다. 하지만 이런 값은 새로고침 뒤에 굳이 원래 상태대로 되돌리지 않아도 되는 경우가 많다. 반면 사용자가 직접 입력한 데이터는 사라지면 곤란하므로 메모리 바깥에 따로 저장하는 경로가 필요하다.


## 데이터 저장 위치와 유지 범위


메모리 바깥으로 값을 내보내 새로고침 뒤에도 남기려면, 브라우저 내부 저장소나 외부 서버에 데이터를 기록해야 한다. 웹 애플리케이션에서 주로 쓰는 저장 경로는 서버 데이터베이스와 브라우저 내부의 두 저장소로 나뉜다.


먼저 `fetch('/api/todos', { method: 'POST', body: ... })`처럼 네트워크 요청으로 데이터를 보내는 서버 전송 방식이 있다. 서버가 받은 데이터를 데이터베이스에 기록해 두면, 다른 기기나 다른 브라우저에서 접속해도 같은 데이터를 읽을 수 있다. 대신 서버와 데이터를 주고받는 규칙인 API의 저장 조건(저장 계약)과 네트워크 오류, 서버 장애 처리까지 함께 확인해야 한다.


브라우저 내부에 저장할 때는 `localStorage.setItem('todos', JSON.stringify(todos))`를 호출해 문자열 형태로 기록한다. 이렇게 브라우저 로컬 저장소인 **localStorage**에 넣은 값은 접속한 사이트 주소가 같은 출처(origin)라면 탭이나 브라우저를 닫았다가 다시 열어도 유지된다. 다만 브라우저마다 정해진 용량 제한이나 사용자 설정 때문에 쓰기가 실패할 수 있어 예외 처리가 필요하다.


브라우저 안의 또 다른 저장소인 **sessionStorage**는 데이터를 읽고 쓰는 방식이 `localStorage`와 같다. 하지만 같은 탭 안에서만 값이 유지되고 탭을 닫으면 사라지므로, 일시적인 화면 메모리와 탭 종료 뒤에도 남는 영속 저장소 사이의 중간 지점에 해당한다.


이처럼 데이터가 놓인 위치에 따라 새로고침이나 탭 종료, 다른 기기에서 조회할 때 값이 유지되는 범위가 달라진다. 메모리에만 있는 화면 상태는 새로고침만 해도 초기화되지만, 브라우저 저장소나 서버 데이터베이스에 기록된 값은 새로고침 뒤에도 다시 읽어 올 수 있다.

## 서버 저장과 화면 갱신의 간격


저장소 가운데 서버 데이터베이스를 쓸 때는 화면이 바뀌는 시점과 실제 저장이 끝나는 시점이 다를 수 있다. 할 일 목록에서 항목을 추가하면 생성(Create), 목록을 불러오면 조회(Read) 요청에 대응한다. 완료 체크박스를 켜고 끄면(토글) 수정(Update), 항목을 지우면 삭제(Delete) 요청을 서버에 보낸다. 서버 쪽 저장은 보통 이 네 가지 데이터 처리의 기본 단위인 **CRUD**(Create, Read, Update, Delete) 연산으로 이루어진다.


이때 사용자가 화면을 조작하는 시점과 서버로 저장 요청이 나가는 시점은 앱의 설계에 따라 달라진다. 입력한 초안으로 화면 목록을 먼저 바꾸고, 별도의 저장 버튼을 눌러야 서버로 `POST` 요청을 보내는 앱이 있다. 이런 앱에서는 저장 버튼을 누르기 전까지 초안이 화면 상태에만 머물며, 서버에 저장된 뒤에야 새로고침할 때 `GET` 요청으로 목록을 다시 불러올 수 있다. 따라서 저장 버튼을 누르기 전까지는 화면에 보이는 상태와 서버에 기록된 상태가 의도적으로 서로 다르다.


![사용자 입력 초안이 화면 목록을 바로 갱신하는 경로와 저장 버튼을 거쳐 할 일 DB에 POST 처리된 뒤 새로고침 시 GET 목록으로 복원되는 흐름도](/images/notion/tech-k26/image-2.png)


그림 2. 화면 상태에서 서버 저장과 새로고침 복원까지 이어지는 데이터 흐름 예제(출처: 본문 예제를 바탕으로 직접 작성).


반대로 체크박스를 누르자마자 곧바로 서버에 수정 요청을 보내는 앱도 있다. 이 방식은 조작할 때마다 저장을 시도하지만, 서버 응답이 돌아오기 전까지는 두 상태가 다를 수 있다. 특히 화면 표시를 먼저 바꾼 뒤 네트워크 오류가 발생하면, 화면은 바뀌었는데 서버에는 반영되지 않는 불일치가 생길 수 있다.


그래서 화면 표시가 바뀐 것만으로는 서버 저장까지 끝났는지 알 수 없다. 실제 저장 여부를 확인하려면 브라우저에서 통신 내역을 보여 주는 개발자 도구의 Network 탭에서 요청과 응답을 대조해 보아야 한다. 서버 응답을 숫자로 나타낸 HTTP 상태 코드 가운데 `202`(Accepted)는 저장 완료가 아니라 요청 접수만 알리는 응답이다. 따라서 상태 코드뿐 아니라 응답 본문과 서버 API의 규칙(계약)이 정한 저장 완료 조건까지 함께 확인해야 한다.


## 저장과 복원 경로의 구분


서버나 브라우저 저장소를 쓰더라도 새로고침을 했을 때 방금 입력한 값이 사라질 수 있다. 이때는 저장소에 값을 쓰지 못한 것인지, 아니면 저장된 값을 다시 읽어 오는 복원 과정이 실패한 것인지 나누어 보아야 한다. 새로고침은 메모리의 화면 상태를 비우고 복원 경로를 처음부터 실행해 보는 출발점이 된다. 따라서 점검 과정은 사용자 입력 뒤 저장 응답을 확인하는 단계와, 새로고침한 새 화면에서 값을 읽어 복원 결과를 대조하는 두 단계로 나뉜다.


![사용자 입력 후 저장 응답 확인 단계와 새 화면에서 읽어 복원 결과를 대조하는 단계를 나눈 점검 흐름도](/images/notion/tech-k26/image-3.png)


그림 3. 저장 완료 확인과 새로고침 뒤의 복원 확인을 구분한 점검 흐름 예제.


첫 단계에서는 사용자가 값을 바꾼 직후 저장소에 값이 제대로 기록되었는지 확인한다. `localStorage`나 `sessionStorage`를 쓸 때는 개발자 도구의 Application 탭에서 저장된 이름(키)과 값을 직접 볼 수 있다. 서버에 저장하는 경우라면 앞서 본 Network 탭에서 쓰기 요청과 응답을 확인한다. 저장소에 실제 값이 들어 있는데도 두 번째 단계인 새로고침 뒤에 화면이 비어 있다면, 쓰기 실패가 아니라 읽기 응답이나 화면 복원 단계의 문제다.


다만 새로고침을 해 보는 것만으로는 모든 저장소의 보관 범위를 구분하기 어렵다. `sessionStorage`의 값도 새로고침에서는 그대로 유지되고 탭을 닫아야 사라진다. 그래서 새로고침 한 번만 해서는 데이터가 `sessionStorage`에 있는지 `localStorage`에 있는지 구별되지 않는다. 의도한 보관 범위를 검증하려면 탭을 닫은 뒤 새 탭(새 세션)에서 열거나 다른 기기에서 읽는 과정까지 구분해 확인해야 한다. 또한 브라우저 저장소는 사용자의 삭제나 브라우저 정책의 영향을 받으므로 영구적인 백업 용도로 쓸 수 없다.


## 결론


화면에 보이는 값은 브라우저 메모리의 일시적인 화면 상태일 수 있으므로, 데이터가 어느 위치에 기록되는지와 언제 복원되는지를 나누어 따져 보아야 한다. 입력한 값을 새로고침이나 탭 종료 뒤에도 남기려면 `sessionStorage`, `localStorage`, 서버 데이터베이스 가운데 유지 범위에 맞는 저장소에 기록해야 한다. 값이 사라지는 문제가 생겼을 때는 개발자 도구와 새로고침을 활용해 저장소에 값을 쓰는 단계와 다시 읽어 복원하는 단계를 구분해 확인해야 한다.


이 글에서는 브라우저의 기본 저장소와 네트워크 요청을 기준으로 화면 상태의 저장 위치와 복원 확인 방법을 다루었다. 실제 웹 화면(프런트엔드) 개발에서는 React의 `useState`나 Vue의 반응형 객체로 화면 상태를 다루면서 서버 상태와 값을 맞추는 동기화 과정을 거친다. 하지만 각 개발 도구(프레임워크)에서 화면 상태와 서버 API 호출을 어떻게 분리하는지는 아직 확인하지 않았다. 각 개발 도구(프레임워크)에서 화면 상태와 서버 API 호출을 분리하는 구조와 오프라인 저장 실패 후의 재시도, 로컬과 서버 데이터의 충돌 해결 방식은 이어지는 글에서 다룬다.
