JavaScript 코드에서 타이머 함수인 `setTimeout`의 지연 시간을 `0`으로 적으면, 그 안에 넣은 함수가 바로 실행될 것처럼 보인다. 하지만 아래 코드를 실행하면 `'B'`는 `'A'` 바로 뒤가 아니라 `'C'`가 출력된 뒤에 마지막으로 나온다.


```javascript
console.log('A');
setTimeout(() => console.log('B'), 0);
console.log('C');
```


이 코드의 출력 순서는 `A`, `C`, `B`다. 다른 함수에 인자로 넘겨 두었다가 정해진 시점에 실행되게 하는 함수를 **콜백**(callback)이라고 부른다. 이때 함께 넘긴 `0`밀리초는 콜백을 즉시 실행하라는 뜻이 아니라 타이머가 기다릴 최소 지연 시간이다. 지연 시간이 `0`인데도 위에서 아래로 차례대로 실행되는 동기 코드가 먼저 끝나는 이유를 콜 스택, 태스크 큐, 이벤트 루프의 동작 순서로 따라간다.


## 콜 스택과 동기 코드


앞선 예제에서 `A`와 `C`가 먼저 출력되는 과정은 현재 실행 중인 함수를 쌓아 두는 **콜 스택**(call stack)의 동작으로 설명된다. JavaScript 실행 환경(런타임)은 함수를 호출할 때마다 실행 정보인 실행 컨텍스트(execution context)를 콜 스택에 쌓는다. 함수 실행이 끝나 값을 반환하면 콜 스택에서 빠지며, 콜 스택이 완전히 비어야 대기 중인 다음 작업을 가져올 수 있다.


이 규칙을 따라 첫 번째 예제를 한 줄씩 실행하면 먼저 `console.log('A')`가 콜 스택에 올라가고, `'A'`를 출력한 뒤 빠져나온다. 이어서 다음 줄의 `setTimeout`이 콜 스택에 올라간다. 이때 `setTimeout`은 콜백 `() => console.log('B')`를 직접 실행하지 않고, 실행 환경의 타이머에 등록만 한 뒤 바로 반환한다.


`setTimeout` 호출이 끝나 콜 스택에서 빠지면 곧바로 다음 줄인 `console.log('C')`가 콜 스택에 올라가 `'C'`를 출력하고 빠진다. 이 시점까지 `A`와 `C`는 이미 화면에 출력되었지만, `B`를 출력할 콜백은 아직 콜 스택 바깥에서 차례를 기다리고 있다.


## 태스크 큐와 이벤트 루프


타이머에 등록된 콜백이 언제 실행되는지는 대기 줄인 **태스크 큐**(task queue, 작업 큐)와 **이벤트 루프**(event loop)가 결정한다. 타이머에 등록된 콜백은 지정한 지연 시간이 지나면 태스크 큐에 들어가 차례를 기다린다. 지연 시간이 `0`이어도 콜백은 콜 스택으로 곧장 들어가지 못하고, 현재 실행 중인 동기 코드가 모두 끝난 뒤에야 실행 기회를 얻는다.


이벤트 루프는 콜 스택이 완전히 비었는지 반복해서 확인하다가, 비어 있으면 태스크 큐에서 작업을 하나 꺼내 콜 스택에 올린다. [MDN 문서](https://developer.mozilla.org/en-US/docs/Web/JavaScript/EventLoop)도 이벤트 루프의 이 동작을 설명한다. 따라서 동기 코드인 `A`와 `C`의 출력이 모두 끝나 콜 스택이 빈 뒤에야 `B`의 콜백이 콜 스택으로 옮겨져 `A`, `C`, `B` 순서로 출력된다.


![콜 스택에서 A와 C가 먼저 실행되고, 타이머를 거쳐 태스크 큐에 들어간 B 콜백이 이벤트 루프를 통해 마지막에 실행되어 A, C, B 순서로 출력되는 다이어그램](/images/notion/tech-k35/image-1.png)


그림 1. setTimeout(0) 콜백의 처리 흐름: 콜 스택의 동기 코드(A, C)가 모두 끝나 스택이 빈 뒤에야 이벤트 루프가 태스크 큐의 B 콜백을 스택으로 옮긴다 (개념도).


이 순서를 지탱하는 규칙이 **런 투 컴플리션**(run-to-completion)이다. 하나의 태스크(작업)가 콜 스택에 올라가 실행을 시작하면, 그 태스크가 끝까지 실행되어 콜 스택이 빌 때까지 다른 태스크는 중간에 끼어들지 못한다.


## 클릭과 네트워크 응답의 실행 순서


앞 절에서 본 런 투 컴플리션 규칙은 브라우저 화면(UI)의 클릭 이벤트와 네트워크 요청이 겹칠 때도 그대로 적용된다. 다음 코드는 버튼을 눌렀을 때 실행할 콜백인 이벤트 핸들러를 등록하고, 동시에 응답이 느린 서버 API를 `fetch`로 호출한다.


```javascript
button.addEventListener('click', () => {
  console.log('클릭 처리');
});

fetch('/slow-api').then(response => {
  console.log('응답 수신');
});
```


코드에서 `fetch`를 먼저 호출했다고 해서 네트워크 응답이 항상 클릭보다 먼저 처리되지는 않는다. 응답이 실제로 도착하는 시점에 따라 실행 순서가 달라지기 때문이다. 여기서는 `fetch` 호출 직후 사용자가 버튼을 빠르게 두 번(클릭 A, 클릭 B) 누르고, 두 클릭 처리가 끝난 뒤에 API 응답이 도착하는 상황을 가정한다. 실제 브라우저는 작업 출처인 태스크 소스(task source)가 여러 개여서, 모든 이벤트를 들어온 순서대로 꺼내는 단일 선입선출(FIFO) 큐 하나로만 처리하지는 않는다. 다만 여기서는 실행 순서를 따라가기 위해 두 클릭 태스크가 차례로 처리된 뒤 네트워크 응답이 준비되는 조건만 떼어 놓았다.


이 시간선에서는 먼저 클릭 A의 핸들러가 콜 스택에 올라가 끝날 때까지 실행되고, 콜 스택이 비면 클릭 B의 핸들러가 이어서 실행된다. 두 번의 클릭 처리가 끝난 뒤 네트워크 응답이 도착하면, `fetch`가 반환한 `Promise`(비동기 작업의 결과를 담는 객체)가 이행(fulfill)된다. 이때 `.then`에 등록한 콜백은 **마이크로태스크 큐**(microtask queue)라는 별도 대기열에 예약된다. 이어서 콜 스택이 빈 시점(체크포인트)에 이 콜백이 콜 스택에 올라가 `'응답 수신'`을 출력한다. 따라서 전체 출력은 `'클릭 처리'`, `'클릭 처리'`, `'응답 수신'` 순서가 된다.


![사용자의 클릭 A와 클릭 B 핸들러가 실행 스택에서 차례대로 완료된 후, 네트워크 fetch 응답에 따른 then 콜백이 마이크로태스크 큐를 거쳐 실행 스택에서 실행되는 시퀀스 다이어그램](/images/notion/tech-k35/image-2.png)


그림 2. 클릭 두 번과 느린 응답의 처리 순서: 두 클릭 태스크가 실행 스택에서 차례로 끝난 뒤 네트워크 응답이 도착해 마이크로태스크 큐에서 then 콜백이 실행된다 (설명용 시퀀스).


만약 첫 번째 클릭 A의 콜백 안에서 시간이 오래 걸리는 작업을 수행하면, 런 투 컴플리션 규칙 때문에 클릭 B의 처리도 그만큼 뒤로 밀린다. 콜 스택을 오래 점유하는 코드가 브라우저 화면의 응답 지연을 일으키는 이유가 여기에 있다.


## 태스크 큐와 마이크로태스크 큐의 우선순위


앞 절에서 클릭 핸들러는 태스크로 처리되었고, `fetch`의 `.then` 콜백은 마이크로태스크 큐로 들어갔다. JavaScript 실행 환경은 작업의 성격에 따라 대기열을 태스크 큐와 마이크로태스크 큐로 나누어 둔다. `setTimeout`이나 UI 이벤트 콜백은 태스크 큐에 들어가고 `Promise.then` 콜백은 마이크로태스크 큐에 들어가며, 두 큐는 실행 우선순위가 다르다.


이벤트 루프는 현재 실행 중인 태스크 하나를 끝낸 뒤, 다음 태스크로 넘어가기 전에 마이크로태스크 큐에 있는 작업을 전부 꺼내 비운다. [HTML 표준 문서](https://html.spec.whatwg.org/multipage/webappapis.html)는 이 순서를 이벤트 루프 처리 모델로 정의한다. 두 큐에 콜백이 동시에 대기할 때 어떤 순서로 실행되는지는 다음 코드에서 확인할 수 있다.


```javascript
console.log('1');
setTimeout(() => console.log('2'), 0);
Promise.resolve().then(() => console.log('3'));
console.log('4');
```


이 코드의 출력 순서는 `1`, `4`, `3`, `2`다. 먼저 동기 코드인 `console.log('1')`과 `console.log('4')`가 콜 스택에서 실행되어 `'1'`과 `'4'`가 출력된다. 그사이 `setTimeout`의 `'2'` 콜백은 태스크 큐에 들어가고, `Promise.resolve().then`의 `'3'` 콜백은 마이크로태스크 큐에 들어간다. 동기 코드가 모두 끝나 콜 스택이 비면, 이벤트 루프는 마이크로태스크 큐의 `'3'`을 먼저 비운 뒤에야 태스크 큐에서 `'2'`를 꺼내 실행한다.


![1단계 동기 코드에서 1과 4를 실행하고, 2단계에서 마이크로태스크 큐의 3을 먼저 실행한 뒤, 3단계에서 태스크 큐의 2를 실행하여 1, 4, 3, 2가 출력되는 흐름도](/images/notion/tech-k35/image-3.png)


그림 3. 동기 코드와 두 큐의 실행 순서 비교: 콜 스택의 동기 코드('1', '4')가 끝나면 마이크로태스크 큐('3')를 먼저 비운 뒤 태스크 큐('2')를 실행한다 (예제 추적도).


이 과정을 일반화하면 "현재 태스크(동기 코드 포함) 실행 → 마이크로태스크 큐 전부 비우기 → 다음 태스크 하나 실행 → 다시 마이크로태스크 큐 전부 비우기"가 반복된다. 실제 브라우저의 화면 렌더링 시점이나 여러 태스크 소스 가운데 어느 것을 먼저 고르는지는 생략하고, 두 큐의 우선순위만 흐름도로 나타내면 다음과 같다.


![현재 태스크 실행 완료 후 마이크로태스크 큐가 비었는지 확인해 빌 때까지 실행하고, 비어 있을 때만 태스크 큐에서 다음 태스크를 하나 꺼내 실행하는 이벤트 루프 순서도](/images/notion/tech-k35/image-4.png)


그림 4. 이벤트 루프의 처리 우선순위: 현재 태스크가 끝나면 마이크로태스크 큐가 완전히 빌 때까지 반복 실행한 뒤에야 다음 태스크를 꺼낸다 (설명용 흐름도).


이 흐름도의 왼쪽 순환 고리를 보면 마이크로태스크를 쓸 때 주의해야 할 조건도 함께 드러난다. 이벤트 루프는 마이크로태스크 큐가 완전히 빌 때까지 다음 태스크로 넘어가지 않는다. 따라서 실행 중인 마이크로태스크가 새로운 마이크로태스크를 계속 큐에 추가하면, 이벤트 루프가 이 구간에 갇혀 다음 태스크를 꺼내지 못한다. 예를 들어 `Promise`가 재귀적으로 자신을 다시 등록하는 경로가 있으면, 태스크 큐의 `setTimeout` 콜백이나 UI 이벤트는 실행 기회를 얻지 못하고 계속 밀린다.


## 결론


브라우저의 JavaScript 환경에서 지연 시간이 `0`인 타이머 콜백이 동기 코드보다 늦게 실행되는 이유는 콜 스택과 두 큐의 우선순위 때문이다. 런 투 컴플리션 규칙에 따라 콜 스택의 현재 작업과 동기 코드가 먼저 끝까지 실행된다. 콜 스택이 비면 이벤트 루프는 마이크로태스크 큐의 `Promise.then` 콜백을 모두 비운 뒤에야 태스크 큐에서 `setTimeout`이나 UI 이벤트 작업을 하나 꺼낸다. 이 순서를 알면 `Promise` 기반 문법인 `async/await`에서도 `await` 뒤의 코드가 언제 마이크로태스크 큐에 들어가 재개되는지 같은 원리로 추적할 수 있다.


이 글에서는 브라우저 시간선 위에서 콜 스택과 두 큐의 실행 순서를 확인했으며, 화면 렌더링 시점이나 여러 태스크 소스 사이의 선택 순서는 다루지 않았다. 또한 서버 환경인 Node.js에서는 이벤트 루프가 `timers`, `poll`, `check`처럼 여러 단계(phase)로 나뉘어 동작한다. [공식 문서](https://nodejs.org/learn/asynchronous-work/event-loop-timers-and-nexttick)가 각 단계의 순서를 다룬다. 브라우저의 두 큐와 비교할 때 Node.js의 `setImmediate`와 `process.nextTick`이 각 단계 사이에서 언제 실행되는지는 이어서 다룰 질문으로 남긴다.
