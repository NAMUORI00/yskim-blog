요청과 응답, 화면 상태, 인증, 인가 개념을 바탕으로 설명용 프로필 API를 두었다. 특정 저장소의 구현을 재현한 코드는 아니며 실제 프로젝트의 대응 경로는 프로젝트 글에서 확인할 범위다.


## 입력 중, 저장 중, 저장됨


서버에는 이름 ‘민수’와 버전 7이 저장돼 있다고 하자. 사용자가 입력란을 ‘지민’으로 바꿨을 때 화면의 초안은 이미 달라졌지만 저장된 값은 그대로다. 저장 버튼을 누르면 ‘지민, 기준 버전 7’을 요청에 싣고, 응답을 받기 전에는 저장 중으로 표시할 수 있다.

## 저장 응답과 성공 상태 처리


브라우저의 fetch는 HTTP 404나 500 응답을 받았다는 이유만으로 Promise를 거부하지 않는다. [MDN의 Fetch 사용 설명](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch)처럼 응답 상태를 확인하고, 본문도 기대한 구조인지 읽어야 한다.


200 응답이어도 애플리케이션 계약상 실패를 본문에 넣는 API라면 그 규칙까지 이해해야 한다. 가능하면 실패를 상태 코드와 명확한 오류 구조로 표현하면 호출자가 해석하기 수월해진다.


서버에서는 사용자가 로그인했는지와 이 대상을 수정할 수 있는지를 따로 확인한다. 화면에서 수정 버튼을 숨기는 일은 사용 편의를 위한 표시일 뿐 서버의 권한 검사를 대신하지 않는다. 이미 다른 곳에서 버전 8로 바꾼 데이터를 버전 7 기준 요청으로 덮어쓰지 않으려면 버전 조건을 비교하는 방법도 고려할 수 있다.


[HTTP의 If-Match 조건](https://www.rfc-editor.org/rfc/rfc9110.html#name-if-match)은 현재 표현의 태그와 요청 조건을 비교하는 방식을 설명한다.


이 예제에서 숫자 버전 필드를 쓰는 설계와 HTTP ETag는 같은 구현이 아니지만, 요청이 어떤 상태를 기준으로 작성됐는지 확인한다는 문제는 이어진다. 검사와 저장 사이에 다른 쓰기가 끼어들지 않도록 데이터베이스 단계에서도 조건부 갱신을 보장해야 한다.

## 새로고침과 늦게 도착한 응답


메모리의 초안과 로컬에 보관한 초안도 구분했다. 새로고침 뒤 복원한 내용에는 마지막 서버 버전과 미저장 상태를 함께 표시할 수 있다. 보관할 값의 민감도와 공용 기기 사용 여부는 저장 위치를 고를 때 남는 조건이다.


검색 화면에서는 요청 순서와 응답 순서가 바뀌는 문제도 있다. ‘제’라는 검색을 보낸 뒤 ‘제주’를 보냈는데 첫 요청이 늦게 끝나면, 더 오래된 결과가 화면을 덮어쓸 수 있다.


응답을 반영하기 전에 현재 입력의 요청 ID와 대조하는 방법을 비교했다. 서버가 이미 변경을 처리했을 수 있어, 요청 취소 후에는 서버의 변경 상태를 별도로 확인해야 한다.


외부 API 자료에는 수집 시각과 자료 자체의 기준 날짜를 함께 놓았다. 화면의 정상 응답과 원본의 최신성은 다른 결과다. 방금 조회한 자료가 오래된 관측일 수 있다는 차이를 표시하는 방식이다.


저장 완료 표시를 응답과 재조회에 연결하는 흐름으로 정리했다. 실패 후 초안 보존, 새로고침 후 복원, 늦은 응답 처리는 실제 화면에서 이어서 확인할 항목으로 남겼다.
