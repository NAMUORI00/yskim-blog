웹 화면에서 입력란의 글자를 고쳤다고 해서 서버의 데이터까지 그 즉시 바뀌는 것은 아니다. 사용자가 키보드로 입력하는 순간부터 저장 버튼을 누르고 서버의 응답을 받기까지, 화면에 보이는 값과 서버에 실제로 저장된 값은 서로 다른 상태를 거친다. 만약 네트워크 요청이 실패하거나 다른 기기에서 같은 데이터를 먼저 수정했다면 두 값의 차이는 더 벌어진다.


이 글에서는 간단한 프로필 편집 예제를 통해 화면의 입력 상태와 서버의 저장 값이 어떻게 맞물리는지 따라가 본다. 요청과 응답, 화면 상태, 인증과 인가 개념을 바탕으로 구성한 설명용 예제이므로 특정 저장소의 구현을 그대로 재현한 것은 아니며, 실제 프로젝트의 대응 경로는 글 말미의 프로젝트 글에서 확인할 수 있다.


## 입력 초안과 서버 저장 값의 분리


서버에 현재 이름 '민수'와 버전 7이 저장되어 있다고 가정해 보자. 사용자가 입력란의 이름을 '지민'으로 바꾸면 화면의 입력 값은 달라지지만, 서버에 저장된 값은 여전히 '민수'다. 이어서 저장 버튼을 누르면 클라이언트는 새로 입력한 이름 '지민'과 함께 자신이 마지막으로 확인한 기준 버전 7을 요청에 실어 보낸다. 이 요청에 대한 서버의 응답이 도착하기 전까지 화면은 '저장 중' 상태에 머문다.


| 구분            | 값  | 상태 의미                          |
| ------------- | -- | ------------------------------ |
| 마지막으로 읽은 서버 값 | 민수 | 서버의 버전 7에서 확인한 값               |
| 입력 중인 초안      | 지민 | 화면에서 수정했지만 아직 저장 여부가 확정되지 않은 값 |
| 전송한 요청        | 지민 | 기준 버전 7과 함께 서버에 처리를 요청한 후보 값   |
| 성공 응답         | 지민 | 서버가 버전 8로 저장을 마쳤다고 알려 온 값      |


이처럼 화면에서 편집 중인 초안과 서버에서 마지막으로 확인한 값을 분리해 두면, 저장 요청이 실패하더라도 사용자가 입력한 초안을 잃지 않고 그대로 유지할 수 있다. 반대로 서버 응답이 오기 전에 화면부터 저장이 끝난 것처럼 바꾸는 **낙관적 갱신**(optimistic update)을 적용하면 사용자에게 반응이 빠르게 느껴지지만, 요청이 실패했을 때 화면 표시를 이전 값으로 되돌리고 오류를 안내하는 복구 처리가 복잡해진다. 따라서 화면 상태를 설계할 때는 체감 응답 속도와 실패 시 복구할 상태의 범위를 함께 따져 보아야 한다.

그림 1처럼 요청을 보낸 뒤의 화면 상태는 서버 결과에 따라 세 갈래로 나뉜다. 서버가 저장을 확인해 주면 마지막 확인 값을 '지민'과 버전 8로 갱신한다. 입력 형식이나 권한 문제로 거부 응답을 받으면 초안은 그대로 두고 수정 안내를 띄운다. 네트워크 오류 등으로 응답 자체를 받지 못했다면 서버에 반영되었는지 알 수 없으므로 결과를 미확인 상태로 두고 다시 조회해 확인해야 한다.


## 응답 판별과 서버의 조건부 저장


클라이언트가 요청을 보낸 뒤 응답을 받았다고 해서 곧바로 저장이 성공했다고 판단할 수는 없다. 브라우저의 `fetch` 함수는 네트워크 연결 자체가 끊기지 않는 한, 서버가 HTTP 404나 500 같은 오류 상태 코드를 반환해도 Promise를 거부(reject)하지 않는다. [MDN의 Fetch 사용 설명](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch)에서 안내하듯 응답 객체의 상태 코드를 먼저 확인하고, 응답 본문도 기대한 구조에 맞는지 직접 읽어야 한다.


간혹 HTTP 상태 코드는 성공을 뜻하는 200으로 내려보내면서 본문 안에 실패 여부를 담아 전달하는 API도 있다. 이런 API를 호출할 때는 해당 애플리케이션이 정한 응답 규칙까지 확인해야 성공과 실패를 정확히 가를 수 있다. 반대로 서버 API를 설계하는 입장이라면, 실패 상황을 적절한 HTTP 상태 코드와 일관된 오류 본문 구조로 표현해야 호출하는 쪽에서 상태를 해석하기 수월하다.


서버가 변경 요청을 받아 실제 저장까지 나아가는 과정에서도 여러 단계의 검사가 이루어진다. 우선 요청을 보낸 사용자가 로그인한 상태인지 확인하는 인증과, 해당 프로필을 수정할 권한이 있는지 확인하는 인가를 별도로 거친다. 웹 화면에서 권한이 없는 사용자에게 수정 버튼을 숨기는 처리는 사용 편의를 위한 표시일 뿐이므로, 서버의 권한 검사를 대신할 수 없다.


권한과 입력 형식을 모두 통과했더라도 동시 수정에 따른 충돌 문제가 남는다. 사용자가 버전 7을 화면에 띄워 두고 '지민'으로 수정 요청을 보낸 사이, 다른 곳에서 이미 같은 프로필을 수정해 서버 상태가 버전 8로 바뀌었을 수 있다. 이때 버전 7을 기준으로 작성된 요청을 그대로 반영하면 앞서 저장된 버전 8의 변경 사항이 덮어써진다. 이를 막으려면 서버가 요청에 담긴 기준 버전과 현재 저장된 버전을 비교해야 한다.


웹 표준인 [HTTP의 If-Match 조건](https://www.rfc-editor.org/rfc/rfc9110.html#name-if-match)은 리소스의 현재 상태를 나타내는 태그(ETag)와 요청 헤더의 조건을 비교해 변경 여부를 결정하는 방식을 정의한다. 이 예제처럼 요청에 숫자 버전 필드를 포함하는 설계와 HTTP ETag를 활용하는 설계는 구현 방식이 다르지만, 요청이 어느 시점의 데이터를 기준으로 작성되었는지 확인한다는 목적은 같다. 또한 서버가 버전을 검사한 시점과 실제로 데이터를 쓰는 시점 사이에 다른 요청이 끼어들지 않도록, 데이터베이스에 반영할 때도 버전을 조건으로 걸어 갱신해야 안전하다.


![지민과 기준 버전 7 요청이 서버에 들어온 뒤 인증 및 권한 확인과 버전 비교를 거쳐 조건이 일치할 때만 버전 8로 조건부 저장되는 순서도](/images/notion/tech-s23/image-2.png)


그림 2. 인증과 권한 확인, 입력 검증, 버전 조건 비교를 거쳐 저장 여부를 결정하는 설명용 서버 흐름도(출처: 직접 구성).


## 새로고침, 늦은 응답, 원본 데이터의 시점 차이


하나의 요청을 보내고 응답을 받는 기본 흐름 외에도, 화면 상태와 실제 데이터가 어긋나는 상황은 여러 곳에서 발생한다. 대표적인 사례가 브라우저 새로고침이다. 화면 메모리에만 초안을 두면 페이지를 새로고침했을 때 작성 중이던 내용이 사라진다. 이를 방지하려고 브라우저의 로컬 저장소에 초안을 임시로 기록한다면, 현재 메모리에 있는 초안과 로컬 저장소에 보관된 초안도 구분해서 다루어야 한다. 새로고침 뒤에 로컬 초안을 복원할 때는 그 초안이 서버의 몇 번 버전을 기준으로 작성되었는지, 그리고 아직 서버에 저장되지 않은 상태라는 점을 화면에 함께 표시할 수 있다. 다만 다루는 정보의 민감도나 공용 기기 사용 여부에 따라 로컬에 데이터를 남겨도 되는지가 달라지므로, 저장 위치를 정할 때는 이러한 보안 조건도 함께 고려해야 한다.


연속해서 요청을 보내는 화면에서는 요청 순서와 응답 도착 순서가 뒤바뀌는 문제도 생긴다. 예를 들어 검색창에 '제'를 입력해 첫 번째 요청을 보낸 직후 마저 '제주'를 입력해 두 번째 요청을 보냈다고 하자. 만약 첫 번째 요청의 처리가 지연되어 두 번째 응답보다 늦게 도착하면, 사용자가 현재 입력해 둔 '제주' 화면 위에 더 오래된 '제'의 검색 결과가 덮어써질 수 있다.


![ID 1인 '제' 검색 요청보다 나중에 보낸 ID 2인 '제주' 검색 응답이 먼저 도착해 화면에 반영되고, 뒤늦게 도착한 ID 1 응답은 현재 ID와 달라 무시되는 흐름도](/images/notion/tech-s23/image-3.png)


그림 3. 연속 요청에서 응답 도착 순서가 뒤바뀌었을 때 요청 ID를 대조해 최신 결과만 반영하는 개념도.


이런 역전을 막으려면 요청마다 고유한 요청 ID를 붙이고, 응답이 도착했을 때 현재 입력 상태의 요청 ID와 일치하는지 대조해 최신 응답만 화면에 반영해야 한다. 다만 단순 조회가 아니라 서버 데이터를 수정하는 요청이라면 주의가 필요하다. 클라이언트 쪽에서 이전 요청을 취소하거나 늦게 온 응답을 무시하더라도 서버는 이미 변경 처리를 마쳤을 수 있으므로, 요청을 취소한 뒤에는 서버의 실제 저장 상태를 다시 조회해 확인해야 한다.


외부 API에서 가져온 데이터를 화면에 보여 줄 때도 응답 시점과 데이터의 기준 시점을 구분해야 한다. 우리 서버가 외부 API에서 자료를 수집한 시각과, 그 자료 자체가 생성되거나 관측된 기준 날짜는 서로 다르다. 방금 요청을 보내 정상 응답을 받았더라도 그 안에 담긴 내용은 과거 시점의 관측값일 수 있다. 따라서 화면이 정상적으로 응답을 받았다는 사실과 원본 데이터가 최신이라는 사실을 구분하고, 수집 시각과 자료의 기준 날짜를 함께 표시해 주어야 사용자가 데이터의 시점을 오해하지 않는다.


결국 화면에 '저장 완료'나 '최신 결과'를 표시하는 일은 단순히 네트워크 호출 함수가 끝났음을 알리는 것이 아니라, 응답 검증과 버전 확인, 필요할 때의 재조회까지 마친 상태를 보여 주는 과정이다. 실패 후 초안 보존, 새로고침 후 복원, 늦은 응답 처리는 실제 화면에서 이어서 확인할 항목으로 남긴다.
