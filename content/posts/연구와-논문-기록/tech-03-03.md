스마트팜 서비스와 연구 자료를 관리하며 저장소별 역할을 정리했다. 수집, 검색, 추론, 화면, 원고가 서로 다른 시점과 브랜치에 놓여 있어 실행에 필요한 연결과 연구 근거의 연결을 구분했다.


## 구현과 확인 과정


스마트팜 프로젝트의 저장소 구성을 살펴봤다. 코드를 한 저장소에 모으는 것과 서비스를 한 프로세스로 실행하는 것은 다르고, SmartFarm의 화면, 자료 수집, 추론 코드가 함께 보관되더라도 각 구성 요소의 실행 조건은 따로 존재한다. 앞 글에서 정리한 승인 흐름을 실제 구성 위에 놓고 보기 위해 제품 코드와 연구 작업 공간의 역할을 나눠 확인했다.


이 글은 NAMUORI00/smartfarm-platform-stack과 NAMUORI00/smartfarm-workspace를 함께 다룬다. 컨테이너, 서비스 주소, 배치 작업의 차이는 설치와 실행을 나눈 보충편에서 이어 읽을 수 있다. 여기서는 같이 보관하는 코드의 범위와 실제로 함께 실행하는 서비스의 범위를 대조했다.


## 구성 요소 통합과 원본 이력 보존


platform-stack의 [README](https://github.com/NAMUORI00/smartfarm-platform-stack/blob/62231b645bdcbed9f93cba06130528932a0c6b23/README.md)에는 분리돼 있던 제품 구성 요소를 git subtree 이력과 함께 가져왔다는 기록이 있다.


가져온 묶음은 frontend, ingest, llm-inference, corpus-pipeline 네 가지이고, 원본 저장소는 보존한다고 명시돼 있다. 저장소를 합친 이유를 과거 경험으로 추측하기보다 이 문서에 적힌 제품 구성과 이력 보존 방침을 출발점으로 삼았다.


| 가져온 저장소                   | 통합 위치                  | 문서에 기록된 역할           |
| ------------------------- | ---------------------- | -------------------- |
| smartfarm-frontend        | apps/frontend          | Streamlit 화면         |
| smartfarm-ingest          | services/ingest        | 오프라인 문서 처리와 색인 산출물   |
| smartfarm-llm-inference   | services/llm-inference | 로컬 모델 서버 설정          |
| smartfarm-corpus-pipeline | pipelines/corpus       | 자료 수집, 추출, 청크, 품질 보고 |


frontend는 main이 아닌 legacy-v2 브랜치를 가져온 상태였다. README가 설명하는 이유는 원본 main이 README만 있는 기준 브랜치였기 때문이다. 이 화면을 현재 smartfarm 저장소의 승인 UI와 같은 구현으로 소개할 수는 없었다. 저장소 이름뿐 아니라 가져온 브랜치와 경로를 함께 확인했다.

## Compose 구성과 실제 실행 단위


[루트 Compose](https://github.com/NAMUORI00/smartfarm-platform-stack/blob/62231b645bdcbed9f93cba06130528932a0c6b23/docker-compose.yml)에는 네 서비스가 정의돼 있었다.


이 가운데 corpus와 ingest는 명령을 실행해 자료나 산출물을 만드는 작업을 담당했다. architecture 문서도 corpus를 배치 중심으로 두고, 기본적으로 상시 API로 만들지 않는 방향을 기록하고 있었다.


frontend는 8501 포트로 화면을 열고, llm-inference는 컨테이너 안에서 8080으로 모델 API를 받도록 설정돼 있었다. 모델 파일은 호스트의 services/llm-inference/models를 컨테이너의 /models로 마운트하는 구조였다.


다만 파일 경로가 올바르게 연결된 것과 GPU에서 실제 모델이 로딩된 것은 별개다. Compose 구문 검증이나 이미지 빌드만으로는 추론 성공 여부를 알 수 없다.


코드를 따라가면서 눈에 띈 부분은 화면이 호출하는 주소였다. [질문 입력 화면](https://github.com/NAMUORI00/smartfarm-platform-stack/blob/62231b645bdcbed9f93cba06130528932a0c6b23/apps/frontend/frontend/streamlit/app.py)은 질문을 보낼 서비스 주소를 별도 환경 설정에서 읽고 있었다.


[질의 함수](https://github.com/NAMUORI00/smartfarm-platform-stack/blob/62231b645bdcbed9f93cba06130528932a0c6b23/apps/frontend/frontend/streamlit/page_modules/qa_demo.py)는 그 서비스의 질문 처리 경로로 요청을 보낸다. 함께 실행되도록 구성된 모델 서버의 채팅 응답 경로와는 요청 형식과 역할이 달랐다.


![03-03-02.png](/images/notion/tech-03-03/image-2.png)


그림 2. 루트 Compose와 화면의 질의 함수에서 확인한 실행 경계. RAG API와 모델 API를 잇는 전체 런타임은 이 그림에서 확인된 구성으로 단정하지 않았다. 출처: Compose, 질문 입력 화면, 질문 전송 처리를 바탕으로 직접 구성.


기본 컨테이너 네트워크에서 127.0.0.1은 frontend 컨테이너 자신을 가리킨다. 별도 RAG API를 호스트나 다른 컨테이너에서 띄운 경우에는 그에 맞는 주소 설정이 필요하고, 모델 API용 환경 변수가 존재한다는 것만으로 /query 호출 대상이 바뀌지는 않는다.


예를 들어 UI와 모델 서버 두 개만 시작한 상태에서 질의가 실패한다면, 모델의 답변 품질보다 RAG API의 존재와 주소를 먼저 확인하는 쪽이 합리적이다. 코드에서 도출한 점검 순서다.


## 논문 작업 공간의 별도 구성


smartfarm-workspace의 [현재 README](https://github.com/NAMUORI00/smartfarm-workspace/blob/9a39fc285db1746ef6bf5d7d01188a846e104779/README.md)에는 QACT-RAG 원고와 재현 근거를 중심으로 범위를 줄였다는 설명이 있었다.


주요 경로는 manuscript, reviews, reproducibility, evidence, submission이다. 제품용 서비스와 배포 Compose를 루트에 다시 섞기보다, 논문에 필요한 구현과 결과를 찾아가는 구조로 정리돼 있었다.


같은 연구에서 나온 코드도 역할과 근거의 범위를 나누어 읽을 수 있다. 제품 저장소에서는 실행 계약과 운영 구성이 중심이고, 논문 작업공간에서는 어떤 버전의 코드와 결과가 어떤 주장을 뒷받침하는지가 중심이다. 한쪽의 파일을 최신으로 바꾸더라도 다른 쪽의 재현 버전이 자동으로 맞춰지지는 않으므로, 서브모듈 커밋이나 산출물 목록으로 양쪽의 연결 상태를 확인할 필요가 있다.


이번에는 소스가 모인 위치와 실제 요청이 흐르는 위치를 따로 그려 보면서 빠져 있던 RAG API 경계를 확인할 수 있었다. 다음 글에서는 모델 서버 저장소 자체로 범위를 좁혀, 실행 스크립트가 성공 메시지를 출력한 시점과 모델이 첫 응답을 만들 수 있는 시점 사이의 차이를 설정과 확인 절차로 나눠 읽어 볼 예정이다.


## 작업을 정리하며


저장소 이름만으로 현재 시스템을 설명하면 서로 다른 버전이 한 구성처럼 섞이기 쉽다. 브랜치와 커밋, 실행 진입점을 함께 남기는 것이 중요하다. 그 기준이 있어야 구현 변화와 논문의 근거도 다시 연결할 수 있다.
