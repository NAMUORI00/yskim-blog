연구로 만든 기능을 실제 서비스로 묶다 보면 자료 수집, 검색용 문서 정리, 모델 추론, 웹 화면 코드와 논문 원고, 실험 결과가 여러 저장소에 흩어진다. 코드를 한 저장소에 모아 두더라도 모든 프로그램을 한꺼번에 켜서 쓰지는 않는다. 화면과 자료 수집기, 모델을 돌리는 추론 서버 코드가 같은 폴더 안에 들어 있어도 각자 실행하는 조건이 다르다. 논문에 실은 실험 근거 또한 서비스의 최신 코드가 아니라 실험 당시의 시점에 고정돼 있다.


운영자 승인을 거쳐 동작하는 제어 흐름을 비롯한 스마트팜 기능이 실제 저장소에 어떻게 놓여 있는지 확인하기 위해 두 저장소를 대조했다. 제품 코드를 모아 둔 `NAMUORI00/smartfarm-platform-stack`과 논문 작업 공간인 `NAMUORI00/smartfarm-workspace`가 비교 대상이다. 이 글에서는 한 저장소에 묶인 코드의 범위와 실제로 함께 켜지는 서비스의 범위가 어떻게 다른지 확인한다. 그 뒤 제품 실행 구성과 논문 실험을 다시 검증하는 재현 자료가 어떻게 분리돼 있는지 비교한다.


## 제품 저장소의 통합 경로와 브랜치 기준


먼저 두 저장소 가운데 제품 코드를 모아 둔 `smartfarm-platform-stack`에서 하위 구성 요소가 어떤 경로와 기준으로 합쳐졌는지 확인했다. 이 저장소의 [README](https://github.com/NAMUORI00/smartfarm-platform-stack/blob/62231b645bdcbed9f93cba06130528932a0c6b23/README.md)에는 원래 분리돼 있던 제품 구성 요소 네 개를 **git subtree**로 합쳤다는 기록이 있다. 이 기능을 쓰면 각 저장소의 변경 기록인 커밋 이력을 그대로 유지한 채 현재 저장소의 하위 폴더로 코드를 가져올 수 있다. 가져온 묶음은 `frontend`, `ingest`, `llm-inference`, `corpus-pipeline` 네 가지이며, 각 원본 저장소는 그대로 보존한다고 명시돼 있다. 저장소를 합친 배경을 임의로 추측하지 않고, 문서에 적힌 제품 구성과 이력 보존 방침을 기준으로 삼았다.


| 가져온 저장소                     | 통합 위치                    | 문서에 기록된 역할           |
| --------------------------- | ------------------------ | -------------------- |
| `smartfarm-frontend`        | `apps/frontend`          | Streamlit 화면         |
| `smartfarm-ingest`          | `services/ingest`        | 오프라인 문서 처리와 색인 산출물   |
| `smartfarm-llm-inference`   | `services/llm-inference` | 로컬 모델 서버 설정          |
| `smartfarm-corpus-pipeline` | `pipelines/corpus`       | 자료 수집, 추출, 청크, 품질 보고 |


네 구성 요소 가운데 `smartfarm-frontend`는 기본 **브랜치**(작업 갈래)인 `main` 대신 `legacy-v2` 브랜치를 가져온 상태였다. README에 따르면 원본 저장소의 `main`은 안내 문서만 들어 있는 기준 브랜치였기 때문이다. 따라서 그림 1에 표시한 `apps/frontend`의 화면을 현재 `smartfarm` 저장소의 운영자 승인 화면과 같은 구현으로 볼 수는 없다. 저장소 이름만 보지 않고 실제로 가져온 브랜치와 하위 경로까지 함께 확인해야 하는 이유다.

## 배치 작업과 상시 실행 서버의 구분


앞 절에서 네 구성 요소가 한 저장소에 모인 구조를 보았다면, 이번에는 이 구성 요소들이 실행 설정에서 어떻게 나뉘어 동작하는지 확인한다. 컨테이너 실행 구성을 적은 [루트 Compose](https://github.com/NAMUORI00/smartfarm-platform-stack/blob/62231b645bdcbed9f93cba06130528932a0c6b23/docker-compose.yml) 파일에도 `corpus`, `ingest`, `frontend`, `llm-inference` 네 서비스가 나란히 정의돼 있었다. 하지만 설정 파일 하나에 함께 묶여 있다고 해서 네 서비스가 모두 항상 켜져 있는 서버로 동작하는 것은 아니다.


그림 2처럼 `corpus`와 `ingest`는 필요할 때 명령을 실행해 원시 자료를 다듬거나 검색용 색인 산출물을 만드는 **배치 작업**(batch job)이다. 저장소의 `architecture` 문서에서도 `corpus`를 한꺼번에 처리하는 일괄 작업 중심으로 두고, 기본적으로 상시 응답하는 API 서버로 띄우지 않는다고 설명한다.


반면 `frontend`와 `llm-inference`는 통신 통로인 포트를 열어 두고 요청을 기다리는 상시 실행 컨테이너다. `frontend`는 `8501` 포트로 Streamlit 웹 화면을 열고, `llm-inference`는 컨테이너 내부 `8080` 포트로 모델 API 요청을 받는다. 추론에 쓸 모델 파일은 호스트의 `services/llm-inference/models` 폴더를 컨테이너 안의 `/models` 경로에 연결(**마운트**)해 읽는다. 다만 파일 경로가 정상적으로 연결된 것과 GPU 메모리에 실제 모델이 올라간 것은 별개다. Compose 문법 검증이나 이미지 빌드만으로는 추론 성공 여부를 알 수 없는 이유다.

## 질문 입력 화면의 요청 경로와 실행 경계


앞 절에서 상시 실행 서버로 구분한 `frontend`와 `llm-inference` 두 컨테이너만 띄운다고 해서 화면의 질의응답이 바로 동작하지는 않는다. 코드를 따라가며 요청이 흐르는 길을 확인해 보니 화면이 질문을 보내는 주소가 모델 서버와 달랐다.


Streamlit 기반의 [질문 입력 화면](https://github.com/NAMUORI00/smartfarm-platform-stack/blob/62231b645bdcbed9f93cba06130528932a0c6b23/apps/frontend/frontend/streamlit/app.py)은 질문을 전달할 서버 주소를 별도 환경 설정에서 읽어 온다. 이어서 실제 요청을 보내는 [질의 함수](https://github.com/NAMUORI00/smartfarm-platform-stack/blob/62231b645bdcbed9f93cba06130528932a0c6b23/apps/frontend/frontend/streamlit/page_modules/qa_demo.py)는 그 서비스의 질문 처리 경로(`/query`)로 HTTP 요청을 전송한다. 이 `/query` 경로는 관련 문서를 검색해 답변을 만드는 별도 **RAG API** 서버의 요청 주소다. 루트 Compose에서 함께 실행되는 `llm-inference` 모델 서버의 채팅 응답 경로와는 요청 형식도 역할도 다르다.


![Streamlit 화면이 루트 Compose 내부의 llm-inference가 아니라 외부의 별도 RAG API로 /query 요청을 보내는 실행 경계 다이어그램](/images/notion/tech-03-03/image-3.png)


그림 3. 루트 Compose와 화면의 질의 함수에서 확인한 /query 요청 경로와 실행 경계. RAG API와 모델 API를 잇는 전체 런타임은 이 그림에서 확인된 구성으로 단정하지 않았다(출처: Compose, 질문 입력 화면, 질문 전송 처리를 바탕으로 재구성).


컨테이너 기본 네트워크에서 자기 자신을 가리키는 `127.0.0.1`은 호스트 컴퓨터가 아니라 `frontend` 컨테이너 내부를 뜻한다. 그림 3처럼 루트 Compose 바깥의 호스트나 다른 컨테이너에 별도 RAG API 서버를 띄웠다면 그에 맞는 주소를 지정해야 한다. 모델 API용 환경 변수가 설정돼 있다는 사실만으로 `/query` 호출 대상이 바뀌지는 않는다.


예를 들어 화면(`frontend`)과 모델 서버(`llm-inference`) 두 개만 시작한 상태에서 질문 전송이 실패할 수 있다. 이때는 모델의 답변 품질을 의심하기보다 별도 RAG API 서버가 떠 있는지와 주소 설정이 맞는지부터 확인하는 편이 합리적이다. 이는 컨테이너를 직접 실행하기 전에 코드의 호출 경로에서 도출한 점검 순서다.


## 논문 작업 공간의 분리와 버전 대조


앞에서 본 제품 저장소와 달리 `smartfarm-workspace`는 논문 원고와 실험 재현 자료를 따로 관리하는 작업 공간이다. 이 저장소의 [현재 README](https://github.com/NAMUORI00/smartfarm-workspace/blob/9a39fc285db1746ef6bf5d7d01188a846e104779/README.md)에는 QACT-RAG 논문 원고와 재현 근거를 중심으로 저장소 범위를 줄였다는 설명이 적혀 있다.


주요 경로를 보면 원고를 두는 `manuscript`, 심사 의견을 모은 `reviews`, 투고본을 관리하는 `submission` 폴더가 있다. 여기에 재현 실험 구성을 담은 `reproducibility`와 근거 자료를 정리한 `evidence` 경로를 함께 두었다. 제품용 서비스 코드나 배포용 Compose 설정을 루트에 다시 섞지 않고, 논문에 필요한 구현과 실험 결과를 찾아가도록 정리돼 있다.


![제품 실행 구성을 담은 smartfarm-platform-stack과 논문 원고 및 재현 근거를 담은 smartfarm-workspace를 서브모듈 커밋과 산출물 목록으로 대조하는 구조도](/images/notion/tech-03-03/image-4.png)


그림 4. 실행 구성을 다루는 smartfarm-platform-stack과 논문 재현 근거를 관리하는 smartfarm-workspace의 경로 구성 및 버전 대조.


같은 연구에서 나온 코드라도 두 저장소가 중심에 두는 관리 기준은 서로 다르다. 그림 4와 같이 제품 저장소(`smartfarm-platform-stack`)에서는 컨테이너 실행 조건과 운영 구성이 중심이다. 반면 논문 작업 공간(`smartfarm-workspace`)에서는 어느 버전의 코드와 실험 결과가 논문의 어떤 주장을 뒷받침하는지가 중심이다. 한쪽 저장소의 파일을 최신으로 바꾸더라도 다른 쪽의 재현 버전이 자동으로 맞춰지지는 않는다. 따라서 다른 저장소의 특정 커밋을 참조하는 **Git 서브모듈**(submodule) 기록이나 산출물 목록으로 양쪽의 연결 상태를 대조해야 한다.


## 결론


두 저장소의 문서와 설정 코드를 대조해 코드가 모인 범위와 실제 서비스가 켜지는 경계, 논문 재현 자료의 관리 기준이 서로 다르다는 점을 확인했다. 저장소 이름만으로 시스템을 설명하면 `legacy-v2` 브랜치의 화면이나 루트 Compose 바깥의 RAG API처럼 서로 다른 버전과 실행 경계가 한 구성처럼 섞이기 쉽다. 구현 변화와 논문의 근거를 다시 연결하려면 저장소 이름뿐 아니라 브랜치와 커밋, 실행 진입점을 함께 남겨야 한다.


이번 글에서는 코드가 모인 위치와 실제 요청이 흐르는 위치를 따로 그려 보며 루트 Compose 바깥에 있던 RAG API 경계를 확인했다. 다만 GPU 메모리에 실제 모델이 올라가 추론이 동작하는지나 RAG API와 모델 API를 잇는 전체 실행 환경은 이번 설정 확인만으로 단정하지 않았다. 다음 글에서는 모델 서버 저장소 자체로 범위를 좁혀, 실행 스크립트가 성공을 알린 시점과 모델이 실제로 첫 응답을 만드는 시점의 차이를 설정과 확인 절차로 나눠 다룬다.
