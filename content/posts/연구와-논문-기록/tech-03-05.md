[앞 글](https://blog.namuori.net/posts/tech-03-04/)에서는 모델 추론 서버가 실제로 답변을 새로 만드는지, 아니면 대체 응답을 돌려주는지 확인했다. 이번에는 `smartfarm-benchmarking` 저장소의 평가 코드를 읽으며 결과 파일의 점수가 어디서 만들어지는지 따라가 봤다. 결과 파일에 '답변 점수', '전송 지연', '최대 메모리' 같은 항목이 적혀 있어도 무엇을 언제 쟀는지에 따라 숫자의 뜻이 달라진다. 예를 들어 답변 점수는 언어 모델이 새로 쓴 문장을 채점한 값일 수도 있고, 검색된 문서에서 잘라낸 문장을 채점한 값일 수도 있다.


검색 지표와 평가 표본, 측정 범위의 기초 개념은 앞선 글에서 먼저 다뤘다. 이 글에서는 평가 코드가 각 지표를 계산하는 실제 경로를 따라가고, 실험 결과를 비교할 때 함께 확인해야 할 조건을 짚어 본다.


## 검색 지표와 발췌 답변의 평가 경로


먼저 답변 점수와 검색 지표가 코드에서 어떻게 갈라져 계산되는지 확인하기 위해 [검색과 답변 평가 코드](https://github.com/NAMUORI00/smartfarm-benchmarking/blob/ad13f5b157ec8b066a25088326fd887782545a1f/benchmarking/experiments/paper_eval.py)를 읽었다. 이 코드는 데이터셋에서 질의와 문서를 읽어 찾기 쉽게 색인을 만든 뒤, 검색 방법별 순위에 따라 검색 지표를 계산한다. 이때 문서 본문과 질의의 뜻을 숫자 배열로 바꾼 **임베딩**(embedding)은 설정된 `provider`를 호출해 얻는다. 따라서 검색 통로만 평가하는 경로라고 해서 외부 모델 호출이 전혀 없는 것은 아니다.


눈여겨볼 곳은 답변 문자열을 만드는 `_build_answer` 함수다. 이 함수는 답변을 새로 쓰는 생성 모델을 호출하지 않고, 첫 번째로 검색된 문서의 본문을 가져와 기본 280자 범위로 자른다. 본문 뒷부분이 잘렸다면 끝에 말줄임표를 붙여 그 문자열을 답변으로 삼는다. 설정에서 `retrieval_only`를 끄면 코드는 이 280자 발췌문을 정답 텍스트와 비교하고, 옵션에 따라 RAGAS 평가에도 넘긴다. 채점 과정에서 평가용 모델을 부를 수 있지만, 채점 대상인 답변 자체는 생성 모델이 쓴 문장이 아니라 문서 발췌문이다.

이 흐름을 놓치면 답변 점수가 달라졌을 때 검색 순위가 바뀐 영향인지 생성 모델의 영향인지 가려내기 어렵다. 이 코드에서는 첫 번째로 검색된 문서가 바뀌면 발췌 답변도 그대로 달라지기 때문이다. 맨 위 문서가 질문과 얼마나 맞는지 묻는 일과 검색된 내용을 종합해 답변을 잘 썼는지 묻는 일은 구분해야 한다. 생성 모델의 답변 품질이 나아졌는지 확인하려면 실제 생성 경로를 연결한 별도 평가가 필요하다.


## 표본 분할과 시드별 비교 쌍 구성


검색 지표와 답변 점수를 계산하는 경로에 이어, 같은 파일에서 전체 질의 데이터를 어떻게 나누는지도 확인했다. 이 파일에는 전체 데이터를 설정값 조정용인 튜닝 표본과 최종 평가용 표본으로 나누는 코드가 들어 있다. 전체 표본 수가 1보다 크고 분할 비율인 `tune_ratio`가 양수이면, 질의 목록을 섞어 앞부분을 튜닝에 쓰고 나머지를 평가에 배정한다. 실행 결과에는 나뉜 표본 수인 `num_tune_samples`와 `num_eval_samples`, 평가 질의 ID 목록의 고유값(fingerprint)이 함께 남는다. 설정과 입력 데이터에 따라 나뉘는 결과가 달라지므로 실제 실행 결과에서 두 표본 수와 고유값을 함께 확인해야 한다.


두 검색 방법의 점수를 맞비교하는 [방법별 결과 비교 코드](https://github.com/NAMUORI00/smartfarm-benchmarking/blob/ad13f5b157ec8b066a25088326fd887782545a1f/benchmarking/experiments/run_main_eval.py)는 무작위 섞기의 시작값인 **시드**(seed)별 결과를 읽는다. 이 코드는 두 방법의 결과에 공통으로 들어 있는 질의 ID(`qid`)만 모아 비교 쌍을 만들고, 한쪽에만 있는 질의는 비교에서 뺀다. 공통 질의 수와 제외된 질의 수를 함께 점검하지 않으면, 어느 한쪽에 유리하게 남은 일부 결과만으로 비교가 이뤄질 수 있다.

여러 시드에서 반복된 질문은 같은 질문을 공유하는 표본으로 다루어야 한다. 현재 코드는 시드별 비교 쌍을 하나로 이어 붙인 뒤, 표본을 다시 뽑아 점수 분포를 살피는 **부트스트랩**(bootstrap) 재표집을 수행한다. 하지만 부트스트랩 반복 횟수나 시드를 늘리는 일과 서로 독립된 새 질문 표본을 늘리는 일은 다르다. 논문에서 신뢰구간을 해석할 때는 같은 질문끼리의 묶음이나 시드 의존성을 따로 검토해야 한다. 통계 검정 함수를 쓰기 전에도 표본 구성과 평가 설계가 검정의 가정을 만족하는지 먼저 따져봐야 한다.


## 클라이언트와 서버의 시간 측정 경계


점수를 비교할 표본 구성을 확인한 뒤에는, 지연 시간과 요청 성공 여부가 어디서 어떻게 기록되는지 [요청 시간 측정 코드](https://github.com/NAMUORI00/smartfarm-benchmarking/blob/ad13f5b157ec8b066a25088326fd887782545a1f/benchmarking/utils/experiment_utils.py)에서 확인했다. 이 코드의 `call_query` 함수는 `/query` 요청 전후 시각을 파이썬 `perf_counter`로 재서 서버가 돌려준 `latency`와 따로 저장한다. 클라이언트가 잰 시간에서 서버가 응답에 담아 돌려준 `latency`를 뺀 값은 `latency_transport_s_raw` 필드에 따로 남는다. 이 값에는 네트워크 전송 시간뿐 아니라 요청 직렬화, 응답 본문 처리, 양쪽의 측정 구간 차이가 섞일 수 있어 순수한 네트워크 지연이라고 보기 어렵다.


예를 들어 클라이언트가 0.98초, 서버가 1.00초를 보고했다면 두 시간의 원시 차이(`raw`)는 −0.02초가 된다. 시간 차이를 보정하는 정규화 함수는 마지막에 `max(0, raw)`를 적용해 이 음수 값을 0으로 바꾼다. 코드 주석에는 작은 음수를 보정하는 이유가 적혀 있지만, 같은 계산식이 적용되기 때문에 큰 음수가 나와도 결과는 똑같이 0이 된다. 보정된 값만 보면 측정 이상을 알아채기 어렵다. 따라서 원시 차이인 `latency_transport_s_raw`를 먼저 확인하고 시간 단위와 측정 구간이 맞는지 되짚어 봐야 한다.


![클라이언트 측정 시간(직렬화, 네트워크 전송, 응답 처리 포함)과 서버 보고 시간의 원시 차이가 -0.02초일 때 max(0, raw) 정규화를 거쳐 0초로 기록되는 과정을 보여주는 그림](/images/notion/tech-03-05/image-3.png)


그림 3. 클라이언트와 서버의 시간 측정 구간 차이와 음수 값이 0으로 정규화되는 예시.


시간 측정과 함께 기록되는 요청 성공 여부도 실제 답변이 만들어졌는지와는 다른 기준으로 판정된다. 이 코드는 HTTP 상태 코드가 200이면 `success`를 `True`로 기록하는데, 이는 통신 규칙에 맞게 응답을 받았다는 뜻일 뿐이다. 답변이 정답인지나 언어 모델이 실제로 문장을 생성했는지는 이 값만 보고 알 수 없다. 대체 응답 여부를 뜻하는 `fallback_mode`와 캐시 사용 여부를 뜻하는 `from_cache`까지 함께 읽어야 어떤 응답을 잰 것인지 알 수 있다.


## 기기 메모리와 첫 토큰 시간 계측


단일 요청의 시간과 성공 판정 기준을 본 데 이어, 반복 요청 실험에서 메모리와 응답 지연을 집계하는 [자원 사용량 측정 코드](https://github.com/NAMUORI00/smartfarm-benchmarking/blob/ad13f5b157ec8b066a25088326fd887782545a1f/benchmarking/experiments/edge_profile.py)를 따라가 봤다. 이 코드는 `/query` 요청을 반복하면서 메모리 사용량과 지연 지표를 모은다. 최대 메모리 사용량인 `rss_peak_mb`는 평가 프로그램이 실제로 쓰고 있는 **물리 메모리 점유량**(RSS)을 기준으로 삼는다. 코드는 `psutil.Process(os.getpid())`를 호출해 성공한 요청 직후마다 자기 프로세스의 메모리를 재고 그중 최댓값을 남긴다. 따라서 추론 서버 프로세스와 GPU 메모리가 실행 내내 가장 높았던 값을 알려면 서버 쪽에서 따로 측정해야 한다.


첫 토큰이 나올 때까지 걸린 **첫 토큰 생성 시간**(`ttft_ms`)도 서버 진단 정보에 따라 기록 방식이 달라진다. 서버 진단 정보에 `ttft_ms`가 없으면 코드는 전체 문장을 만드는 데 걸린 시간인 `generate_ms`를 대체값으로 넣는다. 첫 토큰이 나올 때까지의 시간과 전체 문장 생성 시간은 서로 다른 지표이므로 출처를 적은 `ttft_source`를 확인해야 한다. 특히 요청마다 두 출처가 섞일 수 있어서, 요약 결과의 대표 출처 문자열 하나만 보고 모든 표본이 같은 방식으로 측정됐다고 단정하기 어렵다.

그림 4. 평가 프로그램이 직접 잰 값과 서버가 보고한 진단값을 구분해 수집하는 경로. 출처: 자원 사용량 측정 코드를 바탕으로 직접 구성.


요청이 실패했을 때도 지표마다 계산에 들어가는 전체 표본 수(분모)가 다르다. 네트워크 예외가 발생한 요청은 지연 시간 목록에 들어가기 전에 건너뛰지만, HTTP 오류 응답은 왕복 시간을 목록에 넣은 뒤 실패로 센다. 지연 시간을 빠른 순서로 줄 세웠을 때 100개 중 95번째 값인 **95번째 백분위수**(`p95`)도 이 목록에서 계산된다. 따라서 `p95`가 전체 요청의 사용자 대기 시간을 대표한다고 해석하려면 실패 표본이 어떻게 포함됐는지 먼저 확인해야 한다. 초당 성공 처리량인 `qps_success` 역시 성공 횟수를 전체 반복 구간 경과 시간으로 나눈 값이라 지연 시간 지표와는 분모가 다르다.


## 결론


지금까지 평가 코드를 따라가며 결과 파일의 숫자 이름보다 그 값이 채워지는 코드 위치와 측정 시작점을 먼저 확인했다. 코드에서는 검색 순위와 280자 발췌 답변이 실제 생성 응답과 분리되어 있고, 시드별 비교는 공통 질의만 묶되 반복 질문과 독립 표본을 구분해 해석해야 한다. 시간 지표에서는 클라이언트와 서버의 측정 구간 차이, 음수 시간 차이의 0 보정, 실패 표본의 포함 범위를 확인했다. 자원 지표 역시 요청 직후에 잰 클라이언트 메모리와 서버의 연속 최대 메모리, `ttft_ms`의 실제 측정 출처를 나누어 봐야 한다.


다만 이번에 평가 코드를 읽은 것만으로는 실제 농장 운영 성능이나 특정 기기의 추론 성능을 입증했다고 보기 어렵다. 실제 실행에서 서버 진단값과 요청별 원시 기록을 함께 남겨 실패, 캐시, 대체 응답을 구분하는 표는 다음 실험의 검토 과제로 남긴다.
