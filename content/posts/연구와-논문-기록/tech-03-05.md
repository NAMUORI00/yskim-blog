SmartFarm 평가에서는 요청 지연과 결과 품질을 어떤 조건으로 비교할지 정리했다. 질문과 시드, 전송 시간, 메모리 측정 시점이 지표의 의미를 바꾸므로 평가 코드의 집계 경로를 각각 확인했다.


## 구현과 확인 과정


smartfarm-benchmarking 저장소의 평가 코드를 읽으며, 결과 파일에 기록되는 점수가 어디서 만들어지는지 따라가 봤다. 이 저장소에는 검색 지표를 계산하는 경로와 검색 문서의 발췌문을 답변으로 평가하는 경로가 있었다. 결과 파일에 '답변 점수'가 있더라도 그 답변이 모델이 생성한 문장인지 검색 문서에서 잘라낸 발췌인지에 따라 점수의 의미가 달라진다. 앞 글에서 모델 서버의 실제 생성 여부를 살펴본 데 이어, 이번에는 점수의 입력 쪽을 정리했다.


검색 지표와 평가 표본, 측정 범위에 대한 기초는 앞의 개념, 보충 글에서 이어 읽을 수 있다. 저장소의 평가 코드가 확인하는 항목과 추가 측정이 필요한 항목을 연결해 정리했다.


## 검색 평가와 답변 평가의 경로


[검색과 답변 평가 코드](https://github.com/NAMUORI00/smartfarm-benchmarking/blob/ad13f5b157ec8b066a25088326fd887782545a1f/benchmarking/experiments/paper_eval.py)는 데이터셋에서 질의와 문서를 읽고 색인을 만든 뒤, 방법별 검색 순위에 지표를 계산한다.


본문 임베딩과 질의 임베딩은 provider를 통해 얻는 구조였다. 검색 채널 평가라고 해서 외부 모델 호출이 전혀 없는 것은 아닌 셈이다.


다만 답변을 만드는 `_build_answer`는 생성 모델을 호출하지 않는다. 첫 번째 검색 문서의 본문을 가져와 기본 280자 범위로 자르고 필요하면 말줄임표를 붙인다.


retrieval_only를 끈 경로에서는 이 발췌를 정답과 비교하고, 옵션에 따라 RAGAS 평가에도 전달한다. 여기서 평가용 모델을 호출할 수 있다는 것과, 답변 자체가 모델이 생성한 문장이라는 것은 별개다.

그림 1. 검색, 답변 평가에서 검색 지표와 발췌 답변 평가가 나뉘는 경로. 출처: 검색, 답변 평가 코드를 바탕으로 직접 구성.


이 구분이 빠지면 답변 점수의 변화가 검색 순위 때문인지 생성 모델 때문인지 분리하기 어렵다. 이 코드에서는 첫 문서가 바뀌면 발췌 답변도 함께 달라진다. 생성 품질 개선을 주장하려면 실제 생성 경로를 갖춘 별도 평가가 있어야 하고, 최상위 문서의 관련성이 높아졌는지 확인하는 질문과 문맥을 종합해 답변을 잘 만들었는지 확인하는 질문은 분리해 둘 대상이다.


## 설정 선택용 자료와 최종 평가 자료


같은 파일에는 튜닝 표본과 평가 표본을 나누는 코드도 있었다. 표본 수가 1보다 크고 tune_ratio가 양수일 때 목록을 섞어 앞부분을 튜닝에, 나머지를 평가에 배정한다.


결과에는 각 표본 수와 평가 질의 ID의 fingerprint가 기록된다. 설정과 입력에 따라 분할이 달라지므로, 실제 실행 결과의 num_tune_samples와 num_eval_samples를 함께 확인해야 한다.


[방법별 결과 비교 코드](https://github.com/NAMUORI00/smartfarm-benchmarking/blob/ad13f5b157ec8b066a25088326fd887782545a1f/benchmarking/experiments/run_main_eval.py)는 시드별 결과에서 두 방법에 공통으로 있는 qid를 모아 짝을 만드는 구조였다.


한 방법에만 결과가 있는 질의는 해당 쌍에서 빠진다. 공통 질의 수와 제외된 질의 수를 함께 확인하지 않으면, 유리하게 남은 일부 결과만으로 비교가 이뤄질 여지가 있다.


여러 시드에서 반복된 질문은 같은 질문을 공유하는 표본으로 취급해야 한다. 현재 코드는 시드별 짝을 이어 붙여 재표집한다.


부트스트랩 반복 횟수를 늘리는 것과 독립 표본을 늘리는 것은 다르다. 논문에서 신뢰구간을 해석할 때 질문 단위의 묶음이나 시드 의존성은 별도로 검토할 대상이다. 검정 함수를 적용할 때는 표본 구성과 평가 설계가 검정의 가정을 충족하는지 확인해야 한다.


## 클라이언트와 서버의 측정 구간


[요청 시간 측정 코드](https://github.com/NAMUORI00/smartfarm-benchmarking/blob/ad13f5b157ec8b066a25088326fd887782545a1f/benchmarking/utils/experiment_utils.py)의 call_query는 /query 요청 전후를 perf_counter로 재고, 서버가 반환한 latency와 따로 저장한다.


두 값의 차이는 latency_transport_s_raw에 남는다. 이 차이에는 네트워크뿐 아니라 직렬화, 응답 본문 처리, 계측 경계의 차이 등이 섞일 수 있어서, 순수 네트워크 지연이라고 부르기는 어렵다.


설명용 예로, 클라이언트가 0.98초, 서버가 1.00초라고 보고했다면 차이는 −0.02초다. 현재 정규화 함수는 이를 0으로 바꾼다. 주석에는 작은 음수의 처리 이유가 적혀 있지만, 코드 마지막의 max(0, raw) 때문에 큰 음수도 결국 0이 된다. 원시 차이를 함께 보존한 필드를 먼저 확인하고, 시간 단위나 측정 구간이 맞는지 되짚어 볼 이유가 여기서 생겼다.


HTTP 200일 때 success를 True로 두는 경로도 확인했다. 이 값은 요청이 처리됐는지를 분류하는 기준이고, 답변이 정답인지 혹은 모델 생성이 실제로 수행됐는지와는 별개다. fallback_mode와 from_cache처럼 함께 남는 값까지 읽어야 어떤 응답을 측정한 것인지 구체적으로 파악할 수 있다.


## 기기 평가에서 메모리와 첫 토큰 시간을 읽는 방법


[자원 사용량 측정 코드](https://github.com/NAMUORI00/smartfarm-benchmarking/blob/ad13f5b157ec8b066a25088326fd887782545a1f/benchmarking/experiments/edge_profile.py)는 /query 요청을 반복하는 구조였다.


최대 메모리 사용량인 rss_peak_mb는 psutil.Process(os.getpid())로 얻은 평가 프로그램 자신의 RSS를 바탕으로 한다. 성공 요청 뒤에 관측한 값들의 최댓값이다. 서버 프로세스와 GPU 메모리의 연속 피크는 별도 계측이 필요하다.


ttft_ms가 진단 정보에 없으면 generate_ms를 대체값으로 사용한다. 전체 생성 구간과 첫 토큰까지의 시간은 서로 다른 지표이므로 ttft_source를 확인할 대상이다. 요청마다 두 출처가 섞일 수 있어서, 하나의 대표 출처 문자열만으로 모든 표본이 같은 방식으로 측정됐다고 보기는 어렵다.

요청 실패도 같은 분모로 들어가지 않는다. 네트워크 예외가 난 요청은 지연 목록에 추가되기 전에 건너뛰지만, HTTP 오류 응답은 왕복 시간을 추가한 뒤 실패로 센다.


p95가 전체 요청의 사용자 대기시간을 대표한다고 해석하려면 실패 표본의 포함 방식을 먼저 확인해야 한다. qps_success는 성공 횟수를 전체 루프 경과 시간으로 나눈 값이라, 지연 분위수와는 분모가 다르다.


이번 코드 읽기에서 가장 도움이 됐던 부분은 숫자 이름보다 그 값이 채워지는 위치를 확인하는 일이었다. 검색 순위, 발췌 답변, 생성 응답, 서버 시간, 클라이언트 메모리를 나눠 놓고 보니 다음 실험에서 추가로 기록할 항목도 윤곽이 잡혔다.


실제 서버 진단과 요청별 원시 기록을 함께 남겨 실패, 캐시, 대체 응답을 구분하는 표를 후속 검토 항목으로 남겼다. 이 코드를 읽은 범위만으로 실제 농장 운영 성능이나 특정 기기의 추론 성능을 입증했다고 보기는 어렵다.
