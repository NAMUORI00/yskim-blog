앞 글에서는 PiFi가 대규모 언어 모델(LLM)의 여러 층인 레이어 가운데 어느 것을 가져올지 점수로 고르는 코드를 따라가 봤다. 이번에는 그 코드가 담긴 `PifiIlm` 저장소와 논문 초안이 담긴 `PifiPaper` 저장소를 대조해 실험 결과와 원고의 연결 상태를 확인했다. 본문에 연결한 소스 코드는 비공개 저장소에 들어 있어서 열람하려면 접근 권한이 필요하다. `PifiPaper`의 버전 기록인 `c48ae37` 커밋을 열어 보니 문서 빌드 환경은 갖춰져 있었지만, 본문에는 원고 틀의 예시 문구와 숫자가 그대로 남아 있었다. 빈칸으로 남은 방법론 그림과 실험 표를 실제 연구 결과로 채우려면 `PifiIlm`의 분류 모델 구조와 평가 지표 집계 방식부터 정확히 짚어 봐야 했다.


## 원고 틀과 실험 결과의 분리


먼저 논문 원고 저장소인 `PifiPaper`가 어떤 파일들로 이루어져 있는지 구성을 확인했다. 최상위 문서인 [access.tex](https://github.com/NAMUORI00/PifiPaper/blob/c48ae37ec41cd2d81bc97b9d32727d5bae5cd6ab/access.tex)는 `sections` 디렉터리 아래에서 방법론, 실험, 결론 파일을 차례로 불러온다. 그런데 문서 제목은 여전히 `Research Paper Title`이었고, 초록에도 LaTeX 원고 틀의 작성 안내 문구가 그대로 들어 있었다. 빌드 스크립트는 글꼴과 스타일 경로를 설정한 뒤 문서 제작 도구인 `pdflatex`를 호출한다. 이 과정은 문서 모양을 맞추는 조판을 담당할 뿐 실험 실행이나 결과 대조를 대신하지 않는다.


하위 파일로 나뉜 각 절의 본문도 아직 원고 틀 상태에 머물러 있었다. [방법론 절](https://github.com/NAMUORI00/PifiPaper/blob/c48ae37ec41cd2d81bc97b9d32727d5bae5cd6ab/sections/03_methodology.tex)의 구조도는 기존 `fig1.png`를 임시 자리표시자로 둔다는 주석과 함께 기본 어텐션(Attention) 수식만 보여 주었다. 정작 PiFi의 차원 변환과 레이어 삽입 경로는 그림에 담겨 있지 않았다. [실험 절](https://github.com/NAMUORI00/PifiPaper/blob/c48ae37ec41cd2d81bc97b9d32727d5bae5cd6ab/sections/04_experiments.tex)의 성능 비교 표에도 `XYZ dataset`, `Method A`, `Method B`, `Proposed` 같은 예시 이름이 들어 있었다. 표의 정확도와 시간 칸에도 원고 틀에 있던 예시 숫자가 그대로 적혀 있었다. 이 원고 틀을 재사용해 논문을 완성하려면 그림을 실제 코드 경로에 맞게 새로 그리고, 검증된 실험 산출물이 있는 항목만 표에 연결하는 절차가 따로 필요했다.

## 분류 모델 경로와 대조군 조건


방법론 절의 자리표시자 그림을 실제 구현으로 바꾸기 위해 `PifiIlm` 저장소의 [ClassificationModel](https://github.com/NAMUORI00/PifiIlm/blob/11b64cea2ebd4834decb637954bb0314174d1102/Classification/model/classification/model.py) 코드를 읽었다. 이 모델은 기본 인코더를 통과한 단어 단위 토큰 표현들을 하나의 문장 벡터로 모으는 **풀링**(pooling)을 수행한다. 이때 실행 설정에 따라 첫 번째 토큰 표현만 가져오거나 모든 토큰 표현의 평균을 계산한다. 평균을 구할 때는 문장 길이를 맞추려고 뒤에 채운 빈칸인 패딩(padding)을 포함할지 제외할지 선택한다.


문장 벡터를 만든 뒤에는 실행 설정에 따라 데이터의 이동 경로가 두 갈래로 갈라진다. 기본 모델인 `base` 경로에서는 풀링된 문장 벡터를 정답 범주를 판별하는 분류기(classifier)에 곧바로 전달한다. 반면 `pifi` 경로에서는 문장 벡터에 길이 1인 시퀀스 차원을 먼저 덧붙인다. 그다음 **선형 변환**(linear projection)으로 벡터 크기를 앞서 선택한 LLM 레이어의 입력 차원에 맞춘다. 이 벡터가 LLM 레이어를 통과하면 다시 선형 변환으로 원래 인코더 차원으로 되돌려 분류기에 넣는다.


![기본 인코더와 풀링을 거친 문장 벡터가 base 경로에서는 바로 분류기로 가고 pifi 경로에서는 선형 변환과 선택한 LLM 레이어를 거쳐 분류기로 들어가는 구조도](/images/notion/tech-06-02/image-2.png)


그림 2. ClassificationModel에서 문장 벡터가 분류기로 전달되는 base 경로와 pifi 경로 비교(분류 모델 실행 코드를 바탕으로 직접 구성).


코드를 따라가 보면 `pifi` 경로는 토큰 전체가 아니라 인코더가 하나로 압축한 문장 벡터를 LLM 레이어에 통과시킨다. 또한 `base` 경로와 비교할 때 선택한 LLM 레이어만 추가되는 것이 아니라 차원을 맞추고 되돌리는 선형 변환기도 앞뒤에 함께 들어간다. 따라서 `base`보다 `pifi`의 점수가 높더라도, 그 차이가 LLM 레이어 덕분인지 선형 변환기의 추가 파라미터(가중치) 덕분인지 바로 단정하기 어렵다. 레이어 삽입 효과를 분리해 검증하려면 기본 인코더와 풀링 방식, 분류기, 학습 조건을 똑같이 맞춰야 한다. 여기에 더해 선형 변환기만 추가한 비교 기준인 대조군과 임의의 LLM 레이어를 끼워 넣은 대조군을 후속 비교 실험에 포함해야 한다.


## 배치 단위 집계와 전체 표본 기준


분류 모델의 구조에 이어 실험 절의 표에 들어갈 성능 숫자가 어떻게 계산되는지 확인했다. 평가 과정을 담당하는 [testing 함수](https://github.com/NAMUORI00/PifiIlm/blob/11b64cea2ebd4834decb637954bb0314174d1102/Classification/task/classification/test.py)는 전처리된 평가 데이터(`test_processed.pkl`)와 학습된 가중치(`final_model.pt`)를 불러온다. 그다음 데이터를 한 번에 묶어 처리하는 단위인 **배치**(batch)마다 정확도와 **매크로 F1**(macro F1)을 계산한다.


여기서 눈여겨볼 부분은 배치마다 계산한 지표를 전체 점수로 합산하는 방식이다. 현재 코드는 전체 평가 표본에서 맞힌 개수를 세어 전체 표본 수로 나누지 않고, 배치별 정확도를 구한 뒤 이를 배치 개수로 나누어 평균을 낸다. 예를 들어 평가 표본 5개를 크기 4인 첫 배치와 크기 1인 마지막 배치로 나누어 평가하는 경우를 가정한다. 첫 배치에서 4개를 모두 맞혀 정확도가 1.0이고 마지막 배치 1개를 틀려 정확도가 0.0이면, 배치 평균 정확도는 (1+0)/2=0.5가 된다. 하지만 표본 5개 가운데 4개를 맞혔으므로 전체 표본 기준 정확도는 4/5=0.8이다. 데이터 로더 설정이 `drop_last=False`여서 데이터 개수가 배치 크기로 나누어떨어지지 않으면 마지막 배치는 크기가 작아진다. 이 상태에서 배치 평균을 쓰면 작은 마지막 배치에 속한 표본 하나가 앞선 배치의 표본보다 전체 점수에 더 큰 비중을 차지한다.


![크기 4인 첫 배치에서 4개를 맞히고 크기 1인 마지막 배치에서 틀렸을 때 배치 평균은 0.5가 되고 전체 표본 기준은 0.8이 되는 비교 그림](/images/notion/tech-06-02/image-3.png)


그림 3. 마지막 배치 크기가 작을 때 코드의 배치별 평균 정확도(0.5)와 전체 표본 기준 정확도(0.8)가 달라지는 계산 예.


클래스별 F1 점수를 평균 내는 매크로 F1도 마찬가지로 배치마다 계산한 뒤 평균을 내고 있었다. F1 점수는 모델이 고른 정답 중 실제 정답 비율인 정밀도(precision)와 실제 정답 중 모델이 찾아낸 비율인 재현율(recall)에서 계산하는 비선형 지표다. 따라서 마지막 배치가 작지 않고 모든 배치 크기가 같더라도, 배치별 F1의 평균과 전체 예측 결과를 한데 모아 계산한 F1은 값이 일치한다고 보장할 수 없다. 논문 표에 최종 성능을 적기 전에 모든 표본의 예측과 정답 쌍을 모아 전체 기준으로 다시 계산할지, 현재 코드의 배치 평균 방식을 그대로 보고할지 기준부터 정해야 한다.


## 결과 파일의 실행 기록과 표 연결


점수 계산 방식에 이어 평가 함수가 계산한 숫자를 파일에 남기는 방식을 확인했다. 코드는 평가를 마칠 때마다 데이터셋, 모델, LLM 종류, 선택된 레이어, 성능 지표를 텍스트 파일에 한 줄씩 이어 쓴다. 그러나 기록된 결과 행 자체에는 실행 식별자나 무작위 값을 고정하는 난수 시드(seed)가 함께 적히지 않는다. 코드 커밋이나 불러온 가중치 파일인 체크포인트를 식별하는 고유값인 해시도 결과 행에 남지 않는다. 별도의 설정 파일이나 실행 로그로 보완할 수는 있지만, 결과 파일에서 숫자 한 줄만 복사해 원고 표로 옮기면 나중에 어느 실행에서 나온 값인지 되짚기 어려워질 수 있다.


후속 원고 작업에서는 먼저 방법론 그림을 현재 코드의 입출력 경로에 맞춰 다시 그릴 예정이다. 결과 행마다 코드 커밋, 설정, 데이터 분할, 체크포인트, 예측 파일, 집계 방식을 묶어 기록하는 방식도 함께 검토한다. 또한 원고 표에서는 앞 단계에서 레이어를 고를 때 쓰는 간이 평가인 **프로브**(probe) 점수와 최종 분류 성능을 서로 다른 열에 분리해 둘 계획이다. 두 점수의 열을 나누어 적으면 한 단계의 수치가 다른 단계의 최종 성능처럼 읽히는 문제를 줄일 수 있다.

## 결론


이번에 `PifiPaper`와 `PifiIlm` 두 저장소를 대조해 본 결과, 현재 `PifiPaper`는 연구 결과를 담기 전의 문서 틀에 가까웠다. 실제 구현과 실험 산출물을 그 원고 틀에 옮기려면 코드와 결과 파일의 연결 기준부터 다듬어야 했다. 코드에서는 `pifi` 경로가 문장 벡터를 선택한 LLM 레이어에 넣기 전후로 선형 변환기를 거친다는 점과 평가 함수가 배치 단위로 점수를 평균 낸다는 점을 확인했다. 결과 텍스트 파일에 시드나 해시 같은 실행 추적 기록이 빠진 상태라는 점도 함께 짚었다. 선형 변환기나 임의의 레이어를 넣은 대조군 실험, 점수 집계 기준 확정, 실행 기록 보강과 원고의 그림 및 표 갱신은 후속 작업으로 남아 있다. 다음 글에서는 분산 학습으로 넘어가 같은 조건의 실험을 여러 GPU에서 수행할 때 배치와 학습 단계가 어떻게 달라지는지 확인한다.
