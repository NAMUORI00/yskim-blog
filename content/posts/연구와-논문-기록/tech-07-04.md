외부 검토자에게 코드나 작업물을 봐 달라고 요청할 때는 먼저 어떤 자료를 얼마만큼 묶어 보낼지 정해야 한다. 검토자가 수정을 권하더라도 내 컴퓨터의 다른 코드나 실행 조건까지 모두 본 것은 아니어서, 돌아온 의견을 곧바로 반영하기는 어렵다. 따라서 외부 리뷰를 활용하려면 검토에 필요한 배경 자료를 챙겨 보내는 일과, 돌아온 의견을 실제 코드와 대조해 걸러내는 일을 나누어 다루어야 한다.


`cross-review-bridge` 저장소는 이 과정을 자료 준비 단계와 의견 분류 단계로 나누어 구성한다. 저장소 [README](https://github.com/NAMUORI00/cross-review-bridge/blob/e0e20ea26d0c8eeb67fd3bffcf6d0422d97a2ef6/README.md)는 내 컴퓨터의 작업 폴더인 **로컬 작업 공간**을 실제 수정 기준으로 삼고, 외부 의견은 검증할 조언으로 다룬다고 명시한다. 실제 외부 제출과 리뷰 실행은 자동화 스크립트 밖의 별도 단계로 두고, 스크립트는 제출할 자료를 묶거나 돌아온 응답을 작업표로 정리하는 역할만 맡는다. 구조화된 결과와 승인 상태는 보충 글에서 다루고, 이 글에서는 스크립트가 만든 검토 자료와 작업표가 로컬 근거와 어떻게 연결되는지 확인한다.


## 외부 검토에 전달할 맥락


자료 준비 단계에서는 외부 검토자가 상황을 이해할 수 있도록 어떤 맥락을 묶어 보낼지 먼저 정한다. 수정 전후에 달라진 줄만 보여 주는 코드 차이(`diff`)만 보내면 왜 고쳤는지나 문제를 다시 재현하는 조건이 빠지기 쉽다. 반대로 저장소 전체를 보내면 파일이 너무 많아 정작 검토해야 할 대상이 묻힐 수 있다. 그래서 이 저장소는 무엇을 고치려는지, 관련 파일은 무엇인지, 이미 확인한 결과와 아직 확인하지 못한 내용은 무엇인지를 함께 묶는 방식을 택하고 있었다.


저장소 README는 도구의 역할을 변경 내용을 한 문서로 간추린 **브리프**(brief) 생성, 더 풍부한 ZIP 묶음 생성, 돌아온 의견 분류로 나눈다. 외부 검토자가 이전 대화 맥락을 이미 알고 있다고 가정하지 않고, 검토에 필요한 입력 자료를 새로 꾸리려는 선택으로 읽혔다.

## 브리프와 ZIP 묶음의 수집 범위와 한계


앞서 본 두 가지 입력 자료인 브리프와 ZIP 묶음은 스크립트에 따라 수집하는 파일 범위와 용량 제한이 서로 다르다. 먼저 가벼운 요약본을 만드는 [검토용 변경 요약 생성](https://github.com/NAMUORI00/cross-review-bridge/blob/e0e20ea26d0c8eeb67fd3bffcf6d0422d97a2ef6/skills/cross-review-bridge/scripts/New-CrossReviewBrief.ps1) 스크립트는 Git 상태, `diff` 요약과 본문, 파일 목록, 사용자가 직접 지정한 파일을 한 문서로 모은다.


Git에서는 다음 기록에 넣을 변경분을 대기 칸에 미리 올려 두는데, 이를 **스테이징**(staging)이라고 한다. 이 스크립트가 실행하는 기본 `git diff`는 기존 관리 대상 파일에서 아직 스테이징하지 않은(unstaged) 변경만 읽는다. 이미 스테이징한 변경이나 새로 만들어 아직 추적하지 않는 파일의 본문까지 같은 `diff`에 들어 있다고 생각하면 누락이 생긴다. 또한 파일 목록에 이름이 보이는 것과 실제 파일 내용이 브리프에 들어가는 것은 별개다. 기본 `diff`에는 길이 제한이 있고, 개별 텍스트 파일도 일정 길이를 넘으면 뒷부분이 잘렸다는 표시가 붙는다. 이처럼 길이 제한에 걸린 변경은 빠지므로, 브리프를 만들었다는 사실만으로 모든 변경이 담겼다고 보장할 수는 없다.


더 많은 자료를 담는 [검토 자료 묶음 생성](https://github.com/NAMUORI00/cross-review-bridge/blob/e0e20ea26d0c8eeb67fd3bffcf6d0422d97a2ef6/skills/pro-review-package-handoff/scripts/New-ProReviewPackage.ps1) 스크립트는 스테이징된 `diff`와 스테이징하지 않은 `diff`를 따로 모은다. 여기에 지정한 파일과 선택적으로 찾은 자료를 함께 묶고, 포함 목록과 제외 목록을 묶음 명세표인 **매니페스트**(`manifest`)에 남긴다. 이때도 파일당 최대 크기인 `MaxFileBytes`가 기본 `5MiB`로 정해져 있어서, 이보다 큰 PDF나 이미지는 묶음에서 빠진다.


![New-CrossReviewBrief.ps1과 New-ProReviewPackage.ps1이 수집하는 diff와 파일 범위, 길이 및 용량 제한, 비밀값 치환 한계를 비교한 다이어그램](/images/notion/tech-07-04/image-2.png)


그림 2. 브리프 생성 스크립트와 ZIP 묶음 생성 스크립트의 수집 대상 및 제한 조건 비교.


자료를 묶을 때는 코드 안의 비밀값처럼 보이는 텍스트를 가리는 함수도 함께 동작한다. 하지만 정해진 패턴에 맞는 문자열만 다른 글자로 바꾸는 방식이어서 패턴에서 벗어난 민감한 자료는 그대로 남는다. 텍스트가 아닌 원본 바이너리 자료를 복사하는 경로에서도 글자 바꾸기가 적용되지 않는다. 따라서 스크립트로 파일을 묶음에 담는 일과 외부에 공개해도 되는지 사람이 판단하는 일은 별개 작업이다.


## 외부 의견 추출과 대기 작업표


준비한 자료로 외부 검토를 마치고 응답이 돌아오면, 다음 단계는 긴 답변에서 검토할 항목을 추려 작업표로 정리하는 일이다. [외부 의견에서 검토 항목 추출](https://github.com/NAMUORI00/cross-review-bridge/blob/e0e20ea26d0c8eeb67fd3bffcf6d0422d97a2ef6/skills/external-feedback-integrator/scripts/Convert-ExternalFeedback.ps1) 스크립트는 외부 응답에서 목록 형태이거나 문제, 수정, 근거 같은 단어가 들어간 줄을 찾아 최대 80개까지 후보로 뽑는다. 조건에 맞는 후보 줄이 하나도 없으면 본문 앞부분을 대신 가져오고, 응답 원문 전체는 문서의 별도 구역에 그대로 보존한다.


스크립트가 뽑아낸 항목의 초기 분류는 모두 판정을 미뤄 둔 **대기**(`pending`) 상태다. 최종 분류에는 반영(`apply`), 추가 검토(`consider`), 기각(`reject`), 사용자 결정 필요(`needs user decision`)의 네 가지가 있다. 스킬 이름에는 통합을 뜻하는 `Integrator`가 들어 있지만, 이 가운데 하나를 자동으로 고르거나 코드를 직접 수정하는 기능은 없다. 스크립트가 실제로 내놓는 산출물은 검토자가 직접 판단을 기록할 작업표다.


한 줄씩 후보를 뽑는 방식은 긴 응답에서 검토 대상을 빠르게 모을 수 있지만, 한 주장과 그 조건이 여러 줄에 걸쳐 있으면 따로 떨어질 수 있다. 표 머리글이나 설명용 목록도 후보로 잡힐 수 있어서 추출된 항목은 아래에 보존된 원문 문맥과 대조하며 읽어야 한다. 또한 후보를 최대 80개까지만 뽑는 상한이 있으므로 이 목록이 외부 의견 전체를 빠짐없이 담고 있지는 않을 수 있다.


## 로컬 근거 확인과 후속 분류


작업표에 모인 `pending` 항목을 네 가지 분류 가운데 무엇으로 바꿀지는 로컬 작업 공간의 실제 코드를 확인해 결정한다. 예를 들어 외부 검토에서 "이 경로는 빈 입력에서 예외가 난다"고 지적한 경우를 보자. 이 문장만 보고 곧장 코드를 고치는 대신, 로컬에서 실제 호출 경로와 입력 검사 코드를 읽고 재현해 봐야 실제로 고쳐야 할 문제인지 판단할 수 있다. 이미 앞단에서 빈 입력을 막고 있다면 지적의 조건을 좁히거나 채택하지 않는 이유(`reject`)를 남기면 된다. 반대로 실제 실패가 재현되면 해당 범위를 수정하고 검증하는 단계(`apply`)로 이어진다.


![외부 의견 원문에서 최대 80개 후보 줄을 추출해 pending 작업표를 만들고 로컬 코드와 재현 대조를 거쳐 apply, consider, reject, needs user decision으로 분류하는 흐름도](/images/notion/tech-07-04/image-3.png)


그림 3. 추출한 의견을 로컬 근거와 대조해 분류하고 후속 조치로 연결하는 절차. 출처: 피드백 변환 스크립트의 산출 형식과 README의 로컬 검증 원칙을 바탕으로 직접 구성. 분류와 수정은 자료를 받은 검토자가 수행할 단계다.


외부 모델의 말투가 단호하든 조심스럽든 이러한 대조 절차는 같은 방식으로 적용된다. 문장의 확신 정도보다 특정 시점의 코드 저장 기록인 커밋에서 그 지적이 실제로 참인지를 기준으로 본다. 제품 방향이나 연구 범위처럼 여러 선택이 가능한 사안은 단순한 코드 결함 판정과 나누어 기록한다. 검토 의견이 로컬 구현과 다르다는 이유만으로 모든 항목을 절충하면 원래 변경의 목적과 맞지 않는 수정이 섞일 수 있다.


## 제출 시점과 현재 작업 공간의 대조


로컬 근거를 확인할 때는 외부에 자료를 보낸 시점과 현재 로컬 작업 공간의 상태가 같은지도 함께 맞춰 봐야 한다. 리뷰를 기다리는 동안 로컬 파일이 바뀌면 외부 의견이 가리키는 코드가 현재 코드와 이미 달라져 있을 수 있기 때문이다. 제출 자료에 담긴 커밋이나 `diff`, 포함 파일 목록이 현재 상태와 어긋난 채로 의견을 읽으면 맥락이 맞지 않는 수정을 그대로 적용하게 된다. 앞서 만든 `manifest`는 자료를 제출한 뒤에 일어난 로컬 변경을 자동으로 추적하지 않는다. 따라서 후속 검토 기록에 제출 묶음의 고유 번호(식별자)와 검토 대상 시점을 함께 남겨 두어야 현재 작업 공간과 대조하는 기준으로 삼을 수 있다.


![제출 시점의 묶음 정보와 리뷰 대기 중 변경된 로컬 작업 공간을 묶음 식별자와 시점으로 대조해 반영 여부를 판단하는 흐름도](/images/notion/tech-07-04/image-4.png)


그림 4. 리뷰 대기 중 로컬 작업 공간이 바뀌었을 때 제출 묶음 식별자와 대상 시점을 기준으로 현재 상태와 대조하는 흐름.


## 결론


외부 코드 리뷰 자료는 무조건 많이 묶어 보낼 때보다 검토자의 주장과 로컬 근거, 수정할 원문을 바로 대조할 수 있을 때 읽기 쉽다. 이 글에서 확인한 스크립트들은 검토용 입력 자료를 만들고 돌아온 외부 의견을 `pending` 작업표로 정리하는 단계까지를 맡고 있었다.


반면 생성된 파일 목록과 실제 본문을 대조해 누락이나 비밀값을 점검하는 일은 스크립트 밖의 작업이다. 의견을 받은 뒤 로컬 근거와 제출 시점을 확인해 어떤 원문을 고칠지 최종 분류를 결정하는 단계도 검토자의 몫으로 남아 있다. 다음 글에서는 `paperbanana` 도구가 만든 그림을 대상으로, 생성된 시각 자료를 원문의 주장과 대조하는 과정을 이어서 다룬다.
