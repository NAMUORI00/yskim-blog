외부 리뷰를 준비하며 검토에 필요한 자료를 생성하고 변경 내용과 연결하는 흐름을 정리했다. 자료 생성 스크립트가 맡는 부분과 검토자가 판단할 부분을 나누어, 제출 전 확인할 산출물을 정리했다.


## 구현과 확인 과정


cross-review-bridge 저장소의 코드를 읽으며, 검토 자료를 묶고 돌아온 의견을 분류하는 과정을 살펴봤다. 외부 리뷰가 수정을 권해도 검토자가 보지 못한 코드나 실행 조건이 있을 수 있어서, 이 저장소는 리뷰 문장을 받는 단계와 로컬에서 수정 근거를 확인하는 단계를 나누고 있었다.


저장소 README는 로컬 작업 공간을 기준으로 삼고 외부 피드백은 검증할 조언으로 취급한다고 명시하고 있었다. 자료 생성 스크립트에서 외부 리뷰 준비 흐름을 확인했다. 실제 제출과 리뷰 실행은 별도 단계다. 구조화된 결과와 승인 상태는 보충 글에서 다루고, 여기서는 검토 자료, 분류표, 변경 근거가 연결되는 구조를 정리했다.


## 외부 검토에 전달할 맥락


[README](https://github.com/NAMUORI00/cross-review-bridge/blob/e0e20ea26d0c8eeb67fd3bffcf6d0422d97a2ef6/README.md)는 간단한 브리프, 더 풍부한 ZIP 묶음, 돌아온 피드백의 분류라는 세 역할을 나눈다. 별도 검토자가 전체 대화를 이미 알고 있다고 가정하지 않고 입력 자료를 만들려는 선택으로 읽혔다.


코드 차이만 보내면 변경 전제와 재현 조건이 빠질 수 있고, 저장소 전체를 보내면 검토 대상이 묻힐 수 있다. 이 저장소는 무엇을 고치려는지와 관련 파일, 확인한 결과, 아직 확인하지 못한 내용을 함께 묶는 방식을 택하고 있었고, 로컬이 실제 수정의 기준이라는 점도 문서에 명시돼 있었다.


[검토용 변경 요약 생성](https://github.com/NAMUORI00/cross-review-bridge/blob/e0e20ea26d0c8eeb67fd3bffcf6d0422d97a2ef6/skills/cross-review-bridge/scripts/New-CrossReviewBrief.ps1)은 Git 상태, diff 요약과 본문, 파일 목록, 명시적으로 포함한 파일을 모은다.


기본 diff 길이 제한이 있고, 개별 텍스트 파일도 일정 길이를 넘으면 잘렸다는 표시가 붙는다. 길이 제한에 걸린 변경은 자료에 포함되지 않으므로, 생성된 브리프가 모든 변경을 담고 있는지는 자료 생성만으로 보장되지 않았다.


## 브리프와 ZIP의 구성 범위


간단한 브리프의 git diff는 기본적으로 스테이징하지 않은 추적 파일 변경을 읽는다. 스테이징된 변경이나 추적되지 않는 파일의 본문까지 같은 diff에 들어 있다고 가정하면 누락이 생긴다. 파일 목록에 이름이 보이는 것과 내용이 포함되는 것도 다르다.


[검토 자료 묶음 생성](https://github.com/NAMUORI00/cross-review-bridge/blob/e0e20ea26d0c8eeb67fd3bffcf6d0422d97a2ef6/skills/pro-review-package-handoff/scripts/New-ProReviewPackage.ps1)은 스테이징된 diff와 그렇지 않은 diff를 따로 수집한다.


지정한 파일과 선택적으로 찾은 자료를 묶고, 포함, 제외 목록을 manifest에 남긴다. 기본 MaxFileBytes가 5MiB로 설정돼 있어서, 이보다 큰 PDF나 이미지는 묶음에서 빠지게 된다.

그림 1. 외부 검토에 사용할 입력을 만드는 경로. 출처: 두 자료 생성 스크립트와 README를 바탕으로 직접 구성. 외부 제출은 자료 생성과 별도 단계다.


비밀값처럼 보이는 텍스트를 가리는 함수도 있었다. 정해진 패턴에 맞는 문자열을 치환하는 방식이어서, 패턴에 해당하지 않는 민감 자료는 그대로 남는다. 원본 바이너리 자료를 복사하는 경로에서는 텍스트 치환이 적용되지 않으므로, 파일을 묶음에 담는 것과 공개 가능 여부를 판단하는 것은 별개 작업이었다.


## 피드백 분류와 대기 상태


[외부 의견에서 검토 항목 추출](https://github.com/NAMUORI00/cross-review-bridge/blob/e0e20ea26d0c8eeb67fd3bffcf6d0422d97a2ef6/skills/external-feedback-integrator/scripts/Convert-ExternalFeedback.ps1)은 외부 응답에서 목록 형태이거나 문제, 수정, 근거 같은 단어가 포함된 줄을 후보로 뽑는다. 최대 80개를 취하고, 후보가 없으면 본문의 앞부분을 사용한다. 원문 전체는 별도 구역에 보존한다.


이 스크립트가 만드는 행의 분류는 모두 pending이다. apply, consider, reject, needs user decision 중 하나를 자동으로 결정하거나 코드를 수정하는 기능은 없다. 이름에 Integrator가 들어 있지만, 실제 산출물은 판단을 기록할 작업표였다.


줄 단위 추출은 긴 응답에서 검토할 후보를 빠르게 모을 수 있지만, 한 주장과 그 조건이 서로 다른 줄에 걸쳐 있으면 따로 떨어질 수 있다. 표 헤더나 설명용 목록도 후보로 잡힐 수 있어서, 추출된 항목은 원문 문맥과 대조해서 읽게 된다. 80개 상한이 있으므로 이 목록이 외부 의견 전체를 빠짐없이 담고 있지는 않을 수 있다.


## 검토 의견의 근거 확인


예를 들어 외부 검토가 '이 경로는 빈 입력에서 예외가 난다'고 지적했다고 하자. 로컬에서 실제 호출 경로와 입력 검사를 읽고 재현해 봐야 수정할 문제인지 판단할 수 있다. 이미 앞단에서 빈 입력을 막고 있다면 지적의 조건을 좁히거나 채택하지 않을 이유를 남기면 되고, 실제 실패가 확인되면 해당 범위의 수정과 검증으로 이어진다.


![07-04-02.png](/images/notion/tech-07-04/image-2.png)


그림 2. 추출한 의견을 분류하고 후속 조치로 연결하는 절차. 출처: 피드백 변환 스크립트의 산출 형식과 README의 로컬 검증 원칙을 바탕으로 직접 구성. 분류와 수정은 자료를 받은 검토자가 수행할 단계다.


이 분리는 외부 모델의 말투가 강하든 조심스럽든 같은 방식으로 적용된다. 문장의 확신보다 해당 커밋에서 참인지를 기준으로 보고, 제품 방향이나 연구 범위처럼 여러 선택이 가능한 부분은 결함 판정과 나누어 기록한다. 검토 의견이 다르다는 이유만으로 모든 항목을 절충하면 원래 변경의 목적과 맞지 않는 수정이 섞일 수 있다.


## 한 번 보낸 자료와 현재 작업 공간을 맞추기


리뷰를 기다리는 동안 로컬 파일이 바뀌면 외부 의견이 가리키는 코드가 이미 달라져 있을 수 있다. 제출 자료의 커밋, diff, 포함 파일 목록과 현재 상태가 어긋나면 맥락이 맞지 않는 의견을 그대로 적용하게 된다. manifest가 이런 변경을 자동으로 추적하지는 않으므로, 후속 기록에 제출 묶음 식별자와 검토 대상 시점을 함께 남겨 두면 대조 기준이 된다.


이번에 읽은 구현은 검토 입력을 만들고 외부 의견을 작업표로 정리하는 데까지 다루고 있었다. 채택 판단과 실제 수정은 로컬 근거를 확인하는 단계로 남아 있다. 다음 글에서는 paperbanana 도구가 만든 그림을 살펴보며, 생성된 시각 자료를 원문의 주장과 대조하는 쪽으로 이어간다.


## 작업을 정리하며


리뷰 자료는 많을수록 좋기보다 주장과 근거가 바로 연결될수록 읽기 쉽다. 생성된 파일 목록과 실제 내용을 대조하고, 피드백을 받은 뒤 어떤 원문을 고칠지 식별할 수 있어야 한다. 자료 준비와 수정 이력을 같은 흐름으로 남기고 싶다.
