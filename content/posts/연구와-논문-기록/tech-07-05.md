학술 그림 작성에 사용할 PaperBanana 도구를 검토하며 CLI의 요청과 실제 그림 생성 경로를 정리했다. 입력 길이 제한, 출력 위치, 검토 횟수 설정이 각 단계에서 어떤 의미를 갖는지 확인했다.


## 구현과 확인 과정


paperbanana-codex-skill 저장소를 살펴보며, 이 도구가 학술 그림 생성 과정에서 어디까지를 담당하는지 정리했다. 그림의 화살표 하나가 실제 구현에 없는 데이터 연결을 뜻할 수 있으므로, 생성 결과는 모양뿐 아니라 원문의 입력, 출력 관계와도 대조할 필요가 있다. 코드와 문서를 읽으며 자료 준비, 생성 요청, 검토 각 단계의 실행 주체와 경계를 확인했다.


저장소의 CLI 출력이 실제 그림으로 이어지는 경로를 코드와 문서에서 확인했다. 그림 생성 실험을 새로 수행한 결과는 포함하지 않았다.


## 그림 생성 단계와 실행 주체


[PaperBanana 논문](https://arxiv.org/abs/2601.23265)은 참고 자료 검색, 내용, 스타일 계획, 렌더링, 비평을 연결하는 학술 그림 생성 방식을 제안한다. 2026년 3월 개정본에는 방법론 도식 292개 사례로 구성한 평가셋도 소개되어 있다. 이 연구의 전체 범위와 저장소의 배포 범위는 다르다.


이 저장소의 [README](https://github.com/NAMUORI00/paperbanana-codex-skill/blob/c82a3d1ca4202495fa1fad4ae6f69bd239caba64/README.md)는 Planner → Stylist → Visualizer → Critic을 호스트 대화에서 수행하는 구성이라고 설명한다.


원본의 전체 실행 환경이나 벤치마크를 묶지 않고, 스타일 가이드와 입력을 정리하는 CLI를 제공하는 구성이다. 별도 외부 텍스트, 시각 모델 API 설정을 줄이기 위한 배포 선택으로 보인다.


여기서 keyless는 이 CLI가 별도 외부 API 키를 요구하지 않는다는 범위를 가리킨다. 그림을 생성하는 호스트 기능의 접근 권한, 사용량, 비용은 별도로 존재한다. 함수가 출력하는 requires_host_image_generation 값도 true다.


## 생성 요청의 입력과 출력


[그림 제작 요청 구성 도구](https://github.com/NAMUORI00/paperbanana-codex-skill/blob/c82a3d1ca4202495fa1fad4ae6f69bd239caba64/paperbanana/scripts/paperbanana_cli.py)의 generate는 workflow와 같은 처리 함수로 연결된다.


이 함수는 JSON을 출력하고 종료한다. planner_prompt, stylist_prompt, render_requests, critic_prompt가 담기지만, 이미지 생성 도구를 직접 호출하지는 않는다.


가령 output을 figure.png, 후보 수를 3으로 주면 figure_0.png부터 figure_2.png까지의 경로가 outputs에 들어간다. 이 목록은 앞으로 파일을 저장할 위치를 지정한다. 생성 완료 여부는 해당 파일로 확인한다. 후보별 레이아웃을 제안하는 문장을 생성하며, 실제 이미지의 다양성과 품질은 결과물을 보고 검토해야 한다.

그림 1. CLI 출력과 실제 이미지 생성 사이의 실행 경계. 출처: README와 그림 제작 요청 구성 도구의 호출 경로를 바탕으로 직접 구성. 호스트의 후속 실행이 있어야 이미지 산출물이 생긴다.


단계를 나눈 방식에는 실용적인 이유가 있다. 무엇을 그릴지 정하는 단계와 어떻게 배치할지 정하는 단계를 분리하면, 시각적 변경이 의미까지 바꾸는 문제를 따로 검토할 수 있다. 앞 단계 결과를 다음 단계 입력으로 연결하는 작업은 실행 주체가 맡는다. Stylist 요청에는 이전 Planner 출력을 사용하라는 문장이 들어가고, 실제 연결은 호스트가 수행한다.


## 원문 전달 범위와 길이 제한


clip_text는 입력 길이가 한도를 넘으면 뒤를 자르고 표시를 붙인다. Planner에는 원문을 최대 16,000자, Stylist에는 최대 10,000자, 렌더링과 Critic 요청에는 각각 최대 12,000자까지 넣는다. content_length는 원래 입력 길이를 기록하며, 각 요청에 포함되는 내용은 해당 단계의 길이 제한을 따른다.


예를 들어 원문 뒷부분에 '실선은 구현 경로, 점선은 제안 경로'라는 조건이 있는데 그 부분이 잘렸다고 해 보자. 앞부분만 받은 생성 요청에서는 두 종류의 화살표가 같은 의미로 표현될 수 있다. 길이 제한 구조에서 도출한 검토 사례다. 긴 논문 전체를 넣기보다 해당 그림에 필요한 문단과 표기 규칙을 먼저 추려서 넣는 편이 이 입력 구조에 맞다.


max_critic_rounds도 구분해서 읽었다. JSON과 비평 요청에 반복 상한을 담지만, CLI 내부에 이미지 재생성과 비교를 반복하는 루프는 없다. 값 2는 검토 횟수 설정이며 수행 여부는 실행 기록으로 확인한다. 요청한 횟수, 수행한 횟수, 수정된 산출물은 각각 별도로 기록되어야 구분된다.


## 입출력 검사와 시각 검토


[테스트 파일](https://github.com/NAMUORI00/paperbanana-codex-skill/blob/c82a3d1ca4202495fa1fad4ae6f69bd239caba64/tests/test_paperbanana_cli.py)은 명령 목록, 필요한 입력, 화면 비율 제한, 후보 경로, JSON 필드를 확인한다.


polish 검사에는 실제 이미지가 아닌 임시 바이트 파일을 쓰는 사례도 있다. 경로와 요청 형식을 확인하는 계약 검사다. 그림의 내용과 의미는 별도 검토 대상이다.


doctor 역시 필요한 배포 파일의 존재와 불필요한 원본 묶음 포함 여부를 확인한다. 이 검사가 통과하더라도 현재 호스트의 이미지 생성 호출이나 그림의 글자 가독성은 별도 확인 대상이다. 이 글에서는 테스트 코드를 읽은 범위까지만 다루었고, 실행 통과 여부나 그림 품질에 대한 측정 결과는 포함하지 않았다.

## 그림의 완성도와 주장의 강도를 함께 맞추기


[평가 설명](https://github.com/NAMUORI00/paperbanana-codex-skill/blob/c82a3d1ca4202495fa1fad4ae6f69bd239caba64/paperbanana/references/evaluation-protocol.md)은 충실성, 가독성, 간결성, 미적 구성을 구분한다.


원문에 맞는지와 읽을 수 있는지는 서로 다른 검토 항목으로 읽었다. 화살표의 연결이 틀렸다면 색과 간격을 정돈해도 설명하는 시스템은 원문과 달라질 수 있다.


수치 그래프라면 한 단계가 더 필요하다. 코드의 plot 요청에는 수치를 보존하라는 문장이 있지만, 좌표와 원자료를 계산해 대조하는 구현은 없다. 측정값을 공유하는 경우 원자료로 그래프를 그리고, 생성형 도구는 개념 설명용 시각 자료 범위에서 사용하는 편이 근거 추적에 유리하다.


이 저장소에서 확인한 구현은 생성과 검토에 필요한 입력을 일정한 형식으로 만드는 데 집중되어 있었다. 원문 버전별로 그림과 수정 내용을 함께 보관하는 작업은 후속 검토 항목으로 남았다. 화살표와 표기의 변경 이력이 있으면 시각적인 정돈과 설명의 정확성을 각각 비교할 수 있다.


## 작업을 정리하며


그림 생성에서는 파일이 만들어진 상태와 원문의 의미를 옮긴 상태를 나누어 확인해야 한다. 화살표와 구성요소를 원문의 입력, 출력에 대조하는 과정이 특히 중요하다. 도구가 준비한 요청과 사람이 수행할 검토를 명확하게 연결하려 한다.
