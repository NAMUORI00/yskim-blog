학술 논문에 들어가는 구조도에서는 화살표 하나가 실제 구현에 없는 데이터 흐름을 뜻할 수 있다. 그래서 그림 생성 도구가 만든 결과물은 겉모양만 볼 것이 아니라, 원문에 적힌 입력과 출력 관계에 맞는지 대조해야 한다. 논문 그림 작업에 쓸 도구를 찾으면서 `paperbanana-codex-skill` 저장소의 코드와 문서를 읽었다. 이 도구가 자료 준비와 생성 요청, 결과 검토 가운데 어디까지를 맡는지 확인해 보았다.


이번에는 글자 명령으로 실행하는 **명령줄 도구**(CLI)의 출력이 어떤 경로를 거쳐 실제 그림으로 이어지는지 추적했다. 코드와 문서를 기준으로 입력 길이 제한, 파일 출력 위치, 검토 횟수 설정이 각 단계에서 어떤 역할을 하는지 구분해 보았다. 이 과정에서 실제 그림 생성 실험이나 테스트 코드 실행은 따로 하지 않았다.


## 논문과 저장소의 범위 차이


이 도구의 바탕이 된 [PaperBanana 논문](https://arxiv.org/abs/2601.23265)은 학술 그림을 자동으로 생성하는 다섯 단계 과정을 다룬다. 참고 자료 검색, 내용 계획, 스타일 계획에 이어 실제 그림을 그리는 **렌더링**(rendering)과 비평(`Critic`)을 거친다. 2026년 3월 개정본에는 방법론 도식 292개 사례를 모은 평가 자료(평가셋)도 함께 실려 있다. 다만 논문이 제안한 전체 작업 흐름과 `paperbanana-codex-skill` 저장소가 배포하는 범위는 다르다.


저장소의 [README](https://github.com/NAMUORI00/paperbanana-codex-skill/blob/c82a3d1ca4202495fa1fad4ae6f69bd239caba64/README.md)를 보면 `Planner` → `Stylist` → `Visualizer` → `Critic`으로 이어지는 네 단계가 나온다. 이 네 단계는 도구를 불러 쓰고 대화를 진행하는 주체인 **호스트**(host) 대화 환경에서 수행된다. 논문 원본의 전체 실행 환경이나 성능 비교 자료(벤치마크)를 그대로 묶는 대신, 스타일 가이드와 입력 자료를 정리해 주는 CLI만 따로 두었다. 외부 텍스트 모델이나 시각 모델 연결(API)을 따로 설정하는 부담을 줄이려는 배포 방식으로 보인다.


문서에 적힌 `keyless`라는 표현도 이러한 역할 분담에서 뜻이 드러난다. CLI 자체가 외부 API 키를 요구하지 않는다는 뜻일 뿐, 실제로 그림을 그리는 호스트 기능의 접근 권한이나 사용량 한도, 비용은 별개로 남는다. 실제로 CLI 함수가 항목과 값을 짝지어 돌려주는 **JSON**에서도 `requires_host_image_generation` 값은 `true`로 설정된다.


## 생성 요청 조립과 실행 경계


그림 생성을 호스트에 맡기는 구조에서 CLI가 어디까지 작업하는지는 [그림 제작 요청 구성 도구](https://github.com/NAMUORI00/paperbanana-codex-skill/blob/c82a3d1ca4202495fa1fad4ae6f69bd239caba64/paperbanana/scripts/paperbanana_cli.py)(`paperbanana_cli.py`)에서 확인할 수 있다. 이 파일의 `generate` 명령은 내부적으로 `workflow`와 같은 처리 함수로 이어진다. 처리 함수는 이미지 생성 도구를 직접 호출하지 않고, 인공지능에 건넬 단계별 지시문인 **프롬프트**(prompt)를 담은 JSON만 출력한 뒤 종료한다. 출력된 JSON 안에는 `planner_prompt`, `stylist_prompt`, `render_requests`, `critic_prompt`가 들어간다.


예를 들어 출력 경로인 `output`에 `figure.png`를 주고 후보 수를 3으로 지정해 실행했다고 해 보자. 이때 출력된 JSON의 `outputs` 항목에는 `figure_0.png`부터 `figure_2.png`까지의 경로 목록이 담긴다. 이 목록은 파일이 이미 생성되었다는 뜻이 아니라 앞으로 호스트가 이미지를 저장할 예정 위치를 나타낸다. CLI는 후보별 화면 배치를 제안하는 문장까지만 만들고, 파일 생성 여부와 실제 이미지 품질은 호스트가 생성을 마친 뒤 결과 파일을 열어 확인해야 한다.


![원문과 스타일 가이드를 받아 JSON 요청과 경로만 출력하는 CLI 영역과, 이를 받아 계획 정리부터 이미지 생성 호출 및 원문 대조를 수행하는 호스트 영역을 좌우로 나눈 흐름도](/images/notion/tech-07-05/image-1.png)


그림 1. CLI의 JSON 출력과 호스트의 실제 이미지 생성 사이의 실행 경계(출처: README와 `paperbanana_cli.py` 호출 경로를 바탕으로 직접 구성).


생성 과정을 이처럼 여러 단계로 나누어 둔 데에는 실용적인 이유가 있다. 무엇을 그릴지 정하는 단계와 어떻게 배치할지 정하는 단계를 분리하면, 시각적 표현을 다듬는 과정에서 원래 의미까지 바뀌지 않았는지 따로 짚어볼 수 있다. 다만 앞 단계의 출력을 다음 단계의 입력으로 넘기는 일은 실행 주체인 호스트가 맡는다. `Stylist` 프롬프트에는 이전 `Planner` 출력을 참고하라는 지시가 들어가지만, 두 단계의 데이터를 실제로 이어 주는 작업은 호스트 대화에서 이루어진다.


## 단계별 입력 길이 제한과 검토 횟수 설정


호스트가 각 단계를 순서대로 이어 주더라도, CLI에 긴 원문을 넣을 때는 문자열을 자르는 `clip_text` 함수의 동작을 고려해야 한다. 이 함수는 입력 길이가 단계별 한도를 넘으면 뒷부분을 잘라내고 생략 표시를 붙인다. 원문은 `Planner` 요청에 최대 16,000자, `Stylist` 요청에 최대 10,000자, 렌더링과 `Critic` 요청에 각각 최대 12,000자까지 들어간다. JSON의 `content_length` 항목에는 잘리기 전의 원래 입력 길이가 기록되지만, 실제 각 단계 프롬프트에는 한도만큼 잘린 본문만 전달된다.


![긴 원문 입력이 clip_text 함수를 거치며 Planner 16,000자, Stylist 10,000자, 렌더링과 Critic 12,000자 한도로 잘리고 원문 뒷부분 표기 규칙이 누락될 수 있음을 보여 주는 도식](/images/notion/tech-07-05/image-2.png)


그림 2. clip_text 함수의 단계별 입력 길이 제한과 긴 원문 입력 시 뒷부분 표기 규칙이 잘리는 구조도.


예를 들어 원문 뒤쪽에 "실선은 구현 경로, 점선은 제안 경로"라는 표기 규칙이 있는데 글자 수 제한에 걸려 잘렸다고 해 보자. 앞부분만 전달받은 생성 요청에서는 실선과 점선의 구분이 사라져 두 화살표가 같은 의미로 그려질 수 있다. 이처럼 원문 뒷부분에 적힌 조건이 누락될 수 있으므로, 논문 전체를 그대로 넣기보다 그림과 관련된 문단과 표기 규칙을 먼저 추려서 입력하는 편이 안전하다.


비평 반복 상한을 뜻하는 `max_critic_rounds` 설정도 실제 동작 범위를 구분해 두어야 한다. 이 값을 `2`로 주면 JSON 출력과 비평 프롬프트에 반복 상한이 적히지만, CLI 내부에 이미지를 다시 만들고 비교하는 반복문이 들어 있지는 않다. 설정값은 호스트에 전달하는 목표 횟수일 뿐이므로, 실제로 비평과 재생성이 몇 번 이루어졌는지는 실행 기록과 수정된 이미지 산출물을 따로 남겨야 확인할 수 있다.


## 입출력 계약 검사와 별도 확인 항목


CLI가 요청서 조립까지만 맡는다는 점은 저장소의 [테스트 파일](https://github.com/NAMUORI00/paperbanana-codex-skill/blob/c82a3d1ca4202495fa1fad4ae6f69bd239caba64/tests/test_paperbanana_cli.py)(`test_paperbanana_cli.py`)에서도 드러난다. 예를 들어 이미지를 다듬는 `polish` 명령 테스트에는 실제 그림 파일이 아니라 임시 바이트 파일을 넣어 검사하는 사례가 있다. 파일 경로와 요청 형식이 정해진 규격에 맞는지만 보는 **입출력 계약** 검사이기 때문이다. 이 테스트 파일의 다른 검사들도 지원 명령 목록, 필수 입력값, 화면 비율 제한, 후보 파일 경로, JSON 출력 항목을 확인한다.


환경 점검 명령인 `doctor` 역시 배포에 필요한 파일이 있는지, 불필요한 원본 묶음이 섞여 있지 않은지를 확인하는 수준에 머문다. 테스트 코드를 읽으며 확인한 바로는, 이러한 검사가 모두 통과하더라도 현재 호스트 환경에서 이미지 생성 도구를 호출할 수 있는지는 알 수 없다. 생성된 그림의 글자가 잘 읽히는지, 내용이 원문과 맞는지도 사람이 별도로 확인해야 한다.


![기본 명령, polish, doctor 검사가 다루는 CLI 테스트 검증 범위와 호스트 이미지 생성 호출, 원문 일치, 가독성 등 별도 확인 대상을 좌우로 비교한 도식](/images/notion/tech-07-05/image-3.png)

## 평가 기준과 원문 대조 검토


자동 검사가 다루지 않는 그림의 품질과 원문 일치 여부는 저장소의 [평가 설명](https://github.com/NAMUORI00/paperbanana-codex-skill/blob/c82a3d1ca4202495fa1fad4ae6f69bd239caba64/paperbanana/references/evaluation-protocol.md)(`evaluation-protocol.md`) 문서에 정리된 기준으로 검토할 수 있다. 이 문서는 그림을 검토할 때 충실성, 가독성, 간결성, 미적 구성을 나누어 본다. 화살표 방향이나 모듈 연결이 틀렸다면, 색감과 여백을 아무리 깔끔하게 정돈해도 그림이 설명하는 시스템은 원문과 달라진다. 원문 내용과 맞는지 따지는 충실성과 눈으로 읽기 편한지 보는 가독성이 서로 다른 기준이기 때문이다.


![원문의 연결과 수치 및 후보 그림을 대응표로 묶어 원문 의미 일치 여부를 먼저 판단하고, 통과하면 겹침과 가독성을 확인해 선택 그림과 검토 기록으로 남기는 순서도](/images/notion/tech-07-05/image-4.png)


그림 4. 후보 그림의 요소를 원문과 대조해 검토하고 기록하는 절차(출처: 저장소의 그림 검토 절차 문서를 바탕으로 구성한 검토 예시).


수치를 다루는 그래프(`plot`) 요청에서는 한 가지를 더 주의해야 한다. 코드가 만드는 `plot` 프롬프트에는 수치를 보존하라는 문장이 들어가지만, 생성된 이미지의 좌표와 원래 데이터를 계산해 대조하는 기능은 구현되어 있지 않다. 실험 측정값을 정확히 전달해야 할 때는 원자료로 직접 그래프를 그리고, 생성형 도구는 시스템 구조나 개념을 설명하는 도식에 한정해 쓰는 편이 근거를 추적하기 좋다.


## 결론


`paperbanana-codex-skill`은 그림 생성과 검토에 필요한 단계별 프롬프트와 예정 경로를 일정한 JSON 형식으로 묶어 내는 데 초점을 둔 도구다. 원문을 단계별 길이 한도에 맞춰 자르고 요청 규격을 구성하는 일은 CLI가 맡지만, 각 단계를 이어서 이미지를 만들고 반복 비평을 수행하는 일은 호스트의 몫으로 남는다.


이번 검토에서는 코드와 문서만으로 동작 경로와 검사 범위를 확인했으며, 실제 그림 생성 실험이나 테스트 코드 실행은 수행하지 않았다. 도구가 요청서와 예정 경로를 만들어 주더라도, 파일이 생성된 상태와 원문의 의미가 정확히 옮겨진 상태는 구분해서 확인해야 한다. 앞으로 실제 논문 작업에 쓸 때는 원문 버전별 후보 그림과 화살표나 표기의 수정 이력을 함께 남겨, 시각적 정돈과 의미 수정을 비교해 볼 생각이다.
