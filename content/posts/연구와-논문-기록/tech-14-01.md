학위논문 작업에서는 원고와 그림, 빌드 환경을 함께 관리했다. 상위 프로젝트와 논문 저장소의 커밋이 분리돼 있고 그림 원본과 변환 결과도 다른 파일로 남아, 수정한 자료가 최종 PDF에 반영되는 경로를 정리했다.


## 원고와 그림을 관리하는 방식


학위논문 저장소를 다시 살펴보며 원고와 그림이 관리되는 방식을 정리해 봤다. 본문은 LaTeX로 작성되어 있었고, 일부 그림은 HTML에서 PDF로 변환한 뒤 본문에 넣는 구조였다.


그림을 수정할 때는 원본 HTML과 변환된 PDF를 함께 확인할 필요가 있었다. 본문을 다시 빌드하는 과정에는 그림 변환이 포함되어 있지 않아, 원본만 고치면 이전 그림이 그대로 들어갈 수 있었다.


두 저장소 사이의 자동 동기화는 확인되지 않았다. 한쪽은 LaTeX 원고, 그림, 참고문헌을 관리하고 다른 쪽에는 작성 중인 Markdown 초안이 남아 있었다. 각각 어떤 자료를 담고 있는지부터 나누어 읽었다.


Git 커밋은 파일 묶음의 특정 상태를 가리킨다. 원고 커밋과 실험 코드 커밋을 함께 기록하면 표의 숫자를 해당 실행에 연결할 수 있다. 이 관계를 기준으로 원고의 결과 기록을 살펴봤다.


## LaTeX 원고와 Markdown 초안


확인한 `JNU-THESIS`의 README는 `main.tex`를 단일 원고로 정하고, `refs.bib`, 그림 파일, 빌드 설정을 함께 관리한다고 설명한다. 시스템 저장소가 이 저장소를 `paper/` 하위 모듈로 참조한다는 관계도 명시되어 있다.


논문 저장소 자체에는 시스템, 실험 코드를 포함하지 않는다는 범위가 붙어 있었다. [원고 관리 규칙](https://github.com/NAMUORI00/JNU-THESIS/blob/413cf53ed582594dc3daae7cfadc0a2d3905ca40/README.md)


상위 저장소는 하위 모듈로 논문 저장소의 특정 커밋을 참조한다. 상위 저장소의 `main`과 논문 저장소의 `main`은 각각의 이력으로 관리된다. 시스템과 원고의 대응 관계는 상위 커밋에 기록된 하위 모듈 커밋으로 읽을 수 있었다. [Git 하위 모듈 문서](https://git-scm.com/docs/gitsubmodules)


반면 확인한 `jejunu-masters-thesis`의 Markdown 원고에는 서론과 관련 연구가 있고, 방법론, 실험 결과, 결론은 ‘추후 작성’으로 남아 있었다. 학위논문 전체의 완성도는 이 파일과 각 장, 그림, 실험 자료를 함께 대조해야 했다. 두 저장소 사이의 자동 변환, 동기화 경로도 이번에 확인한 파일에서는 찾지 못했다.


따라서 이 글에서는 별도로 남아 있는 초안과 단일 LaTeX 원고의 역할을 나누어 기록했다. [Markdown 원고의 작성 범위](https://github.com/NAMUORI00/jejunu-masters-thesis/blob/675102c15606844d097ec17759986d10bfa26cdd/papers/masters-thesis.md)

## 그림 변환과 논문 빌드


원고 빌드는 `latexmkrc`에서 pdfLaTeX와 `main.tex`를 기본으로 지정한다. README에는 환경 차이를 줄이기 위해 한글용 kotex-utf와 TeX Live 글꼴을 사용한다고 적혀 있다. 이는 문서에 남은 선택 이유다. 서로 다른 환경에서 PDF가 바이트 단위로 같은지는 별도 비교가 필요하다.


참고문헌은 본문의 인용 키와 `refs.bib` 항목을 연결한다. 이 저장소의 `sorting=none` 설정에서는 처음 인용한 순서가 번호에 영향을 준다. 문단을 옮겼을 때 참고문헌 번호가 바뀌는 것은 오류가 아닐 수 있다.


인용 키로 연결한 본문에서는 문단 순서가 바뀌어도 참고문헌 연결을 유지할 수 있다. latexmk는 LaTeX와 참고문헌 처리에 필요한 반복 실행을 관리한다. [latexmk 설명](https://ctan.org/tex-archive/support/latexmk?lang=en)


그림에는 별도의 경로가 있었다. 그림을 PDF로 변환하는 처리는 HTML을 Edge 또는 Chrome의 headless 인쇄로 PDF로 바꾸고, 파일 존재와 크기를 확인한다. 본문은 그렇게 만들어진 그림 PDF를 `includegraphics`로 삽입한다.


HTML을 수정한 뒤 그림 PDF를 갱신하지 않으면 본문 빌드는 성공해도 이전 그림이 들어갈 수 있다. [그림 변환 코드](https://github.com/NAMUORI00/JNU-THESIS/blob/413cf53ed582594dc3daae7cfadc0a2d3905ca40/figures/src/render_figures.py)


GitHub Actions는 LaTeX 빌드 뒤 `main.pdf`의 존재를 확인해 업로드한다. HTML 그림을 다시 렌더링하는 단계는 없었다. 그림 PDF 갱신은 본문 빌드에 앞선 별도 작업이며, 최종 문서의 그림, 캡션, 잘림은 결과 PDF에서 확인할 항목으로 남는다.

## 실험 결과와 원고 버전의 연결


작은 예로 원고 커밋 A가 시스템 커밋 B의 실험표를 담고 있다고 생각해 보았다. 이후 프로그램이 C로 바뀌어도 A에 있는 표가 저절로 C의 성능이 되지는 않는다. 원고 버전과 측정 대상 버전이 모두 필요한 이유다.


실제 `main.tex`에는 결과표 구간을 표시하는 `BEGIN GENERATED TABLE` 주석과 실행 식별 기록이 있다. 상태 재검토 비교는 `confirmatory-v2-20260831-61024aa`에 귀속시키고, 결정론적 생성기와 정해진 시나리오의 한계를 명시한다.


자연어 품질이나 실제 생성 비용을 측정하지 않았다는 설명도 함께 남아 있다. [원고의 결과 및 한계](https://github.com/NAMUORI00/JNU-THESIS/blob/413cf53ed582594dc3daae7cfadc0a2d3905ca40/main.tex)


일부 검색, 영상 결과의 실행 식별 대조표는 `[TBD]`로 남아 있었다. 원고의 표가 채워진 범위와 수치의 재현 경로가 연결된 범위는 달랐다. 결과 구간 표시는 자동 생성의 실행 증거까지 제공하지 않아, 이번에는 원고에 기록된 연결 규칙과 식별 정보까지 확인했다.


원고를 다시 만들 때 함께 살펴볼 자료는 본문 버전, 그림 원본과 변환본, 빌드 설정, 실험 결과의 식별 정보였다. 다음 글에서는 영상 질의응답 원고의 평가 집단과 판정 규칙을 읽으며 보고된 수치의 범위를 정리한다.
