학위논문을 쓸 때는 글자 배치와 수식을 코드로 적는 조판 도구인 LaTeX을 많이 사용한다. 본문 원고 파일에 그림과 참고문헌을 합쳐 최종 논문 파일(`main.pdf`)로 만드는 과정을 문서 **빌드**(build)라고 부른다. 이 논문을 작성할 때는 본문 원고와 그림, 참고문헌, 실험 코드를 한 파일에 모아 두지 않았다. 시스템을 구현한 코드는 상위 저장소에 두고 LaTeX 논문 원고는 별도 저장소로 분리했다. 본문에 넣을 일부 그림도 웹 문서 형식인 HTML로 먼저 만든 뒤 PDF로 변환해 끼워 넣었다.


이처럼 파일과 저장소가 나뉘어 있으면 그림 원본이나 실험 코드를 고쳐도 최종 논문 파일(`main.pdf`)에 저절로 반영되지 않는다. 어떤 저장소가 실제 본문을 맡는지, 수정한 그림과 실험 결과가 어떤 단계를 거쳐 최종 PDF까지 이어지는지 저장소 설정과 빌드 구성을 따라가며 확인했다.


## 원고 저장소와 하위 모듈 연결


최종 PDF가 만들어지는 경로를 따라가려면 먼저 두 곳으로 나뉜 원고 저장소 가운데 어디가 실제 본문을 맡는지 구분해야 한다. 논문 관련 파일은 LaTeX 원고 저장소인 `JNU-THESIS`와 Markdown 초안이 담긴 `jejunu-masters-thesis`에 나뉘어 있었다. 두 저장소 사이에 파일을 자동으로 맞춰 주는 동기화 설정이 보이지 않았기 때문에 각 저장소의 역할과 작성 범위부터 확인했다.


`JNU-THESIS` 저장소는 [원고 관리 규칙](https://github.com/NAMUORI00/JNU-THESIS/blob/413cf53ed582594dc3daae7cfadc0a2d3905ca40/README.md)을 적은 `README.md`에서 `main.tex`를 단일 원고로 지정한다. 이 저장소는 본문 원고와 참고문헌 파일(`refs.bib`), 그림 파일, 문서 빌드 설정만 관리하고 시스템 구현이나 실험 코드는 담지 않는다. 대신 시스템을 구현한 상위 저장소가 `JNU-THESIS`를 `paper/` 폴더 경로에 Git **하위 모듈**(submodule)로 연결해 참조한다.


버전 관리 도구인 Git은 특정 시점의 파일 묶음 상태를 커밋(commit)이라는 기록으로 남긴다. 하위 모듈을 쓰면 외부 저장소의 파일을 통째로 복사해 오지 않고, 하위 폴더 자리에 가져다 쓸 커밋 식별자만 적어 둘 수 있다. 상위 시스템 저장소의 `main` 브랜치와 `JNU-THESIS`의 `main` 브랜치는 각자의 변경 이력을 따로 쌓는다. 그러면서 상위 저장소의 커밋에 기록된 `paper/` 하위 모듈 커밋을 보면 당시 시스템 코드가 어느 시점의 논문 원고와 짝을 이루는지 알 수 있다. 자세한 동작 방식은 [Git 하위 모듈 문서](https://git-scm.com/docs/gitsubmodules)에 나와 있다.


반면 `jejunu-masters-thesis` 저장소의 [Markdown 원고의 작성 범위](https://github.com/NAMUORI00/jejunu-masters-thesis/blob/675102c15606844d097ec17759986d10bfa26cdd/papers/masters-thesis.md)를 확인해 보니 `papers/masters-thesis.md` 파일에는 서론과 관련 연구만 적혀 있었다. 방법론과 실험 결과, 결론은 '추후 작성'으로 비어 있었다. 확인한 파일 안에서는 이 Markdown 초안을 `JNU-THESIS`의 LaTeX 본문으로 자동 변환하거나 동기화하는 경로도 찾지 못했다. 학위논문 전체의 완성도는 이 파일과 각 장, 그림, 실험 자료를 함께 대조해야 했으므로 별도 초안과 단일 LaTeX 원고의 역할을 나누어 정리했다.

## 본문 조판과 참고문헌 번호 계산


단일 원고 저장소인 `JNU-THESIS`에서 본문과 참고문헌을 PDF로 만드는 규칙은 `latexmkrc` 설정 파일에 적혀 있다. 기본 조판 엔진은 pdfLaTeX이고 빌드를 시작하는 문서는 `main.tex`다. 저장소 설명 문서에는 실행 환경이 달라도 조판 차이를 줄이려고 한글 패키지인 `kotex-utf`와 TeX Live 기본 글꼴을 썼다는 이유가 적혀 있다. 다만 운영체제나 빌드 환경이 달라졌을 때 생성된 PDF 파일이 바이트 단위까지 똑같은지는 별도로 비교해 보지 않았다.


본문에서 참고문헌을 가리킬 때는 번호를 직접 적는 대신 `refs.bib`에 등록한 문헌별 고유 이름표인 **인용 키**(citation key)를 넣는다. 이 저장소는 참고문헌 정렬 옵션을 `sorting=none`으로 설정해 두었다. 이 설정에서는 문헌 목록이 저자 이름순이나 연도순이 아니라 본문에서 처음 인용된 순서대로 번호를 받는다. 따라서 본문 문단의 순서를 바꿨을 때 참고문헌 번호가 바뀌는 현상은 빌드 오류가 아니라 설정에 따른 동작일 수 있다. 문단 위치를 옮기더라도 본문과 문헌 목록이 인용 키로 연결되어 있으면 문헌 대응 관계는 깨지지 않는다. LaTeX는 본문 조판과 참고문헌 번호 계산을 한 번에 끝내지 못해 여러 번 반복 실행해야 하는데, 이 반복 과정은 빌드 도구인 `latexmk`가 맡는다. 자세한 동작은 [latexmk 설명](https://ctan.org/tex-archive/support/latexmk?lang=en)에 정리되어 있다.

## HTML 그림 변환과 본문 빌드의 분리


`latexmk`가 한꺼번에 처리하는 본문 글자나 참고문헌과 달리, 그림 파일은 본문 빌드와 분리된 별도 변환 과정을 거친다. 본문에 들어가는 일부 그림은 HTML로 먼저 작성한 뒤 [그림 변환 코드](https://github.com/NAMUORI00/JNU-THESIS/blob/413cf53ed582594dc3daae7cfadc0a2d3905ca40/figures/src/render_figures.py)인 `figures/src/render_figures.py`를 실행해 PDF로 바꾼다. 이 코드는 웹 브라우저인 Edge나 Chrome을 화면 창 없이 배경에서 실행하는 **헤드리스**(headless) 인쇄 기능으로 HTML을 PDF로 출력한다. 출력이 끝나면 결과 파일이 실제로 만들어졌는지와 파일 크기가 정상인지 함께 검사한다. `main.tex` 본문은 이렇게 만들어진 그림 PDF 파일을 `includegraphics` 명령으로 불러와 문서에 끼워 넣는다.


여기서 주의할 점은 본문을 빌드하는 과정에 HTML 그림 변환이 들어 있지 않다는 것이다. 원본 HTML을 고쳤더라도 `render_figures.py`를 먼저 실행해 그림 PDF를 갱신하지 않으면 본문 빌드는 오류 없이 끝난다. 하지만 완성된 문서에는 수정 전의 이전 그림 PDF가 그대로 들어간다.


저장소에 설정된 자동 [빌드 워크플로](https://github.com/NAMUORI00/JNU-THESIS/blob/413cf53ed582594dc3daae7cfadc0a2d3905ca40/.github/workflows/build.yml)(`.github/workflows/build.yml`)에서도 이 분리 구조는 똑같다. GitHub Actions는 LaTeX 빌드를 실행해 `main.pdf`가 생성되었는지 확인하고 파일을 업로드한다. 이때도 HTML 그림을 다시 PDF로 변환하는 단계는 거치지 않는다. 따라서 그림 PDF를 갱신하는 일은 본문 빌드보다 앞서 수행해야 하는 별도 작업이다. 빌드가 끝난 뒤에는 완성된 `main.pdf`를 직접 열어 그림과 캡션이 제대로 들어갔는지, 가장자리가 잘리지 않았는지 확인해야 한다.


![그림 HTML 수정 후 render_figures.py를 실행해 갱신된 그림 PDF를 만든 뒤 main.tex, refs.bib와 함께 LaTeX 빌드를 거쳐 main.pdf를 생성하고 확인하는 흐름도](/images/notion/tech-14-01/image-3.png)

## 실험 결과표와 실행 식별자 연결


HTML 그림과 마찬가지로 본문에 들어가는 실험 결과표도 원고 버전과 따로 움직일 수 있다. 예를 들어 논문 원고의 커밋 A에 시스템 코드 커밋 B를 실행해 얻은 결과표가 적혀 있다고 해 보자. 이후 시스템 코드를 고쳐 커밋 C를 만들더라도 원고 커밋 A에 적힌 표의 숫자가 저절로 커밋 C의 성능이 되지는 않는다. 표에 적힌 수치가 어떤 코드와 실행 결과에서 나왔는지 추적하려면 원고 버전과 측정 대상의 실행 기록을 함께 남겨야 한다.


실제 `main.tex` 본문을 보면 실험 결과표가 들어가는 구간에 `BEGIN GENERATED TABLE`이라는 주석을 달고 실행 식별 정보를 함께 적어 두었다. 그중 상태 재검토 비교 실험은 실행 식별자 `confirmatory-v2-20260831-61024aa`에서 나온 결과라고 밝히고 있다. 같은 구간에는 같은 입력에 항상 같은 결과를 내는 결정론적 생성기와 정해진 시나리오를 사용했다는 실험 조건도 적혀 있다. 이와 함께 자연어 품질이나 실제 생성 비용은 측정하지 않았다는 한계도 밝혀 두었다. 자세한 본문 기록은 [원고의 결과 및 한계](https://github.com/NAMUORI00/JNU-THESIS/blob/413cf53ed582594dc3daae7cfadc0a2d3905ca40/main.tex)에서 볼 수 있다.


다만 본문에 실린 모든 결과표에 실행 식별자가 채워져 있지는 않았다. 일부 검색 실험과 영상 결과의 실행 식별 대조표는 아직 추후 기입을 뜻하는 `[TBD]`로 비어 있었다. 본문 표에 실험 수치가 채워진 범위와, 그 수치를 다시 얻을 수 있는 재현 경로가 연결된 범위 사이에 차이가 있었다. 또한 원고 안에 `BEGIN GENERATED TABLE`이라는 구간 표시가 적혀 있다고 해서 그 표가 실제로 자동 생성되었다는 실행 증거까지 보장되지는 않는다. 이번에는 원고에 적힌 연결 규칙과 식별 정보가 채워진 범위까지만 확인했다.


![시스템 커밋 B의 실행 식별자 confirmatory-v2-20260831-61024aa가 main.tex의 상태 재검토 비교표에 연결되어 있고, 이후 시스템 커밋 C는 자동 반영되지 않으며, 일부 검색과 영상 결과 대조표는 실행 식별자가 TBD로 남아 있는 구조](/images/notion/tech-14-01/image-4.png)

## 결론


지금까지 분리된 저장소와 파일들이 어떤 단계를 거쳐 최종 논문 파일(`main.pdf`)로 합쳐지는지 확인했다. 실제 논문 본문은 `JNU-THESIS` 저장소의 `main.tex`가 담당하며, 상위 시스템 저장소는 `paper/` 하위 모듈의 커밋 기록으로 원고 버전을 참조한다. 본문 조판과 참고문헌 번호 계산은 `latexmk`가 반복 실행하며 처리한다. 하지만 HTML 그림을 PDF로 바꾸는 `render_figures.py`는 본문 빌드나 자동 워크플로에 들어 있지 않아 따로 먼저 실행해야 한다. 실험 결과표 가운데 상태 재검토 비교표는 실행 식별자 `confirmatory-v2-20260831-61024aa`를 통해 실험 조건 및 한계와 연결되어 있었다.


반면 별도 Markdown 초안을 LaTeX 본문과 자동 동기화하는 경로는 찾지 못했고, 빌드 환경에 따라 PDF가 바이트 단위까지 같은지도 비교하지 않았다. 또한 일부 검색과 영상 결과 대조표는 실행 식별자가 `[TBD]`로 비어 있었고, 주석 표시만으로 표가 자동 생성되었는지도 확인할 수 없었다. 따라서 학위논문 PDF를 다시 만들고 근거를 대조할 때는 `main.tex` 본문 버전, HTML 그림 원본과 변환된 PDF를 먼저 맞춰 보아야 한다. 이와 함께 `latexmkrc`와 워크플로 빌드 설정, 결과표에 적힌 실험 실행 식별 정보까지 대조해야 한다. 다음 글에서는 영상 질의응답 원고의 평가 집단과 판정 규칙을 따라가며 본문에 보고된 수치의 범위를 확인한다.
