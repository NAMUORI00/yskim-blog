SmartFarm 관련 원고와 재현 자료를 정리하며 각 연구 시점의 코드, 결과, 문장을 연결했다. 원고 저장소와 재현 패키지가 담는 역할이 달라 실행 설정과 표의 근거를 각각 대조했다.


## 이전 원고의 결과를 현재 주장에 연결하기


SmartFarm 관련 원고 두 곳과 재현 패키지를 함께 읽었다. 각 저장소가 담은 연구 시점과 자료의 역할이 달라, 현재 원고의 주장에 연결되는 코드와 결과를 구분해 정리했다.


`smartfarm-paper`의 확인한 원고는 QACT-RAG라는 제목으로 Dense, Sparse, Graph 융합을 설명한다. `smartfarm-rag-paper`는 README에서 PeerJ 원고를 현재 작성 위치로, 이전 IEEE Access 자료를 과거 기록으로 구분한다.


`smartfarm-rag-peerj-reproducibility`에는 실행 코드, 공개 벤치마크, 표와 점검 스크립트가 있었다. 원고와 구현, 재현 자료 사이의 연결을 이 패키지의 실행 경로와 대조했다.


검색 품질 지표와 기준선의 기본 뜻은 앞선 평가 글에서 이어받는다. 여기서는 재현을 ‘명령이 실행되는지 확인하기’, ‘같은 조건으로 결과를 만들기’, ‘그 결과가 본문의 주장을 지지하는지 확인하기’로 나누어 살펴봤다.


## 원고별 연구 주장과 구현 범위


현재 PeerJ 원고는 그래프가 도움이 되지 않는 벤치마크 조건에서 밀집 검색을 유지하고 필요한 검색 계열을 선택하는 제한된 주장을 중심에 둔다. 확인한 초록에서는 AgXQA의 Dense-only 대비 개선을 보고하지만, Dense+Sparse보다 우수하다고 주장하지 않는다.


학습한 선택기가 다수 계열 기준선을 넘지 못한 진단도 남아 있다. [현재 원고](https://github.com/NAMUORI00/smartfarm-rag-paper/blob/6570efd0cd29f8c28494d7db00bcf1c3e073050a/source/PeerJ/latex/submission.tex)


이전 원고는 세 채널을 추가하는 장점을 앞세웠고, 현재 원고는 강한 단일, 두 채널 기준선과 그래프의 해로운 기여를 함께 다루고 있었다. 두 시점의 질문이 달라 이전 결과를 현재 주장의 근거로 그대로 연결하기는 어려웠다. 이전 원고는 연구 이력으로, 현재 재현 자료는 현재 비교 조건의 근거로 읽었다.

## 간단한 동작 확인과 논문용 실험


재현 패키지의 실행기는 `smoke`와 `paper`를 구분한다. 코드에서 smoke는 시드 하나, 최대 질의 10개, 부트스트랩 100회로 설정된다. paper는 시드 세 개, 최대 질의 200개, 부트스트랩 10,000회를 전달한다. 실행기에 전달하는 상한과 설정이며, 최종 평가 행 수는 데이터셋과 실행 결과를 확인해야 한다.


실제 원고는 시드별 평가 질의 160개를 보고하므로 입력 제한과 최종 분할의 수를 구분해서 읽었다. [벤치마크 실행기](https://github.com/NAMUORI00/smartfarm-rag-peerj-reproducibility/blob/71e834817a5d33a088ea33236f4b88b4667eb040/scripts/run-public-benchmark-paper.ps1)


README는 별도 임베딩 설정이 없는 smoke 실행에 `hashing_local`을 사용한다고 설명한다. 이 결과는 해시 벡터를 통한 데이터 흐름 확인이며 학습 임베딩의 검색 품질과는 다른 범위다. 논문 수준의 실행에는 신경망 임베딩 백엔드를 지정하도록 안내하고 있었다.


[재현 환경 설명](https://github.com/NAMUORI00/smartfarm-rag-peerj-reproducibility/blob/71e834817a5d33a088ea33236f4b88b4667eb040/README.md)


관계 토큰 설정이 비어 있으면 실행기는 `legacy`와 포함된 그래프 캐시를 기본으로 선택한다. 원고 당시 조건을 유지하기 위한 설정으로 읽었다. 현재 런타임의 확장된 관계 목록으로 바꾼 결과는, 개선 여부와 별개로 동일 실험의 재생과 다른 비교가 된다.


주 실행 인자에는 `--answer-mode extractive`가 들어간다. 이 검색 평가는 검색 결과를 대상으로 한다. 원격 LLM의 자유 서술 답변 평가는 별도 경로로 확인해야 한다. 코드에 마련된 서비스 기능과 실제 측정 경로가 여기서 다시 갈라졌다.


## 점검 스크립트의 확인 범위


평가 자료 점검 코드는 주요 JSON, CSV, 표 파일의 존재, 필요한 비교 방법, 신뢰구간 필드, 그래프 진단 항목 등을 확인한다. 반면 원고 주장과 표 수치 대조 코드는 저장된 표에서 특정 비교값과 주장 조건이 유지되는지 검사한다. 예를 들어 AgXQA에서 제안 조건이 Dense-only보다 높고 Dense+Sparse보다 낮다는 관계를 명시적으로 확인한다. 좋은 쪽의 비교만 원고에 남는 일을 막는 장치로 읽혔다.


[산출물 점검](https://github.com/NAMUORI00/smartfarm-rag-peerj-reproducibility/blob/71e834817a5d33a088ea33236f4b88b4667eb040/scripts/audit-evidence-package.ps1), [표와 주장 대조](https://github.com/NAMUORI00/smartfarm-rag-peerj-reproducibility/blob/71e834817a5d33a088ea33236f4b88b4667eb040/scripts/audit-paper-table-claim-values.ps1)


파일 존재와 예상 숫자의 일치 검사는 입력 데이터의 적절성이나 새 환경의 성능까지 다루지는 않는다. 기본 결과 폴더가 없으면 smoke 결과를 찾는 경로도 있었다. 점검 결과는 실행 설정과 실제 읽은 경로를 함께 확인해야 어느 프로필을 대상으로 했는지 알 수 있다.


실행기 마지막의 완료 문구 역시 개별 결과의 적절성을 대신하지 않는다. 확인한 코드에서는 여러 Python 호출을 이어 실행하지만 매 호출 직후 종료 코드를 검사하지는 않는다. 따라서 완료 문구 하나를 전체 단계의 성공 증거로 삼기보다 각 산출물과 별도 점검 결과를 함께 확인하는 편이 이 코드의 동작에 맞았다.

## 공개 패키지에는 필요한 근거를 골라 담기


내보내기 스크립트는 허용한 파일과 경로를 기준으로 코드를 모으고 원고, 검토용 PDF, 가상환경, 모델 바이너리, 생성 출력 등을 제외하도록 구성되어 있다. 작업 폴더 전체를 복사하는 대신 재현에 필요한 입력과 절차를 식별하려는 구성이었다. 다만 허용 목록이 있다는 사실만으로 모든 파일의 내용이 공개에 적절하다고 보증되는 것은 아니므로, 내보낸 실제 목록과 내용의 확인은 별도 작업으로 남는다.


[패키지 내보내기 코드](https://github.com/NAMUORI00/smartfarm-rag-peerj-reproducibility/blob/71e834817a5d33a088ea33236f4b88b4667eb040/scripts/export-peerj-repro-package.ps1)


세 저장소를 통해 코드 커밋, 백엔드와 데이터 조건, 결과표가 연결되는 위치를 정리했다. 새로 실행한 산출물과 보관된 표의 차이를 대조하는 작업은 남아 있다. 농장 운영 성능이나 보안 효과는 현재 검색 벤치마크 밖의 범위여서 별도의 자료와 실험으로 확인할 주제다.


## 작업을 정리하며


이전 결과를 현재 문장에 인용하려면 어떤 입력과 설정에서 나온 값인지 먼저 연결해야 한다. 원고와 실행 패키지의 버전을 함께 적어 두면 그 연결이 유지된다. 후속 실험에서도 결과 파일부터 표까지 이어지는 경로를 남기려 한다.
