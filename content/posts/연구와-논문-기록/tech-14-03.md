논문을 여러 차례 고쳐 쓰다 보면 연구 질문과 비교 기준이 되는 기존 방법인 **기준선**이 바뀐다. 그러면 예전 원고에 썼던 실험 결과를 새 원고의 근거로 그대로 가져다 쓸 수 없게 된다. SmartFarm 문서 검색 연구에서도 작성 시점과 역할이 다른 자료가 세 저장소에 나뉘어 있었다.


검색 품질 지표와 기준선의 기본 개념은 앞선 평가 글에서 다룬 내용을 따른다. 이 글에서는 세 저장소의 원고와 실행 경로를 나란히 대조하며 실험 재현을 세 단계로 따져 본다. 벤치마크 명령이 정상적으로 실행되는지, 논문과 같은 실험 조건에서 결과를 만드는지, 그 결과 표가 본문 주장을 실제로 뒷받침하는지 확인한다.


## 세 저장소의 역할과 원고 버전별 주장


먼저 세 저장소가 맡은 역할과 원고 버전에 따라 달라진 중심 주장을 비교한다. `smartfarm-paper`에 담긴 [이전 원고](https://github.com/NAMUORI00/smartfarm-paper/blob/761255ed1643205b8814e99dd9a355da140e6af9/access.tex)는 세 가지 검색 채널을 결합하는 `QACT-RAG` 구조를 설명한다. 의미 기반 **밀집 검색**(Dense), 단어 기반 **희소 검색**(Sparse), 관계 기반 **그래프 검색**(Graph)을 모두 더했을 때의 이점을 앞세웠다.


반면 `smartfarm-rag-paper`는 README에 [원고 저장소의 구분 규칙](https://github.com/NAMUORI00/smartfarm-rag-paper/blob/6570efd0cd29f8c28494d7db00bcf1c3e073050a/README.md)을 적어 두었다. 이전 IEEE Access 자료는 과거 기록으로 분류하고, 작성 중인 PeerJ 원고를 기준 문서로 둔다. 이 저장소의 [현재 원고](https://github.com/NAMUORI00/smartfarm-rag-paper/blob/6570efd0cd29f8c28494d7db00bcf1c3e073050a/source/PeerJ/latex/submission.tex)는 그래프 검색이 도움이 되지 않는 벤치마크 조건에 맞춰 주장의 범위를 좁혔다. 밀집 검색을 기본으로 유지하고 필요한 검색 계열만 선택하는 제한된 주장을 중심에 둔다.


확인한 PeerJ 원고 초록에서도 이처럼 좁혀진 주장 범위가 그대로 드러난다. 농업 질의응답 데이터셋인 AgXQA에서 밀집 검색 단독(`Dense-only`)보다 나아진 성능을 보고한다. 하지만 희소 검색을 더한 `Dense+Sparse`보다 앞선다고는 주장하지 않는다. 학습한 선택기가 여러 검색 계열을 묶은 기준선을 넘지 못했다는 진단 결과도 본문에 그대로 남아 있다.


이처럼 이전 원고는 세 채널을 추가하는 장점에 집중했고, 현재 원고는 단일 및 이중 채널 기준선과의 비교와 그래프 검색의 해로운 기여를 함께 다룬다. 연구 질문이 달라졌기 때문에 이전 원고의 실험 결과를 현재 주장의 근거로 곧바로 연결하기는 어려웠다. `smartfarm-rag-peerj-reproducibility`에는 벤치마크 실행 코드와 공개 데이터셋, 결과 표, 점검 스크립트가 모여 있다. 그래서 그림 1처럼 이전 원고는 연구 이력으로만 참고하고, 현재 비교 조건의 근거는 이 재현 패키지 자료에서 찾았다.

## 벤치마크 실행 프로필과 실험 조건


재현 패키지에 모인 코드를 실행할 때는 설정된 프로필에 따라 실험 조건과 확인 범위가 달라진다. [벤치마크 실행기](https://github.com/NAMUORI00/smartfarm-rag-peerj-reproducibility/blob/71e834817a5d33a088ea33236f4b88b4667eb040/scripts/run-public-benchmark-paper.ps1) 코드를 보면 실행 프로필이 빠른 동작 확인용인 `smoke`와 논문 실험용인 `paper`로 나뉜다. `smoke` 프로필은 난수 시드 1개, 최대 질의 10개, 표본을 반복 추출해 신뢰구간을 추정하는 **부트스트랩**(bootstrap) 100회로 설정된다. 반면 `paper` 프로필은 시드 3개, 최대 질의 200개, 부트스트랩 10,000회를 실행기에 전달한다.


여기서 `paper` 프로필의 최대 질의 200개는 실행기에 전달하는 입력 상한선이다. 실제 원고는 시드마다 평가 질의 160개를 보고하므로, 실행기의 입력 상한과 최종 평가 분할의 행 수는 데이터셋과 실행 결과를 열어 구분해야 한다.


문서와 질의를 계산 가능한 숫자 벡터로 변환하는 **임베딩** 설정도 프로필에 따라 다르다. [재현 환경 설명](https://github.com/NAMUORI00/smartfarm-rag-peerj-reproducibility/blob/71e834817a5d33a088ea33236f4b88b4667eb040/README.md)을 담은 README는 별도 임베딩 설정이 없는 `smoke` 실행에 `hashing_local`을 사용한다고 안내한다. 해시 벡터로 데이터 흐름이 이어지는지만 확인하는 설정이어서, 학습된 임베딩 모델의 검색 품질을 재는 실험과는 범위가 다르다. 논문 수준의 수치를 얻으려면 신경망 임베딩 백엔드를 지정해 실행해야 한다.


그래프 검색의 관계 토큰 설정과 답변 평가 모드는 원고 작성 시점의 조건에 맞춰져 있다. 관계 토큰 설정이 비어 있으면 실행기는 `legacy`와 패키지에 포함된 그래프 캐시를 기본으로 선택한다. 원고 작성 당시의 실험 조건을 유지하려는 설정으로 읽었다. 만약 현재 런타임의 확장된 관계 목록으로 바꾸어 실행한다면, 성능 개선 여부와 상관없이 기존 실험의 재현이 아니라 다른 조건의 비교 실험이 된다.


주 실행 인자에는 검색 결과 자체를 채점하는 **추출형 평가** 옵션인 `--answer-mode extractive`가 들어간다. 원격 대규모 언어 모델(LLM)이 생성한 자유 서술 답변은 이 기본 평가 대상에서 제외된다. 코드 안에는 LLM 서비스를 위한 기능도 마련되어 있지만, 프로필별 설정과 공통 조건을 정리한 그림 2처럼 실제 벤치마크 측정 경로는 추출형 검색 평가로 분리되어 있다. 원격 LLM의 자유 서술 답변을 평가하려면 별도 실행 경로를 확인해야 한다.


![smoke 프로필과 paper 프로필의 시드 수, 최대 질의 수, 부트스트랩 횟수, 임베딩 백엔드 차이와 공통 고정 조건인 legacy 그래프 캐시 및 extractive 평가를 비교한 도표](/images/notion/tech-14-03/image-2.png)

## 점검 스크립트의 확인 범위와 한계


벤치마크를 실행해 결과 파일을 얻었더라도 그 수치가 본문 주장과 맞물리는지는 두 가지 점검 스크립트로 따로 검증해야 한다. 먼저 [산출물 점검](https://github.com/NAMUORI00/smartfarm-rag-peerj-reproducibility/blob/71e834817a5d33a088ea33236f4b88b4667eb040/scripts/audit-evidence-package.ps1) 스크립트는 주요 JSON, CSV, 표 파일이 모두 생성되었는지 확인한다. 결과 파일 안에 필요한 비교 방법과 신뢰구간 필드, 그래프 진단 항목이 빠짐없이 들어 있는지도 함께 검사한다.


이어서 [표와 주장 대조](https://github.com/NAMUORI00/smartfarm-rag-peerj-reproducibility/blob/71e834817a5d33a088ea33236f4b88b4667eb040/scripts/audit-paper-table-claim-values.ps1) 스크립트는 저장된 표에서 특정 비교값과 본문의 주장 조건이 유지되는지 대조한다. 예를 들어 AgXQA에서 제안 조건의 수치가 `Dense-only`보다 높고 `Dense+Sparse`보다 낮다는 관계를 명시적으로 확인한다. 수치 관계를 코드로 고정해 유리한 비교만 골라 원고에 남기는 일을 막는 장치로 읽혔다.


다만 점검 스크립트를 통과했다고 해서 모든 검증이 끝나는 것은 아니다. 파일 존재 여부와 예상 수치의 일치 검사는 입력 데이터 자체의 적절성이나 새로운 실행 환경에서의 성능까지 보증하지 않는다. 게다가 코드 안에는 기본 결과 폴더가 없을 때 `smoke` 결과를 대신 찾는 경로도 들어 있었다. 따라서 점검 결과를 읽을 때는 실행 설정과 스크립트가 실제로 읽은 파일 경로를 함께 확인해야 어느 프로필을 검사했는지 알 수 있다.


벤치마크 실행기 마지막에 출력되는 완료 문구도 개별 단계의 성공을 대신하지 않는다. 확인한 실행기 코드는 여러 Python 호출을 차례로 실행하지만, 매 호출 직후에 종료 코드를 검사하지는 않는다. 중간 단계에서 문제가 생겨도 마지막 완료 문구가 그대로 출력될 수 있다. 따라서 그림 3처럼 완료 문구 하나를 성공 증거로 삼기보다 각 산출물 파일과 점검 스크립트 결과를 함께 확인해야 이 코드의 동작 방식에 맞다.

## 허용 목록 기반의 공개용 재현 패키지


실험과 점검에 사용한 작업 폴더를 외부에 공개할 때는 재현에 필요한 근거만 골라 담아야 한다. [패키지 내보내기 코드](https://github.com/NAMUORI00/smartfarm-rag-peerj-reproducibility/blob/71e834817a5d33a088ea33236f4b88b4667eb040/scripts/export-peerj-repro-package.ps1)는 작업 폴더 전체를 복사하는 대신, 그림 4처럼 허용한 파일과 경로 목록을 기준으로 실행 코드와 설정만 모은다. 작성 중인 원고와 검토용 PDF, 가상환경, 모델 바이너리, 생성된 출력물 등은 내보내기 대상에서 제외해 재현에 필요한 입력과 절차만 식별한다. 다만 허용 목록이 있다는 사실만으로 포함된 모든 파일의 세부 내용이 공개에 적절하다고 보장되지는 않는다. 내보낸 실제 파일 목록과 내용을 직접 확인하는 일은 별도 작업으로 남는다.

## 결론


세 저장소를 나란히 대조해 원고 문장이 어떤 코드 커밋과 임베딩 및 캐시 조건, 그리고 어느 결과 표에서 나왔는지 이어지는 위치를 확인했다. 이전 실험 결과를 새 문장에 인용하려면 어떤 입력과 설정에서 나온 값인지부터 연결해야 하고, 원고와 실행 패키지의 버전을 함께 적어 두어야 그 연결이 유지된다.


이제 새로 실행한 산출물과 저장소에 보관된 표의 차이를 직접 대조하고, 내보낸 공개 패키지의 실제 파일 내용을 확인하는 작업이 남아 있다. 실제 농장 운영 성능이나 보안 효과는 현재 검색 벤치마크 밖의 범위여서 별도의 자료와 실험으로 확인할 주제다.
