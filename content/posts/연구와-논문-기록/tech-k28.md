모델 학습 스크립트를 학습률 0.01로 실행해 정확도 0.87을 얻은 상황을 가정해 본다. 일주일 뒤 같은 스크립트를 다시 돌렸더니 정확도가 0.83으로 달라지는 경우가 있다. 코드를 조금도 고치지 않았는데 결과가 달라지면 코드만 남겨 두어서는 원인을 찾기 어렵다. 학습 결과는 코드뿐 아니라 입력 데이터의 내용과 순서, 실행 환경의 영향을 함께 받기 때문이다. 이 글에서는 같은 실험 결과를 다시 얻거나 차이의 원인을 추적하기 위해 실행 기록에 남겨야 할 조건과 반복 측정 방법을 다룬다.


## 환경 변화와 재현 가능성


코드가 같아도 결과가 달라지는 대표적인 원인은 실행 환경의 소프트웨어 버전 변화다. 모델을 학습할 때는 데이터를 무작위로 섞기 위해 처음 출발점 숫자인 **난수 시드**(seed)를 넣어 난수열을 만든다. 그런데 계산 라이브러리인 `numpy` 버전이 올라가면서 난수를 만드는 내부 구현이 바뀌면, 같은 시드를 넣어도 다른 난수열이 나올 수 있다. 그 결과 데이터를 섞는 순서가 바뀌어 학습된 모델의 정확도까지 0.87에서 0.83으로 달라진다.

그림 1. 동일한 코드와 시드에서 라이브러리 버전 차이로 학습 결과가 달라지는 과정을 나타낸 개념도.


이처럼 실험 결과를 다시 확인하는 문제를 다룰 때는 먼저 목표에 따라 용어를 구분해 두어야 한다. 분야마다 쓰임새가 조금씩 다르지만, 같은 데이터와 같은 코드로 동일한 결과를 다시 얻는 일은 **재현 가능성**(reproducibility)이라 부른다. 반면 다른 연구팀이 독립적으로 수집한 데이터로 같은 결론에 도달하는 일은 **재현 독립성**(replicability)이라 구분한다. 이러한 용어 구분은 [DIME Wiki - Reproducible Research](https://dimewiki.worldbank.org/Reproducible_Research)의 정리를 따른다. 연구 안내서인 [The Turing Way - Reproducible Research](https://book.the-turing-way.org/reproducible-research/reproducible-research/)는 재현 가능성을 갖추는 요소를 데이터, 코드, 도구(환경), 결과의 네 가지로 나눈다.


## 두 실행 기록의 비교


앞서 본 네 가지 요소를 바탕으로 두 번의 실험을 실행 기록으로 남겨 두면 어디서 차이가 생겼는지 대조할 수 있다.


```plain text
실행 A                        실행 B
─────────                    ─────────
입력: train_v2.csv           입력: train_v2.csv
코드: commit abc123          코드: commit abc123
Python 3.11.4               Python 3.11.7
numpy 1.25.0                numpy 1.26.1
시드: 42                     시드: 42
학습률: 0.01                 학습률: 0.01
결과: 정확도 0.87            결과: 정확도 0.83
```


두 기록에서 입력 파일 이름(`train_v2.csv`), 코드 저장 번호인 커밋(`abc123`), 시드(`42`), 학습률(`0.01`)은 모두 같다. 반면 결과 정확도는 0.87과 0.83으로 달라졌고, 실행 환경의 버전도 함께 바뀌어 있다. Python의 세부 패치 버전은 3.11.4에서 3.11.7로, `numpy` 버전은 1.25.0에서 1.26.1로 올라갔다.


물론 기록에 적힌 차이가 곧바로 결과 변화의 원인을 확정해 주지는 않는다. 파일 이름이 같아도 두 실행 사이에 파일 안의 내용이 바뀌었을 수 있기 때문이다. 반대로 기록한 항목이 모두 같아도 GPU 드라이버 버전이나 작업 순서를 배정하는 스레드 스케줄링처럼 미처 적지 않은 조건 때문에 결과가 달라질 수 있다. 그래도 입력과 환경, 산출물을 한 단위로 묶은 실행 기록이 남아 있으면 환경 버전 차이를 추가 확인의 출발점으로 삼아 조사 범위를 좁힐 수 있다.


![입력 데이터 해시와 버전 잠금 기록을 실행 환경과 결합해 산출물을 만들고 두 실행 결과 일치 여부에 따라 차이를 추적하는 순서도](/images/notion/tech-k28/image-2.png)


그림 2. 입력과 환경, 산출물을 한 단위로 묶어 재현 여부를 확인하고 차이를 추적하는 실행 기록 구성도.


## 실행 기록의 네 가지 층위


앞선 비교에서 보듯 파일 이름이나 커밋 번호만 적어 두면 빈틈이 생기므로, 실행 기록은 입력 데이터, 코드 버전, 실행 환경, 설정값의 네 층위로 나누어 남긴다.


첫째, **입력 데이터**는 파일 이름 대신 파일 내용에서 계산한 고유 요약값인 파일 해시(SHA-256)로 고정한다. 파일 이름이 `train_v2.csv`로 같더라도 행이 하나 추가되었다면 다른 데이터이기 때문이다. SHA-256 해시값이 일치하면 일반적인 데이터 검증에서는 바이트 단위로 같은 파일이라고 볼 수 있는 강한 근거가 된다. 다만 원본 데이터 자체의 신뢰성이나 데이터 분할의 타당성은 해시값만으로 알 수 없으므로 별도로 검사해야 한다.


둘째, **코드 버전**은 코드의 변경 이력을 식별하는 Git 커밋 해시로 잡는다. 최신 `main` 브랜치를 썼다고만 적어 두면 다음 날 코드가 바뀌었을 때 실행 시점의 스냅샷을 알 수 없다. 이때 실행 시점의 커밋 해시와 함께 아직 커밋하지 않은 변경 사항이 있는지도 기록해야 한다. 현재 작업 중인 파일 상태인 작업 트리(working tree)를 수정한 채로 실행했다면 커밋 해시만으로는 실제 실행된 코드를 복원할 수 없기 때문이다.


셋째, **실행 환경**에는 언어 버전, 라이브러리 버전, 운영체제를 포함한다. 코드와 설정을 남겼더라도 라이브러리 버전을 빠뜨리면 나중에 환경을 복원하거나 차이의 원인을 좁히기 어렵다. Python이라면 `pip freeze > requirements.txt`의 출력을 커밋에 포함하거나 `conda env export`로 환경 전체를 내보낼 수 있다. 만약 `requirements.txt`가 버전 범위를 허용한다면 설치 시점마다 다른 버전이 깔릴 수 있으므로, 정확한 버전과 필요하면 배포 파일 해시까지 기록해 둔다. 또는 `poetry.lock`, `conda-lock.yml`처럼 실제 설치 버전을 적어 두는 잠금 파일(lockfile)로 버전을 따로 고정한다. 프로그램과 환경을 묶는 컨테이너를 쓸 때는 Docker 이미지의 고유 식별값인 다이제스트(digest)가 사용자 공간의 파일과 패키지를 고정하는 데 도움이 된다. 하지만 호스트 커널, 드라이버, GPU 종류는 컨테이너 바깥의 조건이므로 별도로 기록해야 한다.


넷째, **설정값**은 실행 코드에서 분리해 파일 하나로 모아 관리한다. 학습률처럼 사람이 직접 정하는 하이퍼파라미터나 시드, 한 번에 처리할 데이터 묶음인 배치 크기 같은 설정값이 코드 여러 곳에 흩어져 있으면 나중에 모으기 어렵다. 이 값들을 JSON이나 YAML 파일 하나로 분리해 두면 두 실행의 설정 차이를 `diff` 한 줄로 확인할 수 있다.


![입력 데이터의 SHA-256 해시, 코드 버전의 커밋과 작업 트리, 실행 환경의 잠금 파일과 호스트 정보, 설정값의 JSON 및 YAML 분리가 하나의 실행 단위 기록으로 묶이는 도식](/images/notion/tech-k28/image-3.png)


그림 3. 실험 결과에 연결해야 할 실행 기록의 네 가지 층위와 고정 대상을 정리한 구조도.


실험 횟수가 늘어나면 네 가지 층위를 기록하는 과정을 실험 추적 도구로 자동화할 수 있다. 예를 들어 [MLflow - Experiment Tracking](https://mlflow.org/docs/latest/tracking.html)은 파라미터, 지표, 산출물을 실행 단위로 묶어 저장하고 과거 실행과 비교하는 화면을 제공한다. 추적 도구를 쓰든 텍스트 기록을 남기든 입력, 코드, 환경, 설정을 결과 숫자에 연결해 두어야 나중에 실행 차이를 다시 대조할 수 있다.


## 반복 측정과 흔들림 범위


네 가지 층위를 모두 기록해 한 번의 실행을 그대로 재현할 수 있게 되었더라도, 단 한 번의 측정값만으로 모델 성능을 판단하기는 어렵다. 같은 설정에서 시드만 42, 43, 44로 바꿔 세 번 돌렸더니 정확도가 각각 0.87, 0.85, 0.86이 나왔다고 가정해 본다. 세 값의 평균은 0.86이고, 최댓값과 최솟값의 차이인 범위는 0.02다. 만약 한 번 돌린 0.87만 보고했다면 그 숫자가 우연히 운이 좋았던 시드에서 나온 결과인지 알 수 없다. 이때 비교 대상 모델이 정확도 0.85를 냈다면, 이 값은 시드에 따른 흔들림 폭인 0.02(0.85~0.87) 안에 들어온다.


![동일 설정 파일로 시드 42, 43, 44 세 번을 실행해 얻은 정확도 0.87, 0.85, 0.86에서 평균 0.86과 범위 0.02를 구하고 비교 모델 0.85가 이 범위 안에 포함됨을 보여 주는 도식](/images/notion/tech-k28/image-4.png)


그림 4. 시드를 바꾼 세 번의 반복 측정으로 평균과 흔들림 범위를 확인하는 설명용 도식.


이처럼 비교 모델의 성능이 흔들림 범위 안에 겹치면 이 결과만 두고 한쪽 모델이 더 낫다고 말하기에는 근거가 부족하다. 세 번이 충분한 반복인지는 통계 검정의 영역이므로 여기서 다루지 않는다. 그렇더라도 한 번보다 세 번의 측정이 결과의 안정성에 대해 더 많은 정보를 준다는 점은 손계산으로도 확인할 수 있다.


## 실험 조건과 주장의 범위


실행 기록을 빠짐없이 갖추고 반복 측정을 거쳤더라도 실험 결과로 주장할 수 있는 범위는 제한된다. 실험 결과는 특정 데이터셋에서 데이터를 학습에 맞게 다듬는 특정 전처리를 거쳐 특정 하드웨어 위에서 확인한 값이기 때문이다.


앞선 기록이 직접 뒷받침하는 결론은 "이 데이터셋에서 이 설정으로 세 번 측정했을 때 평균 정확도가 1%p 높았다"까지다. 데이터나 전처리가 바뀌면 모델 간 순위도 달라질 수 있으므로, 비교 결과는 항상 관찰한 조건에 연결해 읽어야 한다.


## 결론


재현 가능한 실험을 수행하려면 입력 데이터 해시, 코드 스냅샷, 실행 환경, 설정값을 결과 지표와 한 단위로 묶어 기록해야 한다. 여기에 난수 시드를 바꾼 반복 측정을 더하면 한 번의 우연한 결과에 기대지 않고 성능의 평균과 흔들림 폭을 함께 확인할 수 있다.


다만 이러한 기록과 반복 측정으로 확인한 것은 기록된 조건 안에서의 재현 여부와 측정값의 흔들림 범위까지다. 원본 데이터의 신뢰성이나 반복 횟수의 통계 검정은 별도로 확인해야 하며, 환경을 고정하는 방식만으로는 재현 조건의 일부만 해결된다. 보안 패치나 의존성 업데이트로 버전이 바뀐 뒤에는 얼마만큼의 결과 차이를 허용 범위로 볼지, 버전 변경 전후를 어떤 기준으로 대조할지 정하는 과제가 남는다.
