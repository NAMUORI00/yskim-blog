## 실행 조건과 결과 변화


실험 결과를 다시 확인할 때 필요한 실행 기록을 정리했다. 학습률 0.01에서 정확도 0.87을 얻고 일주일 뒤 같은 스크립트에서 0.83이 나온 상황을 설명용으로 가정했다. 코드 외에도 입력 순서와 환경이 달라질 수 있어 결과 숫자에 연결할 조건을 살펴봤다.


이 문제는 소프트웨어 버전 하나가 올라가는 것만으로도 생긴다. numpy의 난수 생성 내부 구현이 바뀌면 같은 시드를 넣어도 다른 난수열이 나올 수 있고, 데이터를 섞는 순서가 달라지면 학습 결과도 달라진다.


재현 가능성(reproducibility)은 같은 데이터와 코드로 같은 결과를 다시 얻을 수 있느냐의 문제이며, The Turing Way 프로젝트는 이를 데이터, 코드, 도구(환경), 결과 네 요소로 정리한다([The Turing Way - Reproducible Research](https://book.the-turing-way.org/reproducible-research/reproducible-research/)).


## 두 실행 기록의 비교


아래처럼 두 번의 실행을 기록해 두었다고 하자.


```javascript
실행 A                        실행 B
─────────                    ─────────
입력: train_v2.csv           입력: train_v2.csv
코드: commit abc123          코드: commit abc123
Python 3.11.4               Python 3.11.7
numpy 1.25.0                numpy 1.26.1
시드: 42                     시드: 42
학습률: 0.01                 학습률: 0.01
결과: 정확도 0.87            결과: 정확도 0.83
```


파일 이름과 코드 커밋 표기는 같지만 결과는 다르다. 파일 이름만으로 내용까지 같다고 판단할 수는 없다. 기록에서 차이를 찾아보면 Python 패치 버전과 numpy 버전이 다르다.


이 기록에서는 환경 버전 차이를 추가 확인의 출발점으로 삼을 수 있다. 기록한 항목이 모두 같아도 결과가 다르면 GPU 드라이버나 스레드 스케줄링처럼 빠진 조건을 살펴볼 여지가 있다. 기록만으로 원인을 확정하는 단계와는 구분했다.

## 기록의 네 층위


첫째, **입력 데이터**는 파일 해시(SHA-256)로 고정한다. `train_v2.csv`라는 이름이 같아도 행이 하나 추가되었으면 다른 데이터다. SHA-256이 일치하면 통상적인 데이터 검증에서 동일 바이트의 파일로 취급할 강한 근거가 된다. 원본의 신뢰성과 데이터 분할의 타당성은 별도 검사 항목이다.


둘째, **코드 버전**은 커밋 해시로 잡는다. "최신 main"은 내일이면 다른 코드이므로 특정 시점의 스냅샷이 필요하다. 실행 시점의 커밋과 함께 커밋되지 않은 변경 여부도 기록해야 한다. 작업 트리가 수정된 상태라면 커밋만으로 실제 실행 코드를 복원할 수 없다.


셋째, **실행 환경**은 언어 버전, 라이브러리 버전, 운영체제를 포함한다. Python이라면 `pip freeze > requirements.txt`의 출력을 커밋에 포함하거나, `conda env export`로 환경 전체를 내보낼 수 있다.


Docker 이미지 digest는 사용자 공간의 파일과 패키지를 고정하는 데 도움이 된다. 호스트 커널, 드라이버, GPU 종류는 별도로 기록해야 한다.


넷째, **설정값**(하이퍼파라미터, 시드, 배치 크기)은 코드 여러 곳에 흩어져 있으면 나중에 모으기 어렵다. JSON이나 YAML 한 파일로 분리해 두면, 두 실행의 설정 차이를 diff 한 줄로 확인할 수 있다.


빠진 기록이 있으면 다른 자료로 복원해야 할 범위가 커진다. 코드와 설정을 남겼지만 라이브러리 버전을 기록하지 않았다면, 환경을 복원하거나 차이의 원인을 좁히기 어려워질 수 있다. `requirements.txt`가 버전 범위를 허용한다면 잠금 파일로 실제 설치 버전을 따로 고정한다.


정확한 버전과 필요하면 배포 파일 해시까지 기록한 요구사항이나 `poetry.lock`, `conda-lock.yml` 같은 잠금 파일은 나중에 같은 환경을 다시 만들 때 출발점이 된다.


## 반복 측정이 알려주는 것


같은 설정으로 시드만 바꿔 세 번 돌려서 정확도가 0.87, 0.85, 0.86이 나왔다고 하자. 평균은 0.86이고 범위는 0.02다. 한 번 돌린 0.87만 보고했다면 그 숫자가 운이 좋았던 경우인지 알 수 없다.


비교 대상 모델이 0.85를 냈다면, 0.02의 흔들림 폭 안에 들어온다. "이쪽이 낫다"고 말하기에는 근거가 부족하다. 세 번이 충분한 반복인지는 통계 검정의 영역이므로 여기서 다루지 않지만, 최소한 한 번보다 세 번이 결과의 안정성에 대해 더 많은 정보를 준다는 점은 손계산으로도 확인할 수 있다.

## 주장할 수 있는 범위


기록이 완벽해도 주장의 범위는 제한된다. 특정 데이터셋에서, 특정 전처리를 거쳐, 특정 하드웨어 위에서 확인한 결과이기 때문이다. 기록이 뒷받침하는 결론은 “이 데이터셋에서 이 설정으로 세 번 측정했을 때 평균 1%p 높았다”이다.


데이터나 전처리가 바뀌면 모델 간 순위도 달라질 수 있다. 그래서 비교 결과는 관찰한 조건에 연결해 읽었다.


reproducibility와 replicability의 용어는 분야별 사용이 달라 정의를 먼저 명시할 필요가 있다. 여기서는 다음 의미로 구분했다.


재현 가능성은 같은 데이터, 같은 코드로 같은 결과를 얻는 것이고, 재현 독립성은 다른 팀이 독립적으로 수집한 데이터로 같은 결론에 도달하는 것이다([DIME Wiki - Reproducible Research](https://dimewiki.worldbank.org/Reproducible_Research)). 이 글에서 다루는 범위는 전자, 즉 기록을 통해 같은 결과를 다시 만들어낼 수 있는 환경을 갖추는 것까지다.


실험 추적 도구를 쓰면 이 과정을 자동화할 수 있다. MLflow는 파라미터, 지표, 산출물을 실행 단위로 묶어 저장하고, 과거 실행과의 비교 화면을 제공한다([MLflow - Experiment Tracking](https://mlflow.org/docs/latest/tracking.html)).


추적 도구와 텍스트 기록 모두 입력, 코드, 환경, 설정을 결과에 연결하는 수단이다. 이 대응이 남아 있어야 나중에 실행 차이를 다시 대조할 수 있다.


## 후속 검토


환경 고정은 재현 조건 일부를 맞추는 방법이다. 보안 패치나 의존성 업데이트 이후에는 결과 차이의 허용 범위와 비교 기준을 정할 작업이 남는다. 버전 변경 전후의 대조를 후속 주제로 정리했다.
