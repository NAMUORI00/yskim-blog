논문 PDF 한 편을 만들 때는 본문 원고 파일만 쓰이지 않는다. 실험 그래프 같은 그림 파일, 참고문헌 정보를 담은 데이터베이스, 학술지 양식에 맞춘 인용 스타일 파일이 본문과 합쳐져 최종 문서를 이룬다. 그래서 그림 크기가 바뀌거나 참고문헌이 하나 추가되면 본문 안의 인용 번호와 페이지 배치까지 연쇄적으로 달라질 수 있다. 원고 파일만 열었을 때는 보이지 않는 파일 간 의존 관계와, 원본을 고쳤을 때 어느 단계부터 다시 빌드해야 하는지 작은 프로젝트 예제로 짚어 본다.


## 입력 파일 구성: 원고, 그림, 참고문헌


작은 논문 프로젝트의 디렉터리 구조는 보통 다음과 같이 나뉜다.


```plain text
paper/
├── main.tex          # 본문 원고
├── figures/
│   ├── fig1.pdf      # 실험 결과 그래프
│   └── fig2.png      # 시스템 구조도
├── references.bib    # 참고문헌 데이터베이스
└── ieee.bst          # 인용 스타일
```


본문 원고인 `main.tex` 안에는 문장들과 함께 그림을 불러오는 명령(`\includegraphics{figures/fig1.pdf}`)이나 문헌을 인용하는 명령(`\cite{kim2024}`)이 들어간다. 실제 그림 데이터는 `figures/` 디렉터리에 따로 있고, 참고문헌의 상세 서지 정보는 `references.bib`에 모여 있다. `ieee.bst`는 인용 번호와 참고문헌 목록을 어떤 학술지 양식으로 조판할지 정의한 **BibTeX 스타일 파일**(`.bst`)이다.


`references.bib` 파일은 참고문헌의 저자, 제목, 학술지 이름, 발행 연도를 구조화된 텍스트로 담는다. 다음은 문법 설명을 위해 만든 가상 서지 항목이다.


```plain text
@article{kim2024,
  author  = {Kim, Soo},
  title   = {A Method for Sensor Calibration},
  journal = {Journal of Measurements},
  year    = {2024},
  volume  = {12},
  pages   = {34--42}
}
```


첫 줄의 `kim2024`가 본문에서 `\cite{kim2024}`로 부를 때 쓰는 인용 키다. 기본 BibTeX 빌드에서는 `references.bib`에 수십 개의 문헌이 적혀 있어도 본문에서 실제로 인용한 항목만 최종 참고문헌 목록에 추려 넣는다. 본문에 인용 표시를 남기지 않고 문헌 목록에만 추가하고 싶을 때는 예외로 `\nocite{...}` 명령을 쓴다. 본문 속 인용 키와 문헌 목록을 짝지어 번호를 매기는 작업은 사람이 직접 하지 않고 빌드 도구가 자동으로 처리한다.

## 빌드 단계: 컴파일, 참조 해소, 반복


인용 번호와 페이지 번호는 문서 전체를 조판해 봐야 확정되므로, LaTeX 논문 빌드는 한 번의 컴파일로 끝나지 않는다. 이전에 생성된 보조 파일이 전혀 없는 상태에서 pdfLaTeX와 BibTeX를 함께 쓸 때는 보통 다음 네 단계를 거친다. 참고문헌 도구로 biblatex와 Biber를 쓰는 구성에서는 실행 명령과 중간 파일 형식이 달라진다.

1. `pdflatex main.tex`: 본문을 처음 읽어들여 조판하되, 아직 대상을 알 수 없는 인용(`\cite`)과 상호참조(`\ref`) 자리는 `?`로 남겨 둔다.
2. `bibtex main`: 1차 컴파일이 남긴 `.aux` 보조 파일에서 인용 키 목록을 읽고, `.bib` 데이터베이스에서 해당 문헌을 찾아 `.bst` 스타일에 맞게 정렬한 `.bbl` 파일을 만든다.
3. `pdflatex main.tex`: 방금 만들어진 `.bbl` 파일을 읽어 본문 끝에 참고문헌 목록을 붙이고 인용 번호를 채운다.
4. `pdflatex main.tex`: 참고문헌 목록이 들어가면서 뒤로 밀린 페이지 번호와 그림이나 표를 가리키는 상호참조 번호를 최종 확정한다.

첫 번째 컴파일을 마친 직후에는 `\cite{kim2024}`가 몇 번 문헌인지 알 수 없어 PDF 본문에 `[?]`로 찍힌다. 대신 컴파일러가 문서에 등장한 인용 키와 라벨 정보를 `main.aux`에 적어 둔다. 이어서 실행된 BibTeX가 이 `main.aux`를 보고 필요한 서지 항목만 뽑아 조판용 문헌 목록 파일인 `main.bbl`을 생성하면, 두 번째 `pdflatex` 컴파일 때 비로소 참고문헌 목록이 문서에 합쳐진다. 그런데 문헌 목록이 몇 페이지를 차지하면서 앞뒤 지면 배치가 달라질 수 있으므로, 세 번째 컴파일을 한 번 더 돌려 바뀌어버린 페이지 번호와 상호참조까지 맞춰 준다.

원고를 마크다운(Markdown)으로 작성하고 문서 변환 도구인 Pandoc을 쓰면 이 과정을 명령 한 줄로 줄일 수 있다. [Pandoc 공식 문서](https://pandoc.org/MANUAL.html)를 보면 `--citeproc` 옵션을 켰을 때 Pandoc 내부의 인용 처리기가 문헌 연결을 대신 수행한다.


```bash
pandoc main.md --citeproc --bibliography=references.bib --csl=ieee.csl -o paper.pdf
```


여기서 `ieee.csl`은 인용 형식을 정의한 **CSL**(Citation Style Language) 파일이다. 사용자는 명령을 한 번만 입력하지만, 선택한 PDF 엔진과 문서 구조에 따라 내부에서는 여러 단계가 차례로 돌아간다. 특히 PDF 생성 엔진으로 LaTeX을 쓰도록 지정했다면 시스템에 LaTeX 엔진도 설치되어 있어야 한다. `citeproc`이 중간에서 인용 키를 문헌 데이터베이스와 대조해 번호를 매기는 원리는 BibTeX 흐름과 같다.


## 산출물과 중간 파일 구분


LaTeX과 BibTeX가 파일을 주고받으며 빌드를 마치면 작업 디렉터리에는 원본 외에도 여러 파일이 남는다. 각 파일의 역할과 Git 같은 버전 관리 시스템에 포함할지 여부는 다음과 같이 구분할 수 있다.


| 파일               | 역할            | 버전 관리 대상     |
| ---------------- | ------------- | ------------ |
| `main.tex`       | 입력 — 본문 원고    | O            |
| `references.bib` | 입력 — 참고문헌     | O            |
| `figures/*.pdf`  | 입력 — 그림       | O            |
| `main.aux`       | 중간 — 인용 키와 라벨 | X            |
| `main.bbl`       | 중간 — 정리된 문헌   | 제출 규칙에 따라 보존 |
| `main.log`       | 중간 — 컴파일 로그   | X            |
| `main.pdf`       | 최종 산출물        | 선택           |

그림 3. 빌드 후 디렉터리에 남는 파일을 입력 원본, 중간 파일, 최종 산출물로 나눈 버전 관리 기준 (설명용 예제)


언제든 같은 문서를 다시 빌드하려면 표에 적힌 입력 파일뿐 아니라 학술지 템플릿, 글꼴, TeX 엔진, 패키지 버전 같은 실행 환경도 맞아야 한다. 빌드할 때마다 새로 만들어지는 `*.aux`나 `*.log` 같은 중간 파일은 변경 이력이 지저분해지지 않도록 `.gitignore`에 등록해 버전 관리에서 뺀다. 다만 `main.bbl`은 학술지나 논문 투고 시스템에 따라 `.bib` 대신 제출하도록 요구하는 곳이 있어 제출 규칙에 맞춰 보존 여부를 정한다. 최종 산출물인 `main.pdf` 역시 다른 환경에서 빌드를 그대로 재현하기 쉬운지, 아니면 완성된 문서를 이력으로 남겨 바로 확인해야 하는지에 따라 추적 여부를 선택한다.


## 원본 변경과 재빌드 범위


초안 빌드를 마친 뒤 파일을 고칠 때는 수정한 내용에 따라 다시 실행해야 하는 단계가 달라진다. 그렇다고 수정한 파일의 확장자만으로 컴파일 횟수를 미리 단정할 수는 없다. 본문에서 오타 한 글자만 고쳐도 줄바꿈이 달라지면서 문단이 다음 페이지로 넘어갈 수 있기 때문이다. 반대로 참고문헌 파일(`.bib`)이나 본문의 인용 명령(`\cite`)을 건드리지 않았다면 BibTeX나 Biber를 다시 돌릴 필요는 없다.


결국 재빌드 범위는 문헌 입력이 바뀌었는지 먼저 살피고, 이어서 LaTeX 컴파일 로그에 상호참조나 페이지 번호가 바뀌었으니 다시 실행하라는 경고가 남았는지 확인하는 흐름으로 결정된다. [Overleaf의 BibTeX 가이드](https://www.overleaf.com/learn/latex/Bibliography_management_with_bibtex)에서도 이와 같은 순서로 컴파일 단계를 설명한다.

그림 4. 입력 의존성과 재실행 경고를 확인하며 출력을 안정시키는 과정. 직접 작성한 설명용 예제


매번 로그를 읽으며 수동으로 반복하기 번거로울 때는 빌드 자동화 도구인 `latexmk`를 쓴다. 터미널에서 `latexmk -pdf main.tex`를 실행하면 도구가 입력 파일과 보조 파일의 변경 여부를 스스로 비교해, 모든 참조 번호가 흔들리지 않고 확정될 때까지 필요한 횟수만큼만 `pdflatex`와 `bibtex`를 알아서 반복한다. 만약 `latexmk` 없이 `Makefile`로 빌드 규칙을 직접 작성한다면 이러한 파일 간 의존 관계를 규칙에 명시해야 한다.


혼자 문서를 빌드할 때는 이처럼 입력 파일과 보조 파일의 의존 순서만 맞추면 되지만, 여러 저자가 함께 작업하거나 코드로 그래프를 그리는 환경에서는 따져 볼 문제가 더 남는다. 공동 저자가 같은 `.tex` 원고를 동시에 고칠 때 생기는 병합 충돌을 어떻게 줄일지, 그리고 `matplotlib`이나 TikZ 코드로 생성하는 그림은 파이썬 스크립트나 코드 원본만 저장소에 두고 빌드할 때마다 새로 그릴지 아니면 결과 그림 파일(`.pdf`, `.png`)까지 함께 이력에 남길지가 다음 질문으로 이어진다. 이는 공동 작업자의 실행 환경 통일 여부와 산출물 검토 방식을 기준으로 비교해 볼 주제다.
