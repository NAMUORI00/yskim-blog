앞 글에서는 농장 상태가 바뀔 때 이전 답변을 다시 검증하는 과정을 다뤘다. 이번에는 온습도 같은 환경을 조절하라는 조정안을 운영자가 승인한 뒤, 그 처리 과정을 나누어 기록하는 구조를 따라간다. 운영자가 화면에서 조정안을 허용했더라도 실제 설비 대신 동작을 가상으로 흉내 내는 **시뮬레이터**(simulator)에 제어 명령이 전달되지 못할 수 있다. 제어 명령이 적용된 뒤에도 농장의 온습도 지표가 곧바로 정상 범위로 돌아오지 않을 수 있다. 승인 여부와 명령 적용, 환경 회복을 하나의 상태로 묶어 두면 문제가 생겼을 때 어느 단계에서 멈췄는지 구분하기 어렵다.


`smartfarm` 저장소(`426cbe5` 커밋 기준)에서는 각 단계를 어떻게 나누어 기록하는지 서비스 반환값과 웹 화면 타입을 함께 확인했다. 현재 코드는 실제 농장 설비 대신 시뮬레이터 제어를 전제로 하며, 명령 실행의 성공 여부도 시뮬레이터가 돌려주는 반환값을 기준으로 판단한다.


## 승인, 실행, 확인 상태의 분리


세 단계를 구분해 기록하려면 먼저 데이터 구조에서 각 단계의 상태를 따로 담아야 한다. `smartfarm` 저장소에 정의된 [웹 앱의 ApiProposal 타입](https://github.com/NAMUORI00/smartfarm-rag-ops/blob/426cbe5e0dbc9e62d65ed4fdd5ae58e302d1dd8e/apps/web/src/api.ts#L161)은 승인 상태와 실행 결과, 후속 확인 결과를 서로 다른 항목(필드)에 나누어 담는다.


| 필드                     | 답하려는 질문        | 값의 예                                                            |
| ---------------------- | -------------- | --------------------------------------------------------------- |
| `status`               | 조정안을 허용했는가     | `pending_approval`, `approved`, `rejected`, `failed`            |
| `execution.status`     | 명령 적용 결과를 받았는가 | `not_executed`, `applied_to_simulator`, `failed`                |
| `verification.outcome` | 적용 후 무엇을 확인했는가 | `device_pending`, `recovery_pending`, `resolved`, `unrecovered` |


예를 들어 승인 상태(`status`)가 `approved`이고 실행 결과(`execution.status`)가 `applied_to_simulator`인 조정안이 있다. 두 단계가 끝났더라도 후속 회복 결과(`verification.outcome`)를 바로 해결됨(`resolved`)으로 채울 수는 없다. 냉각 출력을 바꾸는 명령이 시뮬레이터에 전달되는 시점과 온도가 실제로 내려가는 변화가 관찰되는 시점이 서로 다르기 때문이다. 운영자의 승인 기록, 시뮬레이터 명령 실행 결과, 후속 회복 확인 기록은 단계별로 나뉘어 차례대로 이어진다.

세 필드를 나누어 둔 코드는 웹 화면에서도 운영자의 승인, 시뮬레이터 반영, 환경 회복의 차이를 구분해 보여 주려는 설계로 읽혔다. 다만 데이터 타입에 상태 값이 정의되어 있다는 사실과, 상태가 바뀌는 모든 과정이 실행 수준에서 검증되었다는 사실은 구별해야 한다.


## 내부 서비스의 인증과 권한 경계


상태를 단계별로 나누어 기록하더라도 아무나 조정안을 승인하고 제어 명령을 내릴 수 있어서는 안 된다. [FarmOps MCP의 요청 인증과 문맥 구성 코드](https://github.com/NAMUORI00/smartfarm-rag-ops/blob/426cbe5e0dbc9e62d65ed4fdd5ae58e302d1dd8e/services/farm-mcp/app/main.py#L30)는 내부 서비스 토큰 검사와 요청 문맥 생성을 분리해 처리한다. 먼저 요청의 부가 정보를 담는 **헤더**(header)에서 서비스 토큰을 꺼내 서버의 설정값과 비교한다. 그다음 농장과 행위자, 역할 헤더가 모두 있는지 확인한 뒤, 역할 문자열을 미리 정해 둔 값 목록인 열거형(enum)으로 변환한다.


상위 호출 계층이 전달한 토큰과 문맥 헤더를 검증한 뒤 승인 함수에 들어갈 때는 `OPERATOR` 또는 `ADMIN` 역할을 요구한다. 허가된 내부 서비스의 요청이라는 사실과 설비 조작을 허용할 역할이라는 사실을 코드에서 따로 확인한다. 이때 권한을 판정하는 규칙은 언어 모델이 생성한 설명문이 아니라 서버의 실행 코드 안에 놓여 있다.


![상위 호출 계층이 전달한 토큰과 문맥 헤더를 FarmOps MCP 서버가 검증하고 OPERATOR 또는 ADMIN 역할을 확인해 approve_control을 실행하는 구조도](/images/notion/tech-03-02/image-2.png)


그림 2. FarmOps MCP 서버에서 서비스 토큰 검증과 문맥 구성, 역할 인가를 분리한 요청 처리 구조.


다만 이 구조는 내부 호출자가 넘겨준 헤더를 신뢰한다는 전제 위에서 동작한다. 토큰을 비교하는 함수 하나만으로 외부 접근이 모두 차단된다고 볼 수는 없다. 외부 사용자의 입력이 이 헤더로 그대로 넘어가지 않도록 상위 호출 계층에서 먼저 통제해야 한다. 여기에 배포 환경의 네트워크 노출 범위와 자격 증명 관리까지 함께 맞물려야 권한 경계가 유지된다.


## 승인 재요청 처리와 실행 결과 대조


권한 확인을 통과해 승인 함수에 들어온 뒤에는 같은 조정안이 중복으로 실행되지 않도록 막아야 한다. 예를 들어 시뮬레이터가 제어 명령을 적용했지만 네트워크 문제로 응답이 중간에 사라질 수 있다. 웹 화면에는 실패처럼 표시되므로 운영자가 같은 승인 버튼을 다시 누르게 된다. 이때 승인 여부만 저장해 두었다면 명령을 새로 실행해야 하는지, 이미 처리된 결과를 찾아 돌려줘야 하는지 구분할 수 없다.


[approve_control](https://github.com/NAMUORI00/smartfarm-rag-ops/blob/426cbe5e0dbc9e62d65ed4fdd5ae58e302d1dd8e/services/farm-mcp/app/service.py#L146) 함수를 따라가면 저장된 조정안의 상태에 따라 이 상황을 나누어 처리한다. 먼저 저장된 조정안을 읽어 이미 실행 결과가 있는지 확인하고, 결과가 있으면 완료 감사 기록을 확인한 뒤 기존 조정안을 그대로 반환한다. 반대로 이미 거절된 조정안이라면 새로 실행하지 않고 상태 충돌 응답으로 처리한다. 아직 대기 중인 조정안일 때만 승인자와 승인 시각을 기록해 저장한 뒤, 시뮬레이터와 통신을 이어 주는 **어댑터**(adapter) 호출로 넘어간다.


어댑터를 호출하는 `_execute_with_reconciliation` 함수는 일반적인 게이트웨이 오류가 발생하면 최대 두 번까지 요청을 시도한다. 반면 상태 충돌 오류는 반복해 요청하지 않고 상위 호출자로 바로 전달한다. 시뮬레이터에서 결과가 돌아오면 `_validate_execution` 함수에서 반환값이 원래 조정안과 맞는지 대조한다. 먼저 `simulated_only` 값이 참인지와 실행 ID가 존재하는지 확인한다. 이어서 제안 ID와 농장, 동작, 구역, 그리고 제안부터 실행 결과까지의 기록을 하나로 잇는 **상관 ID**(correlation ID)가 기대한 값과 일치하는지 대조한다.


![승인 요청을 받았을 때 저장된 실행 결과 유무와 거절 상태를 먼저 확인하고 어댑터 호출 결과를 대조해 저장하는 분기 흐름도](/images/notion/tech-03-02/image-3.png)


그림 3. FarmOperationsService에서 확인한 승인 재요청 분기와 실행 결과 대조 흐름(출처: approve_control, _execute_with_reconciliation, _validate_execution 코드 기반).


다만 상관 ID를 대조한다는 것만으로 중복 실행 방지가 완성되지는 않는다. 같은 조정안에 대한 기존 결과 조회, 어댑터와 시뮬레이터 쪽의 실행 기록, 동시에 들어오는 요청에 대한 처리가 모두 맞물려야 한다. 이번 코드 검토에서는 서비스가 기존 결과를 반환하는 분기와 반환값을 대조하는 절차를 확인했고, 동시 요청 시험은 따로 실행하지 않았다.


## 프론트엔드 저장소별 역할 구분


앞에서 본 승인 화면과 백엔드 코드를 찾다 보면 저장소 이름이 비슷해 출처를 혼동하기 쉽다. 조정안 상태를 정의한 `ApiProposal` 타입은 `smartfarm` 저장소 안의 웹 앱(`apps/web`)에 속한다. 반면 별도 저장소인 [smartfarm-frontend의 기본 브랜치](https://github.com/NAMUORI00/smartfarm-frontend/blob/5747a901d6dfa2e0245311bdd453885289d794d6/README.md)는 안내 문서인 `README.md`만 남아 있는 초기 상태다. 따라서 `ApiProposal`을 `smartfarm-frontend` 저장소의 현재 구현으로 소개하면 출처가 어긋난다.


`smartfarm-frontend` 저장소에는 과거 작업 갈래인 `legacy-v2` **브랜치**(branch)가 따로 남아 있다. 이 브랜치의 [Streamlit 진입점](https://github.com/NAMUORI00/smartfarm-frontend/blob/4f72615f0610b8e8a5dd4de484e0f41ee8f9a936/frontend/streamlit/app.py)을 열어 보면 질의응답, 지식 DB 관리, 프롬프트 설정, 시스템 모니터링 탭이 구성되어 있다. 검색 개수와 랭커 설정을 세션 상태에 보관하는 코드도 남아 있지만, 과거 RAG 관리 화면의 흔적일 뿐이다. 이 화면이 현재 `smartfarm` 저장소의 승인 콘솔이나 MCP 서비스와 연결되어 실행된다고 볼 근거는 없었다.


![smartfarm 저장소의 웹 앱 및 MCP 서비스와 smartfarm-frontend 저장소의 기본 브랜치 및 legacy-v2 브랜치 역할을 비교한 구조도](/images/notion/tech-03-02/image-4.png)

같은 프로젝트 이름 아래에서도 화면과 API 코드가 놓인 저장소와 작성 시점이 서로 달랐다. 나중에 구현을 다시 추적할 때 헷갈리지 않도록 두 저장소의 위치와 역할을 나누어 기록했다.


## 결론


이번에 확인한 구조에서는 운영자가 조정안을 허용했다는 기록을 남기고, 시뮬레이터가 반환한 실행 결과를 원래 조정안과 대조하며, 이후의 환경 회복 관찰을 별도 필드에 담는다. 조정안과 실행 결과를 같은 식별자로 묶고 상태를 세 단계로 분리해 두었기 때문에, 화면의 성공 표시가 승인 완료인지, 시뮬레이터 반영인지, 환경 회복인지를 좁혀서 읽을 수 있었다. 나중에 시뮬레이터 대신 실제 설비로 확장하더라도 이 상태 구분을 유지한 채 장치 응답과 관측 결과를 채워 넣는 편이 자연스럽다.


반면 이번 코드 검토만으로 확인되지 않은 동작과 기준도 남아 있다. 승인 버튼을 누르기 직전에 농장 상태가 바뀌었을 때 실행이 실제로 차단되는지는 코드만으로 확인하지 못했다. 회복 판정(`verification.outcome`)에 어떤 시간 기준과 단위를 쓰는지도 추가로 확인해야 한다. 이번에 본 승인 함수 코드만으로는 최신 경보에 대한 재검증까지 보장되는지 알 수 없었으므로, 연구용 상태 재검증 모듈과 서비스의 제어 실행 경로는 각각 따로 따라가 볼 과제다. 다음 글에서는 저장소의 폴더 구분을 배포 환경의 프로세스, 권한, 데이터 저장소 구성과 나란히 놓고 비교한다.
