SmartFarm에서는 조정안의 제안, 운영자 승인, 시뮬레이터 실행, 결과 확인을 별도 상태로 연결했다. 승인 이후에도 실행 실패나 회복 지연이 있을 수 있어 각 단계의 기록을 유지하는 방식으로 과제를 나누었다.


## 승인과 실행 결과 관리


앞 글의 답변 재검증에 이어, smartfarm에서 조정안의 승인, 실행, 회복 확인이 어떻게 분리되어 기록되는지 살펴봤다. 운영자가 조정안을 허용했어도 명령이 실제로 적용되지 않을 수 있고, 적용된 뒤에도 환경이 회복되지 않을 수 있다. 이 세 단계를 하나의 상태로 표시하면 어느 지점에서 멈췄는지 구분이 안 된다.


현재 코드는 시뮬레이터에 대한 제어를 전제로 한다. 실행 성공은 시뮬레이터 반환값을 기준으로 판단한다. 서비스의 반환값과 화면이 받는 타입을 함께 확인했고, 살펴본 버전은 smartfarm의 `426cbe5` 커밋이다.


## 승인, 실행, 확인 상태의 분리


[웹 앱의 ApiProposal 타입](https://github.com/NAMUORI00/smartfarm-rag-ops/blob/426cbe5e0dbc9e62d65ed4fdd5ae58e302d1dd8e/apps/web/src/api.ts#L161)은 승인 상태, 실행 결과, 확인 결과를 각각 담고 있었다. 이 타입은 smartfarm 저장소 안의 웹 앱에 속한다.


| 필드                   | 답하려는 질문        | 값의 예                                                    |
| -------------------- | -------------- | ------------------------------------------------------- |
| status               | 조정안을 허용했는가     | pending_approval, approved, rejected, failed            |
| execution.status     | 명령 적용 결과를 받았는가 | not_executed, applied_to_simulator, failed              |
| verification.outcome | 적용 후 무엇을 확인했는가 | device_pending, recovery_pending, resolved, unrecovered |


승인 상태가 approved이고 실행 결과가 applied_to_simulator여도, 회복 결과를 바로 resolved로 채울 수는 없다. 냉각 출력을 바꾸는 명령과 온도가 실제로 내려오는 변화는 서로 다른 시점에 관찰되기 때문이다.


타입을 나누어 둔 것은 화면에서도 승인, 실행, 회복의 차이를 표현하기 위한 구성으로 읽혔다. 다만 타입에 값이 정의되어 있다는 것과 모든 상태 전이가 실행 수준에서 검증되었다는 것은 별개다.

## 내부 서비스가 신뢰하는 입력


[FarmOps MCP의 요청 인증과 문맥 구성 코드](https://github.com/NAMUORI00/smartfarm-rag-ops/blob/426cbe5e0dbc9e62d65ed4fdd5ae58e302d1dd8e/services/farm-mcp/app/main.py#L30)에서는 내부 서비스 토큰 검사와 요청 문맥 생성을 분리했다.


먼저 전달된 서비스 토큰을 설정값과 비교하고, 농장, 행위자, 역할 헤더가 있는지 확인한 뒤 역할을 열거형으로 변환한다.


이 서버는 내부 호출자가 제공한 헤더를 신뢰하는 구조였다. 외부 사용자 입력을 그대로 이 헤더에 전달하지 않도록 상위 계층에서 통제하는 범위까지 함께 볼 필요가 있었다. 토큰 비교 함수 하나만으로 외부 접근이 차단된다고 결론 내릴 수는 없었다. 배포 시의 네트워크 노출 범위와 자격 증명 관리도 이 경계에 연결되어 있었다.


승인 함수에서는 OPERATOR 또는 ADMIN 역할을 요구한다. 인증된 요청이라는 사실과 해당 조작을 허용할 역할이라는 사실이 코드에서 분리되어 있었다. 권한 판정 로직은 모델이 생성한 설명문이 아닌 실행 코드 안에 있다.


## 승인 요청을 다시 받았을 때


[approve_control](https://github.com/NAMUORI00/smartfarm-rag-ops/blob/426cbe5e0dbc9e62d65ed4fdd5ae58e302d1dd8e/services/farm-mcp/app/service.py#L146)을 따라가면, 먼저 저장된 제안을 읽고 이미 실행 결과가 있는지 확인한다.


결과가 있으면 완료 감사 기록을 확인한 뒤 기존 제안을 반환한다. 거절된 제안은 충돌 응답으로 처리하고, 대기 중인 제안이라면 승인자와 승인 시각을 붙여 저장한 뒤 어댑터 호출로 넘어간다.


이 분기가 의미 있는 상황을 하나 들면, 시뮬레이터가 명령을 적용했지만 응답이 유실된 경우다. 화면에는 실패처럼 보이고, 같은 버튼을 다시 누를 수 있다. 이때 명령을 새로 만드는 것과 기존 제안의 결과를 찾아 반환하는 것은 다른 작업이고, 승인 상태만 저장해서는 둘을 구분할 수 없다.


`_execute_with_reconciliation`은 일반적인 게이트웨이 오류에 대해 최대 두 번 요청한다. 충돌 오류는 반복하지 않고 위로 전달한다. 반환된 결과에는 `simulated_only`가 참인지, 제안 ID, 농장, 동작, 구역, 상관 ID가 기대한 값과 맞는지, 실행 ID가 있는지를 확인하는 절차도 있다.


![03-02-02.png](/images/notion/tech-03-02/image-2.png)


그림 2. FarmOperationsService에서 확인한 승인 재요청과 결과 대조의 주요 분기. 일반 게이트웨이 오류의 재요청은 본문에 별도로 설명했다. 출처: 승인, 실행 결과 대조 코드의 approve_control, _execute_with_reconciliation, _validate_execution.


상관 ID는 기록을 연결하는 단서다. 다만 ID가 존재한다는 것만으로 중복 실행 방지가 완성되지는 않는다. 같은 제안에 대한 기존 결과 조회, 어댑터와 시뮬레이터 쪽 기록, 동시 요청 처리까지 맞물려야 한다. 이 글에서는 서비스의 기존 결과 반환과 결과 대조 코드를 확인했고, 동시 요청 시험은 실행하지 않았다.


## 프론트엔드 저장소별 역할


저장소 이름이 겹쳐서 혼동되기 쉬운 부분이 있었다. 별도 저장소인 [smartfarm-frontend의 기본 브랜치](https://github.com/NAMUORI00/smartfarm-frontend/blob/5747a901d6dfa2e0245311bdd453885289d794d6/README.md)는 README만 남긴 초기 상태다. 앞서 읽은 ApiProposal 타입은 smartfarm 저장소의 웹 앱에 속하므로, 이 저장소의 현재 구현으로 소개하면 출처가 틀어진다.


과거 `legacy-v2` 브랜치의 [Streamlit 진입점](https://github.com/NAMUORI00/smartfarm-frontend/blob/4f72615f0610b8e8a5dd4de484e0f41ee8f9a936/frontend/streamlit/app.py)에서는 질의응답, 지식 DB 관리, 프롬프트 설정, 시스템 모니터링 탭을 확인했다.


검색 개수와 랭커를 세션 상태에 두는 구성도 있었다. 이것은 과거 RAG 관리 UI의 흔적이며, 현재 smartfarm의 승인 콘솔과 연결되어 실행된다고 볼 근거는 없었다.


같은 프로젝트 이름 아래에서도 화면과 API 코드가 놓인 저장소와 시점이 달랐다. 나중에 같은 구현을 다시 찾아갈 수 있도록 두 저장소의 위치를 함께 남겼다. 각 구현의 역할과 상태를 따로 확인한 기록이다.


## 구현 범위와 후속 검토


이번 코드 읽기에서 유용했던 구분은 허용, 적용, 회복을 각각 기록하는 방식이었다. 사용자가 허용했다는 사실을 남기고, 반환된 실행 결과를 제안과 대조하며, 이후 관찰은 별도 필드에 담는다. 이 구조 덕분에 화면의 성공 표시가 세 단계 중 어디까지를 뜻하는지 좁혀서 읽을 수 있었다.


승인 직전에 상태가 바뀌었을 때 실제로 차단되는지, 회복 판정에 어떤 시간 기준과 단위를 쓰는지는 별도 확인 과제로 남아 있다. 이 승인 함수의 코드만으로는 최신 경보 재검증까지 보장되는지 확인되지 않았다. 연구용 상태 재검증 모듈과 제품의 실행 경로는 각각 따로 따라갈 필요가 있다.


다음 글에서는 서비스 구성을 실제 실행 환경과 연결해 살펴본다. 저장소의 폴더 구분과 배포 환경의 프로세스, 권한, 데이터 저장소 구분을 나란히 놓고 정리하는 내용이다.


## 작업을 정리하며


승인 버튼 하나 뒤에도 여러 상태가 이어진다. 제안과 실행 결과를 같은 식별자로 연결하면 어느 단계에서 멈췄는지 설명할 수 있다. 실제 장치로 확장할 때도 이 상태 구분을 유지한 채 장치 응답과 관측 결과를 추가하는 편이 자연스럽다.
