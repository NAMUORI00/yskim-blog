Discord 봇에서는 대화 기록을 모델 입력으로 연결하고 관리 명령에 승인 단계를 붙였다. 데이터베이스의 대화 기록과 메모리의 승인 대기 목록이 서로 다른 수명을 가져, 요청, 승인, 실행 결과를 구분하는 문제를 다뤘다.


## 구현과 확인 과정


discord-ai-assistant-bot의 코드를 읽으며 대화 기록과 승인 대기 상태가 각각 어디에 저장되는지 살펴봤다. 대화는 데이터베이스에, 자연어 관리 명령의 승인 대기 목록은 프로세스 메모리에 남는 구조였다. 앞 글에서 정리한 실행 규칙과 상태 구분을 이 두 경로에 대입해 읽었다.


메시지 이벤트와 세션, 도구 호출 개념은 앞 글에서 정리했고, 이번에는 두 경로의 상태가 언제 생기고 사라지는지를 따라갔다. 모델이 응답한 상태, 사용자가 승인한 상태, Discord에 반영된 상태가 코드에서 어떻게 나뉘는지를 중심으로 읽었다. 3185669 커밋의 코드에서 관리 명령 처리 경로를 확인했다.


## 일반 대화와 관리 요청의 진입점


[봇 이벤트 처리](https://github.com/NAMUORI00/discord-ai-assistant-bot/blob/3185669871bee8a98b8cb1fb864f711552bf44bc/src/index.js)는 일반 메시지와 상호작용 이벤트를 나누어 처리한다.


메시지 경로는 봇이 쓴 메시지를 제외하고 멘션, 스레드, 허용 채널 조건을 확인한 뒤 대화 처리로 들어간다. 스레드에서는 허용 채널을 검사할 때 부모 채널 ID를 사용한다.


자연어 관리 요청은 /오리명령의 별도 명령 경로에 있다. [관리자 명령 처리](https://github.com/NAMUORI00/discord-ai-assistant-bot/blob/3185669871bee8a98b8cb1fb864f711552bf44bc/src/commands/oriCommand.js)는 관리자 권한 검사를 통과한 요청으로 실행 계획을 만든다. 모델에 관리자 요청이라고 설명하는 문장만으로 권한을 결정하지 않고, 호출 전에 코드에서 권한 조건을 먼저 확인한다.


2026-09-15 확인한 [Discord 상호작용 문서](https://docs.discord.com/developers/interactions/receiving-and-responding)는 명령과 버튼 등으로 발생하는 interaction에 사용자, 서버, 채널 정보가 포함되는 구조를 설명한다.


이 정보가 요청자를 구분하는 재료가 되지만, 어떤 작업을 허용할지는 봇의 자체 검사와 Discord 권한 조건이 함께 관여한다.


## 채널 기준의 대화 문맥 구성


[대화 저장과 응답 처리](https://github.com/NAMUORI00/discord-ai-assistant-bot/blob/3185669871bee8a98b8cb1fb864f711552bf44bc/src/features/personaChat.js)는 사용자 메시지를 먼저 ChatHistory에 저장하고 최근 기록을 모델 입력으로 조립한다.


저장 행에는 사용자 ID가 있지만, [getRecent](https://github.com/NAMUORI00/discord-ai-assistant-bot/blob/3185669871bee8a98b8cb1fb864f711552bf44bc/src/database/models/serverSettings.js)의 조회 조건은 channel_id다. 같은 채널에서 여러 사용자가 대화하면 문맥도 함께 모이는 구성으로 읽었다.


기본 context_length=20은 최근 기록 행의 개수로 사용된다. 사용자 메시지와 봇 응답을 각각 기록 행으로 센다. 사용자와 봇 응답이 각각 행으로 들어가며, 긴 한 메시지는 짧은 여러 메시지보다 모델 입력을 더 크게 만들 수 있다. 그래서 이 설정만으로 긴 대화의 비용이나 입력 잘림 범위까지 판단하지는 않았다. 토큰 길이 제한은 행 개수와 별도로 살펴볼 항목이다.

그림 1. 채널 대화가 저장과 모델 호출을 거쳐 돌아오는 순서. 출처: 대화 저장, 응답 처리와 ChatHistory 구현을 바탕으로 직접 구성. 데이터베이스 저장과 메시지 전송은 각각 성공 여부를 확인해야 하는 작업이다.


저장 순서도 살펴봤다. 모델 호출이 실패해도 먼저 저장한 사용자 메시지는 남는다. 반대로 봇 응답을 데이터베이스에 저장한 뒤 Discord 전송이 실패하면, 다음 문맥에 사용자가 실제로 보지 못한 응답이 포함될 수 있다. 기록된 답변과 전달된 답변을 구분하는 상태는 이 경우를 추적할 보완 항목으로 정리했다.


동시에 들어온 메시지에 대한 채널별 직렬 처리도 이 함수 안에는 보이지 않았다. 같은 문맥을 바탕으로 두 요청이 겹칠 수 있으며, 비동기 함수를 사용한다는 사실만으로 대화 순서가 보장되지는 않는다. 요청 ID와 입력 문맥의 마지막 기록 ID를 함께 남기면 겹침 여부를 사후에 확인할 수 있다.


## 도구 목록과 실제 인자 검사는 나누어 보기


[자연어 요청을 실행 계획으로 바꾸는 처리](https://github.com/NAMUORI00/discord-ai-assistant-bot/blob/3185669871bee8a98b8cb1fb864f711552bf44bc/src/features/naturalCommandRouter.js)는 등록된 스키마를 모델에 전달하고 반환된 도구 호출이나 JSON 내용을 계획으로 바꾼다.


서버, 채널, 사용자를 합친 식별자를 모델 호출에 넘긴다. 이 식별자는 일반 대화의 채널별 데이터베이스 조회와 다른 문맥에서 쓰인다.


[validateActionPlan](https://github.com/NAMUORI00/discord-ai-assistant-bot/blob/3185669871bee8a98b8cb1fb864f711552bf44bc/src/features/actionRegistry.js)은 등록된 이름과 필수 필드 존재를 검사한다.


스키마에는 정수 범위와 enum도 있지만 이 함수가 그 조건을 모두 검사하지는 않는다. 모델에게 형식을 알려주는 역할과 실행 직전 인자를 검증하는 역할이 분리되어 있는 구조다. 전체 허용 범위는 이 함수뿐 아니라 최종 서비스 함수와 Discord API 쪽 검사까지 걸쳐 있다.


이 등록 방식은 미리 만든 서비스 기능으로 실행 경로를 좁히는 선택으로 읽혔다. 새 도구를 추가하는 경우에는 이름과 스키마 외에도 실행기, 인자 검사, 권한, 실패 응답의 연결을 살펴볼 필요가 있다.


## 승인 대기 목록의 메모리 저장


[실행 계획의 승인과 실행 처리](https://github.com/NAMUORI00/discord-ai-assistant-bot/blob/3185669871bee8a98b8cb1fb864f711552bf44bc/src/features/naturalCommandExecutor.js)는 pendingPlans라는 Map에 요청자, 서버, 채널, 계획, 생성 시각을 넣는다.


데이터베이스 저장이 아니므로 프로세스가 재시작되면 대기 계획은 복원되지 않는다. createdAt을 저장하지만 확인한 승인 함수에는 경과 시간을 비교하는 만료 검사가 없다. 따라서 ‘expired or not found’라는 응답 문구만으로 자동 만료가 구현됐다고 읽지 않았다.


![07-03-02.png](/images/notion/tech-07-03/image-2.png)


그림 2. 관리 명령의 즉시 실행과 승인 대기 경로. 출처: 관리자 명령 처리와 실행 계획의 승인, 실행 처리를 바탕으로 직접 구성. 승인 대기 Map은 프로세스 메모리에 상태를 보관한다.


승인 함수는 요청자가 맞는지 확인한 뒤 대기 항목을 삭제하고 작업을 순차 실행한다. 첫 작업이 성공하고 두 번째가 실패해도 앞선 변경이 자동으로 되돌아가는 트랜잭션은 이 함수에 없다. 또한 승인 없이 실행 가능한 작업은 승인 대기 화면을 만들기 전에 이미 수행된다. 작업별 성공과 실패가 갈리는 중간 상태를 표현할 수 있는 구조다.


남은 확인 항목은 계획 전체의 상태와 각 작업의 상태를 분리하는 것, 실행 시도와 실제 반영 결과를 묶어 기록하는 것이다. 일반 대화 쪽은 전달 여부, 관리 요청 쪽은 승인 여부와 부분 성공 여부가 기록 대상에 해당한다.


다음 글에서는 서로 다른 도구의 검토 의견을 모으는 cross-review-bridge를 읽고, 의견을 받는 일과 변경을 적용하는 일이 어떻게 나뉘는지 살펴본다.


## 작업을 정리하며
