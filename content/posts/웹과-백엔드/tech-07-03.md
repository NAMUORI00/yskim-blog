챗봇 하나에 일상 대화 기능과 서버 관리 기능을 함께 넣으면, 두 기능이 기억해 두어야 하는 정보의 유지 기간이 서로 달라진다. 일상 대화는 앞선 이야기를 이어 가야 하므로 기록을 데이터베이스에 오래 남겨 둔다. 반면 서버 설정을 바꾸는 관리 명령은 관리자가 승인할 때까지만 대기 정보를 잠깐 붙잡아 두었다가 지우는 경우가 많다.


앞선 글의 이벤트 처리와 도구 호출, 승인 기록 기준을 코드에 대입해 보려고 `discord-ai-assistant-bot` 저장소의 `3185669` 커밋을 읽었다. 이 봇도 일반 대화 기록은 데이터베이스에 저장하고, 일상적인 말인 자연어로 내리는 관리 명령의 승인 대기 목록은 실행 중인 프로세스 메모리에만 둔다. 두 경로의 상태가 생기고 사라지는 과정을 따라가며, 모델이 만든 응답과 사용자 승인, 실제 Discord 반영 결과가 코드에서 어떻게 나뉘는지 확인했다.


## 일반 대화와 관리 요청의 진입 경로


두 경로의 상태가 나뉘는 지점을 보려면 먼저 사용자 입력이 봇에 들어오는 진입 경로를 확인해야 한다. [봇 이벤트 처리](https://github.com/NAMUORI00/discord-ai-assistant-bot/blob/3185669871bee8a98b8cb1fb864f711552bf44bc/src/index.js) 코드는 채팅창에 적는 일반 메시지와, 명령어나 버튼을 누를 때 발생하는 **상호작용**(interaction) 이벤트를 나누어 받는다. 일반 메시지 경로에서는 먼저 봇 자신이 쓴 메시지를 걸러 내고, 멘션 여부나 채널 안의 하위 대화방인 스레드, 허용 채널 조건을 확인한 뒤 대화 처리로 넘어간다. 대화가 스레드에서 일어날 때는 그 스레드가 속한 부모 채널 ID를 기준으로 허용된 채널인지 검사한다.


반면 자연어로 서버를 제어하는 관리 요청은 `/오리명령`이라는 별도 슬래시 명령 경로를 탄다. [관리자 명령 처리](https://github.com/NAMUORI00/discord-ai-assistant-bot/blob/3185669871bee8a98b8cb1fb864f711552bf44bc/src/commands/oriCommand.js) 코드는 요청자의 관리자 권한을 먼저 확인하고, 이 검사를 통과한 요청으로만 실행 계획을 만든다. 모델에 보내는 지시문인 프롬프트에 관리자 요청이라고 적어 모델이 판단하게 두지 않고, 모델을 호출하기 전에 코드가 권한 조건을 먼저 확인한다.


2026-09-15에 확인한 [Discord 상호작용 문서](https://docs.discord.com/developers/interactions/receiving-and-responding)를 보면 슬래시 명령이나 버튼 클릭으로 발생하는 상호작용 이벤트에는 사용자, 서버, 채널 정보가 함께 담겨 온다. 이 정보가 요청자를 식별하는 재료가 되지만, 실제로 어떤 작업을 허용할지는 Discord의 권한 조건과 봇 내부의 검사 코드가 함께 결정한다.

## 채널 기준 대화 기록과 저장 순서


앞선 두 경로 가운데 일반 대화 경로로 들어온 메시지는 데이터베이스에 쌓여 다음 답변의 배경 정보가 된다. [대화 저장과 응답 처리](https://github.com/NAMUORI00/discord-ai-assistant-bot/blob/3185669871bee8a98b8cb1fb864f711552bf44bc/src/features/personaChat.js) 코드는 사용자 메시지를 받자마자 데이터베이스의 `ChatHistory`에 먼저 저장한다. 그다음 모델이 앞뒤 이야기를 이어 갈 수 있도록 최근 대화 기록을 불러와 대화 **문맥**(context)으로 조립한다. 저장되는 각 행에는 작성자의 사용자 ID가 들어 있지만, 최근 대화를 불러오는 [getRecent](https://github.com/NAMUORI00/discord-ai-assistant-bot/blob/3185669871bee8a98b8cb1fb864f711552bf44bc/src/database/models/serverSettings.js) 함수의 조회 조건은 `channel_id`다. 같은 채널에서 여러 사용자가 돌아가며 대화하면 그 내용이 하나의 문맥으로 함께 모이는 것으로 읽었다.


최근 대화를 조회할 때 쓰는 기본 설정인 `context_length=20`은 불러올 기록 행의 개수다. 사용자 메시지와 봇 응답을 각각 한 행으로 세어 저장하므로, 긴 메시지 한 개가 짧은 메시지 여러 개보다 모델 입력을 더 크게 만들 수 있다. 그래서 행 개수를 정하는 이 설정만으로는 긴 대화의 호출 비용이나 입력이 잘리는 범위까지 판단하지 않았다. 모델이 한 번에 처리하는 글자 조각 단위인 토큰 길이 제한은 행 개수와 별도로 다뤄야 할 항목이다.

그림 2. 채널 대화가 데이터베이스 저장과 모델 호출을 거쳐 전송되는 순서. 출처: 대화 저장, 응답 처리와 ChatHistory 구현을 바탕으로 직접 구성.


데이터베이스 저장과 Discord 전송이 일어나는 순서에 따라 기록과 실제 화면이 어긋날 수도 있다. 코드는 사용자 메시지를 먼저 저장한 뒤 모델을 호출하므로, 모델 호출이 실패하더라도 사용자 메시지는 데이터베이스에 남는다. 반대로 모델 응답을 데이터베이스에 저장한 직후 Discord 전송이 실패하면, 사용자가 실제로는 보지 못한 응답이 다음 대화 문맥에 포함될 수 있다. 이런 불일치를 추적하려면 데이터베이스에 기록된 답변과 사용자에게 전달된 답변을 상태로 구분해야 한다.


동시에 들어온 메시지를 채널별로 한 줄로 세워 차례대로 처리하는 직렬화 장치도 이 함수 안에는 보이지 않았다. 기다리는 작업을 동시에 다루는 비동기 함수를 사용한다는 사실만으로 대화 순서가 보장되지는 않으며, 같은 문맥을 읽은 두 요청이 겹쳐 실행될 수 있다. 요청 ID와 그때 입력 문맥으로 쓴 마지막 기록 ID를 함께 남겨 두면 두 요청이 겹쳤는지 사후에 확인할 수 있다.


## 도구 스키마와 인자 검사의 분리


일반 대화가 이전 기록을 모아 답변 문장을 만든다면, 관리 명령 경로는 사용자의 요청을 봇이 실행할 작업 목록으로 바꾼다. `/오리명령`으로 요청이 들어오면 [자연어 요청을 실행 계획으로 바꾸는 처리](https://github.com/NAMUORI00/discord-ai-assistant-bot/blob/3185669871bee8a98b8cb1fb864f711552bf44bc/src/features/naturalCommandRouter.js)가 먼저 동작한다. 이 모듈은 봇에 등록된 기능 이름과 입력값 규칙을 적은 명세서인 **도구 스키마**(tool schema)를 모델에 전달한다. 그 뒤 모델이 반환한 도구 호출이나 JSON 내용을 실행 계획으로 바꾼다. 이때 모델 호출에는 서버와 채널, 사용자를 합친 식별자를 넘기는데, 채널별 데이터베이스 조회로 문맥을 묶던 일반 대화와는 다른 식별 기준이다.


만들어진 실행 계획은 [validateActionPlan](https://github.com/NAMUORI00/discord-ai-assistant-bot/blob/3185669871bee8a98b8cb1fb864f711552bf44bc/src/features/actionRegistry.js) 함수가 검사한다. 다만 이 함수는 등록된 도구 이름이 맞는지와 필수 필드가 존재하는지까지만 확인한다. 도구 스키마에는 정수 범위나 정해진 값 가운데 하나만 고르는 열거형(`enum`) 조건도 적혀 있지만, 이 함수가 그 세부 조건을 모두 검사하지는 않는다. 모델에게 출력 형식을 알려 주는 역할과 실행 직전에 도구에 넘길 입력값인 인자를 검증하는 역할은 서로 분리되어 있다. 그 결과 실제 허용 범위는 이 함수뿐 아니라 최종 서비스 함수와 Discord API 쪽 검사까지 걸쳐 결정된다.


![도구 스키마 전달, validateActionPlan 검사, 서비스 함수와 Discord API 실행의 세 단계에서 각각 담당하는 인자 확인 범위를 비교한 그림](/images/notion/tech-07-03/image-3.png)


그림 3. 자연어 관리 명령에서 도구 스키마 안내와 단계별 인자 검증이 나뉘는 구조.


이처럼 미리 만든 서비스 기능만 도구로 등록해 두는 방식은 모델이 실행할 수 있는 경로를 좁히는 선택으로 읽혔다. 따라서 새 도구를 추가할 때는 이름과 스키마만 등록하는 데 그치지 않고 실행기, 인자 검사, 권한 확인, 실패 응답이 맞물리는지 함께 확인해야 한다.


## 승인 대기 목록과 부분 실행 상태


기본 검사를 마친 실행 계획은 바로 실행되거나 관리자의 승인을 기다리는 상태로 넘어간다. 이 과정은 [실행 계획의 승인과 실행 처리](https://github.com/NAMUORI00/discord-ai-assistant-bot/blob/3185669871bee8a98b8cb1fb864f711552bf44bc/src/features/naturalCommandExecutor.js) 코드가 맡으며, 승인이 필요한 계획은 메모리 `Map`인 `pendingPlans`에 보관한다. 여기에는 요청자, 서버, 채널, 계획 내용, 생성 시각(`createdAt`)을 함께 담아 둔다. 데이터베이스에 저장하지 않으므로 프로세스가 재시작되면 대기 중이던 계획은 복원되지 않는다. 또한 `createdAt`을 저장하고 `'expired or not found'` 문구도 두었지만, 승인 함수에는 경과 시간을 비교하는 만료 검사가 없었다. 응답 문구만 보고 자동 만료가 구현되었다고 판단하지 않은 이유다.


![권한 검사된 자연어 요청이 계획 생성과 필드 검사를 거친 뒤 승인 필요 여부에 따라 즉시 실행되거나 메모리 Map 저장 및 요청자 승인 후 순차 실행되는 흐름도](/images/notion/tech-07-03/image-4.png)


그림 4. 관리 명령의 즉시 실행 경로와 메모리 Map을 거치는 승인 대기 경로. 출처: 관리자 명령 처리와 실행 계획의 승인, 실행 처리를 바탕으로 직접 구성.


실제 작업이 실행되는 시점도 승인 필요 여부에 따라 나뉜다. 승인 없이 실행할 수 있는 작업은 승인 대기 화면을 만들기 전에 이미 수행된다. 반면 승인이 필요한 경로에서는 승인 함수가 요청자가 맞는지 확인하고 대기 항목을 삭제한 다음, 작업을 차례로 실행한다. 이때 첫 작업이 성공하고 두 번째 작업이 실패하더라도, 앞선 변경을 자동으로 되돌리는 **트랜잭션**(transaction)은 이 함수에 없다. 그 때문에 한 계획 안에서도 작업별 성공과 실패가 갈리는 중간 상태가 생길 수 있다.


## 결론


지금까지 두 경로의 코드를 따라가 보니, 대화가 데이터베이스에 저장되는 것과 관리 명령이 실행되는 것은 완료 기준이 서로 달랐다. 일반 대화는 채널 단위로 데이터베이스에 기록된 뒤 모델 호출과 전송을 거치므로, 저장된 기록과 사용자에게 전달된 응답이 어긋날 수 있다. 관리 명령은 도구 스키마 안내와 단계별 인자 검사가 나뉘어 있고, 메모리의 승인 대기 항목을 지운 뒤 작업을 차례로 실행하므로 부분 성공 상태가 남을 수 있다.


이번에는 `context_length=20` 설정만으로 토큰 길이 제한이나 호출 비용을 판단하지 않았고, 승인 함수에서 시간 만료 검사도 찾지 못했다. 여러 작업 가운데 일부만 성공한 상태를 정확히 설명하려면 계획 전체의 상태와 각 작업의 상태를 나누고, 실행 시도와 반영 결과를 묶어 기록해야 한다. 일반 대화는 응답의 실제 전달 여부와 동시 요청 기록이, 관리 요청은 승인 대기 보관 방식과 승인 여부, 작업별 부분 성공 여부가 다음 개선 기준으로 남는다. 다음 글에서는 여러 도구의 검토 의견을 모으는 `cross-review-bridge`를 읽고, 의견을 받는 일과 변경을 적용하는 일이 어떻게 나뉘는지 확인한다.
