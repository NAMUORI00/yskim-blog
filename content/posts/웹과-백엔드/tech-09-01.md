음원 분리 서비스에서는 Spring의 웹 화면과 FastAPI의 음원 처리 서버를 연결했다. 사용자가 파일을 올린 뒤 분리된 트랙을 재생하고 내려받게 하는 것이 구현의 중심이었다. 그 과정에서 파일 경로, 처리 완료 상태, 로그인과 다운로드 권한을 서로 맞춰야 했다.


## 구현과 확인 과정


2023년 학부 과제로 만들었던 음원 분리 서비스를 다시 정리했다. 로그인과 화면은 Spring Boot가 맡고, 음원을 나누는 처리는 FastAPI와 Spleeter에 연결했다. 파일을 올린 뒤 분리된 트랙을 재생하는 과정에서 두 서버가 어떻게 이어지는지 살펴봤다.


코드를 따라가며 웹 로그인과 Python API의 접근 제어가 별도 경계에 놓여 있음을 확인했다. 브라우저가 처리 서버로 직접 요청을 보내기 때문이다. 이번에는 당시 코드인 `78ee472` 커밋을 기준으로 업로드, 분리, 결과 제공 경로를 나누어 정리했다. 이 글의 근거는 당시 소스 코드이며, 현재 환경의 실행 결과와 분리 품질은 별도 검증 항목이다.


## 브라우저와 Python 처리기의 직접 통신


[Spring의 웹 화면 연결 코드](https://github.com/NAMUORI00/music-splitter-web/blob/78ee4720ca53dcefc896173e265d7601ee6bf2a8/Spring/src/main/java/acc/security/web/SpleeterController.java)는 /spleeter 경로에 대해 화면 템플릿을 반환한다. 음원 파일을 받아서 Python 서버로 중계하는 로직은 이 컨트롤러에 포함되어 있지 않았다.


실제 업로드는 [음원 업로드 화면](https://github.com/NAMUORI00/music-splitter-web/blob/78ee4720ca53dcefc896173e265d7601ee6bf2a8/Spring/src/main/resources/templates/spleeter.html)의 JavaScript가 처리한다.


JavaScript에서 FormData를 구성한 뒤 브라우저가 `http://localhost:8000/audio`로 직접 POST를 보낸다. 응답에 포함된 다운로드 경로에도 같은 호스트 주소를 붙여 오디오 플레이어를 생성한다.


Java 쪽 화면, 사용자 관리 기능과 Python의 음원 처리 라이브러리를 각자의 런타임에서 운영하는 구성이다. 다만 `localhost`는 페이지를 열고 있는 브라우저가 동작하는 컴퓨터를 가리킨다.


개발 PC에서 연결된다는 사실만으로 원격 사용자도 같은 경로를 사용할 수 있다고 보기는 어렵다. 배포 환경의 API 주소와 브라우저에서 접근할 경로가 함께 맞아야 하는 구성으로 읽었다.

## 요청 안의 음원 분리 처리


[음원 처리 서버](https://github.com/NAMUORI00/music-splitter-web/blob/78ee4720ca53dcefc896173e265d7601ee6bf2a8/API/main.py)는 앱 초기화 시점에 spleeter:5stems 설정의 Separator 객체를 생성한다.


모델의 출력 이름은 vocals, drums, bass, piano, other 다섯 종류다. 각 이름은 분리기가 추정한 신호의 범주이며, 출력에는 다른 악기 성분이 섞일 수 있다.


/audio 엔드포인트는 업로드된 파일 전체를 await `file.read`()로 메모리에 읽어 디스크에 저장한 뒤, separate_to_file을 직접 호출한다. 별도 작업 큐에 넣거나 작업 ID를 반환하는 단계 없이, 브라우저는 이 HTTP 요청이 끝날 때까지 로딩 모달을 표시하며 대기한다.


async def로 선언되어 있지만, 내부에서 호출하는 모델 연산 자체가 동기 블로킹이면 이벤트 루프가 그 시간 동안 다른 요청을 처리하지 못한다. [FastAPI의 동시성 설명](https://fastapi.tiangolo.com/async/)에서도 직접 호출하는 일반 동기 함수와 프레임워크가 관리하는 경로 함수의 실행 방식을 구분하고 있다.


분리 호출이 이벤트 루프를 얼마나 점유하는지는 별도 부하 측정으로 확인할 문제이고, async 키워드만으로 동시 처리 성능을 판단하지는 않았다.


디코딩, 분리, 출력 인코딩의 세부 처리는 [Spleeter](https://github.com/deezer/spleeter) 라이브러리 내부에서 이루어진다. 이 저장소의 requirements에는 Spleeter 2.3.2가 명시되어 있었다. 샘플률 변환이나 긴 파일의 처리 구간 분할은 설치된 버전의 기본 설정에 따라 달라지므로, 웹 코드만 보고 원본 오디오 형식이 모두 보존된다고 판단하지 않았다.


## 파일 이름과 요청 식별


원본 파일은 output 디렉터리 아래에 업로드 시 파일 이름 그대로 저장되고, 분리 결과는 확장자를 뺀 이름의 하위 디렉터리에 생성된다. 예를 들어 `song.mp3`를 올리면 song/vocals.wav 같은 경로가 응답에 포함된다. 별도 사용자, 작업 식별자가 없어 사람이 파일을 찾기에는 직관적이지만, 같은 이름의 파일이 올라오면 이전 결과와 구분이 되지 않는다.


`song.mp3`를 다시 올리는 경우뿐 아니라 song.wav처럼 확장자만 다른 파일도 확장자를 제거하면 같은 결과 하위 디렉터리(song/)를 가리키게 된다. 이전 요청의 결과인지 현재 요청의 결과인지 구분하려면 파일 이름 외의 식별자가 있어야 한다. 현재 경로 구성 로직에서 예상되는 충돌 조건이다.

그림 2. 파일 이름을 결과 위치로 사용할 때의 충돌 예제. 출처: API의 경로 구성식을 바탕으로 직접 구성. 작업 ID 방식은 현재 구현이 아닌 후속 검토안이다.


현재 코드는 업로드된 파일 이름을 그대로 저장 경로에 사용하고, 파일 전체를 메모리에 읽는다. 서버가 식별자를 부여하고 저장 경로와 크기, 형식 조건을 검증하는 단계를 두면 운영 범위를 제한하기가 수월해진다. output 디렉터리가 미리 존재하는지 여부도 실행 전 확인이 필요한 조건으로 남아 있다.


## 성공 응답과 실제 재생을 나누어 보기


API는 분리 호출 뒤 예상 파일 경로 다섯 개를 구성해 Success 메시지와 함께 반환한다. 각 WAV 파일이 실제로 존재하고, 정상적으로 디코딩되며, 적절한 길이의 오디오를 담고 있는지 검사하는 로직은 없었다. 다운로드 라우트는 파일 존재 여부를 확인하고, 파일이 없으면 HTTP 404 상태를 지정하는 대신 메시지 객체를 반환했다. 업로드 성공 응답과 플레이어에서 실제 재생이 되는지는 별도로 확인이 필요하다.


인증 경계도 분리되어 있다. Spring 쪽에 사용자 로그인 기능이 있더라도 브라우저가 직접 호출하는 FastAPI 엔드포인트는 같은 권한 검사를 거치지 않는다. API에 설정된 CORS 허용 목록은 브라우저의 출처 정책일 뿐이고, 사용자별 파일 접근 권한을 대체하지 않는다. 이 구분을 인식해야 로그인 화면과 결과 다운로드 사이에 권한 검사가 빠져 있는 구간을 식별할 수 있다.


후속 검토 항목으로는 입력 저장, 처리, 출력 확인, 다운로드 가능 상태를 작업 단위로 기록하는 구조가 있다. 이 구조가 있으면 재시도 시 동일 작업 여부를 판별할 수 있고, 실패한 파일만 선별해 재처리할 수 있다. 이어지는 글에서는 음원 분리 학습 저장소와 Docker 실행 환경을 나누어 읽으며, 모델 학습에 필요한 데이터와 서비스 추론에 필요한 데이터의 차이를 살펴본다.
