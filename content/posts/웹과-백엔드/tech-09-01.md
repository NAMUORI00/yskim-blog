2023년 학부 과제로 만들었던 `music-splitter-web`은 노래 파일에서 목소리와 악기 소리를 분리해 웹에서 바로 듣고 내려받게 하는 서비스였다. 로그인과 웹 화면은 Java 기반의 Spring Boot(이하 Spring 서버)로 만들었다. 음원을 다섯 개 트랙으로 나누는 처리는 Python 기반의 FastAPI(이하 FastAPI 서버)와 음원 분리 도구인 Spleeter에 맡겼다.


역할이 다른 두 서버를 붙여 서비스를 만들 때는 화면이 열리고 파일이 올라가는 것만으로 끝나지 않는다. 두 서버 사이에서 파일 저장 경로와 작업 완료 상태, 그리고 로그인 권한이 어떻게 이어지는지 당시 기록인 `78ee472` 커밋의 소스 코드를 따라가며 다시 짚어 보았다. 이 글은 당시 작성한 코드를 기준으로 요청과 응답 경로를 분석하며, 현재 환경에서의 재실행 결과나 음원 분리 품질은 따로 확인해야 할 항목으로 남겨 두었다.


## 브라우저와 두 서버의 통신 경로


두 서버가 어떻게 연결되어 있는지 보려면, 먼저 사용자가 올린 음원 파일이 어떤 경로를 거쳐 FastAPI 서버에 도착하는지 확인해야 한다. [Spring의 웹 화면 연결 코드](https://github.com/NAMUORI00/music-splitter-web/blob/78ee4720ca53dcefc896173e265d7601ee6bf2a8/Spring/src/main/java/acc/security/web/SpleeterController.java)를 보면 `/spleeter` 경로는 빈 화면 틀(템플릿)만 브라우저에 돌려준다. 이 컨트롤러 코드 안에는 브라우저가 보낸 음원 파일을 받아 FastAPI 서버로 넘겨주는 중간 전달 로직이 없다.


실제 파일 전송은 [음원 업로드 화면](https://github.com/NAMUORI00/music-splitter-web/blob/78ee4720ca53dcefc896173e265d7601ee6bf2a8/Spring/src/main/resources/templates/spleeter.html)에 들어 있는 JavaScript가 직접 맡는다. 스크립트가 전송 데이터를 담는 `FormData`에 파일을 넣어 `http://localhost:8000/audio`로 직접 `POST` 요청을 보낸다. 응답으로 받은 다운로드 경로 앞에도 같은 호스트 주소를 붙여 화면에 오디오 재생기를 만든다. 파일을 올린 뒤 분리된 트랙을 재생하고 내려받는 당시 화면 동작은 저장소의 [당시 데모 영상 보기](https://github.com/NAMUORI00/music-splitter-web#%EB%8D%B0%EB%AA%A8-%EC%98%81%EC%83%81)에서 확인할 수 있다.


![브라우저가 Spring 서버에는 화면 템플릿만 요청하고 FastAPI의 /audio와 /output 엔드포인트로 음원 업로드와 결과 조회를 직접 보내는 구조도](/images/notion/tech-09-01/image-1.png)


그림 1. 브라우저가 Java 중계 없이 화면 서버와 처리 API를 각각 호출하는 실제 구현 흐름도(출처: 웹 화면 연결 코드, 음원 업로드 화면, 음원 처리 서버를 바탕으로 직접 구성).


그림 1처럼 Spring 서버는 화면 제공과 사용자 관리를 맡고, FastAPI 서버는 음원 분리 라이브러리를 실행한다. 다만 브라우저에서 실행되는 JavaScript에 적힌 `localhost`는 서버가 아니라 웹 페이지를 연 사용자의 컴퓨터 자신을 가리킨다. 개발용 PC 한 대에서 두 서버와 브라우저를 함께 띄우면 연결되지만, 배포 환경에서는 외부 브라우저가 `localhost:8000`으로 FastAPI 서버를 찾을 수 없다. 실제로 서비스를 배포하려면 외부에서 접근할 수 있는 API 주소와 브라우저 요청 경로를 함께 맞춰야 한다.


## 단일 요청 안의 음원 분리 과정


브라우저가 보낸 `POST` 요청이 FastAPI 서버에 도착하면, 서버는 요청 하나 안에서 파일을 읽고 분리하는 작업을 차례로 실행한다. [음원 처리 서버](https://github.com/NAMUORI00/music-splitter-web/blob/78ee4720ca53dcefc896173e265d7601ee6bf2a8/API/main.py)는 처음 시작할 때 `spleeter:5stems` 설정으로 음원 분리 객체인 `Separator`를 미리 생성해 둔다. 이 설정은 입력 음원을 목소리와 개별 악기군 단위의 오디오 트랙인 **스템**(stem) 다섯 개로 분리한다. 출력 트랙의 이름은 `vocals`, `drums`, `bass`, `piano`, `other`다. 각 이름은 모델이 추정한 신호 범주일 뿐이어서 실제 결과 파일에는 다른 악기 소리가 섞여 들어갈 수 있다.


`/audio` 경로는 올라온 파일 전체를 `await file.read()`로 메모리에 읽어 디스크에 저장한 뒤 곧바로 `separate_to_file` 함수를 호출한다. 요청을 작업 대기열(큐)에 넣거나 작업 번호를 먼저 돌려주는 단계가 없어서, 브라우저는 이 HTTP 요청 하나가 끝날 때까지 로딩 창(모달)을 띄운 채 기다린다.


![브라우저가 로딩 모달을 띄우고 대기하는 동안 FastAPI의 /audio 엔드포인트 안에서 메모리 읽기, 디스크 저장, 동기 Spleeter 분리 연산이 차례로 실행되는 다이어그램](/images/notion/tech-09-01/image-2.png)


그림 2. 단일 HTTP 요청 안에서 파일 읽기와 동기 분리 연산이 차례로 실행되는 /audio 엔드포인트의 처리 흐름도.


여기서 눈여겨볼 점은 비동기 함수 선언과 실제 모델 연산의 관계다. 코드에서 `/audio` 경로 함수는 여러 요청을 번갈아 처리할 수 있는 비동기 함수(`async def`)로 선언되어 있다. FastAPI는 `async def` 경로 함수를 **이벤트 루프**(event loop)라는 한 줄짜리 작업 관리 흐름 위에서 실행한다. 그런데 그 안에서 앞 작업이 끝나야 다음으로 넘어가는 **동기 함수**로 긴 CPU 연산을 직접 호출하면, 함수가 끝날 때까지 이벤트 루프가 멈춰 다른 요청을 처리하지 못한다. [FastAPI의 동시성 설명](https://fastapi.tiangolo.com/async/)에서도 프레임워크가 스레드 풀(별도 작업 공간)에서 실행하는 일반 경로 함수(`def`)와, 코드 안에서 직접 호출하는 동기 함수의 동작을 구분한다. 물론 `separate_to_file` 호출이 이벤트 루프를 실제로 얼마나 점유하는지는 부하 측정으로 확인해야 할 문제다. 따라서 코드에 `async` 키워드가 적혀 있다는 사실만으로 동시 처리 성능을 단정할 수는 없다.


압축된 오디오를 푸는 디코딩과 분리 연산, 결과 파일을 만드는 인코딩의 세부 과정은 모두 [Spleeter](https://github.com/deezer/spleeter) 라이브러리 내부에서 처리된다. 저장소의 `requirements` 파일에는 Spleeter `2.3.2` 버전이 적혀 있다. 1초당 소리 값을 몇 번 기록할지 정하는 **샘플링 레이트**(sample rate) 변환이나 긴 오디오 파일의 구간 분할 방식은 설치된 라이브러리의 기본 설정을 따른다. 따라서 웹 서버 코드만 보고 원본 오디오의 형식이 그대로 유지된다고 보기는 어렵다.


## 파일 이름 기반 저장 경로와 충돌


분리 연산이 끝난 뒤 결과 파일을 디스크에 저장하는 단계에서는, 파일 이름을 그대로 경로로 쓰는 방식 때문에 서로 다른 요청이 같은 폴더에 겹치는 문제가 생긴다. 예를 들어 `song.mp3`를 올리면 서버는 원본 파일을 `output` 폴더 아래에 원래 이름 그대로 저장한다. 이어서 분리된 다섯 개 트랙은 확장자를 뺀 파일 이름으로 하위 폴더를 만들어 그 안에 생성하므로, 응답에는 `song/vocals.wav` 같은 경로가 담긴다. 사용자 ID나 요청마다 서버가 붙이는 고유 번호인 **작업 ID**를 쓰지 않아 폴더 구조는 단순하지만, 같은 이름의 파일이 다시 올라오면 이전 결과와 구분할 방법이 없다.


`song.mp3`를 두 번 올리는 경우만 문제가 되는 것도 아니다. 한 사용자가 `song.mp3`를 올리고 다른 요청에서 `song.wav`를 올리더라도, 확장자를 떼어 내면 둘 다 같은 결과 폴더인 `output/song/`을 가리킨다.


![song.mp3와 song.wav가 확장자 제거 후 같은 output/song/ 폴더로 모여서 충돌하는 흐름과 작업 ID로 분리하는 후속 검토안 다이어그램](/images/notion/tech-09-01/image-3.png)


그림 3. 확장자를 뺀 파일 이름을 결과 경로로 쓸 때 서로 다른 요청이 같은 폴더에 겹치는 충돌 예시와 작업 ID 후속 검토안(출처: API의 경로 구성식을 바탕으로 직접 구성).


그림 3처럼 현재 경로 생성 방식에서는 확장자만 다른 파일도 같은 폴더에 결과를 덮어쓰게 된다. 어느 요청이 만든 결과인지 구분하려면 파일 이름 대신 서버가 발급한 작업 ID로 저장 경로를 나눠야 한다. 또한 현재 코드는 파일 전체를 한 번에 메모리로 읽고 업로드된 파일 이름을 경로에 그대로 쓴다. 서버가 고유 식별자를 부여하고 저장 경로와 파일 크기, 형식 조건을 검증하는 단계를 두면 운영 범위를 제한하기가 수월해진다. 실행 전에 `output` 폴더가 미리 존재하는지도 따로 확인해야 할 조건으로 남아 있다.


## 결과 파일 확인과 로그인 권한의 공백


파일이 디스크에 저장된 뒤 브라우저로 돌아가는 응답과 다운로드 경로에도 짚어 볼 공백이 두 가지 있다. 첫째는 결과 파일의 생성 여부를 확인하지 않는 작업 완료 판정이다. `/audio` 경로는 `separate_to_file` 호출이 끝나면 다섯 개 트랙의 예상 파일 경로를 문자열로 조합해 `Success` 메시지와 함께 반환한다. 이때 각 WAV 파일이 디스크에 실제로 생성되었는지, 소리 데이터가 정상적으로 디코딩되는지, 오디오 길이가 적절한지 확인하는 검사 로직은 없다. 파일 다운로드 경로 역시 파일 존재 여부는 확인하지만, 파일이 없을 때 HTTP `404` 상태 코드(찾을 수 없음)를 내려주는 대신 일반 메시지 객체를 반환한다. 즉 업로드 요청이 `Success` 응답을 받았다는 사실과 브라우저 재생기에서 다섯 트랙이 모두 정상 재생된다는 사실 사이에는 확인되지 않은 간격이 있다.


둘째는 두 서버 사이에서 끊어진 로그인 권한 검사다. Spring 서버에 로그인 기능을 두었더라도, 브라우저가 직접 호출하는 FastAPI 서버는 Spring 서버의 로그인 상태(세션)를 공유하거나 검사하지 않는다. FastAPI 서버에 설정된 **교차 출처 리소스 공유**(CORS) 허용 목록은 브라우저가 다른 주소(출처)의 서버로 요청을 보낼 수 있게 열어 주는 규칙이다. 이 설정만으로는 로그인한 사용자가 자기 파일에만 접근하도록 제한하지 못한다.


![Spring 서버는 로그인 세션을 확인해 화면을 반환하지만 FastAPI 서버는 CORS 출처만 확인하고 사용자 권한 검사와 출력 파일 확인 없이 동작하는 경계 비교도](/images/notion/tech-09-01/image-4.png)


그림 4. Spring의 로그인 검사와 분리된 채 호출되는 FastAPI의 권한 검사 공백과 파일 미검증 응답 구조.


그림 4처럼 웹 화면 진입에는 로그인이 필요하지만, 정작 음원을 올리고 결과 파일을 내려받는 API 구간에는 사용자 권한 검사가 빠져 있다. 이 구조에서 다음으로 보완할 지점은 입력 저장, 분리 처리, 출력 파일 확인, 재생 가능 상태를 작업 ID 단위로 기록하는 것이다. 이 기록이 있으면 요청을 다시 시도할 때 같은 작업인지 판별할 수 있고, 실패한 파일만 골라 다시 처리할 수 있다. 로그인한 사용자 정보도 이 작업 ID에 함께 묶어야 본인이 요청한 결과 파일만 내려받도록 제어할 수 있다.


## 결론


서로 다른 두 서버를 연결해 서비스를 만들 때는 요청을 주고받는 것만큼이나 저장 경로 분리, 작업 완료 기준, 접근 권한을 한 줄기로 묶는 일이 중요하다. `78ee472` 커밋 코드를 따라가며 확인한 결과, 확장자를 뺀 파일 이름을 그대로 경로로 쓰면 서로 다른 요청의 저장 폴더가 겹친다. 또한 결과 WAV 파일의 실제 생성 여부를 검증하지 않고 응답을 돌려주며, Spring 서버의 로그인 권한 검사가 FastAPI 서버까지 이어지지 않는 공백도 확인했다. 반면 `separate_to_file` 호출이 이벤트 루프를 실제로 얼마나 점유하는지와 원본 오디오 형식이 유지되는지는 코드만으로는 단정할 수 없다. 현재 환경에서의 재실행 결과와 음원 분리 품질 역시 따로 검증해야 할 항목으로 남아 있다.


Spring 서버 안에서 입력값 검사와 작성자 권한 확인을 어떻게 연결했는지는 [Spring 게시판의 입력 검사와 작성자 권한](https://blog.namuori.net/posts/tech-13-01/)에서 이어서 다룬다. 오디오 연재의 다음 글에서는 음원 분리 모델의 학습 저장소와 Docker 실행 환경을 따라가며, 모델 학습에 쓰는 데이터와 웹 서비스 추론에 쓰는 데이터가 어떻게 다른지 비교한다.
