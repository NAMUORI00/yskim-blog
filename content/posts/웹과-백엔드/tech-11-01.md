글을 모아 두고 관리하는 콘텐츠 관리 시스템(CMS)으로 Notion을 쓰면, 원본 글을 고치는 곳과 블로그 화면을 만드는 코드가 분리된다. Notion 페이지에서는 제목과 날짜 같은 페이지 속성과 문단, 그림을 담은 본문 조각을 서로 다른 단계로 나누어 불러온다. 만약 Notion 페이지에는 본문과 그림이 다 들어 있는데 블로그 화면에는 제목만 나온다면, 페이지 속성은 읽었지만 본문 조각을 끝까지 가져오지 못한 상태일 수 있다.


이처럼 속성과 본문을 조회하는 경로가 나뉘어 있어서, 안에 겹쳐 들어간 내용이나 첨부 파일을 빠짐없이 웹 문서로 옮기려면 각 단계의 변환 규칙을 따로 챙겨야 한다. 이 글에서는 블로그 저장소인 `NAMUORI00/yskim-blog`의 특정 기록 시점(`9dd7a22` 커밋)을 기준으로 변환 코드를 따라간다. Notion 페이지의 제목과 본문, 이미지가 어떤 과정을 거쳐 문서 구조를 간단한 기호로 적은 **Markdown** 문서가 되고 각 경계에서 어떤 검사를 거치는지 확인했다.


## 페이지 속성과 본문 블록의 분리


변환 과정은 Notion 데이터베이스에 저장된 글을 페이지 속성과 본문 두 부분으로 나누어 읽는 데서 시작한다. 제목, 날짜, 분류처럼 글을 설명하는 기본 정보는 페이지 속성에 들어간다. 반면 실제 글 내용은 문단, 그림, 코드처럼 본문을 한 조각씩 나눈 **블록**(block)의 모음으로 이루어진다. [Notion의 블록 문서](https://developers.notion.com/reference/block)에서도 블록을 개별 콘텐츠 조각으로 정의하며, 블록 유형마다 담는 데이터 구조가 다르다고 설명한다.


[Notion 글 변환 코드](https://github.com/NAMUORI00/yskim-blog/blob/9dd7a2227d53f1f82fd5a539afce4c1bc35d653f/scripts/notion-content.mjs)의 `pageToPost` 함수는 먼저 페이지 속성에서 제목(`title`), 글의 고유 주소 이름인 `slug`, 날짜, 카테고리, 태그를 읽는다. 이렇게 읽은 값으로 Markdown 문서 맨 앞에 적는 설정 정보인 **머리말**(frontmatter)을 만든다. 이때 Posts 데이터베이스의 `PublishedAt` 속성은 발행 날짜로, `Excerpt`는 요약문으로, `CanonicalUrl`은 원문 주소로 연결한다. Notion 화면에서 데이터베이스 속성 이름을 바꾸면 이 연결이 깨지므로 변환 코드의 속성 대응 부분도 함께 고쳐야 한다.


본문을 아무리 길게 작성했더라도 사이트가 요구하는 기본 정보가 빠져 있으면 웹 문서로 만들 수 없다. 그래서 변환 코드는 본문을 읽기 전에 필수 속성 항목이 모두 들어 있는지부터 먼저 검사한다. 제목, `slug`, 날짜, 카테고리 가운데 하나라도 없거나 태그가 비어 있으면 바로 오류를 내고 변환을 멈춘다. 필수 속성이 빠진 페이지가 웹 화면을 그리는 다음 단계로 넘어가지 못하게 미리 차단하기 위해서다.

## 블록 유형별 변환과 중첩 블록 보존


필수 속성 검사를 통과하면 본문 블록을 유형에 맞게 하나씩 Markdown으로 바꾼다. 만약 코드 블록의 줄바꿈을 일반 문단처럼 합쳐 버리거나 첨부 파일을 단순 글자 주소로만 남기면, 원래 Notion 페이지에 있던 구조 정보가 사라진다. 원본 자료의 구조와 역할을 웹 화면에서도 그대로 유지하려면 블록 유형마다 변환 방식을 나누어야 한다. 그래서 변환 코드를 볼 때도 각 블록이 화면에 어떻게 보이는지와 원문의 어떤 정보를 보존하는지를 함께 확인했다.


기본 변환에는 `notion-to-md` 라이브러리를 쓰고, 원래 표현을 살리기 어려운 블록에는 `installCustomTransformers`로 별도 변환기를 등록한다. 예를 들어 수식 블록은 블록 수식 표기로 바꾸고, 글자로 도식을 그리는 Mermaid 코드는 도식용 HTML로 바꾼다. 나머지 프로그래밍 언어는 기본 코드 블록 처리에 맡긴다. 영상과 오디오 블록은 재생 플레이어로 바꾸고, PDF 블록은 미리보기 화면과 다운로드 링크를 함께 갖춘 형태로 변환한다.


![Notion 블록의 유형을 확인해 일반 문단과 목록, 수식과 Mermaid, 영상과 PDF를 각각 알맞은 표현으로 변환하는 구조도](/images/notion/tech-11-01/image-2.png)


그림 2. Notion 블록의 유형과 역할에 따라 기본 Markdown 변환과 별도 변환기를 나누는 구조(출처: installCustomTransformers 코드를 바탕으로 직접 구성).


코드를 읽다가 강조 상자 블록(Callout)에는 별도 변환기를 등록하지 않았다는 주석이 눈에 들어왔다. 강조 상자 안에는 상단 문장뿐만 아니라 코드 블록이나 목록처럼 다른 블록이 겹쳐 들어갈 수 있는데, 이처럼 블록 안쪽에 담긴 블록을 **자식 블록**이라고 부른다. 문자열 하나만 돌려주는 사용자 정의 변환기를 쓰면 상자 맨 위의 한 문장만 남고 그 안쪽의 자식 블록이 빠질 수 있다. 그래서 변환 코드는 강조 상자를 라이브러리의 기본 처리에 맡겨 안쪽에 중첩된 코드 블록과 목록까지 끝까지 따라가며 변환한다.

## 분류별 저장 경로와 고유 주소 분리


본문 블록 변환을 마친 Markdown 문서는 파일로 저장된 뒤 블로그의 공개 웹 주소와 연결된다. [글의 분류별 저장 처리](https://github.com/NAMUORI00/yskim-blog/blob/9dd7a2227d53f1f82fd5a539afce4c1bc35d653f/scripts/content-paths.mjs) 코드는 변환된 문서를 먼저 파일로 저장하고 카테고리별 폴더로 나누어 정리한다. 반면 독자가 접속하는 공개 주소는 [글의 공개 주소 생성](https://github.com/NAMUORI00/yskim-blog/blob/9dd7a2227d53f1f82fd5a539afce4c1bc35d653f/src/lib/posts.ts) 코드에서 저장 폴더 위치와 상관없이 글에 지정한 `slug`만으로 결정하며, 주소 형식은 `/posts/{slug}/`다.


예를 들어 같은 글을 연구 자료 폴더에서 개발 기록 폴더로 옮기더라도 `rag-notes`라는 `slug`를 그대로 두면 공개 링크는 바뀌지 않는다. 글의 분류를 바꾸는 일과 공개 주소를 바꾸는 일은 독자가 기존 링크로 글을 찾아오는 데 서로 다른 영향을 주기 때문이다.


![연구 자료 폴더에서 개발 기록 폴더로 rag-notes.md 파일을 옮겨도 slug 값을 기준으로 /posts/rag-notes/ 공개 주소가 유지되는 구조도](/images/notion/tech-11-01/image-4.png)


그림 4. 카테고리별 저장 폴더 위치와 상관없이 고유 주소 이름(slug)으로 공개 URL을 유지하는 구조.


본문 안에서 다른 Notion 페이지를 가리키는 `link_to_page` 블록 변환기를 확인해 보니 원본 Notion URL을 그대로 만들고 있었다. 연결된 페이지가 블로그에 발행되어 있더라도 공개 주소로 자동 변환한다는 근거는 코드에서 찾지 못했다. 연재 글 링크가 편집 원본 대신 공개 블로그 글을 가리키게 하려면 Notion 페이지 ID와 공개 URL을 짝지어 주는 처리가 따로 필요하다.


## 문서 형식 검사와 빌드 구성


폴더에 저장된 Markdown 문서는 웹사이트 화면을 만드는 빌드 도구인 Astro로 넘어가며 한 번 더 검사를 거친다. [웹 콘텐츠 형식 검사](https://github.com/NAMUORI00/yskim-blog/blob/9dd7a2227d53f1f82fd5a539afce4c1bc35d653f/src/content.config.ts) 코드는 저장된 문서를 Astro 컬렉션으로 불러오면서 `title`, `date`, `slug` 같은 머리말 항목의 자료형과 형식을 다시 확인한다. 데이터가 지켜야 할 항목과 형식 규칙을 **스키마**(schema)라고 하며, [Astro 콘텐츠 컬렉션 문서](https://docs.astro.build/en/guides/content-collections/)가 안내하는 스키마 기반 구조 검사가 이 단계에서 이루어진다. 앞단의 Notion 속성 검사가 외부 API 입력을 거른다면, 여기서는 빌드 엔진이 읽어들일 로컬 파일의 형식을 서로 다른 경계에서 다시 보장한다.


한편 코드의 기본 문서 문자열 일부에는 또 다른 정적 사이트 생성기인 `Hugo`라는 이름이 남아 있었다. 하지만 실제 [웹사이트 빌드 설정](https://github.com/NAMUORI00/yskim-blog/blob/9dd7a2227d53f1f82fd5a539afce4c1bc35d653f/astro.config.mjs)과 페이지 주소를 연결하는 라우트 코드는 모두 Astro 구성을 따르고 있었다. 정적 자산 폴더 구조와 기존 URL 형태만 그대로 재사용한다는 주석도 함께 적혀 있었다. 남아 있는 문자열 한 줄보다 실제 빌드 설정과 라우트 코드가 현재 실행 구조를 정확히 보여 준다.


## 결론


지금까지 확인한 전체 변환 경로는 Notion에 있는 편집 원본을 건드리지 않고 웹용 Markdown 문서와 자산을 새로 만들어 낸다. 페이지 속성과 본문 블록을 따로 읽은 뒤 블록 유형별 변환기와 기본 처리를 거쳐 안에 겹쳐 들어간 블록까지 보존한다. 변환된 파일은 카테고리별 폴더에 나누어 저장하되 공개 주소는 `slug`로 유지하고, 외부 입력과 로컬 파일의 두 경계에서 필수 항목과 형식을 각각 검사한다.


이번에는 변환 코드의 입력과 출력 형태까지만 확인했고 실제 사이트를 새로 배포하지는 않았다. 파일이 정상적으로 생성되더라도 표나 중첩 블록, 수식, 그림 캡션이 브라우저 화면에 의도대로 나오는지는 따로 확인해야 한다. 대표 블록 유형을 모아 둔 짧은 시험용 글 하나로 Notion 원문과 생성된 Markdown 문서, 실제 브라우저 화면을 나란히 대조해 볼 차례다. 이어지는 다음 글에서는 글 상태에 따른 발행 대상 수집 기준과 만료되는 임시 이미지 주소의 로컬 저장 처리, 빌드 결과를 공개 사이트에 반영하는 배포 과정을 다룬다.
