Notion을 블로그의 편집 원본으로 사용하며 제목, 본문, 이미지를 웹 문서로 변환하는 흐름을 구성했다. 속성 조회와 본문 블록 조회가 별도여서 중첩 블록과 자산을 끝까지 가져오는 문제를 중심으로 정리했다.


## 구현과 확인 과정


yskim-blog의 변환 경로를 살펴보며, Notion 페이지의 제목, 본문, 이미지가 각각 어떤 입력으로 들어와 웹 문서가 되는지 정리해 봤다. Notion에서 본문과 그림이 보이는데 블로그에는 제목만 나오는 경우, 페이지 속성은 읽혔지만 본문 블록을 충분히 가져오지 못한 상태일 수 있다.


기준은 NAMUORI00/yskim-blog의 9dd7a22 커밋이다. CMS, 페이지와 블록, Markdown의 기초를 알고 읽으면 흐름을 따라가기 좋다. Notion을 편집 원본으로 두면 글을 고치는 장소와 웹 화면을 만드는 코드가 분리된다. 이 글에서는 그 사이에서 어떤 정보가 옮겨지고 어떤 검사가 개입하는지를 중심으로 살펴봤다.


## 페이지 속성과 본문 블록


Notion 데이터베이스에서 제목, 날짜, 분류는 페이지 속성이고, 본문은 문단, 그림, 코드 등의 블록으로 구성된다. [Notion의 블록 문서](https://developers.notion.com/reference/block)도 블록을 콘텐츠 조각으로 설명하며 유형마다 담는 정보가 다르다고 안내한다.


[Notion 글 변환 코드](https://github.com/NAMUORI00/yskim-blog/blob/9dd7a2227d53f1f82fd5a539afce4c1bc35d653f/scripts/notion-content.mjs)의 pageToPost는 속성에서 title, slug, 날짜, 카테고리, 태그 등을 읽는다.


Posts 데이터베이스에서는 PublishedAt을 날짜로, Excerpt를 요약으로, CanonicalUrl을 원문 주소로 해석한다. 화면에서 속성 이름을 바꾸면 이 대응 관계가 어긋나므로, 변환 코드 쪽 매핑도 함께 확인할 지점이다.


제목, slug, 날짜, 카테고리가 없거나 태그가 비어 있으면 변환은 오류를 낸다. 본문이 충분히 작성되어 있다는 사실과 사이트가 요구하는 메타데이터를 갖췄다는 사실은 별개였다. 현재 코드에서는 이 필수 항목 검사가 변환 초기에 위치해 있어, 누락된 정보를 가진 페이지가 렌더링 단계까지 흘러가는 경우는 제한된다.

## 블록 유형별 콘텐츠 변환


기본 본문 변환은 notion-to-md를 사용하고 일부 유형은 별도 변환기를 등록한다. 수식은 블록 수식 표기로, Mermaid 코드는 도식용 HTML로 옮긴다. 다른 프로그래밍 언어의 코드 블록은 기본 코드 처리에 맡긴다. 영상, 오디오는 플레이어, PDF는 미리보기와 다운로드 링크를 가진 구조로 바꾼다.


블록 유형마다 변환기를 두는 이유는 자료의 역할을 출력에서도 유지하기 위해서다. 코드의 줄바꿈을 문단처럼 합치거나 첨부파일의 주소만 문자로 남기면, 원래 페이지에서 읽을 수 있었던 구조 정보가 빠진다. 변환기를 읽을 때도 "무엇을 보여 주는가"와 "어떤 원문 정보를 보존하는가"를 함께 봤다.


Callout에는 별도 변환기를 등록하지 않았다는 주석이 눈에 들어왔다. 문자열 하나를 반환하는 사용자 변환기가 중첩된 자식 블록을 빠뜨릴 수 있어 기본 처리에 맡긴다는 설명이었다. 위에 보이는 한 문장만 변환하는 것과 안쪽의 코드, 목록까지 따라가는 것은 다른 작업이다.

## 콘텐츠 경로와 글 주소 구성


변환된 글은 먼저 저장된 뒤 카테고리별로 분류된다. 공개 주소는 폴더 위치와 무관하게, 글에 지정한 고유 주소명인 slug로 결정된다. 주소 형식은 `/posts/{slug}/`다.


[글의 분류별 저장 처리](https://github.com/NAMUORI00/yskim-blog/blob/9dd7a2227d53f1f82fd5a539afce4c1bc35d653f/scripts/content-paths.mjs) [글의 공개 주소 생성](https://github.com/NAMUORI00/yskim-blog/blob/9dd7a2227d53f1f82fd5a539afce4c1bc35d653f/src/lib/posts.ts)


예를 들어 같은 글을 연구 자료 폴더에서 개발 기록 폴더로 옮겨도, 고유 주소명 rag-notes를 유지하면 글 링크는 그대로 만들 수 있다. 분류를 바꾸는 일과 공개 주소를 바꾸는 일은 독자가 기존 링크로 글을 찾아오는 데 서로 다른 영향을 준다.


[웹 콘텐츠 형식 검사](https://github.com/NAMUORI00/yskim-blog/blob/9dd7a2227d53f1f82fd5a539afce4c1bc35d653f/src/content.config.ts)는 Markdown을 Astro 컬렉션으로 읽고 title, date, slug 등의 형태를 검사한다.


[Astro 콘텐츠 컬렉션 문서](https://docs.astro.build/en/guides/content-collections/)에서 설명하는 스키마 기반 구조 검사가 이 단계에 해당한다. 앞 단계의 Notion 속성 검사와 여기의 문서 스키마 검사는 서로 다른 입력 경계에서 각각 동작하고 있었다.


## 기존 명칭과 현재 실행 경로


일부 기본 문서 문자열에는 Hugo라는 이름이 남아 있었다. 그러나 [웹사이트 빌드 설정](https://github.com/NAMUORI00/yskim-blog/blob/9dd7a2227d53f1f82fd5a539afce4c1bc35d653f/astro.config.mjs)과 현재 페이지 코드는 Astro 구성을 따르고 있었다.


정적 자산 폴더와 기존 URL 형태를 재사용한다는 주석도 확인했다. 남아 있는 문자열 한 줄보다는 실제 빌드, 라우트 구성이 현재 구조를 더 정확히 반영하고 있었다.


Notion 내부 페이지 링크도 확인했다. link_to_page 변환기는 Notion URL을 생성하는 구조였다. 연결된 페이지가 블로그에도 존재하더라도 자동으로 공개 slug 주소로 바뀐다는 근거는 코드에서 찾지 못했다. 연재 링크가 편집 원본을 가리킬지 공개 글을 가리킬지 제어하려면, 페이지 ID와 공개 URL의 대응 관계를 별도로 관리하는 부분이 필요하다.


## 변환 결과의 검토 항목


전체적으로, 편집 원본을 바꾸지 않고 웹용 문서와 자산을 생성하는 구조였다. 파일 생성 후에도 표, 중첩 블록, 수식, 그림 캡션의 실제 화면 표시를 확인해야 한다. 대표 블록 유형을 포함한 짧은 글 하나로 원문과 생성 문서를 비교하고, 브라우저에서 실제 렌더링까지 확인하는 과정이 남아 있다.


이번에는 변환 코드의 입력과 출력 형태까지 확인했으며 사이트를 새로 배포하지는 않았다. 다음 글은 글 상태에 따른 수집, 임시 이미지 주소의 처리, 빌드 결과의 공개 사이트 반영 과정으로 이어진다.


## 작업을 정리하며


콘텐츠 변환의 기준은 글 한 편이 이미지와 링크까지 온전히 보이는지다. 대표 블록을 모은 짧은 글로 원문, 생성 문서, 공개 화면을 대조하면 누락 지점을 찾기 쉽다. 변환과 화면 검증을 같은 발행 절차에 두는 것이 중요하다.
