Spring 게시판을 만들며 회원 로그인과 게시글 생성, 수정, 삭제 흐름을 연결했다. 화면 폼과 API가 서로 다른 경로로 같은 데이터를 저장하므로, 입력 검증과 작성자 권한을 어디에서 공통으로 처리할지가 핵심 과제였다.


## 구현과 확인 과정


2023년 Spring Boot와 JPA를 익히면서 만들었던 게시판을 다시 살펴봤다. 글을 입력하고 저장하는 기능은 CRUD라는 이름으로 묶이지만, 요청을 받는 곳부터 작성자를 연결하는 곳까지 따라가면 확인해야 할 조건이 여러 군데에 나뉘어 있었다.


이번에는 `6c9cd15` 커밋에서 입력값 검사와 수정 권한을 중심으로 정리했다. 특히 로그인 여부와 특정 글을 수정할 권한은 따로 확인해야 한다는 점이 남았다. 당시 서버 코드에서 확인한 처리 흐름을 정리했다.


## 컨트롤러에서 화면과 저장 작업이 갈라지는 지점


[boardController](https://github.com/NAMUORI00/spring-community-board/blob/6c9cd155ea7d31e0b5a3497836db4cbd5cd86182/src/main/java/com/example/crud/controller/boardController.java)의 GET /form은 새 Board를 만들거나 ID로 기존 글을 읽어 폼에 넣는다.


같은 폼의 POST /form은 입력값을 Board에 연결하고 검사를 수행한다. 같은 URL이라도 조회 요청과 저장 요청의 역할이 다르다.


제목은 엔티티의 NotNull, Size 조건으로 검사하고, 본문은 BoardValidator에서 빈 값인지 확인한다. 오류가 있으면 폼을 다시 반환한다. 통과한 경우 로그인 이름을 BoardService에 넘기고, 서비스는 사용자 엔티티를 찾아 작성자로 설정한 뒤 저장소의 save를 호출한다.

그림 1. 폼 입력 검증과 작성자 연결을 거쳐 저장한 뒤 목록으로 이동하는 경로. 요청 접근에 대한 인증 검사는 앞단의 보안 설정에서 수행된다. 출처: boardController, BoardValidator, BoardService를 바탕으로 직접 구성.


컨트롤러는 웹 요청과 화면 전환을, 서비스는 사용자와 글을 연결하는 작업을 맡는다. JPA 저장소는 엔티티를 데이터베이스 작업으로 이어 준다.


[Spring Data JPA의 저장 설명](https://docs.spring.io/spring-data/jpa/reference/jpa/entity-persistence.html)에서 save는 엔티티 상태에 따라 persist나 merge를 사용한다. 이 동작을 기준으로 저장 호출에 전달되는 ID와 상태를 함께 읽었다. save 호출만으로 새 행 추가인지 기존 엔티티 반영인지 정해지지는 않는다.


## 로그인과 작성자 권한 검사


[WebSecurityConfig](https://github.com/NAMUORI00/spring-community-board/blob/6c9cd155ea7d31e0b5a3497836db4cbd5cd86182/src/main/java/com/example/crud/Config/WebSecurityConfig.java)는 첫 화면과 회원가입 등을 허용하고 나머지 요청에는 인증을 요구한다.


로그인에는 데이터베이스의 사용자, 권한 조회와 BCrypt 비밀번호 인코더를 연결한다. [Spring Security의 요청 인가 설명](https://docs.spring.io/spring-security/reference/servlet/authorization/authorize-http-requests.html)에서 말하는 경로별 규칙을 적용한 구성으로 읽힌다.


하지만 authenticated는 요청자가 로그인한 사용자라는 조건이다. 특정 글의 작성자 여부는 로그인 확인에 더해 별도의 소유자 비교 규칙으로 검사해야 한다. 현재 삭제 경로는 전달된 ID로 deleteById를 호출하며, 수정 폼 조회와 저장 경로에서도 기존 작성자와 현재 사용자를 비교하는 코드를 찾지 못했다.


더구나 `BoardService.save`는 전달받은 글의 작성자를 현재 로그인 사용자로 설정한다.


새 글에서는 현재 사용자를 작성자로 지정하는 흐름이다. 기존 글에서는 원래 작성자의 보존과 수정 권한을 별도로 확인할 부분이 남는다. 이번에는 다른 사용자의 글을 실제로 변경하지 않고, 서버 코드에서 작성자 비교 단계를 찾아본 범위까지 정리했다.

그림 2. 현재 확인된 로그인 조건과 추가로 필요한 게시글별 권한 판단을 구분했다. 점선은 보완을 검토할 단계다. 출처: 보안 설정과 변경 컨트롤러를 바탕으로 직접 구성.


## 화면용 데이터와 엔티티를 나누어 읽기


목록은 제목이나 본문에 검색어가 포함된 글을 페이지로 조회한다. 기본 페이지 크기는 10이며 ID 내림차순을 사용한다. 반환된 Board에서 제목, 본문, 작성자 닉네임, 시각을 꺼내 BoardDto를 만들고 화면 모델에 넣는다.


DTO는 여기서 화면에 전달할 항목을 모은 객체다. 엔티티에는 사용자나 댓글 관계가 들어 있지만 목록에는 필요한 필드만 담을 수 있다.


실제로 [RestApiController](https://github.com/NAMUORI00/spring-community-board/blob/6c9cd155ea7d31e0b5a3497836db4cbd5cd86182/src/main/java/com/example/crud/controller/RestApiController.java)에는 엔티티를 직접 반환하는 경로와 DTO로 바꾸는 경로가 함께 있어 두 방식을 비교할 수 있었다.


다만 게시글 작성자는 지연 로딩 관계이고 목록 변환에서 닉네임에 접근한다. 글 수가 늘 때 추가 조회가 얼마나 발생하는지는 SQL 기록으로 확인할 문제다. 코드에 지연 로딩이 있다는 이유만으로 조회 효율이 확보됐다고 보지는 않았다.


## 화면, API 경로의 입력 검사 비교


폼의 POST에는 Valid와 본문 검사가 있지만 REST 수정 경로에는 같은 검증 호출이 없다. API 수정은 기존 글이 있으면 제목, 본문을 바꾸고, 없으면 요청 ID를 넣어 저장하는 별도 흐름이다. 폼 검증과 직접 API 요청의 검증 조건을 각각 확인해야 했다.


생성, 수정 시각도 [Board 엔티티](https://github.com/NAMUORI00/spring-community-board/blob/6c9cd155ea7d31e0b5a3497836db4cbd5cd86182/src/main/java/com/example/crud/model/Board.java)의 PrePersist, PreUpdate에서 설정한다.


폼에는 created_at을 숨겨 전달하는 필드도 남아 있었다. 저장 시각을 서버에서 관리하는 구성에서는 클라이언트 입력과 서버가 확정할 값을 나누어 볼 지점이다.


계층별 역할을 따라간 뒤에는 입력 경로 사이의 규칙 차이가 남았다. 폼과 API에서 같은 저장 규칙을 공유하는 위치가 다음 검토 대상이다. README에 기록된 Spring Boot, JPA 학습 목적에서 공통 검증과 권한 처리로 이어지는 부분으로 읽었다.


## 사용자별 수정 권한의 추가 검증


후속 확인에는 작성자 A와 다른 사용자 B의 수정, 삭제 요청을 정리했다. 로그인 여부와 글별 권한의 기대 결과를 나누고, 잘못된 제목을 폼과 API로 보냈을 때 적용되는 규칙을 비교하는 예제다.


CRUD 호출의 연결뿐 아니라 입력 경로별 검사와 작성자 처리까지 살펴볼 수 있었다. 이후에는 폼과 API가 같은 검증 규칙을 공유하도록 바꾸는 방법을 더 살펴보려 한다.


## 작업을 정리하며


CRUD를 연결한 뒤에는 같은 규칙이 모든 요청 경로에 적용되는지가 중요해진다. 로그인 확인, 작성자 비교, 입력 검증을 분리해 보면 공통 서비스 계층에 모을 규칙이 드러난다. 다음 수정에서는 폼과 API에 같은 입력을 보내 결과를 비교하는 것부터 진행하려 한다.
