2023년에 Spring Boot와 JPA로 웹 서버와 데이터베이스를 연결해 만들었던 게시판 코드를 다시 열어 봤다. 게시판에서 글을 쓰고 읽고 고치고 지우는 기본 기능은 흔히 CRUD라는 이름으로 묶어 부른다. 하지만 요청을 받는 컨트롤러부터 작성자를 연결하는 서비스와 저장소까지 따라가 보면 확인해야 할 조건이 여러 곳에 흩어져 있다.


이 게시판은 웹 화면의 입력 칸을 거치는 화면 폼과 데이터만 직접 주고받는 **REST API**라는 두 경로로 같은 게시글을 다룬다. 코드를 다시 읽어 보니 두 경로의 입력값 검사가 서로 달랐고, 로그인 여부만 확인하는 설정과 게시글 작성자 권한도 나뉘어 있었다. 당시 작성한 `6c9cd15` 커밋을 기준으로 서버의 요청 처리 흐름과 비어 있던 검사 단계를 확인했다.


## 화면 폼의 게시글 조회와 저장


먼저 웹 화면에서 게시글을 읽고 저장하는 흐름을 [boardController](https://github.com/NAMUORI00/spring-community-board/blob/6c9cd155ea7d31e0b5a3497836db4cbd5cd86182/src/main/java/com/example/crud/controller/boardController.java)부터 따라갔다. 이 컨트롤러에서는 같은 `/form` 경로라도 데이터를 읽는 `GET`과 값을 보내는 `POST`처럼 HTTP 메서드에 따라 역할이 갈린다. `GET /form`은 빈 `Board` 객체를 새로 만들거나 전달받은 ID로 기존 글을 읽어 입력 폼 화면에 채운다. 반대로 `POST /form`은 사용자가 입력한 제목과 본문을 `Board` 객체에 묶고 유효성 검사를 실행한다.


화면 폼으로 들어온 입력값 검사는 제목과 본문을 확인하는 두 곳에서 나뉘어 돌아간다. 제목은 데이터베이스 표에 대응하는 객체인 **엔티티**(entity) 필드의 `@NotNull`과 `@Size` 조건으로 확인한다. 본문은 `BoardValidator`에서 빈 값인지 검사하며, 어느 한쪽이라도 오류가 있으면 저장하지 않고 입력 폼 화면을 다시 돌려준다. 검사를 통과하면 컨트롤러는 현재 로그인한 사용자 이름을 `BoardService`에 넘긴다. 서비스는 데이터베이스에서 사용자 엔티티를 찾아 게시글의 작성자로 지정한 뒤 저장소의 `save`를 호출한다.

그림 1. POST /form 요청에서 입력 검증과 작성자 연결을 거쳐 게시글을 저장하는 흐름. 출처: boardController, BoardValidator, BoardService를 바탕으로 직접 구성.


이 흐름에서 컨트롤러는 웹 요청 처리와 화면 전환을 맡고, 서비스는 사용자와 게시글 엔티티를 연결한다. 이어서 JPA 저장소가 넘겨받은 엔티티를 실제 데이터베이스 작업으로 이어 준다. 다만 [Spring Data JPA의 저장 설명](https://docs.spring.io/spring-data/jpa/reference/jpa/entity-persistence.html)에서 다루듯 `save` 메서드는 엔티티 상태에 따라 동작이 달라진다. 새 엔티티를 추가할 때는 `persist`를 실행하고, 기존 엔티티를 병합할 때는 `merge`를 선택한다. `save` 호출만 봐서는 새 행을 추가하는지 기존 글을 고치는지 바로 알 수 없으므로, 전달되는 엔티티의 ID와 상태를 함께 따라가야 했다.


## 로그인 인증과 게시글 작성자 권한


게시글 저장 흐름에서 로그인한 사용자를 작성자로 연결했다면, 누가 글 변경 요청을 보낼 수 있는지도 확인해야 한다. 서버의 요청 경로별 접근 제어는 [WebSecurityConfig](https://github.com/NAMUORI00/spring-community-board/blob/6c9cd155ea7d31e0b5a3497836db4cbd5cd86182/src/main/java/com/example/crud/Config/WebSecurityConfig.java)에서 한데 모아 설정한다. 첫 화면과 회원가입 경로 등은 누구나 접근할 수 있게 열어 두고, 나머지 요청에는 로그인을 요구한다. 로그인 처리에는 데이터베이스의 사용자 및 권한 조회와 `BCrypt` 비밀번호 인코더를 연결했다. [Spring Security의 요청 인가 설명](https://docs.spring.io/spring-security/reference/servlet/authorization/authorize-http-requests.html)에서 안내하는 경로별 접근 규칙을 그대로 적용했다.


문제는 보안 설정의 `authenticated` 조건이 요청자가 로그인한 사용자라는 **인증**(authentication)만 보장한다는 점이다. 로그인한 사용자가 특정 게시글의 작성자인지 확인하려면 글 소유자를 비교하는 권한 규칙이 따로 있어야 한다. 당시 코드의 삭제 경로는 전달받은 ID로 곧바로 `deleteById`를 호출해 글을 지우고 있었다. 수정 폼을 여는 경로와 저장 경로에서도 기존 글의 작성자와 현재 로그인한 사용자를 비교하는 코드가 없었다.


여기에 더해 `BoardService.save`는 전달받은 게시글의 작성자를 무조건 현재 로그인한 사용자로 덮어쓴다. 새 글을 쓸 때는 자연스러운 동작이지만, 기존 글을 수정할 때는 원래 작성자가 바뀔 수 있어 수정 권한 확인과 작성자 보존을 따로 챙겨야 한다. 이번 확인에서는 다른 사용자의 글을 실제로 변경해 보지 않고, 서버 코드에 작성자 비교 단계가 빠져 있는 지점까지 파악했다.

## 목록 조회의 엔티티와 DTO 분리


게시글을 저장하고 변경하는 경로에 이어, 저장된 글 목록을 읽어 화면으로 전달하는 흐름을 따라갔다. 게시글 목록은 제목이나 본문에 검색어가 들어 있는 글을 페이지 단위로 조회하며, 기본 페이지 크기는 10개이고 ID 내림차순으로 정렬한다. 서버는 조회된 `Board` 엔티티에서 제목, 본문, 작성자 닉네임, 작성 시각만 꺼내 `BoardDto` 객체를 만들고 화면 모델에 담아 전달한다.


`Board` 엔티티에는 사용자 정보나 댓글 목록 같은 연관 관계가 함께 들어 있다. 그래서 계층 사이에서 화면이나 응답에 필요한 데이터만 추려 옮기는 **DTO**(Data Transfer Object)로 변환해 전달하는 편이 다루기 쉽다. 실제로 [RestApiController](https://github.com/NAMUORI00/spring-community-board/blob/6c9cd155ea7d31e0b5a3497836db4cbd5cd86182/src/main/java/com/example/crud/controller/RestApiController.java)에는 엔티티를 그대로 반환하는 경로와 DTO로 변환해 반환하는 경로가 함께 남아 있어 두 방식의 차이를 코드에서 바로 비교할 수 있었다.


![Board 엔티티의 필드와 지연 로딩된 User 관계에서 댓글 목록을 제외하고 제목, 본문, 시각, 작성자 닉네임만 추려 BoardDto와 목록 화면 모델로 전달하는 구조도](/images/notion/tech-13-01/image-3.png)


그림 3. 목록 조회 시 Board 엔티티에서 필요한 항목만 추려 BoardDto로 변환하는 구조와 지연 로딩 관계.


목록을 DTO로 바꿀 때는 게시글에서 작성자 정보를 참조하는 방식도 함께 봐야 한다. 게시글과 작성자(`User`)는 연관된 데이터를 실제로 읽을 때 조회하는 **지연 로딩**(lazy loading) 관계로 묶여 있다. 그런데 목록을 `BoardDto`로 바꾸는 과정에서 각 글의 작성자 닉네임에 차례로 접근한다. 게시글 수가 늘어날 때 작성자 조회를 위한 추가 SQL이 얼마나 실행되는지는 실제 쿼리 로그로 확인해야 할 문제다. 코드에 지연 로딩 설정이 적혀 있다는 이유만으로 조회 효율이 확보됐다고 단정할 수는 없었다.


## 화면 폼과 REST API의 입력 검사 비교


계층별 역할을 따라가다 보니 글을 저장하고 고치는 규칙도 화면 폼 경로와 REST API 경로에서 서로 달랐다. 화면 폼의 `POST /form` 경로에는 `@Valid`와 `BoardValidator` 본문 검사가 모두 들어 있다. 반면 `RestApiController`의 게시글 수정 경로에는 같은 입력 검증 호출이 빠져 있었다. API 수정 경로는 기존 글이 있으면 제목과 본문을 바로 바꾸고, 없으면 요청에 담긴 ID를 넣어 저장하는 별도 흐름으로 작성되어 있었다.


생성 시각과 수정 시각을 다루는 방식도 서버 엔티티와 화면 폼에 섞여 있었다. [Board 엔티티](https://github.com/NAMUORI00/spring-community-board/blob/6c9cd155ea7d31e0b5a3497836db4cbd5cd86182/src/main/java/com/example/crud/model/Board.java)는 데이터베이스에 처음 저장하기 직전과 수정하기 직전에 실행되는 `@PrePersist`, `@PreUpdate` 메서드로 시각을 기록한다. 그런데 화면 폼에는 생성 시각인 `created_at` 값을 숨겨서 서버로 다시 보내는 입력 필드가 남아 있었다. 저장 시각을 서버에서 관리한다면 클라이언트가 보낸 값과 서버가 확정할 값을 분리해야 한다.


![화면 폼(POST /form)은 @Valid와 본문 검사 및 로그인 사용자 연결을 거치는 반면, API 수정 요청은 입력 검증 없이 제목과 본문을 직접 반영해 Board 엔티티를 저장하는 비교도](/images/notion/tech-13-01/image-4.png)

## 결론


이번 코드 검토에서는 게시글 CRUD 기능이 화면과 데이터베이스에 연결된 상태를 넘어, 어떤 경로로 요청이 들어오든 같은 검증 규칙이 적용되는지 확인했다. 코드를 따라가 본 결과 화면 폼과 REST API의 입력값 검사가 서로 달랐고, 로그인 확인과 별개로 게시글 작성자를 비교하는 단계가 빠져 있었다. 로그인 확인, 작성자 일치 비교, 입력값 검사를 분리해 놓고 보면 컨트롤러가 아니라 공통 서비스 계층에서 묶어 처리해야 할 규칙이 뚜렷해진다.


다만 이번에는 코드 흐름만 읽었을 뿐, 다른 사용자의 글을 실제로 변경해 보거나 지연 로딩에 따른 추가 SQL 실행 횟수를 쿼리 로그로 확인하지는 않았다. 실제 동작을 검증하기 위해 작성자 A가 쓴 글에 다른 로그인 사용자 B가 수정이나 삭제 요청을 보냈을 때의 기대 결과를 먼저 정의했다. 조건에 맞지 않는 제목을 화면 폼과 API로 각각 보냈을 때 어떤 규칙이 작동하는지 비교하는 테스트 시나리오도 함께 나눴다. 인증 처리와 요청 경로 분리는 [Spring과 FastAPI를 연결한 음원 분리 서비스](https://blog.namuori.net/posts/tech-09-01/)에서도 이어서 다뤘다. 다음 작업에서는 먼저 두 경로에 같은 입력을 보내 결과를 비교하고, 화면 폼과 API가 같은 검증 규칙을 공유하도록 고치는 방법을 다룰 생각이다.
