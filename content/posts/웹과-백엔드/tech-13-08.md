`webdev2022` 저장소에는 수업 내용과 짧은 코드 예제를 받아 적은 노트가 남아 있다. `b0c0052` 커밋을 보면 Node.js와 함께 운영체제, 보안, 영상처리, 코딩 테스트 노트가 Markdown 파일로 들어 있다. 완성된 웹 앱이 아니라 수업 내용을 받아 적은 기록이다 보니, 문서에 적힌 설명과 코드의 실제 실행 흐름이 어긋나는 곳이 있었다.


이 글에서는 웹 개발 노트에 담긴 작은 예제들을 실제 코드 및 공식 문서와 대조해 실행 흐름을 바로잡는다. 함수가 호출되고 끝나는 순서부터 서버가 요청을 받아 응답으로 내보내기까지의 처리 단계를 차례로 확인했다. 앞 글에서 다룬 호출 경계를 작은 코드 조각에서 하나씩 확인하는 과정이기도 하다.


## 함수 호출 스택과 반환 순서


가장 먼저 [9월 5일 노트](https://github.com/NAMUORI00/webdev2022/blob/b0c0052e4fe69b827191e3bfcf746f70ca3a80f5/node.js/2022-09-05.md)에 적힌 예제로 함수가 호출되고 원래 자리로 돌아오는 순서를 확인했다. 노트의 코드는 `first`가 `second`를 부르고, `second`가 `third`를 부른 뒤 각자 값을 출력하도록 되어 있다. 프로그램은 이처럼 함수가 호출될 때마다 현재 실행 중인 위치와 끝나고 돌아갈 자리를 **호출 스택**(call stack)에 순서대로 쌓아 둔다.


그런데 노트의 코드에는 마지막 `third` 함수 안에서 다시 `first`를 호출하는 줄이 들어 있었다. 이대로 실행하면 함수가 끝나고 이전 위치로 돌아오는 대신, `first`부터 `third`까지의 호출이 끝없이 반복해서 쌓인다. 노트 설명에는 세 번째 함수부터 차례로 출력을 마친다고 적혀 있었지만, 코드가 첫 함수를 다시 부르는 재귀 호출 형태라 설명대로 동작하지 않았다.


함수가 끝난 뒤 되돌아오는 순서를 확인하려면 `third`에서 다시 `first`를 부르는 부분을 빼야 한다. 호출과 반환의 차이를 분명하게 비교하려고 다음과 같이 작은 예제를 따로 구성했다.


```javascript
function first() { second(); console.log('A'); }
function second() { third(); console.log('B'); }
function third() { console.log('C'); }
first();
```


이 코드를 실행하면 출력은 `C`, `B`, `A` 순서로 나와 함수를 부른 순서와 반대가 된다. `first`는 `second`가 끝나야 `console.log('A')`로 넘어가고, `second`도 `third`가 끝나기를 기다린다. 함수를 호출할 때는 `first` → `second` → `third` 순서로 실행 위치가 쌓인다. 반면 호출이 끝난 뒤 다음 문장으로 돌아오는 순서는 `third` → `second` → `first`여서 `C`가 가장 먼저 출력된다.


![first, second, third 함수가 순서대로 호출된 뒤 C, B, A 순서로 출력하며 반환되는 흐름도](/images/notion/tech-13-08/image-1.png)


그림 1. 재귀 호출을 제거한 설명용 예제에서 함수 호출(위)과 반환 출력(아래)이 진행되는 순서로, 실행 순서의 차이를 확인하기 위해 직접 구성한 도식이다.


물론 이 예제에서 확인한 범위는 앞 작업이 끝날 때까지 순서대로 기다리는 동기 함수의 호출과 반환뿐이다. 타이머나 파일 입출력(I/O)처럼 완료 시점이 따로 정해지는 비동기 작업과 콜백 함수는 이벤트 루프 규칙을 따로 보아야 한다. [Node.js 파일 작업 문서](https://nodejs.org/api/fs.html#ordering-of-callback-and-promise-based-operations)에서도 비동기 작업 사이의 실행 순서를 별도로 다룬다. 먼저 끝나야 하는 비동기 작업이 있다면 코드를 아랫줄에 적는 것만으로는 부족하고, 앞 작업이 완료된 시점에 다음 작업을 이어 주어야 한다.


## 모듈 문법과 실행 환경


함수 하나의 실행 순서를 확인한 뒤에는, 변수와 함수를 여러 파일로 나누어 불러 쓰는 **모듈**(module) 예제를 점검했다. [9월 9일 노트](https://github.com/NAMUORI00/webdev2022/blob/b0c0052e4fe69b827191e3bfcf746f70ca3a80f5/node.js/2022-09-09.md)에는 `module.exports`와 `require`를 사용해 변수와 함수를 여러 파일로 나누는 예제가 있다. 이 코드는 서버 쪽 JavaScript 실행 환경인 [Node.js의 CommonJS 모듈](https://nodejs.org/api/modules.html) 문법을 따른다. 같은 JavaScript라도 표준 **ES 모듈**(ES modules)의 `import`, `export`와는 문법과 동작 조건이 달라 두 방식을 섞지 않도록 구분했다. 브라우저에서 모듈을 쓰는 방법은 [JavaScript 모듈 문서](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Modules)에 따로 정리되어 있다. HTML에서 `type="module"` 속성을 지정하고 `import`와 `export` 문을 사용한다.


![CommonJS 모듈(module.exports, require)과 ES 모듈(export, import)의 문법 및 실행 환경을 나란히 비교한 도식](/images/notion/tech-13-08/image-2.png)


그림 2. CommonJS 모듈과 ES 모듈의 문법 및 기본 실행 환경 비교 개념도.


노트에 적힌 `require('./func')` 파일을 브라우저의 일반 `script` 태그로 불러오면 Node.js와 같은 모듈 환경이 자동으로 만들어지지 않아 오류가 난다. 반대로 Node.js 환경이라도 파일 확장자나 패키지 설정에 따라 모듈을 해석하는 방식이 달라질 수 있다. 노트에 적힌 코드 조각을 다른 곳으로 옮겨 실행할 때는 문법뿐 아니라 실행 위치와 모듈 형식을 함께 확인해야 한다. 따라서 문법만 적어 두기보다 그 예제가 기대하는 실행 조건을 한 줄이라도 함께 남기는 편이 나중에 코드를 다시 실행할 때 도움이 된다.


## Express 미들웨어의 등록 방식과 next 흐름


모듈의 실행 환경을 구분한 뒤에는, 서버 쪽 요청 처리를 다룬 [9월 14일 노트](https://github.com/NAMUORI00/webdev2022/blob/b0c0052e4fe69b827191e3bfcf746f70ca3a80f5/node.js/2022-09-14.md)의 Express 예제를 확인했다. 이 노트는 Node.js 웹 서버 도구인 Express로 요청을 받아 HTML 파일을 응답하는 흐름을 담고 있다. Express 서버는 요청이 들어오면 중간 처리 함수인 **미들웨어**(middleware)를 거치며 요청 객체와 응답 객체를 읽거나 바꾼다. [Express의 미들웨어 안내](https://expressjs.com/en/guide/using-middleware/)에서도 각 미들웨어가 직접 응답을 끝내는 선택과, `next`를 호출해 다음 미들웨어로 제어권을 넘기는 선택을 나누어 설명한다.


그런데 노트의 예제 중에는 `sendFile`로 파일을 보낸 뒤 곧바로 `next`를 호출하고, 다음 미들웨어에서 오류를 던지는 코드가 있었다. 한 요청에서 파일 전송과 오류 응답 경로가 함께 진행될 수 있어, 정상 응답보다는 오류가 어떻게 전달되는지 확인하는 예제로 읽었다.


![HTTP 요청이 요청 기록과 본문 파싱을 거쳐 정상 응답과 오류 처리 미들웨어 경로로 나뉘는 흐름도](/images/notion/tech-13-08/image-3.png)


그림 3. 정상 응답과 오류 전달을 갈라서 이해하기 위한 요청 흐름 개념도. 출처: Express 공식 안내를 참고해 직접 구성.


같은 노트에서 요청으로 들어온 문자열 데이터를 객체로 해석해 바꾸는 본문 파싱 예제인 `app.use(express.json)`도 다시 확인해야 할 부분이었다. [Express API 문서](https://expressjs.com/en/5x/api.html#express.json)와 대조해 보면 `express.json`은 미들웨어 자체가 아니라 본문을 해석하는 파서(parser)를 만드는 함수다. 따라서 일반적인 등록 형태는 `express.json()`을 호출한 결과를 `app.use`에 넘기는 방식이다.


## 정적 파일 제공과 학습 노트의 재현 조건


미들웨어가 요청을 처리해 파일을 응답한 뒤에는, 서버의 정적 파일 제공과 브라우저의 화면 처리 단계를 구분해야 한다. Express의 `sendFile`이나 `express.static`이 맡는 일은 서버에 있는 파일을 그대로 HTTP 응답으로 내려보내는 것까지다. 응답으로 받은 HTML의 구조 해석과 CSS의 표현, 브라우저 JavaScript의 이벤트 처리는 그다음 브라우저 층에서 이루어진다.


![Express 서버의 sendFile, express.static 응답과 브라우저의 HTML 구조, CSS 표현, JavaScript 이벤트 실행 계층을 구분한 도식](/images/notion/tech-13-08/image-4.png)


그림 4. 서버의 정적 파일 응답 역할과 브라우저의 화면 해석 및 이벤트 처리 계층을 구분한 개념도.


파일을 내려보내는 `sendFile` 예제에서도 대상 HTML 파일이 아예 없는 경우와 경로 지정이 잘못된 경우를 나누어 확인할 수 있다. `webdev2022` 저장소는 바로 배포할 수 있는 전체 파일이 갖춰진 형태가 아니라 Markdown 안에 설명과 코드 조각만 남아 있는 학습 기록이다. 이처럼 짧은 코드 조각을 나중에 다시 실행해 보려면 실행 위치와 필요한 파일, 입력 요청과 예상 출력, 실패 조건을 함께 적어 두어야 한다.


## 결론


원본 노트에는 당시 교재와 필기 흔적이 남아 있어, 설명과 실제 실행 흐름이 어긋난 곳을 공식 문서와 대조해 바로잡았다. 함수의 호출 스택과 반환 순서, 모듈 문법과 실행 환경, Express 미들웨어 흐름, 정적 파일 응답과 브라우저 처리 계층을 구분했다. 당시 기록과 이번에 대조한 해석을 구분하고 차이를 설명하기 위해 짧은 예제와 도식도 새로 구성했다.


다만 호출 스택 예제는 동기 함수 범위에서만 확인했고, 노트의 코드 조각들도 아직 Markdown 문서 안에 남아 있는 상태다. 다음에는 Markdown 안의 호출 스택과 미들웨어 예제를 독립된 파일로 분리해 실행하고, 정상 출력과 오류 출력을 한 쌍으로 기록할 계획이다.
