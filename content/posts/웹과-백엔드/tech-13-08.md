## 함수 호출 스택과 이벤트 루프를 나누어 읽기


[9월 5일 노트](https://github.com/NAMUORI00/webdev2022/blob/b0c0052e4fe69b827191e3bfcf746f70ca3a80f5/node.js/2022-09-05.md)에는 함수 호출 스택 예제가 있다.


first가 second를, second가 third를 호출한 뒤 각자 값을 출력한다. 그런데 third가 다시 first를 호출한다. 이대로라면 함수를 끝내고 되돌아오는 대신 호출이 반복해서 쌓이는 경로가 된다.


따라서 노트의 설명처럼 단순히 세 번째 함수부터 출력을 마치는 예제로 읽기는 어려웠다. 반환 순서를 보려면 third에서 다시 first를 부르는 부분이 없어야 한다. 다음은 그 차이를 설명하려고 따로 만든 작은 예제다.


```javascript
function first() { second(); console.log('A'); }
function second() { third(); console.log('B'); }
function third() { console.log('C'); }
first();
```


예상 출력은 C, B, A 순서다. first는 실행 중 second의 반환을 기다리고, second도 third의 반환을 기다린다. 함수를 부르는 순서와 호출 뒤의 문장으로 돌아오는 순서를 구분하면 설명이 더 정확해진다.


![readable-13-08-01.png](/images/notion/tech-13-08/image-1.png)


그림 1. 재귀 호출을 제거한 설명용 예제에서 호출과 반환이 진행되는 순서. 실행 순서의 차이를 확인하기 위해 직접 구성한 도식이다.


이 예제에서 확인하는 범위는 동기 함수의 호출과 반환이다. 타이머나 파일 I/O 콜백의 실행 시점은 비동기 작업의 규칙을 추가로 읽을 부분이다.


[Node.js 파일 작업 문서](https://nodejs.org/api/fs.html#ordering-of-callback-and-promise-based-operations)도 비동기 작업 사이의 순서를 별도로 다룬다. 먼저 끝나야 하는 작업이 있으면 그 완료를 연결해 다음 작업을 시작해야 한다.


## 모듈 문법에서 실행 환경을 함께 적기


[9월 9일 노트](https://github.com/NAMUORI00/webdev2022/blob/b0c0052e4fe69b827191e3bfcf746f70ca3a80f5/node.js/2022-09-09.md)는 module.exports와 require로 변수와 함수를 나누는 예제를 담고 있다.


이 코드는 [Node.js의 CommonJS 모듈](https://nodejs.org/api/modules.html) 문법이다. require를 사용한 예제를 곧바로 ES 모듈의 import와 같은 문법이라고 설명하지 않도록 구분했다.


브라우저에서도 모듈을 사용할 수 있다. [JavaScript 모듈 문서](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Modules)는 type="module"과 import, export를 사용하는 방법을 설명한다. 노트의 예제를 옮겨 실행할 때는 실행 위치와 모듈 형식을 함께 확인할 필요가 있다.


가령 require('./func')가 있는 파일을 일반 브라우저 script로 열면 Node.js와 같은 환경이 자동으로 생기지 않는다. 반대로 Node.js에서도 파일 확장자와 패키지 설정에 따라 모듈 해석이 달라질 수 있다. 문법을 외우는 것보다 예제가 기대하는 실행 조건을 한 줄로 남기는 쪽이 재사용에 도움이 된다.


## Express 미들웨어의 next 처리


[9월 14일 노트](https://github.com/NAMUORI00/webdev2022/blob/b0c0052e4fe69b827191e3bfcf746f70ca3a80f5/node.js/2022-09-14.md)는 Express로 요청을 받고 HTML 파일을 응답하는 흐름을 다룬다.


미들웨어는 요청과 응답 객체를 읽거나 바꾸고, 응답을 끝내거나 다음 처리로 넘기는 함수다. [Express의 미들웨어 안내](https://expressjs.com/en/guide/using-middleware/)에서도 이 두 선택을 나누어 설명한다.


노트에는 sendFile 뒤 next를 호출하고 다음 처리에서 오류를 던지는 예제가 있다. 파일 전송과 오류 응답 경로가 함께 진행될 수 있어, 정상 응답 구성보다는 오류 전달을 살펴보는 예제로 읽었다.


![13-08-02.png](/images/notion/tech-13-08/image-2.png)


그림 2. 정상 응답과 오류 전달을 갈라서 이해하기 위한 요청 흐름. 미들웨어의 책임을 정리한 개념 도식이다. 출처: Express 공식 안내를 참고해 직접 구성.


본문 파싱 예제의 app.use(express.json)도 다시 확인할 부분이다. express.json은 파서를 만드는 함수이므로 일반적인 등록 형태는 express.json()을 호출한 결과를 app.use에 넘기는 방식이다.


[Express API 문서](https://expressjs.com/en/5x/api.html#express.json)와 대조하면 함수 자체와 그 함수가 반환한 미들웨어를 구분할 수 있다.


## 정적 파일 제공과 브라우저 실행


sendFile이나 express.static은 서버 파일을 HTTP 응답으로 제공하는 역할이다. 받은 HTML의 구조, CSS의 표현, 브라우저 JavaScript의 이벤트 처리는 그다음 층이다. 이 저장소에서는 관련 설명과 코드 조각이 Markdown에 남아 있으므로, 배포 가능한 앱의 모든 파일이 갖춰졌다고 주장하지 않았다.


예제를 다시 실행하기 위한 정보는 실행 위치, 필요한 파일, 입력 요청, 예상 출력, 실패 조건으로 정리했다. sendFile에서는 HTML 파일 부재와 경로 오류를 나누어 확인할 수 있다.
