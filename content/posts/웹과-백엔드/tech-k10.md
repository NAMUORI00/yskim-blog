## 재고 한 개를 두 요청이 함께 읽었다


동시 요청에서 읽기와 변경 사이의 상태 차이를 정리했다. 재고가 하나일 때 두 주문이 모두 재고 있음을 읽는 예제를 사용했다. 검사 시점의 값이 변경 시점에도 유효한지 확인하는 방법으로 버전 검사와 원자적 갱신을 나누어 살펴봤다.


아래에서는 두 요청이 `재고 > 0`을 먼저 확인하고, 나중에 조건 없이 현재 재고에서 1을 빼는 구현을 가정했다. A가 차감한 뒤 B가 다시 차감하면 재고가 -1까지 내려갈 수 있다.


두 요청이 미리 계산한 값 0을 덮어쓰면 재고는 0으로 남아도 주문 두 건이 승인될 수 있다. 조건 없이 차감하는 경우와 실패 모습이 달라, 예제의 갱신문도 함께 명시했다.


| 순서 | 요청 A              | 요청 B              | 저장된 재고 |
| -- | ----------------- | ----------------- | ------ |
| 1  | 1개를 읽고 주문 가능 판단   | —                 | 1      |
| 2  | —                 | 1개를 읽고 주문 가능 판단   | 1      |
| 3  | 조건 없이 현재 값에서 1 차감 | —                 | 0      |
| 4  | —                 | 조건 없이 현재 값에서 1 차감 | -1     |


표는 실제 실행 기록이 아닌 가상 순서다. 읽기에서 확인한 조건을 변경 시점까지 유지하지 못하는 구간을 드러내기 위해 구성했다.


## 비슷해 보이는 문제의 이름을 분리하기


검사와 사용 사이에 자원이 바뀌는 경쟁은 보안 문맥에서 TOCTOU라고 부른다. [MITRE CWE-367](https://cwe.mitre.org/data/definitions/367.html)은 파일 경로처럼 검사한 대상과 실제 사용하는 대상이 달라질 수 있는 문제를 다룬다. 확인 후 경로를 다시 여는 사이에 대상이 바뀔 수 있어, 검사와 사용을 같은 대상으로 연결해야 한다.


오래된 읽기라는 말은 조금 더 넓게 쓰인다. 복제 지연이나 캐시 때문에 이미 지난 값을 읽을 수도 있고, 처음 읽은 값은 최신이었지만 실행 전에 바뀔 수도 있다. TOCTOU와 오래된 읽기를 같은 뜻으로 합치기보다, 이 예제에서는 **읽기 이후의 상태 변화**에 초점을 두었다.

그림 1. 읽기 당시의 판단과 실행 당시의 상태가 갈라지는 설명용 예제. 대기 구간에 다른 요청의 변경이 들어간다.


## 조건을 변경과 같은 연산에 두기


재고 한 행의 조건이라면 읽기와 차감을 떨어뜨리지 않는 방법을 먼저 검토할 수 있었다. PostgreSQL을 예로 들면 다음처럼 대상과 조건을 갱신문 안에 함께 적는다.


```sql
UPDATE inventory
SET count = count - 1
WHERE sku = :sku AND count > 0
RETURNING count;
```


`:sku`는 바인딩할 상품 식별자를 뜻하는 예시 표기다. 반환된 행이 있으면 조건을 만족해 변경한 것이고, 없으면 상품 부재나 재고 부족 등을 구분해 처리해야 한다. Read Committed에서 경합한 행이 바뀌면 PostgreSQL은 갱신된 행에 조건을 다시 평가한다.


이 동작은 [트랜잭션 격리 문서](https://www.postgresql.org/docs/current/transaction-iso.html)에서 확인할 수 있었다.


이 한 문장이 주문 전체를 완성하지는 않는다. 주문 기록과 재고 차감이 함께 성공해야 한다면 둘을 트랜잭션으로 묶는 조건도 필요하다. 결제처럼 외부 시스템이 끼면 데이터베이스 트랜잭션만으로 전체 작업을 되돌릴 수도 없다. 단일 행에서 지킬 조건과 여러 시스템에 걸친 업무 조건을 따로 적는 편이 구현 범위를 정하는 데 도움이 됐다.


## 버전을 비교해도 다시 틈이 생길 수 있었다


사용자 승인처럼 대기가 긴 작업은 읽는 동안 잠금을 계속 붙잡아 두기 어렵다. 이때 읽은 버전을 기록해 두고 변경 시 다시 비교하는 방법을 생각할 수 있다. 다만 버전을 먼저 조회해 비교한 다음 별도 갱신을 하면 처음 문제와 같은 틈이 다시 생긴다.


```sql
UPDATE inventory
SET count = count - 1, version = version + 1
WHERE sku = :sku AND version = :read_version AND count > 0
RETURNING count, version;
```


여기서 버전 비교와 변경은 같은 조건부 갱신 안에 있다. 충돌하면 반환 행이 없어지고, 다시 읽어 판단하거나 사용자에게 변경 사실을 알려야 한다. 데이터베이스는 낙관적 동시성 제어를 처리하는 내부 단계에서 잠금을 사용할 수 있다. 애플리케이션이 긴 읽기 구간 동안 잠금을 유지하지 않는다는 점과 데이터베이스 내부의 동시성 처리는 구분했다.

그림 2. 버전 비교와 변경을 한 연산으로 묶은 개념적 흐름. 버전은 변경 순서를 나타내는 식별자다.


## 잠금과 스냅샷을 고를 때 남길 조건


여러 값을 함께 읽고 바꿔야 한다면 잠금이나 더 강한 트랜잭션 격리를 검토할 수 있다. `SELECT ... FOR UPDATE`는 특정 행의 경합을 제어하며, 읽기 허용 범위는 데이터베이스의 잠금, 격리 규칙에 따라 달라진다. 잠금 순서가 어긋나면 교착이나 대기가 생길 수 있으므로 범위를 함께 정해야 했다.


Repeatable Read의 안정된 스냅샷도 최신 값을 계속 보여 주는 기능과는 다르다. PostgreSQL에서는 같은 트랜잭션의 읽기를 일정한 관찰 기준에 맞추지만, 모든 업무 규칙을 자동으로 지켜 주지는 않는다. Serializable에서도 직렬화 실패가 나면 전체 트랜잭션을 재시도할 준비가 필요하다.


선택 기준은 보호할 조건의 범위로 정리했다. 한 행의 조건인지 여러 행의 관계인지, 사람이나 외부 서비스의 대기가 포함되는지에 따라 필요한 처리가 달라진다. 승인 이후 달라진 상태가 어떤 판단을 무효화하는지와 그 의존성 기록은 다음 내용으로 이어진다.
