주문 요청을 처리하는 서버는 보통 재고가 남아 있는지(`재고 > 0`) 먼저 확인한 뒤 수량을 줄인다. 요청이 하나씩 순서대로만 들어온다면 재고를 읽는 단계와 수량을 줄이는 단계를 나누어도 문제가 생기지 않는다. 하지만 마지막 남은 재고 1개에 두 주문 요청이 거의 동시에 들어오면, 확인했을 때의 상태가 실제로 값을 바꿀 때는 더 이상 유효하지 않을 수 있다. 이 글에서는 읽기와 변경 사이에 상태가 달라지는 이유를 짚어 보고, 보호할 조건의 범위와 대기 시간 유무에 따라 동시 요청을 처리하는 방법을 비교한다.


## 읽기와 변경 사이의 상태 어긋남


읽는 단계와 값을 바꾸는 단계가 나뉘어 있을 때 상태가 어떻게 어긋나는지 재고 차감 과정으로 확인할 수 있다. 재고가 1개 남았을 때 두 요청 A와 B가 모두 `재고 = 1`을 읽고 주문이 가능하다고 판단한 상황을 가정한다. 이후 두 요청이 데이터베이스의 재고를 갱신할 때 어떤 현상이 나타나는지는 갱신문을 작성한 방식에 따라 달라진다.


각 요청이 애플리케이션에서 미리 계산한 값(`1 - 1 = 0`)을 데이터베이스에 그대로 덮어쓰면 저장된 재고는 0으로 남는다. 하지만 재고 1개에 대해 주문 두 건이 모두 승인되는 문제가 생긴다. 반대로 각 요청이 별도 조건 없이 현재 저장된 재고에서 1을 빼는 연산(`count = count - 1`)을 실행하면 결과가 달라진다. 요청 A가 먼저 차감해 0이 된 재고에서 요청 B가 다시 1을 빼면서 재고가 -1까지 내려간다. 아래 표는 두 요청이 조건 없이 현재 값에서 1을 차감할 때 상태가 어긋나는 가상의 순서를 보여 준다.


| 순서 | 요청 A              | 요청 B              | 저장된 재고 |
| -- | ----------------- | ----------------- | ------ |
| 1  | 1개를 읽고 주문 가능 판단   | —                 | 1      |
| 2  | —                 | 1개를 읽고 주문 가능 판단   | 1      |
| 3  | 조건 없이 현재 값에서 1 차감 | —                 | 0      |
| 4  | —                 | 조건 없이 현재 값에서 1 차감 | -1     |


요청 B가 2번 단계에서 재고 1개를 읽은 뒤 4번 단계에서 차감을 실행하기 전에, 3번 단계에서 요청 A의 변경이 먼저 반영됐다. 읽을 때 확인한 조건을 변경 시점까지 유지하지 못했기 때문에 재고가 음수로 내려가는 결과가 나온다.


## TOCTOU와 오래된 읽기의 구분


앞선 재고 예제처럼 값을 읽은 뒤 실행하기 전에 상태가 바뀌는 현상은 두 가지 이름으로 불린다. 보안과 시스템 분야에서는 **TOCTOU**(Time-of-check to Time-of-use)나 **오래된 읽기**(stale read)라는 용어를 주로 쓴다. 두 용어 모두 과거 시점의 정보에 기대어 동작한다는 공통점이 있지만 초점을 두는 맥락은 조금 다르다.


보안 분야에서 주로 쓰는 TOCTOU는 자원을 검사한 시점과 실제로 사용하는 시점 사이에 자원이 바뀌는 경쟁 상태를 뜻한다. 예를 들어 보안 취약점 목록인 [MITRE CWE-367](https://cwe.mitre.org/data/definitions/367.html)은 파일 경로를 검사한 뒤 같은 경로 문자열로 파일을 다시 여는 문제를 다룬다. 검사와 열기 사이의 틈에 공격자가 대상 파일을 바꿔치기하면 프로그램은 의도하지 않은 파일을 열게 된다. 검사한 대상과 실제 사용하는 대상이 달라질 수 있으므로, 검사와 사용을 같은 대상에 묶어야 한다.


반면 오래된 읽기는 데이터 일관성 문맥에서 더 넓게 쓰인다. 데이터베이스 복제 지연이나 캐시 때문에 처음부터 이미 지나간 값을 읽는 경우도 오래된 읽기에 속한다. 처음 읽을 때는 최신 값이었지만 실행하기 전 대기하는 사이에 다른 요청이 값을 바꾸는 경우도 포함한다. 두 개념을 하나로 합치기보다, 이 글에서는 최신 값을 읽었더라도 실행 전에 상태가 바뀌어 기존 판단이 깨지는 경우에 초점을 맞춘다.

## 조건부 단일 갱신과 적용 범위


읽기와 실행 사이의 틈을 없애는 단순한 방법은 조건 검사와 값 변경을 하나의 연산으로 합치는 것이다. 보호하려는 조건이 재고 수량처럼 테이블 한 행 안에만 있다면 읽기와 차감을 두 단계로 나누지 않아도 된다. PostgreSQL을 예로 들면 다음과 같이 변경할 대상 식별자와 재고 조건을 `UPDATE` 문 하나에 함께 적는다.


```sql
UPDATE inventory
SET count = count - 1
WHERE sku = :sku AND count > 0
RETURNING count;
```


여기서 `:sku`는 실행할 때 실제 값을 넣을(바인딩할) 상품 식별자 자리다. 조건을 만족해 차감에 성공하면 `RETURNING` 절이 변경된 행을 돌려주고, 조건을 만족하지 못하면 아무 행도 반환하지 않는다. 반환된 행이 없을 때는 상품 자체가 없는지, 재고가 부족한지 구분해 후속 처리를 진행하면 된다.


데이터베이스는 함께 처리할 작업 묶음을 **트랜잭션**(transaction) 단위로 관리한다. 동시에 실행되는 트랜잭션끼리 서로의 변경을 어디까지 보여 줄지 정하는 규칙이 격리 수준이다. 두 요청이 위 갱신문을 동시에 실행하면 PostgreSQL의 기본 격리 수준인 `Read Committed` 규칙에 따라 동작한다. 같은 행을 먼저 수정 중인 트랜잭션이 있으면 뒤따른 `UPDATE`는 앞선 트랜잭션이 끝날 때까지 기다린다. 앞선 요청이 확정(커밋)되어 재고가 0으로 바뀌면, 기다리던 `UPDATE`는 변경된 행을 기준으로 `WHERE` 조건(`count > 0`)을 다시 평가한다. 재고가 이미 0이므로 조건이 거짓이 되어 차감이 일어나지 않는다. 이 재평가 동작은 PostgreSQL의 [트랜잭션 격리 문서](https://www.postgresql.org/docs/current/transaction-iso.html)에서 자세히 설명한다.


물론 이 SQL 문 하나가 주문 처리 전체를 보장하지는 않는다. 주문 내역 기록과 재고 차감이 함께 성공하거나 함께 취소되어야 한다면 두 작업을 하나의 데이터베이스 트랜잭션으로 묶어야 한다. 여기에 외부 결제 시스템 호출까지 끼어들면 데이터베이스 트랜잭션만으로는 이미 완료된 외부 결제를 되돌릴 수 없다. 한 행 안에서 한 번에(원자적으로) 지킬 수 있는 조건과 여러 테이블이나 외부 시스템에 걸친 업무 조건을 나누어 정의해야 각 단계에서 처리할 범위가 명확해진다.


## 대기 구간과 버전 조건부 갱신


조건부 단일 `UPDATE`는 요청을 받자마자 곧바로 값을 바꿀 수 있을 때 유효하다. 반면 현재 상태를 화면에 보여 주고 운영자나 사용자의 승인을 기다리는 작업처럼, 읽기와 실행 사이에 대기 시간이 길어지는 경우도 있다. 이처럼 대기 구간이 길 때는 읽는 동안 데이터베이스 잠금을 계속 붙잡아 두기 어렵다.


이때는 읽을 때의 버전 번호가 변경 시점까지 그대로인지 확인하는 **낙관적 동시성 제어**(optimistic concurrency control)를 쓸 수 있다. 다만 여기서도 버전을 먼저 `SELECT`로 조회해 비교한 뒤 별도의 `UPDATE` 문을 실행하면, 앞선 재고 예제와 똑같이 조회와 갱신 사이에 틈이 다시 생긴다. 버전 비교 역시 변경 연산과 같은 조건부 갱신문 안에 넣어야 한다.


```sql
UPDATE inventory
SET count = count - 1, version = version + 1
WHERE sku = :sku AND version = :read_version AND count > 0
RETURNING count, version;
```


이 쿼리는 처음 읽었던 버전(`:read_version`)과 현재 버전이 일치하는지 확인하면서 재고 조건 검사, 수량 차감, 버전 증가를 한 번에 수행한다. 승인을 기다리는 동안 다른 요청이 해당 행을 수정했다면 버전이 달라져 반환되는 행이 없다. 애플리케이션은 반환 행이 없을 때 충돌을 감지하고, 최신 상태를 다시 읽어 기존 판단을 유지할지 검토하거나 사용자에게 변경 사실을 알려 재승인을 요청해야 한다.


참고로 낙관적 동시성 제어에서 잠금을 잡지 않는다는 말은 애플리케이션이 긴 읽기 및 대기 구간 동안 잠금을 유지하지 않는다는 뜻이다. 데이터베이스는 위 `UPDATE` 문을 실행하는 내부 단계에서 잠금을 사용할 수 있다.


![읽은 값과 버전 7을 바탕으로 승인 대기 후 조건부 갱신을 수행해, 반환 행이 있으면 버전 8로 갱신하고 없으면 다시 읽어 판단 유지 여부를 결정하는 흐름도](/images/notion/tech-k10/image-2.png)

## 행 잠금과 트랜잭션 격리 수준


사용자 대기 없이 짧은 트랜잭션 안에서 끝나는 작업이라도, 여러 행의 값을 함께 읽고 그 관계를 검사한 뒤 수정해야 할 때가 있다. 이처럼 조건이 여러 행에 걸쳐 있으면 단일 행 조건만으로는 부족하므로 명시적인 행 잠금이나 더 강한 트랜잭션 격리 수준을 검토해야 한다.


`SELECT ... FOR UPDATE`는 조회한 행에 즉시 잠금을 걸어 현재 트랜잭션이 끝날 때까지 다른 트랜잭션이 그 행을 수정하지 못하게 막는다. 다른 트랜잭션의 단순 조회 허용 범위는 데이터베이스의 잠금 및 격리 규칙에 따라 달라진다. 여러 행을 잠글 때 요청마다 잠그는 순서가 어긋나면 서로 상대방의 잠금이 풀리기만 기다리는 **교착 상태**(deadlock)나 긴 대기가 생길 수 있다. 따라서 여러 행을 잠글 때는 잠금 범위와 획득 순서를 함께 고정해야 한다.


트랜잭션 격리 수준을 높이는 방법도 특성을 구분해 써야 한다. PostgreSQL의 `Repeatable Read`는 조회 시점의 데이터 상태를 고정해 보여 주는 안정된 스냅샷을 제공한다. 같은 트랜잭션 안에서 반복 조회할 때 관찰 기준을 일정하게 유지해 주는 방식이다. 다만 실시간 최신 값을 계속 보여 주는 기능이 아니며 여러 행에 걸친 모든 업무 규칙을 자동으로 지켜 주지도 않는다. 가장 엄격한 `Serializable` 격리 수준을 쓰더라도 트랜잭션 간 충돌로 직렬화 실패가 발생하면 데이터베이스가 한쪽 트랜잭션을 중단시킨다. 따라서 이 격리 수준을 사용할 때는 애플리케이션에 전체 트랜잭션을 재시도하는 로직을 준비해야 한다.

## 결론


동시 요청 환경에서 값을 읽고 변경하는 사이에 상태가 바뀌면 오래된 판단으로 잘못된 갱신이 실행될 수 있다. 이를 막는 상태 변경 방식을 고르는 기준은 보호할 조건의 범위와 대기 구간 유무로 귀결된다. 한 행 안의 조건이고 즉시 변경한다면 조건과 변경을 합친 조건부 단일 갱신문으로 충분하다. 여러 행의 관계를 짧은 트랜잭션 안에서 지켜야 한다면 잠금 순서를 정한 행 잠금이나 재시도를 포함한 상위 격리 수준이 필요하다. 반대로 사람이나 외부 서비스의 응답을 기다려야 한다면 버전을 포함한 조건부 갱신으로 충돌을 잡아내야 한다.


승인 대기 중에 바뀐 상태가 기존 판단의 어느 부분까지 무효로 만드는지, 그리고 상태 의존성을 어떻게 기록할지는 이어지는 글에서 다룬다.
