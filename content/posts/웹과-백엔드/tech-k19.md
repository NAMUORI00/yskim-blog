## 같은 요청이 두 번 도착하는 상황


작업 재시도를 정리하며 반복 요청의 효과를 살펴봤다. 응답이 끊기면 클라이언트는 서버의 완료 여부를 알지 못할 수 있다. 결제 요청을 설명용 사례로 두고, 같은 요청이 다시 들어와도 의도된 효과가 같게 남는 멱등성의 조건을 정리했다.


## 멱등하다는 말이 가리키는 범위


[RFC 9110](https://datatracker.ietf.org/doc/html/rfc9110#section-9.2.2) Section 9.2.2는 HTTP 메서드의 멱등성을 이렇게 정의한다.


동일한 요청을 여러 번 보내도, 서버에 남는 _의도된 효과_가 한 번 보냈을 때와 같으면 그 메서드는 멱등하다. GET, HEAD, PUT, DELETE가 멱등에 해당하고, POST에는 메서드 자체의 멱등 보장이 없다. 개별 API가 별도의 중복 방지 계약을 제공할 수는 있다.


멱등성의 기준은 요청의 의도된 효과다. PUT /users/42 `{"name": "Kim"}`을 두 번 보내면 접근 로그는 두 줄일 수 있지만 42번 사용자의 이름은 Kim으로 남는다. 로그와 통계 같은 부수 효과는 이 상태 변경과 나누어 읽었다.


POST /orders를 같은 내용으로 두 번 보내면, 서버가 별도로 방어하지 않는 한 주문 두 건이 생긴다. 의도된 효과 자체가 달라지므로 비멱등이다. 같은 내용이라는 사실만으로는 중복이 방지되지 않는다.


## 작업 상태와 재시도의 불확실성


응답을 받지 못한 클라이언트 입장에서, 서버 쪽 작업은 세 가지 상태 가운데 하나에 놓여 있다.

- **시작 전**: 서버가 요청을 받지 못했거나, 검증 단계에서 탈락했다.
- **실행 중**: 서버가 처리를 시작했지만 응답을 보내기 전이다.
- **완료**: 성공이든 실패든 결과가 확정되었다.

셋 중 어디인지 클라이언트가 알 수 없다는 점이 핵심이다. 시작 전이라면 재시도가 필요하고, 이미 완료된 상태에서 재시도하면 같은 작업이 두 번 실행될 수 있다.


계좌에 10,000원이 있을 때 POST /transfer `{"amount": 5000}`을 두 번 보내면, 첫 번째 이후 잔액 5,000원, 두 번째 이후 잔액 0원이 된다. 재시도가 안전하려면 "이미 완료된 작업을 다시 실행해도 결과가 같다"는 보장이 선행되어야 한다.

## 비멱등 작업에 키를 붙이는 방법


POST처럼 본래 멱등하지 않은 작업에도 멱등성을 부여할 수 있다. [Stripe API의 멱등성 키](https://docs.stripe.com/api/idempotent_requests)가 대표적인 구현이다.


```javascript
POST /v1/charges
Idempotency-Key: a1b2c3d4-e5f6-7890-abcd-ef1234567890
```


클라이언트가 UUID 같은 고유 문자열을 만들어 요청 헤더에 넣는다. 서버는 이 키를 처음 받으면 요청을 실행하고, 상태 코드와 응답 본문을 키와 함께 저장한다. 같은 키로 요청이 다시 들어오면 저장된 결과를 그대로 돌려주고 작업을 재실행하지 않는다.


다음 코드는 **완료 결과 재사용만 보여 주는 불완전한 의사 코드**다. 실제 중복 방지 구현으로 사용하기에는 두 빈틈이 남는다.


```python
import uuid

key = str(uuid.uuid4())

def create_charge(amount, idempotency_key):
    saved = lookup_key(idempotency_key)
    if saved is not None:
        return saved          # 저장된 결과 반환, 재실행 없음

    result = process_payment(amount)
    store_key(idempotency_key, result)
    return result
```


의사 코드에는 동시 조회에서 두 요청이 모두 실행될 가능성과 결제 후 결과 저장 전 종료되는 구간이 남는다. 실제 구성에는 키, 요청 내용의 원자적 예약, 진행 상태, 만료, 복구 정책이 더 필요하다. 외부 결제 효과도 해당 서비스의 멱등 계약에 연결할 부분이다.


Stripe는 같은 키에 다른 파라미터가 들어오면 오류를 반환한다. 키를 실수로 재사용하면서 금액이나 수신자를 바꾸는 사고를 막기 위해서다. 문서에서는 생성 후 최소 24시간이 지난 키를 제거할 수 있다고 설명한다.


정확히 24시간에 일괄 만료된다는 뜻은 아니며, 제거된 키를 다시 보내면 새 요청으로 처리될 수 있다. 키의 유효 기간보다 재시도 간격이 길어지면 중복 보호가 풀린다는 뜻이기도 하다.

## 키 없이도 멱등한 경우


멱등성 키의 필요성은 작업의 중복 효과와 식별 방식에 따라 판단한다. 구조적으로 이미 멱등한 작업이 있다.


PUT /balance `{"amount": 5000}`을 두 번 보내면 두 번 다 잔액이 5,000원이 된다. "5,000원으로 설정하라"는 명령이므로 반복해도 결과가 같다. 반면 앞의 POST /transfer `{"amount": 5000}`은 "5,000원을 이체하라"는 명령이라 실행할 때마다 효과가 누적된다.


DELETE /users/42를 두 번 보내면 첫 번째는 삭제를 수행하고, 두 번째는 API 설계에 따라 404 또는 204 등을 반환할 수 있다. 응답 코드는 달라지지만 서버 상태(42번 사용자가 없다)는 동일하다. Stripe 역시 GET과 DELETE 요청에는 멱등성 키를 보내도 효과가 없다고 명시한다. 이 메서드들은 정의 자체로 멱등이기 때문이다.


| 메서드    | 멱등 여부        | 키 필요                  |
| ------ | ------------ | --------------------- |
| GET    | 멱등           | 불필요                   |
| PUT    | 멱등           | 불필요                   |
| DELETE | 멱등           | 불필요                   |
| POST   | 메서드 자체 보장 없음 | API가 지원하는 중복 방지 계약 확인 |


## 재시도 이후의 확인 항목


멱등성을 갖춘 작업도 재시도 횟수와 간격을 정해 자원 사용을 관리해야 한다. Stripe는 500 에러 결과도 키에 저장하기 때문에, 같은 키로 재시도하면 저장된 에러가 그대로 돌아온다. 그렇다고 바로 새 키로 바꾸면 이전 작업과 다른 요청으로 처리되어 효과가 중복될 수 있다.


500 응답만으로 실제 변경이 없었다고 판단하지 않고, 작업 상태 조회나 서비스가 제공하는 복구 절차로 결과를 먼저 확인해야 한다. 검증 실패나 동시 요청 충돌처럼 실행 자체가 시작되기 전에 거부된 경우에는 결과가 저장되지 않으므로, 같은 키로 다시 보내면 정상 실행될 수 있다.


이번에는 요청 하나의 중복 효과와 결과 재사용을 중심으로 정리했다. 멱등성 키 저장소의 장애와 여러 외부 서비스에 걸친 작업의 키 관리가 다음 범위다. 저장소 복구와 서비스별 실행 결과를 연결하는 조건을 더 살펴볼 필요가 있다.
