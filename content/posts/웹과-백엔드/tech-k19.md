요청을 보내는 쪽인 클라이언트가 서버로 요청을 보낸 뒤 네트워크가 끊기거나 응답 시간이 초과될 때가 있다. 이때 클라이언트는 요청이 아예 서버에 도달하지 못했는지, 서버가 처리를 모두 마친 직후 응답만 사라졌는지 알 수 없다. 응답을 받지 못한 클라이언트 입장에서 서버 작업은 시작 전, 실행 중, 완료의 세 가지 상태 가운데 하나에 놓인다. 서버가 요청을 받지 못했거나 검증 단계에서 탈락한 상태가 시작 전이고, 처리를 시작했지만 아직 응답을 보내기 전이 실행 중이다. 성공이든 실패든 서버에서 처리가 끝나 결과가 확정된 상태는 완료에 해당한다. 클라이언트는 이 셋을 구분할 수 없는데, 시작 전이라면 다시 보내야 하지만 완료 상태에서 그대로 재시도하면 같은 작업이 두 번 실행될 수 있다.


예를 들어 잔액이 10,000원인 계좌에서 5,000원을 보내라는 `POST /transfer` `{"amount": 5000}` 요청을 보냈다고 하자. 첫 요청이 완료된 직후 응답만 끊겨 같은 요청을 한 번 더 보내면, 잔액은 첫 실행 뒤 5,000원이 되었다가 두 번째 실행 뒤 0원으로 줄어든다. 이처럼 응답이 끊겼을 때 안전하게 재시도하려면, 완료된 작업에 같은 요청이 다시 들어와도 결과가 한 번 실행했을 때와 같게 남는다는 보장이 필요하다. 이런 성질을 **멱등성**(idempotency)이라고 하며, 이 글에서는 멱등성의 판단 기준과 중복 실행을 막는 멱등성 키의 적용 조건을 다룬다.


## 멱등성의 기준과 키 없이도 멱등한 요청


어떤 요청이 멱등한지 판단하려면 같은 요청을 여러 번 보냈을 때 서버에 남는 결과가 달라지는지 확인해야 한다. 웹에서 요청을 주고받는 규칙인 HTTP 표준 [RFC 9110](https://datatracker.ietf.org/doc/html/rfc9110#section-9.2.2) Section 9.2.2는 이 기준을 의도된 효과(intended effect)로 설명한다. 같은 요청을 여러 번 보내도 서버에 남는 의도된 효과가 한 번 보냈을 때와 같으면 그 요청 방식인 메서드는 멱등하다. HTTP 메서드 가운데 조회나 덮어쓰기, 삭제에 쓰이는 `GET`, `HEAD`, `PUT`, `DELETE`가 여기에 해당한다. 반대로 `POST`에는 메서드 자체의 멱등 보장이 없으며, 서버가 외부 요청을 받는 창구인 개별 API에서 별도의 중복 방지 계약을 제공할 수는 있다.


예를 들어 42번 사용자의 이름을 바꾸는 `PUT /users/42` `{"name": "Kim"}` 요청을 두 번 보냈다고 하자. 서버의 접근 기록인 로그는 두 줄이 남을 수 있지만, 42번 사용자의 이름이 `Kim`으로 바뀐 결과는 한 번 보냈을 때와 같다. 이처럼 로그나 통계 집계 같은 부수 효과는 요청이 본래 의도한 상태 변경과 구분해서 본다. 사용자를 삭제하는 `DELETE /users/42`를 두 번 보낼 때도 마찬가지다. 첫 번째 요청은 삭제를 수행하고, 두 번째 요청은 API 설계에 따라 대상이 없다는 뜻의 `404`나 성공을 뜻하는 `204` 등을 응답 상태 코드로 돌려줄 수 있다. 서버가 처리 결과를 숫자로 알려 주는 응답 코드는 달라지지만, 42번 사용자가 존재하지 않는다는 서버 상태는 동일하다.


잔액을 5,000원으로 설정하라는 `PUT /balance` `{"amount": 5000}` 요청도 두 번 보내면 두 번 다 잔액이 5,000원으로 남는다. 대상을 직접 지정해 목표 상태를 덮어쓰거나 삭제하는 작업은 이처럼 구조적으로 이미 멱등하다. 반면 5,000원을 이체하라는 `POST /transfer` `{"amount": 5000}` 요청은 실행할 때마다 차감 효과가 누적된다. 주문을 생성하는 `POST /orders` 역시 서버가 별도로 방어하지 않는 한 같은 내용으로 두 번 보내면 주문 두 건이 생긴다. 따라서 요청 내용이 같다는 사실만으로는 중복 실행이 방지되지 않는다.

그림 1. 같은 요청을 두 번 보냈을 때 잔액 설정(PUT)과 이체(POST)의 결과 비교(설명용 예제).


별도의 멱등성 키가 필요한지는 작업이 반복될 때 효과가 누적되는지, 그리고 대상을 어떻게 식별하는지에 따라 판단한다. 결제 서비스인 Stripe API도 `GET`과 `DELETE` 요청은 정의 자체로 멱등이므로 멱등성 키를 보내도 아무 효과가 없다고 명시한다.


| 메서드    | 멱등 여부        | 키 필요                  |
| ------ | ------------ | --------------------- |
| GET    | 멱등           | 불필요                   |
| PUT    | 멱등           | 불필요                   |
| DELETE | 멱등           | 불필요                   |
| POST   | 메서드 자체 보장 없음 | API가 지원하는 중복 방지 계약 확인 |


## 멱등성 키를 이용한 결과 재사용


앞선 표에서 보듯 `POST`처럼 본래 멱등하지 않은 작업에도 요청마다 고유한 **멱등성 키**(idempotency key)를 붙여 멱등성을 부여할 수 있다. [Stripe API의 멱등성 키](https://docs.stripe.com/api/idempotent_requests)가 이러한 방식의 대표적인 구현이다.


```plain text
POST /v1/charges
Idempotency-Key: a1b2c3d4-e5f6-7890-abcd-ef1234567890
```


클라이언트는 UUID(범용 고유 식별자) 같은 고유 문자열을 만들어 요청 부가 정보를 담는 `Idempotency-Key` 헤더에 넣는다. 서버는 이 키를 처음 받으면 요청을 실행하고, 응답 상태 코드와 응답 본문을 키와 함께 저장한다. 응답이 중간에 유실되어 클라이언트가 같은 키로 요청을 다시 보내면, 서버는 저장된 결과를 그대로 돌려주고 작업을 다시 실행하지 않는다.


![클라이언트가 멱등성 키 abc-123으로 요청을 보내고 응답이 유실된 뒤 같은 키로 재시도해 키 저장소에 저장된 응답을 돌려받는 시퀀스 다이어그램](/images/notion/tech-k19/image-2.png)


그림 2. 멱등성 키를 이용한 재시도 흐름(설명용 예제). 결과 저장까지 완료된 뒤 응답만 유실된 순차 요청을 가정했으며, 동시 요청과 저장 전 장애는 생략했다. 직접 작성.


다음 의사 코드에서 서버는 먼저 `lookup_key`로 키를 조회해, 저장된 결과가 있으면 작업을 다시 실행하지 않고 그대로 돌려준다. 저장된 결과가 없을 때만 `process_payment`로 결제를 실행한 뒤 `store_key`로 저장하지만, 실제 중복 방지 구현으로 쓰기에는 두 가지 빈틈이 있다.


```python
import uuid

key = str(uuid.uuid4())

def create_charge(amount, idempotency_key):
    saved = lookup_key(idempotency_key)
    if saved is not None:
        return saved          # 저장된 결과 반환, 재실행 없음

    result = process_payment(amount)
    store_key(idempotency_key, result)
    return result
```


![서버가 POST 요청과 키를 받아 키 저장소에 키가 없으면 작업을 실행해 저장한 뒤 새 응답을 반환하고, 키가 있으면 저장된 결과를 조회해 캐시된 응답을 반환하는 흐름도](/images/notion/tech-k19/image-3.png)


그림 3. 서버 측 멱등성 키 처리 흐름도(설명용 예제). 완료 결과 조회의 개념만 나타냈으며 원자적 예약, 진행 중 충돌, 장애 복구는 생략했다. 직접 작성.


## 단순 조회 코드의 빈틈과 키 유효 조건


위 의사 코드는 앞선 요청이 결과 저장까지 모두 끝난 뒤에야 다음 요청이 들어오는 상황만 가정한다. 실제 환경에서는 키 조회와 결제 실행, 결과 저장의 단계 사이에서 두 구간이 문제로 남는다.


첫째는 결과를 저장하기 전에 같은 키가 다시 들어오는 동시 조회 구간이다. 같은 키를 가진 두 요청이 거의 동시에 들어와 첫 요청이 `store_key`를 마치기 전에 두 번째 요청이 `lookup_key`를 실행할 수 있다. 이때는 두 요청 모두 저장된 결과가 없다고 판단해 `process_payment`를 중복으로 실행하게 된다. 둘째는 결제가 끝난 직후부터 결과를 저장하기 전까지의 구간이다. `process_payment`가 실행된 뒤 `store_key`가 완료되기 전에 서버가 종료되면, 결제는 이미 처리되었는데도 키 저장소에는 기록이 남지 않는다. 이 상태에서 클라이언트가 재시도하면 서버는 기록이 없는 것으로 보고 결제를 다시 실행한다.


![키 조회, 결제 실행, 결과 저장의 3단계 사이에서 발생하는 저장 전 동시 조회 구간과 결제 후 저장 전 종료 구간을 표시한 다이어그램](/images/notion/tech-k19/image-4.png)


그림 4. 완료 결과만 조회하는 의사 코드에 남아 있는 두 가지 취약 구간(설명용 예제).


따라서 실제 운영 환경을 만들 때는 완료된 결과만 저장하는 것으로는 부족하다. 작업을 실행하기 전에 중간에 다른 요청이 끼어들 수 없는 한 단위인 **원자적**(atomic) 방식으로 키와 요청 내용을 먼저 예약해야 한다. 여기에 진행 중 상태 표시와 키 만료, 장애 복구 정책도 함께 갖춰야 한다. 외부 결제 서비스를 호출하는 작업이라면 그 외부 서비스가 제공하는 멱등 계약에 키를 연결하는 과정도 필요하다.


클라이언트가 키를 재사용하는 방식과 키의 보관 기간에도 조건이 붙는다. 클라이언트가 실수로 이전 키를 재사용하면서 결제 금액이나 수신자 같은 요청 값(파라미터)만 바꾸는 사고가 날 수 있다. Stripe는 이러한 사고를 막기 위해 같은 키에 이전과 다른 파라미터가 들어오면 오류를 반환한다.


또한 Stripe 문서는 생성된 지 최소 24시간이 지난 키를 저장소에서 제거할 수 있다고 설명한다. 정확히 24시간이 되는 시점에 일괄 만료된다는 뜻은 아니며, 이미 제거된 키를 다시 보내면 새로운 요청으로 처리될 수 있다. 재시도 간격이 서버의 키 유효 기간보다 길어지면 중복 방지 보호가 풀린다는 뜻이기도 하다.


## 에러 응답과 재시도 이후의 확인 항목


키 유효 기간 안에서 멱등성을 갖춘 작업을 다시 보낼 때도 재시도 횟수와 간격을 정해 서버와 네트워크 자원 사용을 관리해야 한다. 재시도 과정에서 에러 응답을 받았을 때는 에러가 발생한 시점에 따라 처리 방식이 달라진다.


요청 검증 실패나 동시 요청 충돌처럼 작업 실행 자체가 시작되기 전에 거부된 경우에는 결과가 키에 확정되어 저장되지 않는다. 따라서 작업이 시작되기 전에 거부된 요청은 같은 키로 다시 보내면 정상 실행될 수 있다. 반면 Stripe는 작업 도중 발생한 서버 오류인 `500` 에러 결과도 키에 저장하므로, 같은 키로 재시도하면 저장된 에러가 그대로 돌아온다.


그렇다고 `500` 에러를 받자마자 바로 새 키로 바꿔 다시 요청하면, 서버가 이전 작업과 별개인 새 요청으로 처리해 효과가 중복될 수 있다. `500` 응답만으로 서버에 실제 상태 변경이 없었다고 단정하지 말고, 작업 상태 조회 API나 서비스가 제공하는 복구 절차로 이전 요청의 결과를 먼저 확인해야 한다.


## 결론


응답이 끊겨 서버의 처리 상태를 알 수 없을 때 안전하게 재시도하려면, 같은 요청을 다시 보내도 결과가 한 번 실행했을 때와 같게 남는 멱등성이 필요하다. 대상을 조회하거나 직접 지정해 덮어쓰고 삭제하는 `GET`, `PUT`, `DELETE` 요청은 별도의 키 없이도 메서드 정의 자체로 멱등하다. 반면 실행할 때마다 효과가 누적되는 `POST` 요청은 요청마다 고유한 멱등성 키를 붙여 이전 결과를 재사용해야 한다. 이때 동시 요청과 서버 종료에 대비한 원자적 예약, 파라미터 검증과 키 유효 기간 관리, `500` 에러 발생 뒤의 상태 확인까지 갖춰야 중복 실행을 막을 수 있다.


이번 글에서는 단일 요청의 중복 효과와 멱등성 키를 이용한 결과 재사용 조건을 확인했다. 실제 운영 환경에서 멱등성 키 저장소 자체에 장애가 나거나 하나의 작업이 여러 외부 서비스에 걸쳐 실행되는 상황은 아직 다루지 않았다. 저장소 복구 방법과 외부 서비스별 실행 결과를 연결하는 조건은 앞으로 더 확인할 과제다.
