서버가 프로그램끼리 데이터를 주고받도록 열어 둔 창구를 API라고 부른다. 같은 웹 API 주소로 요청을 보내도 정상 데이터가 돌아올 때가 있고, `401 Unauthorized`나 `403 Forbidden`처럼 거절 응답이 올 때도 있다.


서버가 어떤 기준으로 이런 결정을 내리는지 파악하려면 브라우저와 서버가 인터넷에서 메시지를 주고받는 규칙인 HTTP의 구조를 먼저 알아야 한다. 요청 하나가 서버에 도착해 신원 확인과 권한 검사를 거쳐 응답으로 돌아오는 과정을 예제로 따라간다.


## HTTP 요청의 구성 요소


먼저 브라우저가 서버에 데이터를 달라고 보낼 때 HTTP 요청 메시지가 어떻게 생겼는지 본다.


```plain text
GET /api/notes HTTP/1.1
Host: example.com
Accept: application/json
Authorization: Bearer <예시-토큰>
```


HTTP 요청은 첫 줄에 적는 **메서드**(method)와 **경로**(path), 둘째 줄부터 이어지는 **헤더**(headers)로 이루어진다. 첫 줄인 요청 줄에는 서버에 원하는 동작을 뜻하는 메서드 `GET`과 노트 목록처럼 서버에서 다룰 데이터(자원)의 위치를 가리키는 경로 `/api/notes`가 놓인다. 경로 뒤에는 통신 규칙(프로토콜)의 버전인 `HTTP/1.1`을 함께 적는다.


요청 줄 아래에 이어지는 헤더는 서버가 요청을 처리할 때 참고할 부가 정보를 담는다. `Host`는 요청이 향하는 서버 주소를 나타내고, `Accept`는 브라우저처럼 요청을 보내는 프로그램인 클라이언트가 원하는 응답 데이터 형식을 알려 준다. `Authorization` 헤더는 요청을 보낸 사용자의 신원을 증명하는 자격 증명을 전달하는 자리다. [MDN의 HTTP 인증 가이드](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Authentication)에 정리된 것처럼, 이 헤더에는 서버가 요구하는 인증 방식(스킴)인 `Bearer`나 `Basic`에 맞춘 자격 증명이 들어간다. 위 예제에서는 서버가 발급한 문자열 표식인 토큰(token)을 `Bearer` 뒤에 붙여 보냈다.


데이터를 새로 등록하는 `POST` 요청이나 기존 데이터를 수정하는 `PUT` 요청에서는 헤더 뒤에 빈 줄을 하나 두고 본문(body)을 덧붙여 데이터를 함께 보낸다. 반면 서버에서 자원을 읽어 오는 `GET` 요청에는 보통 본문을 두지 않는다.


## HTTP 응답과 상태 코드


앞 절에서 본 HTTP 요청을 받은 서버는 처리 결과를 정해진 형식의 HTTP 응답 메시지로 돌려준다.


```plain text
HTTP/1.1 200 OK
Content-Type: application/json

{"notes": [{"id": 1, "title": "첫 번째 노트"}]}
```


첫 줄은 상태 줄로, 통신 규칙 버전 뒤의 `200`은 처리 결과를 숫자로 나타낸 **상태 코드**(status code)이고 `OK`는 상태 메시지다. 상태 코드의 첫 자리 숫자는 응답의 성격을 가리킨다. `2xx`는 요청 처리 성공을 뜻하고, `3xx`는 다른 위치로 이동하라고 안내하는 리다이렉트를 나타낸다. `4xx`는 클라이언트 측 요청 오류이며, `5xx`는 서버 내부 오류로 나뉜다.


둘째 줄의 `Content-Type` 헤더는 빈 줄 뒤에 오는 본문이 어떤 데이터 형식인지 알려 준다. 실제 응답에는 전송할 형태로 인코딩된 본문의 바이트 수를 적은 `Content-Length` 헤더도 함께 붙지만, 위 예제에서는 기본 구조만 보이도록 생략했다.


지금까지 본 HTTP 요청과 응답은 첫 줄, 헤더, 본문이라는 대칭된 틀을 갖는다. 정상 처리 결과뿐 아니라 신원 확인 실패, 권한 부족, 서버 내부 오류도 모두 이 응답 구조 안에서 상태 코드와 헤더, 본문의 조합으로 표현된다. 구체적인 응답 형태는 실패 원인과 API에서 미리 정한 규칙(계약)에 따라 달라진다.

## 인증과 401 응답


응답 구조를 알았으니, 이제 서버가 보호된 자원에 대한 요청을 받았을 때 가장 먼저 검사하는 **인증**(authentication) 단계를 본다. 인증은 요청을 보낸 주체가 누구인지 밝히는 과정이며, 서버가 요청에서 유효한 자격 증명을 찾지 못하면 [401 Unauthorized](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/401) 응답을 돌려보낸다.


```plain text
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer realm="api"
```


이 응답에 포함된 `WWW-Authenticate` 헤더는 클라이언트에게 어떤 인증 방식을 써서 다시 요청해야 하는지 안내한다. 상태 메시지에 `Unauthorized`라는 단어가 쓰이지만, HTTP 표준에서 `401`은 권한 부족이 아니라 신원을 확인할 수 없다는 뜻이다. 요청에 토큰이 아예 없을 때뿐 아니라, 토큰의 유효 기간이 만료되었거나 형식이 잘못되었을 때도 모두 여기에 해당한다. 유효한 자격 증명을 갖춰 다시 요청하면 통과할 수 있다는 점이 다음 절에서 볼 `403`과 다르다.


## 인가와 403 응답


인증을 통과해 요청을 보낸 사람이 누구인지 확인되었더라도, 그 사용자에게 해당 자원을 다룰 권한이 있는지는 따로 따져야 한다. 이 권한 검사 과정을 **인가**(authorization)라고 부르며, 권한이 부족할 때 서버는 [403 Forbidden](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/403) 응답을 돌려보낸다.


```plain text
HTTP/1.1 403 Forbidden
Content-Type: application/json

{"error": "admin role required"}
```


위 예제 본문의 `admin role required`는 이 자원에 접근하려면 관리자 권한이 필요하다는 뜻이다. 앞에서 본 `401`이 유효한 인증 정보가 필요하다는 뜻이라면, `403`은 서버가 요청과 호출자를 이해했지만 접근을 허용하지 않았다는 뜻이다. 이미 신원이 확인된 상태에서 권한이 부족해 거절된 것이므로, 같은 자격 증명으로 요청을 다시 보내도 결과는 바뀌지 않는다. 관리자 계정처럼 필요한 권한을 가진 자격 증명으로 요청해야 인가 단계를 통과할 수 있다.


다만 `403` 응답이 왔다고 해서 언제나 인증이 성공했다고 단정할 수는 없다. 허용되지 않은 IP 대역 차단이나 다른 접근 제한 정책에 걸렸을 때도 서버가 `403`을 반환할 수 있기 때문이다. 예제 서버가 요청을 받아 인증과 인가를 차례로 검사하며 응답을 결정하는 흐름은 다음과 같다.

## 요청 조건별 응답 비교와 한계


앞에서 나눈 인증과 인가 검사가 실제 요청을 받는 API 주소인 엔드포인트(endpoint) 하나에서 어떻게 이어지는지 비교해 본다. 관리자 설정을 조회하는 `GET /api/admin/settings` 엔드포인트에 토큰 조건이 다른 세 가지 요청을 보내는 상황이다.


```plain text
요청 1: Authorization 헤더 없음        → 401 Unauthorized
요청 2: 일반 사용자 토큰              → 403 Forbidden
요청 3: 관리자 토큰                   → 200 OK + 설정 데이터
```


예제 서버는 요청이 들어오면 먼저 `Authorization` 헤더의 토큰으로 신원을 확인하고, 그다음에 해당 사용자가 관리자 권한을 가졌는지 검사한다. 요청 1은 토큰이 없어 신원 확인 단계에서 멈추고, 요청 2는 신원은 확인됐지만 권한 검사에서 거절된다. 관리자 토큰을 담은 요청 3만 두 단계를 모두 통과해 `200 OK` 응답과 함께 설정 데이터를 받는다.

그림 3. 같은 엔드포인트에 토큰 상태가 다른 세 요청을 보냈을 때 달라지는 응답 시나리오(개념도).


위 비교는 예제 API를 기준으로 인증과 인가의 기본 처리 순서를 정리한 결과다. 실제 서비스에서는 자원이 공개되어 있는지나 보안 정책이 어떠한지에 따라 응답 동작이 달라질 수 있다. 예를 들어 권한이 없는 사용자에게 관리자 경로가 존재한다는 사실 자체를 숨기려고 `403` 대신 자원을 찾을 수 없다는 뜻의 `404`를 돌려주기도 한다. 따라서 응답 상태 코드 하나만 보고 서버 내부의 처리 단계를 단정하기보다, API 계약과 서버 로그를 함께 확인해야 원인을 정확히 좁힐 수 있다.


## 결론


HTTP 요청과 응답의 기본 구조 위에서 서버가 자격 증명과 접근 권한을 어느 단계에서 검사하는지 예제 흐름으로 확인했다. 브라우저는 메서드, 경로, 헤더로 구성된 요청을 보내며, `Authorization` 헤더에 `Bearer` 토큰을 담아 신원을 증명한다. 서버는 먼저 누구인지 확인하는 인증 단계에서 유효한 자격 증명이 없으면 `401`을 반환한다. 인증을 통과한 뒤 권한을 따지는 인가 단계에서는 권한이 부족할 때 `403`을, 두 검사를 모두 통과하면 `200 OK`를 돌려준다.


다만 이 흐름은 `Bearer` 토큰을 쓰는 예제 API의 기본 순서이므로, 실제 서비스에서는 보안 정책과 API 계약, 서버 로그를 함께 확인해야 한다. 웹 환경에서 널리 쓰이는 쿠키 인증은 이번 글에서 다루지 않았는데, 쿠키와 `Bearer` 토큰이 요청 구조에서 어떻게 다른지는 다음 비교 주제로 남겨 둔다. 다른 출처(origin)의 API에 브라우저가 먼저 보내는 `OPTIONS` 프리플라이트(preflight) 요청이 인증, 인가 검사와 어떻게 이어지는지도 다음 질문으로 남긴다.
