방문자가 접속할 때마다 서버가 즉석에서 화면을 만드는 동적 웹과 달리, 정적 웹사이트는 완성된 파일들을 미리 만들어 두고 배포한다. 원본 글과 이미지를 모아 웹페이지 파일들로 변환하는 이 과정을 빌드(build)라고 부른다. 글을 보관하고 관리하는 콘텐츠 관리 시스템(CMS)이나 마크다운 파일에 쓴 글도 원본 수집, HTML 변환, 이미지 처리, 배포 단계를 거쳐 정적 웹페이지로 공개된다. 이 글에서는 글 한 편과 이미지 한 장(`photo.jpg`)이 이 경로를 지나며 어떻게 처리되는지 따라간다. 그 과정에서 초안 상태(`draft`)나 이미지 파일 경로 설정이 최종 공개 결과에 어떤 영향을 주는지 확인한다.


## 마크다운 문서와 정적 파일 변환


정적 웹페이지를 만들 때는 원본 마크다운 문서를 HTML 파일로 변환하고 본문에 연결된 이미지를 함께 처리한다. 아래와 같은 마크다운 파일 하나를 정적 웹페이지로 변환하는 경우를 예로 든다.


```markdown
---
title: "첫 글"
date: 2026-09-15
draft: false
---

본문 내용이 여기에 온다.

![사진](photo.jpg)
```


문서 맨 위에 `---`로 구분해 제목이나 날짜 같은 문서 정보(메타데이터)를 적는 영역을 **프런트매터**(front matter)라고 한다. 원본 문서로 사이트를 만드는 **정적 사이트 생성기**(SSG, Static Site Generator)는 빌드할 때 이 값을 읽어 문서를 최종 결과물에 포함할지 결정한다. 예를 들어 정적 사이트 생성기인 Hugo의 기본 규칙에서 `draft: false`는 초안 제외 조건에 걸리지 않는다는 표시다. 이 밖에도 발행일이나 만료일, 빌드 명령의 옵션이 최종 포함 여부에 영향을 준다.


Hugo에서 `hugo build` 명령을 실행하면 `content/` 폴더(디렉터리)의 마크다운 본문을 Goldmark 파서로 해석해 HTML 조각으로 변환한다. 이어서 `layouts/` 폴더에 정의된 화면 틀(템플릿)과 결합해 완성된 HTML 파일을 `public/` 폴더에 출력한다([Hugo - Introduction](https://gohugo.io/about/introduction/)).


본문에 연결된 `photo.jpg`는 파일을 어느 폴더에 두고 템플릿에서 어떻게 다루느냐에 따라 처리 방식이 갈린다([Hugo - Content Organization](https://gohugo.io/content-management/organization/)). `static/` 폴더에 넣은 파일은 별도의 가공 없이 원래 이름 그대로 `public/` 폴더에 복사된다. 반면 파일을 `assets/` 폴더에 두면 이미지 처리 파이프라인을 거칠 수 있다. 이때는 템플릿에서 호출한 리소스 처리 함수에 따라 크기를 줄이거나(resize) 포맷을 변환한 파일을 출력한다. 다만 `assets/` 폴더에 파일을 넣는 것만으로는 변환이 자동으로 일어나지 않으며 템플릿에서 리소스 함수를 실제로 호출해야 한다. 파일 내용으로 계산한 고유 문자열인 해시값을 파일명에 붙이는 지문(fingerprint) 처리를 적용할 때도 주의해야 한다. 함수를 거친 최종 반환 URL이 HTML에 제대로 반영되었는지 함께 확인해야 하기 때문이다. 이렇게 생성된 정적 파일들은 독자와 가까운 서버에서 파일을 빠르게 전달하는 전송망인 CDN에 배포된다.

## 헤드리스 CMS와 웹훅 기반 빌드


앞 절처럼 마크다운 파일을 저장소에 직접 두고 편집하는 대신, 별도의 CMS에서 글을 관리할 수도 있다. 이때 **헤드리스 CMS**(headless CMS)는 콘텐츠의 저장과 관리만 맡고, 방문자에게 보여 줄 화면을 그리는 렌더링은 분리해 둔 시스템이다. 작성자를 위한 자체 편집기나 미리보기 화면은 제공할 수 있지만, 외부로는 프로그램 사이의 통신 창구인 API를 통해 JSON 같은 데이터 형태로만 콘텐츠를 내보낸다. 이 JSON 데이터를 받아 HTML 페이지를 생성하는 일은 정적 사이트 생성기나 화면을 구성하는 프런트엔드 프레임워크가 담당한다.


콘텐츠 저장소와 화면을 분리하면 같은 글 데이터를 웹사이트, 모바일 앱, 뉴스레터에서 각기 다른 형태로 가져다 쓸 수 있다. 나중에 화면을 그리는 기술 스택을 바꾸더라도 기존 콘텐츠 저장소는 그대로 유지할 수 있다. 반면 새 화면 구성에 필요한 데이터 항목이 달라지면 CMS의 입력 항목(필드)과 데이터 모델은 그에 맞춰 조정해야 한다.


반대로 CMS가 테마 렌더링까지 한꺼번에 담당하면 초기 구성은 단순하지만 콘텐츠 구조와 화면 설정이 강하게 묶인다. 물론 WordPress처럼 자체 테마 렌더링을 지원하는 도구도 API를 통해 데이터만 제공하는 헤드리스 구성이 가능하다. 따라서 도구의 종류보다 실제 콘텐츠 제공 경로와 렌더링 주체가 어떻게 나뉘어 있는지 봐야 한다.


분리된 CMS와 빌드 환경은 특정 변화가 생겼을 때 알림 요청을 자동으로 보내는 **웹훅**(webhook)으로 연결한다. 작성자가 CMS에서 글을 발행하거나 상태를 바꾸면 CMS가 빌드 서버에 HTTP POST 요청을 보내 변경 사실을 알린다. 이 신호를 받은 빌드 서버는 CMS API에서 최신 콘텐츠 JSON을 가져와 전체 사이트를 다시 생성하고 배포한다.

## 이미지 URL과 CDN 캐시 갱신


빌드 서버가 만든 HTML과 이미지 파일은 빠른 전송을 위해 보통 CDN에 배포된다. CDN은 한 번 전달한 파일을 임시 사본인 캐시(cache)로 저장해 두고 다음 요청에 빠르게 돌려준다. 이때 이미지 파일명을 원래 이름(`photo.jpg`) 그대로 유지하면 수정 배포 시 문제가 생길 수 있다. 원본 이미지를 새 사진으로 교체해 다시 빌드했더라도, CDN에 이전 버전의 `photo.jpg` 캐시가 남아 있으면 독자의 브라우저에는 여전히 옛 이미지가 보인다.


고정된 파일명에서 이 문제를 해결하려면 배포할 때 CDN에 기존 캐시를 지우는 **퍼지**(purge) 요청을 보내야 한다. 또는 `photo.jpg?v=2`처럼 주소 뒤에 물음표로 값을 덧붙이는 쿼리 문자열을 붙여 버전을 구분할 수도 있다. 다만 쿼리 문자열 방식은 CDN이 캐시 사본을 구분하는 기준인 캐시 키(cache key)에 쿼리 문자열까지 포함하도록 설정된 환경에서만 동작한다. CDN이 쿼리 문자열을 무시하도록 설정되어 있다면 주소를 바꿔도 캐시가 갱신되지 않는다.


빌드 과정에서 파일 내용의 해시값을 파일명에 붙이면 이 문제를 구조적으로 피할 수 있다. 해시가 포함된 파일명은 이미지 내용이 바뀔 때만 최종 URL이 달라진다. 같은 해시 URL이 가리키는 파일 내용은 변하지 않으므로, 접근 정책에 맞는 정적 자원이라면 CDN의 캐시 보관 기간(수명)을 길게 잡아도 안전하다. 이후 이미지를 수정하면 해시값도 함께 바뀌어 HTML에 새 URL이 기록된다. 독자의 브라우저는 이전 캐시와 충돌하지 않고 새 URL로 바뀐 이미지를 요청하게 된다.

## 초안 미리보기와 발행 제어


이미지와 캐시 갱신뿐만 아니라 공개 결과물에 어떤 글을 포함할지도 정적 웹사이트의 빌드 시점에 결정된다. 프런트매터가 `draft: true`로 설정된 글은 일반 빌드 과정에서 제외되므로 `public/` 폴더에 HTML 파일이 생성되지 않는다. 따라서 글을 정식으로 발행하기 전에 화면 구성을 확인하려면 초안을 포함하는 별도의 미리보기 빌드가 필요하다. Hugo에서는 `--buildDrafts` 옵션(플래그)을 붙여 초안까지 포함한 빌드를 실행할 수 있다([Hugo - hugo build](https://gohugo.io/commands/hugo_build/)).


여기서 주의할 점은 초안이 포함된 미리보기 빌드 결과물을 배포하는 경로다. 초안이 포함된 빌드 결과를 인증 없는 공개 CDN에 그대로 올리면 아직 발행하지 않은 초안이라도 외부에서 접근할 수 있는 상태가 된다. 출력 폴더 경로를 나누거나 미리보기 전용 도메인을 따로 연결하는 것은 배포 대상을 구분하는 방법일 뿐, 그 자체로 비공개 상태가 보장되지는 않는다. 작성자만 확인하는 제한된 미리보기 환경을 만들려면 배포 경로 분리와 별개로 인증 같은 접근 제어를 앞에 두어야 한다.


## 결론


정적 웹사이트는 마크다운 문서나 헤드리스 CMS의 데이터를 빌드 시점에 미리 HTML과 이미지 파일로 변환해 CDN에 배포한다. 프런트매터의 `draft` 값과 템플릿의 리소스 함수 호출이 빌드 결과물을 결정하며, 헤드리스 CMS는 웹훅으로 빌드 서버에 변경 사실을 알린다. 빌드 과정에서 이미지 파일명에 내용 해시값을 붙이면 배포 뒤 이전 CDN 캐시와 충돌하지 않고 새 이미지를 바로 보여 줄 수 있다. 또한 초안을 포함한 미리보기 빌드 결과물은 배포 경로 분리와 별개로 인증 같은 접근 제어를 두어야 외부 노출을 막을 수 있다.


이 글에서는 글이 바뀔 때 사이트 전체를 다시 만드는 구성을 기준으로 삼았지만, 글이 많아질수록 전체 빌드에 걸리는 시간도 함께 늘어난다. 다음에는 전체 빌드 시간과 변경된 글만 다시 처리하는 **증분 빌드**(incremental build)를 비교해 볼 만하다. 공통 템플릿을 수정했을 때 영향을 받는 페이지 범위와 재생성 조건은 어떻게 판별하는지도 이어서 다뤄 볼 질문이다.
