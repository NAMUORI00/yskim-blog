프로그램과 실행에 필요한 파일을 한 상자처럼 묶어 돌리는 **컨테이너**(container)는 AI 개발 환경을 만들 때 자주 쓰인다. 이때 컨테이너의 설계도인 **이미지**(image)를 다 만들었거나 설치 검사를 통과했다고 해서 곧바로 모델 작업을 할 수 있는 것은 아니다. 이미지 안의 패키지와 편집기가 고르는 실행 파일, 바깥 컴퓨터(호스트 서버)의 GPU 드라이버, 모델 파일이 서로 다른 곳에 나뉘어 있기 때문이다.


개발용 컨테이너 저장소인 `AI-Container-Suite`(`e3e0c65`)와 이미지 생성 도구 ComfyUI를 배포하는 `comfyui-docker-installer`(`3154d2a`)의 설정 파일과 스크립트를 읽었다. 두 저장소에서 이미지 빌드와 설치, 서비스 실행 단계가 각각 무엇을 준비하고 어디까지 검사하는지 따져 보았다. 이번 글은 저장소를 직접 실행하지 않고 코드와 설정만 검토한 기록이며, 실제 설치 성공 여부와 GPU 성능 측정은 실행 뒤 확인할 항목으로 남겨 두었다.


## 개발 컨테이너의 세 가지 실행 조건


먼저 개발 환경을 담은 `AI-Container-Suite`에서 편집기의 코드가 컨테이너 안의 GPU를 쓰려면 어떤 조건이 필요한지 확인했다. 이 저장소는 VS Code 같은 코드 편집기가 컨테이너 안을 작업 공간으로 연결할 때 읽는 **Dev Container** 설정을 사용한다. [`.devcontainer`](https://github.com/NAMUORI00/AI-Container-Suite/blob/e3e0c65c8a796d1bdb3dceeff6a47a78a374c6e1/.devcontainer/devcontainer.json)[ 설정](https://github.com/NAMUORI00/AI-Container-Suite/blob/e3e0c65c8a796d1bdb3dceeff6a47a78a374c6e1/.devcontainer/devcontainer.json)에는 컨테이너에 GPU를 붙이는 실행 인자와 VS Code 확장 목록이 들어 있다. 같은 파일에 `pytorch_env` 가상환경의 Python 실행 경로와 원격 사용자 계정도 함께 적혀 있다. 이미지를 만드는 `Dockerfile`만 봐서는 알 수 없는 편집기 쪽 실행 조건을 여기서 따로 지정한다.


컨테이너 안에 설치할 패키지는 [CUDA 12.1 환경 파일](https://github.com/NAMUORI00/AI-Container-Suite/blob/e3e0c65c8a796d1bdb3dceeff6a47a78a374c6e1/.devcontainer/cuda-12.1/environment.yml)에 모여 있다. 이 파일은 Python과 PyTorch, NVIDIA GPU 계산 도구인 **CUDA** 관련 라이브러리, 주피터 노트북 도구를 하나로 묶어 정의한다. 자주 쓰는 도구를 한 파일에 모아 두면 새 프로젝트를 시작할 때마다 패키지를 일일이 고르는 수고를 덜 수 있다. 다만 일부 패키지 버전이 고정값 대신 범위로 적혀 있고, 이미지를 빌드할 때 최신 설치 파일을 내려받는 구간도 있다. 같은 설정 파일로 다시 빌드하더라도 시점에 따라 설치되는 세부 버전이 달라질 수 있다. 환경을 똑같이 재현하려면 설정 파일만으로는 부족하고, 빌드 시점에 실제로 설치된 패키지 목록을 함께 남겨야 한다.


이미지 안에 CUDA 라이브러리를 설치했다고 해서 GPU 계산이 바로 되는 것도 아니다. 컨테이너 안의 CUDA 라이브러리는 계산 명령을 전달할 뿐, 실제 하드웨어를 제어하는 호스트 서버의 GPU 드라이버를 대신하지 않는다. [NVIDIA Container Toolkit 문서](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html)에서도 호스트 드라이버 설치, 컨테이너 툴킷 설치, 컨테이너 엔진 설정을 별도 단계로 구분한다. 결국 Python 코드가 GPU를 쓰려면 그림 1처럼 이미지 안의 라이브러리, 편집기가 고른 Python 환경, 호스트 GPU 연결이 실행 시점에 모두 맞아야 한다.


![편집기 설정, 개발 이미지, 호스트 GPU 연결의 세 경로가 선택한 Python 환경에서 만나 텐서 연산과 실행 결과 기록으로 이어지는 구조도](/images/notion/tech-10-01/image-1.png)


그림 1. 이미지의 라이브러리, 편집기의 Python 선택, 호스트 GPU 연결이 실행 시점에 만나는 구조(출처: AI-Container-Suite 설정과 NVIDIA 공식 문서를 바탕으로 직접 구성, 해당 환경의 실행 성공 기록을 대신하지 않는 개념도).


## GPU 환경 점검 코드의 한계


앞선 세 가지 조건을 맞춰 컨테이너와 호스트 GPU를 연결했다면, 다음으로 실제 코드가 장치를 인식하는지 확인해야 한다. 저장소에 들어 있는 [GPU 환경 점검 코드](https://github.com/NAMUORI00/AI-Container-Suite/blob/e3e0c65c8a796d1bdb3dceeff6a47a78a374c6e1/workspace/src/main.py)는 먼저 PyTorch의 CUDA 사용 가능 여부와 장치 정보를 출력한다. 이어서 다차원 배열인 텐서 기본 연산, **혼합 정밀도**(mixed precision) 연산, 추론 최적화 엔진인 TensorRT 접근을 차례로 검사한다.


이 점검 코드가 출력하는 결과를 그대로 읽을 때는 주의할 점이 두 가지 있다. 첫째는 32비트 부동소수점(FP32)과 16비트 부동소수점(FP16)을 섞어 계산 속도를 높이고 메모리를 아끼는 혼합 정밀도 구간의 속도 비교다. 점검 코드는 두 정밀도의 실행 시간을 재서 비율을 출력하지만, 정작 두 경로가 수행하는 작업은 서로 다르다. 그림 2에서 보듯 FP32 경로는 입력으로 결과를 내는 순전파와 오차를 거꾸로 전달하는 역전파만 반복한다. 반면 FP16 경로는 반복문 안에서 매번 `Adam` 옵티마이저(optimizer) 객체를 새로 만들고 가중치를 갱신하는 단계까지 수행한다. 두 경로의 작업량과 상태가 통제되어 있지 않으므로, 여기서 출력되는 속도 비율을 정밀도 간 성능 차이로 삼기는 어렵다. 성능을 제대로 비교하려면 모델과 입력뿐 아니라 가중치 갱신 단계와 초기 지연 시간을 빼기 위한 준비 실행 조건까지 똑같이 맞춰야 한다.


![FP32 반복 구간은 순전파와 역전파만 수행하는 반면 FP16 반복 구간은 Adam 객체 생성과 가중치 갱신까지 수행하여 단순 속도 비교가 불가능함을 보여 주는 비교도](/images/notion/tech-10-01/image-2.png)


그림 2. 점검 코드의 혼합 정밀도 비교 구간에서 FP32 경로와 FP16 경로에 포함된 연산 단계 차이.


둘째는 시스템에서 GPU를 찾지 못했을 때 넘어가는 예외 처리 방식이다. 이 스크립트는 시스템에 GPU가 없으면 일부 연산 검사를 건너뛰고 다음 단계로 넘어간다. 문제는 GPU 연산 검사를 생략하더라도 스크립트 맨 마지막에는 `"모든 테스트가 완료"`라는 문구가 똑같이 출력된다는 점이다. 마지막 줄만 보고 환경 구성이 끝났다고 판단하면 GPU 미인식이나 검사 생략을 놓치게 된다. 따라서 앞선 개별 검사의 출력 결과를 함께 읽어야 완료와 생략, 실패를 구별할 수 있다.


## 서비스 컨테이너의 네트워크와 데이터 분리


앞에서 본 개발용 컨테이너가 편집기 연결에 초점을 맞췄다면, 서비스용 컨테이너는 외부 접속과 데이터 보존을 함께 다룬다. 이미지 생성 도구인 ComfyUI를 배포하는 `comfyui-docker-installer`는 두 개의 컨테이너를 조합해 이 구조를 만든다. 이 저장소의 [Compose 파일](https://github.com/NAMUORI00/comfyui-docker-installer/blob/3154d2afc8c7fd02fc198df93310c8f0a9f9e5fb/compose.yaml)은 웹 서버인 Caddy와 애플리케이션인 ComfyUI를 별도 컨테이너 서비스로 분리한다.


그림 3처럼 호스트 서버 바깥으로 연결 통로(포트)를 여는 쪽은 Caddy뿐이며, ComfyUI는 도커 내부 네트워크로만 연결된다. 외부 접속자를 확인하는 사용자 인증 관문도 Caddy 쪽에 설정되어 있다. 다만 통신 구간을 암호화하는 TLS 설정과 외부 접속 주소 구성은 이 파일만으로는 확인되지 않아 별도 점검 대상으로 남아 있다. 한편 모델 가중치 파일, 입력과 출력 파일, 사용자 설정, 확장 기능인 커스텀 노드의 Python 패키지는 모두 컨테이너 밖의 호스트 데이터 폴더에 둔다. 이렇게 작업 파일을 컨테이너 밖에 분리해 두면 나중에 이미지를 새로 빌드해 교체하더라도 기존 데이터는 그대로 보존된다.


![외부 접속이 내부 네트워크의 Caddy 인증 관문을 거쳐 ComfyUI 컨테이너로 연결되고, 모델 파일과 입출력 데이터 등은 컨테이너 밖의 호스트 데이터 폴더에 분리 저장되는 구조도](/images/notion/tech-10-01/image-3.png)


그림 3. Caddy를 통한 외부 접속 분리와 컨테이너 외부 호스트 폴더를 연결한 데이터 보존 구조.


이미지를 만드는 [Dockerfile](https://github.com/NAMUORI00/comfyui-docker-installer/blob/3154d2afc8c7fd02fc198df93310c8f0a9f9e5fb/Dockerfile)은 의존성 설치 조건과 ComfyUI의 실제 빌드 커밋을 파일로 남긴다. 먼저 PyTorch 계열 패키지의 현재 버전을 **제약 파일**(constraints file)로 만들어, 나머지 의존성 패키지를 설치할 때 버전이 바뀌지 않게 묶는다. 또한 ComfyUI 소스 코드를 가져올 때 기준 브랜치 변수인 `COMFYUI_REF`의 기본값은 `master`로 되어 있다. 이 때문에 같은 설정으로 빌드하더라도 시점에 따라 가져오는 코드 기록(커밋)이 달라진다. Dockerfile은 빌드 시점에 체크아웃된 커밋 해시를 파일에 적어 두어, 시점별 빌드 차이를 추적할 수 있게 한다.


## 설치 검사 범위와 실제 작업 확인


컨테이너 구조와 빌드 규칙을 정의한 뒤에는 스크립트로 설치와 환경 검사를 차례로 실행한다. 전체 과정을 묶은 [설치 스크립트](https://github.com/NAMUORI00/comfyui-docker-installer/blob/3154d2afc8c7fd02fc198df93310c8f0a9f9e5fb/scripts/install.sh)는 데이터 폴더와 인증 설정을 준비한 뒤 이미지 빌드와 환경 검증을 거치고, 선택적으로 서비스를 시작한다. 여기서 호출되는 [설치 환경 검사 스크립트](https://github.com/NAMUORI00/comfyui-docker-installer/blob/3154d2afc8c7fd02fc198df93310c8f0a9f9e5fb/scripts/verify.sh)는 Compose 파일의 구문 오류, 호스트 GPU 인식, 컨테이너 내부의 CUDA 사용 가능 여부를 확인한다. 이어서 패키지 일관성, 출력 폴더의 쓰기 권한, Python 사용자 설치 경로를 검사하고, 실행 중인 서비스 정보가 있으면 포트 노출 상태도 함께 확인한다.


하지만 이 검사 스크립트가 통과했다고 해서 서비스가 실제 이미지 생성 작업까지 마칠 수 있다고 볼 수는 없다. 스크립트 안에는 특정 모델을 불러와 이미지를 한 장 생성해 보는 단계가 없기 때문이다. 게다가 설치 흐름에서 환경 검증 뒤에 서비스를 시작하는 단계는 선택 사항이다. 그림 4처럼 빌드 직후의 환경 검증과 서비스 시작 후 로그인 화면 표시, 모델 기반 이미지 생성 확인은 서로 다른 단계에 놓여 있다.


![폴더 준비부터 이미지 빌드, 환경 검증 스크립트, 선택적 서비스 시작까지의 설치 검증 범위와 점선 너머의 실제 워크플로 요청 및 생성 결과 파일 확인 범위를 구분한 순서도](/images/notion/tech-10-01/image-4.png)


그림 4. 설치 스크립트의 빌드, 검증, 시작 단계와 추가로 확인할 실제 작업 결과의 구분(출처: 설치 및 시작 스크립트와 설치 환경 검사 스크립트를 바탕으로 직접 구성, 점선 오른쪽은 설치 검증에 포함되지 않은 확인 단계).


저장소 문서에 남아 있는 [2026-05-27 사전 점검 기록](https://github.com/NAMUORI00/comfyui-docker-installer/blob/3154d2afc8c7fd02fc198df93310c8f0a9f9e5fb/docs/a6000-2-preflight.md) 역시 이러한 단계 구분을 보여 준다. 이 문서는 호스트 상태를 읽기 전용으로 확인한 기록이며, 설치나 빌드, 서비스 시작을 수행하지 않았다고 범위가 명시되어 있다. 당시 호스트 서버의 상태를 적어 둔 스냅샷일 뿐, 현재 서버의 운영 상태나 배포 완료와는 별개다.


## 결론


두 저장소의 설정과 스크립트를 따라가 보면, 컨테이너 이미지를 빌드하거나 점검 스크립트가 끝났다는 출력만으로는 AI 작업 환경이 다 준비되었다고 볼 수 없다. 개발 환경을 공유하거나 다시 만들 때는 파일이 호스트와 이미지 중 어디에 남는지와 각 점검 도구의 준비 완료 기준을 함께 설명해야 한다.


이번 검토에서는 두 저장소의 코드와 설정을 읽어 빌드와 환경 점검이 확인하는 범위를 구분했다. 실제 설치 성공 여부와 GPU 성능 측정, TLS 설정 확인, 컨테이너 실행 뒤 모델을 불러와 작업 요청까지 마치는 과정은 실행 검증 항목으로 남아 있다. 다음으로는 별도 ComfyUI 환경 저장소의 커스텀 노드와 모델 파일 배치 방식을 보고, 이미지 재빌드 뒤 이전 작업을 재현할 때 필요한 추가 정보를 정리할 계획이다.
