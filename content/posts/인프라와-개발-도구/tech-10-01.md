AI 개발 환경을 마련하며 컨테이너 이미지와 서비스 설치 절차를 정리했다. 패키지, 모델 파일, 호스트 GPU 설정이 서로 다른 위치에 놓여 있어 빌드, 설치, 서비스 실행을 구분하는 데 초점을 맞췄다.


## 구현과 확인 과정


AI 개발 환경과 서비스 설치 도구를 함께 정리했다. 개발할 때 쓸 Python과 CUDA를 이미지에 넣는 작업부터, GPU를 연결하고 데이터를 보존하며 서비스를 시작하는 작업까지 이어서 보려 했다.


설정 파일을 읽다 보니 설치 명령이 끝난 것과 실제 모델 작업이 가능한 것은 다른 상태였다. `AI-Container-Suite`의 `e3e0c65`와 `comfyui-docker-installer`의 `3154d2a`를 기준으로 각 단계에서 무엇을 준비하고 확인하는지 나누어 봤다. 이번에는 설정과 코드를 검토했다. 설치 성공과 GPU 성능은 실행 검증 항목으로 남아 있다.


## 편집기와 Python 개발 환경


AI-Container-Suite의 [.devcontainer 설정](https://github.com/NAMUORI00/AI-Container-Suite/blob/e3e0c65c8a796d1bdb3dceeff6a47a78a374c6e1/.devcontainer/devcontainer.json)은 GPU 실행 인자, VS Code 확장, pytorch_env의 Python 경로와 원격 사용자를 지정한다. Dockerfile에는 들어 있지 않은 편집기 측 조건(확장 목록, Python 인터프리터 경로, 원격 사용자)이 이 파일에 함께 선언되어 있었다.


[CUDA 12.1 환경 파일](https://github.com/NAMUORI00/AI-Container-Suite/blob/e3e0c65c8a796d1bdb3dceeff6a47a78a374c6e1/.devcontainer/cuda-12.1/environment.yml)은 Python, PyTorch, CUDA 계열과 노트북 도구를 묶는다.


이 방식은 프로젝트마다 필요한 도구를 반복해서 고르는 부담을 줄인다. 다만 범위로 지정한 패키지 버전과 최신 설치 파일을 사용하는 부분이 있어서, 같은 설정으로 다시 빌드해도 세부 결과가 달라질 여지가 있다. 설치 명세만으로는 실제 설치된 버전 조합을 특정할 수 없고, 빌드 시점의 설치 목록이 함께 있어야 재현 조건이 갖춰진다.


개발용 이미지 안의 CUDA 라이브러리는 호스트 GPU 드라이버 자체와 역할이 다르다. [NVIDIA Container Toolkit 문서](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html)도 호스트 드라이버, 툴킷 설치, 컨테이너 엔진 설정을 나누어 설명한다.


컨테이너에 CUDA 관련 파일이 포함되어 있는 것과 실행 중인 Python 프로세스가 GPU에 접근할 수 있는 것은 별개 조건이다.

## 테스트 프로그램의 검사 항목


[GPU 환경 점검 코드](https://github.com/NAMUORI00/AI-Container-Suite/blob/e3e0c65c8a796d1bdb3dceeff6a47a78a374c6e1/workspace/src/main.py)는 CUDA 가용성과 장치 정보를 출력하고, 텐서 연산, 혼합 정밀도, TensorRT 접근을 점검하도록 작성되어 있다. 다만 출력되는 속도 비율을 곧바로 정밀도별 성능 비교 수치로 쓰기에는 측정 조건이 통제되어 있지 않았다.


혼합 정밀도 비교에서 FP32 경로는 순전파와 역전파를 반복하고, FP16 경로는 optimizer 갱신까지 수행하며 반복 안에서 Adam 객체를 만든다. 코드상 작업량과 상태가 달라 이 출력만으로 정밀도 간 속도 차이를 해석하기는 어렵다. 비교 실험에는 동일한 모델, 입력, 갱신 단계와 준비 실행 조건이 더 필요하다.


GPU가 없으면 일부 검사를 건너뛰고 다음 단계로 넘어간다. 마지막의 “모든 테스트가 완료” 문구는 GPU 연산 검사 수행 여부와 무관하게 출력된다. 마지막 문구만으로는 완료, 생략, 실패한 검사를 구별할 수 없어 개별 검사 결과를 함께 읽었다.


## 데이터 저장과 접속 경로 구성


comfyui-docker-installer의 [Compose 파일](https://github.com/NAMUORI00/comfyui-docker-installer/blob/3154d2afc8c7fd02fc198df93310c8f0a9f9e5fb/compose.yaml)은 Caddy와 ComfyUI를 별도 서비스로 둔다.


호스트에 포트를 내는 쪽은 Caddy이고 ComfyUI는 내부 네트워크에서 연결한다. [설치 스크립트](https://github.com/NAMUORI00/comfyui-docker-installer/blob/3154d2afc8c7fd02fc198df93310c8f0a9f9e5fb/scripts/install.sh)는 데이터 폴더와 인증 설정을 준비한 뒤 빌드, 검증, 선택적 시작으로 이어진다.


모델, 입력, 출력, 사용자 설정과 커스텀 노드의 Python 패키지를 컨테이너 밖에 두는 구조였다. 이미지를 교체해도 작업 파일이 보존되는 배치다. 인증 관문은 Caddy 쪽에 설정되어 있었고, 전송 암호화(TLS)와 접속 주소 구성은 이 파일만으로는 확인되지 않아 별도 점검 대상으로 남아 있다.


[Dockerfile](https://github.com/NAMUORI00/comfyui-docker-installer/blob/3154d2afc8c7fd02fc198df93310c8f0a9f9e5fb/Dockerfile)은 PyTorch 계열 패키지의 현재 버전을 제약 파일로 만든 뒤 의존성을 설치한다.


ComfyUI의 실제 빌드 커밋도 파일로 남긴다. COMFYUI_REF의 기본값이 master이므로 같은 설정으로 빌드해도 시점에 따라 다른 커밋이 체크아웃된다. 빌드된 커밋 해시가 파일에 기록되는 부분이 이 차이를 추적할 수 있는 지점이었다.

## 설치 검증과 실제 작업 확인 범위


[설치 환경 검사 스크립트](https://github.com/NAMUORI00/comfyui-docker-installer/blob/3154d2afc8c7fd02fc198df93310c8f0a9f9e5fb/scripts/verify.sh)는 Compose 구문, 호스트 GPU, 컨테이너의 CUDA 가용성, 패키지 일관성, 출력 폴더 쓰기 권한과 Python 사용자 설치 경로를 확인한다. 실행 중인 서비스 정보가 있으면 포트 노출도 검사한다.


이 스크립트에는 특정 모델을 불러 이미지 한 장을 생성하는 단계가 포함되어 있지 않다. 설치 흐름에서도 검증 이후 서비스 시작은 선택 사항이다. 빌드 직후의 검증이 확인하는 범위와 로그인 화면 표시, 모델 기반 이미지 생성은 서로 다른 단계에 있다.


저장소의 [2026-05-27 사전 점검 기록](https://github.com/NAMUORI00/comfyui-docker-installer/blob/3154d2afc8c7fd02fc198df93310c8f0a9f9e5fb/docs/a6000-2-preflight.md)도 읽기 전용 점검이며, 문서 자체가 설치, 빌드, 시작을 수행하지 않았다고 범위를 명시한다. 이 기록은 당시 호스트 상태의 스냅샷이며, 현재 서버의 운영 상태나 배포 완료와는 별개다.


이번 글에서는 두 저장소를 실행하지 않고, 코드를 읽어 각 구성이 무엇을 준비하고 무엇을 검증하는지 확인했다. 이어서 살펴볼 항목은 별도 ComfyUI 환경 저장소의 커스텀 노드와 모델 파일 배치다. 이미지 재빌드와 작업 재현 사이에 어떤 정보가 추가로 필요한지도 함께 정리할 주제로 남아 있다.


## 작업을 정리하며


개발 환경을 공유하려면 파일이 어디에 남는지와 준비 완료 기준을 함께 설명해야 한다. 컨테이너 실행 뒤 모델 로딩과 실제 요청까지 확인하는 순서가 유용하다. 환경을 다시 만들 때 필요한 정보를 이 단계에 맞춰 남기려 한다.
