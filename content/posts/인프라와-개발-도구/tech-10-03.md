MediaMTX는 방송 프로그램이 보낸 실시간 영상을 받아 시청자에게 전달하는 중계 서버다. 이 서버를 설치하는 `NAMUORI00/mediamtx-installer` 저장소를 읽으며 설치 완료 검사가 다루는 범위를 정리했다. 이 설치 스크립트는 설정 파일을 만들고 프로그램을 독립된 환경에서 돌리는 Docker 컨테이너를 띄운 뒤 프로세스가 살아 있는지만 확인하고 끝난다. 하지만 컨테이너가 정상으로 실행 중이라고 해서 방송 프로그램이 보낸 영상이 시청자 화면에서 곧바로 나오는 것은 아니다. 영상이 서버에 도착했는지, 시청 경로가 열렸는지, 재생 프로그램이 영상 압축 방식을 풀 수 있는지는 컨테이너 실행 여부와 따로 확인해야 한다.


이 글에서는 저장소의 `048417e` 커밋에 있는 [README](https://github.com/NAMUORI00/mediamtx-installer/blob/048417e4edae5b8a3ae0933033279d553f228501/README.md)와 [영상 중계 서버 설치 스크립트](https://github.com/NAMUORI00/mediamtx-installer/blob/048417e4edae5b8a3ae0933033279d553f228501/install-mediamtx.sh)를 읽고 분석했다. 설치기가 자동으로 준비하는 범위와 실제 재생을 확인할 때 추가로 점검할 구간을 나누어 짚어 본다. 이번 작업에서는 스크립트 코드와 설정 구성을 읽고 검토했으며, 설치기를 실제로 실행하거나 방화벽을 바꾸지는 않았다.


## 송출과 시청 프로토콜 연결 구조


설치기가 준비하는 범위와 추가 점검 구간을 구분하려면 먼저 영상이 어떤 통신 규칙, 즉 프로토콜을 거쳐 시청자에게 전달되는지 보아야 한다. 저장소 안내 문서에서는 방송 프로그램인 OBS가 서버로 영상을 올릴 때 주로 쓰는 **RTMP**(Real-Time Messaging Protocol)로 영상을 송출한다. MediaMTX는 받은 영상을 VLC 미디어 플레이어에는 **RTSP**(Real-Time Streaming Protocol)로 전달한다. RTSP는 미디어 플레이어나 관제 화면에서 실시간 스트림을 받아 볼 때 많이 쓰는 프로토콜이다. 웹 브라우저에는 **HLS**(HTTP Live Streaming)로 영상을 보낸다. HLS는 영상을 작은 파일 조각과 재생 목록으로 나누어 일반 웹(HTTP)으로 보내므로 별도 플러그인 없이 브라우저에서 바로 재생하기 좋다.


이처럼 MediaMTX가 중간에서 프로토콜을 바꾸어 내보내므로 영상을 보내는 쪽과 보는 쪽이 같은 방식을 쓸 필요는 없다. MediaMTX 공식 문서에서도 기능을 [송출](https://mediamtx.org/docs/features/publish)과 [읽기](https://mediamtx.org/docs/features/read)로 나누어 지원하는 프로토콜을 안내한다.


설치 스크립트가 만드는 설정 파일에는 RTMP, RTSP, HLS와 저지연 전송 프로토콜인 SRT(Secure Reliable Transport)가 켜져 있다. 반면에 브라우저 간 실시간 통신 규격인 WebRTC(Web Real-Time Communication)는 꺼져 있다. RTSP도 데이터 전달을 확인하는 TCP 전송만 허용하도록 제한해 MediaMTX의 전체 기능 가운데 일부만 열어 두었다.


![OBS의 RTMP 송출이 송출 인증을 거쳐 MediaMTX 스트림 경로로 전달되고, RTSP/TCP를 통해 VLC 재생으로, HLS 조각과 목록을 통해 브라우저 재생으로 나뉘는 흐름도](/images/notion/tech-10-03/image-1.png)


그림 1. README와 영상 중계 서버 설치 스크립트를 바탕으로 직접 구성한 송출, 중계, 시청 프로토콜 연결 구조.


여기서 전송 프로토콜을 바꾸어 주는 일과 영상이나 소리를 압축하는 방식인 **코덱**(codec)을 다시 변환하는 인코딩 작업은 별개다. 그림 1처럼 MediaMTX가 RTMP로 들어온 스트림을 HLS나 RTSP로 포장해 내보내더라도, 그 안에 담긴 영상과 음성 코덱까지 자동으로 바꾸어 주지는 않는다. 설치 스크립트는 영상 변환 도구인 FFmpeg가 포함된 `latest-ffmpeg` 컨테이너 이미지를 내려받는다. 하지만 스크립트가 만드는 설정 파일에는 FFmpeg를 호출해 영상을 다른 코덱으로 변환하는 실행 명령이 들어 있지 않다. 따라서 송출자가 보낸 코덱을 브라우저가 지원하지 않는다면 HLS 경로가 열려 있어도 모든 브라우저에서 영상이 재생된다고 볼 수 없다.


## 실행 환경과 접근 권한 구성


앞서 본 프로토콜 경로를 서버에 열기 위해 `install-mediamtx.sh` 스크립트는 실행 환경과 접근 권한을 자동으로 구성한다. 이 스크립트는 먼저 운영체제 종류와 실행 권한을 확인하고, 시스템에 Docker가 없으면 새로 설치한다. 그다음에 사용할 포트 번호와 송출 키를 입력받아 영상 중계 설정 파일, Docker Compose 파일, 접속 정보 파일을 차례대로 만든다. 파일 생성이 끝나면 입력받은 포트를 여는 방화벽 규칙을 적용하고 컨테이너를 시작한다.


![포트와 송출 키 입력을 받은 install-mediamtx.sh 스크립트가 영상 중계 설정, Compose 파일, 접속 정보 파일을 생성하고 호스트 네트워크 실행 환경에서 송출, 시청, 관리 API 권한을 분리하는 구조도](/images/notion/tech-10-03/image-2.png)


그림 2. 설치 스크립트가 입력값을 받아 설정 파일을 생성하고 호스트 네트워크 기반 컨테이너와 접근 권한을 구성하는 흐름.


그림 2와 같이 스크립트가 만드는 Compose 파일은 컨테이너 네트워크를 격리하지 않고 호스트 서버의 네트워크를 그대로 쓰는 `host` 네트워크 모드를 사용한다. 컨테이너 내부 포트와 호스트 포트를 하나씩 연결해 주는 포트 매핑 표를 거치지 않으므로, 설정 파일에 지정한 주소와 포트가 호스트 서버에서 곧바로 열린다.


접근 권한은 송출과 시청, 관리 경로마다 다르게 나뉘어 있다. 영상을 서버로 보내는 송출에는 입력받은 송출 키가 걸린 `publisher` 계정을 쓰지만, 스트림을 읽고 재생하는 경로는 인증 없이 익명으로 허용한다. 서버 상태를 조회하거나 바꾸는 관리 API에만 접속 가능한 주소 대역 조건이 걸려 있다. 따라서 송출 키로 아무나 방송을 올리지 못하게 막더라도, 시청 주소를 아는 사람은 누구나 인증 없이 영상을 볼 수 있다.


설정 파일 생성부터 방화벽 적용과 컨테이너 시작까지 스크립트 하나로 묶어 두면 환경을 반복해서 꾸릴 때 수동 작업을 줄일 수 있다. 다만 호스트 네트워크를 직접 쓰고 방화벽 설정을 바꾸므로, 서버의 기존 서비스나 포트 사용 현황, 네트워크 보안 정책에 미칠 영향을 실행 전에 함께 따져 봐야 한다.


## 지연 시간 설정과 메모리 상한 해석


스크립트가 만든 설정 파일에는 실행 환경뿐만 아니라 영상 지연 시간과 메모리 사용량을 조절하는 수치도 적혀 있다. 그중 HLS 설정에는 저지연 모드(`lowLatency`), 1초 세그먼트, 200ms 부분 조각(part), 세그먼트 보관 개수 7개가 들어 있다. 숫자만 보면 지연이 아주 짧을 것 같지만, 이 설정값을 송출부터 시청자 화면까지 걸리는 전체 지연 시간으로 곧바로 읽을 수는 없다.


[MediaMTX 설정 문서](https://mediamtx.org/docs/references/configuration-file)는 세그먼트와 부분 조각의 길이를 서버가 스트림을 자르는 최소 길이로 설명한다. 실제 조각이 만들어지는 간격은 화면 전체 정보를 담고 있는 **키프레임**(keyframe)이 들어오는 주기나 오디오 샘플 간격에 영향을 받는다. 여기에 시청자 쪽 플레이어가 재생 끊김을 막으려고 데이터를 모아 두는 버퍼를 얼마나 채운 뒤에 화면을 띄우는지도 재생 시점을 좌우한다. HLS 조각을 짧게 잡는 설정은 전체 지연을 결정하는 여러 조건 가운데 하나일 뿐이다.


예를 들어 송출 인코딩에 100ms, 네트워크 전송과 서버 중계에 150ms, 플레이어의 재생 버퍼에 600ms가 걸렸다면 전체 지연은 이를 모두 더한 850ms가 된다. 이처럼 전체 지연 시간은 각 단계의 처리 시간과 전송 시간이 합쳐진 값이므로 구간을 나누어 측정해야 한다. 위 숫자들은 실제 측정값이 아니라 지연을 단계별로 나누어 보기 위한 계산 예다.


![송출 인코딩 100ms, 전송과 중계 150ms, 재생 버퍼 600ms가 더해져 전체 지연 합계 850ms가 되는 과정과 가운데 전송과 중계 구간에 HLS 최소 길이 설정이 적용됨을 나타내는 도식](/images/notion/tech-10-03/image-3.png)


그림 3. 송출 인코딩, 전송과 중계, 재생 버퍼를 합산한 전체 지연 시간 계산 예와 HLS 설정이 적용되는 구간.


그림 3에서 보듯이 MediaMTX의 HLS 조각 설정은 가운데에 있는 전송과 중계 구간에만 관여한다. 만약 플레이어 재생 버퍼에서 600ms가 걸리고 있다면 중계 서버의 설정만 바꾸어서는 체감 지연을 크게 줄이기 어렵다.


Compose 파일에 적힌 메모리 설정인 `512M`도 같은 기준으로 구분해 읽어야 한다. 이 값은 컨테이너가 사용할 수 있는 메모리 상한일 뿐, 그 범위 안에서 스트림이 언제나 안정적으로 유지된다고 보장하지는 않는다. 입력 영상의 해상도와 초당 데이터 전송량인 비트레이트, 동시 시청자 수에 따라 실제로 메모리를 얼마나 쓰는지 측정한 기록이 있어야 안정적인 운영 범위를 판단할 수 있다.


## 설치기의 검사 범위와 재생 점검 절차


설정값만으로 실제 성능을 단정할 수 없듯이, 설치 스크립트의 완료 확인만으로 영상 재생까지 준비되었다고 볼 수도 없다. 스크립트의 `start_container` 함수는 컨테이너를 시작한 뒤 3초를 기다렸다가 `docker ps` 출력에 `mediamtx`가 있는지만 확인한다. 컨테이너 프로세스가 떠 있는지만 검사하므로 송출자가 정상으로 연결되는지, 스트림 안에 영상과 음성 트랙이 들어 있는지는 알 수 없다. HLS 재생 목록이 갱신되는지와 플레이어가 코덱을 해석해 화면을 그리는지도 이 검사에 포함되지 않는다.


![컨테이너 실행 중 상태에서 송출 유무, 스트림 경로 일치 여부, 플레이어 해석 가능 여부를 차례대로 확인해 화면, 소리, 지연 확인에 이르는 점검 순서도](/images/notion/tech-10-03/image-4.png)


그림 4. 설치기의 확인 범위와 MediaMTX의 송출 및 읽기 문서를 바탕으로 직접 구성한 단계별 재생 점검 흐름.


따라서 컨테이너가 뜬 뒤에는 그림 4와 같은 순서로 재생 점검을 따로 수행해야 한다. 먼저 서버로 송출 스트림이 들어오는지 확인하고, 들어오지 않는다면 서버 주소와 송출 인증 정보, 방송 프로그램의 송출 상태를 점검한다. 송출이 들어오는데도 재생이 안 된다면 송출 경로와 시청 경로의 이름이 일치하는지 대조한다. 경로까지 맞는데 화면이 나오지 않는다면 플레이어가 해당 코덱을 지원하지 않거나 버퍼 설정에 문제가 있는지 확인해야 한다.


나중에 스크립트를 다시 실행했을 때 같은 실행 환경이 재현되는지도 점검할 부분이다. 설치 스크립트는 컨테이너 이미지 버전을 고정하지 않고 `latest-ffmpeg` 태그를 사용한다. 이 상태에서는 나중에 스크립트를 다시 실행할 때 실제로 내려받는 MediaMTX 버전이 달라질 수 있다. 예를 들어 저장소 스크립트에 적힌 스트림 경로 설정 방식은 현재 공식 문서의 설정 예시와 표기가 달랐다. 실행되는 버전이 해당 설정 문법을 어떻게 해석하는지 일관되게 확인하려면, 이미지 고유 식별값과 생성된 설정 파일을 함께 보관하는 편이 낫다.


## 결론


이번에 저장소 코드를 읽으며 확인한 범위는 MediaMTX 스트리밍 엔진 자체의 성능이 아니라 설치, 설정 생성, 컨테이너 시작 절차를 묶은 자동화 구성이었다. 설치 스크립트는 프로토콜 경로와 호스트 네트워크, 접근 권한을 자동으로 설정하고 컨테이너 프로세스가 살아 있는지 확인한다. 하지만 송출 연결 여부와 코덱 호환성, 실제 지연 시간은 컨테이너 실행 여부만으로 알 수 없으므로 단계별로 따로 점검해야 한다. 설정 파일에서 저지연 HLS 옵션과 512MB 메모리 상한도 확인했지만, 실제 스트림을 흘려보내며 측정한 자료는 없었으므로 설정값을 성능 수치로 바꾸어 적지는 않았다.


체감 지연과 재생 안정성은 방송 프로그램의 송출부터 플레이어 디코딩까지 여러 단계가 합쳐진 결과다. 다음 확인 단계로는 컨테이너 이미지 버전과 입력 조건을 고정한 채 짧은 시험 영상을 송출하고, 같은 스트림 경로를 RTSP와 HLS로 각각 읽어 보는 실행 검증을 남겨 두었다. 화면과 소리의 정상 재생 여부, 구간별 지연 시간, 연결이 끊겼을 때의 복구 동작은 그때 각각 측정해 기록하려 한다. 이어지는 원격 운영 도구 글에서는 접속 경로와 서비스 동작을 나누어 다룬다.
