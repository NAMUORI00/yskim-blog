MediaMTX 실행 환경에서는 설치 설정과 스트리밍 경로를 정리했다. 송출, 전송, 재생에 걸리는 시간을 나누고 메모리 제한과 버전별 설정 해석을 함께 확인하는 흐름을 구성했다.


## 구현과 확인 과정


mediamtx-installer를 읽으며 설치 완료 검사가 다루는 범위를 정리했다. 서버 실행 이후에도 입력 스트림의 도착, 시청 경로의 연결, 코덱 재생은 각각 확인할 단계로 남는다. 설치 스크립트와 설정 파일을 이 흐름에 맞춰 살펴봤다.


확인한 소스는 NAMUORI00/mediamtx-installer의 048417e 커밋이다. [README](https://github.com/NAMUORI00/mediamtx-installer/blob/048417e4edae5b8a3ae0933033279d553f228501/README.md)는 OBS의 RTMP 송출을 MediaMTX로 받아 VLC의 RTSP 또는 브라우저의 HLS로 시청하는 구성을 제시하고 있었다. 스트림, 코덱, 전송 프로토콜의 기초를 바탕으로 각 설정이 연결되는 지점을 정리했다.


## 송출과 시청 프로토콜 구성


OBS가 보내는 프로토콜과 시청자가 사용하는 프로토콜은 같지 않아도 된다. MediaMTX는 송출 쪽에서 스트림을 받아 읽는 쪽에 제공하는 중간 서버다.


현재 공식 문서도 [송출](https://mediamtx.org/docs/features/publish)과 [읽기](https://mediamtx.org/docs/features/read)를 나누어 지원 프로토콜을 설명한다.


이 프로젝트의 설정은 RTMP, RTSP, HLS, SRT를 켜고 WebRTC는 끈 상태였다. RTSP는 TCP 전송으로 제한되어 있었다. MediaMTX가 지원하는 전체 기능 가운데 일부만 활성화된 구성이다.

프로토콜을 바꾸어 제공하는 것과 영상 코덱을 다시 인코딩하는 것은 별개다. 설정에 FFmpeg가 들어 있는 이미지 이름이 보이지만, 이 설치기가 만드는 파일에는 FFmpeg로 영상을 변환하는 실행 명령이 없었다. 따라서 어떤 코덱을 입력받아도 모든 브라우저에서 재생 가능하다고 볼 근거는 부족하다.


## 설치 스크립트가 준비하는 항목


[영상 중계 서버 설치 스크립트](https://github.com/NAMUORI00/mediamtx-installer/blob/048417e4edae5b8a3ae0933033279d553f228501/install-mediamtx.sh)는 운영체제와 실행 권한을 먼저 확인하고, Docker가 없으면 설치하는 흐름이었다.


이어서 포트, 송출 키를 입력받아 영상 중계 설정 파일, Compose 파일, 접속 정보 파일을 생성한 뒤 방화벽 설정과 컨테이너 시작까지 처리한다.


Compose는 host 네트워크를 사용한다. 컨테이너 포트 매핑 표 대신 호스트에서 실제로 열리는 주소와 포트가 중요한 구성이다. 인증은 송출 권한과 시청 권한이 분리되어 있었다. 송출에는 publisher 계정을 사용하고 읽기, 재생은 익명 허용이다. 관리 API에는 주소 대역 조건이 걸려 있었다. 송출 키가 설정되어 있어도 시청은 인증 없이 가능한 구조다.


설정 파일 생성과 실행 순서가 하나의 스크립트로 묶여 있었다. 수동으로 반복할 단계를 줄일 수 있는 대신 기존 서비스, 포트 사용 현황, 네트워크 정책에 주는 영향도 함께 살펴볼 구성이다. 이번에는 코드를 읽었으며 설치기 실행이나 방화벽 변경은 수행하지 않았다.


## 지연 설정과 전체 측정 구간


HLS 설정에는 lowLatency, 1초 세그먼트, 200ms 부분 조각, 세그먼트 7개가 들어 있었다. 숫자가 작아 보이지만 이 값을 곧바로 송출부터 화면까지의 지연으로 읽을 수는 없다.


[MediaMTX 설정 문서](https://mediamtx.org/docs/references/configuration-file)에서는 세그먼트와 부분 조각의 길이를 최소 길이로 설명하고 있으며, 실제 길이는 키프레임이나 샘플 간격에도 영향을 받는다고 안내하고 있다.


클라이언트가 버퍼를 어느 만큼 채우는지도 재생 시점에 영향을 준다. HLS 조각을 짧게 설정하는 것은 전체 지연을 구성하는 여러 조건 중 하나다.


설명용 예를 들어 송출 인코딩에 100ms, 전송, 중계에 150ms, 재생 버퍼에 600ms가 걸렸다면 합은 850ms다. 전체 지연은 각 단계의 처리, 전송 시간이 합쳐진 값이므로 단계별로 측정해야 한다. 이 숫자들은 실측값이 아니며, 지연을 단계별로 나누어 보는 계산 예다.


메모리도 같은 구분이 적용된다. Compose의 512M은 메모리 사용량 상한 설정이다. 그 안에서의 스트림 안정성은 실제 입력 조건으로 측정해야 한다. 해상도, 비트레이트, 동시 시청 수에 따른 실제 자원 사용 기록이 있어야 운영 범위를 판단할 수 있다.


## 설치기의 동작 검사 범위


start_container는 컨테이너 시작 뒤 3초를 기다린 다음 docker ps 출력에 mediamtx가 있는지 확인하는 방식이었다. 송출자 연결, 스트림의 미디어 트랙, HLS 목록의 갱신, 플레이어의 디코딩 결과를 확인하는 단계는 포함되어 있지 않다.

설치 파일은 latest-ffmpeg 태그를 사용하고 있어서 다시 설치할 때 실제 버전이 달라질 수 있다. 재현성을 위해서는 이미지 식별값과 생성한 설정을 함께 보관하는 편이 낫다. 예를 들어 저장된 스크립트의 경로 설정과 현재 공식 설정 예시는 표기가 달랐다. 실행 버전이 해당 설정을 어떻게 해석하는지 확인할 항목이다.


## 연결 이후의 미디어 재생 확인


이 저장소에서 확인한 범위는 MediaMTX 자체의 스트리밍 엔진보다 설치, 설정, 시작 절차를 묶은 부분이었다. 저지연과 저자원 사용을 목표로 한 설정값은 읽을 수 있었지만, 실측 검증 자료는 없었으므로 성능 수치로 바꾸어 적지는 않았다.


짧은 시험 영상을 송출하고 같은 경로를 RTSP와 HLS로 읽는 실행 검증이 남았다. 화면, 소리, 지연, 연결 복구는 그때 각각 기록할 항목이다. 이어지는 원격 운영 글에서는 접속 경로와 서비스 동작을 나누어 살펴본다.


## 작업을 정리하며


스트리밍의 체감 지연은 여러 단계가 합쳐진 결과다. 각 설정값과 실제 측정 구간을 연결해 두면 지연 원인을 좁힐 수 있다. 실행 버전과 입력 조건을 고정한 작은 송출, 재생 시험을 다음 확인 단위로 삼으려 한다.
