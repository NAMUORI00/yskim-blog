원격 운영 환경에서는 주소와 연결 설정, 상태 확인과 복구 절차를 연결했다. 도구마다 입력 주소를 해석하고 설정을 반영하는 방식이 달라 설치 스크립트의 검사와 실제 접속 단계를 구분했다.


## 구현과 확인 과정


원격 연결 설정 코드와 운영, 복구 문서를 읽으며, 네트워크 연결, 사용자 인증, 애플리케이션 동작이 각각 어떤 단계로 나뉘는지 정리해 봤다. 앞 글에서 접속과 재생을 구분한 흐름의 연장이다.


살펴본 대상은 NAMUORI00/jetkvm-tailscale-service-hub의 7daea22 코드와 openclaw-gcp-ops-manual의 56dd9b1 운영 문서다. 전자는 연결 설정을 적용하는 프로그램이고, 후자는 운영, 복구 절차를 기록한 문서다. 코드와 문서를 읽은 범위의 정리이며, 현재 서버에 접속해 확인하는 작업은 하지 않았다.


## 서버마다 설치하는 대신 중간 호스트를 둔 구성


JetKVM 서비스 허브의 [README](https://github.com/NAMUORI00/jetkvm-tailscale-service-hub/blob/7daea22d32b09756831b2c769f829d12cdcff2ef/README.md)에는 뒤쪽 서버마다 Tailscale을 설치하지 않고 선택한 서비스만 연결하겠다는 목적이 적혀 있었다. 허브는 서비스 목록 파일을 읽어 Tailscale Service 정의와 JetKVM의 연결 설정을 관리하는 구조였다.


[Tailscale Services 문서](https://tailscale.com/docs/features/tailscale-services)에서 서비스 정의와 이를 제공하는 호스트는 별도 요소로 다뤄진다. 이 구분을 코드에 대입하면 이름, 포트를 등록하는 일, 호스트가 연결을 제공한다고 알리는 일, 그 호스트를 승인하는 일이 따로 존재하는 이유가 드러난다.


![10-04-01.png](/images/notion/tech-10-04/image-1.png)


그림 1. 서비스 목록에서 제어 설정을 만들고 JetKVM을 통해 내부 서버로 연결하는 구조. 출처: 서비스 목록 동기화, 연결 설정 적용과 Tailscale 공식 문서를 바탕으로 직접 구성. 실제 계정, 주소, 토큰은 표시하지 않았다.


[서비스 목록 동기화](https://github.com/NAMUORI00/jetkvm-tailscale-service-hub/blob/7daea22d32b09756831b2c769f829d12cdcff2ef/bin/sync.sh)는 구분자로 나뉜 텍스트를 CSV로 변환하고 서비스명과 포트를 검사하는 스크립트였다.


노출, 대상 포트는 22와 443으로 제한되어 있었고, 대상 주소는 `172.18.*.*` 패턴으로 확인하고 있었다. 문자열 패턴을 검사하는 구현이며 IPv4 각 구간의 숫자 범위는 별도 검증이 필요했다.


## 설정 파일과 적용 상태 비교


[연결 설정 적용](https://github.com/NAMUORI00/jetkvm-tailscale-service-hub/blob/7daea22d32b09756831b2c769f829d12cdcff2ef/bin/apply.sh)은 기본 동작에서는 생성할 설정을 남기고 끝나고, --apply 플래그가 있을 때 API와 로컬 연결 설정을 실제로 변경한다.


적용 순서는 API 정의 갱신, 로컬 serve 적용, 광고, 호스트 승인이었다. 중간 단계에서 실패해도 앞 단계의 변경을 되돌리는 처리는 없어서, 단일 트랜잭션으로 묶이지 않는 구조다.


목록에서 빠진 항목을 정리하는 범위도 확인했다. --prune-tailnet은 API가 반환한 서비스 목록과 원하는 목록을 비교한다. 이 허브가 만든 항목만 골라내는 소유 표시 조건은 코드에서 보이지 않았다. 여러 도구가 같은 서비스 공간을 관리하는 환경이라면, 정리 대상의 범위가 겹칠 여지가 있다.


[설정 변경 감시](https://github.com/NAMUORI00/jetkvm-tailscale-service-hub/blob/7daea22d32b09756831b2c769f829d12cdcff2ef/bin/watch.sh)는 시작할 때 한 번 적용을 실행하고, 이후 기본 30초 간격으로 파일 체크섬 변화를 감시한다.


코드에서 기억하는 last 값은 적용 성공 여부와 무관하게 갱신된다. 새 파일을 감지하면 바뀐 체크섬을 먼저 기록한 뒤 적용을 시도하는 흐름이었다.


파일 A가 B로 바뀐 직후 API 오류가 발생한 경우, 같은 B 파일이 계속 남아 있으면 체크섬 변화가 없으므로 다음 주기에 자동 재시도가 일어나지 않는다. 실패는 로그에 남지만, 파일이 다시 바뀌지 않는 한 재적용 트리거가 없는 셈이다. 변경 감지와 실패 복구가 별도 상태로 분리되어 있지 않은 지점이다. 코드에서 추적한 연결, 복구 흐름이다.


## 연결 로그의 확인 범위


연결 설정 적용의 마지막에는 JetKVM에서 대상 포트로 연결을 시도하는 검사가 있었다. 다만 이 검사는 허브에서 내부 서버까지의 연결만 확인하며, 원격 사용자가 서비스 이름으로 접근하는 전체 경로를 포괄하지는 않는다. 허브→내부 서버 구간이 열려 있어도 사용자 권한이나 서비스 등록 상태는 별도 확인이 필요하다.


검사 결과를 OK로 분류하는 조건에는 일부 시간 초과 문구도 포함되어 있었다. 이 표시만으로 SSH 인증 성공이나 HTTPS 응답 검증까지 확인되었다고 보기는 어렵다. 연결 시도, 프로토콜 응답, 인증, 실제 기능 호출 각각을 구분해서 남기면 로그가 어디까지의 증거인지 판단하기 수월해질 것이다.


## 관리 접속과 웹 서비스 경로


[OpenClaw 운영 매뉴얼](https://github.com/NAMUORI00/openclaw-gcp-ops-manual/blob/56dd9b1c3f3505b5f05406e75e88a6b679cbf083/README.md)에는 웹 접근에 Cloudflare Tunnel, 관리 SSH에 GCP IAP를 사용하는 구성이 기록되어 있었다. 같은 VM을 대상으로 하지만 두 경로의 구성 요소는 서로 다르다.


![10-04-02.png](/images/notion/tech-10-04/image-2.png)


그림 2. 문서에 기록된 웹 접근과 관리 접근, 애플리케이션 내부 상태의 구분. 출처: openclaw-gcp-ops-manual README를 바탕으로 직접 구성. 연결 구성과 상태 확인 지점을 나타낸 그림이다.


[Cloudflare 문서](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/)에 따르면 cloudflared는 VM 안에서 외부로 연결을 시작하는 모델이다.


[GCP IAP 문서](https://docs.cloud.google.com/iap/docs/using-tcp-forwarding)에 따르면 외부 IP가 없는 VM에도 관리용 TCP 터널을 제공할 수 있다. IAP를 통한 SSH 접속이 되더라도 cloudflared의 외부 연결 상태와는 별개이므로, 한쪽의 정상 여부로 다른 쪽을 판단할 수 없다.


매뉴얼에는 외부 IP를 제거했을 때 웹 경로에 문제가 생겨 당시 구성에서는 외부 IP를 유지했다는 기록이 있었다. 이는 해당 설치 스크립트의 주소 처리 방식이며 Cloudflare Tunnel의 일반 연결 조건과는 구분해 읽는다. 해당 환경에서 외부로 나가는 대체 경로가 준비되어 있었는지가 별도 확인 사항이다.


## 복구 순서를 서비스 내부까지 이어 가기


매뉴얼의 복구 절차는 외부 응답, 터널 프로세스, 컨테이너 상태, 모델 인증, 채널 연결, 장치 승인 상태를 차례로 확인하는 순서로 구성되어 있었다. 이전 작업에서 장치가 승인 대기 상태로 남았던 기록이 포함되어 있어, 네트워크 연결이 복구된 뒤에도 애플리케이션 수준의 승인 상태가 서비스에 영향을 줄 수 있는 사례였다.


이번 정리는 원격 장비에 접속하거나 설정을 적용하지 않고, 코드와 문서를 대조한 범위에 한정된다. 비용, 모델 이름, 현재 VM 목록처럼 시점에 따라 달라질 수 있는 운영 값은 옮겨 적지 않았다.


마지막 성공 시각, 시도한 구성, 적용 실패 단계, 사용자 요청 결과는 운영 기록을 보완할 항목으로 남았다. 이번에 읽은 연결 설정과 복구 절차를 실제 요청의 결과에 연결하는 데 필요한 정보다. 이어지는 퍼블리싱 글에서는 저장된 정보가 웹페이지로 반영되는 과정을 살펴본다.


## 작업을 정리하며


복구 절차는 어느 연결이 끊겼는지 알아야 선택할 수 있다. 주소 검증, 서비스 실행, 외부 접속을 단계별로 기록하면 같은 증상도 원인을 나누어 볼 수 있다. 정상 경로와 복구 후 확인 경로를 함께 남기고 싶다.
