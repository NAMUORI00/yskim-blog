앞 글에서는 Notion에 쓴 글을 블로그용 문서로 변환하는 과정을 다뤘다. 하지만 변환 규칙이 준비되어 있어도 Notion에서 고친 문장이나 새로 바꾼 그림이 공개 사이트에 바로 나타나지는 않는다. 원본 글이 독자 화면에 닿기까지 글을 가져오는 수집, 웹용 파일을 만드는 **빌드**, 결과물을 사이트에 올리는 **배포**를 차례로 거치기 때문이다.


여기에 한 번 만든 응답을 일정 시간 다시 쓰는 **캐시**까지 겹치면 각 단계가 움직이는 시점과 조건에 따라 시간차가 생긴다. 이 글에서는 수집한 글이 어떤 조건에서 공개 사이트까지 이어지고, 만료 시간이 있는 Notion 파일 주소가 캐시와 만날 때 어떤 시간차가 생기는지 살핀다. 이 두 가지를 확인하기 위해 `NAMUORI00/yskim-blog` 저장소(`9dd7a22` 커밋 기준)의 수집 스크립트와 배포 설정을 읽었다.


## 발행 상태 필터와 콘텐츠 수집 시점


공개 사이트 반영의 첫 단계는 Notion에 적힌 글 가운데 이번 실행에서 가져올 대상을 고르는 일이다. 예를 들어 Notion 데이터베이스에는 다 쓴 글인 `Published`와 작성 준비 단계인 `Ready`처럼 진행 상태가 적혀 있다. [발행 대상 글 수집](https://github.com/NAMUORI00/yskim-blog/blob/9dd7a2227d53f1f82fd5a539afce4c1bc35d653f/scripts/notion-content.mjs) 스크립트는 기본값으로 `Published` 상태인 페이지만 가져오므로 `Ready` 상태인 글은 수집에서 빠진다. 이 조회 조건은 실행 옵션이나 실행할 때 밖에서 값을 넘기는 설정인 `NOTION_STATUS` 환경 변수로 바꿀 수 있다. 따라서 실제 사이트에 들어가는 글의 범위는 각 실행에 넘긴 상태 필터가 결정한다.


주의할 점은 가져온 글의 출력 문서에는 원래 상태 이름과 상관없이 초안이 아니라는 뜻의 `draft: false`가 들어간다는 것이다. 만약 수집 조건을 `Ready`로 바꿔 실행하면 `Ready` 상태인 글도 모두 공개용 문서(`draft: false`)로 변환된다. 결국 Notion에 적힌 상태 이름만 보고는 그 글이 실제 사이트에 공개되었는지 판단할 수 없다. 해당 실행에서 어떤 상태를 수집 대상으로 지정했는지를 함께 확인해야 공개 여부를 알 수 있다.


수집 대상에 포함되었더라도 뒤이은 빌드와 배포 단계가 끝날 때까지는 시간차가 생긴다. 예를 들어 10시 정각에 Notion에서 글을 고치고 10시 5분에 블로그를 열었다고 가정해 보자. 그 5분 사이에 수집, 빌드, 배포가 실행되지 않았다면 사이트에는 이전 내용이 그대로 보이는 것이 정상이다. 반대로 수집과 빌드는 성공했지만 마지막 배포가 실패했다면, 생성된 문서와 공개 사이트의 화면이 서로 달라진다.

## 본문 이미지와 첨부파일 처리 경로


앞 절에서 본 글 본문뿐 아니라 글에 넣은 이미지와 첨부파일도 수집 방식과 실행 시점의 영향을 받는다. [Notion 파일 문서](https://developers.notion.com/reference/file-object)를 보면 Notion이 직접 보관해 제공하는 파일 주소에는 만료 시각(`expiry_time`)이 붙어 있다. 유효 시간이 지나면 파일 객체를 다시 조회해야 하므로, 이 임시 주소를 웹페이지(정적 HTML)에 그대로 넣으면 만료 시각 뒤에는 그림이 열리지 않는다.


이 저장소는 수집 단계에서 본문 이미지와 표지를 미리 내려받아 사이트 내부의 정적 파일 경로로 바꾼다. 독자의 브라우저는 Notion의 임시 주소 대신 사이트의 정적 파일을 읽으므로 시간이 지나도 그림이 깨지지 않는다. 대신 다음 수집과 배포가 실행되기 전까지는 Notion에서 그림을 바꾸더라도 사이트 화면에는 반영되지 않는다.


영상, 오디오, PDF 같은 일반 첨부파일은 `mediaMode` 설정에 따라 처리 경로가 두 갈래로 나뉜다. 기본값인 `download` 모드는 본문 이미지와 마찬가지로 첨부파일을 미리 내려받아 빌드 결과물에 함께 넣는다. 반면 `proxy` 모드는 첨부파일 주소를 `/media/{블록 ID}` 형태로만 적어 두고, 독자가 파일을 요청할 때 새 파일 주소를 구해 연결한다. 용량이 큰 파일을 매번 빌드 결과물에 포함하지 않으려고 경로를 나눈 것으로 보였다. `proxy` 모드를 켜더라도 본문과 표지 이미지는 그대로 수집 시점에 내려받는다.


다만 저장소의 자동 실행 설정과 호출 스크립트를 확인했을 때 `NOTION_MEDIA_MODE=proxy` 설정을 넘기는 곳은 없었다. 현재 실행 경로의 기본값은 모두 `download`여서 일반 첨부파일도 수집 시점에 내려받는다. 저장소에 `proxy` 기능 코드가 존재한다는 것과 현재 배포가 그 기능을 실제로 쓰고 있다는 것은 별개다.


![본문 이미지와 기본 download 모드의 첨부파일은 수집 시 내려받아 정적 빌드 자산으로 저장되고, proxy 모드의 첨부파일은 블록 ID 경로로 변환되어 독자 요청 시 주소를 조회하는 비교 다이어그램](/images/notion/tech-11-02/image-2.png)

## 주소 캐시와 첨부파일 만료 시간


현재 배포에서 `proxy` 모드를 쓰지는 않지만, 요청 시점에 주소를 조회할 때 만료 시간을 어떻게 다루는지 보려고 [첨부파일 주소 조회 함수](https://github.com/NAMUORI00/yskim-blog/blob/9dd7a2227d53f1f82fd5a539afce4c1bc35d653f/functions/media/%5Bid%5D.js)도 함께 읽었다. 이 함수는 파일 바이트를 직접 전송하지 않고, 실제 파일 주소를 찾아 브라우저가 그 주소로 이동하게 하는 **HTTP 302 응답**을 보낸다. 주소를 찾을 때는 키와 값 형태로 저장하는 **KV 캐시**를 먼저 확인하고, 저장된 값이 없을 때만 Notion API를 호출한다. 이때 KV 캐시는 같은 파일 주소를 2,700초(45분) 동안 보관하고, HTTP 302 응답에도 2,700초 동안 재사용을 허용하는 `max-age`를 붙인다.


두 단계의 캐시 유지 시간과 원본 주소의 만료 시간을 숫자로 대조해 보았다. 예를 들어 0분에 Notion에서 받은 파일 주소가 60분에 만료된다고 놓으면, 이 주소는 먼저 KV 캐시에 45분 동안 보관된다. 만약 44분에 들어온 요청이 KV 캐시를 읽으면, 그때 나가는 302 응답에도 새로 45분의 재사용 허용 시간(`max-age`)이 붙는다. 이 응답을 재사용하는 쪽에서는 89분까지 유효하다고 여길 수 있지만, 정작 원본 파일 주소는 60분에 먼저 만료된다.


![독자의 첨부파일 요청이 KV 캐시 확인과 Notion 블록 조회를 거쳐 45분 캐시가 적용된 302 응답으로 반환되고, 원본 Notion 파일 주소가 먼저 만료되면 접근에 실패할 수 있음을 보여 주는 가로 흐름도](/images/notion/tech-11-02/image-3.png)


그림 3. proxy 모드의 첨부파일 주소 조회와 두 캐시 계층의 경계를 나타낸 흐름도(functions/media/[id].js를 바탕으로 직접 구성).


원본 파일 주소의 남은 수명을 계산해 캐시 시간을 줄이는 처리가 없어서 각 캐시 계층마다 유효 시간이 새로 시작된다. 코드에서 도출한 개선 방향은 첫째로 Notion이 돌려주는 `expiry_time`을 함께 보관해 남은 시간보다 짧게 응답을 캐시하는 방법이다. 둘째로는 302 응답의 재사용 자체를 제한해 매번 KV 캐시나 Notion에서 주소를 다시 확인하게 하는 방법이다. 나중에 이 경로를 검증할 때는 정상적인 첫 요청뿐 아니라 만료 직전에 캐시에서 주소를 꺼내 쓰는 상황(캐시 적중)도 검증 범위에 넣어야 한다.


## 빌드 검사와 실제 배포의 분리


앞 절들에서 확인한 수집과 변환이 끝나면, [콘텐츠 검사, 빌드, 배포 작업](https://github.com/NAMUORI00/yskim-blog/blob/9dd7a2227d53f1f82fd5a539afce4c1bc35d653f/.github/workflows/validate-and-build.yml) 워크플로가 결과물을 검사하고 실제 사이트에 올린다. 자동 실행 절차인 이 워크플로는 콘텐츠 수집, 검사, 빌드를 거친 파일을 결과물 묶음인 **아티팩트**(artifact)로 보관한다. 이어지는 배포 단계에서는 다시 수집하거나 새로 빌드하지 않고, 앞 단계에서 보관한 아티팩트를 그대로 내려받아 Cloudflare Pages에 올린다. 실제 공개 사이트에 올라간 결과가 이 아티팩트와 일치하는지는 해당 배포 실행에서 확인할 부분이다.


이 워크플로에서는 빌드 검사를 실행하는 조건과 실제 사이트(프로덕션)에 배포하는 조건이 분리되어 있었다. 코드 변경을 합치기 전에 검토하는 **PR**(Pull Request)은 빌드 검사를 거치지만 실제 사이트 반영 대상에는 포함되지 않는다. 정해진 시각에 도는 예약 실행, `main` 브랜치 푸시, 그리고 배포 옵션을 켠 수동 실행만 실제 사이트 배포 경로로 이어진다. 수동 실행에는 수집할 글의 상태 필터도 있어서, 실행 기록을 볼 때 상태 조건과 배포 여부를 함께 확인할 수 있다.


![PR 실행, main 푸시와 예약 실행, 수동 실행이 모두 수집, 검사, 빌드를 거쳐 아티팩트를 보관한 뒤, 배포 대상 조건에 해당하는 실행만 Cloudflare Pages 배포로 이어지는 다이어그램](/images/notion/tech-11-02/image-4.png)


그림 4. 실행 조건에 따라 빌드 검사와 프로덕션 배포를 분리한 워크플로 흐름도(.github/workflows/validate-and-build.yml을 바탕으로 직접 구성).


그래서 Notion에서 글을 고쳤는데도 사이트가 갱신되지 않았다면 단계별 경계를 순서대로 대조해 어느 지점에서 멈췄는지 좁힐 수 있다. Notion 수정 시각, 워크플로가 수집한 상태와 시각, 생성된 문서, 빌드 결과물, 배포 결과 순으로 확인하면 된다. 만약 첨부파일만 문제라면 해당 파일이 정적 파일로 저장된 것인지(`download`), 요청 시점에 주소 이동으로 연결되는 것인지(`proxy`)를 먼저 구분하면 된다.


## 결론


이번 글에서는 Notion 원본 저장부터 공개 블로그 주소 반영까지 이어지는 수집, 빌드, 배포, 캐시 경로를 코드와 설정으로 추적해 점검 순서를 정리했다. 상태 필터(`NOTION_STATUS`)에 따른 수집 범위와, 첨부파일 경로 가운데 현재 배포가 `download` 모드를 기본으로 쓴다는 점을 확인했다. 또한 `proxy` 모드의 두 캐시 계층에서 원본 주소가 먼저 만료될 수 있는 조건과, 워크플로가 빌드 검사와 실제 배포를 분리한 구성을 짚었다.


이번 내용은 문서와 코드를 읽은 범위의 기록이며, 실제 배포 실행 대조나 첨부파일 만료 재현 실험은 아직 남아 있다. 다음 글에서는 같은 프로젝트 정보가 블로그, 포트폴리오, GitHub 프로필에서 어떻게 다르게 구성되는지 이어서 다룬다.
