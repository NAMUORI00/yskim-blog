## 구현과 확인 과정


앞 글에서 Notion 콘텐츠가 블로그 문서로 변환되는 과정을 정리했고, 이번에는 그 뒤를 이어 콘텐츠 수집, 빌드, 배포, 캐시가 각각 어떤 조건에서 동작하는지 yskim-blog 코드를 읽으며 확인했다. 이 단계들은 서로 다른 시점에 움직이기 때문에, Notion에서 문장을 고치더라도 사이트에 곧바로 반영되지 않을 수 있다.

## 발행 상태와 콘텐츠 수집 조건


[발행 대상 글 수집](https://github.com/NAMUORI00/yskim-blog/blob/9dd7a2227d53f1f82fd5a539afce4c1bc35d653f/scripts/notion-content.mjs)은 기본적으로 Published 상태의 페이지를 가져온다.


상태는 옵션이나 NOTION_STATUS 환경 변수로 바꿀 수 있었다. 기본 Published 조회는 Ready 글을 제외하며, 실제 공개 범위는 각 실행의 조회 필터로 결정된다.


가져온 글의 출력 문서에는 draft: false가 들어간다. 따라서 수집 조건을 Ready로 바꾸면 Ready인 글도 공개용 문서로 변환된다. 글의 상태 이름만으로는 실제 공개 여부를 알 수 없고, 해당 실행이 어떤 상태를 수집 대상으로 지정했는지가 함께 기록되어야 판단할 수 있다.


예를 들어 10시에 글을 고치고 10시 5분에 사이트를 열었다고 하자. 그 사이에 수집, 빌드, 배포가 실행되지 않았다면 이전 내용이 보이는 것이 정상이다. 반대로 수집은 성공했지만 배포가 실패했다면 생성된 문서와 공개 사이트의 내용이 달라진다. 단계 사이의 시간차를 설명하기 위해 구성한 예시다.

## 이미지 주소를 저장하는 두 가지 방식


[Notion 파일 문서](https://developers.notion.com/reference/file-object)에 따르면 Notion이 호스팅하는 파일 주소는 만료 시각을 가지며, 만료 후에는 파일 객체를 다시 조회해야 한다. 이 주소를 정적 HTML에 그대로 넣어 두면 빌드 직후에는 보이던 그림이 만료 이후에는 열리지 않게 된다.


이 저장소는 본문 이미지와 표지를 내려받아 사이트의 정적 자산 경로로 바꾸고 있었다. 이렇게 저장된 그림은 독자가 볼 때 원래의 임시 주소에 다시 접속할 필요가 없다. 대신 다음 수집이 실행되기 전까지는 Notion에서 교체한 그림이 사이트에 반영되지 않는다.


영상, 오디오, PDF, 일반 첨부파일은 mediaMode에 따라 경로가 달라진다. 기본 download 모드는 파일을 빌드 자산으로 옮긴다. proxy 모드는 Notion 업로드 파일에 /media/{블록 ID} 주소를 넣고, 요청 시점에 새 파일 주소를 구하는 방식이다. 큰 파일을 매번 빌드 결과에 포함하지 않기 위한 구성으로 읽었다. 이미지 다운로드는 proxy 모드에서도 유지된다.


다만 확인한 워크플로와 호출 스크립트에는 NOTION_MEDIA_MODE=proxy 설정이 없었다. 이 실행 경로의 기본값은 download다. 저장소에 proxy 기능의 코드가 존재한다는 것과 현재 배포가 그 기능을 사용하고 있다는 것은 별개다.


## 주소 캐시와 첨부파일 만료 시간


[첨부파일 주소 조회 함수](https://github.com/NAMUORI00/yskim-blog/blob/9dd7a2227d53f1f82fd5a539afce4c1bc35d653f/functions/media/%5Bid%5D.js)는 파일 바이트를 대신 전송하지 않는다.


이 함수는 캐시나 Notion API에서 주소를 찾아 HTTP 302로 독자를 해당 주소로 보낸다. KV 캐시는 같은 파일의 주소를 2,700초 동안 보관하고, 302 응답에도 2,700초의 max-age를 붙인다.


이 구조에서 만료 시간 계산을 한 번 짚어 봤다. 설명용으로 0분에 받은 파일 주소가 60분에 만료된다고 놓자. 44분에 KV 캐시를 읽은 응답에도 새로 45분의 캐시 허용 시간이 붙는다. 이 응답을 재사용하는 쪽에서는 89분까지 유효하다고 취급할 여지가 있지만, 파일 주소 자체는 60분에 먼저 만료된다. 캐시 계층마다 나이가 새로 시작되는 구조다.


![11-02-02.png](/images/notion/tech-11-02/image-2.png)


그림 2. proxy 모드의 주소 조회와 두 캐시 경계. 출처: functions/media/[id].js를 바탕으로 직접 구성. 파일 주소의 남은 수명을 계산해 캐시 시간을 줄이는 처리는 이 코드에 없다.


코드에서 도출한 캐시 점검 조건이다. 개선 방향으로는 expiry_time을 함께 보관하고 남은 시간보다 짧게 응답을 캐시하는 방법, 또는 리디렉션 응답의 재사용 자체를 제한하는 방법이 있다. 정상적인 첫 요청뿐 아니라 만료 직전의 캐시 적중도 검증 범위에 포함된다.


## 빌드 성공과 배포 성공을 각각 남기기


워크플로는 콘텐츠 수집, 검사, 빌드를 거친 파일을 아티팩트로 보관하고, 배포 단계에서 그 파일을 내려받아 Cloudflare Pages에 올린다. 배포 직전 다시 수집하거나 빌드하는 단계가 없어 검사한 산출물을 그대로 사용하는 구성이다. 실제 공개 결과의 일치 여부는 해당 배포 실행에서 확인할 부분이다.


[콘텐츠 검사, 빌드, 배포 작업](https://github.com/NAMUORI00/yskim-blog/blob/9dd7a2227d53f1f82fd5a539afce4c1bc35d653f/.github/workflows/validate-and-build.yml)


배포 조건은 별도로 지정되어 있었다. PR은 빌드 검사를 거치지만 production 반영 대상에는 포함되지 않는다. 예약 실행, main 푸시, 배포가 켜진 수동 실행이 production 경로로 이어진다. 수동 실행에는 상태 필터도 있어서, 실행 기록을 볼 때 상태 조건과 배포 여부를 함께 확인할 수 있다.


글이 갱신되지 않은 경우, Notion 수정 시각 → 수집된 상태와 시각 → 생성 문서 → 빌드 산출물 → 배포 결과 순으로 대조하면 어느 경계에서 멈췄는지 좁힐 수 있다. 첨부파일만 문제라면 해당 파일이 정적 자산으로 저장된 것인지 요청 시점에 리디렉션으로 제공되는 것인지를 먼저 구분하면 된다.


이번에는 수집에서 배포까지 이어지는 경로의 코드와 설정을 확인했다. 문서와 코드를 읽은 범위의 기록이며, 실제 배포 실행이나 만료 재현 실험은 아직 남아 있다. 다음 글에서는 같은 프로젝트 정보가 블로그, 포트폴리오, GitHub 프로필에서 어떻게 다르게 구성되는지 살펴볼 예정이다.


## 작업을 정리하며


발행 완료는 편집 원본 저장부터 공개 URL 확인까지 이어져야 한다. 수집과 배포 상태를 구분하고 만료되는 자산 주소를 따로 다루면 변경이 보이지 않는 이유를 추적할 수 있다. 이 단계 구분을 블로그 운영의 기본 점검 순서로 삼았다.
