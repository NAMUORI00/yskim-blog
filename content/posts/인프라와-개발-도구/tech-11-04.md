개인 노트를 여러 환경에서 관리하며 동기화, Git 변경 이력, 백업의 보관 범위를 정리했다. 노트 본문과 첨부 이미지의 추적 규칙이 달라 새 기기에서 복원할 자료를 함께 확인했다.


## 구현과 확인 과정


두 노트 저장소의 구조와 제외 규칙을 살펴봤다. 노트를 원격 Git 저장소에 올렸더라도 첨부 이미지가 제외돼 있으면 다른 기기에서 글을 온전히 복원하지 못할 수 있다. 현재 파일을 맞추는 동기화, 이전 버전을 되찾는 버전 관리, 기기를 잃은 뒤 되살리는 백업을 나눠서 보관 범위를 확인했다.


yskim_note의 5e590cc와 obsidian_sync_mybook의 eda1301 커밋에서 README와 저장소 설정을 살펴봤다. Git의 커밋은 기록할 파일의 스냅샷을 남기고, push는 그 커밋을 원격에 전달한다는 정도를 출발점으로 삼았다. 개인 노트의 내용보다는 저장 구조와 제외 규칙을 중심으로 읽었다.


## Markdown 노트의 저장 구조


[Obsidian의 저장 방식](https://help.obsidian.md/Files+and+folders/How+Obsidian+stores+data)에 따르면 vault는 로컬 폴더이고 노트는 Markdown 텍스트 파일이다.


Markdown 파일이므로 별도 편집기로도 열 수 있고, Git에서 문장 단위의 변경을 비교하기 좋다. 첨부 이미지와 프로그램 설정은 노트 본문과 별도 파일로 존재한다.


[yskim_note의 README](https://github.com/NAMUORI00/yskim_note/blob/5e590cc6c0b288921e81769e79e0f4962e523003/README.md)는 PARA 폴더 구분과 단일 주제의 노트, 관련 노트의 내부 링크를 작성 규칙으로 제시한다.


Projects는 끝낼 작업, Areas는 계속 관리할 영역, Resources는 참고할 자료, Archives는 완료되거나 비활성화된 항목이다.


이 구분을 Git의 브랜치나 커밋과 같은 것으로 읽지는 않았다. PARA는 자료를 찾고 정리하는 기준이고 Git은 그 파일들이 어떻게 바뀌었는지 남기는 수단이다. Archives로 옮긴 변화가 원격 이력에 남으려면 이동 내용을 커밋하고 전송해야 한다.


## 저장소별 동기화 범위


[yskim_note의 .gitignore](https://github.com/NAMUORI00/yskim_note/blob/5e590cc6c0b288921e81769e79e0f4962e523003/.gitignore)에는 .obsidian 폴더, 첨부파일 폴더, 휴지통과 일부 생성 데이터의 제외 규칙이 있다.


반면 [obsidian_sync_mybook의 README](https://github.com/NAMUORI00/obsidian_sync_mybook/blob/eda1301dfc310c398ab1cd39662faf15b46644fe/README.md)는 설정과 플러그인 정보도 함께 저장할 수 있다는 점을 설명한다. 실제 트리에서도 편집기 기본 설정과 활성 플러그인 목록을 확인했다.


노트 본문 위주로 이력을 남기면 기기마다 자주 달라지는 화면 배치나 캐시가 변경 목록을 채우는 일을 줄일 수 있다. 설정까지 포함하면 다른 기기에서 비슷한 환경을 바로 구성할 수 있다. 어느 범위를 택하든 "저장소를 다시 받았을 때 무엇이 돌아오는가"를 먼저 확인해 두는 편이 낫다.


![11-04-01.png](/images/notion/tech-11-04/image-1.png)


그림 1. vault 전체와 Git이 실제로 기록하는 파일 집합의 차이. 출처: 두 저장소의 README, 설정, 제외 규칙을 바탕으로 직접 구성. 제외된 파일은 별도 보관 경로를 점검해야 한다.


노트에 이미지 링크가 남아 있어도 이미지 파일 자체가 기록 대상에서 빠졌다면, 새 기기에서는 글만 복구되고 그림은 열리지 않는다. 링크 문자열이 살아 있다는 것과 링크가 가리키는 파일이 함께 보관되었다는 것은 별개다. 백업을 확인할 때 파일 개수뿐 아니라 대표 노트에서 그림과 내부 링크를 실제로 따라가 보는 것은 이 때문이다.


[Git의 gitignore 문서](https://git-scm.com/docs/gitignore)는 이미 추적 중인 파일에는 제외 규칙이 소급 적용되지 않는다고 설명한다. 원격 파일의 존재 여부는 제외 목록과 실제 커밋 트리를 함께 확인한다. 현재 커밋의 트리, 과거 이력에 남아 있는 파일, 새 파일에 적용될 규칙은 각각 따로 확인해야 한다.


## 플러그인 설명과 현재 설정을 구분하기


obsidian_sync_mybook의 README는 obsidian-git 플러그인을 통한 push와 merge를 설명한다. 그런데 확인한 커밋의 활성 플러그인 목록에는 obsidian-git 항목이 없었다.


README는 사용 방식을 설명하고 있지만, 활성 플러그인 목록에 해당 항목이 없으므로 이 설정만으로 자동 동기화가 현재 켜져 있다고 보기 어렵다. 다른 환경에서 사용했거나 설정이 나중에 바뀌었을 가능성이 있고, 이를 구분하려면 별도 기록이 있어야 한다.


편집기 기본 설정에서는 Markdown 링크 사용과 링크 자동 갱신 옵션을 확인했다. Git 병합 후 문장의 의미 일치는 작성자가 검토해야 한다. 편집기 안에서 파일 이름을 바꾸는 작업과 원격 변경을 병합하는 작업은 다른 경로다.


## 두 기기의 수정 충돌 처리


설명용으로 "측정 간격은 10초"라는 문장이 있다고 해 보자. 노트북에서 5초로, 데스크톱에서 30초로 바꾸고 각각 커밋하면 두 변경은 같은 출발점에서 갈라진다. 어떤 값이 맞는지는 최신 시각만으로 정할 수 없다. 실제 설정을 바꾼 기록인지 다음 실험을 위한 계획인지는 문맥을 봐야 구분된다.


![readable-11-04-02.png](/images/notion/tech-11-04/image-2.png)


그림 2. 같은 문장을 서로 다르게 고친 경우의 설명용 병합 예제. 직접 구성. 


충돌 표식을 없애는 것만으로 복구가 끝나지는 않는다. 선택한 문장이 다른 노트의 수치, 링크와 맞는지도 확인해야 한다. 삭제를 동기화하면 두 기기에 같은 삭제 상태가 반영된다. 실수 이전 자료를 되찾으려면 별도 이력이나 백업이 필요하다.


## 노트와 첨부파일 복원 확인


두 저장소에서 파일 기반 기록 방식, 관리 규칙, 포함된 일부 설정과 제외 목록을 확인했다. 새 폴더로 복원해 모든 첨부파일을 열어 본 검증은 아직 남아 있다. 대표 노트, 이미지, 내부 링크, 설정을 실제로 복원했을 때 돌아오는 범위가 다음 확인 대상이다.


동기화는 최신 파일 상태, 버전 관리는 이전 커밋, 백업은 원본 환경과 분리된 복구 수단을 기준으로 정리했다. 이 구분으로 두 저장소가 보관하는 범위와 복원에서 확인할 부분을 나눌 수 있었다. 다음 글은 명함 CMS의 편집 내용이 공개 화면에 반영되는 과정으로 이어진다.


## 작업을 정리하며


본문에 링크가 남는 것과 실제 파일이 보관되는 것은 각각 확인해야 한다. 대표 노트의 이미지와 내부 링크를 따라가 보는 점검이 중요한 이유다. 동기화가 삭제까지 전달한다는 점을 고려해 복구용 이력과 별도 백업도 함께 관리하려 한다.
