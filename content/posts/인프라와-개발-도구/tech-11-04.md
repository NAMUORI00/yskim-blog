개인 노트를 여러 기기에서 이어 쓰려고 원격 Git 저장소에 올리다 보면 모든 자료가 안전하게 백업되었다고 생각하기 쉽다. 하지만 노트 본문과 첨부 이미지, 편집기 설정 파일에는 서로 다른 기록 규칙이 적용될 수 있다. 다른 기기에서 원격 저장소를 그대로 내려받는 복제(clone)를 했을 때, 글만 복원되고 그림이나 작업 환경은 빠진 채로 열리기도 한다.


Git은 관리 대상으로 지정해 추적하는 파일만 골라서 변경 내역을 기록한다. 추적 대상 파일의 당시 상태를 스냅샷으로 찍어 **커밋**(commit)에 남기고, 푸시(push)로 그 커밋을 원격 저장소에 전달한다. 따라서 여러 기기의 현재 파일을 같게 맞추는 동기화, 과거 이력을 되찾는 버전 관리, 분리된 곳에 복사본을 따로 보관하는 백업은 다루는 범위가 다르다. 이 글에서는 개인 노트 저장소인 `yskim_note`의 `5e590cc` 커밋과 `obsidian_sync_mybook`의 `eda1301` 커밋을 비교했다. 두 저장소의 README와 설정, 제외 규칙을 대조해 새 기기에서 실제로 복원되는 범위를 점검했다.


## Markdown 노트의 저장 구조와 폴더 분류


복원 범위를 파악하려면 먼저 노트 앱인 Obsidian이 파일을 저장하는 구조와 폴더 분류 방식을 알아야 한다. [Obsidian의 저장 방식](https://help.obsidian.md/Files+and+folders/How+Obsidian+stores+data) 문서를 보면 작업 공간인 vault는 컴퓨터 안의 일반 로컬 폴더다. 개별 노트는 서식 기호를 글자로 적는 Markdown(`.md`) 텍스트 파일로 저장된다. 일반 텍스트 파일이므로 Obsidian이 아닌 다른 편집기로도 바로 열 수 있고, Git에서 문장이나 줄 단위로 변경 내역을 비교하기에도 알맞다. 다만 노트에 넣은 첨부 이미지와 편집기 설정은 Markdown 본문 안에 합쳐지지 않고 폴더 안의 별도 파일로 존재한다.


노트 파일을 정리하는 방식은 [yskim_note의 README](https://github.com/NAMUORI00/yskim_note/blob/5e590cc6c0b288921e81769e79e0f4962e523003/README.md)에 적힌 작성 규칙에서 볼 수 있다. 이 저장소는 노트 하나에 주제 하나만 담고 관련 노트를 내부 링크로 잇는 원칙을 따른다. 폴더는 역할에 따라 네 가지로 구분하는 PARA 기준으로 나눈다. 끝내야 할 작업은 `Projects` 폴더에 두고, 꾸준히 관리할 영역은 `Areas` 폴더에 모은다. 참고 자료는 `Resources`에, 완료되었거나 더 이상 다루지 않는 항목은 `Archives` 폴더에 보관한다.


여기서 폴더를 나누는 기준과 Git이 이력을 남기는 방식은 역할이 다르다. 예를 들어 다 끝난 노트를 컴퓨터 안의 `Projects` 폴더에서 `Archives` 폴더로 옮겼다고 해 보자. 그 파일 이동을 커밋하고 원격 저장소로 푸시하지 않으면 원격 이력에는 이전 상태가 그대로 남는다. PARA가 로컬 폴더에서 자료를 분류하고 찾기 위한 정리 기준이라면, Git은 그 파일들이 시간 순서에 따라 어떻게 바뀌었는지 기록하는 도구다.


## 두 저장소의 제외 규칙과 실제 보관 범위


로컬 vault 폴더에는 노트 본문 외에도 첨부파일과 편집기 설정이 함께 들어 있다. 같은 Markdown 노트 저장소라도 추적 제외 규칙을 적어 두는 `.gitignore` 설정에 따라 Git이 기록하는 범위는 크게 달라진다. 로컬 vault 안에 있는 파일 가운데 Git 추적 대상에 들어가는 것만 커밋과 원격 저장소로 이어지고, 제외된 파일은 별도 보관 경로를 마련해야 한다.


![로컬 vault 안의 Markdown 노트, 첨부 이미지와 파일, Obsidian 설정이 Git 추적 대상 여부에 따라 원격 저장소와 별도 보관 범위로 갈라지는 흐름도](/images/notion/tech-11-04/image-1.png)


그림 1. 로컬 vault 전체 파일과 Git이 실제로 기록하는 파일 집합의 차이를 두 저장소의 README, 설정, 제외 규칙을 바탕으로 재구성한 구조도다.


두 저장소의 커밋에 기록된 파일 목록인 커밋 트리와 `.gitignore`를 비교하면 이 차이가 분명하게 드러난다. 먼저 [yskim_note의 .gitignore](https://github.com/NAMUORI00/yskim_note/blob/5e590cc6c0b288921e81769e79e0f4962e523003/.gitignore)는 편집기 설정이 모인 `.obsidian` 폴더, 첨부파일 폴더, 휴지통, 일부 생성 데이터를 제외한다. 반면 [obsidian_sync_mybook의 README](https://github.com/NAMUORI00/obsidian_sync_mybook/blob/eda1301dfc310c398ab1cd39662faf15b46644fe/README.md)는 노트뿐 아니라 설정과 플러그인 정보까지 함께 저장하는 구성을 안내한다. 실제 `eda1301` 커밋 트리에도 편집기 기본 설정과 활성 플러그인 목록 파일이 포함되어 있었다.


![yskim_note 저장소와 obsidian_sync_mybook 저장소의 Git 추적 대상 파일과 제외 파일 구성을 나란히 비교한 그림](/images/notion/tech-11-04/image-2.png)


그림 2. yskim_note와 obsidian_sync_mybook의 커밋 트리와 .gitignore에서 확인한 추적 포함 항목 및 제외 항목 비교도다.


두 방식은 관리 편의성과 환경 재현성에서 각각 장단점이 있다. `yskim_note`처럼 노트 본문만 추적하면 기기마다 수시로 바뀌는 창 배치나 캐시 파일이 변경 목록을 채우는 일을 줄일 수 있다. 반대로 `obsidian_sync_mybook`처럼 설정까지 포함하면 새 기기에 저장소를 복제했을 때 평소 쓰던 편집 환경을 빠르게 재현할 수 있다. 어느 쪽을 택하든 저장소를 다시 내려받았을 때 무엇이 돌아오고 무엇이 빠지는지를 미리 알아 두어야 한다.


특히 첨부파일 폴더를 Git 추적에서 제외했을 때는 본문 안의 링크와 실제 파일의 보관을 분리해서 봐야 한다. Markdown 본문에 이미지를 불러오는 링크 문자열이 남아 있더라도 원격 저장소에 이미지 파일이 없으면 새 기기에서는 글만 열리고 그림은 깨진다. 따라서 백업 상태를 점검할 때는 전체 파일 개수만 세어 보는 데 그치지 말아야 한다. 대표 노트를 직접 열어 그림이 표시되는지와 내부 링크가 제대로 이어지는지까지 따라가 봐야 한다.


또한 `.gitignore` 파일만 읽어서는 원격 저장소에 어떤 파일이 들어 있는지 단정할 수 없다. [Git의 gitignore 문서](https://git-scm.com/docs/gitignore)가 설명하듯, 이미 Git이 추적하고 있던 파일은 나중에 제외 규칙을 추가해도 추적 대상에서 저절로 빠지지 않기 때문이다. 실제 보관 범위를 파악하려면 새 파일에 적용될 `.gitignore` 규칙, 현재 커밋의 파일 트리, 과거 커밋 이력에 남은 파일을 각각 따로 확인해야 한다.


## 문서에 적힌 플러그인 설명과 실제 설정의 차이


저장소 문서를 읽을 때는 사용 설명과 현재 커밋에 반영된 실제 설정도 구분해야 한다. `obsidian_sync_mybook`의 README는 `obsidian-git` 플러그인으로 변경분을 자동 푸시하고 합치는 병합(merge) 방법을 설명한다. 그런데 `eda1301` 커밋의 활성 플러그인 목록 파일을 열어 보니 `obsidian-git` 항목이 들어 있지 않았다.


문서에 사용법이 적혀 있어도 활성 플러그인 목록에 해당 항목이 없다면, 커밋된 설정만 보고 당시에 자동 동기화가 켜져 있었다고 판단하기는 어렵다. 다른 기기 환경에서만 플러그인을 켰거나 설정이 나중에 바뀌었을 가능성이 있는데, 이런 차이는 저장소 밖의 별도 기록이 있어야 구분할 수 있다.


같은 커밋의 편집기 기본 설정에서는 Markdown 형식 링크를 쓰는 옵션과 파일 이름이 바뀔 때 내부 링크를 자동으로 고쳐 주는 옵션을 확인했다. 다만 편집기 안에서 파일 이름을 바꿀 때 동작하는 자동 갱신과 Git으로 원격 변경분을 병합하는 작업은 경로가 다르다. Git 병합을 거친 뒤에도 문장 뜻이 자연스럽게 이어지는지, 다른 노트를 가리키는 링크가 어긋나지 않았는지는 작성자가 직접 검토해야 한다.


## 기기 간 병합 충돌과 삭제 전파


Git 병합은 편집기 기능과 별개로 동작하므로, 여러 기기에서 같은 노트의 같은 줄을 다르게 고치면 **병합 충돌**이 일어날 수 있다. 예를 들어 공통 커밋의 노트에 `"측정 간격은 10초"`라는 문장이 적혀 있었다고 해 보자. 이 문장을 노트북에서는 `5초`로 고쳐 커밋하고, 데스크톱에서는 `30초`로 고쳐 커밋하면 두 변경은 같은 출발점에서 서로 다른 방향으로 갈라진다.


![공통 커밋 10초에서 노트북 5초와 데스크톱 30초로 갈라진 변경이 충돌한 뒤 작성자가 문맥을 확인해 새 커밋으로 합치는 과정](/images/notion/tech-11-04/image-3.png)


그림 3. 두 기기에서 같은 문장을 서로 다른 값으로 고쳤을 때 발생하는 병합 충돌과 해결 과정을 나타낸 설명용 예제다.


이처럼 같은 자리를 다르게 고친 충돌은 어느 커밋의 시각이 더 최신인지만 보고 기계적으로 합칠 수 없다. `5초`와 `30초` 가운데 어느 쪽이 실제 설정을 바꾼 기록이고 어느 쪽이 다음 실험을 위한 계획인지는 앞뒤 문맥을 읽어야 판단할 수 있기 때문이다. 충돌 표시 기호를 지워 문법상 오류를 없애는 것만으로 복구가 끝나지도 않는다. 남기기로 선택한 수치가 연결된 다른 노트의 값이나 링크와 어긋나지 않는지도 함께 맞춰 봐야 한다.


실수로 파일이나 문단을 지웠을 때도 기기 간 연동만으로는 이전 내용을 되돌릴 수 없다. 여러 기기의 현재 파일 상태를 같게 맞추는 **동기화**가 동작하면, 한 기기에서 지운 상태가 다른 기기에도 그대로 반영되기 때문이다.


![동기화, 버전 관리, 백업 각각의 보관 기준과 복구 가능 범위를 세 열로 비교한 그림](/images/notion/tech-11-04/image-4.png)


그림 4. 현재 상태를 맞추는 동기화, 변경 이력을 남기는 버전 관리, 원본과 분리해 보관하는 백업의 복구 범위를 비교한 개념도다.


따라서 동기화만으로는 실수로 지운 자료나 추적 대상에서 빠진 파일을 되살릴 수 없다. 지우기 전의 문장을 되찾으려면 Git 커밋처럼 과거 시점의 변경 이력을 남기는 **버전 관리** 기록이 있어야 한다. 기기를 잃어버리거나 `.gitignore`로 제외된 첨부파일까지 복구하려면 작업 폴더와 분리된 곳에 자료를 따로 보관하는 **백업**이 필요하다.


## 결론


`yskim_note`와 `obsidian_sync_mybook` 두 저장소를 비교해 로컬 파일 기반의 노트 구조와 폴더 관리 규칙을 확인했다. 커밋에 포함된 편집기 설정과 `.gitignore` 제외 목록에 따라 원격 저장소에 실제로 남는 파일 범위가 달라진다는 점도 점검했다. 최신 상태를 맞추는 동기화, 이전 커밋을 되찾는 버전 관리, 원본과 분리해 보관하는 백업을 구분해야 각 저장소의 실제 보관 범위와 복원할 때 비는 영역을 가려낼 수 있다.


다만 원격 저장소를 완전히 새로운 폴더로 복제해 모든 첨부파일과 링크를 하나씩 열어 보는 실전 복원 검증은 아직 남아 있다. 대표 노트를 새 환경에 복원했을 때 본문과 첨부 이미지, 내부 링크, 편집기 설정이 어디까지 온전히 돌아오는지 직접 확인하는 작업이 다음 과제다. 이어지는 글에서는 명함 CMS에서 편집한 내용이 미리보기와 배포를 거쳐 공개 화면에 반영되는 과정을 다룬다.
