블로그 글을 관리 프로그램으로 불러오거나 새 문서로 옮기다 보면, 본문은 남아도 원래 글의 주소나 통계 숫자의 출처가 끊기기 쉽다. 화면에 적힌 숫자가 실제 서버의 값인지, 새로 묶은 문서에 원래 글이 빠짐없이 들어갔는지 확인하려면 결과물과 함께 출처를 남겨야 한다.


데이터에 출처와 상태를 남기는 방법을 두 코드 저장소를 읽으며 비교했다. 데스크톱 프로그램인 `Tistory_Dashboard`(`83f2712` 커밋)는 서버에서 블로그 글과 통계를 불러와 관리한다. 문서 저장소인 `blog_renew-archive`(`f31822f` 커밋)는 옛 개념 정리 글을 주제별 Markdown 문서로 다시 묶은 자료다. 두 저장소가 서로 연결된 자동 이전 시스템이라는 전제는 두지 않았다. 서버에서 자료를 받아 오는 도구와 여러 원문을 다시 묶는 문서에서 각각 조회 상태와 원문 출처를 어떻게 남기는지 대조했다.


## 데스크톱 화면과 서비스 호출 분리


먼저 `Tistory_Dashboard`가 블로그 서버에서 글 목록과 통계를 어떤 경로로 가져오는지부터 확인했다. 이 도구는 웹 기술로 데스크톱 프로그램을 만드는 Electron 기반 애플리케이션이다. Electron에서는 화면을 그리는 실행 단위인 프로세스와 실제 시스템 작업을 처리하는 메인 프로세스가 나뉘어 있다. 두 프로세스는 **IPC**(Inter-Process Communication, 프로세스 간 통신)로 메시지를 주고받는다. 예를 들어 [preload 코드](https://github.com/NAMUORI00/Tistory_Dashboard/blob/83f271276b34d6482b077aebe3d0ff047b07051f/src/preload/index.ts)는 `getPosts`, `getPost`, `getBlogSummary` 같은 조회 메서드를 이 IPC 호출에 연결하고 있었다. 화면에서 요청을 보내면 메인 프로세스의 서비스가 선택된 블로그의 자료를 서버에서 가져온다.


화면과 메인 프로세스 사이에 별도 통로를 두는 이유는 실행 권한을 분리하기 위해서다. [Electron의 context isolation 문서](https://www.electronjs.org/docs/latest/tutorial/context-isolation)는 사전 연결 코드인 `preload` 스크립트와 웹 화면의 실행 문맥을 나누고, 필요한 기능만 `contextBridge`로 노출하는 방식을 안내한다. 화면에 임의의 작업 권한을 한꺼번에 넘기지 않고 허용할 요청의 범위만 제한하는 경계가 된다.


이 경계를 넘어 메인 프로세스로 들어온 요청 가운데 [글 목록 수집](https://github.com/NAMUORI00/Tistory_Dashboard/blob/83f271276b34d6482b077aebe3d0ff047b07051f/src/main/services/tistory/posts.ts)의 `getPosts`는 페이지를 차례대로 돌며 글 목록을 모은다. 응답에 담긴 전체 글 개수에 도달하거나 더 이상 항목이 없으면 순회를 멈추고, 반복 상한은 100페이지로 제한한다. 반복 상한이 정해져 있기 때문에, 반환된 목록에 모든 글이 들어 있는지는 응답의 총개수와 실제 수집 범위를 대조해야 알 수 있다.

## 조회 실패와 숫자 0의 구분


글 목록에 이어 방문자 수나 전체 글 개수 같은 통계 숫자를 가져올 때도 값의 출처를 함께 확인해야 한다. [방문과 글 통계 수집](https://github.com/NAMUORI00/Tistory_Dashboard/blob/83f271276b34d6482b077aebe3d0ff047b07051f/src/main/services/tistory/summary.ts) 코드는 방문자 수의 초기값을 아직 값이 없다는 뜻인 `null`로 둔다. 그 뒤 블로그 관리 화면과 통계 화면에서 읽어 온 수치를 `visitorSource`라는 출처 정보와 함께 돌려준다.


전체 글 개수를 조회할 때도 결과 숫자가 0이면 실제로 작성한 글이 없는 것인지, 조회에 실패해 0이 채워진 것인지 숫자만으로는 구별할 수 없다. 코드는 조회 경로에 따라 출처 필드를 `blog-info-api`, `session-cache`, `unavailable` 세 가지로 나누어 이 문제를 다룬다. 서버의 조회 창구인 **API**로 값을 받아 오면 `blog-info-api`를 남기고, 실패하면 접속 중 임시로 저장한 **세션 캐시**(`session-cache`) 값으로 대체한다. 출처가 조회 불가를 뜻하는 `unavailable`일 때 숫자 필드가 0으로 채워지는 경로가 있어서, 화면에서는 숫자와 출처 정보를 함께 확인해야 두 상태를 구분할 수 있다.


또한 관리 화면에서 수치를 읽어 오는 코드는 Tistory 화면의 구조나 문구가 바뀌면 추출 조건이 맞지 않을 수 있다. 이번에는 실제로 로그인해 통계를 조회하지 않고 코드만 읽었기 때문에, 현재 Tistory 환경에서도 그대로 동작하는지는 직접 실행해 확인해야 한다.


![통계 및 글 개수 조회 시 blog-info-api, session-cache, unavailable 세 경로에 따라 수치를 반환하고 출처 표시로 실제 숫자 0과 조회 실패를 구분하는 다이어그램](/images/notion/tech-11-06/image-2.png)

## 편집기 표현과 원격 저장 상태의 구분


통계 수치뿐 아니라 글 본문을 읽고 수정할 때도 화면에 보이는 값과 실제 서버에 반영된 상태를 구분해야 한다. Tistory 본문에는 웹 문서 표준인 일반 HTML 태그 외에 Tistory 고유의 이미지 삽입 표기가 함께 들어갈 수 있다. [게시글 본문 형식 변환](https://github.com/NAMUORI00/Tistory_Dashboard/blob/83f271276b34d6482b077aebe3d0ff047b07051f/src/shared/tistoryContent.ts) 코드는 편집기 안에서 다루는 화면용 표현과 서버에 제출할 표현을 나누어 관리한다. 편집기에서 미리보기 이미지로 보여 주던 부분도 서버에 저장할 때는 원래의 Tistory 삽입 표기로 되돌린다.


글을 불러올 때도 서버의 정보를 어디까지 읽었는지에 따라 돌려주는 결과가 달라진다. 코드는 먼저 글 제목이나 번호 같은 기본 정보인 **메타데이터**(metadata)를 가져온 뒤 편집 상태를 추가로 읽는다. 이때 편집 상태를 읽지 못하면 메타데이터만으로 만든 결과를 돌려주는 대체 경로가 있었다. 따라서 목록에서 글 제목이 보이는 상태와 실제로 편집할 수 있는 전체 본문을 확보한 상태는 서로 다르다.


글을 저장한 뒤에도 서버 응답의 실패 여부와 글 ID를 확인하고 메타데이터를 다시 조회한다. 만약 이 재조회가 끝내 실패하면, 방금 내 컴퓨터에서 제출한 값으로 묶어 만든 **대체 객체**(`fallback`)를 반환한다. 대체 객체는 로컬에서 보낸 값을 그대로 담은 것이라 실제 서버에 저장된 본문과 일치한다고 보장할 수 없다. 저장 결과가 재조회까지 마친 값인지 대체 객체인지 구분하고, 필요하다면 본문과 이미지, 공개 상태를 다시 읽어 확인해야 한다.


![편집기 본문의 미리보기 이미지를 제출용 삽입 표기로 변환해 원격 저장한 뒤 재조회 성공 시 원격 확인 결과를, 실패 시 제출값 fallback을 반환하는 흐름도](/images/notion/tech-11-06/image-3.png)

## 주제별 문서 재구성과 원문 출처 대조


데스크톱 도구가 API 조회와 화면 추출의 출처를 데이터에 남긴다면, 기존 블로그 글을 새로 묶는 작업에서는 원문과의 대응 기록이 출처가 된다. [blog_renew-archive의 README](https://github.com/NAMUORI00/blog_renew-archive/blob/f31822f81a053f47759135cdaf26f0751a7e9d6c/README.md)에는 한반가 블로그의 개념 정리 글을 바탕으로 재구성한 자료라는 출처가 적혀 있다. 이 저장소에는 `README.md`를 포함해 파일 28개가 들어 있으며, 자료구조, 응용확률론, 객체지향 프로그래밍, 화일처리 네 가지 주제별 문서로 나뉘어 있다.


여러 원문을 주제별로 합칠 때는 문서에 남겨 둔 원본 글 번호가 연결 단서가 된다. 예를 들어 첫 번째 자료구조 문서에는 원본의 '공부 #1'과 '공부 #2'를 함께 다룬다는 표시가 남아 있다. 이처럼 원문 여러 편을 하나의 주제 문서로 묶을 때는 원문 개수와 새 문서 개수만 비교해서는 빠진 내용을 찾을 수 없다. 어떤 원문이 새 문서의 어느 절로 들어갔는지 대응 관계를 따라가야 누락 여부를 확인할 수 있다.


다만 합친 글 번호만 적어 둔 상태에서는 문단이나 코드, 그림 단위의 대조까지 끝나지 않는다. 예를 들어 원문 A의 그림을 새 문서 두 번째 절로 옮겼다면, 그 절 가까이에 원문 주소와 그림 출처를 적어 두어야 글 제목이 바뀌어도 원래 설명을 찾아갈 수 있다. 그림을 넣을 때도 외부 이미지 주소를 참조했는지 저장소에 파일로 보관했는지 구분해 두면 이미지가 깨졌을 때 원인을 찾기 쉽다. 이번에는 원문 사이트의 내용을 직접 대조하지 못했기 때문에, 이 저장소가 원문 전체를 빠짐없이 옮긴 상태인지는 아직 확인하지 못했다.

## 결론


지금까지 두 저장소의 코드를 통해 데이터와 문서의 출처를 남기는 방식을 비교했다. `Tistory_Dashboard`는 화면의 요청과 서버 조회 상태를 연결하고, `blog_renew-archive`는 여러 원문과 재구성한 주제 문서를 연결한다. 다루는 대상은 다르지만 결과물만 남기지 않고 원래 상태나 출처를 다시 확인할 경로를 함께 둔다는 점은 같다.


다만 코드와 문서만 읽었기 때문에, 실제 로그인 환경에서 통계 추출이 그대로 동작하는지와 새 문서가 원문 전체를 빠짐없이 옮겼는지는 아직 확인하지 못했다. 다음 글에서는 문서 내용뿐 아니라 파일을 고친 이유를 Git 커밋에 남기는 도구를 이어서 다룬다.
