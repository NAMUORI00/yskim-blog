블로그 관리와 기존 글 정리 작업에서 요청, 원격 상태, 원문 출처를 연결했다. Tistory_Dashboard는 서비스 자료를 가져오는 경로로, blog_renew-archive는 여러 원문을 주제별로 재구성하는 사례로 나누어 정리했다.


## 구현과 확인 과정


Tistory_Dashboard와 blog_renew-archive 두 저장소를 읽으며, 서비스 자료를 가져오는 쪽과 기존 글을 주제별로 정리하는 쪽에서 원문 출처를 각각 어떻게 남기는지 살펴봤다. 글을 새 문서로 옮기면 본문은 남아도 원래 링크나 통계의 출처가 끊길 수 있어서, 두 저장소를 하나의 이전 시스템으로 가정하지 않고 추적 방법을 비교했다.


Tistory_Dashboard는 83f2712 커밋, blog_renew-archive는 f31822f 커밋을 기준으로 읽었다. 전자는 글과 통계를 다루는 데스크톱 도구이고, 후자는 기존 개념 글을 주제별 Markdown 문서로 정리한 자료다. 두 저장소가 연결된 자동 이전 시스템이라는 전제는 두지 않았고, 각각의 입력과 결과에서 출처가 어떤 형태로 남는지를 비교 대상으로 삼았다.


## 데스크톱 화면과 실제 서비스 호출을 나누기


Tistory_Dashboard의 [preload 코드](https://github.com/NAMUORI00/Tistory_Dashboard/blob/83f271276b34d6482b077aebe3d0ff047b07051f/src/preload/index.ts)는 getPosts, getPost, getBlogSummary 같은 메서드를 IPC 호출에 연결한다.


IPC는 Electron의 화면 프로세스와 메인 프로세스가 메시지를 주고받는 경로다. 코드를 보면 화면에서 요청이 오면 메인 쪽 서비스가 선택한 블로그의 자료를 가져오는 구조였다.


[Electron의 context isolation 문서](https://www.electronjs.org/docs/latest/tutorial/context-isolation)에서는 preload와 웹 콘텐츠의 실행 문맥을 나누고 필요한 기능만 contextBridge로 노출하는 방식을 설명한다. 화면에 임의의 작업 권한을 한꺼번에 전달하는 대신, 허용할 요청의 범위를 정하는 경계에 해당한다.


[글 목록 수집](https://github.com/NAMUORI00/Tistory_Dashboard/blob/83f271276b34d6482b077aebe3d0ff047b07051f/src/main/services/tistory/posts.ts)의 getPosts는 페이지를 순회해 목록을 모은다.


응답의 총개수에 도달하거나 항목이 없으면 멈추며, 반복 상한도 100페이지로 두고 있다. 반환된 목록이 실제로 모든 글을 포함하는지는 총개수와 수집 범위를 대조해야 알 수 있다.

## 조회 실패와 숫자 0의 표시


[방문과 글 통계 수집](https://github.com/NAMUORI00/Tistory_Dashboard/blob/83f271276b34d6482b077aebe3d0ff047b07051f/src/main/services/tistory/summary.ts)은 방문자 수의 초기값을 null로 둔다.


관리 화면과 통계 화면에서 수치를 찾아 visitorSource로 출처를 함께 돌려준다. 글 개수는 API 조회가 가능하면 그 값을 쓰고, 불가능하면 세션에 저장된 값으로 돌아가는 경로가 있었다.


출처에는 blog-info-api, session-cache, unavailable 같은 구분이 있다. unavailable일 때 숫자 필드가 0으로 채워지는 경로도 있어서, 숫자 0만으로는 실제 글이 없는 것인지 조회에 실패한 것인지 알 수 없다. 화면에서 이 둘을 구분하려면 출처 정보를 함께 확인해야 한다.


관리 화면에서 읽는 수치는 화면 구조나 문구가 바뀌면 추출 조건도 달라질 수 있다. 현재 Tistory 환경의 동작 여부는 해당 환경에서 실행해 확인해야 한다. 이번에는 로그인이나 실제 통계 조회 없이 코드만 읽은 범위의 기록이다.


## 편집기 표현과 제출할 원문을 구분하기


본문에는 일반 HTML뿐 아니라 Tistory의 이미지 삽입 표기가 들어갈 수 있다. [게시글 본문 형식 변환](https://github.com/NAMUORI00/Tistory_Dashboard/blob/83f271276b34d6482b077aebe3d0ff047b07051f/src/shared/tistoryContent.ts)에서는 편집기에서 저장할 표현과 제출할 표현을 구분하고 있었다. 미리보기 이미지를 원래 삽입 표기로 되돌리는 처리도 이 경계에서 이루어진다.


글을 조회할 때는 메타데이터를 가져온 뒤 편집 상태를 추가로 읽는다. 편집 상태를 읽지 못하면 메타데이터 기반 결과만 반환하는 대체 경로가 있었다. 목록에서 제목이 보이는 상태와 편집 가능한 전체 본문을 확보한 상태는 서로 다르다.


저장 후에도 응답의 실패 상태와 글 ID를 확인하고 메타데이터를 다시 조회한다. 재조회가 끝내 성공하지 못하면 제출값으로 만든 fallback 객체를 반환하는 경로가 있었다. 이 fallback은 실제 원격 본문과 완전히 일치한다는 보장이 없으므로, 본문, 이미지, 공개 상태를 따로 읽어 확인하는 작업이 남아 있다.


## 원문 여러 편을 주제 하나로 정리할 때


[blog_renew-archive의 README](https://github.com/NAMUORI00/blog_renew-archive/blob/f31822f81a053f47759135cdaf26f0751a7e9d6c/README.md)에는 한반가 블로그의 개념정리 글을 바탕으로 재구성한 자료라는 출처가 적혀 있었다.


저장소에는 README를 포함해 28개 파일이 있었고, 자료구조, 응용확률론, 객체지향 프로그래밍, 화일처리라는 주제별 문서로 나뉘어 있었다.


첫 자료구조 문서에는 원본의 공부 #1과 #2를 함께 다룬다는 표시가 있었다. 여러 원문을 하나의 주제 문서로 묶는 구조이므로, 누락 여부는 원문별 대응 관계로 확인해야 한다.


다만 이 표시만으로 문단, 코드, 그림 단위의 원문 대조가 끝나지는 않는다. 이번에는 원문 사이트 내용을 직접 대조하지 못했으므로, 이 저장소가 원문 전체의 완전한 복제인지는 확인되지 않은 상태다.

## 문서 이전 후 확인 항목


예를 들어 원문 A의 그림이 새 문서의 두 번째 절에 들어갔다면, 원문 주소와 그림 출처를 그 절 가까이에 남겨 두면 글 제목이 바뀌어도 독자가 원래 설명으로 돌아갈 수 있다. 외부 이미지 주소를 참조한 것인지 파일 자체를 보관한 것인지를 구분해 두면 나중에 깨진 그림의 원인을 추적하기 쉽다.


대시보드는 요청과 원격 상태를, 아카이브는 원문과 재구성 문서를 연결한다. 두 작업 모두 결과물을 만드는 것에 더해 다시 확인할 경로를 함께 남긴다는 점이 공통적이었다. 다음 글에서는 파일의 변경 내용뿐 아니라 그 변경 이유를 Git 커밋에 남기는 작은 도구를 살펴본다.


## 작업을 정리하며


글을 옮기는 작업에서도 다시 확인할 원문 경로가 필요하다. 여러 글을 합쳤다면 원문 수와 문서 수를 비교하는 대신 대응표로 누락을 확인하는 편이 정확하다. 요청 결과와 출처 연결을 함께 남기는 방식이 두 작업의 공통 기준이다.
