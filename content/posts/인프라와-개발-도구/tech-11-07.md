커밋 메시지 작성에 사용할 템플릿과 등록 스크립트를 정리했다. 변경 내용과 이유를 나중에 다시 찾을 수 있도록 유형, 제목, 본문의 역할을 나누고 운영체제별 등록 경로를 구성했다.


## 구현과 확인 과정


CommitConvention 저장소를 살펴보며 커밋 메시지 템플릿의 구성과 등록 방식을 정리해 봤다. 제한값을 20에서 50으로 바꾼 diff만으로는 더 많은 결과가 필요했는지, 임시 검증용 변경인지 구분되지 않는다. 이 저장소는 커밋 편집기에 템플릿을 띄워 변경 이유를 코드와 별도로 기록할 수 있게 한다.


fd64795 커밋의 README에는 개발 환경을 바꾸거나 컴퓨터를 다시 설치할 때마다 커밋 메시지 양식을 찾아오는 번거로움을 줄이려고 저장소를 만들었다고 적혀 있었다. 선택 이유가 기록으로 남아 있는 경우였다. 구성도 복잡한 서비스 없이 템플릿 파일 하나와 등록 스크립트만으로 되어 있었다.


## 변경 내용과 이유의 기록


Git의 diff는 어떤 줄이 바뀌었는지 보여 준다. 똑같이 제한값을 20에서 50으로 바꿔도 이유는 여러 가지일 수 있다. 더 많은 결과가 필요해서인지, 화면에서 페이지를 나누기로 해서인지, 임시 검증을 위한 변경인지 숫자만으로는 구분되지 않는다.


[커밋 메시지 양식](https://github.com/NAMUORI00/CommitConvention/blob/fd64795dba1b4eb16c4b49135e18ace3971f9dad/gitmessage.txt)은 제목, 본문, 꼬리말을 나누고 본문에서 무엇을, 왜, 어떻게 수정했는지 적도록 안내한다. 제목에는 변경의 방향을 짧게, 본문에는 diff에서 읽기 어려운 이유를 두는 구성으로 이해했다.


아래는 형식을 설명하기 위한 가상 예제다. 수정과 검증 내용을 커밋 메시지에 기록하는 방법을 보여 주는 가상 예제다.


```plain text
fix: 검색 목록의 다음 페이지 연결 수정

첫 페이지 뒤의 결과를 열 수 없어 탐색이 중단됐다.
응답의 다음 페이지 커서를 요청에 전달하도록 바꿨다.
빈 결과와 마지막 페이지에서는 추가 요청을 만들지 않는다.
```


이 예제 메시지에는 변경 전 문제, 선택한 방식, 경계 조건이 들어 있다. 함수 이름을 모두 나열하지 않아도 선택의 배경을 다시 읽을 수 있는 형태다. 실제 테스트 결과는 별도의 확인 기록이 있을 때 덧붙일 내용으로 남겨 두었다.

## 커밋 템플릿 등록과 적용


[유닉스 계열 설치 스크립트](https://github.com/NAMUORI00/CommitConvention/blob/fd64795dba1b4eb16c4b49135e18ace3971f9dad/run.sh)와 [Windows 설치 스크립트](https://github.com/NAMUORI00/CommitConvention/blob/fd64795dba1b4eb16c4b49135e18ace3971f9dad/run.bat)는 모두 commit.template에 커밋 메시지 양식을 전역 설정한다. 파일을 복사하거나 각 저장소에 검사 규칙을 설치하는 동작은 없다.


[Git 설정 문서](https://git-scm.com/docs/git-config#Documentation/git-config.txt-committemplate)에 따르면 commit.template은 새 커밋 메시지에 사용할 템플릿 파일 경로다.


이 저장소의 스크립트에는 파일 이름만 들어 있어서, 다른 프로젝트에서 사용할 때 해당 파일을 찾을 수 있는 경로인지가 관건이 된다. 환경을 복원하는 상황에서는 설정값이 존재하는 것과 실제 템플릿 파일을 읽을 수 있는 상태가 별개이므로 따로 점검할 지점이 있다.


전역 설정은 한 저장소에만 적용하는 설정과 범위가 다르다. 여러 작업에서 같은 양식을 쓰기에는 편하지만, 프로젝트별 규칙이 있으면 충돌 여부를 확인할 부분이 생긴다. 이번에는 스크립트를 읽는 데 그쳤고 현재 컴퓨터의 전역 Git 설정은 바꾸지 않았다.


## 템플릿 안내와 형식 검사의 범위


[git commit 문서](https://git-scm.com/docs/git-commit)는 템플릿을 편집기의 시작 내용으로 설명한다. 메시지를 다른 방식으로 전달하는 -m이나 -F 옵션에는 이 템플릿이 영향을 주지 않는다. 작성자는 등록한 양식을 참고해 각 커밋 메시지를 구성한다.


템플릿의 안내 줄은 #으로 시작한다. 기본 편집 모드에서는 주석이 제거되지만 cleanup이나 주석 문자 설정에 따라 달라질 수 있다. 안내문이 최종 기록에 남는지는 사용 환경에서 확인할 항목이다. 제목 길이와 본문 줄 길이는 작성자가 적용할 템플릿 지침으로 제시됐다.

그림 2. 템플릿을 사용하는 편집 경로와 직접 메시지를 전달하는 경로. 출처: 저장소의 등록 스크립트와 Git 공식 문서를 바탕으로 직접 구성. 별도의 형식 검사기는 이 저장소에 포함되어 있지 않다.


## 개인 규칙과 도구가 이해하는 규칙


템플릿에는 feat, fix, docs, refactor뿐 아니라 post, rename, remove와 대소문자가 다른 일부 항목도 들어 있었다. 블로그 작성이나 파일 이동을 별도로 찾으려는 개인 분류로 보인다. 외부 자동화 도구가 이 이름들을 어떻게 해석하는지는 별개 문제다.


[Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/)도 feat와 fix 외의 유형을 허용하지만, 추가 유형에 자동적인 버전 증가 의미를 부여하지는 않는다.


이 저장소의 목록을 사용한다는 사실만으로 변경 로그 생성이나 릴리스 버전 계산이 구성되어 있다고 볼 수는 없었다. 자동화를 붙이려면 허용할 유형 목록과 호환성 변경 표기를 먼저 맞출 부분이 있다.


## 다시 읽을 수 있는 정도의 기록


이 저장소에서 확인한 구현은 작은 템플릿 하나와 두 운영체제용 등록 스크립트였다. 기록된 목적에 비춰 보면 양식을 다시 찾아오는 일을 줄이는 데 집중한 구성이었다. 커밋 분할과 설명의 사실 확인은 작성자가 맡는다.


이 양식을 검토하며 남긴 기준은 제목으로 변경을 구분할 수 있는지, 본문에서 이유를 다시 찾을 수 있는지였다. 이어지는 데이터 자동화 글에서는 값의 변화를 추적하는 수집 시각, 기준 날짜, 변환 규칙을 살펴본다.


## 작업을 정리하며


짧은 커밋 제목이 작업을 식별하고 본문이 선택 이유를 설명하면 이력을 다시 읽기 쉽다. 양식은 그 기록을 돕는 틀이므로 실제 변경 범위와 검증 결과를 작성자가 채워야 한다. 작은 도구라도 이후의 확인 비용을 줄이는 방향으로 평가하고 싶다.
