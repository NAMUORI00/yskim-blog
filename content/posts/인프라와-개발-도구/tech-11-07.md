조회 결과 제한값을 20에서 50으로 바꾼 코드가 있을 때, 변경 전후를 줄 단위로 비교하는 `git diff`는 숫자가 달라진 줄만 보여 준다. 숫자만 봐서는 한 번에 더 많은 결과가 필요했는지, 화면의 페이지 분할 방식을 바꿨는지, 테스트하려고 임시로 늘려 둔 것인지 구분할 수 없다. 버전 관리 도구인 Git에서 변경 내역을 한 묶음으로 저장하는 **커밋**(commit)을 만들 때는 코드와 별도로 설명 글인 커밋 메시지를 남긴다. 코드만으로는 드러나지 않는 판단 근거를 이 메시지에 적어 두어야 나중에 이력을 다시 읽을 때 맥락을 파악할 수 있다.


개인 저장소인 CommitConvention의 `fd64795` 커밋 README에는 이 저장소를 만든 이유가 적혀 있다. 컴퓨터를 다시 설치하거나 개발 환경을 옮길 때마다 커밋 메시지 양식을 찾아오는 번거로움을 줄이려는 목적이다. 별도의 서비스나 복잡한 도구 없이, 미리 정해 둔 입력 양식인 **커밋 템플릿**(commit template) 파일 하나와 운영체제별 등록 스크립트 두 개만 두었다. 이 저장소의 파일들과 Git 공식 문서를 함께 읽으며, 양식이 변경 이유를 기록하도록 돕는 방식과 실제 환경에 등록할 때 따져 봐야 할 조건을 짚어 보았다.


## 변경 내용과 변경 이유의 분리


변경 이유를 빠뜨리지 않고 적으려면 먼저 메시지 안에 무엇을 채울지 자리가 정해져 있어야 한다. 저장소의 [커밋 메시지 양식](https://github.com/NAMUORI00/CommitConvention/blob/fd64795dba1b4eb16c4b49135e18ace3971f9dad/gitmessage.txt)인 `gitmessage.txt`는 작성할 글을 제목, 본문, 꼬리말 세 영역으로 나눈다. 맨 위 제목에는 작업 유형과 변경 방향을 짧게 적고, 본문에는 무엇을, 왜, 어떻게 수정했는지 풀어 적도록 안내한다. 제목의 글자 수 제한이나 본문의 줄바꿈 길이도 작성자가 참고할 지침으로 적혀 있다. `git diff`가 코드의 변경 결과를 남긴다면, 커밋 메시지 본문은 코드에 드러나지 않는 문제 상황과 선택 이유를 남기는 역할을 맡는다.


![이전 코드와 수정한 코드의 줄 단위 비교에서 나오는 '무엇이 바뀌었는가'와 문제, 제약, 판단에서 나오는 '왜 이렇게 바꿨는가'가 합쳐져 커밋 기록에 저장되는 흐름도](/images/notion/tech-11-07/image-1.png)


그림 1. 코드 비교(diff)가 보여 주는 변경 내용과 작성자가 템플릿에 기록하는 변경 이유가 합쳐져 커밋 기록이 되는 구조(직접 구성).


아래는 검색 결과 화면에서 다음 페이지가 열리지 않던 문제를 고쳤다고 가정하고, 이 양식에 맞춰 수정 배경과 확인 범위를 적은 가상 예제다.


```plain text
fix: 검색 목록의 다음 페이지 연결 수정

첫 페이지 뒤의 결과를 열 수 없어 탐색이 중단됐다.
응답의 다음 페이지 커서를 요청에 전달하도록 바꿨다.
빈 결과와 마지막 페이지에서는 추가 요청을 만들지 않는다.
```


이 예제 메시지는 본문 첫 문장에서 수정 전의 문제를 밝히고, 둘째 문장에서 서버가 알려 준 다음 페이지 위치(커서)를 요청에 넘기는 해결 방식을 설명한다. 마지막 문장에서는 검색 결과가 비어 있거나 마지막 페이지에 닿았을 때처럼 끝부분에서 추가 요청을 멈추는 경계 조건을 덧붙인다. 수정한 함수 이름을 일일이 나열하지 않아도 왜 이런 방식으로 코드를 바꿨는지 다시 읽을 수 있다. 실제 테스트 결과는 별도의 확인 기록이 있을 때 덧붙일 내용으로 남겨 두었다.


## 커밋 유형 분류와 외부 도구 호환성


본문이 변경 이유를 담는다면, 제목 맨 앞에 붙이는 커밋 유형은 쌓인 이력을 나중에 분류하고 검색하는 기준이 된다. `gitmessage.txt`에는 기능 추가(`feat`), 오류 수정(`fix`), `docs`, `refactor`처럼 흔히 쓰이는 항목이 들어 있다. 여기에 더해 `post`, `rename`, `remove` 같은 항목도 있고, 대소문자 표기가 다른 항목도 섞여 있다. 블로그 글 작성이나 파일 이름 변경, 파일 삭제를 이력에서 따로 걸러 보려는 개인 분류로 보였다.


커밋 메시지 형식을 정한 공개 규칙인 [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/) 문서도 `feat`와 `fix` 외에 작성자가 정한 추가 유형을 허용한다. 다만 추가 유형에는 프로그램의 버전 번호를 자동으로 올리는 의미를 부여하지 않는다.


![gitmessage.txt 양식의 제목 유형 중 기본 유형(feat, fix)과 개인 유형(post, rename)은 모두 사람의 이력 검색에 쓰이지만, 외부 버전 자동화 도구에는 기본 유형만 연결되는 구조도](/images/notion/tech-11-07/image-2.png)


그림 2. gitmessage.txt 양식의 영역별 구성과 커밋 유형이 개인 이력 검색 및 외부 자동화 도구에 적용되는 범위 비교.


사람이 직접 커밋 기록을 읽을 때는 `post`나 `rename` 같은 유형이 작업을 구분하는 데 도움을 준다. 반면에 버전마다 바뀐 점을 모은 **변경 로그**(changelog)를 자동으로 생성하거나 릴리스 버전을 계산하는 외부 도구를 붙이려면 사정이 다르다. 도구가 인식할 유형 목록과 대소문자 규칙, 이전 버전과 호환되지 않는 큰 변경인 하위 호환성 변경(breaking change) 표기 방식을 먼저 맞춰야 한다. 따라서 이 저장소의 템플릿을 쓴다는 사실만으로 배포나 버전 자동화 준비가 끝났다고 볼 수는 없다.


## 전역 등록 스크립트와 파일 경로 조건


양식의 항목 구성을 정했더라도, 새 커밋을 만들 때마다 Git이 이 양식을 불러오게 하려면 설정에 파일 경로를 등록해야 한다. 저장소에 들어 있는 [유닉스 계열 설치 스크립트](https://github.com/NAMUORI00/CommitConvention/blob/fd64795dba1b4eb16c4b49135e18ace3971f9dad/run.sh)와 [Windows 설치 스크립트](https://github.com/NAMUORI00/CommitConvention/blob/fd64795dba1b4eb16c4b49135e18ace3971f9dad/run.bat)는 모두 Git의 `commit.template` 항목에 양식 파일을 등록한다. 이때 컴퓨터 안의 모든 저장소에 공통으로 적용하는 **전역 설정** 옵션을 사용한다. 템플릿 파일을 시스템의 특정 폴더로 복사하거나 각 저장소에 형식 검사 규칙을 설치하는 동작은 없다. 이번에는 스크립트 내용만 확인했고, 현재 작업 중인 컴퓨터의 전역 Git 설정은 바꾸지 않았다.


[Git 설정 문서](https://git-scm.com/docs/git-config#Documentation/git-config.txt-committemplate)를 보면 `commit.template`은 새 커밋 메시지를 작성할 때 편집기에 불러올 파일 경로를 뜻한다. 그런데 이 저장소의 등록 스크립트에는 최상위 폴더부터 파일 위치를 끝까지 적은 고정 **절대 경로**가 아니라 `gitmessage.txt`라는 파일 이름만 적혀 있다.


![전역 설정에 파일 이름만 넣으면 다른 프로젝트 폴더에서 탐색에 실패하고, 고정 절대 경로를 넣으면 템플릿 파일 로드에 성공하는 비교도](/images/notion/tech-11-07/image-3.png)


그림 3. 전역 commit.template 설정에 파일 이름만 넣었을 때와 고정 절대 경로를 넣었을 때 다른 프로젝트 폴더에서 템플릿을 불러오는 결과 비교.


전역 설정에 파일 이름만 들어가 있으면, 다른 프로젝트 폴더에서 커밋을 실행할 때 Git이 그 프로젝트 폴더 안에서 `gitmessage.txt`를 찾게 된다. 해당 폴더에 파일이 없으면 템플릿을 불러오지 못한다. 새 컴퓨터에서 개발 환경을 복원할 때는 전역 설정값이 들어 있는지만 볼 것이 아니라, 어느 저장소에서든 그 경로의 템플릿 파일을 실제로 읽을 수 있는지 함께 확인해야 한다. 또한 전역 설정은 컴퓨터 안의 모든 저장소에 똑같이 적용되므로, 팀이나 프로젝트마다 별도의 커밋 규칙이 있다면 저장소 단위 설정과 충돌하지 않는지도 따져 봐야 한다.


## 편집기 실행 경로와 주석 처리 범위


파일 경로를 바르게 등록했더라도 모든 커밋 명령에서 템플릿이 열리는 것은 아니다. [git commit 문서](https://git-scm.com/docs/git-commit)는 템플릿을 커밋 편집기의 초기 내용으로 설명한다. `git commit` 명령으로 텍스트 편집기 창을 띄울 때만 `gitmessage.txt`의 내용이 화면에 미리 채워진다. 명령줄에서 `-m` 옵션으로 짧은 메시지를 바로 넘기거나 `-F` 옵션으로 다른 파일을 지정해 커밋할 때는 등록해 둔 템플릿이 개입하지 않는다.


편집기에 불러온 템플릿의 안내문은 각 줄이 `#` 기호로 시작한다. Git의 기본 편집 모드에서는 커밋을 저장할 때 `#`으로 시작하는 **주석**(comment) 줄을 자동으로 지우므로 안내문은 최종 커밋 기록에 남지 않는다. 다만 Git의 메시지 정리 설정인 `cleanup` 옵션이나 주석 문자 설정(`core.commentChar`)을 바꾼 환경에서는 주석 제거 동작이 달라질 수 있다. 따라서 안내문이 실제 기록에 남지 않는지 사용 환경에서 한 번 확인해 두는 편이 안전하다.


![commit.template 설정을 통해 편집기에서 이유를 입력하고 주석을 제거하는 경로와 -m, -F 옵션으로 직접 메시지를 전달하는 경로가 최종 커밋 메시지로 모이는 흐름도](/images/notion/tech-11-07/image-4.png)


그림 4. 템플릿을 불러오는 편집기 실행 경로와 템플릿을 건너뛰는 직접 메시지 전달(-m, -F) 경로 비교(저장소 스크립트와 Git 공식 문서를 바탕으로 직접 구성).


## 결론


CommitConvention 저장소는 컴퓨터를 옮길 때마다 양식을 다시 찾아오는 수고를 덜기 위해 템플릿 파일 하나와 등록 스크립트 두 개만 남긴 단출한 형태다. 이번 검토에서는 저장소 파일과 Git 공식 문서를 읽으며 양식이 변경 이유를 남기는 방식과 등록 조건을 확인했다. 작업 중인 컴퓨터의 전역 설정은 직접 바꾸지 않았으며, 다른 폴더에서의 경로 접근이나 주석 제거 동작은 실제 적용 환경에서 따로 확인해야 한다. 또한 커밋 메시지 형식을 강제하는 검사기가 없으므로, 작업을 적절한 단위로 쪼개고 변경 이유와 검증 결과를 채워 넣는 일은 작성자의 몫으로 남는다.


이 양식을 검토하며 세운 기준은 제목만으로 어떤 변경인지 식별할 수 있는가, 그리고 본문에서 당시의 선택 이유를 다시 찾을 수 있는가 하는 두 가지다. 코드 변경에서 이유를 남기는 기준을 확인했으니, 이어지는 데이터 자동화 글에서는 수집 시각과 기준 날짜, 변환 규칙을 기록해 데이터 값의 변화를 추적하는 방법을 다룬다.
