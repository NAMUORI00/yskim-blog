원본 저장소를 통째로 복제한 별도 저장소인 **포크**(fork)에서 작업하다 보면, 내가 직접 고친 범위만 따로 확인해야 할 때가 있다. 이때 현재 포크와 최신 원본을 그대로 비교하면, 포크를 만든 뒤 원본에 추가된 변경까지 결과에 섞일 수 있다. 내가 바꾼 부분만 골라내려면 두 저장소가 갈라지기 직전의 지점인 **공통 조상**(common ancestor)을 기준으로 비교해야 한다. 이 글에서는 작은 예제로 이력이 갈라지는 구조를 짚어 보고, 내가 수정한 범위를 저장소부터 파일과 줄 단위까지 확인하는 방법을 다룬다.


## 포크와 브랜치의 이력 구조


공통 조상을 기준으로 변경 이력을 비교하려면 먼저 원본과 포크에서 작업 기록이 어떻게 갈라지는지 알아야 한다. Git은 코드를 고친 기록을 **커밋**(commit) 단위로 쌓으며, 원본 저장소에 커밋 두 개가 차례로 있는 상황에서 출발한다.


```plain text
커밋 A: README.md 생성 — "프로젝트 소개"
커밋 B: config.json 추가 — {"port": 3000}
```


이 시점에 포크를 만들면 포크 저장소에 커밋 A와 B가 그대로 복제된다. 포크는 원본과 분리된 별도 저장소이므로, 이후 어느 한쪽에서 새 커밋을 추가해도 다른 쪽 저장소에는 반영되지 않는다. 이 상태에서 포크 저장소를 내 컴퓨터인 로컬에 복제(clone)해 설정 파일을 고치는 커밋 C를 하나 추가한다.


```plain text
커밋 C (포크): config.json 수정 — {"port": 8080}
```


한 저장소 안에서 작업 줄기를 나눈 **브랜치**(branch)라면 `main`과 `feature`가 같은 로컬 저장소에 나란히 존재한다. 이때는 `git log main..feature` 한 줄만 실행해도 `feature`에만 있는 커밋 C를 곧바로 확인할 수 있다.


반면 포크는 저장소가 분리되어 있어서 로컬에 원본의 원격 주소(remote)를 등록하고 이력을 가져와야 같은 방식으로 비교할 수 있다. 원격 주소를 한 번 등록해 두면 이후에도 원본 이력을 반복해서 가져와 비교하기 편하다. 원본 저장소를 포크하고 로컬로 복제해 수정한 뒤, 원본의 새 커밋 유무를 확인해 변경을 반영하는 전체 흐름은 다음과 같다.

## 공통 조상 기준 브랜치 비교


포크를 원본과 비교하기에 앞서, 한 저장소 안에 있는 두 브랜치를 비교하는 기본 명령부터 확인한다. 같은 저장소 안에서는 별도 설정 없이 `git log`와 `git diff`만으로 변경 범위를 찾아낼 수 있다.


```bash
# feature에만 있는 커밋
git log main..feature --oneline

# 공통 조상 기준 변경 파일
git diff main...feature --stat
```


`git log`에 적은 `main..feature`는 `main`에는 없고 `feature`에만 있는 커밋 목록을 보여 준다. 파일 내용의 차이를 확인할 때는 `git diff`에 점 세 개(`...`)를 넣어 `main...feature`로 지정한다. 이렇게 쓰면 두 브랜치가 갈라진 공통 조상부터 `feature`의 최신 커밋까지 바뀐 내용만 추려 낸다. 뒤에 `--stat` 옵션을 붙이면 파일마다 추가되고 삭제된 줄 수를 요약해 주어, 어느 파일에 수정이 집중되었는지 한눈에 파악할 수 있다.


여기서 공통 조상 B에서 갈라진 뒤 `main`에 새 커밋 D가 생기고 `feature`에 커밋 C가 생긴 상황을 생각해 볼 수 있다. `git diff main..feature`처럼 점 두 개(`..`)를 쓰면 두 브랜치 끝인 커밋 D와 C의 스냅샷을 직접 비교한다. 그 결과 내가 고치지 않은 `main`의 새 커밋 D까지 차이 목록에 함께 섞여 나온다. 반면 `git diff main...feature`처럼 점 세 개(`...`)를 쓰면 공통 조상인 커밋 B와 `feature` 끝인 커밋 C를 비교한다. 따라서 분기 이후 내 브랜치에서 수정한 내용만 골라 보려면 점 두 개가 아니라 점 세 개(`...`)를 써야 한다.

## 원본 원격 등록과 포크 비교


한 저장소 안에서 브랜치를 비교하던 원리는 분리된 포크 저장소에도 그대로 적용할 수 있다. 포크는 GitHub 같은 코드 호스팅 서비스가 저장소 사이의 복제 관계를 관리하는 기능이다. Git 자체는 로컬에 있는 커밋 이력 구조인 커밋 그래프만 알 뿐, 이 저장소가 어느 원본에서 복제되었는지는 기억하지 않는다. 따라서 로컬 저장소에서 원본과 비교하려면 원본 주소를 원격 저장소(보통 `upstream`)로 직접 등록하고 이력을 가져와야 한다.


```bash
git remote add upstream https://github.com/원본/repo.git
git fetch upstream

git log upstream/main..HEAD --oneline
git diff upstream/main...HEAD
```


`git remote add`는 내 로컬 저장소에 원격 주소를 추가하는 설정일 뿐이므로 원본 서버에는 아무 영향을 주지 않는다. 이어서 `git fetch upstream`을 실행하면 원본의 커밋 이력이 로컬의 `upstream/main` 참조로 내려온다. 이로써 로컬 저장소 안에 원본 이력(`upstream/main`)과 현재 내 작업 이력(`HEAD`)이 모두 모인다. 원본과 포크의 이력을 로컬로 가져온 뒤 앞서 본 브랜치 비교 명령으로 변경분을 추려 내는 흐름은 다음과 같다.

## 파일과 줄 단위 변경 출처 추적


저장소 전체의 변경 목록을 확인한 뒤, 특정 파일의 각 줄이 어느 커밋에서 바뀐 것인지 좁혀 보려면 `git blame`을 사용한다.


```bash
git blame config.json
```


`git blame`의 기본 출력은 파일의 각 줄을 가장 마지막에 고친 커밋과 작성자 정보를 보여 준다. 다만 마지막 수정자가 그 줄의 최초 작성자나 주요 기여자와 항상 같지는 않다. 코드를 다른 곳에서 옮기거나 복사했을 때, 또는 들여쓰기 같은 서식만 바꿨을 때도 마지막 수정 커밋이 덮어써지기 때문이다. 따라서 마지막 작성자 메타데이터만 보고 코드의 원래 출처나 소유권을 단정할 수는 없다.


이럴 때는 [git-blame 문서](https://git-scm.com/docs/git-blame)에 정리된 코드 이동, 복사 추적 옵션을 함께 쓰는 편이 정확하다. 또는 `git log -p -- config.json` 명령으로 파일 하나의 전체 변경 이력을 직접 확인할 수도 있다. `git log -p`에 파일 경로를 넣으면 그 파일을 고친 모든 커밋과 변경 내용이 시간순으로 나와, 변화 과정을 처음부터 따라갈 수 있다.


## 변경 범위 확인과 원본 동기화의 구분


지금까지 본 변경 범위 확인과 달리 원본 저장소의 새 변경을 내 포크에 합치는 동기화는 작업 목적에 따라 구분해야 한다. 포크를 만든 뒤 원본 저장소에 새 커밋 D가 추가되면 내 포크에는 아직 커밋 D가 없는 상태가 된다. 이때 내가 수정한 범위를 읽고 확인만 하려는 목적이라면 두 저장소의 이력을 합칠 필요가 없다. `git fetch upstream`으로 최신 원본 이력만 로컬에 가져오면 내 작업 이력은 그대로 유지된다. 그 상태에서 앞서 본 `git log`와 `git diff`를 실행하면 내 이력을 건드리지 않고도 수정 범위를 바로 확인할 수 있다.


반면 내 변경을 원본에 합쳐 달라고 Pull Request를 보낼 때는 원본의 커밋 D와 내 커밋 C 사이에서 충돌이 생길 수 있다. 이때는 최신 원본을 가져온 뒤 `git rebase upstream/main`을 실행해 갱신된 원본 기반 위에서 내 커밋을 다시 만들 수 있다. 다만 이미 다른 사람과 공유한 커밋을 `rebase`로 다시 쓰면 협업 중인 기준 이력이 서로 달라질 위험이 있다. 여러 사람이 공유하는 브랜치라면 기존 커밋 이력을 그대로 유지하면서 합치는 `merge`가 안전한 대안이 된다.


## 결론


브랜치나 포크에서 내가 직접 수정한 범위만 골라내려면 최신 원본이 아니라 두 이력이 갈라진 공통 조상을 기준으로 비교해야 한다. 포크 저장소라도 원본을 원격 저장소로 등록해 이력을 로컬로 가져오면 내 작업 이력을 건드리지 않고 비교할 수 있다. `git log`와 점 세 개(`...`)를 쓴 `git diff`는 공통 조상 이후 내가 바꾼 커밋과 파일만 추려 준다. 여기서 특정 파일의 줄 단위 이력까지 내려가야 할 때는 `git blame`과 `git log -p`로 변경 출처를 확인한다.


다만 Git 내부의 커밋, 트리, 블롭(blob) 저장 구조가 실제 `git diff` 출력과 이어지는 원리는 이 글에서 다루지 않았다. 이 내부 저장 구조와 함께, 여러 사람이 같은 줄을 고쳤을 때 생기는 충돌을 병합 전략에 따라 어떻게 해결하는지는 다음 글의 주제로 남긴다.
