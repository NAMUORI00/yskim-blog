원격 서버에 접속할 때 만나는 오류는 겉보기에 비슷해 보여도 실제 원인이 발생한 단계는 서로 다르다. 예를 들어 같은 서버 주소인 `192.168.1.50`이라도 포트 `22`는 SSH 접속을 받고 포트 `80`은 웹 요청을 받는다. VPN을 껐을 때 아예 연결이 되지 않는 현상과, 연결은 되었지만 `403 Forbidden`이 반환되는 현상도 서로 다른 단계에서 일어난 일이다. 도메인 이름을 찾는 과정부터 패킷이 이동하는 경로, 포트를 통한 프로세스 연결, 연결 이후의 권한 검사까지 단계별로 나누어 보면 오류 메시지가 가리키는 위치를 좁힐 수 있다.


## 도메인 이름을 IP 주소로 바꾸는 DNS


터미널에 `ssh dev.example.com`을 입력하면 운영체제는 먼저 `dev.example.com`이라는 도메인 이름을 숫자로 된 IP 주소로 바꿔야 한다. 이 변환을 맡는 시스템이 **DNS**(Domain Name System)다.


클라이언트 운영체제는 로컬에 설정된 DNS **리졸버**(resolver)에 질의를 보낸다. 리졸버는 이전에 찾아 둔 결과가 캐시에 남아 있으면 그 값을 바로 돌려준다. 캐시에 답이 없으면 루트 네임서버, `.com` 네임서버, `example.com`의 권한 네임서버 순서로 질의를 이어 가며 최종 IP 주소를 받아 온다. 이때 클라이언트가 리졸버에게 최종 답을 달라고 요청하는 방식을 재귀 질의라고 부르고, 리졸버가 각 권한 서버의 안내를 따라가며 차례로 물어보는 과정은 보통 반복 질의로 구분한다([RFC 1035 — Domain Names: Implementation and Specification](https://datatracker.ietf.org/doc/html/rfc1035)).


![클라이언트가 DNS 리졸버에 dev.example.com의 재귀 질의를 보내고, 리졸버가 루트, .com, example.com 네임서버에 반복 질의해 10.0.1.50 주소를 받아 오는 흐름도](/images/notion/tech-k36/image-1.png)


그림 1. 도메인 이름을 IP 주소로 바꾸는 DNS의 재귀 질의와 반복 질의 개념도.


이 변환 결과는 `nslookup dev.example.com`이나 `dig dev.example.com` 명령으로 직접 확인할 수 있다.


```plain text
$ dig dev.example.com +short
10.0.1.50
```


도메인 이름을 잘못 입력했거나 네임서버에 장애가 생겼을 때, 또는 네트워크가 DNS 요청을 차단했을 때는 이 단계가 실패한다. 이미 캐시에 유효한 주소가 남아 있거나 IP 주소를 직접 입력해 접속하는 경우가 아니라면, 이름을 주소로 바꾸지 못해 새 연결을 시작할 수 없다. "호스트를 찾을 수 없습니다"와 같은 오류 메시지는 대부분 이 단계에서 나온다.


## 기계와 서비스를 각각 지정하는 IP 주소와 포트


DNS를 통해 `10.0.1.50`이라는 IP 주소를 얻었다면 요청을 보낼 목적지 주소가 정해진 셈이다. IP 주소는 네트워크 계층에서 특정 네트워크 인터페이스나 논리적인 접속 지점을 가리킨다. 물리적인 컴퓨터 한 대가 여러 IP 주소를 쓰기도 하고, 반대로 대표 주소 하나 뒤에 여러 기계가 묶여 있기도 하다([RFC 791 — Internet Protocol](https://datatracker.ietf.org/doc/html/rfc791)).


하지만 IP 주소만으로는 그 기계 안에서 돌아가는 여러 프로그램 가운데 어느 것과 통신할지 알 수 없다. 서버 한 대에서 원격 셸, 웹 서버, 데이터베이스가 동시에 실행될 수 있기 때문이다. 이때 어떤 서비스 프로세스에 연결할지 구분하는 값이 **포트**(port) 번호다.


| 포트   | 서비스        | 용도        |
| ---- | ---------- | --------- |
| 22   | SSH        | 원격 셸 접속   |
| 80   | HTTP       | 웹 서버(평문)  |
| 443  | HTTPS      | 웹 서버(암호화) |
| 5432 | PostgreSQL | 데이터베이스    |


포트 번호는 0부터 65535까지의 정수를 쓴다. 그중 0부터 1023까지는 잘 알려진 포트(well-known ports)로 지정되어 있어 프로세스가 이 번호를 점유하려면 운영체제의 관리 권한이 필요한 경우가 많다. 1024 이상의 번호는 일반 사용자 프로세스도 자유롭게 열어 두고 연결을 기다릴 수 있다.


![클라이언트 요청이 서버 192.168.1.50의 포트 22(SSH), 포트 80(HTTP), 포트 443(HTTPS), 포트 5432(PostgreSQL)로 각각 연결되는 개념도](/images/notion/tech-k36/image-2.png)


그림 2. 단일 IP 주소(192.168.1.50)에서 포트 번호에 따라 각 서비스 프로세스로 연결이 분기되는 구조.


따라서 접속 대상을 `192.168.1.50:5432`라고 적으면 `192.168.1.50` 주소의 기계에서 `5432`번 포트를 열고 대기 중인 프로세스에 연결하라는 뜻이 된다. 같은 IP 주소로 요청을 보내더라도 포트 번호에 따라 전혀 다른 서비스가 응답하는 이유가 여기에 있다.


## 사설 네트워크와 VPN을 거치는 라우팅 경로


목적지 IP 주소와 포트 번호를 알더라도 패킷이 그곳까지 도달할 수 있는 네트워크 경로가 열려 있어야 한다. 클라이언트가 보낸 패킷은 여러 라우터를 거쳐 목적지로 이동하며, 각 라우터는 자신이 가진 라우팅 테이블을 보고 패킷을 다음 라우터로 넘긴다.


이 과정에서 `10.0.x.x`나 `192.168.x.x` 대역의 사설 IP 주소는 다루는 방식이 다르다. 사설 주소는 기관이나 가정 같은 내부 네트워크 안에서만 유효한 주소다. 내부 라우터로 서로 연결된 사설 네트워크 사이에서는 이 주소로 바로 통신할 수 있지만, 공용 인터넷에서는 사설 주소로 패킷을 바로 전달하지 않는다. 따라서 외부 네트워크에서 사설 IP를 가진 서버에 접근하려면 별도의 연결 경로를 만들어야 한다.


**VPN**(Virtual Private Network)은 공용 인터넷 위에 암호화된 가상의 터널을 뚫어, 외부에 있는 클라이언트를 내부 네트워크에 들어와 있는 것처럼 이어 준다. 만약 VPN을 켜면 접속이 잘 되다가 VPN을 끄자마자 시간 초과(timeout)가 난다면, VPN 유무에 따라 라우팅 경로나 DNS 응답, 혹은 방화벽의 접근 정책이 달라졌을 가능성이 크다. 이 가운데 어느 요소가 영향을 주었는지는 VPN을 켜기 전과 후의 네트워크 설정을 비교해 봐야 정확히 좁힐 수 있다.


![DNS 리졸버에서 10.0.1.50을 얻은 뒤 공용 인터넷 경로는 사설 목적지에 도달하지 못해 연결 시간 초과가 나고, VPN 터널 경로는 VPN 게이트웨이를 거쳐 서버 10.0.1.50의 포트 22 SSH에 도달하는 흐름도](/images/notion/tech-k36/image-3.png)


그림 3. 외부에서 사설 IP 서버(10.0.1.50)에 접근할 때 공용 인터넷 경로와 VPN 터널 경로의 연결 결과 비교.


패킷이 실제로 어떤 경로를 따라 이동하는지는 `traceroute`(Windows에서는 `tracert`) 명령으로 살펴볼 수 있다. 이 명령은 목적지까지 거치는 중간 경유지(홉)를 순서대로 보여 주므로 VPN 연결 전후의 경로 차이를 비교할 때 유용하다. 다만 중간 장치가 응답하지 않거나 VPN 터널 내부 구간이 한 번에 묶여 보일 수 있어, 모든 경유지가 빠짐없이 드러나지는 않는다.


## 연결, 인증, 서비스 응답 단계의 오류 구분


라우팅 경로를 따라 목적지 서버에 닿은 뒤에도 실제 데이터를 주고받기까지는 몇 단계를 더 거친다. 이 과정을 TCP 포트 연결(connection), 신원을 확인하는 인증(authentication), 애플리케이션이 결과를 돌려주는 서비스 응답(service response)으로 나누어 보면 각 오류 메시지가 어느 단계에서 멈춘 것인지 가려낼 수 있다.


![접속 시도 후 DNS 해석 실패 시 호스트를 찾을 수 없음, 포트 연결 실패 시 Connection refused 또는 timed out, 인증과 접근 정책 실패 시 401 또는 403 오류가 발생하고 모두 통과하면 서비스 응답을 수신하는 흐름도](/images/notion/tech-k36/image-4.png)


그림 4. DNS 해석, 포트 연결, 인증과 접근 정책 검사 단계에서 실패했을 때 나타나는 오류 메시지 구분.


먼저 `Connection refused`와 `Connection timed out`은 둘 다 TCP 연결 단계에서 발생하지만 뜻하는 바가 다르다. `Connection refused`는 패킷이 목적지까지는 도착했으나 해당 포트에서 대기 중인 프로세스가 없거나 방화벽이 거절 응답을 명시적으로 돌려보냈을 때 나타난다. 반면 `Connection timed out`은 정해진 시간 안에 아무런 응답도 받지 못했다는 뜻이다. 라우팅 경로가 잘못되었거나 방화벽이 패킷을 응답 없이 버렸을 때(DROP), 혹은 서버에서 돌아오는 경로에 장애가 있거나 서버가 과부하 상태일 때도 같은 메시지가 나온다.


이와 달리 HTTP 요청에서 `401 Unauthorized`나 `403 Forbidden`을 받았다면 DNS 변환과 라우팅, TCP 포트 연결까지는 이미 성공한 상태다. 어떤 HTTP 응답자와 통신은 이루어졌지만, 요청에 필요한 인증 정보가 빠졌거나(`401`) 해당 자원에 접근할 권한이 부족해(`403`) 거절당한 것이다. 다만 이 응답을 돌려준 주체가 최종 원본 서버가 아니라 앞단에 놓인 프록시나 게이트웨이일 수도 있으므로 어느 지점이 응답했는지 함께 확인해야 한다. 마찬가지로 SSH 접속에서 나타나는 키 인증 실패도 네트워크 연결은 끝난 뒤 SSH 프로토콜의 인증 단계에서 거절된 경우다.


## 연결 단계 요약과 다음 질문


원격 접속은 도메인 이름을 IP 주소로 바꾸고, 라우팅 경로를 따라 목적지 기계에 도달한 뒤, 지정된 포트로 프로세스와 연결을 맺고 인증을 거쳐 서비스 응답을 받는 순서로 진행된다. 접속 오류가 발생했을 때 어느 단계까지는 통과했고 어디서 멈췄는지를 먼저 구분하면, 네트워크 경로를 살펴봐야 할지 서버의 프로세스와 권한 설정을 봐야 할지 점검 범위를 바로 좁힐 수 있다.


HTTPS의 TLS 핸드셰이크와 인증서 검증은 다음 주제로 남겼다. `certificate verify failed`나 `ERR_CERT_AUTHORITY_INVALID` 같은 인증서 오류를 TCP 연결 이후 어느 단계에 놓을지는 이어서 살펴볼 수 있다.
