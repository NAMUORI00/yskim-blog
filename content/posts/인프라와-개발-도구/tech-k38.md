두 기기에서 파일을 함께 다룰 때 최신 상태를 똑같이 맞추는 일과 이전 상태를 되살리는 일은 조건이 다르다. 한 기기에서 지운 파일이 다른 기기에서도 함께 지워지면 두 기기의 현재 상태는 같아진다. 하지만 삭제하기 전 내용을 다시 복원할 수 있는지는 별개의 문제다.


최신 파일을 여러 기기에서 이어서 편집하려면 기기 사이의 현재 상태를 똑같이 맞추는 **동기화**가 필요하다. 반면 실수나 장애가 났을 때 이전 내용을 되돌리려면 특정 시점의 복사본을 보관하는 **백업**이나 바뀐 과정을 되짚는 **변경 이력** 관리가 필요하다. 이 글에서는 `rsync`와 Syncthing을 예로 들어 동시 수정과 파일 삭제가 처리되는 방식과 복원 조건을 비교한다.


## 단방향 복사와 양방향 동기화


동기화와 백업의 차이를 이해하려면 먼저 기기 사이에 파일을 옮기는 방식을 단방향 복사와 양방향 동기화로 나누어 봐야 한다. 단방향 복사는 원본을 유지하면서 대상 경로에 내용을 한쪽으로만 복제하는 작업이다.


```bash
rsync -avz ./notes/ server:/backup/notes/
```


단방향 복사에 자주 쓰는 **rsync** 명령은 지금 작업하는 로컬 기기의 `notes/` 디렉터리를 서버의 `/backup/notes/`로 복사한다. 반대로 서버에서 바뀐 내용을 로컬 기기로 가져오지는 않으므로 전달 방향이 한쪽으로 고정된다. `rsync`는 원본과 대상의 파일 크기, 수정 시각을 비교해 바뀐 파일만 전송한다. 네트워크로 연결된 다른 기기에 보내는 원격 전송에서는 대상에 이미 있는 파일과의 차이를 활용해 전송량을 줄일 수 있다. 다만 같은 기기 안에서 복사하는 로컬 복사나 파일 전체를 보내는 `whole-file` 옵션 등에서는 동작이 달라진다.


양방향 동기화는 한쪽으로만 보내는 복사와 달리 양쪽 기기의 변경을 모두 반영한다. 노트북과 데스크톱을 오가며 작업할 때 한쪽에서 고친 내용이 다른 쪽에도 전달된다. 그런데 노트북에서 `report.md`를 수정하는 같은 시간에 데스크톱에서도 같은 파일의 같은 부분을 고치면 양쪽 변경을 그대로 합치기 어렵다.

## 동시 수정 충돌과 파일 보존


앞 절에서 본 것처럼 두 기기에서 같은 파일을 동시에 수정해 실제 내용이 달라지면, 양방향 동기화 도구는 이를 **충돌**(conflict)로 처리한다. 노트북에서 14:00에 `report.md`를 수정하고, 데스크톱에서는 14:02에 같은 파일을 수정한 상황을 가정한다. 이 상태에서 양방향 동기화 도구인 **Syncthing**으로 동기화가 일어나면 두 버전은 다음과 같이 정리된다.

- `report.md`: 수정 시각이 더 늦은 데스크톱 버전(14:02)으로 유지
- `report.sync-conflict-20260915-140000-ABCDE.md`: 수정 시각이 앞선 노트북 버전(14:00)을 새 이름으로 보존

[Syncthing 공식 문서](https://docs.syncthing.net/users/syncing.html)에 따르면, Syncthing은 충돌이 생겼을 때 두 버전 가운데 수정 시각이 더 오래된 쪽의 파일 이름을 바꿔서 보존한다. 이렇게 이름이 바뀐 충돌 파일도 일반 파일처럼 다른 기기에 그대로 전파된다. 다만 파일 안의 다른 내용을 알아서 하나로 합치는 자동 병합은 되지 않으므로, 두 버전을 직접 읽고 남길 내용을 고르는 단계가 남는다.


![노트북의 14:00 수정본과 데스크톱의 14:02 수정본이 동기화될 때 데스크톱 버전은 원래 이름으로 유지되고 노트북 버전은 sync-conflict 파일로 보존되는 흐름도](/images/notion/tech-k38/image-2.png)

## 파일 삭제 전파와 이전 버전 보관


파일을 수정할 때뿐 아니라 삭제할 때도 동기화와 백업은 동작 조건이 다르다. 삭제를 전파하는 양방향 동기화 설정에서는 노트북에서 지운 파일이 다른 기기에서도 함께 지워질 수 있다. 반면 앞의 `rsync` 예제는 대상에만 남은 파일을 지우는 `--delete` 옵션을 쓰지 않아 원본에서 지워진 파일을 대상에서 자동으로 삭제하지 않는다. 현재 상태를 맞추는 동기화와 복사본을 남기는 백업의 차이가 여기서 드러난다.


지워진 파일을 복원하려면 삭제 시점 이전의 복사본이 백업에 남아 있어야 한다. Syncthing의 파일 버전 관리 기능은 이 문제를 부분적으로만 해결한다. [Syncthing 버전 관리 문서](https://docs.syncthing.net/users/versioning.html)에 따르면, 다른 기기에서 전달된 변경이 로컬 기기의 파일을 대체할 때 이전 버전을 `.stversions` 폴더에 보관한다.


그러나 이 버전 관리 기능은 로컬 기기에서 직접 삭제한 파일에는 적용되지 않는다. 다른 기기에서 넘어온 변경으로부터는 이전 파일을 보호하지만, 작업하던 기기에서 바로 지운 파일까지 그 기기의 `.stversions`에 남겨 두지는 않는다. 동기화 도구의 버전 관리와 전용 백업 도구의 보호 범위는 이처럼 다르다.


![다른 기기에서 변경이 전달될 때는 로컬 .stversions에 이전 버전이 보관되지만 로컬 기기에서 직접 삭제할 때는 로컬 .stversions에 보관되지 않는 차이를 나타낸 도식](/images/notion/tech-k38/image-3.png)

## 보관 방식별 복원 경로와 조건


이처럼 도구마다 파일을 보호하는 범위가 다르기 때문에, 이전 파일을 되살릴 때는 어떤 방식으로 기록을 남겨 두었는지에 따라 찾아가는 복원 경로가 달라진다. 작업 도중 "어제 버전의 `report.md`로 돌아가고 싶다"는 상황이 생겼을 때를 생각해 보면 방식별 차이가 선명해진다. 여기에 특정 시점의 상태를 통째로 저장해 두는 **스냅샷** 백업과 변경 이력을 기록하는 버전 관리 도구 **Git**을 함께 비교할 수 있다. Git은 바뀐 내용을 **커밋**(commit)이라는 저장 단위로 묶어 기록할 때마다 그 시점의 상태를 남긴다.


| 방식                  | 복원 가능 여부              | 조건                  |
| ------------------- | --------------------- | ------------------- |
| 단방향 복사 (rsync)      | 마지막 복사본만 있음           | 이전 버전은 덮어써서 사라짐     |
| 양방향 동기화 (Syncthing) | 버전 관리, 충돌 사본 등에 따라 다름 | 복원할 사본이 실제 남아 있어야 함 |
| 스냅샷 백업              | 날짜별 복원 가능             | 백업 주기에 따라 빈 시간대 존재  |
| 버전 관리 (Git)         | 커밋 단위로 복원             | 커밋하지 않은 변경은 기록 없음   |

## 결론


변경 사항을 기기 간에 전파하는 동기화와 과거 상태를 시점별로 보관하는 백업 및 변경 이력 관리는 서로 다른 조건에서 동작한다. 동기화 도구로 이전 파일을 되살릴 수 있는지는 삭제나 덮어쓰기 전 버전의 보관 여부와 보관 기간에 달려 있다. 반대로 백업만으로는 여러 기기에서 작업한 최신 편집 내용이 자동으로 반영되지 않는다.


이번 글에서는 파일 단위의 충돌 보존과 방식별 복원 조건을 확인했지만, 작업 빈도와 백업 주기를 비교해 복원 시점의 간격을 정하는 방법은 아직 다루지 않았다. 다음에는 파일 형식에 따라 변경 내용을 자동으로 병합할 수 있는 조건과, 백업과 백업 사이에 잃을 수 있는 변경량을 이어서 다루려 한다.
