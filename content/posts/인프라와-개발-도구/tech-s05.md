오래전에 포크(fork)한 저장소에서 내가 실제로 고친 범위가 어디까지인지 확인해야 할 때가 있다. 이때 현재 포크 상태를 최신 원본(upstream)과 바로 비교하면, 포크에서 수정한 내용과 그동안 원본에 새로 쌓인 변경이 한꺼번에 섞여 나온다. 변경된 줄 수를 세거나 수정 내역을 정리하기 전에 비교 기준이 되는 원본 버전부터 먼저 고정해야 하는 이유다.


## 두 끝점 비교와 공통 조상 비교


비교 기준에 따라 결과가 어떻게 달라지는지 작은 커밋 이력 예제로 살펴보자. 공통 조상 커밋인 `O`에서 갈라져 나온 뒤, 원본 저장소는 `U1`, `U2` 순서로 진행하고 개인 포크 브랜치는 `F1`, `F2` 순서로 진행했다고 가정한다.


![공통 조상 O에서 갈라진 원본 끝점 U2와 포크 끝점 F2 사이에서 현재 상태 차이와 분기 후 반영 범위를 비교하는 커밋 그래프](/images/notion/tech-s05/image-1.png)


그림 1. 비교 기준점에 따라 달라지는 Git diff의 확인 범위 개념도. 출처: Git diff, merge-base 개념을 바탕으로 직접 구성.


여기서 두 현재 끝점인 `U2`와 `F2`를 비교하면 오늘 시점에서 두 브랜치의 파일 상태가 어떻게 다른지 보게 된다. 반면 공통 조상 `O`와 포크 끝점 `F2`를 비교하면 분기 이후 개인 브랜치 쪽에 반영된 변경만 추려 볼 수 있다. 오늘의 원본과 차이를 맞춰 보는 목적과 분기 이후 포크에서 일어난 변화를 읽는 목적은 서로 다르다. 물론 `O`와 `F2` 사이의 차이가 곧바로 개인이 직접 작성한 코드라는 증거는 아니지만, 적어도 검토해야 할 범위는 분명하게 좁혀 준다.


이 두 가지 비교는 Git의 두 커밋 지정 방식과 세 점(`...`) 표기로 나누어 실행할 수 있다. 아래 명령에서 `upstream/main`은 예시 참조 이름이므로 실제 저장소에 등록된 원본 참조 이름으로 바꿔서 읽어야 한다. 비교하기 전에 원격 참조가 언제 마지막으로 갱신되었는지도 먼저 확인해야 한다. 여기서는 상태를 변경하지 않는 조회 명령만 적었다.


```bash
git diff --name-status upstream/main HEAD
git diff --stat upstream/main HEAD
git diff upstream/main...HEAD -- path/to/file
```


앞의 두 명령은 `upstream/main`과 `HEAD`라는 두 끝점의 현재 상태 차이를 보여 준다. 세 번째 명령은 세 점 표기를 사용해 두 참조의 공통 조상(merge-base)부터 `HEAD`까지의 차이만 계산하며, 결과를 특정 파일(`path/to/file`)로 한정한다.


명령 결과를 읽을 때 주의할 점도 있다. `--stat` 옵션은 변경이 발생한 파일만 요약해 출력하므로, 수정되지 않은 파일을 '0줄 변경 행'으로 찾아내려는 방식은 통하지 않는다. 또한 변경된 줄 수만 보고 단순 설정 변경인지 핵심 로직 변경인지 구분할 수도 없다. 명령별 상세 동작은 [git diff 문서](https://git-scm.com/docs/git-diff)와 [merge-base 문서](https://git-scm.com/docs/git-merge-base)에서 확인할 수 있다.


## 변경 파일 안의 출처와 역할 구분


공통 조상을 기준으로 비교 범위를 좁혔다면, 그다음에는 차이로 잡힌 내용의 성격을 나눌 차례다. 검토할 때는 원본과 그대로 일치하는 구간, 설정 차이, 소스 코드 변경, 도구가 만든 생성 파일로 나누어 보면 파악하기 수월하다. 다만 파일 하나에 네 가지 분류 중 하나만 기계적으로 붙이기보다, 한 파일 안에 섞여 있는 변경을 구간별로 쪼개어 읽는 편이 정확했다.


이 과정에서 설정 변경을 소스 코드 변경보다 늘 안전하거나 병합하기 쉬운 것으로 취급하지는 않았다. 설정 한 줄이 기능이나 보안 조건을 크게 바꾸기도 하기 때문이다. 예를 들어 조건부 컴파일 매크로 값 하나로 특정 코드 블록이 빌드에서 통째로 빠진다면, 함수 본문 코드를 한 글자도 고치지 않았더라도 실제 실행 동작은 완전히 달라진다.


원본 저장소에 없던 새 파일이 나타났다고 해서 곧바로 직접 작성한 코드로 분류할 수도 없다. 외부 라이브러리에서 가져온 코드이거나, 원본의 다른 버전에서 복사해 온 파일이거나, 빌드 도구가 자동으로 생성한 결과물일 가능성이 있기 때문이다. 바이너리 파일 역시 파일 확장자만 보지 않고 빌드 기록과 해시값을 대조해 빌드 출처를 확인한다. 외부 배포용 파일이나 테스트 자료를 의도적으로 저장소에 넣어 관리하는 경우도 있으므로, 파일의 출처와 포함 목적부터 먼저 따져 봐야 한다.


![차이가 난 파일에서 비교 기준을 먼저 확인한 뒤 외부 코드, 직접 수정한 코드, 생성 및 배포 파일로 나누어 기록하는 순서도](/images/notion/tech-s05/image-2.png)


그림 2. diff 결과에서 비교 기준을 확인하고 파일 및 코드 구간별 출처를 분류하는 검토 흐름. 출처: 본문의 검토 예제로 직접 구성.


## 실제 헤더 파일에서 읽히는 단서와 이력 비교의 경계


파일 하나를 열람해 얻을 수 있는 단서와 별도 이력 비교가 필요한 영역을 구분하기 위해, 개인 포크 저장소인 `cheat-engine-custom`의 [외부 코드의 자료형과 설정 정의](https://github.com/NAMUORI00/cheat-engine-custom/blob/8088992c054bf16a34ebb9a371fa856f018168ae/dbvm/vmm/config.h) 파일(`dbvm/vmm/config.h`)을 예로 들어 보자. 해당 링크는 저장소 접근 권한이 있어야 열람할 수 있다.


이 헤더 파일의 앞부분을 읽으면 diStorm 프로젝트의 저작권 및 라이선스 안내문이 적혀 있고, 그 아래로 정수 자료형을 직접 선언하는 조건부 컴파일 구간이 나온다. 즉 이 파일 하나만 읽어도 원본 프로젝트 밖에서 유래한 외부 코드가 포함되어 있다는 사실과 빌드 조건에 따라 분기되는 구간이 있다는 점을 알 수 있다.


하지만 파일 앞부분의 저작권 안내문은 코드의 유래를 알려 주는 단서일 뿐이다. 이 파일이 특정 시점의 원본 커밋과 바이트 단위로 완전히 똑같은지, 아니면 포크 이후 일부가 수정되었는지는 원본 이력과 직접 대조해 봐야 안다. 마찬가지로 파일 안의 매크로 이름이나 README에 적힌 원본 안내 문구만 보고 개인 패치가 들어갔는지, 전체 수정 범위가 어디까지인지 단정할 수는 없다.


| 확인한 자료     | 현재 파일 열람만으로 알 수 있는 내용        | 이력 및 환경 비교로 추가 확인할 내용  |
| ---------- | ---------------------------- | ---------------------- |
| 헤더의 출처 안내  | 외부 프로젝트에서 유래한 코드가 포함되어 있음    | 기준이 된 원본 버전과 실제 수정 구간  |
| 조건부 자료형 선언 | 빌드 설정에 따라 선택적으로 컴파일되는 구간이 있음 | 실제로 사용 중인 빌드 설정과 실행 영향 |
| 포크 저장소의 파일 | 현재 개인 저장소 트리에 해당 파일이 존재함     | 직접 작성, 원본 복사, 도구 생성 여부 |


위 표는 원본과 diff를 검토할 때 현재 파일을 읽어서 바로 말할 수 있는 사실과, 커밋 이력이나 빌드 설정을 대조해야만 확인할 수 있는 영역을 구분해 둔 기록이다.


## 변경 이유 확인과 새 원본 재적용 검증


코드가 바뀐 구간을 찾았더라도 '조건문이 추가되었다'는 사실 자체와 '당시 왜 그 조건문을 추가했는가'라는 변경 이유는 나누어 읽어야 한다. 커밋 메시지, 이슈 기록, 테스트 코드, 패치 설명에 변경 이유가 남아 있다면 당시 선택의 근거로 연결할 수 있다. 반대로 별도 기록이 남아 있지 않은 구간은 현재 코드를 읽고 예상할 수 있는 동작 효과까지만 해석 범위로 삼는다.


마지막으로 포크의 수정 사항을 새로운 원본 버전에 다시 적용할 때는 텍스트 병합 성공 여부 너머의 호환성을 봐야 한다. 포크에서 전혀 건드리지 않아 예전 원본과 똑같은 파일이라도, 새 원본에서 함수 인자나 자료구조 같은 인터페이스가 바뀌었으면 주변의 포크 수정 코드와 맞물려 문제를 일으킬 수 있다. Git의 자동 병합이 충돌 없이 끝났더라도 빌드 여부와 실행 호환성을 따로 검증해야 하는 이유가 여기에 있다.


![새 원본의 인터페이스 변경과 포크의 기존 수정 코드가 Git 자동 병합을 통과한 뒤에도 호환성 충돌을 확인하고 빌드 및 실패 조건 재현을 거치는 다이어그램](/images/notion/tech-s05/image-3.png)


그림 3. 포크 수정 사항을 새 원본에 다시 적용할 때 자동 병합 이후 빌드와 실행 재현까지 확인하는 흐름.


그래서 후속 확인 작업으로는 개인 포크의 변경 사항을 새 원본에 적용한 뒤, 원래 다루던 입력값과 과거의 실패 조건을 다시 넣어 동작을 재현해 보는 절차를 남겨 두었다. 변경 전후의 실행 기록까지 확보되면 포크에서 실제로 수정한 범위와 그 수정이 만든 효과를 빈틈없이 연결해 설명할 수 있다.
