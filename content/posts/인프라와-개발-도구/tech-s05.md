## 저장소 소유와 코드의 출처


포크의 수정 범위를 읽기 위해 Git 이력의 두 끝점과 공통 기준을 나누었다. 최신 원본과 오래된 포크의 차이에는 개인 수정과 아직 가져오지 않은 원본 변경이 함께 나타난다. 비교 시점을 정하는 작업부터 정리했다.


변경 줄 수를 세기 전에 기준으로 삼을 원본 버전을 골랐다. 오늘의 upstream과 비교하는 목적과 분기 이후 개인 브랜치의 변화를 읽는 목적은 다르기 때문이다.


## 두 끝점과 갈라진 지점


작은 이력 예제를 놓았다. 공통 커밋 O에서 upstream은 U1, U2로 진행했고, 개인 브랜치는 F1, F2로 진행했다고 하자. U2와 F2의 파일을 비교하면 현재 두 상태의 차이를 본다. O와 F2를 비교하면 갈라진 이후 개인 브랜치 쪽에 반영된 차이를 본다. 이 차이가 곧 개인 저작의 증거는 아니지만, 읽어야 할 범위는 좁아진다.


![S05-01.png](/images/notion/tech-s05/image-1.png)


그림 1. 비교 기준에 따라 diff가 답하는 질문이 달라지는 설명용 커밋 그래프.  출처: Git diff, merge-base 개념을 바탕으로 직접 구성.


Git의 두 커밋 비교와 세 점 표기 차이를 알면 이 구분을 확인할 수 있다. 아래 `upstream/main`은 예시 참조 이름이므로 실제 저장소에서 존재하는 원본 참조로 바꿔 읽어야 한다. 원격 참조의 갱신 시점도 확인해야 하며, 여기서는 읽기 명령만 적었다.


```bash
git diff --name-status upstream/main HEAD
git diff --stat upstream/main HEAD
git diff upstream/main...HEAD -- path/to/file
```


첫 두 명령은 두 끝점의 상태 차이를 보여 준다. 마지막 명령은 두 참조의 공통 조상에서 `HEAD`까지의 차이를 해당 파일에 한정한다. `--stat`에는 보통 변경된 파일이 나오므로, 목록에 없는 파일을 “0줄 변경 행”에서 찾는 방식은 맞지 않는다.


줄 수만으로 설정과 로직 변경을 구분할 수도 없다. [git diff 문서](https://git-scm.com/docs/git-diff), [merge-base 문서](https://git-scm.com/docs/git-merge-base).


## 파일 안의 변경 유형


검토할 때는 원본과 일치한 범위, 설정 차이, 소스 변경, 생성 파일을 구분하면 도움이 됐다. 다만 파일마다 네 종류 중 하나를 강제로 붙이기보다, 파일 내부에서 섞여 있는 변경을 나눠 보는 편이 정확했다.


설정 한 줄도 기능과 보안 조건을 크게 바꿀 수 있다. 예를 들어 조건부 컴파일 값 하나로 특정 코드가 빌드에서 제외된다면 함수 본문이 그대로여도 결과 동작은 달라진다. 설정 변경은 늘 안전하고 병합이 쉽다는 서열을 만들지는 않았다.


원본에 없는 파일도 바로 직접 작성으로 분류할 수 없다. 다른 라이브러리에서 가져왔거나, 원본의 다른 버전에서 복사했거나, 도구가 생성했을 수 있다. 바이너리의 빌드 출처는 확장자에 더해 빌드 기록과 해시 등으로 확인한다. 외부 배포 파일이나 테스트 자료로 의도적으로 관리할 수도 있어서 출처와 목적을 먼저 확인해야 한다.

## 실제 헤더에서 읽을 수 있는 것


cheat-engine-custom의 [외부 코드의 자료형과 설정 정의](https://github.com/NAMUORI00/cheat-engine-custom/blob/8088992c054bf16a34ebb9a371fa856f018168ae/dbvm/vmm/config.h)를 읽으면 파일 앞부분에 diStorm 저작권과 라이선스 안내가 있고, 정수 자료형을 직접 선언하는 조건부 컴파일 구간이 보인다. 저장소 접근 권한이 필요하다. 이 파일만으로도 다른 프로젝트에서 유래한 코드가 포함됐다는 단서를 얻을 수 있다.


저작권 안내는 코드의 유래를 읽는 단서다. 특정 upstream 커밋과 바이트 단위로 같은지는 별도 비교가 필요하다. 매크로 이름이나 README의 원본 안내만으로 개인 패치 여부와 전체 수정 범위를 판단하지 않았다.


| 확인한 자료     | 지금 말할 수 있는 내용          | 추가로 필요한 확인          |
| ---------- | ---------------------- | ------------------- |
| 헤더의 출처 안내  | 외부 코드의 유래를 설명하는 기록이 있음 | 해당 버전과 실제 변경 구간     |
| 조건부 자료형 선언 | 빌드 조건에 따라 선택되는 코드가 있음  | 사용 중인 빌드 설정과 영향     |
| 개인 저장소의 파일 | 현재 저장소에 포함되어 있음        | 직접 작성, 원본 복사, 생성 여부 |


원본과의 diff를 검토할 때 사용할 항목을 정리한 표다. 현재 파일 읽기로 알 수 있는 내용과, 이력 비교가 있어야 알 수 있는 내용을 나눈 기록이다.


## 변경 이유와 재적용 기록


조건문이 추가된 사실과 당시 변경 이유도 나누어 읽었다. 커밋 메시지, 이슈, 테스트, 패치 설명에 남은 이유는 당시 선택의 근거로 연결할 수 있다. 기록이 없는 부분은 현재 코드에서 예상되는 효과까지가 해석 범위다.


원본과 일치하는 파일도 이후 인터페이스 변경으로 주변 수정 코드와 충돌할 수 있다. 자동 병합 성공 이후 빌드와 실행 호환성을 따로 확인하는 이유다.


후속 확인 대상으로는 개인 변경을 새 원본에 적용한 뒤 원래 입력과 실패 조건을 재현하는 과정을 남겼다. 변경 전후의 동작 기록이 있으면 수정 범위와 그 효과를 함께 설명할 수 있다.
