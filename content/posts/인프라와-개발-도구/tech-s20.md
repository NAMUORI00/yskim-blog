Notion의 글 하나와 그림 하나가 사이트로 반영되는 경로를 정리했다. 편집 원본의 저장, 웹 파일 생성, 이미지 배포를 각각 나누어 속성 조회부터 독자의 화면까지 따라갔다.


설명용 페이지에는 문단과 이미지를 하나씩 두었다. 페이지 속성, 본문 블록과 정적 빌드 개념을 바탕으로 소스의 변환 경로를 읽었다. 특정 배포의 성공 여부는 이번 확인 범위에 포함하지 않았다.


## 속성에 있는 제목과 본문에 있는 그림


Notion 데이터베이스의 글은 제목, 상태, 슬러그 같은 속성을 갖고, 실제 문단이나 이미지는 본문 블록에 들어간다. 제목 속성과 본문 블록은 각각 조회해야 한다. 블록 안에 자식 블록이 있으면 내려가서 읽어야 하고, 목록 조회에 다음 페이지가 남으면 그것도 이어 받아야 한다.


[Notion의 자식 블록 조회 문서](https://developers.notion.com/reference/get-block-children)는 자식 조회와 페이지네이션을 별도로 설명한다.


예를 들어 제목은 ‘검색 결과의 출처’, 슬러그는 source-trace라고 하자. 제목을 고쳐도 주소를 유지하고 싶다면 두 값을 분리할 이유가 생긴다. 반대로 슬러그를 바꾸면 이전 주소로 들어오는 링크를 어떻게 처리할지 결정해야 한다. 제목과 주소를 한 문자열로 취급하면 단순한 문장 수정이 링크 변경으로 이어질 수 있다.

## 첨부파일 주소와 보관 방식


Notion에서 호스팅하는 파일의 API 응답에는 만료 시간이 있는 URL이 포함된다. [파일 객체 문서](https://developers.notion.com/reference/file-object)는 이를 영구 주소처럼 캐시하지 말고 다시 조회하도록 안내한다.


외부 호스팅 파일 URL과도 구분해야 한다. external이라는 형식 자체가 외부 서버의 영구 가동까지 보장해 주지는 않는다.


임시 이미지 주소를 HTML에 남기는 방식과 파일을 사이트 자산으로 배치하는 방식을 비교했다. 후자는 본문 경로를 바꾸어 만료 주소 의존성을 줄일 수 있다. 대신 이미지 갱신과 저장 공간을 사이트에서 관리할 범위가 생긴다.


yskim-blog의 [글과 이미지 수집 처리](https://github.com/NAMUORI00/yskim-blog/blob/9dd7a2227d53f1f82fd5a539afce4c1bc35d653f/scripts/notion-content.mjs)는 이미지를 사이트에서 제공할 미디어 폴더에 저장하고 본문의 주소를 바꾼다.


다운로드 응답이 실패하면 예외를 발생시키며, 주소를 바꾼 뒤 임시 Notion URL이 남았는지도 검사한다. 이 코드는 이미지 확보와 주소 변환의 의도를 보여 준다. 모든 이미지 형식이 실제 브라우저에서 정상 표시됐다는 검증까지 대신하지는 않는다.


파일명도 확인할 부분이다. 같은 주소에 다른 이미지 내용이 배포되면 브라우저나 CDN의 캐시가 이전 내용을 보여 줄 수 있다. 내용 해시를 파일명에 넣거나 캐시 갱신 규칙을 정하는 방식이 있지만, 그 선택은 배포 구조와 함께 검토해야 한다. 이미지 응답이 200이라는 사실에 더해 실제 내용이 새 파일인지 확인할 이유가 여기에 있다.


## Ready, 가져오기 성공, 배포 성공의 차이


확인한 변환 코드의 기본 상태 필터는 Published다. 실행 옵션이나 환경 설정으로 바꿀 수 있으므로 항상 고정된 값이라고 말할 수는 없지만, 기본 동작에서는 Ready인 글이 출력 대상이 되지 않는다. 원고가 작성됐다는 상태와 공개할 글로 선택됐다는 상태를 구분할 수 있는 지점이다.


문장을 A에서 B로 바꾸고 Ready 상태를 유지하는 예제에서는 기본 필터가 B를 제외할 수 있다. Published 이후에도 새 수집, 빌드, 배포가 없다면 이전 HTML이 남는다. 저장 상태와 사이트 반영 상태를 따로 기록하는 이유다.

그림 2. 원문 저장부터 독자가 보는 응답까지 확인 위치를 구분한 그림. 출처: 직접 구성.


글 수와 수집 시각은 출력 작업을 추적하는 기록이다. 독자가 보는 버전까지 확인하려면 생성 본문과 배포 경로의 문장, 그림을 연결할 필요가 있다. 수집 기록만으로 배포 완료까지 판단하지 않았다.


수집 중 원문이 다시 수정되는 경우는 후속 확인 항목으로 남겼다. 조회 사이에 원문이 바뀔 수 있으면 수정 시각이나 해시로 수집 전후 변경을 감지하는 방식을 검토할 수 있다. 현재 코드에서 확인한 기능으로 서술하지는 않았다.


코드, 수식, 표, 캡션을 넣은 작은 페이지로 변환 전후를 비교하는 작업을 다음 범위로 두었다. 블록별 보존 결과를 남기면 지원 범위와 실패 조건을 구체적으로 확인할 수 있다.
